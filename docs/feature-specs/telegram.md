# Telegram Channel

<!-- This spec describes the current system capability. Updated through delta reconciliation. -->

## Overview

A grammY-based Telegram bot, shipped as the `telegram` extension, that receives text, media, and emoji-reaction updates from a single authorized chat, submits them to the conversation loop, and renders agent exchanges and background deliveries back as Telegram messages. It records the session that produced or received each message so that replying to a past message routes the new turn back to that conversation. It also registers agent-facing tools for sending files, reacting with emoji, pinning messages, and presenting inline-button prompts through the same bot instance.

The channel contract it implements (`start`/`respond`/`deliver`/`stop`) and the idle/immediate delivery gating are owned by the conversation loop — see [conversation-loop](conversation-loop.md). Background-originated text reaches `deliver()` through the notifications extension and other producers — see [notifications](notifications.md).

## User Stories

- As a user, I want to talk to Tachikoma from any Telegram client so that I am not tied to a terminal
- As a user, I want to send photos, voice messages, and documents so that the agent can work with my non-text content
- As a user, I want background notifications to arrive as a single push alert so that I am notified without being spammed per chunk
- As a user, I want a push notification when a response I've stepped away from finishes, so I know to come back — without a flicker on every quick reply while I'm still watching
- As a user, I want to answer the agent's structured prompts by tapping a button so that yes/no and multiple-choice answers do not require typing
- As a user, I want to react to a message with an emoji and have the agent see it so that I can give quick feedback without typing
- As a user, I want to reply to one of the agent's earlier messages and have my new message picked up by that conversation so that I can resume an older topic without re-explaining it

| R1 | The bot token is validated (`bot.init()` / `getMe`) before long polling starts; after init the channel registers every slash command in Telegram's command menu via `setMyCommands` — `new`, `queue`, `stop`, `checkpoint`, `back`, `rollback`, `skill`, `tasks`, and `reload` — each with a usage hint in its description (the argument-taking commands `new`/`queue`/`skill` show their argument form, e.g. "Start a new topic — `/new <first message>`"); a `setMyCommands` failure is logged as a warning and does not block startup. A typing indicator refreshes throughout, and the message finalizes when the stream ends; `error` events are sent immediately as `⚠️ Error: …` notices — a recoverable error sends just `⚠️ Error: <message>`, while a non-recoverable one appends a second paragraph: `This needs your attention — the next message won't recover on its own.` |

An entity larger than the limit is dropped (its text still renders, plain) rather than split |
| R6 | Messages are converted from the agent's GitHub-flavored markdown into a literal display string plus `MessageEntity[]` (via `markdown-it`) and sent with `parse_mode` omitted and the entities attached — so ordinary punctuation (`.`, `-`, `!`, `(`) is literal and can't trigger a parse failure. | R7 | All channel sends (`respond()` and `deliver()`) are serialized through a FIFO mutex so two send sequences never interleave their API calls, and a rejected task does not stall the queue |

| R9 | A bootstrap hook creates the media directory (`{dataDir}/media`) and prunes files older than 30 days |
| R10 | Media failures (file too large, download error) send an explanatory notice to the chat and leave the conversation usable |

| R12 | Each agent session registers five tools: `send_telegram_file`, `react_to_message`, `pin_message`, `unpin_message`, `send_message_with_buttons`; failures throw from `execute` |
| R13 | `send_telegram_file` resolves workspace-relative paths, requires an existing regular file under an allowed root (workspace, system temp dir, configured `extraFileRoots`), names the allowed roots on rejection, and auto-detects photo/audio/video/document from the extension |
| R14 | `pin_message` pins the in-flight response inline at its own `tool-start` (the moment the held response text is revealed and its message id is known) and returns that id, so a later turn can unpin that specific message with `unpin_message` (which needs the id). The audible pin delivers the turn's push (`pin_message` is a notifying tool, so the completion copy-delete is skipped and the message keeps its id through finalization). It always targets the response being produced, never a previous one; a pin on a turn that yields no response text throws `No message available to pin`; `react_to_message` defaults to the user's last inbound message and fails when no target message exists |
| R15 | `send_message_with_buttons` validates the layout (≥1 row, ≥1 button per row, non-empty labels, non-empty values, values ≤58 UTF-8 bytes, ≤100 buttons) and sends an inline keyboard whose `callback_data` encodes the value and the single-use flag; the prompt text is converted to a `MessageEntity[]` payload (R6) and sent alongside the keyboard, falling back to plain text on a render rejection so agent markdown in the prompt renders formatted rather than as raw syntax |
| R16 | Button taps are acknowledged immediately (before authorization), unpacked from the wire format, and routed as a framed inbound turn carrying the tapped value. The tapped button message is resolved to its branch: a tap on an earlier branch stamps `forcedBranchId` so the boundary forces a shift with context injection, while a tap on the live branch appends normally; an unrecorded target falls through to normal handling. Single-use taps remove the keyboard via a detached call whose failure never blocks routing |
| R17 | A `/stop` text message aborts the in-flight agent run instead of being submitted as a turn; it is acknowledged with `⏹ Stopped.` and the abort wires to the coordinator's exchange abort |
| R18 | An authorized emoji reaction is surfaced to the agent as an inbound turn that names the emoji(s) added and/or removed; unless the reaction targets the live branch's most recent message (already at the bottom of the conversation), the reacted-to message's text is recovered from its session-tree entry and prepended as a truncated `Reacted to:` quote so the agent knows which message the emoji targets (mirroring the reply quote, R21); a reaction update whose emoji set is unchanged is dropped |
| R19 | The channel records every message id it handles — inbound user messages and the bot's outbound replies — in the `channel_messages` table, mapping the message id to the trunk tree entry and branch it corresponds to (`messageId → { treeEntryId, branchId }`, keyed by channel and message id, re-pointed on conflict). The live leaf's `{ treeEntryId, branchId }` is the recency anchor: a referenced message whose routing matches it is the live branch's most recent message |
| R20 | When an inbound message (text, media, reaction, or button tap) targets a previously recorded message — via Telegram reply-to, the reacted-to message id, or the tapped button message — and that message resolves to a `{ treeEntryId, branchId }`, the turn carries `metadata.forcedBranchId` (with `forcedTreeEntryId`) so the boundary force-routes it to the owning branch (same live branch → append; an earlier branch → forced collapse + context injection); a target with no recorded routing is handled by kind per R25 rather than silently falling through |
| R21 | A reply to a message that carries text quotes a truncated form of that text as a `Replied to:` prefix on the turn so the agent sees what was replied to, unless the replied-to message is the live branch's most recent message (already live in the agent's context); routing metadata is set either way |
| R22 | `shutdownStatus(text)` renders shutdown-sequence progress on a single dedicated message: the first call sends it as an italic `_<text>_` message, subsequent calls edit that message in place; it is serialized through the send mutex and the final line is left visible in the chat. The coordinator calls it during teardown (see [conversation-loop](conversation-loop.md) R18/R20) because the streaming renderer that hosts normal `status()` lines no longer exists |
| R23 | On receipt of a submitted inbound text or media message (excluding `/stop`, which aborts), the channel fires a one-shot `typing` chat action immediately in its message handler — ahead of `runtime.submit()` (text) or the media download — so an indicator is visible before the coordinator's preparation work (inbox drain, inbound middleware, session open) runs, bridging the gap until `respond()`'s typing refresh loop takes over. During preparation (the window before streaming starts), `status()` lines surface on a single provisional lead-in message: the first creates it, subsequent lines edit it in place, and the typing indicator is refreshed alongside. When the response streams, `respond()` reclaims that message as the streaming message so the response text replaces it in place; if the exchange yields no text, the lead-in is deleted. Messages steered into or queued behind a live exchange skip preparation, so no lead-in is shown for them |
| R24 | Because Telegram edits never notify, `respond()` forces a push on completion of a streamed response: when `pushNotifications` is on and the streamed exchange lasted at least `pushNotificationMinSeconds` (default 10), it copies the finalized message within the same chat (a fresh send that notifies) and deletes the streamed original, so exactly one push fires on the final message. Under `pushNotifications` the streamed work-in-progress, the lead-in, and any overflow chunks are sent silently so the copy is the only push. The push is skipped for quick turns under the threshold (the user is assumed still watching — no flicker) and when a notifying tool (`send_telegram_file`, `pin_message`, `send_message_with_buttons`) already delivered a push during the turn. For a multi-message response only the final chunk is copied; reply routing records the copied message id (the streamed id when the push is skipped). A copy-API failure leaves the streamed message in place (delivered without a push) rather than losing it |
| R25 | When an inbound reply-to or reaction targets a message id that is not recorded, the channel surfaces it rather than silently mis-routing: a reaction is dropped with a user-visible notice that the conversation couldn't be found (its meaning is bound to the referenced message, so submitting it to an unrelated branch would mis-attribute intent), while a text/media reply proceeds under normal routing with a system hint appended to the turn so the agent knows the reply couldn't be matched to its original conversation |
| R26 | A turn-scoped decision header carried by an exchange (`{ label, note, rollbackable }` — set by the boundary extension for a branching decision or a rollback) is rendered as the whole header — label plus one-line note — in italics (`_label — note_`) anchored above the streamed text. Because `editMessageText` replaces the full message text, the renderer recomposes the header on every edit so the streamed body never overwrites it; the header rides the first chunk when the response overflows, and it is dropped for the rest of the exchange once the body grows past the edit limit (best-effort — the decision itself still took effect). The header is turn-scoped: it is set fresh for one exchange and never carried to a later turn. Manual command acks bake their label into the ack text directly and never carry a streamed header |
| R27 | `lifecycleStatus(text, fresh?)` renders trunk-lifecycle progress (nightly close, stale-trunk recovery) on a single dedicated italic message, parallel to `shutdownStatus` but on a separate message id that is never seeded into the `StreamRenderer` and so persists untouched across later exchanges. The first call with `fresh` starts a new message (one per lifecycle event — e.g. each recovered trunk); subsequent calls edit it in place. It is serialized through the send mutex. The coordinator calls it for the nightly `closeTrunkIfDue` and stale-trunk recovery closes (see [conversation-loop](conversation-loop.md) R20), because those have no following exchange to reclaim the preparation lead-in — the close pipeline's per-processor lines update the lifecycle message in place, ending at `Trunk closed` (or `Trunk close failed`). Recovery runs before the channel attaches, so its lines are buffered and flushed in order at attach time |
| R28 | When a single streamed Telegram message accumulates more than `intensiveWorkThreshold` (default 4) tool→text boundaries — a contiguous block of one or more tool calls followed by any text counting as one boundary, not one per tool call — the turn is treated as intensive work and every unit before the last content-type unit folds into a single collapsed Telegram **expandable blockquote** (collapsed by default, tap-to-expand), leaving the last unit expanded by default. A unit is a preface text segment plus the tool group it introduces; the collapse split therefore follows content-type transitions (it lands at the start of the last text segment, not at a paragraph break), so a streaming multi-paragraph text answer stays expanded as a whole rather than folding paragraph-by-paragraph. The threshold is a trigger (collapse activates only once the count strictly exceeds it), not a quota of segments kept visible, so turns at or below it render exactly as R4. Collapse is positional — no length or content heuristic decides what folds — and deferred to `finalize()`: while the agent streams the message stays fully expanded (no folding mid-stream, so the user can follow the work as it happens), then folds once at the end — every unit before the last content-type unit collapses into one block while the last unit stays expanded (a turn ending on a trailing tool keeps its `[last preface + trailing tool summary]` expanded rather than collapsing the whole body). Detection resets at each Telegram message boundary so a split or already-committed message is never retroactively collapsed; `collapseIntensiveWork: false` (default on) disables it entirely. The `expandable_blockquote` is emitted by the renderer as a structured payload, not by the markdown converter (so `>` still maps to an expanded `blockquote`, R6). Any `>` quotes inside the folded region are flattened to plain text (no nested `blockquote` entity) so the single collapsed block stays valid — Telegram forbids a `blockquote` from nesting inside an `expandable_blockquote`, and the quote's text and inner inline formatting survive |

## Behaviors

### Channel Lifecycle and Authorization (R0, R1, R2)

The extension wires one `Bot` instance shared by the channel and the agent tools; misconfiguration disables the feature without failing startup.

**Acceptance Criteria**:
- Given `botToken` is `""` or `chatId` is `0`, when the extension sets up, then it logs that the channel is disabled and registers no channel, hook, or tools
- Given valid config, when `start()` runs, then `bot.init()` validates the token before polling begins, `setMyCommands` registers every command (`new`, `queue`, `stop`, `checkpoint`, `back`, `rollback`, `skill`, `tasks`, `reload`) with usage hints (a failure is logged and ignored), and polling runs detached with `allowed_updates: ["message", "callback_query", "message_reaction"]`
- Given a message from a chat other than `chatId`, when received, then it is ignored without response
- Given polling or update handling throws, when the error surfaces, then it is logged via `bot.catch` / the polling catch handler and the process continues

### Inbound Text (R3, R17)

**Acceptance Criteria**:
- Given an authorized text message, when handled, then `mapTextMessage` produces an `InboundMessage` with trimmed text, `channel: "telegram"`, and `metadata.messageId`, submitted via `runtime.submit()`
- Given empty or whitespace-only text, when handled, then `mapTextMessage` returns `null` and nothing is submitted
- Given any inbound message (text or media), when handled, then the channel records its message ID as the last inbound message (target for `react_to_message`)
- Given a `/stop` message, when handled, then the in-flight run is aborted via the configured `stop` callback (it is never submitted as a turn), `⏹ Stopped.` is sent as acknowledgement, and an abort failure is logged without breaking the channel

### Inbound Reactions (R18, R2, R25)

**Acceptance Criteria**:
- Given an authorized `message_reaction` update, when handled, then `mapReaction` diffs the new and old emoji sets and produces an `InboundMessage` naming what was added and/or removed (e.g. `The user reacted 👍 to a previous message.`)
- Given a reaction update from a user other than `chatId`, when handled, then it is dropped and nothing is submitted
- Given a reaction update whose added and removed emoji sets are both empty, when handled, then `mapReaction` returns `null` and nothing is submitted
- Given a reaction is surfaced, when submitted, then `metadata.reaction` is `true` and `metadata.replyToMessageId` is the reacted-to message id so reply routing can apply
- Given the reaction targets a message other than the live branch's most recent message and its text is recovered, when handled, then the turn text is prefixed with `Reacted to:\n> <truncated text>` of that message and ends with `Interpret it in context and respond accordingly.`
- Given the reaction targets the live branch's most recent message, when handled, then no `Reacted to:` block is prepended — the turn text is the bare reaction prose (the message is already at the bottom of the conversation)
- Given the reaction targets an earlier message whose text can't be recovered (e.g. the entry was compacted away), when handled, then the turn text is the bare reaction prose
- Given a reaction targets a message id that is not recorded, when handled, then a notice that the conversation couldn't be found is sent to the user and the reaction is not submitted (dropped rather than routed to an unrelated branch); a notice send failure is warn-logged and the reaction is still not submitted

### Message Recording and Reply Routing (R19, R20, R21, R25)

The channel persists a message-id↔branch mapping (`messageId → { treeEntryId, branchId }`) so a later reply, reaction, or button tap can be force-routed to the branch that owns the referenced message, bypassing topic classification.

**Acceptance Criteria**:
- Given an exchange finished rendering, when `respond()` finalizes, then the inbound message id (when present) and the finalized outbound message id are recorded against the live leaf's `{ treeEntryId, branchId }` as `incoming`/`outgoing`; with no live trunk, nothing is recorded
- Given a recording call throws, when handled, then the failure is logged at debug and the exchange proceeds
- Given an inbound message replies to (or a reaction/button targets) a message id that resolves to a known `{ treeEntryId, branchId }`, when routed, then the turn carries `metadata.forcedBranchId` (and `forcedTreeEntryId`) set to that branch
- Given a text/media reply targets a message id that is not recorded, when routed, then no `forcedBranchId` is attached, a system hint noting the reply couldn't be matched to its original conversation is appended to the turn, and it follows normal routing
- Given a turn carries `metadata.forcedBranchId`, when the boundary middleware runs, then it force-routes: the live branch appends normally, an earlier recorded branch forces a collapse + context injection, and an id that resolves to no record falls through to classification
- Given a reply targets a message that carries text, when mapped, then a truncated `Replied to:` quote of that text is prepended to the turn, unless the replied-to message is the live branch's most recent message (already live in the agent's context) — in which case the quote is omitted but `metadata.replyToMessageId` is still set so routing is unaffected

### Response Rendering (R4, R5, R6, R7)

The channel renders each exchange progressively under the mutex: a `StreamRenderer` holds streamed text and reveals each segment in one go when the next tool call settles it (or at finalize), baking a marker for each tool→text transition, then finalizes it when the stream ends.

**Acceptance Criteria**:
- Given an exchange starts, when events are being consumed, then a typing chat action is sent and refreshed every 5 seconds until the stream ends
- Given `text` events stream in, when the renderer flushes, then nothing renders until the next `tool-start`/`status` line or `finalize()` reveals the accumulated segment in one go (so a segment is never cut mid-stream), with sends/edits at most once per ~1500 ms and edits that would not change the rendered text skipped
- Given a `tool-start` event arrives, when handled, then a live italic line `_🔧 <friendly activity>_` (a wrench glyph plus the args-aware `formatToolActivity` label, e.g. "Reading <path>") is shown below the settled text, and the tool is recorded for the segment summary
- Given text resumes after one or more `tool-start` events (or the exchange finalizes with tools pending), when handled, then the recorded tools collapse via `summarizeToolActivities` into a persistent italic marker `_🔧 <summary>_` baked into the buffer, blank-line separated from the surrounding text so consecutive text segments never run together
- Given a `status` event arrives, when handled, then a transient italic line showing the status text is shown below the streamed text and is dropped as soon as more text arrives
- Given the streamed text grows past the 4096-character edit limit, when the renderer flushes, then full chunks are finalized in place (paragraph > line > hard split, surrogate-safe) and only the tail keeps streaming
- Given the stream ends with non-blank text, when `finalize()` runs, then any pending tool summary is baked, the dangling trailing separator is trimmed, the streaming message is upgraded to its final entity-safe chunked form bypassing the throttle, and the last sent message ID becomes the pin target; an exchange that produced no text deletes the streaming message
- Given a streaming send or edit fails, when the renderer marks itself broken, then it stops editing and `finalize()` deletes the partial message and resends the full text fresh via `sendChunked`
- Given a recoverable `error` event arrives mid-stream, when handled, then `⚠️ Error: <message>` is sent immediately and consumption continues
- Given a non-recoverable `error` event arrives mid-stream, when handled, then `⚠️ Error: <message>` plus the paragraph "This needs your attention — the next message won't recover on its own." is sent immediately and consumption continues
- Given Telegram rejects an entity send with "can't parse entities", "entities too many", or "message is too long", when the fallback runs, then the raw text is resent with no entities and the message is delivered unformatted (rare — omitting `parse_mode` means ordinary punctuation can't be rejected)
- Given a response contains a GFM table (with any surrounding inline formatting), when converted, then the table is flattened to a bullet list (`- **<first cell>**: <remaining cells>`) before conversion, so the surrounding formatting survives as entities; tables inside fenced code blocks are left intact
- Given a formatting span (e.g. bold or a fenced code block) would straddle the 4096-character chunk boundary, when split, then the entity falls entirely within one chunk (the split moves to just before it) instead of being cut, so the formatting survives across multi-message responses; an entity larger than the limit is dropped and its text rendered plain
- Given a `respond()` and a `deliver()` overlap, when both run, then the mutex serializes them FIFO and their API calls never interleave
- Given the coordinator calls `shutdownStatus()` during teardown, when the first line arrives, then a dedicated italic message is sent; when subsequent lines arrive (e.g. `Post-processing: …`, `Done`), then that same message is edited in place rather than new messages being sent

### Receipt and Preparation Feedback (R23)

The channel gives immediate feedback the moment a message arrives and keeps a visible status line through preparation (boundary detection, middleware, session open) — the window before `respond()` starts streaming. The preparation lead-in is a single provisional message that the streaming response reclaims, so feedback never opens a second message and never lingers past a normal exchange. (If an exchange aborts after a lead-in already appeared — a rare preparation error with no response — that line may remain until a later preparation or response reclaims the same message.)

**Acceptance Criteria**:
- Given an authorized text or media message that will be submitted, when handled, then a one-shot `typing` chat action fires immediately on receipt — before the message is submitted (text) or before its download begins (media)
- Given a `/stop` message, when handled, then no typing action fires (only `⏹ Stopped.` is sent)
- Given a `status()` line arrives during preparation (no streaming renderer active), when handled, then it surfaces on a single provisional italic `_<text>_` message — created on the first line, edited in place on subsequent lines — and the `typing` indicator is refreshed
- Given a lead-in message exists when `respond()` starts, when the exchange streams text, then the lead-in is reclaimed as the streaming message (the response text edits it in place rather than sending a second message)
- Given a lead-in message exists when `respond()` starts, when the exchange yields no text, then the lead-in message is deleted
- Given a message is steered into a live exchange or queued behind it, when submitted, then it skips preparation and no lead-in is shown for it
- Given a nightly (`closeTrunkIfDue`) trunk close (or a stale-trunk recovery) with no exchange following, when post-processing runs, then no lead-in is created; instead the per-processor lines surface on a dedicated persistent `lifecycleStatus` message that the next exchange does not reclaim — opening fresh and editing in place through each phase to a final "Trunk closed" (or "Trunk close failed"). Recovery that runs before the channel attaches buffers the lines and flushes them in order at attach time (see [conversation-loop](conversation-loop.md) R20)
- Given a bare argument-taking command (`/new`, `/queue`, `/skill`) the coordinator intercepted for pending-input, when its prompt is rendered, then it surfaces through this same `status()`/lead-in path (a non-LLM line the eventual streamed response reclaims), so the pending-input flow is channel-agnostic — the channel only renders the prompt text

### Inbound Media (R8, R9, R10)

**Acceptance Criteria**:
- Given a supported media message, when resolved, then the first match in priority order (animation, sticker, video note, photo, voice, video, audio, document) determines kind, label, extension, MIME type, and a human-readable summary; the largest photo size is used and video notes map onto the `video` kind
- Given a resolved file with `fileSize` over 20 MB, when downloading, then `MediaTooLargeError` aborts before any network call and its message is sent to the user
- Given a successful download, when submitted, then the `InboundMessage` carries the caption (or empty text) and one `MediaAttachment` with the saved path, MIME type, and description (e.g. `Photo (800 × 600, 117 KB)`)
- Given a stored file, when named, then a random hex prefix guarantees uniqueness while preserving the original filename or falling back to the resolved extension
- Given `allowMedia` is `false`, when media arrives, then it is ignored
- Given the bootstrap hook runs, when the media directory contains files older than 30 days, then they are deleted

### Background Deliveries and Push Notifications (R11)

**Acceptance Criteria**:
- Given `pushNotifications` is `true`, when `deliver()` runs, then every chunk but the last is sent with `disable_notification: true` and the last is sent audibly, so exactly one push fires (on the final chunk)
- Given `pushNotifications` is `false`, when `deliver()` runs, then all chunks are sent with default notification behavior

### Response Completion Push (R24)

A streamed response is built by sending a message and editing it in place as text arrives; Telegram edits never notify, so on their own these never fire a push. `respond()` therefore forces one push on completion — but only when the turn ran long enough that the user likely stepped away, and only when no tool already pushed — so quick back-and-forth doesn't flicker while the user is still watching.

**Acceptance Criteria**:
- Given `pushNotifications` is `true` and a streamed exchange lasting at least `pushNotificationMinSeconds`, when `respond()` finalizes, then the finalized (last) message is copied within the same chat and the streamed original deleted, so exactly one push fires on the copy; reply routing records the copied message id and `lastOutboundId` points at it
- Given a streamed exchange lasting less than `pushNotificationMinSeconds`, when `respond()` finalizes, then no copy or delete occurs and the streamed message stands in place (no flicker, no push)
- Given a turn in which a notifying tool (`send_telegram_file`, `pin_message`, or `send_message_with_buttons`) ran, when `respond()` finalizes, then no copy or delete occurs — the tool already delivered a notifying message
- Given a multi-chunk streamed response that pushes, then only the final chunk is copied and deleted; earlier chunks are left untouched
- Given `pushNotifications` is `true`, while a response streams, then the work-in-progress message, the preparation lead-in, and any overflow chunks are all sent with `disable_notification: true`, so the completion copy is the only push
- Given `pushNotifications` is `false`, when `respond()` runs, then it streams with default notification behavior and never copy-deletes
- Given the copy API call fails on completion, then the streamed message is left in place (delivered, without a push) and no delete is attempted; the streamed message id is recorded

### Decision Header Rendering (R26)

When an exchange carries a decision header (a branching decision or a rollback, set by the boundary extension), `respond()` anchors it above the streamed text before any text streams, and the renderer recomposes it on every edit so the streamed body never overwrites it.

**Acceptance Criteria**:
- Given an exchange whose metadata carries a decision header, when `respond()` starts, then the renderer is seeded with the header before streaming begins, and it renders as the whole header (label plus one-line note) in italics anchored above the streamed text
- Given a header is anchored, when the streamed text is edited in place, then the header is recomposed atop the new body on every edit and is never overwritten by the streamed text
- Given a header is anchored and body text has been shown, when more text streams without a new tool/status line settling a segment, then the visible body is preserved — the message is not edited back to a header-only render; the header surfaces alone only as the initial reveal, before any body settles
- Given a response that overflows into multiple chunks, when it finalizes, then the header rides the first chunk
- Given a streamed response that overflows the edit limit mid-stream (before finalize), when the renderer commits the first overflow chunk, then the header rides that first committed chunk — it is consumed there and never re-revealed on a later tail message below the already-committed body
- Given a streamed body that grows past the 4096-character edit limit, when the composition no longer fits, then the header is dropped (and logged) for the rest of the exchange — the decision itself still took effect; the transient live line is dropped first
- Given a render failure mid-stream, when the renderer goes broken, then the header is logged and the response degrades to a plain send (best-effort surfacing)
- Given a header was anchored for one exchange, when the next exchange renders with no header, then none is carried forward — it is turn-scoped

### Intensive-work collapse (R28)

When a single streamed message crosses a boundary threshold, the renderer folds every unit before the last content-type unit into one collapsed Telegram expandable blockquote, keeping the last unit — the preface text plus its tool group, or the final answer — as the prominent, expanded content by default. The split follows content-type transitions (a tool-group → new-text transition), not paragraph breaks, so a streaming multi-paragraph text answer stays expanded as a whole. This path replaces the markdown compose for that message once active, while every below-threshold and disabled turn renders byte-identically to R4.

**Acceptance Criteria**:
- Given several tool calls grouped into segments, when the renderer counts intensive work, then it counts one segment (a block of one or more tool calls followed by text) as a single boundary — not one per tool call (e.g. five `read` calls before one text block count as one boundary, not five)
- Given a tool block is followed by even a single character of text, when the text resumes, then it completes one boundary — there is no minimum text length required to form one
- Given a turn whose final tool block has no following text, when it finalizes, then that trailing block adds no boundary (a boundary requires tool→text); its summary bakes at finalize into the last unit, which stays expanded (not into the collapsed block)
- Given the default threshold of 4, when exactly 4 boundaries have formed, then no collapse occurs — collapse activates at the boundary where the count exceeds the threshold (once the 5th boundary forms, not at 4); a custom `intensiveWorkThreshold` is the value the count must exceed
- Given a turn crosses the threshold mid-stream, when the crossing boundary forms, then the live message keeps streaming fully expanded (no `expandable_blockquote`) — the fold is deferred; at `finalize()` every unit before the last content-type unit (including ones that streamed inline) folds into the collapsed block, leaving the last unit expanded
- Given collapse is active and the final answer spans multiple paragraphs, when it finalizes, then the whole final text segment stays expanded (not folded paragraph-by-paragraph); only units before the last content-type transition (a tool resuming after text) fold
- Given collapse is active and a tool is currently running (its live `_🔧 <activity>_` line showing), while the turn streams the message stays fully expanded (no block) — the running tool's preface and live activity line are both visible; the fold (earlier units only) is applied at `finalize()` (the preface explains the running tool group)
- Given an intensive turn ending in a final answer, when it finalizes, then all earlier units are wrapped in a single collapsed `expandable_blockquote` and only the final answer text is expanded by default; the block carries the baked `_🔧 <summary>_` markers (inner italic/code entities), not the live activity labels
- Given an intensive turn that ends on a tool with no following text, when it finalizes, then the last unit — the trailing tool's preface text plus its baked summary — stays expanded and only earlier units collapse (the whole message is not the block); the message is non-empty and the earlier units remain expandable to reveal the work
- Given an intensive turn, when the finalized message is laid out, then the collapsed block renders above the final unit in chronological order, with the final unit as the last expanded content
- Given the folded region's markdown contains `>` quotes, when it is wrapped in the `expandable_blockquote`, then those inner quotes are flattened to plain text (no nested `blockquote` entity) so the single collapsed block stays valid; the quote's text and inner inline formatting survive, while a `>` in the expanded tail stays a real `blockquote` (it is outside the block)
- Given a long turn whose stream splits into multiple messages at the 4096-character limit, when each message is committed/streamed, then every overflow-committed chunk renders fully inline (no collapsed block) — collapse is exclusive to the final message of the turn and is applied at `finalize()` — and the boundary count is evaluated independently per message (detection resets at each split), so an already-committed message is never collapsed and the streaming tail collapses only if it itself re-crosses the threshold
- Given `collapseIntensiveWork` is `false`, or a turn at or below the threshold, when it renders, then no collapse ever occurs and the message is indistinguishable from R4 (no `expandable_blockquote` entity, baked markers inline)
- Given an intensive turn carrying a turn-scoped decision header (R26), when it composes, then the header anchors outside and above (never inside) the collapsed block on every recompose; the completion-push copy-delete, `error`/`status` transient lines, and notifying tools (`send_telegram_file`, `pin_message`, `send_message_with_buttons`) compose with the collapsed block without conflict
- Given a streaming send/edit failure trips the renderer into the broken-render fallback, when `finalize()` resends the full text via the plain chunked path, then collapse is not applied — the message is delivered as plain inline text (no `expandable_blockquote` entity) so a blockquote-entity failure can never lose or block delivery

### Agent Tools (R12, R13, R14, R15)

**Acceptance Criteria**:
- Given a `filePath` resolving outside every allowed root, missing, or not a regular file, when `send_telegram_file` runs, then it throws an error naming the allowed roots or the failure
- Given a valid file, when sent, then the extension selects `sendPhoto`/`sendAudio`/`sendVideo`/`sendDocument` (case-insensitive extension match, document fallback) with the optional caption
- Given no `messageId` argument, when `react_to_message` runs, then it targets the last inbound message and throws if none exists; the emoji string is passed through so the Telegram API rejects unsupported emoji
- Given a response with rendered text, when `pin_message` runs, then the in-flight response message is pinned inline (at the tool's `tool-start`) with `disable_notification: false` and its ID is returned; with no response text it throws `No message available to pin`
- Given an invalid button layout (empty rows, blank label, empty value, value over 58 bytes, over 100 buttons), when `send_message_with_buttons` validates, then it throws naming the offending row/field before any API call (an empty label throws "has an empty label"; an empty value throws "has an empty value")

### Button Taps (R16)

**Acceptance Criteria**:
- Given any callback query, when handled, then `answerCallbackQuery()` runs first so the tapper's spinner clears regardless of authorization or agent state
- Given a tap from a user other than `chatId`, when handled, then it is dropped after acknowledgement with no keyboard removal or submission
- Given an authorized tap with recognized callback data (`btn1:`/`btnN:` prefix), when routed, then the turn text is `` The user tapped the option `<value>` out of the options you displayed. `` with `metadata.buttonValue`; the tapped button message is resolved to its branch — a tap on an earlier branch stamps `forcedBranchId` (the boundary forces a shift + context injection), a tap on the live branch appends normally, and an unrecorded target falls through to normal handling
- Given a single-use tap (`btn1:`), when routed, then keyboard removal runs as a detached call and its failure is logged without blocking the turn
- Given unrecognized callback data, when handled, then it is logged and dropped
