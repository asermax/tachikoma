# Skills

<!-- This spec describes the current system capability. Updated through delta reconciliation. -->

## Overview

Skills give the agent packaged expertise: Agent Skills-format directories from both the user's workspace (`{workspace}/skills/`) and the skills extension's bundled `builtin-skills/` directory (built-in authoring skills) are contributed to pi as native skill sources, so pi's progressive disclosure surfaces each skill's description in the system prompt and the agent reads the full `SKILL.md` only when relevant. On top of progressive disclosure, the extension proactively surfaces relevant skills: on each turn a conversation-aware classifier picks which loaded skills fit the latest message and injects each match's full content directly as a hidden message, so the right expertise is available immediately — no separate `/skill` load — instead of relying on the agent to notice it from the catalog alone. The extension otherwise stays thin — it wires the sources, adds a `/reload` path so the live session can pick up skill changes, and adds the one capability pi does not cover: agent definitions bundled inside skills become delegable subagents through a `delegate_to_agent` tool. A built-in `general-purpose` agent ships alongside the skill-bundled ones, so the main agent can always delegate focused, context-heavy work (e.g. exploring files) even with no skills installed.

## User Stories

- As a user, I want to drop skill packages into my workspace skills directory so that the agent gains specialized knowledge without code changes or registry configuration
- As the assistant, I want skill descriptions available via progressive disclosure so that I load full skill content only when it is relevant to the task
- As the assistant, I want relevant skills' full instructions proactively injected based on the conversation so that I can apply them immediately, even when I would not have chosen to load them on my own
- As a skill author, I want to bundle agent definitions inside a skill so that focused work can be delegated to an isolated subagent with its own prompt and tools
- As the assistant, I want an always-available general-purpose subagent so that I can offload context-heavy exploration and searching without a skill having to ship one

| R6a | An agent that declares a `model` runs its headless delegation on that model; an agent without one runs on the side-runner's default tier |

A pi-native extension is grantable by virtue of being installed (it cannot call `app.agent.use`), on the same terms as a factory tool |

Either source alone yields that source; neither yields none (the read-only built-in default still applies, never "no tools"). A declared name resolves — or throws the same self-correcting error as a caller-requested one — via the source-agnostic path in R6c/[ADR-015](../architecture/ADR-015-subagent-extension-tool-grants.md) |
| R7 | Invalid agent files are logged and skipped; a missing skills root or agents directory yields empty discovery, never an error |
| R8 | Agent discovery re-runs at every session creation and on every `delegate_to_agent` execution, so new and edited agents apply without a restart |
| R9 | The extension can be disabled via `[extensions.skills] enabled = false` (default enabled) |
| R10 | A `/reload` command and a `reload_resources` tool reload skills, prompts, and extensions from disk into the running session; the tool queues `/reload` as a follow-up (reload must run in command context) so additions and edits apply mid-session without a restart |
| R11 | The session factory (skill sources + `delegate_to_agent` + reload) is registered with `{ sessionScopes: ["main", "background"] }`, opting it into autonomous background task runs, so those runs also receive the skill sources and the `delegate_to_agent` tool (not just conversational sessions); the factory receives its binding session type (`{ scope }`) and adapts accordingly |
| R12 | On each genuine top-level turn (main conversation and background task runs, not post-processing forks — gated by `app.agent.isForking()`), a conversation-aware classifier selects which loaded skills are relevant to the latest message and the extension injects each selected one as a single hidden message — the full `SKILL.md` (wrapped per skill) for a skill whose content is not yet on the active path, or a lightweight reminder for a skill already injected this branch (its content still in context) — so no separate `/skill` load is needed; the classifier considers every invocable (non-`disable-model-invocation`) skill each turn (it does not pre-filter already-injected ones, so they can be re-anchored as reminders), a skill is injected in full at most once per branch, and the record of fully-injected skills resets when the topic changes or the session compacts (R16) |
| R13 | Proactive skill selection feeds the classifier the recent conversation, the latest user message, and the catalog of invocable skills (name + description); it returns skill names validated against that catalog, then routes each match — full content for a skill not yet injected this branch, a lightweight reminder for one already injected; an empty selection is a valid result and the classifier may signal it by omitting the `skills` key (or returning `{}`) — the selection schema defaults a missing key to an empty list, so "no relevant skills" is a clean no-op rather than a parse failure; the pass is best-effort — a classify failure, a deadline abort, or a skill whose content cannot be read (or is empty) skips that skill and never blocks the response; the classify is bounded by a short, request-cancelling deadline (it aborts the underlying call rather than racing it), and a transient status line surfaces while it runs in conversational (main) sessions — background task runs execute the classifier too but suppress the status, since a background session has no streaming renderer to host it (so it cannot orphan as a stray) |
| R14 | Proactive skill injection is gated by `[extensions.skills] proactiveLoading` (default enabled); when disabled, no selection runs and skill loading falls back to pi's progressive disclosure alone |
| R15 | The extension owns its agent-facing skill guidance rather than baking it into the core base prompt: a `skills-usage` context section (`src/extensions/skills/usage.ts`, contributed via `provideContext(..., "skills-usage")`) tells the agent that a relevant skill defines the correct process — follow its instructions and workflows rather than improvising an alternative, treat a proactively injected skill as authoritative for its domain, and when no skill was injected read a fitting skill's `SKILL.md` from the catalog; it is scoped to `["main", "background"]` and gated by `enabled`, so a disabled skills extension contributes no guidance and the core base prompt stays feature-agnostic ([DES-005](../design/DES-005-base-prompt-ownership.md)) |
| R16 | The per-branch injection record resets whenever injected content may have left the active context path: on a genuine topic change (the boundary extension emits `session:topic-changed` on an auto-detected shift, a manual `/new`, or a forced jump to an earlier branch — not on a tangent/checkpoint) and on mid-branch compaction (pi's `session_compact`, which summarizes older entries out of the active context). In both cases the skills extension clears its already-injected set so affected skills re-evaluate from scratch — re-injecting in full if still relevant. The daily trunk is one pi session for the whole day, so without these resets a skill would stay "injected" after its content left the active context path |

## Behaviors

### Skill Source Contribution and Reload (R0, R1, R2, R10)

The session factory answers pi's `resources_discover` event with the workspace skills path and the built-in skills path; everything downstream (frontmatter parsing, description injection into the system prompt, on-demand `SKILL.md` reads) is pi's native pipeline. A `/reload` command and a `reload_resources` tool let a running session pick up skill changes without a restart.

**Acceptance Criteria**:
- Given the workspace has no `skills/` directory, when bootstrap runs, then the directory is created; a second run makes no changes
- Given a valid Agent Skills package in the workspace or the bundled `builtin-skills/` directory, when an agent session is created, then pi surfaces the skill through progressive disclosure (description in the system prompt, content loaded on demand)
- Given a skill is added while the app is running, when the next agent session is created, then the new skill is discovered; the running session can also pick it up via `/reload` or `reload_resources`
- Given the agent calls `reload_resources`, when it executes, then `/reload` is queued as a follow-up message (so it runs in command context) and resources refresh once the current run finishes

### Agent Discovery (R3, R4, R7, R8)

`discoverSkillAgents` (`src/extensions/skills/agents.ts`) scans every `<skill>/agents/*.md` file under the skills root and parses frontmatter metadata.

**Acceptance Criteria**:
- Given `skills/research/agents/scout.md` with a `description` and a YAML `tools` list, when discovery runs, then an agent named `research/scout` is returned with those tools and the body as its system prompt
- Given frontmatter declaring `name: pathfinder`, when discovery runs, then the agent is named `research/pathfinder` (explicit name wins over the file stem)
- Given `tools: read, ls` as a comma-separated string, when discovery runs, then the tools parse to `["read", "ls"]`
- Given `model: anthropic/claude-opus-4-5:high`, when discovery runs, then the agent's `model` is that reference; an agent without `model` discovers as `null`
- Given a non-string `model` value, when discovery runs, then a warning is logged and the agent loads with `model` `null` (the bad field never drops the agent)
- Given an agent file without a `description`, when discovery runs, then the file is skipped with a warning and other agents still load
- Given a skill without an `agents/` directory, or a missing skills root, when discovery runs, then an empty list is returned
- Given `extensionTools:\n  - web_search\n  - scrape` (or `extensionTools: web_search, scrape`), when discovery runs, then the agent's `extensionTools` is `["web_search", "scrape"]`; an absent or empty `extensionTools` discovers as `null`; a malformed format is warned and ignored (the agent still loads with `extensionTools` `null`)
- Given `tools:\n  - read\n  - Glob`, when discovery runs, then a warning names `Glob` (and the valid built-ins) and the agent's `tools` is `["read"]`; if every declared name is unknown (e.g. `Glob`, `WebSearch`), `tools` falls back to `null` (read-only default) and the agent still loads

### Delegation (R5, R5a, R5b, R6, R6a, R6b, R6c, R6d, R6e)

The `delegate_to_agent` tool (`src/extensions/skills/delegate.ts`) lists the available agents (the built-in `general-purpose` agent first, then discovered skill agents) in its description and runs the chosen agent in a fully isolated headless session via `app.agent.side.run` (`isolatePrompt: true`), passing the agent's declared `model` when set and accepting an optional per-delegation `tools` override (R6b). It can also grant exposed extension tools additively via `extensionTools` (R6c), resolved source-agnostically against the opened subagent session.

**Acceptance Criteria**:
- Given the built-in agent plus discovered skill agents, when the tool description is built, then `general-purpose` is listed first, followed by each skill agent as `<skill>/<name>: <description>`
- Given a delegation call with a known agent, when the tool executes, then the headless run uses the agent's system prompt, its declared tools, the task as the prompt, and `isolatePrompt: true` (the run sees only the agent's own prompt); the agent's final text is the tool result
- Given an agent with no declared tools, when delegated to, then the run uses the default read-only tool set
- Given a delegation that passes `tools: ["read", "grep", "bash"]`, when the tool executes, then the headless run uses exactly those tools (overriding the agent's declared set) and remains fully isolated (`isolatePrompt: true`); the built-in `general-purpose` agent's prompt reflects that it may modify files / run commands rather than claiming read-only
- Given a delegation that passes a non-built-in name in `tools` (e.g. a web tool), when the tool executes, then it throws a self-correcting error listing the built-ins and directing extension/web tools to `extensionTools`; no run is attempted
- Given an extension that has exposed a tool (e.g. `web_search`) for subagent use, when the calling agent delegates with that tool requested via `extensionTools`, then the subagent run has the granted tool *in addition to* its resolved built-ins and can call it; the run stays in-memory, prompt-isolated (`isolatePrompt: true`), and disposed after
- Given a delegation that requests an extension tool alongside a built-in `tools` override (e.g. `extensionTools: ["web_search"]` plus `tools: ["read", "grep", "bash"]`), when the run executes, then the subagent's active set is exactly those built-ins plus the granted tool
- Given a delegation that omits `extensionTools` (or passes `[]`), when the run executes, then it takes the built-in-allowlist path unchanged — no extension tools granted, read-only stays the default
- Given an agent that declares `extensionTools: ["web_search"]` and a delegation that omits `extensionTools`, when the tool executes, then the subagent run is granted `web_search` (the agent's declared grant is auto-applied with no caller action)
- Given an agent that declares `extensionTools: ["web_search"]` and a delegation that passes `extensionTools: ["scrape", "web_search"]`, when the tool executes, then the granted set is the union `["web_search", "scrape"]` (declared first, caller additions after, de-duplicated) — the caller extends but cannot narrow
- Given a delegation that requests an extension tool name that does not resolve (a typo, or a factory that did not opt into the `subagent` scope), when the run executes, then it throws a self-correcting error listing the grantable (non-builtin) tools *before* any prompt; no run is attempted
- Given a delegation that requests several extension tools and one does not resolve, when it executes, then the whole request fails before the run — partial resolution is not granted
- Given a requested extension tool name that differs only in case from an exposed tool (e.g. `Web_Search` vs `web_search`), when resolution runs, then it does not resolve — resolution is exact, case-sensitive name match
- Given a factory registered with `{ sessionScopes: […, "subagent"] }`, when a delegated run that requests extension tools opens, then that factory binds into the subagent session with `{ scope: "subagent" }` and its tools are among the grantable set; a factory without the `subagent` scope does not bind and its tools are not grantable
- Given a pi-native extension installed under `.pi` (or packages/settings), when the agent requests its tool via `extensionTools`, then it resolves, binds into the subagent session, and is callable on the same terms as a Tachikoma-factory tool
- Given the `delegate_to_agent` description, prompt snippet/guidelines, and `skills-usage` guidance are built, then they advertise that exposed extension tools can be granted via `extensionTools` and direct the calling agent to delegate tool-dependent work (e.g. web research) with them granted rather than performing it on the main session
- Given two providers expose the same tool name (a collision), when the agent requests it, then resolution is last-wins (pi's registry dedupes by name) rather than an error — a collision is undetectable, especially for pi-native providers (see [ADR-015](../architecture/ADR-015-subagent-extension-tool-grants.md))
- Given a delegation that passes an empty `tools: []` or omits it, when the tool executes, then the run uses the agent's declared tools, or the read-only default if the agent declares none
- Given an agent that declares a `model`, when delegated to, then the headless run is pinned to that model; an agent without a `model` runs on the side-runner's default tier
- Given an unknown agent name, when the tool executes, then it throws an error listing the available agents (including `general-purpose`); no run is attempted
- Given no skill agents exist, when a session is created and the skills extension is enabled, then `delegate_to_agent` is still registered and lists the built-in `general-purpose` agent; when the extension is disabled, no `delegate_to_agent` tool is registered
- Given a delegation call that includes a `description`, when the tool executes, then tool-activity displays surface the `description` alongside the agent, while the delegated run receives only the `task` as the prompt (the run options contain no `description`)

### Proactive Skill Loading (R12, R13, R14)

On each genuine top-level turn, a `before_agent_start` handler runs a conversation-aware classifier over the invocable skills and injects each match directly as a hidden message — full content for a skill not yet injected this branch, a lightweight reminder for one already injected — so relevant skills reach the agent, instructions in hand, no separate load step, even when it would not pick them from the catalog itself. The pass augments progressive disclosure (descriptions stay in the system prompt) rather than replacing it, runs silently apart from a transient status line, and degrades to no injection on any failure.

**Acceptance Criteria**:
- Given an invocable skill not yet injected this branch and a relevant latest message, when the classifier selects it, then a single hidden message (`customType: "skill-content"`, not rendered to the user) is injected containing its body (YAML frontmatter stripped, as `/skill` does), wrapped as `<injected-skill name="…">` with a per-skill adherence line directing the agent to follow the skill's instructions and start any defined workflow, and preceded by a one-time authority-framed preface (the matched skills define the correct process for the request — follow them rather than improvise; their content is already here, so no `/skill` load is needed); multiple matches share one message, each in its own wrapped section
- Given a skill already fully injected earlier on the same branch (its content still in context), when the classifier selects it again, then it is not re-injected in full; instead a lightweight reminder (`<skill-reminder name="…">`) is injected, directing the agent to re-apply its already-loaded instructions and start any defined workflow. The classifier sees already-injected skills (it does not pre-filter them) precisely so they can be re-anchored this way
- Given a skill was fully injected then the session compacted (`session_compact`), when a later turn selects it, then it is re-injected in full (not a reminder): the compaction cleared the per-branch record because its content had been summarized out of the active context. The same reset happens on a topic change (`session:topic-changed`), so a skill whose content left the active path on a collapsed branch is re-injected on the new branch (R16)
- Given a matched skill's content cannot be read (or is empty/whitespace), when the handler builds the injection, then that skill is skipped (logged) and any other matched skills are still injected; the skipped skill is not marked injected, so the classifier can select it again on a later turn, and if every matched skill is skipped nothing is injected
- Given the turn runs inside a post-processing fork (memory/core-context extraction), when the handler fires, then it skips entirely — no classification, no injection
- Given the classifier returns a name not among the eligible skills, or a `disable-model-invocation` skill exists, then that name/skill is never injected
- Given the classifier fails or its deadline aborts the call, then the injection is skipped and the response is never blocked beyond that short deadline
- Given no invocable skills exist (none loaded or all `disable-model-invocation`), then no classifier call and no status line occur; when all invocable skills are already injected, the classifier still runs each turn so they can be re-anchored as reminders if relevant
- Given the turn is a background task run (not a conversational main turn), when proactive selection runs, then the classifier still executes (background tasks keep proactive skill injection) but no status line surfaces — a background session has no channel renderer, so the line is suppressed rather than orphaned as a stray
- Given `[extensions.skills] proactiveLoading` is disabled, then no proactive selection runs and loading falls back to progressive disclosure alone

### Skill Guidance (R15)

The extension contributes its own `skills-usage` context section so the agent treats a relevant skill as the correct process for the task, rather than improvising around it. The section is extension-owned (not part of the core base prompt), scoped to main and background sessions, and present only while skills are enabled.

**Acceptance Criteria**:
- Given the skills extension is enabled, when a main or background session starts, then the `skills-usage` section reaches the agent, framing injected skills as authoritative for their domain and directing the agent to follow a relevant skill's instructions and workflows rather than improvising
- Given the skills extension is disabled (`enabled = false`), when any session starts, then no skill guidance reaches the agent and the core base prompt carries no skill text (it stays feature-agnostic)

## Notes

Machinery deliberately left out of this implementation:

- **Skills hot-reload/watcher** — discovery runs per agent session, so new skills appear on the next session (the daily trunk reopens each day, or on restart) and agent definitions are re-read on every delegation; for the live session, `/reload` (and the `reload_resources` tool) re-reads resources on demand. No filesystem watcher — reload is explicit, not automatic
- **Skill `dependencies`** — not part of the Agent Skills standard. Skills that build on other material reference it directly in their content for the agent to read

See [../reference/pi-sdk-notes.md](../reference/pi-sdk-notes.md) (Skills section) for the pi-native behavior this extension relies on.
