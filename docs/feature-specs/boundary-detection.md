# Boundary Detection

<!-- This spec describes the current system capability. Updated through delta reconciliation. -->

## Overview

Boundary detection decides, for every incoming message, whether the conversation continues in the active session, starts a fresh one, or resumes a recently closed one. A rolling per-session summary — regenerated by a side-channel LLM call after every exchange — gives the classifier material to compare the incoming message against, alongside the verbatim last exchange and the summaries of recently closed sessions.

The feature ships as the `boundary` extension (`src/extensions/boundary/`): an exchange processor that maintains the summary and an inbound middleware that classifies messages and drives session transitions through the coordinator's middleware contract (see [DES-001](../design/DES-001-unified-extension-api.md) and [conversation-loop](./conversation-loop.md)).

## User Stories

- As a user, I want topic shifts detected so that unrelated conversations are processed as separate sessions and context doesn't bleed between them
- As a user, I want the assistant to recognize when I'm returning to a recent topic so that the earlier session is resumed instead of starting from scratch
- As a developer, I want boundary detection to be best-effort so that classification failures never block message handling

## Requirements

| ID | Requirement |
|----|-------------|
| R0 | After every completed exchange, a rolling session summary is regenerated via a side-channel completion (`processor` model tier) and stored on the session record, clipped to 600 characters |
| R1 | The verbatim last exchange (`user: …\nassistant: …`, clipped to 2000 characters) is stored on the session record on every exchange |
| R2 | When summarization fails, the last exchange is still persisted, the previous summary is left untouched, and the error is logged |
| R3 | Each inbound message is classified as `continue`, `new`, or `resume` via a single structured side-channel classification (`classifier` model tier) |
| R4 | Classification is skipped when there is nothing to compare against: no active-session summary and no resume candidates |
| R5 | Resume candidates are closed sessions within the configured window (`sessions.resumeWindowSeconds`, default 86400) that have a non-null summary, excluding the active session |
| R6 | A `new` decision with an active session closes it — running its post-processing to completion — before the message is handled in a fresh session |
| R7 | A `resume` decision naming a known candidate closes the active session and reopens the named one, restoring its pi session file |
| R8 | A `resume` decision naming an unknown session id is downgraded to `continue` with a warning |
| R9 | Classifier errors fail open: the decision defaults to `continue` and the message proceeds in the active session |
| R10 | Progress lines are surfaced through the active channel during detection and transitions (`app.status`) |
| R11 | Setting `[extensions.boundary] enabled = false` disables the feature entirely — neither the summary processor nor the middleware is registered |

## Behaviors

### Rolling Summary (R0, R1, R2)

`createSummaryProcessor` (`src/extensions/boundary/summary.ts`), registered via `app.sessions.onExchange`, feeds the previous summary and the latest clipped exchange to a side completion and persists the result through `app.sessions.update`.

**Acceptance Criteria**:
- Given a session with an existing summary, when an exchange completes, then the session record is updated with a fresh trimmed summary (clipped to 600 characters) and the last exchange in `user:`/`assistant:` form (clipped to 2000 characters)
- Given the side completion throws, when the processor runs, then only `lastExchange` is updated — the previous summary survives for the next boundary check
- Given a long conversation, when summaries are regenerated each exchange, then the stored summary stays bounded regardless of conversation length

### Boundary Classification (R3, R4, R5, R9)

The inbound middleware (`src/extensions/boundary/index.ts`) builds candidates from `app.sessions.listResumable()` and calls `detectBoundary` (`src/extensions/boundary/detector.ts`), which renders the active summary, last exchange, candidate list, and incoming message into tagged prompt sections and classifies against `BoundaryDecisionSchema`.

**Acceptance Criteria**:
- Given an active session with a summary, when a message arrives, then it is classified as `continue`, `new`, or `resume` using the summary, the last exchange when available, and candidate summaries with their ids
- Given no active session (or one without a summary yet) and no candidates with summaries, when a message arrives, then classification is skipped and the message proceeds directly
- Given the classification prompt, then it instructs the model to default to `continue` when in doubt and always for short reactions, follow-ups, or answers to the assistant
- Given the classifier throws or returns unparseable output, when detection runs, then the decision falls back to `continue` and the error is logged

### Session Transitions (R6, R7, R8)

On `new` or `resume`, the middleware drives the transition through the `InboundContext` (`closeSession` / `resumeSession`) before calling `next()`, so the coordinator handles the message in the right session.

**Acceptance Criteria**:
- Given a `new` decision with an active session, when the middleware acts, then the active session is closed (post-processing runs) and the message is subsequently handled in a freshly created session with no prior pi context
- Given a `resume` decision whose id matches a candidate, when the middleware acts, then the current session is closed and the named session is reopened from its stored pi session file
- Given a `resume` decision whose id matches no candidate, when `detectBoundary` validates it, then the decision is downgraded to `continue` and a warning is logged
- Given a `resume` decision whose id is no longer found in the registry, when the middleware looks it up, then no transition occurs and the message continues in the active session

### Configuration (R11)

**Acceptance Criteria**:
- Given `[extensions.boundary] enabled = false`, when the extension loads, then setup logs the disabled state and registers nothing — messages are never classified and summaries are never generated
