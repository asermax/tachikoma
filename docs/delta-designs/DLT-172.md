## Purpose

This document explains the design rationale for this delta: the modeling choices, data flow, system behavior, and architectural approach.

After implementation, the "Detected Impacts" section will guide reconciliation into feature design docs.

## Problem Context

Plugins currently accept no user configuration — they can only declare skills and metadata. Plugin authors have no mechanism to accept API keys, feature toggles, or endpoint URLs through Tachikoma's config system. Additionally, startup notifications (restart announcements) are dispatched independently, with no consolidation mechanism for other startup-time events like plugin load failures.

## Design Overview

Two concerns: (1) a typed config schema in the plugin manifest with validation and runtime access, and (2) a startup notification consolidation mechanism that merges restart announcements with plugin load failure summaries into a single delivered notification.

| Part | Mechanism | Flag |
|------|-----------|:----:|
| **S1** | Config schema model — Pydantic model for declared settings (field name, type, description, default, required) parsed from manifest `[config.<field_name>]` sections, with validation of the schema itself (type validity, default type consistency, required/default mutual exclusion) | |
| **S2** | Config value extraction — parse `[plugins.<alias>.config]` from user config TOML and map values to the schema fields; absent sub-table yields empty dict | |
| **S3** | Config validation engine — type checking with integer/float coercion, required field enforcement, default application, unknown key warning; produces diagnostics on failure | |
| **S4** | Runtime config access — new `config: dict[str, str \| int \| bool \| float]` field on `LoadedPlugin` holding validated values | |
| **S5** | Config surfacing in list_plugins — per-plugin `config` key in MCP tool output with schema, current values, and validation diagnostics | |
| **S6** | Startup notification consolidation — `dispatch_startup_notifications()` function in `__main__.py` called after `bootstrap.run()` completes, collects restart marker (consume-once clear) and plugin failure summaries from the plugin manager, merges into a single notification dispatched via the event bus | |
| **S7** | Plugin failure integration — plugin manager collects failure diagnostics during reconciliation; config validation failures contribute alongside manifest/source failures; failures exposed via a method on the plugin manager for S6 to consume | |
