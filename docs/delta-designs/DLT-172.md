| **S5** | Adapt the trunk-close pipeline (`close-pipeline.ts`) to iterate the topics store for extraction and prune via the shared `MEMORY_STORES`; the phased marker/commit machinery is unchanged | |

### Flagged Unknowns

#### S7 — Migration mechanism

The migration's mechanism is not yet pinned. Three open questions for the design phase (likely a spike):

- **Where it hooks.** A guarded startup/bootstrap step (runs before the first session) vs the migration subsystem (the path DLT-175's refactor migration took) vs piggybacking on the first trunk-close. The spec's startup-ordering AC implies it runs before the first session's memory index injection.
- **How same-topic merging is directed.** Fully agent-decided (the agent reads every old file and groups semantically) vs a host-side filename pre-grouping heuristic that hands the agent pre-paired files. A deterministic heuristic cannot reliably judge whether `facts/work-info.md` and `preferences/communication-style.md` are or aren't the same subject.
- **How self-detection/idempotency is marked, and where that marker lives.** Detection by `topics/` presence vs an explicit persisted marker (file flag vs app/session state vs a migration-subsystem record). The completion marker must be written ONLY after the full pass (per the interruption/idempotency AC), so a partial run re-runs cleanly.

**Lean (noted for design, not a decision):** startup/bootstrap step; fully agent-decided merge; detection by `topics/` presence plus a persisted completion marker.

## Notes

- Foundational delta: DLT-123 (learnings) builds on the topics store's layout/indexing/extraction conventions; DLT-173 (phased consolidation) will replace the interim maintenance model this delta adapts — keep maintenance changes minimal here.
- DLT-175 (daily trunk sessions) is already implemented; memory extraction/maintenance already runs as the trunk-close pipeline. This delta changes the store model that pipeline operates on, not the pipeline itself.
