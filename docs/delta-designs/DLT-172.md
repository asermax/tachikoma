## Purpose

This document explains the design rationale for this delta: the modeling choices, data flow, system behavior, and architectural approach.

After implementation, the "Detected Impacts" section will guide reconciliation into feature design docs.

## Problem Context

Tachikoma keeps long-term memory as git-versioned markdown under `memories/`. Today the *reference* knowledge a subject is split across two stores — `memories/facts/` (stable, objective) and `memories/preferences/` (subjective choices) — separated by an LLM classification/routing boundary enforced in two places:

- **Extraction** (`extraction.ts`): a facts-vs-preferences *classification self-check* routes each signal to one of two stores, and a separate `AGENTS.md`-preference skip avoids duplicating preferences already in `AGENTS.md`.
- **Maintenance** (`maintenance.ts`): a *misclassification-detection* pass moves content the extraction step placed in the wrong store.

That boundary fragments knowledge about a single subject across two files (a stable detail in `facts/`, a related preference in `preferences/`), and recalling a topic silently depends on guessing which store a piece of knowledge was filed under. The classification and the backstop that tries to correct it are both error-prone.

DLT-175 (daily trunk sessions) is already implemented: memory extraction and maintenance run as the **trunk-close pipeline** (`close-pipeline.ts`) — per-branch extraction → prune → consolidate → core-context, each guarded by an idempotent session marker. This delta changes the **store model** that pipeline operates on; it does not touch the pipeline's trigger, ordering, or marker machinery.

Constraints from the spec and its related deltas:

- Episodic memory (date-stamped summaries, time-tiered consolidation) and transcript archives are **unchanged** (R8).
- Richer *phased* consolidation is the scope of **DLT-173**, not this delta — so maintenance changes here stay minimal: unify the prompts and drop the misclassification logic, nothing more (R5).
- This is **foundational for DLT-123** (learnings layer), which builds on the topics store's layout, indexing, and extraction conventions — so those conventions must stay clean and reusable.
- Existing `facts/` + `preferences/` content must be folded into `topics/` with **no data loss** (R7).

## Design Overview

Collapse `facts/` and `preferences/` into a single **topic-oriented store** at `memories/topics/`, where each `<topic>.md` file holds *everything* known about a subject — stable reference facts and subjective preferences together, in free-form unified prose — with one index entry in `topics/MEMORY.md`.

Four areas change, plus a one-time migration:

1. **Store model** (`layout.ts`): `MEMORY_STORES` becomes `["episodic", "topics"]`, `INDEXED_STORES` becomes `["topics"]`; `ensureMemoryLayout` creates `topics/` instead of `facts/`/`preferences/`.
2. **Static index injection** (`indexes.ts`): the per-message context block emits one `## Topics Index` (not separate Facts + Preferences indexes) plus an updated layout section.
3. **Extraction** (`extraction.ts`): one `topics` extraction folds *both* factual and preferential signals into topic files; the classification self-check and the separate `AGENTS.md`-preference skip are removed.
4. **Maintenance** (`maintenance.ts`): one unified topics maintenance prompt (staleness, redundancy, overlap, cluster consolidation, size limits, context-file reconciliation); the misclassification-detection logic is removed.
5. **Migration** (new `migration.ts`): a one-time, self-detecting, idempotent agent-driven fold of the old stores into `topics/`.

The trunk-close pipeline (`close-pipeline.ts`) and the shared prompt sections (`prompts.ts`) adapt to the new store set. The authority hierarchy simplifies to **Skills > Topics > Context** (topics subsume both facts and preferences; context files SOUL/USER/AGENTS remain summaries/pointers).

The migration is the one mechanism whose *how* was unknown at spec time. It is resolved below (S7): a bootstrap hook, gated on old-store content presence, with no separate completion marker.

### Cross-Layer Contracts

- **Store set as the seam.** `MEMORY_STORES` and `INDEXED_STORES` in `layout.ts` are the single source of truth. `close-pipeline.ts` (extraction + prune loops) and the maintenance manifests (`buildCrossStoreManifest`, `buildStoreManifestForContext`) iterate them, so changing the constants propagates everywhere without touching call sites.
- **Headless-LLM seam.** Extraction (via `forkAndContinue` on a forked branch) and maintenance/migration (via `Runner.run`) all use the `SideRunner` with the shared `FILE_EDIT_TOOLS` allowlist and the `processor` tier. The migration reuses the *exact same* runner/tool/tier the maintenance ticks use.
- **Commit seam.** All workspace-mutating passes commit through the shared `commitChanges` helper (`app.git.createCommitAgent("workspace")` + `commitAll`). The migration uses the same helper so its fold and sweep land as git commits (which is also the backup/recovery mechanism).
- **Index contract.** Every agent that creates/modifies/deletes a topic file also maintains `topics/MEMORY.md` per the `INDEX_UPDATE_SECTION` rules. `ensureMemoryLayout` is idempotent and only seeds an absent index.

### Shared Logic

- **`storeDir`, `sweepEmptyMarkdown`** (layout.ts): directory resolution and the empty-file sweep are reused by extraction, maintenance, and migration alike.
- **Broad-topic naming + consolidation-at-write-time**: the *same* convention (broad, future-mergeable filenames; merge-into-existing-before-create; cluster collapse at 3+ files) is shared by the topics extraction prompt, the topics maintenance prompt, and the migration fold prompt — so all three agents produce a consistent store shape.
- **`buildCrossStoreManifest` / context dedup**: the topics maintenance agent reconciles against the other listed stores (now: episodic + context files) and trims to pointers per the authority hierarchy.

## Modeling

- **`MemoryStore`** narrows from `episodic | facts | preferences` to `episodic | topics`.
- **`INDEXED_STORES = ["topics"]`** — the only store with a `MEMORY.md` index. Episodic uses date-stamped filenames (`YYYY-MM-DD.md` + weekly/monthly rollups) and has no index; transcripts are raw `.jsonl`. This is unchanged from today; only `topics` replaces the two former indexed stores.
- **A topic** = exactly one `memories/topics/<topic>.md` file in free-form unified prose (facts and preferences coexist with **no prescribed internal structure** — a required `## Facts`/`## Preferences` layout would re-introduce the classification boundary inside the file) plus a single `[Name](./file.md): description` entry in `topics/MEMORY.md`.
- **Authority hierarchy**: `Skills > Topics > Context`. Skills' `SKILL.md` files own operational knowledge for their domain (highest); topics hold the durable reference + preference detail; context files (SOUL/USER/AGENTS) are concise summaries/pointers (lowest). When content conflicts, the higher source wins; when a topic duplicates a context file, the topic trims to a pointer. (Preferences had no clean tier under the old `Skills > Facts > Context`; folding them into topics gives them a home above context.)
- **Migration state** is *derived*, not persisted: it is the presence of non-empty `.md` content in the old stores. There is no migration record, flag, or DB row — the filesystem state is the source of truth, mirroring how the legacy migration subsystem detects work (`sessions` table presence, `context/` dir presence).

## Data Flow

### 1. Static injection — every message (pre-processing)

```
message → provideContext("memories") → buildMemoryContext(workspaceRoot)
  → LAYOUT_SECTION (topics store described)
  → for topics in INDEXED_STORES: read topics/MEMORY.md → formatMemoryIndex → "## Topics Index"
  → "" when memories/ absent; index section omitted when header-only
```

### 2. Extraction — trunk-close, per unextracted branch

```
extractBranches → for each branch without `extracted` marker:
  forkAndContinue(branchFile, storeInstruction("topics"), FILE_EDIT_TOOLS)
    → agent reads existing topics/, folds both factual + preferential signals from the branch's turns
       into topic files (create-or-merge, broad naming, prune stale, dedup vs context files)
    → updates topics/MEMORY.md
  sweepEmptyMarkdown(topics/)  → host removes blanks
  markBranchExtracted
```

### 3. Maintenance — trunk-close prune phase (+ interim ticks)

```
prunePhase → for topics in MEMORY_STORES:
  side.run(maintenanceSystemPrompt("topics"), FILE_EDIT_TOOLS)
    → consolidate clusters (3+ → one broad file), prune stale/redundant, enforce size,
       reconcile vs context files + episodic per authority hierarchy, rebuild/refresh index
  sweepEmptyMarkdown(topics/) → commit
coreContextStep (unchanged) → side.run(contextMaintenanceSystemPrompt) → commit
```

### 4. Migration — bootstrap, once

```
host.bootstrap() → migrate-memory-stores hook (before init-memory-layout):
  detect: any non-empty .md in facts/ or preferences/ ?
    no  → no-op (fresh install or already migrated)
    yes → side.run(fold prompt): read ALL old files + existing topics/, fold durable content
            into broad topic files (same-subject merge, distinct stay distinct, merge/dedup),
            update topics/MEMORY.md
          → commit (folded topics durable in git BEFORE any old store is touched)
          → host sweeps facts/ and preferences/ (remove blanks; old files already emptied by fold)
          → commit (the git history is the pre-migration backup)
  → init-memory-layout runs next: ensures topics/ exists, seeds/preserves topics/MEMORY.md
```

## Key Decisions

### KD1: One unified `topics/` store (not a reformed two-store model)

**Choice**: Collapse facts + preferences into a single topic-oriented store; each topic file holds both signal types in free-form prose.

**Why**: The classification/routing boundary is the root problem (R0). Any model that keeps two homes for a subject reintroduces the guess of "which store" and the misclassification backstop. A single home per subject means recall never depends on the classification.

**Alternatives considered**:
- *Keep two stores but fix the classifier*: rejected — the boundary itself is the defect; a better classifier is still a classifier that can be wrong, and still fragments a subject across files.
- *Two stores, one file per subject with typed sections*: rejected — a prescribed `## Facts` / `## Preferences` structure re-introduces the boundary *inside* the file (R2 explicitly forbids required structure).

**Sources**: Spec R0/R2; codebase `extraction.ts` (classification self-check) and `maintenance.ts` (misclassification detection in `PREFERENCES_MAINTENANCE_PROMPT`).

**Consequences**: Pro — one home per subject, simpler recall, less prompt surface. Con — loses the (lossy) signal of "this is a preference vs a fact"; acceptable, since the *content* is preserved and the distinction was the bug.

### KD2: One extraction that folds both signal types

**Choice**: A single `topics` extraction replaces the separate facts and preferences passes; it writes/merges into the relevant topic file regardless of whether the signal is factual or preferential.

**Why**: With one store there is no routing decision to make — the agent just identifies the topic and consolidates. Two passes were the mechanism being removed (R3).

**Alternatives considered**:
- *Two extraction passes writing to one store*: rejected — two passes is exactly what R3 removes, and running both per branch doubles the fork cost for no benefit.

**Sources**: Spec R3; codebase `extraction.ts` `STORE_INSTRUCTIONS` (per-store prompts) and `close-pipeline.ts` `extractBranches` (loops `MEMORY_STORES`).

**Consequences**: Pro — halves the per-branch fork-and-continue cost; simpler prompt. Con — the unified prompt must capture both stable-reference and subjective signals without one biasing the other; mitigated by reusing the proven consolidation-at-write-time instructions from the existing facts prompt.

### KD3: Authority hierarchy → Skills > Topics > Context

**Choice**: Topics subsume both former stores and sit above the root context files (SOUL/USER/AGENTS); skills remain highest.

**Why**: Topics now hold the durable detail (reference + preference); context files are intentionally concise summaries/pointers, so they defer to topics. Under the old `Skills > Facts > Context`, preferences had no tier — folding them into topics gives them a defined place.

**Alternatives considered**:
- *Topics below context files*: rejected — context files are deliberately terse and would then be wrong to treat as more authoritative than the detailed topic content.

**Sources**: Spec R6; codebase `prompts.ts` `STORE_PURPOSE_SECTION` and `maintenance.ts` `CONTRADICTION_DETECTION_SECTION`.

### KD4: Migration hook point — a bootstrap hook ordered before `init-memory-layout`

**Choice**: Register `migrate-memory-stores` as a memory-extension bootstrap hook, ahead of `init-memory-layout`, dispatching the fold via `app.agent.side`.

**Why**: The startup sequence (`src/app.ts`) makes this the *only* viable seam. The legacy migration subsystem (`adaptWorkspace`, `app.ts:57`) runs **before the `AgentManager` is constructed** (`app.ts:69`), so it cannot dispatch the agent-driven fold the spec requires. The first trunk-close (`coordinator.recoverStaleTrunks`/`closeTrunkIfDue`) runs after `channel.start` and violates the spec AC that the *first session's* memory index injection already reflect migrated topics. Bootstrap hooks run at `app.ts:98` — after the agent is ready, before `channel.start` (`app.ts:127`) — so the fold completes before any message is handled. Ordering the hook before `init-memory-layout` means the fold creates the topic files first and the layout hook then seeds/preserves their index.

**Alternatives considered**:
- *Migration subsystem (`adaptWorkspace`)*: rejected — agent infrastructure not yet constructed at that point; it is built for deterministic file ops (rename/copy), not LLM folds.
- *First trunk-close / first-session gate*: rejected — defers migration past the first session, contradicting R7's first-session AC.

**Sources**: `src/app.ts` startup ordering (lines 57, 69, 95, 98, 127); `src/extensions/api.ts` (`app.agent.side`, `app.db`, `app.git` available in setup); `src/extensions/memory/index.ts` (existing `init-memory-layout` bootstrap hook); `src/migration/index.ts` (subsystem runs pre-agent).

**Consequences**: Pro — runs exactly once, before any session; reuses the existing bootstrap seam. Con — an LLM call blocks startup on the migrated launch (one-time); acceptable for a migration and consistent with the spec's "once, at startup."

### KD5: Migration merge — fully agent-decided (one run over all old files)

**Choice**: A single agent side-run reads *all* old `facts/` + `preferences/` files plus any existing `topics/` files and decides the grouping/merging into broad topic files, reusing the established broad-topic-naming and consolidation conventions.

**Why**: A deterministic host-side filename heuristic cannot judge whether two files across stores describe the same subject (e.g. is `facts/work-info.md` the same subject as `preferences/communication-style.md`?). Semantic grouping is exactly what the extraction and maintenance agents already do, so the migration leans on the same capability rather than inventing brittle heuristic code.

**Alternatives considered**:
- *Host-side filename pre-grouping handed to the agent*: rejected — same-subject files across stores rarely share a prefix, and a wrong grouping either over-merges unrelated topics or leaves duplicates. The agent reading everything is simpler and more accurate.

**Sources**: Spec R7 ("agent folds … files about the same subject across both old stores merge"); codebase `extraction.ts` / `maintenance.ts` (agent-driven consolidation is the established pattern).

**Consequences**: Pro — accurate semantic merging; no heuristic to maintain. Con — one larger agent context on migration (bounded by old-store size, which is small in practice).

### KD6: Migration detection — state-based (old-store content presence), no persisted marker

**Choice**: Run the migration iff `facts/` or `preferences/` contains any non-empty `.md` file; it is a no-op once both are empty (and on fresh installs, which never create them). No DB key, file sentinel, or migration record is written.

**Why**: The empty-old-stores state is *intrinsically* the completion signal — it is reached only by the final sweep — so a separate completion marker is redundant. This mirrors the legacy migration subsystem's convention of detecting work by filesystem/database state rather than persisted flags (`sessions` table presence, `context/` dir presence). Keying on **old-content presence** (rather than `topics/` presence) is what makes an interrupted pass re-run correctly: after a fold that created `topics/` but crashed before the sweep, the old stores still hold content, so the check correctly re-runs; keying on `topics/`-absence would falsely read "done" in that mid-fold state.

**Re-run safety without a marker**: the fold is **merge/dedup** (re-folding into existing topic files updates rather than appends), and the **fold-before-empty** ordering means no old content is lost before its durable form exists in `topics/`. The pre-migration state is always git-recoverable (the stores are committed markdown). The two interruption/idempotency ACs were revised in the spec to describe this state-based behavior.

**Commit and failure semantics**: the migration makes **two commits** — one after the fold (so the folded topic files are durable in git *before* any old store is touched) and one after the sweep. This separates concerns so an interruption *between* fold and sweep still leaves the folded topics committed and the old content untouched (→ re-runs). Failure isolation is handled at two levels: (a) *soft* — a file the agent cannot parse is skipped per the prompt (it logs and continues folding the rest), leaving that file in the old store so it still has content and is retried on the next run; the fold then commits and the sweep proceeds for the files that were folded; (b) *hard* — if the agent run itself errors, the hook catches it, logs, and **aborts without sweeping**, so the old stores still contain content and the whole pass retries on the next startup (any partial topic writes are re-merged by the fold's dedup). Either way, no partial corruption is committed and no old content is lost.

**Alternatives considered**:
- *`topics/` presence as the trigger*: rejected — false "done" after a mid-fold crash (topics created, old stores not yet swept).
- *DB `app_state` completion key*: rejected — redundant given the filesystem already encodes completion; adds a second source of truth that could drift from the actual store state.
- *File sentinel (e.g. `topics/.migrated`)*: rejected — redundant for the same reason, and a hidden workspace artifact.

**Sources**: `src/migration/drop-sessions-table.ts` and `src/migration/context.ts` (state-based detection idiom); spec R7 + revised interruption/idempotency ACs. **User decision** (confirmed during design).

**Consequences**: Pro — no marker state to manage or drift; filesystem is the single source of truth; simplest possible detection. Con — a re-run after an interrupted fold relies on the agent's merge/dedup to avoid duplication (mitigated by merge instructions + the next maintenance pass pruning residual redundancy).

### KD7: No new external libraries; reuse existing infrastructure

**Choice**: Every mechanism reuses already-validated internal infrastructure — `node:fs` for file ops, the `SideRunner` for the agent fold, `app.git` for commits, and the legacy migration subsystem's state-detection idiom.

**Why**: This delta is an internal store-model restructuring. It introduces no new external dependency or library capability, so there is no external documentation whose currency could affect the design.

**Alternatives considered**: none applicable — no library selection is in scope.

**Sources**: codebase (`src/agent/side-run.ts` SideRunner; `src/extensions/memory/index.ts` `app.git`/`app.agent.side` usage; `src/migration/*` patterns). **External documentation search is not applicable** here — recorded as a considered judgment rather than an omission: the design adds no library and reuses only patterns already present and exercised by the existing tests.

**Consequences**: Pro — no supply-chain surface added; all behavior is testable against the existing test harness. Con — none.

### KD8: Keep maintenance minimal; defer richer consolidation to DLT-173

**Choice**: Unify the maintenance prompt and remove the misclassification logic, but do **not** add new phased consolidation. The `consolidatePhase` stays a marker-guarded interim no-op.

**Why**: R5 explicitly defers richer phased consolidation to DLT-173, which will replace the interim maintenance model. `close-pipeline.ts` is already a pluggable seam (its header documents that the phase bodies are swappable behind the same exported functions), so this delta changes only the store the existing prune body operates on.

**Sources**: Spec R5; codebase `close-pipeline.ts` (seam documentation + interim `consolidatePhase`); DELTAS.md DLT-173.

**Consequences**: Pro — small, focused change; leaves DLT-173 a clean slot. Con — topics maintenance is no richer than today's facts/preferences maintenance until DLT-173 lands.

## System Behavior

### Scenario: Fresh install

**Given** an empty workspace, **when** the memory extension bootstraps, **then** the `migrate-memory-stores` hook detects no `facts/`/`preferences/` content and is a no-op; `init-memory-layout` creates `memories/{topics,episodic,transcripts}/` and a header-only `topics/MEMORY.md`. No `facts/` or `preferences/` is ever created.
**Rationale**: Fresh installs never had the old stores, so detection correctly skips them (R7).

### Scenario: Legacy workspace migration (happy path)

**Given** a workspace with `facts/` and `preferences/` files and no `topics/`, **when** bootstrap runs, **then** the migration hook detects old content; one agent run folds every old file's durable content into `topics/` (same-subject fact+preference files merge into one topic; distinct subjects stay distinct), updates `topics/MEMORY.md`; the host sweeps the old stores; the result is committed. `init-memory-layout` then preserves the populated index. The first session's injected memory context shows the `## Topics Index`.
**Rationale**: One-time, lossless cutover (R7); first session sees migrated topics.

### Scenario: Migration interrupted mid-fold

**Given** the migration crashed after creating some `topics/` files but before sweeping the old stores, **when** the system restarts and the hook runs, **then** the old stores still contain content, so the pass re-runs; the agent re-folds, merging into the existing topic files rather than duplicating; then the old stores are swept. No data is lost (pre-migration state is git-recoverable).
**Rationale**: State-based detection makes an interrupted pass re-run cleanly without a persisted marker (KD6, revised interruption AC).

### Scenario: Migration file-level failure isolation

**Given** the agent errors while folding one old file (unreadable/garbled content), **when** the failure occurs, **then** it is logged; the run continues folding the remaining files and the failed file is left in place (still has content) so it is retried on the next run. No partial corruption is committed.
**Rationale**: A failure on one file must not lose or corrupt the others (R7).

### Scenario: Empty old file

**Given** a 0-byte or whitespace-only old file, **when** the migration runs, **then** it is skipped — no empty topic file is created.
**Rationale**: Don't create empty topics (R7); matches the existing `sweepEmptyMarkdown` blank-detection threshold.

### Scenario: Extraction folds a fact and a preference about the same subject

**Given** a closed branch where the user stated a stable fact and a related preference about the same subject, **when** extraction runs, **then** both signals land in the same topic file (create-or-merge); no classification self-check runs and nothing is routed between stores. `topics/MEMORY.md` is updated once.
**Rationale**: The unified store removes the routing decision (R0/R3).

### Scenario: Maintenance collapses a fragmented cluster

**Given** `topics/` has 3+ narrow files sharing a topic (e.g. per-incident leftovers that survived migration), **when** the prune phase runs, **then** they are consolidated into one broad-topic file; misclassification detection does **not** run (there is no second store).
**Rationale**: Cluster consolidation carries over; the misclassification backstop is gone (R5).

### Scenario: Static injection with a header-only or absent index

**Given** `topics/MEMORY.md` has only the `# Memory Index` header (or `memories/` is absent), **when** a message is handled, **then** the layout section is still injected but no `## Topics Index` section appears (empty content contributes nothing); malformed index lines are dropped silently while well-formed ones are kept.
**Rationale**: Carry-over behavior from the current injection (R4).

## Resolved During Design

- **Unified topic size guard — a single fixed ~50-line limit.** Facts used 40 lines, preferences 30; a unified topic legitimately holds more than either alone. Both the topics extraction and maintenance prompts state a single ~50-line guard (over-size → consolidate/prune within the file, or flag that the detail belongs in project docs/episodic). It is a prompt-stated constant, not a config value, consistent with today's fixed 40/30 limits.
- **Migration index authoring — the fold writes full descriptions.** The fold agent uses the shared `INDEX_UPDATE_SECTION` so `topics/MEMORY.md` carries accurate descriptions immediately. `init-memory-layout`'s seeding is idempotent and only fires when the index is absent (it preserves the fold's index otherwise).
