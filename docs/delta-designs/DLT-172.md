## Purpose

This document explains the design rationale for this delta: the modeling choices, data flow, system behavior, and architectural approach.

After implementation, the "Detected Impacts" section will guide reconciliation into feature design docs.

## Problem Context

Plugins currently accept no user configuration — they can only declare skills and metadata. Plugin authors have no mechanism to accept API keys, feature toggles, or endpoint URLs through Tachikoma's config system. Additionally, startup notifications (restart announcements) are dispatched independently, with no consolidation mechanism for other startup-time events like plugin load failures.

**Constraints:**
- User config values live in `[plugins.<alias>.config]` sub-tables in the existing TOML config file — no separate config files or environment variables.
- The manifest's `[config.<field_name>]` sections declare the schema; validation happens at load time.
- Plugins with invalid config fail to load with a diagnostic (consistent with existing fail-safe loading).
- The existing `extra="forbid"` on source models means config values must be an explicit field.
- Config values are typed at the TOML level — no string-to-bool coercion, but float-to-integer coercion for zero-fraction values (TOML integers and floats are distinct types).

**Interactions:**
- **`plugins/sources.py`** — source models gain a `config` field carrying raw user values from TOML.
- **`plugins/manifest.py`** — manifest parsing gains `[config.<field_name>]` section extraction.
- **`plugins/loader.py`** — discovery flow adds config validation after manifest parsing.
- **`plugins/tools.py`** — `list_plugins` output gains config info.
- **`config.py`** — `_validate_plugins` extracts `[plugins.<alias>.config]` sub-tables.
- **`__main__.py`** — startup notification consolidation replaces standalone restart notification dispatch.
- **`updates/rollback.py`** — `handle_restart_notification` gains plugin failure collection.

## Design Overview

Two concerns: (1) a typed config schema in the plugin manifest with validation and runtime access, and (2) a startup notification consolidation mechanism that merges restart announcements with plugin load failure summaries into a single delivered notification.

For concern 1, user config values flow through the existing `PluginSource` models via a new `config` field. The plugin manifest declares a schema in `[config.<field_name>]` sections. During discovery, the loader validates user values against the schema and produces either a validated config dict or failure diagnostics. Validated config is stored on `LoadedPlugin` for runtime access.

For concern 2, the existing `handle_restart_notification` function is extended to collect plugin failures from the `PluginManager` and merge them into a single notification dispatch, replacing the standalone restart announcement when both signals are present.

## Shape

| Part | Mechanism | Flag |
|------|-----------|:----:|
| **S1** | Config schema model — Pydantic `ConfigFieldSchema` model for declared settings (field name, type, description, default, required) parsed from manifest `[config.<field_name>]` sections, with `model_validator` enforcing schema validity (type validity, default type consistency, required/default mutual exclusion) | |
| **S2** | Config value extraction — `config: dict[str, Any] | None` field on each `PluginSource` variant; `_validate_plugins` in `config.py` extracts `[plugins.<alias>.config]` sub-table and attaches it to the source model | |
| **S3** | Config validation engine — `validate_config()` function takes schema + user values, performs type checking with float→integer coercion for zero-fraction values (`isinstance(v, float) and v.is_integer()`), required field enforcement, default application, unknown key warning; always returns `ConfigValidationResult` — never raises | |
| **S4** | Runtime config access — `config: dict[str, str | int | bool | float]` field on `LoadedPlugin` holding validated values; empty dict when no schema or no user values | |
| **S5** | Config surfacing in list_plugins — per-plugin `config` key in MCP tool output with schema (type, description, default, required), current user value, and validation diagnostics for failed plugins | |
| **S6** | Startup notification consolidation — `handle_restart_notification` in `rollback.py` gains plugin failure collection from `PluginManager.failed_plugins()` property; merges restart content + plugin failure summary into a single `dispatch_notification` call | |
| **S7** | Plugin failure integration — `PluginManager` gains a `failed_plugins()` method returning `list[LoadedPlugin]` filtered by `status != "loaded"`; config validation failures contribute alongside manifest/source failures during discovery | |

## Components

### Implementation Structure

| Layer/Component | Responsibility | Key Decisions |
|-----------------|----------------|---------------|
| `plugins/config_schema.py` (new) | `ConfigFieldSchema` Pydantic model; `validate_config()` function; `ConfigDiagnostic` dataclass | New module keeps config logic separate from manifest and loader; follows project pattern of small focused modules |
| `plugins/manifest.py` (extend) | Parse `[config.<field_name>]` sections from `tachikoma-plugin.toml`; return schema dict alongside existing manifest data | `TachikomaManifest` gains `config: dict[str, ConfigFieldSchema]` field; CC plugins have no config schema support |
| `plugins/loader.py` (extend) | Call `validate_config()` after manifest parsing; set `LoadedPlugin.config` on success or mark plugin as failed with diagnostic | Validation sits in discovery flow, same location as existing manifest validation |
| `plugins/sources.py` (extend) | Add `config: dict[str, Any] | None = None` to each source model | Explicit field on existing frozen models; `None` = no user config provided |
| `plugins/tools.py` (extend) | Extend `handle_list_plugins` output with config schema/values/diagnostics | Additive change to existing output structure |
| `plugins/manager.py` (extend) | Add `failed_plugins()` property; no changes to install/remove flows | Read-only filter over existing `_loaded` dict |
| `config.py` (extend) | Extract `[plugins.<alias>.config]` sub-tables in `_validate_plugins` and attach to source models | Source models already accept extra fields explicitly; config dict passed through as-is (raw TOML values) |
| `updates/rollback.py` (extend) | `handle_restart_notification` accepts optional plugin manager; collects failures; merges content | Replaces standalone dispatch with consolidated one |
| `__main__.py` (extend) | Pass plugin manager to `handle_restart_notification` | Single line change; manager already available in bootstrap extras |

### Cross-Layer Contracts

**Config value flow (config.toml → LoadedPlugin.config):**

```
config.toml                          Settings model
[plugins.weather]                    GitPluginSource(
git = "https://..."                      git="...", ref="main",
ref = "main"                              config={"api_key": "sk-...", "timeout": 60}
                                           )
[plugins.weather.config]
api_key = "sk-..."
timeout = 60

    ↓ _validate_plugins in config.py
    ↓ extract config sub-table, attach to source

plugins_hook                          loader._discover_one
reconcile → discover                     parse_manifest → PluginManifest
                                          + config_schema dict
    ↓
    ↓ validate_config(schema, user_values)
    ↓ → validated dict or diagnostics

LoadedPlugin(
    alias="weather",
    config={"api_key": "sk-...", "timeout": 60},
    status="loaded"
)
```

**Startup notification consolidation flow:**

```
__main__.py (after bootstrap.run(), before channel.run())
    ├── restart_notification = read_restart_notification()
    ├── rollback_was_dispatched = ...
    ├── plugin_manager = bootstrap.extras["plugin_manager"]
    └── handle_restart_notification(bus, restart_notification,
            rollback_was_dispatched, plugin_manager)
            ├── clear_restart_notification()  # DES-011 consume-once
            ├── Build restart content (if marker exists + no rollback)
            ├── Collect failed_plugins from manager
            ├── Build plugin failure summary (if any failures)
            ├── Merge into single content string
            └── dispatch_notification(bus, ...)  # single dispatch
```

**Integration Points:**
- `config.py` ↔ `sources.py`: `_validate_plugins` sets `config` field on source models before they reach the plugin hooks
- `manifest.py` ↔ `config_schema.py`: manifest parsing produces `ConfigFieldSchema` dict consumed by validation
- `loader.py` ↔ `config_schema.py`: discovery calls `validate_config()` using schema from manifest + values from source
- `rollback.py` ↔ `manager.py`: `handle_restart_notification` reads `failed_plugins()` for consolidation

### Shared Logic

- **`ConfigFieldSchema`**: Pydantic model shared between manifest parsing (produces it) and config validation (consumes it). Lives in `config_schema.py` to avoid circular imports between `manifest.py` and validation logic.
- **`ConfigDiagnostic`**: Frozen dataclass used by validation to report issues. Consumed by loader (sets `LoadedPlugin.diagnostic`) and tools (surfaces in `list_plugins` output).
- **Type coercion map**: `_TYPE_CHECKERS` mapping from string type literals to validation functions. Shared between schema self-validation (checking default type) and user-value validation.

## Modeling

### ConfigFieldSchema

```
ConfigFieldSchema (frozen Pydantic, extra="forbid")
├── type: Literal["string", "integer", "boolean", "float"]
├── description: str
├── default: str | int | bool | float | None = None
├── required: bool = False
│
├── @model_validator(mode="after")
│   ├── If required=true AND default is not None → ValueError
│   └── If default is not None AND type(default) doesn't match declared type → ValueError
```

### ConfigDiagnostic

```
ConfigDiagnostic (frozen dataclass)
├── field: str | None          # None for non-field errors (e.g., "unknown key")
├── message: str               # Human-readable diagnostic
```

### Validation result

```
ConfigValidationResult (frozen dataclass)
├── values: dict[str, str | int | bool | float]   # Validated values (populated for valid fields even when diagnostics exist)
├── diagnostics: list[ConfigDiagnostic]            # Non-empty = validation failure
├── unknown_keys: list[str]                         # Logged as warnings, not errors
└── is_valid: bool (property)                       # True when diagnostics is empty
```

`validate_config()` always returns a `ConfigValidationResult` — never raises. When `is_valid` is false, `values` contains the subset of fields that passed validation (for diagnostic context), and `diagnostics` lists the failures. The caller checks `is_valid` to decide whether to use `values` or report the diagnostics.

### Extended PluginSource models

```
GitPluginSource (frozen Pydantic, extra="forbid")
├── git: str
├── subdir: str | None = None
├── ref: str
└── config: dict[str, Any] | None = None     # NEW — raw user values from TOML

UrlPluginSource / LocalPluginSource — same pattern (config field added)
```

### Extended TachikomaManifest

```
TachikomaManifest (frozen Pydantic, extra="forbid")
├── name: str
├── version: str | None = None
├── description: str
├── skills: list[str] = []
└── config: dict[str, ConfigFieldSchema] = {}   # NEW — config schema from manifest
```

### Extended PluginManifest

```
PluginManifest (frozen dataclass)
├── name: str
├── version: str | None
├── description: str | None
├── source_format: Literal["tachikoma", "cc"]
├── skill_dirs: list[Path]
├── ignored_cc_contributions: list[str]
└── config_schema: dict[str, ConfigFieldSchema]   # NEW — empty dict for CC plugins
```

### Extended LoadedPlugin

```
LoadedPlugin (frozen dataclass)
├── alias: str
├── source: PluginSource
├── manifest: PluginManifest | None
├── status: Literal["loaded", "stale-fallback", "failed"]
├── diagnostic: str | None
├── plugin_dir: Path
├── contributed_skills: list
└── config: dict[str, str | int | bool | float]   # NEW — validated values; empty dict if no schema
```

## Data Flow

### Manifest config schema extraction

```
_parse_native(plugin_dir, manifest_path)
    ├── tomllib.loads(manifest content)
    ├── TachikomaManifest.model_validate(data)
    │       └── config field: each [config.<field_name>] sub-table
    │           parsed into ConfigFieldSchema via Pydantic
    │           (type validity, default type check, required/default exclusion)
    ├── Resolve skill paths (existing)
    └── PluginManifest(
            ...,
            config_schema=parsed.config,   # dict[str, ConfigFieldSchema]
        )
```

### User config value extraction

```
Settings._validate_plugins(data)
    ├── For each [plugins.<alias>] entry:
    │   ├── Extract source fields → parse_plugin_source(source_data)
    │   ├── Extract config sub-table (if present):
    │   │   config_values = value.get("config", None)
    │   │   if config_values is dict:
    │   │       source.config = config_values
    │   └── validated[alias] = source_with_config
    └── raw["plugins"] = validated
```

### Config validation during discovery

```
_discover_one(outcome, install_dir, plugin_sources)
    ├── Existing: parse manifest, validate skill dirs
    ├── NEW: if manifest has config_schema:
    │   ├── user_values = source.config or {}
    │   ├── result = validate_config(manifest.config_schema, user_values)
    │   ├── if not result.is_valid:
    │   │   └── return LoadedPlugin(status="failed",
    │   │           diagnostic=format_diagnostics(result.diagnostics), ...)
    │   └── validated_config = result.values
    ├── else:
    │   └── validated_config = {}
    └── return LoadedPlugin(..., config=validated_config)
```

### Startup notification consolidation

```
async handle_restart_notification(bus, restart_notification, rollback_was_dispatched, plugin_manager=None)
    ├── if restart_notification is not None:
    │   └── clear_restart_notification()  # DES-011 consume-once
    ├── parts = []
    ├── if restart_notification AND not rollback_was_dispatched:
    │   └── parts.append(build_back_online_content(restart_notification))
    ├── if plugin_manager is not None:
    │   └── failed = plugin_manager.failed_plugins()
    │       if failed:
    │           summary = format_plugin_failures(failed)
    │           └── parts.append(summary)
    ├── if parts:
    │   └── await dispatch_notification(bus, source=..., content="\n\n".join(parts), ...)
    └── return
```

Note: The early return is based on whether `parts` is empty after checking both sources, not on whether `restart_notification` alone is None. This ensures plugin failures without a restart marker still produce a notification.

## Key Decisions

### Config values on PluginSource models (Option B)

**Choice**: Add `config: dict[str, Any] | None = None` to each source model variant, rather than a separate top-level `plugin_user_config` field on `Settings`.

**Why**: Keeps user config values co-located with their plugin source declaration. The entire plugin definition (source + user values) travels together through the pipeline — from config parsing through discovery to the `LoadedPlugin`. Avoids threading a parallel dict through hooks and into the loader.

**Alternatives Considered**:
- Separate `plugin_user_config: dict[str, dict[str, Any]]` on `Settings`: Cleaner separation (source models stay source-only), but requires parallel threading through the bootstrap hook chain and into the loader. Adds a field to `Settings` that only the plugin subsystem cares about.
- Config values on `LoadedPlugin` during construction (lazy extraction): Would require the loader to reach back into `SettingsManager` to read TOML directly, breaking the clean data flow where settings are consumed through the `PluginSource` models.

**Consequences**:
- Pro: Single dict per alias in `settings.plugins` carries everything; no parallel threading needed.
- Pro: Install flow already constructs source models — config values from the install call are naturally included.
- Con: Source models gain a field unrelated to their source-variant responsibility (mitigated: the field is optional and nullable, defaulting to None for existing plugins).

### New `config_schema.py` module

**Choice**: Create `plugins/config_schema.py` with the `ConfigFieldSchema` model, `validate_config()` function, and supporting types, rather than embedding validation in `manifest.py` or `loader.py`.

**Why**: The config schema concern is self-contained — it has its own types (`ConfigFieldSchema`, `ConfigDiagnostic`, `ConfigValidationResult`), its own validation logic (type checking, coercion, default application), and is consumed from two places (manifest parsing produces schemas, loader validates values against them). A dedicated module avoids bloating `manifest.py` (which is already focused on parsing) or `loader.py` (which orchestrates discovery).

**Alternatives Considered**:
- Embed in `manifest.py`: Would couple manifest parsing with validation logic. The manifest module's responsibility is parsing manifests — validation of user values against schemas is a different concern.
- Embed in `loader.py`: The loader orchestrates discovery; mixing in validation types and logic would make it harder to test in isolation.

**Consequences**:
- Pro: Testable in isolation — unit tests for validation logic don't need manifest fixtures or loader setup.
- Pro: Clean imports — `manifest.py` imports `ConfigFieldSchema`, `loader.py` imports `validate_config`.
- Con: One more file in the plugins package (mitigated: small focused module, follows project pattern).

### No config schema support for CC plugins

**Choice**: Only `tachikoma-plugin.toml` manifests support `[config]` sections. Claude Code plugins (`.claude-plugin/plugin.json`) have no config schema — `config_schema` is always an empty dict for CC-format plugins.

**Why**: CC plugins use JSON manifests with their own schema. Adding config schema support would require inventing a JSON equivalent of `[config.<field_name>]` sections that doesn't exist in the CC spec. Since CC plugins are a compatibility layer (non-skill contributions are already silently ignored), omitting config is consistent.

**Consequences**:
- Pro: No CC schema invention needed; clean implementation boundary.
- Pro: CC plugins install and work normally — they just don't accept configuration.
- Con: CC plugin authors who want config must provide a `tachikoma-plugin.toml` (which takes precedence anyway per AC-MP-5).

### Float-to-integer coercion for zero-fraction values

**Choice**: When a field declares `type = "integer"` and the user provides a TOML float with zero fraction (e.g., `30.0`), coerce to integer `30`. Reject non-zero-fraction floats (e.g., `30.5`).

**Why**: TOML distinguishes integers from floats at the parse level, but some TOML generators or copy-paste scenarios may produce `30.0` for what the user intends as an integer. Rejecting `30.0` would be pedantic and frustrating. Rejecting `30.5` catches genuine mistakes.

**Alternatives Considered**:
- No coercion at all (strict type matching): `30.0` would fail for `type = "integer"`. Surprising UX for users whose TOML editor auto-adds `.0`.
- Coerce all numeric types: `30` for `type = "float"` would become `30.0`. Less justified — TOML integers and floats are distinct, and `30` for a float field is more likely a user mistake.

**Consequences**:
- Pro: Forgiving for the common zero-fraction case while still catching real mistakes.
- Con: Asymmetric — only float→integer coercion, not integer→float.

### `handle_restart_notification` extension over new function

**Choice**: Extend the existing `handle_restart_notification` in `rollback.py` to accept an optional `PluginManager` and consolidate plugin failures into the same notification, rather than creating a new `dispatch_startup_notifications()` function in `__main__.py`.

**Why**: The restart notification handler already owns the DES-011 consume-once logic and the conditional dispatch (skip if rollback was dispatched). Adding plugin failure collection there keeps all startup notification logic in one place. A new function in `__main__.py` would duplicate the conditional logic or require the existing handler to be split.

**Alternatives Considered**:
- New `dispatch_startup_notifications()` in `__main__.py`: Would need to duplicate the restart marker handling or call the existing handler and then separately dispatch plugin failures — resulting in two dispatches (defeating consolidation).
- Plugin manager dispatches its own notification: Would fire independently, no consolidation possible.

**Consequences**:
- Pro: Single function owns all startup notification composition.
- Pro: DES-011 consume-once semantics preserved without duplication.
- Con: `rollback.py` gains a dependency on `PluginManager` type (mitigated: optional parameter, `TYPE_CHECKING` import).

## System Behavior

### Invariants

1. **Config values are always validated**: A loaded plugin's `config` dict contains only values that passed type checking. No unvalidated user input reaches plugin code.
2. **Config schema is optional**: Plugins without `[config]` sections load normally with `config = {}`. Users without `[plugins.<alias>.config]` sub-tables get default values (or empty dict if no schema).
3. **Fail-safe config validation**: Config validation failures mark the plugin as `failed` with a diagnostic, consistent with existing manifest and source validation failures. Other plugins are unaffected.
4. **Startup notification is at-most-once**: DES-011 consume-once semantics apply. The restart marker is cleared before dispatch. No re-fire on subsequent startups.
5. **Consolidation is additive**: Plugin failures are appended to the restart notification. Each can appear independently (restart only, failures only, both, neither).

### Scenario: Plugin with required config field, user provides value

**Given**: Manifest declares `[config.api_key]` with `type = "string"`, `required = true`. User config has `[plugins.weather.config]` with `api_key = "sk-..."`.
**When**: Plugin discovery runs.
**Then**: `validate_config()` finds the required field present with correct type. `LoadedPlugin.config = {"api_key": "sk-..."}`.
**Rationale**: Happy path — user provides all required config.

### Scenario: Plugin with required config field, user omits value

**Given**: Manifest declares `[config.api_key]` with `type = "string"`, `required = true`. User config has no `[plugins.weather.config]` section.
**When**: Plugin discovery runs.
**Then**: `validate_config()` produces a diagnostic: "Required config field 'api_key' is missing". Plugin status is `"failed"` with the diagnostic.
**Rationale**: Fail-safe — required fields must be provided. The diagnostic names the missing field so the user can fix it.

### Scenario: Type mismatch on user value

**Given**: Manifest declares `[config.timeout]` with `type = "integer"`. User provides `timeout = "thirty"` (a string).
**When**: Plugin discovery runs.
**Then**: `validate_config()` produces a diagnostic: "Config field 'timeout' expects type integer, got str". Plugin status is `"failed"`.
**Rationale**: Strict type checking prevents runtime errors in plugin code.

### Scenario: Unknown user config key

**Given**: Manifest declares `[config.api_key]`. User provides both `api_key = "sk-..."` and `base_url = "https://..."` (undeclared).
**When**: Plugin discovery runs.
**Then**: `api_key` is validated normally. `base_url` triggers a WARNING log. Plugin status is `"loaded"`. `base_url` is NOT included in `LoadedPlugin.config`.
**Rationale**: Forward-compatible — unknown keys are likely from a newer plugin version or user typo. Warning (not failing) prevents brittle behavior when plugin versions change.

### Scenario: Plugin with all-default config, no user values

**Given**: Manifest declares `[config.timeout]` with `type = "integer"`, `default = 30` and `[config.debug]` with `type = "boolean"`, `default = false`. No `[plugins.weather.config]` section in user config.
**When**: Plugin discovery runs.
**Then**: `LoadedPlugin.config = {"timeout": 30, "debug": false}`.
**Rationale**: Defaults apply when no user values are present.

### Scenario: Optional field with no default and no user value

**Given**: Manifest declares `[config.region]` with `type = "string"`, no `required`, no `default`. No user value provided.
**When**: Plugin discovery runs.
**Then**: `LoadedPlugin.config` does not contain `"region"` key. Plugin loads normally.
**Rationale**: Optional without default means "absent if not provided" — the plugin checks `if "region" in config`.

### Scenario: Optional string field with empty string value

**Given**: Manifest declares `[config.api_key]` with `type = "string"`, no `required`, no `default`. User provides `api_key = ""` (empty string) in config.
**When**: Plugin discovery runs.
**Then**: `LoadedPlugin.config = {"api_key": ""}`. The empty string is a valid string value — it is distinct from key absence (no user value provided at all).
**Rationale**: TOML's `api_key = ""` produces an empty string, which is a valid value. The validation engine treats it as a present value of the correct type. Only key absence triggers the "missing required field" path.

### Scenario: Boolean field with required=true

**Given**: Manifest declares `[config.enabled]` with `type = "boolean"`, `required = true`, no `default`.
**When**: User provides no value. Plugin discovery runs.
**Then**: Validation produces diagnostic: "Required config field 'enabled' is missing". Plugin fails to load.
**Rationale**: Boolean fields can be required — the plugin author decides whether the setting must be explicitly provided. Without `required`, a boolean field with no user value and no default is simply absent from the config dict.

### Scenario: CC plugin with user config values

**Given**: A Claude Code plugin (`.claude-plugin/plugin.json`) with no `tachikoma-plugin.toml`. User provides `[plugins.cc-plugin.config]` with `key = "value"` in TOML config.
**When**: Plugin discovery runs.
**Then**: CC manifest has no config schema (empty dict). The user-provided config dict is present on the source model but `validate_config({}, {"key": "value"})` finds no schema to validate against. The unknown keys are logged as warnings. Plugin loads normally with `config = {}`.
**Rationale**: User config for a CC plugin without a schema is harmlessly ignored — consistent with how CC plugins handle other Tachikoma-specific features. The warning guides the user to check if the plugin supports configuration.

### Scenario: Schema self-validation — unsupported type value

**Given**: Manifest declares `[config.items]` with `type = "array"` (not a supported type).
**When**: The manifest is parsed (`TachikomaManifest.model_validate`).
**Then**: Pydantic's `Literal` validation rejects the value. The error is caught by `_parse_native`, wrapped into a manifest parse failure, and the plugin is marked `"failed"` with a diagnostic including the invalid type and the list of valid types (string, integer, boolean, float).
**Rationale**: Pydantic's `Literal` type naturally catches unsupported types at parse time. The error formatting includes the list of valid types to guide the plugin author.

### Scenario: Schema self-validation — required + default conflict

**Given**: Manifest declares `[config.api_key]` with `required = true` and `default = "fallback"`.
**When**: The manifest is parsed (`TachikomaManifest.model_validate`).
**Then**: Validation fails with error: "Config field 'api_key' declares both required=true and a default value. Required fields cannot have defaults."
**Rationale**: The spec says required fields must not have defaults — the two are semantically contradictory.

### Scenario: Schema self-validation — default type mismatch

**Given**: Manifest declares `[config.timeout]` with `type = "integer"` and `default = "thirty"` (a string).
**When**: The manifest is parsed.
**Then**: Validation fails with error: "Default value for 'timeout' has type str, expected integer."
**Rationale**: Catching schema errors early — at manifest parse time — gives plugin authors clear feedback.

### Scenario: Consolidated startup notification — restart + plugin failures

**Given**: Restart notification marker exists (update restart). Two plugins failed config validation during bootstrap.
**When**: `handle_restart_notification` runs after bootstrap completes.
**Then**: Restart marker is cleared (DES-011). A single notification is dispatched with content: "Tachikoma is back online after an update restart (upgraded from X to Y).\n\nPlugin startup issues:\n- weather: Required config field 'api_key' is missing\n- analytics: Config field 'timeout' expects type integer, got str"
**Rationale**: Single message is less noisy than two separate notifications. User sees everything that needs attention at once.

### Scenario: Startup notification — plugin failures only, no restart

**Given**: No restart notification marker. One plugin failed config validation.
**When**: `handle_restart_notification` runs.
**Then**: No restart content. Plugin failure summary is dispatched as a standalone notification.
**Rationale**: Plugin failures are worth notifying even without a restart signal.

### Scenario: Startup notification — manual restart with plugin failures

**Given**: Restart notification marker exists with `reason = "manual"`. One plugin failed config validation.
**When**: `handle_restart_notification` runs.
**Then**: Restart marker is cleared. Consolidated notification dispatched: "Tachikoma is back online after a manual restart.\n\nPlugin startup issues:\n- weather: Required config field 'api_key' is missing".
**Rationale**: Consolidation applies to both "update" and "manual" restart reasons — any startup that has both signals merges them.

### Scenario: Startup notification — no restart, no failures

**Given**: No restart notification marker. All plugins loaded successfully.
**When**: `handle_restart_notification` runs.
**Then**: No notification dispatched.
**Rationale**: No news is good news — don't notify when everything is fine.

### Scenario: list_plugins shows config for loaded plugin

**Given**: A loaded plugin with `config = {"api_key": "sk-...", "timeout": 30}` and schema declaring both fields.
**When**: `list_plugins` is invoked.
**Then**: Output includes:

## Notes
- No new dependencies required — uses existing Pydantic for models, `tomllib` for manifest parsing, `tomlkit` for config write-back.
- CC plugin compatibility maintained — CC plugins simply have no config schema (empty dict), loading and working normally.
- The `config` field on source models is deliberately `dict[str, Any] | None` (not typed) because user values haven't been validated yet — they're raw TOML values that get validated against the schema during discovery.
- Config values are NOT reloaded at runtime — changes to `config.toml` require a restart (per spec's out-of-scope note on runtime reload).
