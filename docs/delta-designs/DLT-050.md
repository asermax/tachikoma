## Purpose

This document explains the design rationale for this delta: the modeling choices, data flow, system behavior, and architectural approach.

After implementation, the "Detected Impacts" section will guide reconciliation into feature design docs.

## Problem Context

Plugins cannot contribute session-level post-processors. Currently only built-in processors (episodic memory extraction, facts/preferences extraction, git commits, etc.) participate in the `PostProcessingPipeline`. Plugin developers need the ability to run custom extraction, side effects, or integrations after a conversation session closes — for example, syncing action items to a task tracker or sending summaries to a webhook.

The plugin system already supports context provider contributions via a well-established pattern: manifest declaration → module validation → `LoadedPlugin` field → lifecycle event wiring. This delta extends that same pattern to post-processors.

Constraints:
- Must not break existing built-in processor registration (backward compat for `phase=` parameter)
- Plugin post-processors follow the same error isolation as built-in processors
- Manifest field naming must be extensible for DLT-171 (per-message post-processors) without rework
- `PromptDrivenProcessor` subclasses need `agent_defaults` injection at instantiation
- `AgentDefaults` is not available during bootstrap discovery — it's created after bootstrap in `__main__.py`. Validation and instantiation must accommodate this.

## Design Overview

The design follows the existing plugin contribution pattern established by context providers, with two additional concerns: phase declaration and `agent_defaults` injection.

**Phase as class attribute**: `PostProcessor` gains a `phase` class attribute defaulting to `MAIN_PHASE`. `PostProcessingPipeline.register()` uses a sentinel default to detect when no explicit `phase` argument is passed, reading the class attribute instead. This preserves backward compatibility with existing call sites. Built-in processors are refactored to declare their phase as a class attribute and remove the explicit `phase=` argument.

**Manifest extension**: `TachikomaManifest` and `PluginManifest` gain a `post_processors: dict[str, str]` field mapping processor names to module names. CC manifests with `post_processors` silently ignore it (added to `_CC_CONTRIBUTION_TYPES`).

**Validation and instantiation**: A new `_validate_post_processors()` function mirrors `_validate_providers()`. It receives `AgentDefaults` as a parameter (from the caller chain). During initial bootstrap discovery, `plugins_hook()` creates `AgentDefaults` via `agent_defaults_from_settings(settings)` before calling `discover()` — this is a pure function that only needs settings, which are already available. The same `AgentDefaults` instance is stored in `PluginManager` for reuse during runtime install/update operations.

**Lifecycle**: `register_plugin_provider_listeners` gains a `PostProcessingPipeline` parameter and registers/unregisters plugin post-processors on `PluginInstalled`/`PluginRemoving` events.

**Unregister**: `PostProcessingPipeline` gains `unregister()` matching the `PreProcessingPipeline.unregister()` pattern — identity-based removal, safe no-op, no lock needed (lifecycle events are serialized by the plugin manager's async lock).

## Components

### Implementation Structure

| Layer/Component | Responsibility | Key Decisions |
|-----------------|----------------|---------------|
| **PostProcessor** (ABC) | Base class for all processors | Add `phase: str = MAIN_PHASE` class attribute |
| **PostProcessingPipeline** | Orchestrates phased processor execution | Add `unregister()`; update `register()` with sentinel default to read class attribute |
| **TachikomaManifest** (Pydantic) | Native manifest schema | Add `post_processors` dict field with bare module name validation |
| **PluginManifest** (dataclass) | Unified manifest consumed by loader | Add `post_processors` dict field |
| **loader.py (_validate_post_processors)** | Validate and instantiate plugin processors | Mirror `_validate_providers()` with added phase/agent_defaults checks. Receives `AgentDefaults` as parameter. |
| **LoadedPlugin** (dataclass) | Plugin discovery result | Add `post_processors: list[PostProcessor]` field |
| **hooks.py (plugins_hook)** | Bootstrap hook for plugin discovery | Create `AgentDefaults` from settings, pass to `discover()` |
| **PluginManager** | Runtime plugin operations | Store `AgentDefaults`, pass to validation during install/update |
| **provider_listeners.py** | Lifecycle event wiring | Accept `PostProcessingPipeline`, wire register/unregister |

### Cross-Layer Contracts

**`register()` signature change** (S1):
```python
_UNSET = object()

def register(self, processor: PostProcessor, phase: str | object = _UNSET) -> None:
    if phase is _UNSET:
        phase = processor.phase
    if phase not in _VALID_PHASES:
        valid_list = ", ".join(sorted(_VALID_PHASES))
        raise ValueError(f"Invalid phase '{phase}'. Valid phases: {valid_list}")
    self._phases[phase].append(processor)
```

**`_validate_post_processors()` contract** (S4):
```python
def _validate_post_processors(
    manifest: PluginManifest,
    plugin_dir: Path,
    alias: str,
    validated_config: dict[str, Any],
    agent_defaults: AgentDefaults,          # Required: caller must provide
) -> list[PostProcessor]:
```

**AgentDefaults availability chain** (S8):
```
plugins_hook(ctx)
  → agent_defaults = agent_defaults_from_settings(ctx.settings_manager.settings)
  → discover(install_dir, report, settings.plugins, agent_defaults)
    → _discover_one(..., agent_defaults)
      → _validate_post_processors(manifest, plugin_dir, alias, validated_config, agent_defaults)
  → PluginManager(..., agent_defaults=agent_defaults)  # store for runtime reuse
```

**Integration Points**:
- `PostProcessingPipeline.register()` reads `processor.phase` when no explicit `phase` kwarg → `PostProcessor` must have `phase` attribute before registration
- `_validate_post_processors()` receives `AgentDefaults` from caller → passed conditionally to processors whose `__init__` accepts it
- `register_plugin_provider_listeners()` receives `PostProcessingPipeline` → calls `register()`/`unregister()` on plugin lifecycle events

**Error handling strategy**:
- Validation failures during discovery fail the plugin (same as context providers) — `LoadedPlugin.status = "failed"` with diagnostic
- Phase validation happens in `_validate_post_processors()` during discovery (fail fast at plugin load time), NOT at pipeline registration time
- Runtime failures in plugin processors are handled by existing pipeline error isolation (`asyncio.gather(return_exceptions=True)`)
- `unregister()` is a safe no-op (never raises)

### Shared Logic

- **`_import_handler_module()`**: Reused from existing loader infrastructure for importing plugin modules
- **`_validate_bare_module_names()`**: Reused from manifest validation for module name constraints
- **`agent_defaults_from_settings()`**: Already exists in `agent_defaults.py`, called from `plugins_hook()` (currently only called from `__main__.py`)
- **Phase constants** (`MAIN_PHASE`, `PRE_FINALIZE_PHASE`, `FINALIZE_PHASE`, `_VALID_PHASES`): Already defined in `post_processing.py`, imported by loader during validation

### Directory Convention

Plugin post-processor modules live at `plugin_dir/post_processors/<module_name>.py`, matching the manifest key name (consistent with `context_providers/` convention).

## Data Flow

### AgentDefaults Availability (S8)

`AgentDefaults` is needed during post-processor instantiation but is currently created after bootstrap in `__main__.py`. The solution: create it in `plugins_hook()` (which has access to settings) and thread it through the discovery chain.

```
plugins_hook(ctx):
  settings = ctx.settings_manager.settings
  agent_defaults = agent_defaults_from_settings(settings)  # pure function
  discover(install_dir, report, settings.plugins, agent_defaults)
  manager = PluginManager(..., agent_defaults=agent_defaults)
```

For runtime install/update, `PluginManager` uses its stored `agent_defaults`:
```
PluginManager.install(alias, source):
  # ... reconcile, materialize ...
  _validate_post_processors(manifest, staging, alias, validated_config, self._agent_defaults)
```

Note: `__main__.py` continues creating its own `AgentDefaults` for built-in processors. The two instances are identical (frozen dataclass from same settings) but separate — no shared state needed.

### Plugin Discovery (startup)

```
1. plugins_hook(ctx) in hooks.py
   ├─ create AgentDefaults from settings
   └─ discover(install_dir, report, settings.plugins, agent_defaults)

2. _discover_one() in loader.py
   ├─ parse manifest → PluginManifest with post_processors dict
   ├─ validate config schema
   ├─ _validate_handlers() (existing)
   ├─ _validate_providers() (existing)
   ├─ _validate_post_processors(manifest, plugin_dir, alias, validated_config, agent_defaults) (NEW)
   │   ├─ for each module_name in manifest.post_processors.values():
   │   │   ├─ import module from plugin_dir/post_processors/<name>.py
   │   │   ├─ find concrete PostProcessor subclasses (skip abstract)
   │   │   ├─ validate __init__ accepts "config"
   │   │   ├─ validate phase attribute value against _VALID_PHASES
   │   │   ├─ build kwargs: config=validated_config
   │   │   ├─ if __init__ also accepts "agent_defaults": add agent_defaults=agent_defaults
   │   │   └─ instantiate: cls(**kwargs)
   │   └─ return list[PostProcessor]
   └─ build LoadedPlugin with post_processors field

3. register_plugin_provider_listeners subscribes to events
   ├─ on PluginInstalled: register each processor into PostProcessingPipeline
   └─ on PluginRemoving: unregister each processor from PostProcessingPipeline
```

### Runtime Pipeline Execution (unchanged)

```
PostProcessingPipeline.run(session)
  for phase in [main, pre_finalize, finalize]:
    processors = self._phases[phase]  # includes plugin processors
    await asyncio.gather(*[_run_one(p) for p in processors], return_exceptions=True)
```

Plugin processors participate identically to built-in processors — same error isolation, same phase execution order, same context summary injection. Plugin processors extending `PromptDrivenProcessor` inherit DES-004 behavior (resumption augmentation, context summary injection, permission scoping) automatically via the base class's `process()` method.

### Plugin Removal

```
1. PluginRemoving event fires (before directory deletion)
2. on_plugin_removing handler:
   ├─ lookup LoadedPlugin from plugin_manager.loaded_plugins()
   └─ for each processor in plugin.post_processors:
       └─ PostProcessingPipeline.unregister(processor)  # identity-based, safe no-op
3. PluginRemoved event fires
4. Directory cleanup
```

`unregister()` is safe to call while `run()` is executing: it removes the processor from the phase list for future runs, but any currently executing processor completes its `process()` call. This matches the `PreProcessingPipeline.unregister()` behavior — no lock needed because lifecycle events are serialized by the plugin manager's async lock.

## Key Decisions

### Phase as class attribute with backward-compatible parameter

**Choice**: Add `phase: str = MAIN_PHASE` as a class attribute on `PostProcessor`. Update `register()` to use a private sentinel `_UNSET = object()` as the default — when no explicit `phase` kwarg is provided, read `processor.phase`; when provided, use the explicit value.

**Why**: The spec requires phase to be a class attribute (R1) so plugin developers declare it on their class. But existing call sites use `register(SomeProcessor(), phase=PRE_FINALIZE_PHASE)` and must continue working without modification. A sentinel default cleanly distinguishes "not passed" from "passed as MAIN_PHASE".

**Alternatives Considered**:
- Remove the `phase` parameter entirely: Would break all existing call sites (7 registrations in `__main__.py`)
- Use `None` as default: Ambiguous — `None` could mean "not passed" or "explicitly passed None"

**Consequences**:
- Pro: Built-in processor registrations work unchanged until refactored at convenience
- Pro: Plugin processors declare their phase declaratively on the class
- Con: Two ways to set phase (class attribute vs parameter) — but the parameter is only for backward compat

### Manifest field naming for DLT-171 extensibility

**Choice**: Use `post_processors` as the manifest key for session-level post-processors. DLT-171 will add `message_post_processors` as a separate key.

**Why**: Session-level and per-message post-processors are fundamentally different — different pipeline, different interface (`PostProcessor` vs `MessagePostProcessor`), different lifecycle. Separate keys make the manifest self-documenting. The `post_processors` name is generic enough that it doesn't need rework when DLT-171 lands; it simply gains a sibling key.

**Alternatives Considered**:
- Single `post_processors` key with ABC detection (like context_providers): Would conflate two different pipelines and interfaces. A class implementing both `PostProcessor` and `MessagePostProcessor` is unlikely since session-level and per-message processing are very different concerns.
- Nested `post_processors.session` and `post_processors.message`: Over-engineering for two flat contribution types. Adds nesting complexity to the TOML schema.

**Consequences**:
- Pro: Clear, self-documenting manifest structure
- Pro: DLT-171 adds a new key without touching existing schema
- Con: Two keys instead of one, but this matches the pattern (context_providers works because both ABCs contribute to the same conceptual "context")

### Validation mirrors context provider pattern exactly

**Choice**: `_validate_post_processors()` follows the same structure as `_validate_providers()`: import module → find concrete subclasses → validate constructor → instantiate.

**Why**: Consistency with the existing pattern reduces cognitive load and makes the two validation functions easy to compare. The only additions are phase validation (check against `_VALID_PHASES`) and conditional `agent_defaults` injection.

**Alternatives Considered**:
- Generic `_validate_contributions()` shared between providers and processors: Would require abstracting over different ABC types, different constructor requirements, and different post-validation routing. The complexity isn't worth it for two nearly identical functions.

**Consequences**:
- Pro: Familiar pattern for anyone who has read the context provider code
- Pro: Easy to test (same test structure as context provider tests)
- Con: Some duplication between `_validate_providers()` and `_validate_post_processors()`, but the functions are small and the differences are meaningful

### Conditional agent_defaults injection via signature inspection

**Choice**: Inspect the processor class's `__init__` signature. If it accepts `agent_defaults` as a keyword argument, pass the system's `AgentDefaults` instance during instantiation. Always pass `config=validated_config`.

**Why**: `PromptDrivenProcessor` subclasses need `agent_defaults` to fork the SDK session. Plain `PostProcessor` subclasses (no SDK interaction) don't. The conditional pattern avoids requiring every processor to accept an unused parameter. Plugin processors extending `PromptDrivenProcessor` must override `__init__` to accept both `config` and `agent_defaults`, store config, and call `super().__init__(prompt, agent_defaults, ...)`.

**Alternatives Considered**:
- Always pass `agent_defaults`: Would force every processor's `__init__` to accept it, even simple ones that don't fork the SDK
- Check `issubclass(cls, PromptDrivenProcessor)`: Would miss custom base classes that fork the SDK without inheriting from `PromptDrivenProcessor`

**Consequences**:
- Pro: Only processors that need `agent_defaults` receive it
- Pro: Signature-based detection works regardless of class hierarchy
- Con: Plugin developers extending `PromptDrivenProcessor` must follow the `__init__` override pattern (accept `config` + `agent_defaults`, call `super().__init__(...)`)

### AgentDefaults created in plugins_hook for discovery

**Choice**: `plugins_hook()` creates `AgentDefaults` via `agent_defaults_from_settings(settings)` before calling `discover()`, and passes it through the discovery chain. `PluginManager` stores it for reuse during runtime install/update.

**Why**: `AgentDefaults` is needed during post-processor instantiation (for `PromptDrivenProcessor` subclasses), but it's currently only created in `__main__.py` after bootstrap completes. Creating it in `plugins_hook()` works because `agent_defaults_from_settings()` is a pure function that only needs settings, which are already available via `ctx.settings_manager.settings`. The frozen dataclass is immutable and identical to the one created in `__main__.py`.

**Alternatives Considered**:
- Store classes instead of instances in `LoadedPlugin`, instantiate later: Would split validation from instantiation, complicating error handling (validation errors would surface at registration time instead of discovery time, contradicting the fail-fast pattern)
- Move `AgentDefaults` creation to its own bootstrap hook: Adds a new hook dependency ordering for a single value — over-engineering
- Make `_validate_post_processors()` not need `AgentDefaults`: Would require storing uninstantiated classes and deferring instantiation, losing the fail-fast validation

**Consequences**:
- Pro: Validation and instantiation stay together in discovery (fail fast)
- Pro: Same pattern for bootstrap discovery and runtime install/update
- Con: `plugins_hook()` now creates `AgentDefaults` as a side effect — but it's a pure dataclass with no side effects

### Phase validation at discovery time

**Choice**: Phase value is validated in `_validate_post_processors()` during plugin discovery, not at `PostProcessingPipeline.register()` time.

**Why**: Fail-fast at plugin load time gives immediate feedback to the developer. The pipeline's `register()` still validates phase for safety, but plugin processors with invalid phase values never reach registration — the plugin fails during discovery with a diagnostic message listing valid phases.

**Consequences**:
- Pro: Immediate, clear error messages during plugin loading
- Pro: Invalid plugins are marked failed before any registration attempts
- Con: Phase is validated twice (discovery + registration), but the redundancy is harmless

## System Behavior

### Scenario: Plugin with session-level post-processor

**Given**: A plugin manifest with `[post_processors]` section containing `"summary" = "summary"`
**When**: The plugin is loaded during discovery
**Then**: The module `post_processors/summary.py` is imported, concrete `PostProcessor` subclasses are found, validated, and instantiated with `config=validated_config`. The resulting instances are stored in `LoadedPlugin.post_processors`.

### Scenario: Plugin with PromptDrivenProcessor subclass

**Given**: A plugin post-processor module containing a class that extends `PromptDrivenProcessor` with a custom `__init__` accepting both `config` and `agent_defaults`
**When**: The loader validates and instantiates it
**Then**: The class is accepted (it's a concrete `PostProcessor` subclass). It's instantiated with both `config=validated_config` and `agent_defaults=system_agent_defaults`. The processor's `process()` inherits DES-004 behavior (resumption augmentation, context summary injection) from `PromptDrivenProcessor.process()`.

### Scenario: Multiple processors in one module

**Given**: A post-processor module containing two concrete `PostProcessor` subclasses (`SummaryProcessor` and `WebhookProcessor`)
**When**: The loader validates it
**Then**: Both classes are discovered, validated, and instantiated. Both are stored in `LoadedPlugin.post_processors` and registered at their respective declared phases. This follows the context provider pattern where a single module can contribute multiple implementations.

### Scenario: Invalid phase value on plugin processor

**Given**: A plugin post-processor class with `phase = "custom_phase"`
**When**: The loader validates it (during discovery, not at registration time)
**Then**: The plugin fails with diagnostic: `"Processor class 'X' declares invalid phase 'custom_phase'. Valid phases: finalize, main, pre_finalize"`. The processor is never registered. The plugin is marked as `status="failed"`.

### Scenario: Plugin processor fails at runtime

**Given**: A registered plugin post-processor that raises during `process()`
**When**: The pipeline runs
**Then**: The exception is caught by `asyncio.gather(return_exceptions=True)` and logged. Other processors in the same phase continue. Subsequent phases execute normally. This is the same error isolation as built-in processors.

### Scenario: Plugin removal with registered processors

**Given**: A loaded plugin with registered post-processors
**When**: The `PluginRemoving` event fires
**Then**: The handler looks up the `LoadedPlugin` from the plugin manager and calls `unregister()` for each processor. The pipeline removes them by identity from the phase list. If the pipeline is currently executing `run()`, the processors still complete their current `process()` call (unregister only prevents them from running in future invocations — no lock needed since lifecycle events are serialized by the plugin manager's async lock).

### Scenario: Unregister processor not in pipeline

**Given**: A `PostProcessingPipeline` with no registered processors from plugin X
**When**: `unregister(processor_from_x)` is called during plugin removal
**Then**: `list.remove()` raises `ValueError`, suppressed by `contextlib.suppress(ValueError)`. Safe no-op, consistent with `PreProcessingPipeline.unregister()`.

### Scenario: Built-in processor registration after refactor

**Given**: `__main__.py` with `pipeline.register(ProjectsProcessor(agent_defaults), phase=PRE_FINALIZE_PHASE)`
**When**: The register call executes after the refactor
**Then**: The explicit `phase=PRE_FINALIZE_PHASE` argument takes precedence over the class attribute. The processor runs in the `pre_finalize` phase. The call site continues working without modification.

### Scenario: Built-in processor after class attribute refactor

**Given**: `ProjectsProcessor` with `phase = PRE_FINALIZE_PHASE` class attribute, and `__main__.py` refactored to `pipeline.register(ProjectsProcessor(agent_defaults))`
**When**: The register call executes
**Then**: No explicit `phase` kwarg (sentinel `_UNSET`) → `register()` reads `processor.phase` → `PRE_FINALIZE_PHASE`. Same behavior.

### Scenario: CC plugin with post_processors key

**Given**: A CC-format plugin manifest (`plugin.json`) containing `"post_processors": {...}`
**When**: The manifest is parsed
**Then**: `"post_processors"` is added to `ignored_cc_contributions` and logged at INFO. The plugin loads successfully with no post-processors registered.
