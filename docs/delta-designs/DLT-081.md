# Design: DLT-081 - Workflow State Machine for Skills

**Delta Spec**: [../delta-specs/DLT-081.md](../delta-specs/DLT-081.md)
**Status**: Draft

## Purpose

This document explains the design rationale for the workflow state machine: how workflows are defined within skills, how state is tracked, how the MCP tools enforce the state machine boundary, and how the system integrates with existing Tachikoma infrastructure.

## Problem Context

Skills that define multi-step workflows (morning routines, deployment processes, reading list processing) rely entirely on the LLM to remember which steps are done and what comes next. Without explicit state, the agent skips steps, repeats completed ones, or loses its place after context compaction. The solution uses a file-tree-based approach where workflows are directory structures the agent navigates natively, with MCP tools enforcing state transitions and a database table persisting state across context boundaries.

## Design Overview

Workflows are optional subdirectories within skills (`workflows/<name>/`), each containing ordered step directories with instructions, references, and scripts. Four MCP tools (`start_workflow`, `update_workflow_state`, `get_workflow_state`, `end_workflow`) form the state machine boundary — the agent cannot change workflow state except through these tools, which validate all transitions. State is persisted in a database table, making it resilient to context compaction and process restarts.

## Shape

| Part | Mechanism | Flag |
|------|-----------|:----:|
| **S1** | Workflow definition loader — discovers and parses `workflows/` directories within skills, reads step subdirectories with their instructions.md frontmatter, references/, and scripts/ | |
| **S2** | Workflow state database model — SQLAlchemy model for workflow instances (id, skill_name, workflow_name, current_step, step_states JSON, definition_snapshot JSON, created_at, updated_at) | |
| **S3** | `start_workflow` MCP tool — creates DB record with definition snapshot, loads workflow definition, returns step list + agent guidance | |
| **S4** | `update_workflow_state` MCP tool — validates transitions against step properties (start/complete/skip actions), advances state, returns step instructions | |
| **S5** | `get_workflow_state` MCP tool — read-only lookup returning full workflow state for resumption | |
| **S6** | `end_workflow` MCP tool — marks workflow completed/aborted, removes DB record | |
| **S7** | Stale workflow cleanup — periodic or startup check removing workflows with `updated_at` older than configurable threshold (default 24h) | |
| **S8** | System preamble workflow section — static text explaining workflows and their MCP tools | |
| **S9** | Built-in `workflow-authoring-guide` skill — directory with SKILL.md and references for creating workflow definitions | |
| **S10** | Skill registry extension — expose workflow definitions alongside skill data so MCP tools can look them up by name | |

## Components

### Implementation Structure

| Layer/Component | Responsibility | Key Decisions |
|-----------------|----------------|---------------|
| Workflow Definition Loader | Parse skill `workflows/` directories, load step metadata from frontmatter | Uses python-frontmatter (consistent with skill loading) |
| Workflow State Model | SQLAlchemy model for active workflow instances | Follows ADR-007 (SQLAlchemy async + aiosqlite), JSON column for step states |
| MCP Tool Server | Expose workflow lifecycle tools to the agent | Follows DES-006 (MCP tool server factory pattern) |
| Skill Registry Extension | Expose workflow definitions for lookup by MCP tools | Extends existing SkillRegistry, no new registry needed |
| System Preamble | Static workflow awareness section in system prompt | Follows ADR-008 (system prompt composition via append) |
| Built-in Skill | Workflow authoring guide | Follows existing built-in skill pattern (skill-authoring-guide) |
| Stale Cleanup | Remove old workflow state records | Runs at startup or as periodic task, configurable threshold |

### Cross-Layer Contracts

**MCP Tool Schemas**:

```
start_workflow(skill_name: str, workflow_name: str)
  → { workflow_id: str, steps: [{id, title, skippable}], guidance: str }
  | { error: str }

update_workflow_state(workflow_id: str, step: str, action: "start" | "complete" | "skip")
  → { step: str, status: str, instructions: str, references: str[], scripts: str[] }
  | { workflow_complete: true, message: str }
  | { error: str }

get_workflow_state(workflow_id: str)
  → { workflow_id: str, skill_name: str, workflow_name: str, current_step: str, steps: [{id, title, status}], created_at: str, updated_at: str }
  | { error: str }

end_workflow(workflow_id: str, action: "complete" | "abort")
  → { message: str }
  | { error: str }
```

**Integration Points**:
- MCP tools call skill registry to resolve skill_name → workflow definition
- MCP tools call workflow state repository for all DB operations
- Stale cleanup runs at startup via bootstrap hook
- System preamble static text added to preamble template

### Shared Logic

- **Workflow definition model**: Parsed step structure (id, title, instructions path, references, scripts, frontmatter properties) shared between loader and MCP tools
- **Step state enum**: `pending | started | completed | skipped` — shared between state model and transition validation
- **Transition validation**: Central logic in MCP tool handler, enforcing step ordering and frontmatter properties

## Modeling

```
WorkflowDefinition (filesystem):
  skill_name: str
  workflow_name: str
  steps: [StepDefinition]

StepDefinition (filesystem):
  id: str (directory name, e.g., "01-plan")
  title: str (from frontmatter)
  instructions_path: Path
  references_path: Path | None
  scripts_path: Path | None
  skippable: bool (default false)
  properties: dict (extensible frontmatter fields)

WorkflowState (database):
  id: str (UUID)
  skill_name: str
  workflow_name: str
  current_step: str | None
  step_states: JSON ({"01-plan": "completed", "02-execute": "started", ...})
  definition_snapshot: JSON (serialized step definitions at start time)
  created_at: datetime
  updated_at: datetime
```

## Data Flow

```
1. Skill detection loads skill with workflows/
2. Agent reads SKILL.md → discovers available workflows
3. Agent calls start_workflow(skill_name, workflow_name)
   → Loader parses workflow definition from skill directory
   → Creates WorkflowState record in DB (with definition snapshot)
   → Returns step list + agent guidance (TodoWrite, scratchpad)
4. Agent creates TodoWrite tasks for steps
5. Agent calls update_workflow_state(id, step, "start")
   → Validates step exists and is next in order
   → Updates step_states in DB
   → Returns step instructions + references/scripts paths
6. Agent executes step
7. Agent calls update_workflow_state(id, step, "complete")
   → Marks step completed, advances to next step
   → Returns next step instructions (or completion message)
8. Repeat 5-7 until all steps done
9. Agent calls end_workflow(id, "complete") → DB record removed
```

## Key Decisions

### File tree as workflow definition

**Choice**: Workflows mapped to directory structures the agent navigates natively
**Why**: Resilient to model capability changes — if a model can handle multiple steps in one go, steps can be condensed without changing the system
**Alternatives Considered**:
- YAML manifest with step definitions: More structured but creates a parallel format the agent must learn
- Database-only definitions: Loses the filesystem alignment that makes skills intuitive

**Consequences**:
- Pro: Agent already knows how to navigate directories; aligns with skill folder pattern
- Pro: Steps are self-contained with their own references and scripts
- Con: Ordering relies on naming convention (alphabetical sort with numeric prefix)

### MCP tools as state machine boundary

**Choice**: All state transitions go through MCP tools that validate and enforce rules
**Why**: Prevents the agent from corrupting state; tools return step-specific instructions at transition points, guiding the agent naturally
**Alternatives Considered**:
- Context-injected state with agent self-management: Relies on LLM discipline, defeats the purpose
- Event-driven state machine: Over-engineered for the use case

**Consequences**:
- Pro: Strong state guarantees regardless of agent capability
- Pro: Tool results naturally guide the agent to the next action
- Con: Agent must call tools correctly (but tool errors provide clear guidance)

### Definition snapshot at start time

**Choice**: Workflow definition is serialized when started and stored with the state record
**Why**: If a skill's workflow definition changes while a workflow is active, the active workflow uses the original definition — preventing mid-flight inconsistencies
**Alternatives Considered**:
- Always read from filesystem: Could cause steps to appear/disappear mid-workflow
- Version workflow definitions: Adds complexity without clear benefit for current scope

**Consequences**:
- Pro: Active workflows are insulated from definition changes
- Con: Definition snapshot increases DB record size (mitigated by small step definitions)

### Database table for state (not filesystem)

**Choice**: Workflow state persisted in a SQLAlchemy database table
**Why**: Consistent with existing persistence pattern (ADR-007), supports concurrent workflows, queryable, and benefits from existing database infrastructure
**Alternatives Considered**:
- JSON files in `.tachikoma/state/workflows/`: Simpler but loses queryability and transactional safety

**Consequences**:
- Pro: Follows established patterns, no new persistence mechanism
- Pro: Atomic updates, concurrent access safety
- Con: Adds a migration for the new table (follows existing Alembic pattern)

## System Behavior

### Scenario: Workflow resumption after context compaction

**Given**: An active workflow with ID "abc-123" at step "03-review"
**When**: Context compaction occurs and the agent loses the workflow context
**Then**: The agent calls `get_workflow_state("abc-123")`, receives the full state, and resumes from step "03-review"
**Rationale**: State lives in the database, not conversation memory — the ID is the only thing needed to recover

### Scenario: Attempting to skip a non-skippable step

**Given**: An active workflow where step "02-execute" has `skippable: false` in its frontmatter
**When**: The agent calls `update_workflow_state(id, "02-execute", "skip")`
**Then**: The tool returns an error explaining the step cannot be skipped
**Rationale**: Frontmatter properties enforce workflow integrity at the tool boundary

### Scenario: Stale workflow cleanup

**Given**: A workflow state record with `updated_at` 25 hours ago (default threshold: 24h)
**When**: The cleanup mechanism runs
**Then**: The record is removed from the database
**Rationale**: Prevents accumulation of abandoned workflows; threshold is configurable for different use cases

### Scenario: Definition changes during active workflow

**Given**: An active workflow started from a 3-step definition
**When**: The skill author modifies the workflow to have 4 steps
**Then**: The active workflow continues with the original 3-step definition (from snapshot)
**Rationale**: Mid-flight definition changes would corrupt in-progress state

## Open Questions

- [ ] Should stale cleanup run at startup only, or also periodically during runtime?
- [ ] Should `update_workflow_state` return the full step content (instructions file contents) or just the file paths for the agent to read?
- [ ] Should the system preamble include active workflow state, or should the agent call `get_workflow_state` to discover active workflows?

## Notes

- Inspired by the "file tree as agent workflow" concept (https://youtube.com/shorts/tbVtt2-qUJo) — mapping workflows to directory structures that coding agents navigate natively
- Workflow steps use the SDK's native TodoWrite for progress tracking, which is separate from Tachikoma's task management system
- The scratchpad concept is prompting-based — the agent is instructed to maintain notes in a file, not through a dedicated MCP tool
