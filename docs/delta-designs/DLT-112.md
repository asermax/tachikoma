## Shape

| Part | Mechanism | Flag |
|------|-----------|:----:|
| **S1** | Priority buffer component — maintains a priority queue of pending deliverables, checks the front item's timing against `coordinator.last_message_time` and `_is_busy`, and dispatches delivery when conditions are met | ⚠️ |
| **S2** | Buffer item protocol — a common interface for anything enqueued (notifications, session tasks, future types), carrying priority level and a delivery callback for lifecycle completion | |
| **S3** | Priority field on Notification — add `priority` field (default Normal) to the `Notification` event; `dispatch_notification()` accepts priority parameter; executor sets Urgent for all failure notifications | |
| **S4** | Priority parameter on `send_notification` — add optional `priority` argument to the MCP tool schema and `handle_send_notification()`; background task system prompt documents available levels and usage guidance | |
| **S5** | Channel subscription change — channels subscribe to buffer delivery events instead of directly to `Notification` and `SessionTaskReady` events | |
| **S6** | Session task scheduler integration — scheduler enqueues ready instances into the buffer at Normal priority instead of dispatching `SessionTaskReady` directly; removes its own idle gating logic; preserves completion callback | |
| **S7** | Timing configuration — priority level definitions (idle window, max hold) configurable via config | |

### Flagged Unknowns

#### S1 — Buffer check mechanism

The buffer needs to check the front item's timing frequently enough to honor 30s idle windows, but the implementation approach — polling loop with a short interval, event-driven wake-up on message activity, or a hybrid — is a design decision with different tradeoffs (simplicity vs responsiveness vs CPU usage). Needs investigation during design phase.
