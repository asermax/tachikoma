## Shape

| Part | Mechanism | Flag |
|------|-----------|:----:|
| **S1** | New MCP tool server in `telegram/` (DES-006 factory + Pydantic args) — builds `InlineKeyboardMarkup` from rows, calls `bot.send_message(reply_markup=...)`, returns the sent message ID | |
| **S2** | aiogram `CallbackQuery` handler on the dispatcher's `callback_query` router, filtered by `from_user.id == authorized_chat_id`; acknowledges first, then branches into keyboard-removal + envelope wrapping + enqueue | |
| **S3** | Envelope abstraction in `message.py`: base envelope type (Protocol or sealed/discriminated union) with `TextMessage` (≈ today's `IncomingMessage`: `text`, `force_new`, `pinned_skills`) and `ButtonTapMessage` (`value`) subtypes; coordinator queues, enqueue methods, deferred-queue APIs, and `_message_source` all operate on the base type | |
| **S4** | SDK-input shaping at the `_message_source` boundary (or its inline equivalent) renders each envelope subtype into the SDK's input string: `TextMessage` → text as-is; `ButtonTapMessage` → *"The user tapped the option `<value>` out of the options you displayed."*; all message paths (initial, steered, re-queued) share the same shaping function | |
| **S5** | Keyboard removal on tap via `bot.edit_message_reply_markup(chat_id, message_id, reply_markup=None)` after ack when `single_use=True`; failures logged, tap routing continues independently; duplicate-removal ("message is not modified") treated as no-op | |
| **S6** | Tap routing reuses the existing `_delivery_lock` + `_coordinator.enqueue()` pattern from `_handle_message` so busy/idle/deferred semantics are inherited unchanged | |
| **S7** | Authorization filter on `CallbackQuery` (different field name from message filter: `from_user.id`); unauthorized taps still get `answer()` then drop | |
| **S8** | Input validation in the tool (via Pydantic): per-button `value` ≤ 64 bytes, non-empty `label`/`value`, ≥1 row with ≥1 button, total markup within Telegram payload limits; clear validation errors via `is_error: True` results | |
| **S9** | Envelope adoption at producer sites — REPL, priority buffer, session-task delivery, background-task delivery, and Telegram media/command paths wrap their text inputs in `TextMessage` envelopes when enqueueing (mechanical change once the envelope lands) | |

### Flagged Unknowns

_None at spec time. The envelope-discriminator strategy (sealed class vs Protocol vs discriminated union) is a design-phase choice but not flagged as an unknown — multiple viable approaches exist; design phase picks one._
