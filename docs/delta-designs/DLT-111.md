## Shape

| Part | Mechanism | Flag |
|------|-----------|:----:|
| **S1** | Isolate mid-stream queue from main buffer — `_message_source` reads from a dedicated per-turn queue instead of `_message_buffer`, so messages enqueued during SDK teardown stay in the main buffer | |
| **S2** | Forwarding bridge between main buffer and mid-stream queue — while the SDK session is active, transfers messages from `_message_buffer` to the per-turn queue for mid-stream delivery; stops before disconnect | ⚠️ |
| **S3** | Telegram final drain — `_process_through_coordinator` re-checks `has_pending_messages` after all cleanup (ChatActionSender exit, on_complete), processing remaining messages before clearing `_is_processing` | |
| **S4** | REPL drain consistency — ensure session task and notification processing in the REPL drains any remaining buffered messages after coordinator completes | |

### Flagged Unknowns

#### S2 — Forwarding bridge atomicity
The forwarding mechanism itself has the same atomicity concern it's trying to solve — if the forwarder task is cancelled between consuming from `_message_buffer` and putting into the per-turn queue, a message could be lost. During design we need to investigate whether: (a) a dedicated forwarder task can be made safe with a try/finally recovery pattern, (b) a pull-based approach works (message source pulls from main buffer but with a "stop" signal before disconnect), or (c) a simpler mechanism exists that avoids the two-queue complexity entirely (e.g., draining the per-turn queue back to main buffer after disconnect).
