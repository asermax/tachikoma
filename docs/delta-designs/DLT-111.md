# Design: DLT-111 - Prevent message loss during response finalization

**Delta Spec**: [../delta-specs/DLT-111.md](../delta-specs/DLT-111.md)
**Status**: Design

## Purpose

This document explains the design rationale for this delta: the modeling choices, data flow, system behavior, and architectural approach.

After implementation, the "Detected Impacts" section will guide reconciliation into feature design docs.

## Problem Context

Two independent timing windows silently drop user messages:

1. **Coordinator teardown race (R0/R1).** The `_message_source` async generator
   (`src/tachikoma/coordinator.py:73`) and `send_message()`
   (`src/tachikoma/coordinator.py:328`) both consume from the same
   `_message_buffer`. During the `finally: await client.disconnect()` block
   (line 590), the SDK cancels its internal task group — which includes
   `_message_source`. If that generator was suspended on `await buffer.get()`,
   the cancellation can leave a delivered item orphaned, or at minimum makes
   the safety argument depend on `asyncio.Queue.get()`'s version-sensitive
   cancellation behavior.

2. **Telegram drain gap (R2).** `_process_through_coordinator`
   (`src/tachikoma/telegram/__init__.py:804`) guards concurrent coordinator
   use with a boolean `_is_processing`. The drain loop exits when
   `has_pending_messages` is False, then `ChatActionSender` unwinds,
   `on_complete` runs, and `_is_processing = False` happens in `finally`.
   Any message enqueued between the `while` check and the flag reset sits in
   `_message_buffer` forever — the next `_handle_*` short-circuits on
   `_is_processing`, but nothing is still draining.

DLT-112 already solved the equivalent problem for REPL by replacing the
flag pattern with `_delivery_lock: asyncio.Lock`
(`src/tachikoma/repl.py:90`). R2 for REPL is therefore neutralized; only
Telegram still exhibits the race.

## Design Overview

Two mutually independent fixes, one per layer:

**Layer 1 — Coordinator (R0/R1/R3/R4).** Isolate the SDK-facing message
stream from the channel-facing buffer with a per-turn `_sdk_inbox` queue
and a small `_forwarder` task that moves items between them. The only
consumer of `_message_buffer` is the forwarder; the only consumer of
`_sdk_inbox` is `_message_source`. On teardown the coordinator stops the
forwarder *before* `client.disconnect()`, then drains any items stuck in
`_sdk_inbox` back into `_message_buffer` atomically (no `await` between
drain and re-enqueue) to preserve FIFO order.

**Layer 2 — Telegram (R2).** Replace the `_is_processing` flag with the
same `_delivery_lock: asyncio.Lock` pattern DLT-112 introduced in the REPL.
Every `_handle_message`, `_handle_media`, and `_handle_buffered_delivery`
acquires the lock, enqueues, and calls `send_message()` under it. Because
`asyncio.Lock.acquire()` queues waiters, any message that arrives during
the previous turn's cleanup is picked up by the next lock holder
immediately — no drain-gap window.

## Shape

| Part | Mechanism | Flag |
|------|-----------|:----:|
| **S1** | Per-turn `_sdk_inbox: asyncio.Queue[str]` created at the top of `send_message()`; `_message_source(initial, sdk_inbox)` reads only from `_sdk_inbox`, never from `_message_buffer` | |
| **S2** | `_forwarder` task started alongside the SDK client: `while True: _sdk_inbox.put_nowait(await _message_buffer.get())`. Cancelled in `finally` before `client.disconnect()` so `_message_buffer` has no consumer during teardown | |
| **S3** | Atomic drain-back: after the SDK client is disconnected, synchronously drain both `_sdk_inbox` and `_message_buffer` via `get_nowait()`, then re-enqueue `sdk_inbox_items + buffer_items` in that order via `put_nowait()` — one synchronous block (no `await`), so concurrent `enqueue()` cannot interleave | |
| **S4** | `_message_source` recovery: wrap the yield loop in `try/finally` that re-enqueues the locally held item to `_sdk_inbox` if the generator is cancelled mid-step, so step S3's drain can recover it | |
| **S4b** | `_forwarder` recovery: wrap the `await get() → put_nowait()` loop in `try/finally` that re-enqueues a locally held item to `_message_buffer` on `CancelledError` — belt-and-suspenders for KD-2 | |
| **S5** | Telegram `_delivery_lock: asyncio.Lock` replaces `_is_processing`: `_handle_message`/`_handle_media`/`_handle_buffered_delivery` each `async with self._delivery_lock: enqueue; drain` — mirrors REPL's DLT-112 pattern | |

All flagged unknowns from the shape-only seed have been resolved (see **Key Decisions**).

## Components

### Coordinator (`src/tachikoma/coordinator.py`)

- **New field**: nothing at instance level; `_sdk_inbox` lives as a local in `send_message()` and is passed to `_message_source` + `_forwarder`.
- **`_message_source` signature change**: `_message_source(initial: str, inbox: asyncio.Queue[str])` — reads from the per-turn `inbox` instead of `_message_buffer`.
- **New method `_forwarder(inbox: asyncio.Queue[str])`**: forever-loop, single suspension point on `_message_buffer.get()`, synchronous `put_nowait` into `inbox`.
- **`send_message()` restructuring**: the `try/finally` block around the SDK session now also owns the forwarder lifecycle. The `finally` runs this exact sequence:

  ```python
  finally:
      forwarder_task.cancel()
      with contextlib.suppress(asyncio.CancelledError):
          await forwarder_task
      await client.disconnect()
      self._drain_back(sdk_inbox)   # synchronous
      self._client = None           # synchronous, same block as drain-back
  ```

  The `_drain_back` and `self._client = None` statements form a single synchronous section — no `await` between them — so `is_busy` transitions cleanly (see KD-3).
- **Drain-back helper `_drain_back(inbox: asyncio.Queue[str])`**: synchronous, no awaits; extracts all items from `inbox` and from `_message_buffer`, re-populates `_message_buffer` with `inbox` items first, then `_message_buffer` items in their original order.

### Telegram channel (`src/tachikoma/telegram/__init__.py`)

- **Remove** `_is_processing: bool` field and all guard checks.
- **Add** `_delivery_lock: asyncio.Lock = asyncio.Lock()`.
- **Change** `_handle_message`, `_handle_media`, `_handle_buffered_delivery` to acquire `_delivery_lock` around the `enqueue + send_message` sequence (mirroring `src/tachikoma/repl.py:151`).
- **Simplify** `_process_through_coordinator`: since the lock serializes entry, the method collapses to a single `send_message()` iteration — no outer `while has_pending_messages` drain loop needed. (The lock queue replaces the drain loop.)
- **`_active_renderer` + `ChatActionSender` scope**: both move inside the lock-held single-iteration body. The renderer is created per message exchange (instead of per drained batch), and `ChatActionSender` (typing indicator) starts/stops per message. This is a user-visible change: where two rapid-fire Telegram messages previously shared one typing indicator (the drain loop held it across both), they now get distinct indicators. This matches the REPL's per-exchange rendering model from DLT-112 and is accepted as intentional.

### REPL

- No changes. `_delivery_lock` already satisfies R2 for REPL.

## Cross-Layer Contracts

- **Channels → Coordinator**: unchanged. Channels still call
  `coordinator.enqueue(text)` synchronously. The buffer's invariant is
  unchanged from the channel's perspective — items enqueued here are
  eventually processed.
- **Coordinator → SDK**: the generator passed to `client.connect()` now
  reads from a per-turn queue. SDK sees identical message dicts in
  identical order.
- **Coordinator `is_busy`**: unchanged. Still `_client is not None or
  has_pending_messages or _pending_msg_task`. The drain-back step
  re-populates `_message_buffer` before `_client` is cleared, so
  `is_busy` never flickers false while items are pending. This keeps
  `_maybe_emit_idle()` (`coordinator.py:932`) emitting `CoordinatorIdle`
  exactly once per true busy→idle transition.

## Modeling

### Data: per-turn queue ownership

`_sdk_inbox` is created fresh inside `send_message()` and lives only until
`finally` completes. It is passed by reference to `_forwarder` and
`_message_source`. The queue instance is never reused across turns —
this is what makes the drain-back safe (we can `get_nowait()` it to
completion without coordinating with future turns).

### Concurrency: three concurrent coroutines per turn

1. The `send_message()` coroutine itself — drives the SDK response loop.
2. `_forwarder` — running as a background `asyncio.Task`.
3. `_message_source` — async generator consumed by the SDK's internal task group (created by `client.connect(...)`).

All three share the event loop. The forwarder and `_message_source`
never touch the same queue, which is the invariant that fixes R0/R1.
Only `_forwarder` is a real `asyncio.Task`; `_message_source` is a
generator scheduled by the SDK's task group — the distinction matters
for teardown (we cancel the forwarder directly, but `_message_source`
is torn down by `client.disconnect()`).

## Data Flow

### Happy path (single turn, no mid-stream messages)

```
channel.enqueue("hi")                → _message_buffer = ["hi"]
coordinator.send_message()
  ├─ text = _message_buffer.get_nowait()        # "hi"; _message_buffer = []
  ├─ sdk_inbox = asyncio.Queue()
  ├─ forwarder_task = create_task(_forwarder(sdk_inbox))
  ├─ message_source = _message_source("hi", sdk_inbox)
  ├─ client.connect(message_source)
  │    └─ (SDK consumes _user_message("hi") from the generator)
  ├─ async for sdk_message in client.receive_response(): …
  └─ finally:
       ├─ forwarder_task.cancel(); await forwarder_task   # no-op, buffer empty
       ├─ await client.disconnect()                        # _message_source cancelled
       └─ _drain_back(sdk_inbox)                           # sdk_inbox empty, no-op
```

### Mid-stream message (R4)

```
channel.enqueue("hi") → _message_buffer = ["hi"]
send_message() starts → _message_buffer = [], sdk_inbox = []
(forwarder blocks on _message_buffer.get())
(message_source yields "hi", SDK processing)

channel.enqueue("follow-up") → _message_buffer = ["follow-up"]
   ├─ forwarder wakes: text = "follow-up"; sdk_inbox.put_nowait("follow-up")
   └─ message_source reads from sdk_inbox, yields to SDK mid-stream
```

### Teardown race (R0/R1)

```
SDK finalizing; forwarder blocked on _message_buffer.get(); message_source
blocked on sdk_inbox.get().

channel.enqueue("late") → _message_buffer = ["late"]
   └─ forwarder wakes: text = "late"; sdk_inbox.put_nowait("late")
       (message_source wakes, about to yield "late" — or not yet)

finally block runs:
1. forwarder_task.cancel(); await forwarder_task → forwarder's next await
   raises CancelledError; S4b re-enqueues any local to _message_buffer
   (none here — it had already put "late" into sdk_inbox).
2. await client.disconnect() → message_source cancelled.
   - If it had not yet pulled "late" from sdk_inbox: item sits in sdk_inbox.
   - If it had pulled "late" into local var but not yielded: S4's try/finally
     puts it back via sdk_inbox.put_nowait().
3. _drain_back(sdk_inbox):        # synchronous, no await
     recovered = [i for i in sdk_inbox]   # ["late"]
     pending  = [i for i in _message_buffer]  # []
     for item in recovered + pending:
         _message_buffer.put_nowait(item)
   → _message_buffer = ["late"]
4. self._client = None            # same synchronous block as step 3
```

On the next `send_message()` call, "late" is the initial message.

### Ordering under concurrent enqueue during teardown (R3)

```
During teardown:
  forwarder has moved A into sdk_inbox = [A]
  forwarder is cancelled before it can pull B
  meanwhile channel enqueues B → _message_buffer = [B]

_drain_back:
  recovered = [A]
  pending   = [B]   # drained synchronously, no race with concurrent enqueue
  re-enqueue in order → _message_buffer = [A, B]

No await inside _drain_back means no channel enqueue can interleave,
so ordering by arrival time is preserved.
```

### Telegram concurrent messages (R2)

```
user sends msg1 → _handle_message:
  async with _delivery_lock:
    enqueue(msg1)
    await send_message() iteration

(mid-send_message, user sends msg2)
_handle_message(msg2):
  async with _delivery_lock:   # waits for msg1's holder to release
    enqueue(msg2)
    await send_message() iteration

During msg1's cleanup (ChatActionSender exit, on_complete, finally):
  msg2's task is already queued on the lock. The moment msg1's lock
  context exits, msg2's handler runs. No flag transition gap.
```

## Key Decisions

### KD-1: Two-queue isolation over cancellation-safe single-queue

**Decision**: Use a dedicated `_sdk_inbox` rather than making `_message_source`'s
consumption of `_message_buffer` cancellation-safe.

**Alternatives considered**:
- (A) Single-queue with `try/finally` that pushes back to `_message_buffer`
  on `GeneratorExit` / `CancelledError`.
- (B) Two-queue with forwarder (chosen).
- (C) Single queue + explicit stop sentinel; block disconnect until sentinel
  is delivered.

**Why two-queue**: The invariant "channel-facing queue is never consumed by
anything in the SDK's cancellable task group" makes the safety argument
structural rather than cancellation-semantic. It does not depend on
`asyncio.Queue.get()` behavior changing across Python versions. It also
keeps `_message_source` trivial; the recovery in S4 becomes a small
belt-and-suspenders rather than the primary safety mechanism.

**Cost**: one extra task (the forwarder) per turn. Negligible — the task
has one suspension point and does no real work.

### KD-2: Cancel forwarder before `client.disconnect()`

**Decision**: The order in `finally` is
`forwarder_task.cancel()` → `await forwarder_task` → `await client.disconnect()`
→ `_drain_back(sdk_inbox)` → `self._client = None`.

**Why**: If the forwarder were still running when drain-back starts, its
`await _message_buffer.get()` could resume with an item pulled into a
local variable that drain-back's `get_nowait()` on `_message_buffer`
would not see — the item would be stranded. Stopping the forwarder
first makes both queues stable snapshots before we reason about their
contents. S4b (forwarder recovery) adds defensive pushback for the
worst case, but the primary guarantee is structural: drain-back runs
strictly after the forwarder task has terminated (`await forwarder_task`
has returned) and after `_message_source` has fully torn down (inside
`client.disconnect()`'s await).

### KD-3: Synchronous drain-back to preserve FIFO order and `is_busy` invariant

**Decision**: `_drain_back` does all queue manipulation in one
synchronous block (no `await`), using repeated `get_nowait()` / `put_nowait()`
on unbounded queues. `self._client = None` follows drain-back in the
same synchronous section.

**Why (ordering)**: Channel `enqueue()` is `put_nowait()`, synchronous.
On a single-threaded asyncio event loop, any synchronous code block is
atomic w.r.t. other coroutines' `put_nowait()` calls. This gives us
ordering without adding a lock that channels would need to care about.

**Why (is_busy invariant)**: `is_busy` evaluates
`_client is not None or has_pending_messages or _pending_msg_task`
(`coordinator.py:918`). Drain-back runs *before* `_client = None`, so
any recovered items are visible via `has_pending_messages` at the exact
moment `_client` flips to `None`. No scheduling gap can cause
`_maybe_emit_idle` to observe `False` while items remain pending.

### KD-4: `_message_source` recovery (S4) as defence in depth

**Decision**: `_message_source` wraps its read-yield loop in `try/finally`
that pushes back a locally held item to `_sdk_inbox` on any exception.

**Why**: With KD-1 in place, the main race is already closed at the
queue-isolation level. S4 covers the narrow window where
`_message_source` has pulled an item from `_sdk_inbox` into a local
variable but not yet yielded it to the SDK — cancellation at that point
would otherwise strand the item in a local. Pushing it back means
`_drain_back` will recover it.

**Happens-before chain** (the invariant the recovery relies on):

1. `forwarder_task.cancel()` + `await forwarder_task` completes →
   no more items can be appended to `_sdk_inbox`.
2. `await client.disconnect()` awaits to completion → the SDK's task
   group has fully torn down, including `_message_source`'s `finally`
   block running to completion (S4's `put_nowait` back into
   `_sdk_inbox` has executed).
3. `_drain_back(sdk_inbox)` executes synchronously on a frozen
   `_sdk_inbox` — neither the forwarder nor `_message_source` can
   mutate it anymore.

This ordering is what makes drain-back's simple `get_nowait()` loop sufficient.

### KD-4b: Forwarder recovery (S4b) as defence in depth

**Decision**: `_forwarder` wraps its loop in `try/finally` that re-enqueues
a locally held item back to `_message_buffer` on `CancelledError`.

**Why**: By the atomicity argument in Open Questions, the
`await get() → put_nowait()` step cannot be preempted — CPython's
cancellation model only raises `CancelledError` at `await` points, and
`put_nowait` is synchronous. However, making the recovery explicit
means the code remains correct even if future refactors introduce an
`await` between the two, and it documents the invariant for readers.
Cost is negligible (three lines).

### KD-5: Drop the Telegram drain loop

**Decision**: Replace `_is_processing` with `_delivery_lock`, and remove
the `while self._coordinator.has_pending_messages: …` loop in
`_process_through_coordinator`.

**Why**: With the lock serializing entry points, `send_message()` only
needs to process the single message the entry point enqueued. If more
messages arrived, they are already waiting on the lock; they will be
picked up by the next handler call without a drain loop. This matches
how REPL (DLT-112) structures the same contract and removes the
flag-based race wholesale rather than patching it.

**Trade-off**: each Telegram message now pays a distinct
`send_message()` invocation where previously a single call could drain
multiple buffered messages in one loop.

**Scope clarification on R4 (mid-stream steering)**: with the lock,
rapid same-channel follow-ups from a Telegram user are *serialized* —
the second message waits on the lock and lands as the *next* turn,
not as mid-stream steering within the current turn. REPL already has
this property post-DLT-112. The mid-stream delivery mechanism in the
coordinator (forwarder → `_sdk_inbox` → `_message_source`) remains
intact and active — it is exercised whenever any caller enqueues
between lock release and `client.disconnect()`. R4's AC is satisfied
at the coordinator-mechanism level: "follow-up is delivered as a
steering message" is a property of the path, not a per-channel
contract. Channels may choose to serialize (REPL, Telegram) or not
(future callers).

**Ordering note**: `asyncio.Lock.acquire()` grants waiters in FIFO
order in CPython 3.10+; the language spec does not strictly require
this, but Tachikoma targets CPython, so R3 (ordering) is preserved
under contention.

## System Behavior

### Interaction with `CoordinatorIdle`

`_maybe_emit_idle()` (`coordinator.py:932`) emits on busy→idle transitions
based on `is_busy`, which includes `has_pending_messages`. The drain-back
step re-populates `_message_buffer` *before* `_client = None` is set
(because drain-back is inside the `finally` block that runs before the
post-response code). Therefore:

- If the drain recovered items, `is_busy` stays True through `_client` reset (via `has_pending_messages`), and `_maybe_emit_idle()` correctly does not emit an idle transition.
- If drain-back is empty, `is_busy` flips to False after `_client = None` and the subsequent `_maybe_emit_idle()` call emits as before.

This preserves the buffer subsystem's exact-once idle contract that
DLT-112 depends on.

### Error paths

- **`CLIConnectionError` / `ProcessError`**: caught at line 575; `finally` still runs the full teardown sequence → forwarder cancelled, disconnect awaited, drain-back recovers any pending items, then `_client = None`. Messages in `_message_buffer` are preserved (existing behavior, now also covers `_sdk_inbox`).
- **Unhandled exception inside `async for sdk_message in …` loop**: same `finally` path.
- **Forwarder task raises** (non-cancellation): the awaiter uses
  `contextlib.suppress(asyncio.CancelledError)` for the expected
  cancellation and catches other exceptions explicitly
  (`except Exception: _log.exception("Forwarder failed")`) — the error
  is logged and the teardown continues. Items already moved into
  `_sdk_inbox` are recovered by drain-back; items still in
  `_message_buffer` are untouched. The coordinator does not re-raise
  forwarder errors because a forwarder failure cannot invalidate the
  response the SDK already returned.

### Shutdown (`__aexit__`)

Unchanged. The coordinator's `__aexit__` does not iterate `_message_buffer`
before exit; pending messages at shutdown remain out of scope per spec
scope-boundaries. The buffer subsystem's `flush_on_shutdown` (DLT-112)
handles notifications/tasks separately.

## Open Questions

None. All shape-level unknowns are resolved:

**S2 forwarder atomicity (resolved)**: `put_nowait` on an unbounded
queue is synchronous (no `await`, no `QueueFull` branch). CPython's
cancellation model only injects `CancelledError` at `await` points.
So the forwarder's

```python
while True:
    text = await _message_buffer.get()
    _sdk_inbox.put_nowait(text)
```

has exactly one cancellation point (`await get()`). Cases:
1. Cancellation fires *during* `await get()` before an item is
   delivered: `CancelledError` raises, `text` is never bound, no
   item is consumed.
2. `get()` returns a value, then cancellation fires at the next
   iteration's `await get()`: the prior item has already been
   `put_nowait`'d into `_sdk_inbox` (synchronous path, no preemption).

There is no third case — cancellation cannot arrive between
`get()` returning and `put_nowait()` executing, because no `await`
sits between them. S4b's defensive pushback exists to make the code
robust to future edits that might introduce such an `await`.

## Detected Impacts

### Affected Feature Designs

- **docs/feature-designs/agent/core-architecture.md** — `_message_source` signature changes (now takes a per-turn inbox), teardown sequence gains forwarder + drain-back. Section on message buffer lifecycle should document the two-queue model.
- **docs/feature-designs/channels/telegram.md** — `_is_processing` replaced by `_delivery_lock`. The "mid-stream buffering" sub-section should cite the lock's queueing behavior as the drain guarantee. The `_process_through_coordinator` drain loop is removed.
- **docs/feature-designs/channels/terminal-repl.md** — no design change; note in "related deltas" that R2 for REPL is covered by DLT-112's `_delivery_lock`, and DLT-111 covers the equivalent fix on the Telegram side.
- **docs/feature-designs/tasks/session-task-execution.md** / **background-task-execution.md** — no direct change; delivery via `BufferedDelivery` now inherits both R0/R1 (coordinator isolation) and R2 (Telegram lock) guarantees.

### Notes for Reconciliation

- Feature designs for both channels should note that all entry-point serialization is now lock-based (`asyncio.Lock`), unifying REPL and Telegram patterns.
- Core architecture design should document the forwarder task as part of the per-turn SDK client lifecycle.
- No API changes visible to external callers; `coordinator.enqueue()` signature and semantics are unchanged.

## Notes

- The design does not introduce any new public methods or settings. Everything is internal to the coordinator and Telegram channel modules.
- The forwarder task is cheap (single await, no CPU work); per-turn cost is one `asyncio.Task` create + cancel.
- Drain-back is O(n) in the total queue size; in practice n ≤ 2–3 messages.
