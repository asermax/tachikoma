# Design: DLT-169 - Track External Message IDs Per Session

**Delta Spec**: [../delta-specs/DLT-169.md](../delta-specs/DLT-169.md)
**Status**: Draft

## Purpose

This document explains the design rationale for tracking platform-specific message IDs alongside conversation sessions, enabling reaction-based session switching.

## Problem Context

The system has no mechanism to map external message IDs (e.g., Telegram `message_id`) to internal session IDs. When a user reacts to a message from a previous conversation, there is no way to determine which session that message belonged to, making reaction-based session routing impossible.

## Design Overview

A channel-agnostic external ID mapping table records incoming and outgoing message IDs per session. The Telegram channel captures IDs at ingestion and response finalization. When a reaction arrives, the handler looks up the reacted-to message's external ID, and if it maps to a different session, triggers a session switch before routing.

## Shape

| Part | Mechanism | Flag |
|------|-----------|:----:|
| **S1** | New `session_external_ids` DB table with domain model (`SessionExternalId` frozen dataclass), ORM record (`SessionExternalIdRecord`), and migration SQL | |
| **S2** | Repository methods: `save_external_id(session_id, channel, direction, external_id)` using `on_conflict_do_nothing()` on the unique index, and `lookup_session_by_external_id(channel, external_id) -> str \| None` | |
| **S3** | Registry facade methods wrapping repository: `record_external_id()` and `find_session_by_external_id()` — both return early with a warning log when the registry is `None` | |
| **S4** | Add `external_id: str \| None = None` field to `TextMessage` and `ReactionMessage` envelopes (field, not property hook — this is data, not behavior per DES-013) | |
| **S5** | Telegram incoming: set `external_id` on envelope and call `record_external_id` after session is determined | |
| **S6** | Telegram outgoing: expose finalized message IDs from ResponseRenderer, persist asynchronously after finalization — the Telegram channel captures `session_id` from the active session before entering `_process_through_coordinator()` and uses it in the async task spawned after Result | |
| **S7** | Telegram reaction: extract `event.message_id` from `MessageReactionUpdated`, set on `ReactionMessage` envelope, perform session lookup and switching before routing | |
| **S8** | Coordinator gains a public `switch_to_session(target_session_id)` method that closes the current session (triggering async post-processing) and reopens the target session — the Telegram reaction handler calls this when external ID lookup resolves to a different session | |

## Components

### Implementation Structure

| Layer/Component | Responsibility | Key Decisions |
|-----------------|----------------|---------------|
| DB Model | `session_external_ids` table with cascade delete, unique constraint on `(channel, external_id)` | Raw SQL migration (project convention) |
| Repository | Persist and query external IDs | `on_conflict_do_nothing()` on unique index; session-scoped query ordered by `id ASC` for insertion-order guarantee |
| Registry | Facade over repository with graceful degradation | Best-effort, errors logged not raised; returns early when registry is `None` |
| Message envelope | `external_id` field on `TextMessage` and `ReactionMessage` | Optional field (data, not property hook per DES-013), `None` = no-op |
| Telegram channel (incoming) | Capture `message.message_id`, set on envelope, persist after session determined | Persist after session creation/resume to know session_id |
| Telegram channel (outgoing) | Expose `_current_message_id` + `_split_message_ids` after finalization, persist async | Capture session_id before processing; spawn async task after Result; each split ID recorded as its own row |
| Telegram channel (reaction) | Extract `event.message_id`, lookup session, switch if needed | Only switches when delivery lock is free (idle); calls `coordinator.switch_to_session()` |
| Coordinator | Public `switch_to_session(target_session_id)` method | Reuses existing close + `reopen_session` logic; returns `False` if reopen fails (validation failure, already open, etc.) |

### Integration Points

- Telegram channel calls `record_external_id` after session is determined (incoming) and after response finalization (outgoing)
- Telegram reaction handler calls `find_session_by_external_id` before routing; if different session found, calls `coordinator.switch_to_session(target_id)`
- If `switch_to_session` returns `False` (reopen failed), the reaction routes to the current session without switching (graceful degradation)
- The `external_id` field on envelopes is read by the coordinator and registry but does not affect the existing `sdk_input` property hook — it is pure metadata

## Modeling

### SessionExternalId

```
SessionExternalId:
  id: int (auto-increment)
  session_id: str (FK → sessions.id, ON DELETE CASCADE)
  channel: str (canonical: "telegram", "repl")
  direction: str ("incoming" | "outgoing")
  external_id: str

Indexes:
  - UNIQUE (channel, external_id) — on_conflict_do_nothing on duplicate
  - session_id — for session-scoped queries (ordered by id ASC)
```

### SQLAlchemy Pattern

The project uses `sqlalchemy.dialects.sqlite.insert` (established in `app_state.py` with `on_conflict_do_update`). For insert-or-ignore:

```python
from sqlalchemy.dialects.sqlite import insert as sqlite_insert

stmt = sqlite_insert(SessionExternalIdRecord).values(
    session_id=session_id, channel=channel, direction=direction, external_id=external_id
)
stmt = stmt.on_conflict_do_nothing(index_elements=["channel", "external_id"])
await db.execute(stmt)
```

## Data Flow

### Incoming Message

```
Telegram message → _handle_message/media
  → TextMessage(external_id=str(message.message_id))
  → coordinator.enqueue(envelope)
  → coordinator: session creation/resume
  → registry.record_external_id(session_id, "telegram", "incoming", external_id)
```

### Outgoing Message

```
Before processing:
  Telegram channel captures current session_id into local variable

ResponseRenderer finalizes:
  → exposes (_current_message_id, _split_message_ids)
  → Telegram channel reads IDs

After Result event:
  → spawn async task:
      for each ID: registry.record_external_id(captured_session_id, "telegram", "outgoing", str(id))
  → errors logged only (graceful degradation)

Note: split messages (typically 2-3 per response) are recorded individually in a loop;
bulk insertion is unnecessary given the small count and async execution.
```

### Reaction with Session Switch

```
MessageReactionUpdated → _handle_reaction (only when delivery lock is free)
  → ReactionMessage(external_id=str(event.message_id))
  → target_id = registry.find_session_by_external_id("telegram", external_id)
  → if target_id and target_id != current_session_id:
      → success = coordinator.switch_to_session(target_id)
      → if not success: log warning, route to current session (graceful degradation)
  → enqueue ReactionMessage
```

## Key Decisions

### Unique constraint with on_conflict_do_nothing

**Choice**: UNIQUE on `(channel, external_id)` with `on_conflict_do_nothing()`
**Why**: The same message ID should never map to two sessions. If a re-processing occurs (e.g., duplicate event), the existing mapping is preserved rather than overwritten. This uses `sqlalchemy.dialects.sqlite.insert` with `on_conflict_do_nothing()`, distinct from the UPSERT pattern (`on_conflict_do_update`) used in `app_state.py`.
**Sources**: SQLAlchemy 2.x docs; project pattern established in `src/tachikoma/app_state.py`
**Alternatives Considered**:
- No unique constraint: allows stale duplicates, complicates lookups
- UPSERT (replace): could overwrite a valid mapping with a stale one
- `prefix_with('OR IGNORE')`: works but `on_conflict_do_nothing()` is the idiomatic SQLAlchemy approach

**Consequences**:
- Pro: Idempotent recording, clean semantics, uses project-established dialect
- Con: First recording wins — if the same external ID somehow reaches two sessions, the first session owns it

### Session switching only when idle

**Choice**: Reaction-based session switching only occurs when the delivery lock is free (agent is idle), following DES-009
**Why**: Switching sessions mid-response would disrupt the in-flight SDK exchange. The delivery lock already serializes message processing (via `if self._delivery_lock.locked()` check), so mid-stream reactions are steered into the current session as they are today — no session switch occurs.
**Sources**: DES-009 (Channel Delivery Serialization via asyncio.Lock)
**Alternatives Considered**:
- Interrupt mid-response: would require aborting SDK session, complex and risky
- Queue the switch for after response: adds complexity, lock serialization handles this naturally

**Consequences**:
- Pro: Simple, reuses existing locking semantics
- Con: User must wait for current response to complete before session switches via reaction

### Outgoing ID recording is async

**Choice**: Outgoing IDs are recorded asynchronously after the Result event
**Why**: Blocking response delivery on a database write adds unnecessary latency. The mapping is not needed until a future reaction arrives.
**Consequences**:
- Pro: No impact on response delivery latency
- Con: Brief window where outgoing IDs are not yet recorded — if a reaction arrives in this window, the mapping won't exist yet and the reaction routes normally (graceful degradation)

### Coordinator integration via public method

**Choice**: Add a `switch_to_session(target_session_id) -> bool` method on the coordinator
**Why**: The session switch logic (close current + reopen target) is coordinator-owned — it involves session state, SDK session ID management, and post-processing triggers. Exposing it as a public method keeps the integration boundary clean: the Telegram channel identifies *which* session to switch to (via external ID lookup), and the coordinator handles *how* to switch.
**Alternatives Considered**:
- Channel calls registry close/reopen directly: would bypass coordinator state management (SDK session ID, post-processing triggers)
- Special case in `_process_through_coordinator`: too coupled, mixes channel concerns into the generic processing path

**Consequences**:
- Pro: Clean separation of concerns, reusable for future session-switching triggers (e.g., DLT-086 reply-based switching)
- Con: One more public method on the coordinator surface

## System Behavior

### Scenario: Reaction on message from previous session

**Given**: A reaction arrives on a message whose external ID maps to a closed session that is not the current active session
**When**: The delivery lock is free (agent is idle)
**Then**: The coordinator closes the current session (triggering async post-processing), reopens the target session, and routes the reaction there
**Rationale**: Preserves conversation context — the reaction is processed within the session that generated the reacted-to message

### Scenario: Reaction on message from current session

**Given**: A reaction arrives on a message whose external ID maps to the current active session
**When**: The lookup succeeds
**Then**: No session switching occurs, the reaction routes normally
**Rationale**: No-op path — the reaction is already in the correct session

### Scenario: Reaction on unknown message

**Given**: A reaction arrives on a message whose external ID is not in the mapping table (pre-feature messages, orphaned IDs)
**When**: The lookup returns `None`
**Then**: The reaction routes to the current session without switching
**Rationale**: Graceful degradation — the system cannot determine the target session, so it continues with the current one

### Scenario: Reaction while agent is busy

**Given**: A reaction arrives while the delivery lock is held (agent is streaming a response)
**When**: `_delivery_lock.locked()` returns True
**Then**: The reaction is enqueued for steering into the current session — no session lookup or switching occurs
**Rationale**: Per DES-009, mid-stream messages go through the steering path. Session switching only happens when the lock is free

### Scenario: Target session fails resumption validation

**Given**: A reaction's external ID lookup finds a session, but that session fails resumption validation (missing transcript, too old, already open)
**When**: `coordinator.switch_to_session()` returns `False`
**Then**: The reaction routes to the current session without switching; a warning is logged
**Rationale**: Session resumption has safety checks (transcript exists, not too old, not already open). If those fail, the current session is the safe default

### Scenario: Outgoing ID recording failure

**Given**: The async task that records outgoing IDs encounters a database error
**When**: The error occurs
**Then**: The error is logged and the conversation continues
**Rationale**: Outgoing ID recording is best-effort — a missing mapping means future reactions on that message route normally (graceful degradation), not an error condition

### Scenario: Registry is None

**Given**: The session registry is not available (None)
**When**: `record_external_id` or `find_session_by_external_id` is called
**Then**: Both methods return early with a warning log
**Rationale**: Consistent with existing graceful degradation pattern for session tracking failures
