# Design: DLT-169 - Track External Message IDs Per Session

**Delta Spec**: [../delta-specs/DLT-169.md](../delta-specs/DLT-169.md)
**Status**: Draft

## Purpose

This document explains the design rationale for tracking platform-specific message IDs alongside conversation sessions, enabling reaction-based session switching.

## Problem Context

The system has no mechanism to map external message IDs (e.g., Telegram `message_id`) to internal session IDs. When a user reacts to a message from a previous conversation, there is no way to determine which session that message belonged to, making reaction-based session routing impossible.

## Design Overview

A channel-agnostic external ID mapping table records incoming and outgoing message IDs per session. The Telegram channel captures IDs at ingestion and response finalization. When a reaction arrives on a message from a different session, the reaction handler looks up the target session via the external ID, sets `target_session_id` on the envelope, and defers the reaction for processing. The coordinator's existing session management flow short-circuits when it sees `target_session_id`, closing the current session and reopening the target before routing the message.

## Shape

| Part | Mechanism | Flag |
|------|-----------|:----:|
| **S1** | New `channel_messages` DB table with domain model (`ChannelMessage` frozen dataclass), ORM record (`ChannelMessageRecord`), and migration SQL | |
| **S2** | Repository methods: `save(channel_message)` using `on_conflict_do_nothing()` on the unique index, and `lookup_session(channel, external_id) -> str \| None` | |
| **S3** | Registry facade methods wrapping repository: `record_channel_message()` and `find_session_by_external_id()` — both return early with a warning log when the registry is `None` | |
| **S4** | Add `external_id: str \| None = None` field to `TextMessage` and `ReactionMessage` envelopes (channel-specific metadata, not on the base class) | |
| **S5** | Add `target_session_id: str \| None = None` field to the base `MessageEnvelope` — a generic routing instruction that any message type can carry; the coordinator's session management checks this before boundary detection and short-circuits to the target session when set | |
| **S6** | Telegram incoming: set `external_id` on envelope and call `record_external_id` after session is determined | |
| **S7** | Telegram outgoing: expose finalized message IDs from ResponseRenderer, persist asynchronously after finalization — the Telegram channel captures `session_id` from the active session before entering `_process_through_coordinator()` and uses it in the async task spawned after Result | |
| **S8** | Telegram reaction: extract `event.message_id` from `MessageReactionUpdated`, look up target session via external ID — if it maps to a different session, set `target_session_id` on the `ReactionMessage` envelope and defer the message; otherwise route normally (steer if busy, process if idle) | |

## Components

### Implementation Structure

| Layer/Component | Responsibility | Key Decisions |
|-----------------|----------------|---------------|
| DB Model | `channel_messages` table with cascade delete, unique constraint on `(channel, external_id)` | Raw SQL migration (project convention) |
| Repository | Persist and query external IDs | `on_conflict_do_nothing()` on unique index; session-scoped query ordered by `id ASC` for insertion-order guarantee |
| Registry | Facade over repository with graceful degradation | Best-effort, errors logged not raised; returns early when registry is `None` |
| Base envelope | `target_session_id: str \| None = None` field on `MessageEnvelope` | Generic routing instruction, available to all subtypes; checked by coordinator before boundary detection |
| Message envelope (subtype fields) | `external_id` field on `TextMessage` and `ReactionMessage` | Optional field (data, not property hook per DES-013), `None` = no-op |
| Telegram channel (incoming) | Capture `message.message_id`, set on envelope, persist after session determined | Persist after session creation/resume to know session_id |
| Telegram channel (outgoing) | Expose `_current_message_id` + `_split_message_ids` after finalization, persist async | Capture session_id before processing; spawn async task after Result; each split ID recorded as its own ChannelMessage row |
| Telegram channel (reaction) | Extract `event.message_id`, look up session, defer with `target_session_id` if different session found | Defers (like `/queue`) when session switch is needed; normal reaction path otherwise |
| Coordinator session management | Check `target_session_id` as a short-circuit before boundary detection | Reuses existing close + `reopen_session` logic; falls back to current session on reopen failure |

### Integration Points

- Telegram channel calls `record_channel_message` after session is determined (incoming) and after response finalization (outgoing)
- Telegram reaction handler calls `find_session_by_external_id` — if different session found, sets `target_session_id` on the envelope and defers the message via `enqueue_deferred()`
- Coordinator's session management checks `target_session_id` before boundary detection; when set, closes current session and reopens target (same flow as boundary-detected session resumption)
- `target_session_id` is a field on the base envelope (DES-013: data, not a property hook) — any message type can carry it, making the routing mechanism generic

## Modeling

### ChannelMessage

```
ChannelMessage:
  id: int (auto-increment)
  session_id: str (FK → sessions.id, ON DELETE CASCADE)
  channel: str (canonical: "telegram", "repl")
  direction: str ("incoming" | "outgoing")
  external_id: str

Indexes:
  - UNIQUE (channel, external_id) — on_conflict_do_nothing on duplicate
  - session_id — for session-scoped queries (ordered by id ASC)
```

### SQLAlchemy Pattern

The project uses `sqlalchemy.dialects.sqlite.insert` (established in `app_state.py` with `on_conflict_do_update`). For insert-or-ignore:

```python
from sqlalchemy.dialects.sqlite import insert as sqlite_insert

stmt = sqlite_insert(ChannelMessageRecord).values(
    session_id=session_id, channel=channel, direction=direction, external_id=external_id
)
stmt = stmt.on_conflict_do_nothing(index_elements=["channel", "external_id"])
await db.execute(stmt)
```

## Data Flow

### Incoming Message

```
Telegram message → _handle_message/media
  → TextMessage(external_id=str(message.message_id))
  → coordinator.enqueue(envelope)
  → coordinator: session creation/resume
  → registry.record_channel_message(session_id, "telegram", "incoming", external_id)
```

### Outgoing Message

```
Before processing:
  Telegram channel captures current session_id into local variable

ResponseRenderer finalizes:
  → exposes (_current_message_id, _split_message_ids)
  → Telegram channel reads IDs

After Result event:
  → spawn async task:
      for each ID: registry.record_channel_message(captured_session_id, "telegram", "outgoing", str(id))
  → errors logged only (graceful degradation)

Note: split messages (typically 2-3 per response) are recorded individually in a loop;
bulk insertion is unnecessary given the small count and async execution.
```

### Reaction without Session Switch

```
MessageReactionUpdated → _handle_reaction
  → diff emojis (same as today)
  → lookup external_id → not found or same session
  → ReactionMessage(external_id=str(event.message_id))
  → if busy: enqueue (steer into current session)
  → if idle: enqueue + process (current session)
```

### Reaction with Session Switch (Deferred)

```
MessageReactionUpdated → _handle_reaction
  → diff emojis (same as today)
  → lookup external_id → found, maps to different session
  → ReactionMessage(
      external_id=str(event.message_id),
      target_session_id=target_id,
    )
  → enqueue_deferred() — reaction waits for current turn to complete

When deferred queue drains:
  → coordinator picks up ReactionMessage
  → session management sees target_session_id is set
  → short-circuit: close current session + reopen target session
  → if reopen fails: log warning, continue with current session
  → process reaction in the (now-current) session
```

### Coordinator Session Management (Updated)

```
Before boundary detection, coordinator checks envelope:

if envelope.target_session_id is not None:
    → close current session (async post-processing)
    → reopen_session(target_session_id)
    → if reopen fails: log warning, continue with current session
    → skip boundary detection
elif envelope.force_new:
    → skip boundary detection, force new session (existing behavior)
elif envelope.runs_boundary_detection:
    → run boundary detection (existing behavior)
else:
    → continue current session or create one (existing behavior)
```

## Key Decisions

### Generic target_session_id on base envelope

**Choice**: Add `target_session_id: str | None = None` as a field on the base `MessageEnvelope` class, not specific to `ReactionMessage`
**Why**: Session routing is a coordinator concern, not a channel-specific one. By putting `target_session_id` on the base class, any message type can trigger a session switch — reactions via external ID lookup, future reply-based switching (DLT-086), or other triggers. The coordinator's existing session management handles it uniformly.
**Sources**: DES-013 (Typed Envelope with Property Hooks) — `target_session_id` is data (a routing instruction), not a behavioral hook
**Alternatives Considered**:
- `target_session_id` only on `ReactionMessage`: couples session routing to one message type, not reusable
- New property hook on the base: over-engineering for a simple nullable field; hooks are for behavioral variation, not data
- New coordinator public method (`switch_to_session`): bypasses the existing session management flow, creates a parallel path

**Consequences**:
- Pro: Reusable across all message types, integrates naturally into existing coordinator flow
- Pro: No new coordinator method — session switching uses the same close + reopen logic boundary detection already uses
- Con: Every concrete envelope subtype carries the field (minor — defaults to `None`)

### Reactions with session switch are deferred

**Choice**: When a reaction's external ID maps to a different session, the reaction handler defers the message (via `enqueue_deferred()`) rather than immediately switching sessions
**Why**: Session switching involves closing the current session (triggering async post-processing) and reopening a target. Deferring ensures this only happens between turns — never mid-response. The deferred queue naturally handles busy/idle: when busy the reaction waits, when idle it processes immediately.
**Sources**: DES-009 (Channel Delivery Serialization); existing deferred queue pattern used by `/queue` command
**Alternatives Considered**:
- Immediate switch when delivery lock is free: would work but creates an inline session management path in the reaction handler, mixing channel logic with session state
- Steer mid-stream with session switch: too complex, risks disrupting the in-flight SDK exchange

**Consequences**:
- Pro: Clean separation — reaction handler only identifies the target; coordinator handles the switch
- Pro: Consistent with `/queue` pattern — deferred messages wait for current turn, process on drain
- Con: Even when idle, the reaction goes through the deferred queue drain path (one extra step) — acceptable because idle drains are immediate

### Unique constraint with on_conflict_do_nothing

**Choice**: UNIQUE on `(channel, external_id)` with `on_conflict_do_nothing()`
**Why**: The same message ID should never map to two sessions. If a re-processing occurs (e.g., duplicate event), the existing mapping is preserved rather than overwritten. This uses `sqlalchemy.dialects.sqlite.insert` with `on_conflict_do_nothing()`, distinct from the UPSERT pattern (`on_conflict_do_update`) used in `app_state.py`.
**Sources**: SQLAlchemy 2.x docs; project pattern established in `src/tachikoma/app_state.py`
**Alternatives Considered**:
- No unique constraint: allows stale duplicates, complicates lookups
- UPSERT (replace): could overwrite a valid mapping with a stale one
- `prefix_with('OR IGNORE')`: works but `on_conflict_do_nothing()` is the idiomatic SQLAlchemy approach

**Consequences**:
- Pro: Idempotent recording, clean semantics, uses project-established dialect
- Con: First recording wins — if the same external ID somehow reaches two sessions, the first session owns it

### Outgoing ID recording is async

**Choice**: Outgoing IDs are recorded asynchronously after the Result event
**Why**: Blocking response delivery on a database write adds unnecessary latency. The mapping is not needed until a future reaction arrives.
**Consequences**:
- Pro: No impact on response delivery latency
- Con: Brief window where outgoing IDs are not yet recorded — if a reaction arrives in this window, the mapping won't exist yet and the reaction routes normally (graceful degradation)

## System Behavior

### Scenario: Reaction on message from previous session (deferred)

**Given**: A reaction arrives on a message whose external ID maps to a closed session that is not the current active session
**When**: The reaction handler detects the different session
**Then**: The reaction is enqueued as a deferred message with `target_session_id` set; when the deferred queue drains, the coordinator closes the current session, reopens the target session, and processes the reaction there
**Rationale**: Deferring ensures session switching happens between turns, not mid-response. The deferred queue handles the busy/idle distinction naturally.

### Scenario: Reaction on message from current session

**Given**: A reaction arrives on a message whose external ID maps to the current active session
**When**: The lookup succeeds
**Then**: No `target_session_id` is set; the reaction routes normally through the existing path (steer if busy, process if idle)
**Rationale**: No-op path — the reaction is already in the correct session

### Scenario: Reaction on unknown message

**Given**: A reaction arrives on a message whose external ID is not in the mapping table (pre-feature messages, orphaned IDs)
**When**: The lookup returns `None`
**Then**: No `target_session_id` is set; the reaction routes normally to the current session
**Rationale**: Graceful degradation — the system cannot determine the target session, so it continues with the current one

### Scenario: Reaction while agent is busy

**Given**: A reaction arrives while the delivery lock is held (agent is streaming a response)
**When**: The reaction handler processes the event
**Then**: If the reaction maps to a different session, it is deferred (waits for current turn to complete). If it maps to the current session or has no match, it is steered into the current session (same as today).
**Rationale**: Per DES-009, mid-stream messages go through the steering path. Reactions needing session switching are deferred to avoid disrupting the in-flight exchange.

### Scenario: Target session fails resumption validation

**Given**: A deferred reaction's `target_session_id` points to a session that fails resumption validation (missing transcript, too old, already open)
**When**: The coordinator attempts to reopen the target session
**Then**: `reopen_session()` returns `None`; the coordinator logs a warning and falls back to the current session; the reaction routes to the current session
**Rationale**: Session resumption has safety checks (transcript exists, not too old, not already open). If those fail, the current session is the safe default.

### Scenario: Outgoing ID recording failure

**Given**: The async task that records outgoing IDs encounters a database error
**When**: The error occurs
**Then**: The error is logged and the conversation continues
**Rationale**: Outgoing ID recording is best-effort — a missing mapping means future reactions on that message route normally (graceful degradation), not an error condition

### Scenario: Registry is None

**Given**: The session registry is not available (None)
**When**: `record_channel_message` or `find_session_by_external_id` is called
**Then**: Both methods return early with a warning log
**Rationale**: Consistent with existing graceful degradation pattern for session tracking failures

### Scenario: Non-reaction message with target_session_id

**Given**: Any message type carries `target_session_id` (not just reactions)
**When**: The coordinator's session management processes the message
**Then**: The same short-circuit applies — close current session, reopen target, process the message there
**Rationale**: `target_session_id` is generic on the base envelope. This enables future triggers (e.g., DLT-086 reply-based switching) to reuse the same routing mechanism without coordinator changes.
