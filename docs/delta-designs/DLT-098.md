# Design: DLT-098 - Capture SDK stderr on error for debugging

**Delta Spec**: [../delta-specs/DLT-098.md](../delta-specs/DLT-098.md)
**Status**: Draft

## Purpose

This document explains the design rationale for this delta: the modeling choices, data flow, system behavior, and architectural approach.

After implementation, the "Detected Impacts" section will guide reconciliation into feature design docs.

## Problem Context

When an SDK call fails (the CLI subprocess exits non-zero), the raised `ProcessError` contains only a static message — not the actual stderr output from the subprocess. The SDK provides a `ClaudeAgentOptions.stderr` callback (`Callable[[str], None]`) that receives each stderr line during execution, but Tachikoma doesn't set it. Operators debugging failures have no subprocess diagnostic context.

**Constraints:**
- The `stderr` callback is synchronous and invoked per-line by the SDK's `SubprocessCLITransport`
- Stderr capture must never cause secondary failures (fail-open policy per R3)
- The callback field exists in the SDK source but is not yet documented in official docs — verified from `claude_agent_sdk.types.ClaudeAgentOptions` (line 1006)
- There are two distinct SDK call patterns: standalone `query()` (8 sites) and `ClaudeSDKClient` (2 sites), each needing different integration

**Interactions:**
- `agent_defaults.py` provides shared SDK configuration (cwd, cli_path, env) used by all call sites
- `sdk_transport.py` already provides a custom transport subclass — this delta adds a sibling module
- DES-002 logging conventions govern how stderr is included in log calls
- DES-005 query generator consumption governs how `query()` iterators are consumed

## Design Overview

Three components form a layered solution: a reusable accumulator, a query wrapper, and integration points at the two `ClaudeSDKClient` sites.

```
┌──────────────────────────────────────────────────────┐
│                    sdk_query.py                        │
│                                                        │
│  ┌─────────────────────┐  ┌────────────────────────┐  │
│  │  StderrAccumulator   │  │  stderr_aware_query()  │  │
│  │  __call__(line)      │  │  creates accumulator   │  │
│  │  get(max_chars)      │  │  installs on options   │  │
│  │  ──────────────────  │  │  delegates to query()  │  │
│  │  Silently swallows   │  │  logs stderr on error  │  │
│  │  internal errors     │  │  re-raises unchanged   │  │
│  └─────────────────────┘  └────────────────────────┘  │
└──────────────────────────────────────────────────────┘
         ▲                           ▲
         │                           │
    Used by S3                  Used by 8 sites
  (coordinator,              (boundary, forks,
   bg executor)             memory, skills, etc.)
```

The `StderrAccumulator` is the shared primitive. `stderr_aware_query()` wraps the SDK's `query()` for standalone consumers. The coordinator and background task executor create their own accumulator instances and install them directly, reading the buffer in their existing error handlers.

## Shape

| Part | Mechanism | Flag |
|------|-----------|:----:|
| **S1** | **Stderr accumulator** — Class in `sdk_query.py` with `__call__(line: str)` (the `ClaudeAgentOptions.stderr` callback), `get(max_chars: int) -> str | None` for retrieval with tail-truncation, and silent error swallowing in `__call__`. Returns `None` from `get()` when buffer is empty (no noise in logs). Created fresh per SDK call, discarded after. | |
| **S2** | **Wrapped `query()`** — `stderr_aware_query()` async generator in `sdk_query.py`. Creates S1, installs on `options.stderr`, delegates to SDK's `query()`. On `ProcessError`, logs accumulated stderr as structured field (`stderr={...}`) per DES-002, then re-raises unchanged. All 8 standalone `query()` consumers switch to this function. `fork_and_consume`/`fork_and_capture` also switch internally. | |
| **S3** | **ClaudeSDKClient stderr integration** — Coordinator's `_build_options()` accepts and installs an S1 instance on `ClaudeAgentOptions.stderr`. The coordinator's `send_message()` creates the accumulator before `_build_options()`, and the existing `except (CLIConnectionError, ProcessError)` handler adds the accumulated stderr to its log call. Background task executor follows the same pattern: creates accumulator **before** the `async with ClaudeSDKClient(options) as client:` block so it remains in scope, installs on options, and the outermost `except Exception` handler (line 386) reads the accumulated stderr. | |

## Components

### Implementation Structure

| Layer/Component | Responsibility | Key Decisions |
|-----------------|----------------|---------------|
| `sdk_query.py` | StderrAccumulator class + `stderr_aware_query()` wrapper | New module alongside `sdk_transport.py`; houses all stderr capture logic |
| `coordinator.py` | Creates accumulator, passes to `_build_options()`, reads in error handler | Accumulator created in `send_message()`, scoped to single message exchange |
| `tasks/executor.py` (execute) | Creates accumulator before `async with` block, installs on options, outermost `except Exception` reads it | Accumulator created before client context manager so it stays in scope |
| `tasks/executor.py` (_run_evaluator) | Switches lazy `from claude_agent_sdk import query` to `from tachikoma.sdk_query import stderr_aware_query` | Lazy import pattern preserved; function name changes |
| `post_processing.py` | `fork_and_consume()`/`fork_and_capture()` switch to `stderr_aware_query()` | Internal change only — function signatures unchanged |
| 5 other `query()` consumers | Switch `query()` import to `stderr_aware_query()` from `sdk_query` | One-line import change + function name swap per site |

### Cross-Layer Contracts

**StderrAccumulator API**:
```python
class StderrAccumulator:
    def __call__(self, line: str) -> None: ...
    def get(self, max_chars: int = 10_000) -> str | None: ...
```

**`stderr_aware_query()` signature** (mirrors SDK `query()`):
```python
async def stderr_aware_query(
    *,
    prompt: str | AsyncIterable[dict[str, Any]],
    options: ClaudeAgentOptions | None = None,
    transport: Transport | None = None,
) -> AsyncIterator[Message]: ...
```

**Integration Points**:
- `stderr_aware_query()` is a drop-in replacement for SDK `query()` — same signature, same yielded types, same exception types
- Coordinator and executor create `StderrAccumulator` manually and install via `options.stderr = accumulator`
- Error handlers read `accumulator.get()` and include the result as a `stderr=` keyword in existing log calls

### Shared Logic

- **StderrAccumulator**: Shared between the query wrapper (S2) and direct client integration (S3). Both paths create an instance, install it as the `ClaudeAgentOptions.stderr` callback, and read the buffer on error.
- **Truncation logic**: Centralized in `StderrAccumulator.get()` — all consumers get consistent truncation behavior.

## Modeling

The design introduces one new type:

**`StderrAccumulator`** — a stateful callable that serves as both the SDK callback and the buffer reader. It's not persisted or shared across calls — each SDK invocation creates a fresh instance. The lifecycle is:

```
Created → Installed on options.stderr → Invoked per stderr line → Read on error → Discarded
                                                                   (or discarded on success)
```

No database entities, no configuration, no new domain types.

## Data Flow

### Standalone `query()` path (S2)

```
Consumer calls stderr_aware_query(prompt, options)
  │
  ├─ Create StderrAccumulator
  ├─ Install accumulator on options.stderr
  ├─ Delegate to SDK query(prompt, options)
  │     │
  │     ├─ SDK subprocess starts, stderr piped
  │     ├─ Per stderr line → accumulator.__call__(line) → appended to buffer
  │     ├─ Per SDK message → yielded to consumer
  │     │
  │     ├─ [SUCCESS] Generator exhausted normally
  │     │     └─ Accumulator discarded (buffer garbage collected)
  │     │
  │     └─ [FAILURE] ProcessError raised
  │           └─ stderr_aware_query catches it
  │                 ├─ stderr = accumulator.get(max_chars=10_000)
  │                 ├─ If stderr is not None: log with stderr={stderr}
  │                 └─ Re-raise ProcessError unchanged
  │
  └─ Consumer receives ProcessError as before (no behavior change)
```

### `ClaudeSDKClient` path (S3)

```
Coordinator.send_message() / Executor.execute()
  │
  ├─ Create StderrAccumulator
  ├─ Install on ClaudeAgentOptions.stderr (via _build_options or direct)
  ├─ Create ClaudeSDKClient with options
  ├─ Iterate receive_response()
  │     │
  │     ├─ Per stderr line → accumulator.__call__(line)
  │     ├─ Per SDK message → processed normally
  │     │
  │     ├─ [SUCCESS] Response complete
  │     │     └─ Accumulator discarded
  │     │
  │     └─ [FAILURE] CLIConnectionError / ProcessError / Exception
  │           └─ Existing error handler fires
  │                 ├─ stderr = accumulator.get(max_chars=10_000)
  │                 ├─ If stderr is not None: add stderr={stderr} to existing log call
  │                 └─ Original error handling continues unchanged
```

## Key Decisions

### New module rather than extending `agent_defaults.py`

**Choice**: Create `sdk_query.py` as a sibling to `sdk_transport.py`
**Why**: `agent_defaults.py` is a frozen dataclass with merge logic — it defines configuration, not behavior. The stderr accumulator and query wrapper are behavioral components that wrap SDK calls. Placing them in a separate module follows the same pattern as `sdk_transport.py` (another SDK behavioral wrapper).
**Alternatives Considered**:
- `agent_defaults.py`: Mixes data (frozen config dataclass) with behavior (async generator, stateful accumulator). Would blur the module's single responsibility.
- Inline in each consumer: Violates R1 (centralization). Would duplicate accumulator creation and error logging across 10 sites.
**Consequences**:
- Pro: Clean separation — config in `agent_defaults`, transport in `sdk_transport`, query wrapping in `sdk_query`
- Con: New module (minimal — it's small and focused)

### Tail-truncation (keep most recent stderr)

**Choice**: When stderr exceeds `max_chars`, discard the beginning and keep the tail
**Why**: The most diagnostically valuable stderr lines are typically the final ones — the error message, stack trace, or crash output. Earlier lines are often progress/debug noise. This matches how operators read logs: bottom-up from the error.
**Alternatives Considered**:
- Head-truncation (keep oldest): Loses the error message that triggered the failure
- Middle-truncation: More complex, unclear benefit
- Line-count limit: Characters are a more predictable size bound for log storage
**Consequences**:
- Pro: Maximizes diagnostic value in truncated output
- Con: May lose early context (e.g., deprecation warnings preceding the error) — acceptable trade-off

### `StderrAccumulator` as a class rather than closure

**Choice**: A class with `__call__` and `get()` methods
**Why**: Explicit API makes it testable (can assert on `get()` return values), inspectable, and self-documenting. The class encapsulates the truncation threshold, error swallowing, and empty-buffer-returns-None logic in one place. A closure would hide the retrieval interface behind captured variables.
**Alternatives Considered**:
- Closure returning `(callback, get_buffer)` tuple: Less discoverable, harder to test, no natural place for truncation logic
- Plain list with external helper: Scatters the logic across creation and consumption sites
**Consequences**:
- Pro: Clean testable API, single responsibility, easy to mock
- Con: Slightly more code than a bare closure — acceptable for clarity

### Default truncation threshold of 10,000 characters

**Choice**: 10KB default for `max_chars` parameter
**Why**: Balances capturing enough context for meaningful diagnosis against log size. A typical Python traceback is 2-5KB. The SDK's stderr output is usually short (a few lines of error context). 10KB accommodates multi-frame tracebacks and multi-line error messages without risking log explosion from pathological stderr spam.
**Alternatives Considered**:
- 1KB: Too aggressive — could truncate a useful traceback
- 50KB: Excessive for a log field — risks slow log pipelines
- Configurable via config.toml: Over-engineering for an edge case; the default is sensible and the parameter is already adjustable per call site
**Consequences**:
- Pro: Reasonable default, overridable per-call via `get(max_chars=N)`
- Con: Not user-configurable — acceptable since this is an operator diagnostic, not a user-facing feature

## System Behavior

### Scenario: SDK subprocess fails with stderr output

**Given**: A standalone `query()` consumer (e.g., boundary detector) calls `stderr_aware_query()`
**When**: The SDK subprocess writes diagnostic output to stderr and exits non-zero, raising `ProcessError`
**Then**: The wrapper catches `ProcessError`, calls `accumulator.get()`, logs with `stderr={accumulated_output}`, and re-raises the original `ProcessError` unchanged. The consumer's caller (e.g., coordinator) handles the exception identically to before.
**Rationale**: The wrapper adds observability without changing error propagation. Callers don't need to know stderr capture exists.

### Scenario: SDK subprocess fails with no stderr

**Given**: An SDK call fails but the subprocess produced no stderr output
**When**: The error handler calls `accumulator.get()`
**Then**: `get()` returns `None`. The log call omits the `stderr=` field entirely.
**Rationale**: Prevents empty/noise fields in logs. Only log stderr when there's something to show.

### Scenario: Accumulator callback itself throws

**Given**: The `__call__` method encounters an unexpected error (e.g., memory pressure during list append)
**When**: The SDK transport invokes the stderr callback
**Then**: The exception is silently swallowed inside `__call__`. The SDK subprocess continues unaffected. The buffer may be incomplete but the primary operation is unimpacted.
**Rationale**: R3 — stderr capture must never cause secondary failures. The callback is an observer, not a participant.

### Scenario: Massive stderr output

**Given**: A subprocess writes 100KB+ to stderr (e.g., verbose debug logging)
**When**: The error handler calls `accumulator.get(max_chars=10_000)`
**Then**: The first ~90KB is discarded, the last 10KB is returned with a `[stderr truncated]\n` prefix followed by the tail content.
**Rationale**: R4 — prevents log explosion while preserving the most diagnostic content (tail).

### Scenario: Coordinator catches CLIConnectionError

**Given**: The coordinator's `send_message()` catches a `CLIConnectionError` (R6 = Out of scope)
**When**: The error handler fires
**Then**: The accumulated stderr is still available via `accumulator.get()` and included in the log. Although R6 scoped out CLIConnectionError specifically, the coordinator's error handler catches both exception types in a single `except` clause — the stderr will be logged for both because the accumulator is already installed.
**Rationale**: No reason to conditionally exclude CLIConnectionError from logging when the accumulator is already there. The spec scoped out making CLIConnectionError a *requirement*, but including it is a natural side effect at zero cost.

## Notes

- The SDK's `ClaudeAgentOptions.stderr` field (`Callable[[str], None] | None`) exists in the SDK source (types.py) but is not yet in official documentation. Verified working via `SubprocessCLITransport._handle_stderr()` which pipes stderr when the callback is set.
- `ProcessError.stderr` attribute exists but is populated with whatever string the SDK passes at raise time — not necessarily the real subprocess stderr. Our accumulator captures the real output independently.
