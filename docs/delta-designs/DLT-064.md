## Purpose

This document explains the design rationale for this delta: the modeling choices, data flow, system behavior, and architectural approach.

After implementation, the "Detected Impacts" section will guide reconciliation into feature design docs.

## Problem Context

When the agent performs intensive work — a code-implementation turn that reads, edits, and searches across many files — the Telegram `StreamRenderer` renders every tool summary and each short bridging text paragraph inline, in arrival order. A long turn of that shape produces a single tall message: a wall of `_🔧 <summary>_` markers interleaved with one- or two-line prose fragments, with the actual final answer buried at the bottom. The user has to scroll past all of the mechanics to reach the substance.

The channel already has the building blocks: `appendTool` records each tool and bakes a `_🔧 <summary>_` marker (via `summarizeToolActivities`) into the buffer at the next text or finalize, separated by blank lines; `compose()` rebuilds the whole display string on every flush and `editMessageText` replaces the full text. What is missing is a notion of *intensive work* and a way to fold the accumulated intermediate activity into a compact, collapsed region so the final answer is what the user sees by default.

**Constraints (from the spec and the existing channel):**

- The collapse region has no representation in the agent's GitHub-flavored markdown — GFM `>` maps to `blockquote`, never to Telegram's collapsed `expandable_blockquote`. The collapse boundary is a renderer concept derived from event timing, not from markdown structure.
- Telegram renders an `expandable_blockquote` collapsed only when it spans **multiple lines**; a single short line renders as a plain (expanded) quote. The trigger must therefore reliably produce a multi-line block.
- An in-progress tool must stay visible while it runs (the user should see active work); a segment may fold only once its tools have completed — i.e. at the next boundary, never mid-execution.
- `editMessageText` replaces the *full* message text and entities on every edit (re-confirmed against the Bot API), so any collapsed region must be recomposed on every flush, exactly as the decision header (DES-009) already is.
- A message already committed (overflow chunk or finalized) must never be retroactively collapsed; detection is per-message and resets at each split. The send path must never lose text when rendering fails — the existing broken-render plain fallback (`sendChunked`, no entities) must stay collapse-free so a blockquote-entity failure can never block delivery.

**Interactions:**

- `StreamRenderer` (`src/extensions/telegram/streaming.ts`) owns the buffer, the bake/fold/flush/finalize loop, and the decision header.
- `entities.ts` owns markdown→entity conversion and entity-safe chunking; this delta adds the structured-payload helpers the collapse path needs.
- `channel.ts` constructs the renderer and would thread the two new config keys; `index.ts` declares the config schema.
- DES-009 (turn-scoped anchored header) — the header must anchor *above* the collapsed block on every recompose.

Confirmed spec decisions this design builds on: mechanism = Telegram `expandable_blockquote`; threshold as a **trigger** (default 4, collapse when *exceeded*); counting unit = the tool→text transition; positional collapse (all intermediate segments fold into one block, only the final tail stays expanded; no length/content heuristic); retroactive fold on crossing; a separate enable flag; in-progress tools stay expanded.

## Design Overview

The `StreamRenderer` gains **collapse state** — a boundary counter and an enable flag — alongside its existing buffer/transient/header state. As events arrive it counts tool→text transitions within the current uncommitted message; once the count exceeds the threshold, collapse becomes active for that message. Collapse changes only *how the live message is composed into a payload*, not how events are recorded: the buffer, the baked `_🔧 <summary>_` markers, and the paragraph-gated streaming all behave exactly as today.

When collapse is inactive the renderer keeps its current path: `compose()` builds a markdown string and `toTelegramEntities(display)` converts it. When collapse is active the renderer instead builds a **structured payload**: it splits its content into the *intermediate* region (every completed summary marker and bridging-text segment chronologically before the live tail) and the *live tail* (the streaming paragraph or the currently-running tool), converts each separately, wraps the intermediate region in one `expandable_blockquote` entity, and concatenates the two. Two small pure helpers in `entities.ts` — `wrapExpandable` and `concatPayloads` — make this a localized change that reuses the existing convert-then-split pipeline and the existing `editWithFallback`/`sendWithFallback` send path.

The fold is **retroactive and positional**: on the boundary that crosses the threshold, the live message is rebuilt from the buffer so segments that had rendered inline fold into the block, leaving only the current tail expanded; as each new boundary forms, the previous tail folds in and the new tail stays. Collapse is applied only at boundaries (never while a tool runs), resets at each message boundary, and is skipped entirely on the broken-render plain fallback. The threshold-as-trigger model guarantees the block holds several baked summaries (multi-line) by the time collapse activates, so it collapses reliably.

### Cross-Layer Contracts

- **Config → renderer**: `collapseIntensiveWork: boolean` and `intensiveWorkThreshold: number` flow `index.ts` (schema + destructuring) → `channel.ts` (options) → `StreamRenderer` constructor. The renderer treats `collapseIntensiveWork === false` as "never active" (short-circuits the counter), preserving today's rendering exactly.
- **Renderer → send path**: unchanged. The collapse path produces a `TelegramPayload` and hands it to the same `editWithFallback`/`sendWithFallback` the markdown path uses; those already attach `entities` and fall back to plain text on a render rejection, so a blockquote-entity failure degrades to inline (expanded) text rather than losing the message.
- **Renderer → chunker**: the finalized collapsed payload is chunked by the existing `splitMessageWithEntities`, which drops only entities whose `length > limit`. Since the collapsed block lives within one ≤4096 message, the `expandable_blockquote` entity is never the oversized one dropped. When the buffer exceeds the edit limit, `commitOverflow()` finalizes every *full* chunk in place before the collapse region can grow large enough to risk overflow — the collapsed block therefore lives in the tail message, and each committed chunk is itself evaluated for collapse independently (a committed message is never edited again, so it is never retroactively collapsed).

### Shared Logic

- **Boundary counting** — one increment per tool→text transition. "Tool block followed by any text" is one boundary regardless of how many tools it contained (mirrors `summarizeToolActivities`, which already collapses a tool burst into one phrase). A trailing tool block with no following text adds no boundary.
- **Intermediate/tail split** — positional. The live tail is the currently-streaming paragraph or the currently-running tool (the same "tail" the existing `streamableBuffer()`/`transient` logic tracks); everything chronologically before it is intermediate and folds. No length or content heuristic decides bridging vs. substantive.
- **Payload assembly** (collapse path) — `headerPayload ⊕ wrapExpandable(convert(intermediate)) ⊕ convert(tail)`, joined by `concatPayloads` with `\n\n` separators. The header is converted from its markdown form separately and prepended, so it anchors above the block (DES-009) without being inside it.
- **Collapse-eligibility gating** — a segment becomes foldable only when text (or another tool) resumes after its tools, i.e. at a boundary; the running tool's live line is never folded. This is what makes R3 ("in-progress tools stay visible") fall out of the boundary model.

## Modeling

The domain is a classification of the rendered message's content into regions, driven by event order within one uncommitted message:

```
one StreamRenderer (per exchange) ── one current uncommitted message
 │
 ├─ header            (DES-009; expanded, anchored, optional)
 ├─ collapsed block   (expandable_blockquote; only when collapse active)
 │   └─ intermediate segments:  { _🔧 <summary>_ } + bridging text, per tool→text segment
 └─ live tail          (expanded): the streaming paragraph | the running tool's live line
```

**Segment / boundary model.** Events arrive as `text` deltas and `tool-start`s. The renderer groups them into segments. A boundary is the **tool→text transition** — the moment text resumes after one or more tools. This names the *completing* transition, not the order content appears: a real segment reads "text + tools" (the assistant narrates, then acts), and the text resuming *after* the next tool burst is the signal that the preceding text+tools block is done and foldable. Counting the tool→text transition vs. the text→tool transition yields the same count for real alternation (they differ by at most one at the very start/end of a turn, negligible against the threshold).

**Region classification is positional, not heuristic.** "Intermediate" is *everything chronologically before the live tail*; "tail" is the currently-streaming text or the currently-running tool. Collapse never inspects text length or content to decide what is bridging — R4's rule. This is what keeps the final answer (the last tail) expanded while all prior narration folds, regardless of how long any single paragraph is.

**Collapse state lifecycle (per uncommitted message):**

```
            (events accumulate, count grows)
 count ≤ threshold ──────────────► inactive: render exactly as today
                    │
          count > threshold (crossing boundary)
                    ▼
              active ──► fold intermediate on every flush; tail stays expanded
                    │
        message boundary (overflow commit / finalize split)
                    ▼
              reset counter; next message evaluated independently
```

## Data Flow

**Live streaming (per `flush()`):**

```
text delta / tool-start / status
        │
        ▼
bakePendingTools() + buffer/transient update        (unchanged)
        │
        ▼
update boundary counter on a tool→text transition   (new: S1)
        │
        ▼
collapse active?  ── no ──► compose(): string → toTelegramEntities(display)   (unchanged path)
        │
        yes
        ▼
split content into intermediate | tail              (S3, positional)
        │
        ▼
build payload: wrapExpandable(convert(intermediate)) ⊕ convert(tail)   (S4)
        │   (+ prepend header payload if a header is set)
        ▼
editWithFallback(payload)   ── on render rejection → plain text (block lost, text safe)
        │
        ▼
earlier segments now folded; only live tail expanded
```

On the boundary that crosses the threshold, the next flush rebuilds from the buffer and segments that had rendered inline fold in retroactively — the user watches intermediate work collapse in as the answer grows.

**Finalize (`finalize()`):** `bakePendingTools()` runs first — for a trailing tool block with no following text, this bakes its summary into the buffer as the final segment; since no subsequent text forms a boundary after it, that summary folds into the collapsed block (the all-intensive case). If broken → existing `finalizeBroken` (`sendChunked`, **no collapse**, no entities). Otherwise build the finalized payload: `headerPayload ⊕ wrapExpandable(convert(intermediate)) ⊕ convert(tail)` when collapse is active, else the existing `convertAndSplit(header + body)`. Chunk via `splitMessageWithEntities` (entity-safe), edit the first chunk in place, send the rest. **All-intensive edge:** when there is no tail text (the turn ends on a tool, or the threshold was crossed on the final boundary), the final `convert(tail)` and its separator are omitted — `concatPayloads` returns the left operand unchanged for an empty right — so the payload's entire body is the collapsed block (`headerPayload ⊕ wrapExpandable(convert(intermediate))`), never an empty message.

**Overflow (`commitOverflow()`):** when the buffer exceeds the limit, commit full chunks in place and keep the tail streaming. A committed chunk is a message boundary: the counter resets, and a committed chunk that was itself intensive carries its own collapsed block (the compose path runs at commit time too). A committed message is never edited again, so it is never retroactively collapsed (R9).

## Key Decisions

### Collapse mechanism: Telegram `expandable_blockquote` (collapsed-by-default blockquote)

**Choice**: Fold intermediate segments into a Telegram `expandable_blockquote` entity — a collapsed-by-default, tap-to-expand block — emitted directly as a `MessageEntity` (the channel sends with `parse_mode` omitted and entities attached, consistent with the existing entity-based rendering).
**Why**: The collapse must be compact by default yet fully retrievable. Telegram's `expandable_blockquote` (TL `messageEntityBlockquote` with `collapsed=true`) is exactly that: it renders collapsed with a tap-to-expand affordance, native to every Telegram client, with no extra dependency. Emitting it as an entity keeps it on the same render path as the channel's existing bold/italic/code/blockquote entities and their plain-text fallback.
**Sources**: Telegram Bot API `MessageEntity` — `expandable_blockquote` = "collapsed-by-default block quotation" (`https://core.telegram.org/bots/api#messageentity`, Bot API 10.1, June 2026); confirmed present in the installed `@grammyjs/types@3.27.3` (`message.d.ts:506`, grammY `1.43.0`); [ADR-005](../architecture/ADR-005-telegram-library.md) establishes grammY as the Telegram library, whose current types carry the entity directly.
**Options Researched**:
- **Spoiler tag (`spoiler` entity)** — hides content behind a tap-to-reveal overlay. Rejected: a spoiler is for *hidden* content (revealed once, then shown); it is not a compact summary the user can expand and scan, and its affordance reads as "secret," not "collapsed work log."
- **Inline-expanded text / a second message** — sending the intermediate content as a separate message or plain collapsed-looking text. Rejected: a second message lingers and breaks the single-message stream (the same reason DES-009 anchors the header rather than sending it separately); plain text can't collapse at all.
- **Telegram Rich Messages `<details>` block (Bot API 10.1)** — a newer collapsible `<details>`/summary block. Rejected: it requires the new `sendRichMessage`/`editMessageText` `rich_message` path (a parallel rendering pipeline the channel does not use) and is far newer/less ubiquitous than the entity-based blockquote; the entity path composes with the existing convert-then-split pipeline at zero architectural cost.
**Why This Over Alternatives**: The `expandable_blockquote` entity is the only option that is (a) native and ubiquitous, (b) collapsible-by-default with a tap-to-expand summary, and (c) expressible on the channel's existing entity-based send path without a new pipeline or dependency.
**Consequences**:
- Pro: One collapsed block, native affordance, zero new dependencies, reuses the entity send + fallback path.
- Pro: Inner `italic`/`code`/`bold` markers (the baked summaries) nest validly inside it (Bot API: only `blockquote`/`expandable_blockquote` can't nest *each other*).
- Con: A single short line won't collapse (renders as an expanded quote) — mitigated by the threshold-as-trigger model (next decision).
- Con: One more entity type the renderer can emit; contained in the collapse path only.

### Emission path: renderer-driven structured payload (not a markdown sentinel)

**Choice**: Build the collapsed region as a structured `TelegramPayload` in the renderer, via two pure `entities.ts` helpers — `wrapExpandable(payload)` (wrap a converted payload in one `expandable_blockquote` span) and `concatPayloads(a, b, sep?)` (join payloads, rebasing offsets) — instead of introducing a markdown construct the converter maps.
**Why**: The collapse region is a renderer concept with no markdown representation (GFM `>` → `blockquote`, never expandable). The boundary is computed from event timing, not document structure, so it cannot come out of `markdown-it`'s token walk. Building the payload structurally — convert the intermediate and tail regions separately, wrap one, concat — is a localized change that leaves the markdown-buffer model intact for every non-collapse flush and reuses the existing convert-then-split pipeline and entity-safe chunker.
**Sources**: `entities.ts` (`Renderer.beginSpan(type, extra)` is already parameterized by entity type; the `blockquote` emission path; `splitMessageWithEntities` rebase logic); `@grammyjs/types@3.27.3` (`MessageEntity.type` accepts `"expandable_blockquote"`); Bot API nesting rules (`https://core.telegram.org/bots/api#formatting-options`). Full investigation: [SPIKE-DLT-064](../spikes/SPIKE-DLT-064-expandable-blockquote.md).
**Options Researched**:
- **Markdown sentinel (Option B)** — a custom markdown token/HTML comment the converter maps to `expandable_blockquote`, so the renderer keeps composing one markdown string. Rejected: markdown-it runs with `html: false` (HTML is dropped), and a surviving custom block token would need a plugin registration; the sentinel would be a non-standard, fragile convention invented solely to avoid a clean structured splice.
- **Generalize the existing `blockquote_open` handler** — emit `expandable_blockquote` for some markdown variant of `>`. Rejected: there is no GFM construct that should map to *collapsed*; `>` is and must remain an expanded blockquote. Collapsing is not a property of the agent's prose.
**Why This Over Alternatives**: It is the only option that keeps the collapse boundary a pure renderer concept (matching its event-timing derivation) while reusing the existing payload/send/chunk machinery, with no invented markdown convention and no new rendering pipeline.
**Consequences**:
- Pro: The collapse path is additive; below-threshold/disabled/broken-render paths are untouched.
- Pro: The helpers are pure and unit-testable independently of the renderer.
- Con: The renderer has two compose paths (markdown string vs. structured payload) rather than one; contained by a single `collapse active?` branch.

### Threshold as a trigger, not a quota; no enforced floor

**Choice**: `intensiveWorkThreshold` (default 4) is the count the boundary number must **exceed** to activate collapse — not a budget of segments kept visible. Turns at or below it render exactly as today. The threshold is **not** clamped to a minimum floor: it is fully configurable, with the documented behavior that a deliberately low value may produce a single-summary (single-line) block that Telegram renders expanded rather than collapsed.
**Why**: The threshold's job is to distinguish a normal turn (a few tool uses) from intensive work, then get out of the way — collapse is positional thereafter. Treating it as a trigger (not a quota) means there is no "keep the first N segments visible" bookkeeping; the count is a single integer compared once per boundary. Enforcing a floor would override explicit user config to paper over a cosmetic edge (an expanded quote is still readable), which is worse than honoring the config and documenting the constraint.
**Sources**: Spec R6/R8 and the "collapse triggers only once the 5th boundary forms" AC; the multi-line collapse requirement is empirically observed Telegram client behavior (the Bot API `expandable_blockquote` spec does not state a line minimum, but clients render a single short line as an expanded quote) — corroborated by `https://stackoverflow.com/questions/79427631` (retrieved 2026-06-21).
**Options Researched**:
- **Enforce a minimum floor (e.g. clamp effective threshold to 2)** so the block always has enough summaries to collapse. Rejected (per user decision): guarantees collapse at the cost of overriding explicit config; the default already collapses reliably, and an expanded quote under a pathological low threshold is acceptable degradation, not a failure.
- **Synthetic padding** — pad a too-short block with extra lines so it collapses. Rejected: invents content the agent never produced, purely to satisfy a client rendering quirk; worse than letting it render expanded.
**Why This Over Alternatives**: Honors explicit configuration, matches the "threshold as trigger" model, and degrades gracefully (expanded quote) rather than inventing content or silently overriding settings.
**Consequences**:
- Pro: Simplest possible trigger semantics; no floor/padding machinery; config is honest.
- Pro: At the default (4), the block always holds ≥5 boundaries' worth of summaries (multi-line) and collapses reliably.
- Con: A user who sets the threshold to 1 may see an expanded (non-collapsed) quote; documented, not enforced.

### Retroactive, positional fold (no content heuristic)

**Choice**: When collapse is active, *all* content chronologically before the live tail folds into the single collapsed block; the live tail (streaming paragraph or running tool) stays expanded. The fold is applied at boundaries and rebuilt from the buffer on every flush, so segments that rendered inline before the threshold was crossed fold in retroactively.
**Why**: The user's goal is to see the final answer by default, so "everything that is not the final tail is intermediate" is the correct, predictable rule. Making it positional (not a length/content heuristic) means collapse never has to guess what is "bridging" vs. "substantive" — a guess that would misfire on short-but-important paragraphs. Rebuilding from the buffer on each flush is what the renderer already does for the header/body, so the retroactive fold reuses that recomposition rather than adding incremental patching.
**Sources**: Spec R2/R4 and the "collapse is purely positional" AC; DES-009 (recompose-on-every-edit model).
**Options Researched**:
- **Length heuristic** (collapse only "short" paragraphs). Rejected: misfires on a short-but-load-bearing paragraph; unpredictable.
- **Incremental fold** (fold each segment in place as it completes, never rebuild). Rejected: would require per-segment edit bookkeeping and can't cleanly handle the crossing boundary (earlier inline segments must fold at once); rebuilding from the buffer is simpler and already proven by the header path.
**Why This Over Alternatives**: Positional collapse is predictable, requires no heuristic, and reuses the existing rebuild-from-buffer recomposition.
**Consequences**:
- Pro: The final answer is always the prominent, expanded content; the rule is easy to reason about.
- Pro: No length/heuristic tuning; the crossing boundary is handled for free by the rebuild.
- Con: A turn whose "final" paragraph is not last (rare) would fold it — acceptable, since the tail is defined as the live/last content, which is the answer by construction at finalize.

## System Behavior

### Scenario: A normal turn stays exactly as today

**Given** a turn whose boundary count is at or below the threshold (default 4), or `collapseIntensiveWork` is `false`
**When** the renderer flushes and finalizes
**Then** collapse is never active; the message is composed via the existing markdown path (`compose()` → `toTelegramEntities(display)`), every `_🔧 <summary>_` marker bakes inline with blank-line separation, and the streamed shape is indistinguishable from current behavior (no new artifacts, no layout change).
**Rationale** R8 — the feature must be a strict no-op below the threshold / when disabled.

### Scenario: The threshold is crossed mid-stream (retroactive fold)

**Given** a turn streaming text and tools alternately, with the boundary count about to exceed the threshold
**When** the crossing boundary forms (text resumes after the tool block that takes the count over the threshold)
**Then** the next flush rebuilds the live message from the buffer: every segment before the live tail folds into the collapsed `expandable_blockquote` block (including segments that had rendered inline), and only the current live tail stays expanded. As each subsequent boundary forms, the previous tail folds in and the new tail stays — the user watches intermediate work collapse in as the answer grows.
**Rationale** R2/R3 — collapse is positional and retroactive; the rebuild reuses the existing recompose-on-every-edit model.

### Scenario: An in-progress tool stays visible

**Given** collapse is active and a tool is currently running (its live `_🔧 <activity>_` line showing)
**When** the renderer flushes
**Then** the running tool remains expanded and visible — it is the live tail; only completed segments (those whose tools finished, at a boundary) are folded. The segment becomes foldable when text or another tool resumes after it.
**Rationale** R3 — never fold mid-execution; "boundary" means the tools completed.

### Scenario: An all-intensive turn (no final text)

**Given** an intensive turn that ends on a tool with no following text, or whose threshold is crossed on its final boundary
**When** `finalize()` runs
**Then** the entire message is the collapsed block carrying the per-segment `_🔧 <summary>_` markers — there is no expanded content outside it — so the block is non-empty and expandable to reveal the work, rather than an empty message.
**Rationale** R10 — the collapse is meaningful even with no final answer.

### Scenario: A long turn splits across messages (per-message reset)

**Given** a turn whose stream exceeds the 4096-char limit and splits into multiple messages at the overflow commit
**When** each message is committed/streamed
**Then** the boundary counter is evaluated independently per message (it resets at each split). A message already committed is never retroactively collapsed; a single committed chunk that itself exceeded the threshold carries its own collapsed block for its intermediate segments.
**Rationale** R9 — detection is per-message; committed messages are immutable.

### Scenario: Composition with the decision header

**Given** an exchange carrying a turn-scoped decision header (DES-009) that also qualifies as intensive work
**When** the renderer composes the message
**Then** the header is converted separately and prepended above the collapsed block (which sits above the final tail), recomposed on every edit and never overwritten by the collapsed content. If the composition exceeds the edit limit, the existing best-effort drop order applies (transient first, then the header) — the collapsed block is part of the body.
**Rationale** R11 / DES-009 — the header stays anchored; collapse is a body-level concern.

### Scenario: Completion push, errors, and status are unaffected

**Given** an intensive turn under `pushNotifications`, or one that receives a `status`/`error` event, or one that trips the broken-render fallback
**When** finalize / event handling runs
**Then** the completion-push copy-delete copies the finalized message (collapsed block included) as-is; `status` renders as the existing transient line below the streamed content; `error` renders as the existing `⚠️ Error:` notice; and if the renderer is broken, `finalizeBroken` sends the full text via `sendChunked` with **no entities and no collapse** (intermediate segments inline) — so a blockquote-entity failure can never lose or block delivery.
**Rationale** R11 — collapse composes with the rest of the rendering contract; delivery is never gated on the entity succeeding.
