# Design: DLT-117 - Attach specific skills to task definitions

**Delta Spec**: [../delta-specs/DLT-117.md](../delta-specs/DLT-117.md)
**Status**: Draft

## Purpose

This document explains the design rationale for this delta: the modeling choices, data flow, system behavior, and architectural approach.

After implementation, the "Detected Impacts" section will guide reconciliation into feature design docs.

## Problem Context

Task definitions rely on LLM-based skill classification at execution time to determine which skills are relevant. This is unreliable for tasks that always need specific domain knowledge — the classifier may not select the right skills for a terse task prompt or for task types where the skill connection is implicit. The system needs a way for task definitions to declare specific skills that are always loaded, ensuring the agent has guaranteed access to domain knowledge regardless of classification accuracy.

**Constraints:**
- Both background and session task execution paths need support
- Skills must be resolved with transitive dependencies (reusing the existing `resolve_chain()`)
- Invalid skill names should warn but not block creation or execution
- Pinned skills must appear in context before `SkillsContextProvider` classification runs
- The coordinator's message boundary currently accepts raw strings — extending it to carry metadata requires an envelope type
- Context entries with `skill_name` metadata (ADR-011) are the established pattern for skill tracking

**Interactions:**
- Task model (`task-management`): gains `skills` field
- MCP tools (`task-management`): `create_task` and `update_task` gain `skills` parameter; `get_task` and `list_tasks` display skills
- Skill registry (`agent/skills`): `resolve_chain()` reused for transitive resolution
- Context entries (ADR-011): pinned skills emit same-shape entries with `skill_name` metadata
- Coordinator boundary: `IncomingMessage` envelope replaces raw string
- SkillsContextProvider: resolves pinned skills (both paths) via `resolve_chain()` before classification
- Background task executor: passes `definition.skills` to pipeline as `pinned_skills`
- Session task scheduler → buffer → channel → coordinator: skill names threaded through delivery path

## Design Overview

Both execution paths route pinned skills through the same mechanism — the `SkillsContextProvider`:

1. **Background tasks**: The executor passes `definition.skills` as the `pinned_skills` parameter to `msg_pipeline.run()`. The pipeline's `SkillsContextProvider` resolves them via `resolve_chain()`, emits context entries, and skips those skills during classification.

2. **Session tasks**: Skill names are carried from the scheduler through the priority buffer to the channel via `BufferedItem.metadata`. The channel constructs an `IncomingMessage` envelope carrying the skill names. The coordinator passes `msg.pinned_skills` to `msg_pre_pipeline.run()`. The shared `SkillsContextProvider` resolves them identically to the background path.

Both paths produce `ContextResult` entries shape-identical to classification-loaded entries — `derive_agents_from_entries()` treats them uniformly.

A new `IncomingMessage` frozen dataclass replaces raw `str` at the `coordinator.enqueue()` boundary. All callers (REPL, Telegram, buffered delivery) construct the envelope. For regular user messages, `pinned_skills` is empty.

### Cross-Layer Contracts

**Pinned skill injection for background tasks:**

```
BackgroundTaskExecutor._run_preprocessing(instance, definition, registry)
    |
    +-- (existing) Run MessagePreProcessingPipeline.run(pinned_skills=definition.skills)
    |   |
    |   +-- SkillsContextProvider.provide(message, existing_entries=..., pinned_skills=definition.skills)
    |       |
    |       +-- If pinned_skills is non-empty:
    |       |   +-- registry.refresh() (dirty check)
    |       |   +-- For each skill name in pinned_skills:
    |       |   |   +-- try: resolved += registry.resolve_chain(name)
    |       |   |   +-- except (KeyError, Exception): log warning, skip
    |       |   +-- Dedup resolved skills across chains (first-seen wins)
    |       |   +-- For each unique skill:
    |       |   |   +-- Create ContextResult(tag="skills", content=XML, metadata={"skill_name": name})
    |       |   +-- Add pinned skill names to "already loaded" set
    |       +-- (existing) Run skill classification -> skips skills already in "already loaded" set
    |       +-- Return all entries (pinned first, then classified)
    +-- Return result
```

**Pinned skill injection for session tasks:**

```
Session task scheduler tick
    |
    +-- Query pending session instances
    +-- For each ready instance, load definition:
    |   +-- BufferedItem(prompt=..., metadata={"pinned_skills": list(definition.skills)})
    +-- buffer.enqueue(item)

Channel handles BufferedDelivery
    |
    +-- Collect pinned_skills from session_task items only
       (filter by item.kind == "session_task"; notifications contribute none)
    +-- coordinator.enqueue(IncomingMessage(text=event.prompt, pinned_skills=tuple(skills)))

Coordinator.send_message()
    |
    +-- Read IncomingMessage from buffer
    +-- Run per-message pre-processing pipeline via MessagePreProcessingPipeline.run(pinned_skills=msg.pinned_skills)
    |   |
    |   +-- SkillsContextProvider.provide(message, existing_entries=..., pinned_skills=msg.pinned_skills)
    |       |
    |       +-- (same resolution logic as background path — see above)
    |       +-- Return all entries (pinned first, then classified)
    +-- derive_agents_from_entries(all_entries, registry) -> includes pinned skill agents
    +-- Send to SDK with derived agents
```

**Integration Points:**
- `IncomingMessage` -> `coordinator.enqueue()`: new envelope boundary replaces raw string
- `BufferedItem.metadata["pinned_skills"]` -> channel -> `IncomingMessage.pinned_skills`: skill names flow through delivery
- `TaskDefinition.skills` -> executor -> `pipeline.run(pinned_skills=...)`: background task passes skills to pipeline
- `IncomingMessage.pinned_skills` -> coordinator -> `pipeline.run(pinned_skills=...)`: session task passes skills to pipeline
- `SkillsContextProvider.provide(pinned_skills=...)` -> `resolve_chain()`: unified resolution for both paths
- `TaskDefinition.skills` -> MCP tools -> validation: skill name validation at creation/update time
- `SYSTEM_PREAMBLE_TEMPLATE` -> agent awareness: `skills` parameter documented in task tool descriptions

**Error contract:**
- Unknown skill names in MCP tools: warnings in response text, definition still created/updated
- Unknown skills at execution time: warnings logged, execution proceeds with resolved skills
- No skills resolve: warning logged, execution proceeds with classification-only loading
- Registry errors during resolution: logged, task proceeds without pinned skills

## Data Flow

### Pinned skill creation

```
1. Agent calls create_task/update_task with skills parameter (JSON-encoded string)
2. Tool decodes JSON string -> list[str] via helper
3. Tool validates each name against registry (warn on unknown, still persist)
4. Tool persists skills as JSON array string in TaskDefinitionRecord.skills
5. TaskDefinition.to_domain() deserializes: json.loads(record.skills) -> tuple[str, ...]
```

### Background task execution with pinned skills

```
1. BackgroundTaskExecutor picks up instance, loads definition
2. In pre-processing:
   a. Run pipeline with pinned_skills=definition.skills
   b. SkillsContextProvider resolves pinned skills:
      - For each skill name: call registry.resolve_chain(name)
      - Flatten and dedup resolved skills across chains (first-seen wins)
      - Background tasks run in fresh context each execution — no pre-existing
        skill entries to skip. Dedup is only for overlapping transitive deps.
      - Create ContextResult entries, shape-identical to classification-loaded entries
      - Add pinned skill names to "already loaded" set
   c. SkillsContextProvider runs classification -> skips pinned skills
   d. Return result with pinned entries first
3. derive_agents_from_entries() picks up agents from pinned skills normally
```

### Session task delivery with pinned skills

```
1. Session task scheduler tick:
   a. Query pending session instances
   b. For each ready instance, load definition
   c. If definition.skills is non-empty:
      set metadata={"pinned_skills": list(definition.skills)} on BufferedItem
   d. buffer.enqueue(item)

2. Priority buffer delivers when idle:
   a. Dispatches BufferedDelivery(prompt, items)
   b. Channel handler receives event

3. Channel:
   a. Collect pinned_skills from session_task items only
      (filter by item.kind == "session_task"; notifications contribute none;
      shutdown digest merges skills from all session_task items)
   b. Construct IncomingMessage(text=event.prompt, pinned_skills=tuple(merged))
   c. coordinator.enqueue(msg)

4. Coordinator.send_message():
   a. Read IncomingMessage from buffer
   b. Run per-message pre-processing pipeline with pinned_skills=msg.pinned_skills
   c. SkillsContextProvider resolves pinned skills (same logic as background path)
   d. SkillsContextProvider runs classification -> skips pinned skills
   e. derive_agents_from_entries(all_entries, registry) -> includes pinned skill agents
   f. Assemble prompt with derived agents, send to SDK
```

## Key Decisions

### IncomingMessage envelope with no backward compatibility

**Choice**: Replace `coordinator.enqueue(text: str)` with `coordinator.enqueue(msg: IncomingMessage)` everywhere. All callers construct the envelope. No `str | IncomingMessage` union.

**Why**: Consistency — using the envelope in all cases avoids a split boundary where some paths pass strings and others pass envelopes. A clean break ensures no caller is accidentally still passing a raw string. The user explicitly requested this approach.

**DLT-125 relationship**: DLT-125 ("Message envelope for typed message routing") envisions a richer envelope carrying content types, media metadata, and modality-specific data. `IncomingMessage` is intentionally a thin transport envelope — it carries only the text and pinned skill names needed for this delta's scope. When DLT-125 is implemented, `IncomingMessage` should be subsumed by that richer type (or evolve into it). The fields on `IncomingMessage` (`text`, `pinned_skills`) are a subset of what DLT-125 would carry, making migration straightforward. If DLT-125 lands first, this delta's changes adapt to the richer envelope; if this delta lands first, `IncomingMessage` serves as the interim boundary type.

**Alternatives Considered**:
- Backward-compatible `str | IncomingMessage`: User explicitly rejected for consistency
- Subclassing `str`: Fragile, hides the envelope in a surprising way
- Dict/kwargs: No type safety, easy to miss fields
- Wait for DLT-125: Would block this delta indefinitely on a Medium-priority backlog item; the interim envelope is trivial and migration path is clear

**Consequences**:
- Pro: Single consistent boundary type
- Pro: Any future metadata (DLT-125) extends `IncomingMessage` naturally
- Pro: Clear migration path to DLT-125's richer envelope
- Con: All enqueue callers must be updated (REPL, Telegram, buffered delivery, tests)
- Con: Temporary type that will be replaced when DLT-125 lands (acceptable — the replacement is a rename/extend, not a rewrite)

### Resolution at consumption time for session tasks

**Choice**: Carry skill names through the delivery path and resolve them in the coordinator when the message is consumed, rather than resolving at scheduler enqueue time.

**Why**: The registry may change between enqueue and delivery (skill files modified, registry refreshed). Resolving at the last possible moment ensures the agent gets the latest skill definitions. The staleness window for session tasks is typically seconds to minutes, but the cost of late resolution is negligible (dict lookups, no I/O).

**Alternatives Considered**:
- Resolve at enqueue time: Simpler, but content could go stale if skills are modified between enqueue and delivery
- Resolve at enqueue time with TTL: Adds complexity for negligible benefit

**Consequences**:
- Pro: Always uses current skill definitions
- Pro: Registry mutations during queue wait are naturally handled
- Con: Slightly more work at delivery time (resolve + entry creation)
- Con: Skill names must be threaded through the delivery path (via `BufferedItem.metadata` and `IncomingMessage`)

### JSON-encoded string for MCP tool skills parameter

**Choice**: Declare the `skills` parameter as `str | None` in Pydantic args, requiring the agent to pass a JSON-encoded array string (e.g., `'["skill-a", "skill-b"]'`). Parse and validate in the tool handler.

**Why**: The SDK's MCP transport rejects array-typed arguments at its client-side JSON Schema validator (documented in DES-006 "Array-Typed Args" section). This is the established project pattern for array-typed MCP tool arguments. A module-level `_decode_skills(raw: str) -> list[str]` helper follows the same shape as `_decode_paths` from DES-006, providing parse-and-validate logic with clear error messages.

**Alternatives Considered**:
- Array-typed parameter: Rejected by SDK transport validator
- Comma-separated string: Ambiguous (what if a skill name contains a comma?), no standard parser

**Consequences**:
- Pro: Follows established DES-006 pattern
- Pro: Unambiguous parsing via `json.loads()`
- Con: Agent must format as JSON string (mitigated by clear tool description with example)

### Shape-identical context entries for pinned skills

**Choice**: Pinned skills emit `ContextResult` entries identical in shape to classification-loaded entries: same `tag="skills"`, same XML content format, same `metadata={"skill_name": name}`.

**Why**: Downstream consumers (`SkillsContextProvider.extract_skill_names()`, `derive_agents_from_entries()`, system prompt assembly) treat all skill entries uniformly. If pinned entries had a different shape, every consumer would need special-case handling.

**Alternatives Considered**:
- Different tag or metadata for pinned entries: Would require changes to `extract_skill_names()`, `derive_agents_from_entries()`, and the `SkillsContextProvider` filtering logic

**Consequences**:
- Pro: Zero changes to existing skill entry consumers
- Pro: `SkillsContextProvider` naturally skips pinned skills via existing metadata dedup
- Pro: `derive_agents_from_entries()` picks up pinned skill agents automatically
- Con: Cannot distinguish pinned vs classified entries in context (acceptable — the distinction is execution-order, not behavior)

### Unified resolution in SkillsContextProvider

**Choice**: SkillsContextProvider handles pinned skill resolution for both background and session task paths. The executor and coordinator are pass-throughs — they pass `pinned_skills` to the pipeline, and the provider does the resolution.

**Why**: SkillsContextProvider already owns skill classification, `resolve_chain()` expansion, dedup, and `ContextResult` emission for both paths. Adding pinned skill resolution there keeps all skill-loading logic in one place. Both background and session tasks already use SkillsContextProvider via the pre-processing pipeline, so no new coupling is introduced.

**Alternatives Considered**:
- Separate resolution in executor and coordinator: Would duplicate `resolve_chain()` + dedup + entry creation logic in two places
- Shared helper function outside the provider: Possible, but the provider already has registry access and the classification skip logic — a helper would still need to coordinate with the provider

**Consequences**:
- Pro: Single location for all skill resolution logic
- Pro: Pinned skills naturally feed into the existing classification-skip mechanism
- Pro: Both paths use identical resolution (no subtle divergence risk)
- Con: `MessageContextProvider.provide()` and `MessagePreProcessingPipeline.run()` gain a `pinned_skills` parameter (minimal interface change)

### Reuse of existing resolve_chain() for pinned skill resolution

**Choice**: Use `registry.resolve_chain()` to expand each pinned skill name into its transitive dependency chain, then dedup across all chains.

**Why**: `resolve_chain()` already handles transitive deps, cycles, diamonds, unknown-dep skipping, and memoization. Reusing it means pinned skills get the same dependency resolution as classification-detected skills with zero new resolution logic.

**Consequences**:
- Pro: Dependency resolution is consistent across all skill injection paths
- Pro: Unknown deps in pinned skill chains are silently skipped (matching existing behavior)
- Con: If a pinned skill's dependency is unknown, the user won't know at task creation time (they see a warning only if they call `resolve_chain` manually)

### Warn-only validation for unknown skill names

**Choice**: When `create_task` or `update_task` receives skill names not in the current registry, the tool warns in the response text but still persists the definition. At execution time, unknown names are logged as warnings and skipped.

**Why**: Skills may not be registered yet at task creation time (e.g., the skill is being authored in a separate session). Blocking creation would force ordering constraints. The registry may also change between creation and execution (skills added/removed).

**Alternatives Considered**:
- Reject unknown skills: Forces creation-order dependency; skill may not exist yet
- Silent acceptance (no warning): User/agent doesn't know they made a typo

**Consequences**:
- Pro: Flexible — task creation is independent of skill availability
- Pro: Warnings surface likely typos at creation time
- Pro: Execution-time handling matches existing unknown-dep tolerance in `resolve_chain()`
- Con: A task with all-unknown skills silently degrades to classification-only (mitigated by warning log)

## System Behavior

### Scenario: Creating a task with pinned skills

**Given**: The agent calls `create_task` with `skills='["research", "planning"]'`
**When**: The tool processes the request
**Then**: The tool decodes the JSON string, checks each name against the registry (warning about any unknown names in the response text), and persists the definition with `skills=("research", "planning")`.

### Scenario: Background task with pinned skills

**Given**: A background task definition with `skills=("research", "planning")`
**When**: The executor runs pre-processing
**Then**: The executor passes `pinned_skills=("research", "planning")` to `pipeline.run()`. The `SkillsContextProvider` resolves each skill via `resolve_chain()`, dedupes, emits `ContextResult` entries, adds them to the "already loaded" set, then runs classification (skipping pinned skills).

### Scenario: Background task with pinned skill that has dependencies

**Given**: A background task with `skills=("workflow-runner",)` and workflow-runner depends on `workflow-authoring-guide`
**When**: The SkillsContextProvider resolves the pinned skills
**Then**: `resolve_chain("workflow-runner")` returns `[workflow-authoring-guide, workflow-runner]`. Both are emitted as context entries in deps-first order.

### Scenario: Session task with pinned skills

**Given**: A session task definition with `skills=("research",)`
**When**: The scheduler enqueues the task, the buffer delivers it, and the channel processes the delivery
**Then**: The scheduler sets `metadata={"pinned_skills": ["research"]}` on the `BufferedItem`. The channel constructs `IncomingMessage(text=prompt, pinned_skills=("research",))`. The coordinator passes `pinned_skills=("research",)` to `pipeline.run()`. The `SkillsContextProvider` resolves "research" via the registry, emits a context entry, and skips it during classification.

### Scenario: Unknown skill at creation time

**Given**: The agent calls `create_task` with `skills='["real-skill", "typo-name"]'`
**When**: The tool validates against the registry
**Then**: The tool warns about "typo-name" in the response text but creates the definition with `skills=("real-skill", "typo-name")`. At execution time, "typo-name" is skipped (logged as warning), "real-skill" loads normally.

### Scenario: All pinned skills unknown at execution time

**Given**: A task definition with `skills=("removed-skill",)` where the skill was deleted
**When**: The task executes
**Then**: A warning is logged. Execution proceeds with classification-only skill loading (same as if no skills were pinned).

### Scenario: Overlapping pinned skills with classified skills

**Given**: A task with `skills=("research",)` and the classifier also detects "research"
**When**: The per-message pipeline runs
**Then**: The `SkillsContextProvider` sees "research" already in context entries (via `extract_skill_names()` metadata match) and skips it. No duplicate entry.

### Scenario: Ad-hoc background task (no definition)

**Given**: An ad-hoc `run_task_now` with just a `prompt`
**When**: The executor runs
**Then**: No definition exists to read skills from. Execution proceeds with classification-only skill loading. No special handling needed.

### Scenario: Regular user message (no pinned skills)

**Given**: A user sends a message through Telegram or REPL
**When**: The channel calls `coordinator.enqueue(IncomingMessage(text=user_input))`
**Then**: `pinned_skills` is empty (default). No pinned skill resolution occurs. Pre-processing runs normally.

### Scenario: By-reference background task with pinned skills

**Given**: An agent calls `run_task_now` with `task_id` referencing a definition with `skills=("analysis",)`
**When**: The executor picks up the instance
**Then**: The definition's prompt is snapshotted onto the instance (existing behavior), and the executor passes `definition.skills` as `pinned_skills` to the pipeline. The `SkillsContextProvider` resolves the skills during pre-processing. The pinned skills load for this execution even though the instance itself doesn't carry a skills field.
