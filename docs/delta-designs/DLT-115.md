### Flagged Unknowns

#### P2 — Detachment mechanics across platforms
The user-facing requirement (R1) is that a spawned process survives Tachikoma's own exit, restart, or crash. `subprocess.Popen(start_new_session=True)` sets up a new session via `setsid` on POSIX, which should cause the process to be reparented to init when Tachikoma exits. What needs investigation:
- Confirm that this holds on both Linux and macOS in practice (no residual SIGHUP delivery, no inherited controlling terminal, no file-descriptor sharing that would block Tachikoma's shutdown).
- Decide whether a `preexec_fn=os.setsid` fallback or an explicit double-fork is warranted, or whether `start_new_session=True` is sufficient on its own.
- Decide the source of the OS-reported process start time used for the identity tuple — `psutil.Process(pid).create_time()` (cross-platform, adds a dependency) vs. parsing `/proc/{pid}/stat` directly (Linux-only, no dependency). This interacts with P3.

#### P3 — PID-reuse check portability
The liveness check needs to (a) ask the OS "is there a process at this PID?" and (b) read that process's start time to detect PID reuse. Same dependency question as P2 applies (`psutil` vs. `/proc` vs. `os` primitives). Also to settle:
- Race window between the liveness check and any subsequent signal in P5 (the PID may have been recycled between the check and the `kill`).
- Handling of zombie processes (`Z` state) — whether they count as "still alive" for our purposes.

#### P10 — Exit-code capture mechanism
Simplest mechanism is `sh -c 'USER_COMMAND; echo $? > /path/to/{id}.exit'`. Consequences to weigh:
- This changes the command string observed by the OS from the user's raw input, which could confuse users reading `ps` output.
- Signal propagation: when the agent stops the wrapper via SIGTERM, the inner command may or may not receive the signal depending on shell behavior — needs validation.
- The wrapper process itself is the one whose PID we record, not the real child — which is fine as long as killing the wrapper kills the child group (which `start_new_session=True` + process-group signalling should achieve), but needs confirmation.
- Alternative: skip the wrapper entirely and leave R13 formally Nice-to-have but unimplemented in v1. The ACs allow an always-null exit code.

#### P11 — Exit watcher cadence, failure-isolation, registration
The watcher is straightforward in principle but has several design choices:
- **Cadence**: must be short enough that the worst-case gap between exit and detection does not defeat the Urgent-priority 30s idle window. A fixed short period (e.g. ~5s) is the obvious default; consider whether the period should be config-driven and whether it should adapt (longer when zero records are `running`, shorter when some are).
- **Wake-up model**: purely periodic polling vs. event-aware (wake on `start_process` to shorten first-detection latency when transitioning from zero to one running record).
- **Failure isolation**: per-record error handling — a liveness check or dispatch that throws for one record must not kill the loop. Strategy should mirror the priority-buffer loop's "log and continue" posture.
- **Registration surface**: whether the watcher is owned by a new field in `bootstrap.extras` and started explicitly in `__main__.py` (like `background_task_runner`), or whether it slots into an existing scheduler module. The former is simpler and more explicit.
- **Coordination with `stop_process`**: the spec's AC that "the watcher only considers records currently marked `running`" pins the mechanism; the design still needs to decide whether that filter happens in the SQL query or in Python after the fetch, and whether there's any in-memory dedup needed against a watcher cycle that overlaps a `stop_process` call.
