# Design: DLT-088 - Scheduled Memory Store Maintenance

**Delta Spec**: [../delta-specs/DLT-088.md](../delta-specs/DLT-088.md)
**Status**: Draft

## Purpose

This document explains the design rationale for this delta: the modeling choices, data flow, system behavior, and architectural approach.

After implementation, the "Detected Impacts" section will guide reconciliation into feature design docs.

## Problem Context

The memory store accumulates files over time with no automated cleanup. Episodic entries pile up as daily files with no consolidation. Facts become stale as projects complete and circumstances change. Preferences drift into overlapping files as related topics get split across separate entries. Without maintenance, the memory store degrades — more files to search, more stale content to mislead the agent, more redundancy wasting context budget.

Constraints:
- Maintenance must be agent-driven (agents read and edit files, no code-level file manipulation) per the project's established pattern
- Must not interfere with user conversations (runs on a schedule, not triggered by messages)
- Must be idempotent and safe — running twice produces the same result, and git provides rollback for mistakes
- Must not leak system internals into the user-facing task management system

## Design Overview

Three `CronTrigger` scheduler jobs — one per memory type — each running an agent through the existing `query_and_consume` helper with scoped writer permissions (DES-004). This follows the same pattern as the update checker, plugin check, and one-shot cleanup: plain Python tick functions wired to the central scheduler, with no database records or user-visible task definitions.

The key reuse is `query_and_consume`, currently in `git/processor.py`, which creates fresh SDK sessions with `dontAsk` permissions and tool scoping. Promoting it to a shared location establishes a general extension point for any future scheduled agent work.

## Components

### Implementation Structure

| Layer/Component | Responsibility | Key Decisions |
|-----------------|----------------|---------------|
| `query_and_consume` (promoted to `post_processing.py`) | Shared helper for fresh SDK sessions with DES-004 tool scoping | Moved from `git/processor.py`; existing git callers import from new location |
| `memory/maintenance.py` (new) | Tick functions for episodic, facts, and preferences maintenance; `git_commit_memory_changes()` helper for post-agent commits | Each tick builds a prompt, calls `query_and_consume`, then commits via the helper |
| `MemorySettings` / `MaintenanceSettings` (on `config.py`) | Configuration model for maintenance thresholds and schedule | Single shared `schedule` cron expression applies to all three jobs; nested under `memory.maintenance` in TOML; new top-level `memory` field on `Settings` |
| `MAINTENANCE_BASH_HOOK` (in `post_processing.py`) | Bash gate extending utility prefixes with `rm` | Reuses `make_bash_gate_hook` from DES-004 infrastructure |
| `__main__.py` (scheduler wiring) | Registers three maintenance scheduler jobs | `CronTrigger` from config; conditional on `enabled` flag |

### Cross-Layer Contracts

**Tick function signature** (follows DES-010 pattern):
```python
async def episodic_maintenance_tick(
    agent_defaults: AgentDefaults,
    maintenance_settings: MaintenanceSettings,
) -> None:
    """One pass. No loop, no sleep."""
```

**Integration Points**:
- Tick functions call `query_and_consume` (shared agent execution)
- Tick functions call git commit helper (shared git infrastructure)
- Scheduler drives tick functions on cron schedule (DES-010)
- Config provides thresholds and schedule (standard config pattern)

### Shared Logic

- **`query_and_consume`**: Already used by `GitProcessor` and `ProjectsProcessor`. Promoting to `post_processing.py` makes it available to maintenance ticks and any future scheduled agent work without cross-module imports.
- **`abs_rule`, `build_permissions_settings`, `make_bash_gate_hook`**: Existing DES-004 infrastructure reused for maintenance agent scoping.
- **`UTILITY_BASH_PREFIXES`**: Extended with `rm` to create `MAINTENANCE_BASH_PREFIXES` — shared across all maintenance tick functions.

## Modeling

No new database entities. The domain model is configuration-driven:

```
Settings
└── memory: MemorySettings
    └── maintenance: MaintenanceSettings
        ├── enabled: bool (default: true)
        ├── schedule: str (cron expression, default: "0 3 * * *", shared across all three jobs)
        ├── recent_days: int (default: 15)
        ├── weekly_threshold_months: int
        └── monthly_threshold_months: int
```

Each maintenance tick maps to a scheduler job. All three share a single cron schedule from `memory.maintenance.schedule` — they're all nightly maintenance and there's no reason to stagger them. If per-type scheduling is needed in the future, the config can be extended with individual fields.

The prompt acts as the "strategy" — the agent decides what to do based on the content it reads and the instructions in the prompt.

Existing users get the new config section seamlessly — Pydantic's `ConfigDict(frozen=True, extra="ignore")` on all settings models means the TOML file is not required to have a `[memory]` section. Defaults apply automatically.

## Data Flow

```
Scheduler (CronTrigger fires)
  → maintenance_tick(agent_defaults, settings)
    → Build prompt from settings thresholds + $WORKSPACE paths
    → query_and_consume(prompt, agent_defaults,
        tools=[Read, Glob, Grep, Bash, Edit, Write],
        allow=[scoped Read/Edit/Write + unrestricted Glob/Grep/Bash],
        hooks=[MAINTENANCE_BASH_HOOK],
        model=processor_model)
      → Agent reads memory directory
      → Agent edits, merges, creates, or deletes files
      → Agent completes (response fully consumed, per DES-005)
    → git_commit_memory_changes(agent_defaults, memory_type)
      → query_and_consume(git_add_commit_prompt, ...,
          tools=[Read, Glob, Grep, Bash, Edit, Write],
          allow=[GIT_ALLOW rules],
          hooks=[GIT_BASH_HOOK])
      → Agent runs: git add memories/<type>/ && git commit -m "memory maintenance: <type>"
  → Tick returns (scheduler error containment wraps the whole thing)
```

## Key Decisions

### Scheduler jobs instead of task definitions

**Choice**: Wire maintenance as scheduler jobs (like update checker, one-shot cleanup) rather than task definitions in the database.
**Why**: Mixing system-owned behavior into the user-facing task subsystem creates confusing patterns — users would see system tasks they didn't create, and the task tools (create, update, delete) would need special-casing for system ownership. The scheduler tick pattern already exists for system-level work and is the right abstraction level.
**Alternatives Considered**:
- System-owned task definitions: Would provide execution history and failure notifications for free, but at the cost of mixing two ownership models in one subsystem and adding complexity to every task tool's authorization logic.
- Plain Python functions with no agent: Would be simpler but can't do the nuanced judgment that maintenance requires (evaluating staleness, deciding what counts as "overlap," exercising editorial discretion on consolidation).

**Consequences**:
- Pro: Clean separation — system work stays in the scheduler, user work stays in the task subsystem. No user-visible artifacts.
- Con: No execution history in the database (only logs). No built-in failure notifications (though the scheduler logs errors).

### Fresh SDK sessions via query_and_consume

**Choice**: Reuse `query_and_consume` (currently in `git/processor.py`) for maintenance agent execution. Promote it to `post_processing.py` as a shared utility.
**Why**: It already creates fresh SDK sessions with DES-004 tool scoping (`dontAsk` mode, allow rules, hooks). It's a battle-tested path used by `GitProcessor` and `ProjectsProcessor`. Promoting it makes it available as the standard path for any scheduled agent work, establishing a reusable extension point.
**Alternatives Considered**:
- New `run_agent_tick` helper: Would be a near-copy of `query_and_consume` with a different name. Better to promote the existing function.
- Using the background task executor: Would pull in the evaluator loop, notification system, and database tracking — all unnecessary for scheduled maintenance and mixing system/user patterns.

**Consequences**:
- Pro: Single shared function for all non-session agent work. Existing callers (`GitProcessor`, `ProjectsProcessor`) import from the canonical location.
- Con: Minor refactor to move the function and update import sites. git/processor.py becomes thinner (it keeps the git-specific prompt and processor class).

### Bash gate with rm for file deletion

**Choice**: Extend `UTILITY_BASH_PREFIXES` with `rm` to create `MAINTENANCE_BASH_PREFIXES`, used by a maintenance-specific `MAINTENANCE_BASH_HOOK`.
**Why**: Maintenance agents need to delete files (removing obsolete facts, deleting old episodic entries after consolidation). The existing `UTILITY_BASH_HOOK` only allows read-only inspection commands. Adding `rm` to the prefix list lets agents delete within their already-path-scoped directory. The agent's prompt restricts deletion to the target directory, and git provides rollback for mistakes (per spec AC).
**Alternatives Considered**:
- Agent writes empty files + Python cleanup step: Adds indirection and an extra processing step. The agent is already trusted with Edit/Write in the scoped directory — `rm` is a natural extension.
- Dedicated "delete file" MCP tool: Over-engineered for this use case. The bash gate pattern already exists and is simpler.

**Consequences**:
- Pro: Simple, leverages existing infrastructure. Agents can directly delete files.
- Con: `rm` is not path-scoped by the bash gate (it only checks command prefixes, not arguments). Mitigated by prompt restrictions, path-scoped Edit/Write as the primary tool, and git rollback.

### Post-maintenance git commit

**Choice**: Each tick function runs a lightweight git add/commit after the agent completes, using `query_and_consume` with a scoped git prompt.
**Why**: Maintenance changes (consolidated summaries, removed files, merged entries) should be committed promptly so git history reflects what happened. Without this, changes sit uncommitted until the next session close's git processor picks them up — which could be hours away, and the uncommitted state would be misleading.
**Alternatives Considered**:
- No commit (let next session close handle it): Simpler, but leaves uncommitted maintenance changes in the working directory for potentially hours. Breaks the expectation that git history reflects actual changes.
- Subprocess `git add && git commit`: No agent involvement. Simpler but doesn't handle generating meaningful commit messages from the actual changes.

**Consequences**:
- Pro: Changes are committed immediately with descriptive messages. Git history is a clear audit trail of maintenance activity.
- Con: Three extra agent calls per night (one commit per maintenance type). Minimal cost since the commit agent is lightweight (processor model, tiny diff).

### Configuration in [memory.maintenance]

**Choice**: New `[memory]` section in config.toml with a `[memory.maintenance]` subsection containing `enabled`, `schedule`, `recent_days`, `weekly_threshold_months`, and `monthly_threshold_months`.
**Why**: Follows the existing nested config pattern (`[tasks]`, `[buffer.urgent]`, etc.). A new top-level `memory` section leaves room for future memory configuration (e.g., context retrieval settings) without crowding the existing sections. The `maintenance` subsection groups related settings together.
**Alternatives Considered**:
- Add thresholds to `[tasks]`: Would mix memory-specific configuration into the generic task settings. Semantically wrong — these are memory parameters, not task scheduling parameters.
- Hardcode defaults with no configuration: Simpler but the spec explicitly calls for configurability (R6).

**Consequences**:
- Pro: Clean config organization. Memory settings are self-contained and discoverable.
- Con: One new Pydantic model and field on `Settings`. Minor boilerplate.

## System Behavior

### Scenario: Normal episodic maintenance run

**Given**: The episodic directory has daily files spanning 4 months, including some already-consolidated weekly summaries from a previous run.
**When**: The episodic maintenance tick fires on its cron schedule.
**Then**: The agent reads all files, categorizes by age, cleans verbosity from recent files (last 15 days), consolidates the 15-day-to-3-month range into weekly summaries (merging into existing ones where present), leaves the 3-month-to-1-year range untouched if already consolidated, and deletes nothing older than 1 year (there are none). Changes are committed.
**Rationale**: Idempotent — a second run produces no changes because the recent files are already clean and the weekly summaries already exist.

### Scenario: Empty memory store

**Given**: The memory directory for a type exists but is empty (no files).
**When**: The maintenance tick fires.
**Then**: The agent reads the directory, finds nothing to process, and exits with no changes. No git commit is attempted (no changes to commit).
**Rationale**: No-op is the correct behavior — nothing to maintain.

### Scenario: Malformed or empty files

**Given**: A memory file is empty (0 bytes) or contains only garbage characters.
**When**: The maintenance agent encounters it.
**Then**: The agent skips the file and continues processing others. For episodic, empty files may be deleted as part of cleanup. For facts/preferences, the agent uses judgment — if the file has a meaningful name but empty content, it may delete it; if it has partial content, it may attempt to preserve what's useful.
**Rationale**: Agent judgment handles edge cases that deterministic code can't anticipate. The prompt instructs the agent to skip malformed files rather than crash.

### Scenario: Concurrent access during maintenance

**Given**: A user is actively chatting while the maintenance tick fires.
**When**: The maintenance agent reads and edits files that the post-processing pipeline might also be writing to.
**Then**: The agent's view reflects whatever state it read. If a file is modified during processing, the worst case is that the file is processed in its next-run state on the following night. No locking is needed.
**Rationale**: Spec AC explicitly states no locking is required. Nightly runs mean low collision probability, and git rollback covers any mistakes.

### Scenario: Maintenance agent fails mid-run

**Given**: The maintenance agent encounters an SDK error or produces invalid output partway through processing.
**When**: The error propagates out of `query_and_consume`.
**Then**: The scheduler's error containment catches it, logs the error, and continues with other jobs. The other two maintenance ticks are unaffected. Partial changes from the failed agent are in the working directory but uncommitted — they'll either be committed by the next successful run or can be manually reverted via git.
**Rationale**: Scheduler error isolation means one failure doesn't block the others. Git provides implicit rollback for partial changes.

### Scenario: Idempotent re-run

**Given**: The episodic maintenance tick ran successfully last night, producing clean daily files and weekly summaries.
**When**: The tick fires again tonight with no new conversations having occurred.
**Then**: The agent reads the files, finds the recent daily files already clean, the weekly summaries already consolidated, and no new files to process. It exits with no changes. No git commit.
**Rationale**: Prompt design ensures the agent checks for work that needs doing rather than re-processing everything unconditionally. The "already clean" and "already consolidated" states are the natural result of the agent's judgment.

### Scenario: Configuration changes mid-stream

**Given**: The user changes `recent_days` from 15 to 30 in config.toml.
**When**: The maintenance tick fires.
**Then**: The tick function reads the current config value at call time (passed through from the settings object). The agent uses the new threshold (30 days) for its consolidation decisions.
**Rationale**: Config is read at tick execution time, not cached. Changes take effect on the next tick without restart.
