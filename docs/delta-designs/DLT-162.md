# Design: DLT-162 - Telegram Message Pinning

**Delta Spec**: [../delta-specs/DLT-162.md](../delta-specs/DLT-162.md)
**Status**: Draft

## Purpose

This document explains the design rationale for adding message pinning tools to the Telegram channel: how the agent discovers which message to pin, how the MCP tool server is structured, and how errors are surfaced.

## Problem Context

The agent sometimes produces responses worth keeping visible — summaries, decisions, reference material. Currently there is no way for the agent to pin these messages in the Telegram chat. The Telegram Bot API provides `pinChatMessage` and `unpinChatMessage` endpoints that are idempotent and support silent pinning (no notification). The existing `create_send_file_server()` factory in `tools.py` establishes the pattern for adding MCP tools to the Telegram channel.

**Constraints:**
- Must follow DES-006 (SDK MCP Tool Server Factory) — same structure as `send_file`
- The renderer tracks `_current_message_id` but does not expose it publicly; needs a getter
- Private chats need no special permissions; groups need `can_pin_messages`; channels need `can_edit_messages`
- The pin/unpin operations must be idempotent per Telegram Bot API guarantees

**Interactions:**
- ResponseRenderer (`__init__.py`): provides the message ID via a new getter
- `get_mcp_servers()` (`__init__.py`): registers the pinning server alongside `send-file`
- DES-006 pattern (`tools.py`): factory shape, Pydantic args, extracted handler

## Design Overview

Add two MCP tools (`pin_message`, `unpin_message`) via a new factory function `create_pinning_server()` in a new `pinning.py` module. Expose the renderer's current message ID through a public getter. Register the server in `get_mcp_servers()`.

```
┌─────────────────────────────────────────────────────────────┐
│                    Existing                                  │
│  ┌────────────────────────────────────────────────────────┐  │
│  │  ResponseRenderer                                      │  │
│  │  _current_message_id: int | None                      │  │
│  │  + get_last_message_id() -> int | None   ← NEW        │  │
│  └──────────────────────────┬─────────────────────────────┘  │
│                             │ getter captured by factory      │
│  ┌──────────────────────────▼─────────────────────────────┐  │
│  │  pinning.py (NEW)                                      │  │
│  │  ┌──────────────────────────────────────────────────┐  │  │
│  │  │  PinMessageArgs(BaseModel)                       │  │  │
│  │  │  UnpinMessageArgs(BaseModel)                     │  │  │
│  │  │  handle_pin_message(...)  → dict                 │  │  │
│  │  │  handle_unpin_message(...) → dict                │  │  │
│  │  │  create_pinning_server(bot, chat_id, getter)     │  │  │
│  │  └──────────────────────────────────────────────────┘  │  │
│  └────────────────────────────────────────────────────────┘  │
│                                                              │
│  get_mcp_servers() returns:                                  │
│    {"send-file": ..., "telegram-pinning": ...}               │
└─────────────────────────────────────────────────────────────┘
```

## Shape

| Part | Mechanism | Flag |
|------|-----------|:----:|
| **S1** | Message ID getter on ResponseRenderer: `get_last_message_id() -> int \| None` returning `_current_message_id` | |
| **S2** | `pin_message` tool: calls the renderer getter, pins via `bot.pin_chat_message()` with `disable_notification=True`, returns success with the ID; returns error if no message ID or API failure | |
| **S3** | `unpin_message` tool: accepts `message_id: int` (Pydantic-validated), calls `bot.unpin_chat_message()`, returns success; returns error on API failure | |
| **S4** | MCP server factory: `create_pinning_server()` in `pinning.py` — captures `bot`, `chat_id`, and message ID getter via closures; defines both tools inside factory body | |
| **S5** | Integration: add `"telegram-pinning"` entry in `get_mcp_servers()` alongside `"send-file"`, passing `bot`, `chat_id`, and `renderer.get_last_message_id` | |

## Components

### Implementation Structure

| Layer/Component | Responsibility | Key Decisions |
|-----------------|----------------|---------------|
| `pinning.py` (new) | Pin/unpin tool handlers + factory | Follows DES-006 exactly; extracted handlers for testability |
| `ResponseRenderer` (modify) | Expose current message ID | Minimal getter — no behavioral change |
| `get_mcp_servers()` (modify) | Register pinning server | Captures renderer getter at factory call time |

### Cross-Layer Contracts

**MCP Tool Response Format** (consistent with `send_file`):
```
Success: {"content": [{"type": "text", "text": "Message pinned (ID: <id>)"}]}
Error:   {"is_error": true, "content": [{"type": "text", "text": "<error message>"}]}
```

**Integration Points**:
- Factory captures `Callable[[], int | None]` — a zero-arg getter, not the renderer itself. This keeps the pinning module decoupled from the renderer class.
- Error handling uses `TelegramAPIError` catch, same pattern as `handle_send_file()`.

## Tool Descriptions

The `@tool()` decorator descriptions are the primary way the agent discovers and understands these tools. No separate system prompt instructions are needed — following the same approach as `send_file`.

### pin_message

```
Pin a message in the active Telegram chat.

Parameters: none

Pins the most recent response message silently (no notification).
Returns the pinned message's Telegram ID on success.
Returns an error if no response has been sent yet or if pinning fails
(e.g., insufficient permissions in groups/channels).

Idempotent: pinning an already-pinned message succeeds.
```

### unpin_message

```
Unpin a previously pinned message in the active Telegram chat.

Parameters:
- message_id (int, required): The Telegram message ID to unpin

Returns success on unpin. Returns an error if the message ID doesn't
exist or unpinning fails.

Idempotent: unpinning a non-pinned message succeeds.
```

## Key Decisions

### Getter vs Direct Attribute Access

**Choice**: Public getter method `get_last_message_id()` on ResponseRenderer
**Why**: Encapsulates access to private state. The factory captures a `Callable[[], int | None]` (the bound method), keeping `pinning.py` free of any import or knowledge of the `ResponseRenderer` class.
**Alternatives Considered**:
- Expose `_current_message_id` as a public attribute: breaks encapsulation, allows external mutation
- Pass the renderer instance to the factory: couples `pinning.py` to the renderer class

**Consequences**:
- Pro: Clean separation — `pinning.py` only depends on `Bot`, `int`, and a callable
- Pro: Getter can evolve (e.g., return last non-split message) without changing the factory
- Con: One trivial method on the renderer — but it follows the existing `has_sent_content()` precedent

### Separate Module vs Extending tools.py

**Choice**: New `pinning.py` module alongside existing `tools.py`
**Why**: `tools.py` is dedicated to the `send_file` tool with its file validation logic. Pinning is an unrelated concern with no shared code. Separate modules keep each focused.
**Alternatives Considered**:
- Add pinning tools to `tools.py`: would mix unrelated concerns (file I/O vs message pinning), no shared logic to justify co-location

**Consequences**:
- Pro: Each module has a single responsibility
- Pro: Tests are isolated per module
- Con: One more file in the package — minimal cost

### UnpinMessageArgs Has Required message_id

**Choice**: `message_id: int` is required on `UnpinMessageArgs`
**Why**: The Telegram Bot API allows omitting `message_id` on unpin (defaults to most recent pinned), but that "unpin latest" behavior is implicit and fragile. Requiring an explicit ID gives the agent clear control.
**Alternatives Considered**:
- Make `message_id` optional, defaulting to unpin-all or unpin-latest: ambiguous semantics, agent should be explicit about which message to unpin

**Consequences**:
- Pro: Agent always specifies exactly what to unpin — no surprises
- Pro: Simpler tool description for the agent to understand
- Con: Agent must track pinned message IDs — but it receives them from `pin_message` responses

## Data Flow

### Pin Message

```
Agent calls pin_message tool
  → Pydantic validates args (no parameters needed)
  → Factory-captured getter() called → returns int | None
  → If None: return error "No message available to pin"
  → If int: bot.pin_chat_message(chat_id, message_id, disable_notification=True)
    → Success: return {"content": [{"type": "text", "text": "Message pinned (ID: <id>)"}]}
    → TelegramAPIError: return {"is_error": true, "content": [{"type": "text", "text": "Failed to pin message: <error>"}]}
```

### Unpin Message

```
Agent calls unpin_message tool with message_id
  → Pydantic validates args (message_id: int, required)
  → bot.unpin_chat_message(chat_id, message_id)
    → Success: return {"content": [{"type": "text", "text": "Message unpinned (ID: <id>)"}]}
    → TelegramAPIError: return {"is_error": true, "content": [{"type": "text", "text": "Failed to unpin message: <error>"}]}
```

## System Behavior

### Scenario: Pin after response

**Given**: The agent has completed a response, `ResponseRenderer._current_message_id` holds the final message ID
**When**: The agent calls `pin_message`
**Then**: The message is pinned silently and the tool returns the message ID
**Rationale**: The most common flow — agent decides a response is important and pins it

### Scenario: Pin with no active response

**Given**: The renderer has been reset or no response has been sent yet
**When**: The agent calls `pin_message`
**Then**: Returns `{"is_error": true, "content": [{"type": "text", "text": "No message available to pin"}]}`
**Rationale**: The getter returns `None`, and the tool must give the agent a clear reason rather than attempting an invalid API call

### Scenario: Permission denied in group

**Given**: The bot is in a group without `can_pin_messages` permission
**When**: The agent calls `pin_message`
**Then**: Telegram returns a `TelegramAPIError`; the tool returns `{"is_error": true, "content": [{"type": "text", "text": "Failed to pin message: <error details>"}]}`
**Rationale**: Permission errors surface as `TelegramAPIError` — the tool doesn't need special permission detection, it just reports what Telegram returns

### Scenario: Idempotent pin

**Given**: A message is already pinned
**When**: The agent calls `pin_message` on it again
**Then**: The operation succeeds without error
**Rationale**: Telegram's `pinChatMessage` is idempotent — pinning an already-pinned message is a no-op that returns success

### Scenario: Unpin non-existent message

**Given**: A message ID that doesn't exist in the chat
**When**: The agent calls `unpin_message` with that ID
**Then**: Telegram returns a `TelegramAPIError`; the tool returns the error details
**Rationale**: The tool surfaces the API error rather than second-guessing Telegram's response
