## Purpose

This document explains the design rationale for this delta: the modeling choices, data flow, system behavior, and architectural approach.

After implementation, the "Detected Impacts" section will guide reconciliation into feature design docs.

## Problem Context

A delegated subagent (`delegate_to_agent` → `SideRunner.run`) runs in a **bare, isolated, in-memory pi session**: it binds no Tachikoma extension factories and the SDK's hard `tools` allowlist admits only pi's built-in tools. Extension and web tools — a Firecrawl scrape/search extension, MCP-backed capabilities, any factory-registered tool scoped to the main session — are therefore **doubly unreachable** from a delegation:

1. No Tachikoma factory binds (`selectExtensionFactories` returns `[]` for a bare session).
2. The hard `tools` allowlist masks any tool that *does* register (including pi-native extensions, which load via `agentDir` discovery even into a bare session).

So when the assistant faces tool-dependent work — most concretely web research — it cannot hand it to a parallel, isolated subagent. It is forced to run that work on the main session, burning main-session context.

**Constraints (from the spec):**

- The isolated, ephemeral run is preserved: in-memory, `isolatePrompt: true`, disposed after the run. Granted tools execute *inside* that boundary, never in the main session (R2).
- Read-only built-ins stay the default; extension tools are opt-in per delegation and never granted by default (R3).
- The grant is **source-agnostic**: a requested name resolves whether its provider is a Tachikoma factory opted into the new scope *or* a pi-native extension loaded from `.pi` / packages / settings (R4).
- Credentials are out of scope — no secrets plumbing; a granted tool reaches its credentials the same way it does in the main session (R7). No operator allowlist/denylist (R8) and no change to background-task binding (R9).

**Interactions:**

- The delegation runner already composes a per-delegation built-in override (`R6b`: `resolveTools` resolves `params.tools` → `agent.tools` → `DEFAULT_AGENT_TOOLS`). The grant is *additive on top of* whichever built-in set applies.
- The session-scope / factory-binding model is currently two-valued (`main`/`background`) with no ADR of its own; this delta extends it and records the decision (R10).

## Design Overview

Three coordinated changes, all built on primitives pi already exposes — no new binding mechanism is required:

1. **A new `subagent` session scope.** A Tachikoma factory opts its tools into subagent grantability via `app.agent.use(f, { sessionScopes: […, "subagent"] })`. This threads through the existing scope machinery (`SESSION_SCOPES`, `factoryBindingTargets`, `selectExtensionFactories`) exactly as `background` did. A pi-native extension cannot call `app.agent.use`, so its grantability signal is simply **installed = grantable** (installing an extension in `.pi` is itself a trust act).

2. **An additive `extensionTools` grant, resolved source-agnostically at execute time.** The calling agent names exposed extension tools via a new `extensionTools` parameter on `delegate_to_agent`, layered on top of the resolved built-in set. The resolution mechanism leans on two `AgentSession` primitives verified in the installed SDK: `getAllTools()` (enumerates *every* registered tool — Tachikoma-factory and pi-native alike — with source metadata) and `setActiveToolsByName()` (narrows the active set to an exact list). At execute time the subagent session is opened with the `subagent`-scoped factories bound; every requested name is validated against `getAllTools()` (throwing a self-correcting error *before* the run if any fails to resolve), then the active set is narrowed to exactly the resolved built-ins plus the granted extension tools.

3. **Agent-facing guidance.** The `delegate_to_agent` tool description, its `promptSnippet`/`promptGuidelines`, and the `skills-usage` section advertise the grant capability (generically) and direct the calling agent to delegate tool-dependent work with the relevant tools granted, replacing today's built-in-only messaging.

**Key insight that shaped the design:** the existing in-repo comments feared the `tools` allowlist was built-in-only and that enabling a *subset* of extension tools would need a new primitive. The installed SDK types disprove the fear. `createAgentSession({ tools })` is "an allowlist of tool names" (any names — extension tools are masked today only because the code lists built-in names exclusively); `AgentSession.getAllTools()` enumerates the full registered set source-agnostically; and `AgentSession.setActiveToolsByName(names)` narrows to an exact subset ("only tools in the registry can be enabled; unknown names ignored"). So the grant is *bind-the-subagent-factories, validate-via-getAllTools, narrow-via-setActiveToolsByName* — reusing the same enumeration/activation surface the runtime already has.

### Cross-Layer Contracts

**`delegate_to_agent` parameter contract** (additive change — `agent`/`task`/`description`/`tools` unchanged):

```
delegate_to_agent({ agent, task, description, tools?, extensionTools? })
  tools?          : string[]   # R6b built-in override, unchanged (read,grep,find,ls,bash,edit,write)
  extensionTools? : string[]   # NEW — exposed extension tool names, additive on top of `tools`
                               # empty/omitted = none granted (never "no tools")
→ tool result text (tail-truncated)   # on unresolved name: throws before any run
```

**`SideRunner.run` grant path** (internal contract):

```
run({ prompt, system, tools, extensionTools, isolatePrompt, ... })
  if extensionTools?.length:
    session = open({ inMemory, bare, bindSubagentFactories, isolatePrompt })   # no tools allowlist
    available = session.getAllTools().map(t => t.name)                          # source-agnostic
    missing = extensionTools.filter(n => !available.has(n))
    if missing: dispose(); throw self-correcting error (lists grantable non-builtin names)  # before prompt
    session.setActiveToolsByName([...tools, ...extensionTools])                 # exact subset
    session.prompt(prompt); dispose()
  else:
    today's built-in-allowlist path (unchanged)
```

**Integration Points**:

- `delegate.ts` → `SideRunner.run` → `AgentManager.open` → `selectExtensionFactories` (binds `subagentFactories`) → pi `createAgentSession`/`bindExtensions`. The session then exposes `getAllTools`/`setActiveToolsByName`, which is where validation and narrowing happen.
- **Error handling:** an unresolved extension name throws *before* `session.prompt` — no run is attempted, so the model is steered to correct the name (mirroring today's unknown-tool / unknown-agent errors). A granted tool that throws *during* the run surfaces to the subagent as a normal tool error (the subagent may recover or fail on its own); the delegation does not auto-terminate solely because a granted tool threw.
- **Lifecycle:** the session and any resources a binding opened are disposed in the same `finally` block as today.

### Shared Logic

- **Built-in resolution (`resolveTools`)** stays the single source for the built-in set and is shared by both paths — the grant path feeds its result into `setActiveToolsByName` rather than into the open-time allowlist. Rationale: one precedence rule (`params.tools` → `agent.tools` → `DEFAULT_AGENT_TOOLS`) serves both the built-in-only and the grant paths, so they cannot drift.
- **Self-correcting error shape:** the unknown-agent, unknown-built-in-tool, and unresolved-extension-tool errors all share the same "list what is valid" form, so the model gets a consistent correction signal across all three free-text inputs on `delegate_to_agent`.

## Modeling

- **`SessionScope`** widens from a two-valued to a three-valued union: `main | background | subagent`. `subagent` means "a delegated subagent run that requested extension tools." It is selected by the new `bindSubagentFactories` open-option, exactly as `background` is selected by `bindBackgroundFactories`.
- **`AgentSessionSources`** holds three independent factory lists (`piFactories`, `backgroundFactories`, `subagentFactories`). Membership is independent: a factory scoped to `"subagent"` only lives in `subagentFactories` without being a main or background factory.
- **`FactorySessionContext`** is unchanged in shape (`{ scope }`); the scope value set widens. A factory written `(pi) => …` still binds unchanged and ignores the scope; a factory that adapts (e.g. suppresses a user-facing surface in `background`) gains a third value to switch on.
- **Grant request** = `{ builtinTools, extensionTools }`. `builtinTools` is the resolved built-in set (full-replace semantics); `extensionTools` is an additive list of exposed extension names. The **resolved active set** is their union, applied via `setActiveToolsByName`.
- **Tool resolution** is a pure membership check: a requested name *resolves* iff it appears in the opened subagent session's `getAllTools()`. Resolution is intentionally source-blind — the same check covers a Tachikoma-factory tool and a pi-native extension tool.

## Data Flow

```
calling agent
  → delegate_to_agent({ agent, task, description, tools?, extensionTools? })
  → resolveTools(tools, agent.tools) ──────────────────────► resolvedBuiltins   (R6b, unchanged)
  ├─ extensionTools empty/omitted?
  │     yes → SideRunner.run({ tools: resolvedBuiltins, isolatePrompt })         (today's path)
  │     no  → SideRunner.run({ tools: resolvedBuiltins, extensionTools, isolatePrompt })
  │             → manager.open({ inMemory, bare, bindSubagentFactories, isolatePrompt })
  │                  └─ selectExtensionFactories binds subagentFactories w/ {scope:"subagent"}
  │                  └─ pi loads pi-native extensions via agentDir (installed = grantable)
  │             → available = session.getAllTools().map(t => t.name)             (source-agnostic)
  │             → missing = extensionTools − available
  │             → missing? → dispose; throw self-correcting error (lists grantables)  ◀─ BEFORE session.prompt: no run attempted
  │             → session.setActiveToolsByName([resolvedBuiltins, ...extensionTools])
  │             → session.prompt(task) → lastAssistantText
  │             → dispose (finally)
  → truncateTail(result.text) → tool result
```

## Key Decisions

### A new `subagent` session scope, with per-factory opt-in

**Choice**: Add a third value to `SESSION_SCOPES` and a third factory list (`subagentFactories`). A factory opts its tools into subagent grantability with `app.agent.use(f, { sessionScopes: […, "subagent"] })`. Opt-in granularity is **per-factory**, not per-tool.

**Why**: The scope/factory-binding model is the existing mechanism for "which session contexts does a factory bind into." `background` was added the same way for autonomous task runs; `subagent` is the symmetric addition for delegated runs. Per-factory matches the model (scopes are a factory-level property) and is the coarsest opt-in that still lets an extension author choose exposure — a factory either exposes its tools to subagents or it does not.

**Sources**: `src/extensions/api.ts` (`SESSION_SCOPES`, `UseFactoryOptions`, `FactorySessionContext`); `src/extensions/host.ts` (`factoryBindingTargets`, `app.agent.use`); `src/agent/manager.ts` (`selectExtensionFactories`); `docs/reference/pi-sdk-notes.md` (session-scope / binding model, verified @ 0.79.6).

**Alternatives Considered**:
- **Per-tool declaration** (`app.agent.use(f, { subagentTools: ["web_search"] })`): finer exposure, but it duplicates the scope concept with a per-tool list, requires the author to keep the list in sync with what the factory actually registers, and buys little — an extension that exposes one tool to subagents almost always exposes all of them. Rejected for complexity; the spec explicitly left this open and leaned per-factory.
- **Re-scoping the relevant tools** rather than the factory: there is no per-tool scope concept in the binding model, so this would invent one — same downside as per-tool declaration.
- **A separate registration surface** (`app.agent.exposeToSubagents(...)`): rejected — it would parallel `app.agent.use` without adding power over a third scope value.

**Consequences**:
- Pro: one concept (a scope) extends uniformly; `background` and `subagent` are symmetric; existing factories bind unchanged.
- Con: opt-in is all-or-nothing per factory — an author cannot expose a strict subset of a factory's tools. Acceptable given the spec's lean and the typical one-tool-per-extension reality.
- Con: the scope/factory-binding model gains a third value without a prior ADR; this delta supplies that ADR (R10 / S6).

### Source-agnostic resolution via `getAllTools()`, with generic advertising (the lean approach)

**Choice**: Resolve requested extension tool names against the *opened subagent session's* `session.getAllTools()` at execute time — one source-blind membership check covers Tachikoma-factory tools and pi-native extension tools identically. The `delegate_to_agent` description advertises the grant capability **generically** (it does not enumerate specific tool names), because names are only knowable after a session opens. No registration-time tool-name declaration contract is introduced.

**Why**: Tool names are only known after a factory runs inside a session (registration happens during `open`/`bindExtensions`). `getAllTools()` — verified on the installed `AgentSession` — enumerates every registered tool with source metadata, source-agnostically, so a single post-open check validates any requested name regardless of provider. This unifies the two sources the spec requires (R4) for free. The spec (R11) explicitly permits generic advertising "when the implementation can discover them without opening a subagent session (otherwise it advertises the capability generically)" — so generic advertising is sanctioned, and it avoids a new declaration contract that every exposing factory would have to maintain.

**Sources**: `node_modules/.../pi-coding-agent/dist/core/agent-session.d.ts` (`getAllTools(): ToolInfo[]`, `setActiveToolsByName(toolNames)`, `getActiveToolNames()`), verified @ 0.79.6; `docs/reference/pi-sdk-notes.md` (`registerTool` runs at load time and runtime; tool names known after session open).

**Alternatives Considered**:
- **Registration-time declaration (the "declaring" approach):** `app.agent.use(f, { sessionScopes: ["subagent"], tools: ["web_search", …] })` would let the description enumerate Tachikoma grantable tools precisely. Rejected (user decision): it adds a declaration contract that must be kept in sync with what the factory registers, it cannot cover pi-native extensions (which never call `app.agent.use`), and the spec sanctions generic advertising. Validation still has to happen at execute time for pi-native names, so declaration only helps advertising — not worth the machinery.
- **Resolve against the main session's bound tool set:** the main session is already open, so `getAllTools()` there is cheap. Rejected: the main session binds `main`-scoped factories, not `subagent`-scoped ones, and a pi-native extension need not be bound to the main session — so the main session's tool set is the wrong universe for validating subagent grants.

**Consequences**:
- Pro: Tachikoma and pi-native tools are handled by one code path; no declaration contract; the description never goes stale (it advertises a capability, not a list).
- Pro: validation is precise — the granted name is checked against the *actual* tools the subagent session has, not a cached/declared list.
- Con: the description cannot enumerate grantable tool names, so the model must know or guess a tool name to request it. Mitigated by `promptGuidelines` naming the common case (web research → web tools) and by the self-correcting error listing the grantable set on a miss.
- Con (see Open Questions): because pi's tool registry dedupes by name, a *name collision* between two providers is not observable from `getAllTools()` (only the survivor appears), so the spec's ambiguity AC is met on a best-effort basis only.

### Subset enabling via `setActiveToolsByName` instead of the hard allowlist

**Choice**: On the grant path, open the subagent session **without** a `tools` allowlist (so every bound factory tool registers and is enumerable), validate, then narrow the active set to exactly `[...resolvedBuiltins, ...granted]` with `session.setActiveToolsByName(...)`. The built-in-only path keeps today's hard allowlist unchanged.

**Why**: A provided `tools` allowlist means "only the listed names are enabled" — so listing only built-ins masks extension tools (the existing double-block). Two clean fixes exist: (a) name the extension tools too in an inclusive `tools` allowlist, or (b) drop the allowlist and narrow with `setActiveToolsByName`. (b) is chosen because validation already requires a post-open step (to know whether a name resolves), so narrowing then is natural, and it sidesteps any question of whether an inclusive allowlist would silently drop an unknown name. It also restores the read-only built-in default cleanly: with no allowlist, pi enables its default built-ins (`read,bash,edit,write`), and `setActiveToolsByName([read,grep,find,ls, …granted])` sets exactly the intended set.

**Sources**: `node_modules/.../pi-coding-agent/dist/core/sdk.d.ts` (`tools` "allowlist of tool names… when omitted, extension/custom tools stay enabled"; `excludeTools`; `noTools`), verified @ 0.79.6; `agent-session.d.ts` (`setActiveToolsByName`: "only tools in the registry can be enabled; unknown names ignored"); `src/agent/side-run.ts` (the background path already drops the allowlist precisely so factory tools survive — the comment is the precedent).

**Alternatives Considered**:
- **Inclusive `tools` allowlist** (`tools: [...resolvedBuiltins, ...grantedExtensionNames]` at open time): also viable since `tools` accepts any name, but it would silently ignore an unresolved name rather than throw, so a separate validation pass is still needed — and once that pass exists, `setActiveToolsByName` is the cleaner narrowing primitive.
- **`excludeTools` denylist**: requires enumerating the *universe* of tools to deny (every other bound factory tool plus unwanted built-ins), which is more fragile than naming the small desired set.
- **Selective factory binding** (bind only the factories owning a requested tool): rejected — binding is just registration (cheap; credentials are touched at tool execution, not registration, per R7), and binding-all-then-narrowing is simpler and still leaves non-granted tools inert (`setActiveToolsByName` makes them uncallable).

**Consequences**:
- Pro: the exact active set is controlled in one place after validation; the read-only default is preserved; the background path's "no allowlist so factory tools survive" pattern is reused.
- Con: between `open` and `setActiveToolsByName` the session briefly has pi's default built-ins active — irrelevant, since no prompt runs until after narrowing.

### An additive `extensionTools` parameter, separate from `tools`

**Choice**: A new `extensionTools?: string[]` param on `delegate_to_agent`, additive on top of the resolved built-in set. The existing `tools` param keeps its full-replace semantics and built-in-only validation.

**Why**: The built-in resolution is a full-replace list with a clear precedence (`resolveTools`: `params.tools` → `agent.tools` → default). Folding additive extension names into `tools` would muddle replace-semantics and force a split validation path inside one param. A separate param keeps the built-in-vs-extension distinction honest in the schema and the description, and lets each param validate against its own universe (built-ins vs. the opened session's registry). An empty/omitted `extensionTools` means "none granted" — never "no tools" (the built-in set always applies).

**Sources**: `src/extensions/skills/delegate.ts` (`resolveTools`, `DelegateParams`); spec R1 ("granted extension tools are added on top of whichever built-in set applies").

**Alternatives Considered**:
- **Widen `tools` to accept any grantable name** with a split validation path: rejected — it overloads one param with two semantics (replace-builtins vs. add-extension) and makes the description's "only built-in tools are grantable" wording harder to evolve honestly.

**Consequences**:
- Pro: each param has one job; the built-in path (R6b) is byte-for-byte unchanged, so its tests and behavior are preserved.
- Con: two params where one might suffice — acceptable for the clarity gained.

### Pi-native grantability signal: installed = grantable

**Choice**: A pi-native extension loaded from `.pi` / packages / settings is grantable by virtue of being installed. There is no additional opt-in for pi-native extensions (they cannot call `app.agent.use`).

**Why**: Installing an extension under `.pi` (or via settings/packages) is already a trust act — it binds the extension into every session pi opens, including today's bare delegated session (its tools are merely masked by the allowlist). Requiring a second signal would be inconsistent with how pi-native extensions are treated everywhere else, and there is no Tachikoma-side hook for a pi-native extension to declare intent. The grant just stops masking tools the extension already registered.

**Sources**: `node_modules/.../pi-coding-agent/dist/core/resource-loader.d.ts` (`DefaultResourceLoader` loads `agentDir` extensions + `additionalExtensionPaths` + inline `extensionFactories`; `noExtensions`/`extensionsOverride` exist to suppress/redirect); `docs/reference/pi-sdk-notes.md` (extension load sources).

**Alternatives Considered**:
- **An operator allowlist/denylist for subagent grants:** explicitly out of scope (R8).
- **A manifest convention for pi-native extensions to declare subagent exposure:** rejected — no mechanism exists for pi-native extensions to speak to Tachikoma, and inventing one contradicts "installed = trusted."

**Consequences**:
- Pro: pi-native extensions are grantable with zero author-side changes; the source-agnostic check covers them uniformly.
- Con: any installed pi-native extension is grantable to any delegation — there is no per-extension gate. Bounded by R8 being out of scope and by the fact that installation is already a trust boundary.

### Recursion stays structurally impossible

**Choice**: The skills/delegate factory is registered with `sessionScopes: ["main", "background"]` — **not** `"subagent"`. A subagent session therefore never binds `delegate_to_agent`, so a delegated subagent cannot itself delegate.

**Why**: Today this invariant falls out of the bare session binding nothing. With `subagent`-scoped factories now binding, the invariant must hold by *omission* — deliberately not adding `"subagent"` to the skills factory scopes — rather than by bareness. Stating it explicitly prevents a future change from accidentally enabling recursion.

**Consequences**:
- Pro: no runtime recursion guard needed; the invariant is structural, as today.
- Con: if a future extension legitimately wants subagents to delegate, it must grapple with recursion explicitly — which is the correct forcing function.

## System Behavior

### Scenario: Grant a Tachikoma-factory extension tool

**Given**: A web extension factory is registered with `app.agent.use(webFactory, { sessionScopes: ["subagent"] })` and registers `web_search`.
**When**: The main agent calls `delegate_to_agent({ agent: "general-purpose", task: "research X", extensionTools: ["web_search"] })`.
**Then**: The subagent session opens in-memory, prompt-isolated, with the web factory bound (`{ scope: "subagent" }`); `web_search` appears in `getAllTools()`; validation passes; `setActiveToolsByName(["read","grep","find","ls","web_search"])` enables exactly the read-only built-ins plus `web_search`; the run executes and its final text returns as the tool result. The session is disposed after.

### Scenario: Grant alongside a built-in override

**Given**: A task needs shell access and web search.
**When**: `delegate_to_agent({ agent: "general-purpose", task: "...", tools: ["read","grep","bash"], extensionTools: ["web_search"] })`.
**Then**: `resolveTools` returns `["read","grep","bash"]`; the subagent's active set is exactly `["read","grep","bash","web_search"]`; the built-in `general-purpose` worker prompt is rebuilt (via `dynamicPrompt`) to reflect that it may run commands.

### Scenario: No extension tools requested — today's behavior preserved

**Given**: A delegation that omits `extensionTools` (or passes `[]`).
**When**: It executes.
**Then**: It takes today's built-in-allowlist path unchanged — read-only default (or the agent's declared tools / the `tools` override), no subagent factories bound, no extension surface. Read-only stays the default.

### Scenario: Unknown extension tool name

**Given**: The calling agent requests `extensionTools: ["web_srch"]` (a typo).
**When**: The delegation executes.
**Then**: The subagent session opens with the `subagent` factories bound, `getAllTools()` is enumerated, `web_srch` is not found, the session is disposed, and the delegation throws a self-correcting error listing the grantable (non-builtin) tool names — *before* any prompt runs. No run is attempted.

### Scenario: A factory that did not opt into `subagent` is not grantable

**Given**: A factory registered with `sessionScopes: ["main"]` registers `notify_user`.
**When**: The agent requests `extensionTools: ["notify_user"]`.
**Then**: That factory does not bind into the subagent session, so `notify_user` is absent from `getAllTools()`; the request is treated as unresolvable and the delegation throws (it is not silently granted).

### Scenario: A pi-native extension tool is granted on the same terms

**Given**: A pi-native extension installed under `.pi/extensions/` registers `mcp_query`.
**When**: The agent requests `extensionTools: ["mcp_query"]`.
**Then**: pi loads the extension via `agentDir` discovery into the subagent session; `mcp_query` appears in `getAllTools()`; validation passes; it is enabled and callable — on the same terms as a Tachikoma-factory tool.

### Scenario: Partial resolution fails the whole request

**Given**: The agent requests `extensionTools: ["web_search", "web_srch"]` and only `web_search` resolves.
**When**: The delegation executes.
**Then**: Because `web_srch` does not resolve, the delegation throws before the run — partial resolution is not granted. Every requested name must resolve.

### Scenario: A granted tool errors mid-run

**Given**: A granted `web_search` throws during the subagent run.
**When**: The error occurs.
**Then**: It surfaces to the subagent as a normal tool error; the subagent may recover or fail on its own. The delegation does not auto-terminate solely because a granted tool threw.

### Scenario: Isolation preserved on the grant path

**Given**: A delegation grants an extension tool.
**When**: The run executes.
**Then**: The session is still in-memory, prompt-isolated (`isolatePrompt: true`), and disposed after the run; the extension tool runs inside that boundary. It executes against a fresh binding in the subagent session (scope `subagent`) — it does not share the main session's in-memory state or handles. Only the subagent's final text returns as the tool result.

## Decisions closed during design

- **Name-collision / ambiguity → accept pi registry last-wins.** pi's tool registry dedupes by name, so when two providers expose the same name only the survivor appears in `getAllTools()`. A per-factory `pi.registerTool` interceptor (the alternative) could detect Tachikoma-factory-vs-factory collisions, but it is blind to pi-native extensions (which receive their own unwrapped `pi` from pi's loader), so it cannot fully satisfy the spec's ambiguity AC either — at the cost of real machinery. The chosen behavior is therefore **registry last-wins, documented**: a colliding name resolves to whichever provider registered last, and no ambiguity error is thrown. This scopes the spec's ambiguity AC to best-effort (see Detected Impacts for the spec reconciliation). *Requires user confirmation — see the open item below.*
- **Advertising discoverability → generic advertising is the baseline for this delta.** Generic advertising means the model must know or name a tool to request it, mitigated by `promptGuidelines` naming the common case (web research → web tools) and by the self-correcting error listing the grantable set on a miss. Enumerating grantable names (e.g. from the main session, or via registration-time declaration) is a possible **future enhancement, out of scope here** — filed as a follow-up, not a blocker.

## Open Item (needs user confirmation)

- [x] **Ambiguity AC scoping — RESOLVED (accept last-wins).** The spec lists "a name resolving to more than one provider throws an ambiguity error" as a Must-have AC. Neither the lean approach nor a `registerTool` interceptor can fully satisfy it (pi's registry dedupes by name; pi-native collisions are undetectable from Tachikoma's side). **Confirmed: accept registry last-wins** as the documented behavior and scope the spec's ambiguity AC to best-effort (see Detected Impacts for the spec reconciliation). A partial Tachikoma-only collision detector was considered and rejected — machinery for incomplete coverage.

### Pre-flight SDK verification (Batch 1, re-confirmed against the installed 0.79.6 `.d.ts`)

The installed version is `0.79.6` (matches the design's original verification version). The three primitives the grant path (Batch 2) leans on resolve as follows — **every one is synchronous**, so no `await` is needed on them and `dispose()` is a plain call in the `finally`:

- `AgentSession.setActiveToolsByName(toolNames: string[]): void` — **sync**, returns `void`. Doc: "Only tools in the registry can be enabled. Unknown tool names are ignored.
