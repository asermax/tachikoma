### Flagged Unknowns

#### S2 — Request shape

How does the calling agent express the grant? Today `tools` is a full-replace list validated against built-ins only (`resolveTools`). Admitting extension tools *additively* (on top of the resolved built-in set) raises a parameter-shape question: a separate `extensionTools` param layered on top, versus widening `tools` to accept any grantable name with a split validation path. The choice must keep the model self-correcting (clear errors on unknown names) and keep the tool description honest about the built-in-vs-extension distinction. Need to confirm the chosen shape against the existing `resolveTools` precedence (`params.tools` → `agent.tools` → `DEFAULT_AGENT_TOOLS`) and the rebuilt `general-purpose` worker prompt (`buildSubagentSystemPrompt(tools)`).

#### S3 — Discovery before session open (most load-bearing)

Tool names are only known *after* a factory runs inside a session (registration happens in factory execution during `open`). How does `delegate_to_agent` know which extension tool names are valid — to advertise them in the tool description (R11) and to validate requests (R4) — without opening a subagent session? Candidate approaches: (a) declare tool names at factory-registration time via a registry/declaration so they're knowable up front; (b) resolve requested names against the main session's currently-bound tool set; (c) a lightweight discovery pass that opens a throwaway session to enumerate tools. This determines whether validation can be precise and whether the tool description can enumerate grantable tools — and it gates how cleanly R11's "list grantable tool names" can be met. May surface a new requirement (e.g. a registration-time declaration contract).

#### S4a — Enabling a subset of bound tools

The SDK `tools` allowlist admits built-in names only and filters out extension/custom tools (confirmed in `SideRunner.run`: the background path sets NO allowlist precisely so factory tools survive). To grant extension tools, the subagent run must open without that allowlist. How is a *subset* (only the requested extension tools, plus the resolved built-ins) enabled rather than every tool the bound providers register? Candidate: pi's `excludeTools` list (per `pi-sdk-notes.md`), selective provider binding (bind only the factories/extensions that own a requested tool), or another per-tool enable mechanism. Need to confirm `excludeTools` semantics and how it composes with the built-in allowlist path.

#### S4b — pi-native binding today + grantability signal

Two linked questions. First, a factual spike: do pi-native extensions (loaded by pi's `DefaultResourceLoader` from `.pi/extensions/`, packages, settings) bind into today's *bare* delegated session at all, or does enabling them require a non-bare / selective load path? (The bare session currently binds nothing via `selectExtensionFactories`, but pi's own agentDir discovery may still load pi-native extensions — needs verification.) Second, since a pi-native extension cannot call `app.agent.use` to opt into a Tachikoma scope, how is its grantability determined? Lean from speccing: **installed = grantable** (installing an extension in `.pi` is itself a trust act). Confirm this is acceptable or define an alternative signal.
