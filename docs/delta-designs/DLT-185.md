## Purpose

This document explains the design rationale for replacing the background-task evaluator with goal-driven self-declaration: the modeling choices, data flow, system behavior, and architectural approach.

After implementation, the "Detected Impacts" section will guide reconciliation into the tasks feature design.

## Problem Context

Background tasks today end when an **external evaluator** says so. After each turn, `evaluateCompletion` runs a `side.classify` over the agent's response and returns `complete` / `continue` / `error`; the loop acts on that verdict, and on `complete` the evaluator's *reason* becomes the instance `result`. That model has three problems this delta resolves:

- **No goal to anchor "done".** Completion is judged turn-by-turn against the task prompt loosely, with no explicit success check. The evaluator is a strict classifier precisely because a reviewing one caused quality-gating loops — but strict classification of "did the agent *say* it's done?" is a weaker signal than "is the goal *actually* met?"
- **Fail-open burns iterations.** The evaluator is best-effort: any exception maps to `continue`. A flaky classifier model can never abort a healthy run, so the iteration cap is the only backstop — and a persistently broken evaluator silently burns every iteration before failing.
- **The result is the judge's summary, not the agent's.** The instance `result` is the evaluator's factual paraphrase, so the user-facing outcome and the audit trail are both second-hand.

A task that genuinely cannot be finished has no voice either: it loops to the cap and fails with "max iterations reached," never telling the user *why*.

**Constraints:**

- pi provides no scheduling, completion judgment, or buffered delivery — those are host concerns ([pi-sdk-notes](../reference/pi-sdk-notes.md)). The tasks extension expresses this using only `AppContext` services (DES-001): `app.agent.side`, `app.db`, `app.events`, `app.sessions.runPostProcessors`.
- Background runs are detached, concurrency-capped, and crash-recoverable; an evaluator restructure must not disturb `ask_user` pause/resume, the concurrency cap, stop/cancel, post-processing, or failure-notice routing (R12).
- The iteration cap must remain the **single clean fail-point** for an undeclaring run, so the unspecced DLT-134 (iteration-limit escalation) can intercept that exact point later (R9).
- The agent's tool surface must stay Google-API-compatible: pi uses `StringEnum` rather than `Type.Union` of literals for that reason ([pi-sdk-notes](../reference/pi-sdk-notes.md)).

**Scope boundaries:** this delta changes *how background runs decide they are done*. It does not change scheduling, delivery, concurrency, retention, session-task behavior, or any non-background path.

## Design Overview

Definitions and instances gain a nullable, free-text **`goal`**. A goal flows: provided on `create_task` / `update_task` / `run_task_now` → snapshotted onto the instance at creation → **extracted from the task prompt at run start if still absent** (via the existing `side.classify` structured-extraction pattern) → written back to the definition when one exists and still has none → surfaced to the agent in the opening turn.

The agent then **self-declares its terminal outcome** through one new per-run custom tool, `update_goal` (built exactly like the existing `ask_user` tool — a `defineTool` whose `execute` handler sets a closure flag the loop reads after the turn). It declares either:

- **`completed`** — restating the goal and citing concrete, checkable evidence that its success check is met, plus a summary of what was accomplished; or
- **`not_completable`** — with a reason that reaches the user as a failure notice.

The loop no longer runs a post-turn evaluator. After each turn it reads the closure flags: a pending question pauses (unchanged `ask_user` path); a valid pending declaration terminates (`completed` → completed + dispose + post-processors; `not_completable` → fail with the reason); neither → inject a **completion nudge** as the next prompt that re-evaluates the goal without forcing a premature declaration. The iteration cap remains as the sole safety net: never declaring → reaching the cap fails the run as an error.

```
run start
  ├─ goal absent? ── side.classify(extract) ── usable? ── write back to def (if null) + store on instance
  │                                              └─ unusable/fail ── proceed on task-prompt basis, persist nothing
  ├─ opening turn: task + goal + "declare via update_goal when the check is met"
  └─ loop (1..maxIterations):
       prompt
       ┌─ pendingQuestion   ── waiting/pause (ask_user, unchanged)
       ├─ pendingDeclaration ─ completed   ── completed(result=summary) + dispose + post-processors
       │                      └ not_completable ── fail(reason in notice)
       └─ neither            ── nudge (re-evaluate vs goal) ── next iteration
     cap reached without declaring ── fail (sole auto-fail point)
```

### Cross-Layer Contracts

**`update_goal` tool contract** (per-run custom tool, same shape as `ask_user`):

```
update_goal
Parameters:
  status:     "completed" | "not_completable"          // StringEnum discriminator
  // required when status === "completed":
  goalRestated: string   // the goal, restated in the agent's own words
  evidence:     string   // concrete, checkable proof the stated check is satisfied
  summary:      string   // what was accomplished — the user-facing outcome
  // required when status === "not_completable":
  reason:       string   // why the goal cannot be completed

execute (in-tool validation):
  completed      → require goalRestated, evidence, summary (non-empty after trim)
                   valid  → set pendingDeclaration { status, summary }; return success text
                   invalid → return an error result (agent retries within the run)
  not_completable → require reason (non-empty after trim)
                   valid  → set pendingDeclaration { status, reason }; return success text
                   invalid → return an error result (agent retries)

Loop reads pendingDeclaration after the turn:
  completed       → instance.result = summary
  not_completable → instance.result = reason; emitted in the warning-notice
```

**Goal-extraction contract** (`side.classify`):

```
extractGoal(side, taskPrompt):
  side.classify({ system: GOAL_EXTRACTION_SYSTEM, user: taskPrompt, schema: ExtractedGoalSchema })
  → { goal: string }   // free text following the recommended structure
  catch / fails heuristic → null  (run proceeds on task-prompt basis; nothing persisted)
```

**Integration points:**

- The loop's post-turn dispatch is a single `if/else` over the two closure flags (`pendingQuestion`, `pendingDeclaration`), replacing the `evaluateCompletion` switch. The closure-flag pattern is unchanged from `ask_user`; `update_goal` adds a second flag.
- The instance `result` is now sourced from the tool output (`summary` or `reason`) on a terminal declaration. The cap, thrown-error, and cancel paths keep their existing `result` strings — only the *declaration* and *evaluator-success* paths change, and the latter is removed.
- The failure notice for `not_completable` reuses the existing `fail(reason, noticeMessage)` helper, so it flows through the notifications router's `warning → Normal-tier` mapping exactly like the cap and thrown-error failures.

### Shared Logic

- **Goal prose structure** ("end state + stated check + invariants") is described once in the extraction system prompt, the opening-turn instruction, the usage section, and the tool descriptions. It is *recommended prose*, not a parsed schema, so all four surfaces use the same wording and there is no structure to keep in sync.
- **In-tool validation** is the single gate for a valid declaration. The loop trusts any `pendingDeclaration` it sees (the flag is only set after validation passes), so terminal logic stays in one place and the loop stays a thin dispatcher.

## Modeling

```
TaskDefinition                         TaskInstance
├─ id, name, schedule, taskType        ├─ id, definitionId (nullable)
├─ prompt                              ├─ taskType, status, prompt
├─ enabled, lastFiredAt, since         ├─ scheduledFor, startedAt, completedAt
├─ createdAt                           ├─ result (summary | reason | fail-reason)
└─ goal: text | null   ◀── new         ├─ question, userResponse, resumeContext
                                       ├─ piSessionFile
                                       ├─ updatedAt, createdAt
                                       └─ goal: text | null   ◀── new
```

**`goal` is a snapshot, not a reference.** An instance's `goal` is fixed at creation. A definition goal written back by extraction *after* an instance was created never reaches that instance — it extracts its own goal at run start (R3 AC: "instances never inherit a goal written back after their creation"). This mirrors the existing `prompt` snapshot semantics (a `run_task_now` by-reference run snapshots the prompt without mutating the definition).

The `result` field's source becomes: declaration (`summary` / `reason` via `update_goal`) on a self-declared terminal; `"Max iterations (N) reached without a terminal declaration"` on the cap; the thrown-error / cancel reasons unchanged. The full audit — the re-stated goal and the cited evidence — lives in the session transcript (the agent emitted them through the `update_goal` call), not in the `result` string (R10).

## Data Flow

1. **Goal set on a definition** — `create_task` / `update_task` carry an optional `goal`; persisted on the definition.
2. **Instance creation snapshots the goal** — generation (cron/one-shot) and `run_task_now` (by-reference snapshots `definition.goal`; ad-hoc carries an inline `goal`; an explicit run-now override wins over the definition goal) write it onto the instance. No goal → null.
3. **Run start** — if `instance.goal` is null, `extractGoal` runs before the agent begins; on a usable result it is stored on the instance, and written back to the definition **iff** `definition.goal` is still null at write-back time. Ad-hoc instances (no parent definition) store the goal on the instance only.
4. **Opening turn** — the agent receives the task, its goal, and the instruction to self-declare via `update_goal`.
5. **Each turn** — the agent works toward the goal; calling `ask_user` sets `pendingQuestion`; calling `update_goal` (after in-tool validation) sets `pendingDeclaration`.
6. **After each turn** — `pendingQuestion` → `waiting`/pause (unchanged); `pendingDeclaration.completed` → `completed(result=summary)` + dispose + post-processors; `pendingDeclaration.not_completable` → `fail(reason)`; neither → inject the nudge and iterate.
7. **Cap** — the loop exits without a declaration → `fail("Max iterations (N) reached…")` — the sole automatic failure path.

## Key Decisions

### Free-text goal, not a structured JSON object

**Choice**: `goal` is a nullable free-text column; "end state + stated check + invariants" is *recommended prose structure* documented across the prompt surfaces, not a parsed schema.
**Why**: The spec frames that structure as *recommended* (R13: "documents what a goal is and the recommended structure"), and R6 asks the agent to "restate the goal and provide evidence that its **stated check** is satisfied" — phrasing that treats the check as part of the goal text the agent restates. Free text is one nullable column, a cheap single-shot extraction, and — critically for R15 — has the fewest ways to extract a degenerate shape (a structured `{endState, check, invariants[]}` JSON goal adds a JSON column, costlier extraction, and more malformed-output failure modes that R15 must then degrade around).
**Alternatives Considered**:
- A structured JSON goal `{ endState, check, invariants[] }`: would let the tool validate `evidence` against a discrete `check` field more tightly. Not chosen — the machine-checking gain is marginal (the in-tool validator already requires a non-empty `evidence` string), and the extraction-failure surface grows.
**Consequences**:
- Pro: One nullable text column; cheap extraction; the recommended structure is enforced by *instruction* (the extraction prompt, the opening turn, the usage docs) rather than a schema the model can fumble.
- Pro: Lower risk of a malformed structured goal blocking a run — R15 stays a simple "non-empty / min-length" check.
- Con: "Is the evidence actually about *the* check?" is judged by the agent and the in-tool validator, not structurally guaranteed.

### One `update_goal` tool with a `StringEnum` discriminator + optional per-variant fields

**Choice**: A single per-run custom tool `update_goal` whose parameters are a flat `Type.Object` with a `StringEnum` `status` discriminator (`completed` / `not_completable`) and `Type.Optional` per-variant fields — **not** a `Type.Union` of two objects, and **not** two separate tools.
**Why**: TypeBox's `Type.Union` emits JSON-Schema `anyOf` and has **no `discriminator` support** (`discriminator` is a non-standard OpenAPI keyword) — TypeBox issues [#37](https://github.com/sinclairzx81/typebox/issues/37) and [#1307](https://github.com/sinclairzx81/typebox/issues/1307) — and pi uses `StringEnum` rather than unions of string literals specifically for **Google/Gemini API compatibility** ([pi-sdk-notes](../reference/pi-sdk-notes.md)). A flat object with a `StringEnum` discriminator and `Type.Optional` fields avoids `anyOf`/`oneOf` entirely, stays Google-safe, and matches how every other tool parameter in this codebase is expressed. A single tool is also what R5 asks for ("a single goal-status tool … is the sole way the agent declares a terminal outcome").
**Sources**: TypeBox issues [#37](https://github.com/sinclairzx81/typebox/issues/37), [#1307](https://github.com/sinclairzx81/typebox/issues/1307), [#48](https://github.com/sinclairzx81/typebox/issues/48); [pi-sdk-notes](../reference/pi-sdk-notes.md) (`StringEnum` for Google API compat).
**Alternatives Considered**:
- `Type.Union` of two `Type.Object`s (discriminated by a literal): rejected — emits `anyOf` with no discriminator, and literal-union fields hurt Google-API compat.
- Two tools (`complete_task` + `declare_not_completable`): rejected — simpler per-tool schema, but two terminal surfaces to keep consistent and a muddier "single sole terminal path" (R5).
**Consequences**:
- Pro: One terminal surface (R5); Google-safe schema; consistent with existing tool-param style.
- Con: The `Type.Optional` per-variant fields are conditionally required (validated in-tool), so the JSON Schema alone does not encode "evidence required iff status=completed" — the in-tool validator closes that gap.

### Tool name `update_goal`, field `status` — aligned with the agent-harness convention

**Choice**: Name the tool `update_goal` and the discriminator field `status`.
**Why**: `update_goal` is an established agent-harness tool — part of a `create_goal` / `get_goal` / `update_goal` trio in which `update_goal({ status: "complete", evidence })` is exactly the completion-declaration verb (documented across harnesses such as OpenClaw's Codex harness, the Seshat Go package, and CodeWhale, with an OpenCode goal-plugin retaining a string `evidence` field). Models exposed to those harnesses may already have the verb in their tool-use behavior. The field name `status` follows the same convention; the values `completed` / `not_completable` match this codebase's `TASK_STATUSES` and the spec's R5/R7 wording (internal consistency wins over the convention's exact `complete` spelling).
**Sources**: OpenClaw tools/harness docs, Seshat (`pkg.go.dev/github.com/KPO-Tech/seshat`), CodeWhale CHANGELOG, OpenCode goal-plugin — surfaced via WebSearch (the `katachi:doc-researcher` Context7 path was non-functional in this environment, so verification fell back to web search against those projects).
**Alternatives Considered**:
- `declare_task_outcome` / `report_goal_status` (self-describing): accurate but unconventional — forgoes the familiarity benefit.
- `complete_task`: misleading, since the tool also declares `not_completable`.
**Consequences**:
- Pro: Familiar verb for models trained on goal-tracking harnesses; aligns with the spec's own "goal-status tool" language (R5/R10).
- Con: `update_goal` literally suggests "edit the goal," so the tool description must make clear it only accepts the two terminal statuses (it cannot edit the goal text) — the in-tool validator enforces that.

### In-tool validation for incomplete declarations

**Choice**: The `update_goal` `execute` handler validates the declaration and **returns an error result** when it is incomplete (`completed` missing `goalRestated`/`evidence`/`summary`, or `not_completable` missing `reason`), so the agent self-corrects and retries within the same run. The closure flag is set only for a *valid* declaration.
**Why**: This reuses pi's `defineTool` error-return self-correction pattern (the same mechanism DLT-184 relies on for "self-correcting errors before the run starts") and keeps the loop a thin dispatcher that only ever sees valid terminal declarations. The alternative — accepting the tool call and rejecting it in the loop after the turn — would waste a turn and push validation logic into the loop.
**Sources**: [pi-sdk-notes](../reference/pi-sdk-notes.md) (`registerTool` error-return / `terminate` patterns); DLT-184 self-correcting-error pattern.
**Alternatives Considered**:
- Accept-then-reject in the loop after the turn: rejected — wastes an iteration and splits validation from the tool.
**Consequences**:
- Pro: Immediate, in-turn correction; one validation site; the loop trusts the flag.
- Con: An agent that repeatedly submits incomplete declarations burns iterations on retries — bounded by the cap (the same backstop as any other non-terminating behavior).

> **Implementation finding (Batch 3):** the in-tool error mechanism is **throw-from-`execute`**, verified against the pinned `pi 0.79.6` `.d.ts`. `@earendil-works/pi-agent-core`'s `AgentTool.execute` type is documented *"Throw on failure instead of encoding errors in `content`."* (`dist/types.d.ts:332`), and the agent loop's `executePreparedToolCall` **catches** a thrown error and converts it into an `isError: true` tool result whose content is `error.message` (`dist/agent-loop.js:435-442`), surfaced to the model for self-correction — the run does NOT terminate. `AgentToolResult` carries only `terminate?: boolean` (the early-termination / structured-output escape hatch); there is **no `isError` field** on the execute-return type (the `isError` fields live on event/UI types, not on the result object), so there is no "return an isError content block" path. So `update_goal.execute` **throws** an `Error` naming the missing field on an incomplete declaration (flag stays null, agent retries within the run) and returns a normal `AgentToolResult` on a valid one — the same shape as `ask_user`. This matches the DES-002 throw convention and the DLT-184 self-correcting-error pattern referenced in `side-run.ts`.

### Conservative completion: restated goal + concrete evidence

**Choice**: A valid `completed` declaration must restate the goal and cite concrete, checkable evidence (an artifact, measurement, or observable outcome) that the stated check is satisfied, plus a summary.
**Why**: Self-declared completion must be disentangled from *actual* completion — the **Vigil** evaluation framework (arXiv 2605.08747) makes terminal commitment independently measurable precisely because agents self-declare prematurely. Requiring the agent to *restate* the goal and *produce evidence* is the conservatism mechanism: it forces the agent to ground its claim rather than assert it. **Premature commitment** (arXiv 2606.22936) — agents locking onto one reading of the evidence early — is the failure mode this combats.
**Sources**: [Vigil — Disentangling World Completion from Self-Termination in Embodied Agents (arXiv 2605.08747)](https://arxiv.org/html/2605.08747v4); [Diagnosing Premature Commitment in LLM Agents (arXiv 2606.22936)](https://huggingface.co/papers/2606.22936).
**Alternatives Considered**:
- A bare `status: "completed"` with no evidence (faster, fewer fields): rejected — R6 explicitly forbids it, and it removes the only check against unfounded declarations.
**Consequences**:
- Pro: The declaration is auditable — the transcript holds the restated goal and the cited evidence (R10).
- Con: The in-tool validator can only check that `evidence` is *present*, not that it is *true*; a determined agent can fabricate plausible evidence. The cap and the user's stop/cancel remain the outer guards, same as today.

### Per-turn nudge that re-evaluates without forcing a declaration

**Choice**: A non-terminal turn injects a short nudge asking the agent to evaluate the goal and call `update_goal` if its check is met — while explicitly allowing it to continue working.
**Why**: Forcing a declaration each turn invites premature termination; never reminding lets a forgetful agent loop without revisiting completion. The nudge threads that needle, and the **premature-commitment** research above argues for re-evaluation over forced commitment. It is a user message (not a system note) so it lands as a normal turn the agent responds to.
**Sources**: [Premature Commitment in LLM Agents (arXiv 2606.22936)](https://huggingface.co/papers/2606.22936); R8 acceptance criteria ("the agent may continue working").
**Alternatives Considered**:
- The old evaluator-note continuation (`"Continue working on the task. Evaluator note: …"`): removed with the evaluator; carried no goal and offered no declaration path.
- A bare `"continue"`: rejected — too easy to ignore and never declare.
**Consequences**:
- Pro: The agent revisits completion every turn without being rushed; multi-turn progress is uninterrupted.
- Con: Adds one short user message per non-terminal turn — cheap, and the persistent session already absorbs continuation context.

### The cap is the sole automatic fail-point (unchanged, now load-bearing)

**Choice**: A run that never declares a terminal outcome fails at the iteration cap with `"Max iterations (N) reached without a terminal declaration"` — the only automatic failure path, and a single `fail()` call.
**Why**: R9 requires one clean fail-point so the unspecced DLT-134 (iteration-limit escalation) can intercept *this* call to escalate to the user instead of failing. With the evaluator removed, the cap is no longer one of several terminations — it is the *only* one the system initiates for an undeclaring run, so it must be identifiable as a single call site.
**Alternatives Considered**:
- Reintroducing a soft "stuck" detector: rejected — that is exactly the external judgment R11 removes, and DLT-130 (progress visibility) / DLT-134 (escalation) are the planned successors on this subsystem.
**Consequences**:
- Pro: One place for DLT-134 to hook; deterministic failure semantics.
- Con: A run that is genuinely progressing slowly but never declares still fails at the cap — DLT-134 is the intended remedy.

### Lazy goal migration (no backfill), conditional write-back

**Choice**: Existing definitions acquire a goal on first run via extraction (S3); there is no backfill pass. Extraction writes the goal back to a definition **only when its goal is still null at write-back time** — it never clobbers a goal set by `update_task` or an earlier write-back.
**Why**: R14 forbids a mandatory backfill; first-run extraction is the marker-free, state-based migration in the spirit of DES-006 (the resulting non-null goal *is* the done signal). The conditional write-back (R3 AC) prevents a race where a definition goal is set between an instance's creation and its run-start extraction from being overwritten by that extraction.
**Sources**: DES-006 (state-based, marker-free migration detection); R3/R14 acceptance criteria.
**Alternatives Considered**:
- A one-time backfill over all definitions: rejected (R14) — costly, and many definitions may never run again.
**Consequences**:
- Pro: Zero migration surface; existing definitions work unchanged until they next run.
- Con: The first run of a legacy definition pays one extraction call before it begins; subsequent runs reuse the persisted goal.

## System Behavior

### Scenario: a definition with a provided goal

**Given**: the agent calls `create_task` with a `goal`.
**When**: the definition fires and an instance is generated.
**Then**: the instance snapshots the definition goal at creation; the run starts with a goal present, so no extraction runs, no write-back occurs, and the opening turn surfaces that goal. (R1, R2)

### Scenario: `update_task` changes the goal

**Given**: the agent calls `update_task` with a new `goal` on a definition.
**When**: the next instance is generated.
**Then**: that instance snapshots the new goal; instances generated before the edit keep the goal they snapshotted. (R2)

### Scenario: `run_task_now` by-reference, ad-hoc, and override

**Given**: a by-reference `run_task_now` — the instance snapshots the definition's current goal; an ad-hoc `run_task_now` with a `goal` carries it directly with no parent definition; an explicit `run_task_now` `goal` override wins over any definition goal. (R2)

### Scenario: first run of a legacy definition (lazy migration)

**Given**: a definition created before this delta (goal null), and an instance with a snapshotted null goal.
**When**: the run starts.
**Then**: `extractGoal` derives a goal from the task prompt; if usable, it is stored on the instance and written back to the definition (whose goal is still null); the opening turn surfaces the extracted goal. The next run reuses the persisted definition goal and does not re-extract. (R3, R14)

### Scenario: write-back is skipped when the definition goal was set in the meantime

**Given**: an instance was created while its definition's goal was null, and between creation and run-start the definition goal was set (by `update_task` or an earlier instance's write-back).
**When**: this instance's run-start extraction completes.
**Then**: the derived goal is stored on the instance for this run, but the write-back is skipped — the existing definition goal is never clobbered. (R3)

### Scenario: a queued instance created before a write-back extracts its own goal

**Given**: an instance queued before its definition's goal was written back (it snapshotted null).
**When**: it starts later, after the definition goal is now non-null.
**Then**: it uses the goal it snapshotted (null) and extracts its own goal at run start — it does not inherit the definition goal written back after its creation. (R3)

### Scenario: extraction fails or returns an unusable goal

**Given**: `extractGoal` throws, returns unparseable output, or a goal that fails the trim + minimum-length heuristic.
**When**: the run starts.
**Then**: the run proceeds using the task prompt as the goal basis, nothing is persisted, and a later run retries extraction. There is no give-up counter — every subsequent run retries until it produces a usable, persisted goal. (R15)

### Scenario: a valid `completed` declaration

**Given**: the agent calls `update_goal({ status: "completed", goalRestated, evidence, summary })` with all three fields non-empty.
**When**: the loop processes the declaration after the turn.
**Then**: the instance is marked `completed` with `result = summary`, the session is disposed, and the registered post-processors run once against the transcript (memory extraction + workspace persistence). No success notice is emitted automatically. (R6, R10)

### Scenario: an incomplete `completed` declaration is rejected in-tool

**Given**: the agent calls `update_goal({ status: "completed", … })` missing `evidence` (or `goalRestated`/`summary`).
**When**: the tool's `execute` handler runs.
**Then**: it returns an error result telling the agent which field is missing; `pendingDeclaration` is not set; the agent retries within the same run. The loop never sees an invalid declaration. (R6)

### Scenario: a `not_completable` declaration

**Given**: the agent calls `update_goal({ status: "not_completable", reason })`.
**When**: the loop processes the declaration after the turn.
**Then**: the instance is marked `failed` with `result = reason`, and a `warning`-severity failure notice carrying the reason is emitted on the `notify` event. (R7)

### Scenario: a non-terminal turn injects the nudge

**Given**: a turn ends with no terminal declaration and no `ask_user` call.
**When**: the loop prepares the next iteration.
**Then**: it injects the completion nudge as the next prompt; the agent may declare or continue working. (R8)

### Scenario: `ask_user` pauses (unchanged)

**Given**: the agent calls `ask_user`.
**When**: the run returns.
**Then**: the instance suspends to `waiting`, the question is emitted as an `urgent` notice, and a later `respond_to_task` resumes the persistent session — unchanged. The nudge is not injected on an `ask_user` turn. (R12)

### Scenario: the run never declares — the cap is the sole auto-fail

**Given**: the agent never calls `update_goal` (and never pauses via `ask_user`).
**When**: the run reaches the iteration cap.
**Then**: the instance is marked `failed` with `"Max iterations (N) reached without a terminal declaration"` and a `warning`-severity notice is emitted — the sole automatic failure path, a single `fail()` call DLT-134 can intercept. (R9)

### Scenario: `stop_task` cancels (unchanged)

**Given**: `stop_task` cancels a running instance.
**When**: the abort signal fires.
**Then**: the live run is aborted and the instance marked `failed` with a cancellation reason — unchanged; the `update_goal` mechanism does not interfere with cancellation. (R12)
