# Design: DLT-079 - Escape markdown-sensitive characters in Telegram output

**Delta Spec**: [../delta-specs/DLT-079.md](../delta-specs/DLT-079.md)
**Status**: Draft

## Purpose

This document explains the design rationale for this delta: why tool arguments break in Telegram, how inline code wrapping at the markdown source level prevents it, and how the formatting is structured across live tool lines and summaries.

After implementation, the "Detected Impacts" section will guide reconciliation into feature design docs.

## Problem Context

Tool activity lines in the Telegram channel use markdown italics (`*🔧 Globbing **/*.ts*`) before being passed to `convert()` from `telegramify_markdown`. When arguments contain markdown-sensitive characters — `**` in glob patterns, `__` in dunder filenames, backticks in shell commands — `convert()` misinterprets them as formatting:

- `*🔧 Globbing **/*.ts*` → `**` parsed as bold, producing garbled output (`**/.ts*`)
- `*🔧 Reading /src/__init__.py*` → `__` parsed as bold, making `init` appear bold within italics

The REPL channel doesn't have this problem because it renders plain text, not markdown.

**Constraints:**
- The fix must operate at the markdown source level (before `convert()` transforms it to entities)
- REPL behavior must be unaffected — display.py can only change in a backwards-compatible way
- Six tools get code wrapping (Grep, Glob, Bash, Read, Edit, Write); Agent, ToolSearch, unknown/MCP tools are excluded
- Both live tool lines (`handle_tool`) and transition summaries (`handle_text`/`finalize`) must be covered

## Design Overview

Wrap dynamic tool arguments in backticks at the markdown source level. When `convert()` encounters backtick-wrapped text, it produces a `code` entity — the content is preserved verbatim regardless of special characters. This is the same mechanism markdown uses for inline code, and `telegramify_markdown` handles it correctly.

The implementation adds:
1. A `code_wrap()` utility that handles backtick collision
2. Telegram-specific formatter maps for live lines and summaries
3. An optional `summary_map` parameter on the shared `summarize_tool_activity()` function

```
Before (broken):                          After (fixed):
*🔧 Globbing **/*.ts*                    *🔧 Globbing `**/*.ts`*
  → convert() misreads ** as bold           → convert() sees code span, preserves content
  → garbled output                          → italic + code entity rendered correctly
```

## Components

### Implementation Structure

| Layer/Component | Responsibility | Key Decisions |
|-----------------|----------------|---------------|
| `src/tachikoma/telegram.py` | `code_wrap()` utility, `TELEGRAM_TOOL_DISPLAY` and `TELEGRAM_TOOL_SUMMARY` formatter maps, updated `handle_tool()` and summary insertion in `handle_text()`/`finalize()` | `handle_tool()` switches from imported `TOOL_DISPLAY` to local `TELEGRAM_TOOL_DISPLAY`; the `TOOL_DISPLAY` import is removed; `handle_text()`/`finalize()` pass `summary_map=TELEGRAM_TOOL_SUMMARY` to the shared summary function |

### Cross-Layer Contracts

**Integration point — `summarize_tool_activity()`:**

```
# Current signature (unchanged behavior when called without summary_map)
summarize_tool_activity(activities: list[ToolActivity]) -> str

# New signature (backwards-compatible)
summarize_tool_activity(
    activities: list[ToolActivity],
    summary_map: dict[str, Callable[[dict[str, Any]], str]] | None = None,
) -> str
```

When `summary_map` is `None`, `TOOL_SUMMARY` is used (current behavior). The `_TOOL_AGGREGATE` map is always used for counts >2 since aggregated phrases contain no dynamic arguments.

**Telegram calls it as:**

```
summarize_tool_activity(self._tool_activities, summary_map=TELEGRAM_TOOL_SUMMARY)
```

### Shared Logic

- **Grouping, aggregation, phrase joining, capping**: All remain in `summarize_tool_activity()` in display.py — the Telegram side only provides different per-tool formatters, not different aggregation logic
- **`_TOOL_AGGREGATE`**: Shared for both paths — aggregated phrases ("reading 5 files") contain no dynamic arguments and don't need code wrapping
- **`format_tool_name()`**: Shared for MCP tool name formatting in fallback paths

## Modeling

### `code_wrap(text: str) -> str`

Produces a markdown inline code span from arbitrary text:
- If `text` contains no backticks: wraps in single backticks → `` `text` ``
- If `text` contains backticks: wraps in double backticks with space padding → ``` `` `text` `` ```

The space padding rule comes from CommonMark spec: when a code span starts or ends with a backtick, a space is added inside the delimiters to prevent the parser from misreading the boundary. `convert()` strips these padding spaces when producing the `code` entity.

### Formatter maps

**`TELEGRAM_TOOL_DISPLAY`** — live tool line formatters (present-progressive, full paths):

| Tool | Format |
|------|--------|
| Read | `` Reading `{file_path}` `` |
| Grep | `` Searching for `{pattern}` `` |
| Glob | `` Globbing `{pattern}` `` |
| Bash | Prefers description over command: `` `{description}` `` if present, else `` Running: `{command}` `` |
| Edit | `` Editing `{file_path}` `` |
| Write | `` Writing `{file_path}` `` |
| Agent | `Agent: {description}` (no code wrap) |
| ToolSearch | `Searching tools: {query}` (no code wrap) |
| Fallback (unknown/MCP) | `{formatted_name}...` (no code wrap, same as shared) |

Note: The shared `TOOL_DISPLAY["Bash"]` always shows the command. The Telegram variant diverges by preferring the `description` field when present — this matches the Telegram summary behavior and the spec's AC for Bash with description. When both `command` and `description` are present, `description` wins.

Included tools (Read, Grep, Glob, Bash, Edit, Write) apply `code_wrap()` to the extracted argument. The formatter uses `.get(key, "...")` so fallback placeholders (`...`) are also code-wrapped naturally.

**`TELEGRAM_TOOL_SUMMARY`** — summary formatters (present-progressive, basenames):

| Tool | Format | Diff from shared |
|------|--------|------------------|
| Read | `` reading `{basename}` `` | code-wrapped |
| Grep | `` searching for `{pattern}` `` | code-wrapped, no quotes (R6) |
| Glob | `` globbing `{pattern}` `` | code-wrapped, no quotes (R6) |
| Bash | Prefers description: `` `{description}` `` if present, else `` running: `{truncated_cmd}` `` | code-wrapped; same precedence as shared `_format_bash_summary()` |
| Edit | `` editing `{basename}` `` | code-wrapped |
| Write | `` writing `{basename}` `` | code-wrapped |
| Agent | `agent: {description}` | unchanged (no code wrap) |
| ToolSearch | `searching tools` | unchanged |

## Data Flow

### Live tool line path

```
1. ToolActivity event arrives at handle_tool()
2. Check tool_name against TELEGRAM_TOOL_DISPLAY
   ├─ Found (included tool) → formatter extracts argument, applies code_wrap()
   ├─ Found (excluded tool: Agent, ToolSearch) → formatter produces label without code wrap
   └─ Not found → fallback: format_tool_name(name) + "..." (no code wrap)
3. Compose tool line: f"*🔧 {label}*"
4. Store as self._tool_line, flush to Telegram
```

### Summary path

```
1. Tool→text transition detected in handle_text() (or finalize for end-of-response)
2. Call summarize_tool_activity(self._tool_activities, summary_map=TELEGRAM_TOOL_SUMMARY)
3. Inside summarize_tool_activity():
   a. Group activities by tool_name (preserving first-seen order)
   b. For each group:
      ├─ count > 2 → use _TOOL_AGGREGATE (shared, no code wrapping)
      └─ count ≤ 2 → use summary_map (TELEGRAM_TOOL_SUMMARY) per activity
         ├─ Known tool → formatter extracts argument, applies code_wrap()
         └─ Unknown tool → fallback: "used {formatted_name}" (no code wrap)
   c. Cap at 5 phrases, join with commas/"and", capitalize
4. Insert into buffer: f"*🔧 {summary}*"
```

## Key Decisions

### Code wrapping at markdown source level

**Choice**: Apply backtick wrapping to arguments before they enter the markdown buffer, so `convert()` sees them as inline code spans.
**Why**: `convert()` parses standard markdown. Inline code spans are the native markdown mechanism for preventing interpretation of special characters. This works with the library rather than against it — no escaping heuristics, no post-processing of entities.
**Sources**: `telegramify_markdown`'s indexed documentation only covers `markdownify()` (MarkdownV2 string output); the `convert()` function (entities output mode) is not documented. Behavior verified experimentally: `convert()` produces correct `code` entities from backtick-wrapped input, double-backtick with space padding works for content containing backticks, and nested code spans inside italics (`*...\`code\`...*`) produce the expected italic + code entity combination. CommonMark spec section 6.1 (code spans) defines the backtick string matching and space-stripping rules.
**Options Researched**: (1) Escape special characters before `convert()` — fragile, must track all markdown-sensitive chars; (2) Post-process entities after `convert()` — complex, would need to identify and fix garbled ranges; (3) Backtick wrapping at source level — simple, leverages existing markdown semantics.
**Why This Over Alternatives**: The escaping approach is a whack-a-mole problem (new special chars can appear). Post-processing entities is complex and error-prone. Backtick wrapping is the idiomatic markdown solution and has the side benefit of improving readability (monospace font distinguishes arguments from prose).

**Consequences**:
- Pro: Works with the markdown parser, not against it
- Pro: Handles all current and future special characters
- Pro: Improved readability — monospace distinguishes arguments from prose
- Con: Arguments render in monospace font (a visual change, but an improvement)

### Parameterized summary function

**Choice**: Add optional `summary_map` parameter to `summarize_tool_activity()` instead of duplicating grouping logic in telegram.py.
**Why**: The grouping, aggregation, capping, and joining logic (~30 lines) would need to stay in sync if duplicated. A single optional parameter lets Telegram inject its own formatters while reusing all shared logic. The default (`None` → `TOOL_SUMMARY`) preserves REPL behavior exactly.
**Options Researched**: (1) Full reimplementation in telegram.py — strict display.py isolation but duplicates logic; (2) Optional parameter — minimal display.py change, DRY; (3) Post-process summary string with regex — fragile, can't reliably identify argument boundaries.
**Why This Over Alternatives**: The spec was updated to allow this backwards-compatible change. The parameter is additive — it doesn't change any existing call site. Duplication would create a maintenance risk if summary logic evolves (e.g., aggregation thresholds, phrase capping).

**Consequences**:
- Pro: Single source of truth for grouping/aggregation logic
- Pro: Backwards-compatible — no existing call sites change
- Con: display.py gains awareness that formatters can be swapped (minimal coupling)

## System Behavior

### Scenario: Glob pattern with asterisks

**Given**: A Glob tool activity with pattern `**/*.ts`
**When**: `handle_tool()` renders the live line
**Then**: The formatter produces `` Globbing `**/*.ts` ``, which becomes `` *🔧 Globbing `**/*.ts`* ``. `convert()` produces italic entity over the whole line + code entity over `**/*.ts`, preserving the asterisks.
**Rationale**: Without code wrapping, `**` is parsed as bold, destroying the pattern.

### Scenario: Dunder filename

**Given**: A Read tool activity with path `/src/tachikoma/__init__.py`
**When**: `handle_tool()` renders the live line
**Then**: The path is code-wrapped. `convert()` produces a code entity preserving `__init__` verbatim.
**Rationale**: Without code wrapping, `__` is parsed as bold markers.

### Scenario: Bash command with backticks

**Given**: A Bash tool activity with command `` echo `date` ``
**When**: `handle_tool()` renders the live line
**Then**: `code_wrap()` detects backticks in the content, switches to double-backtick wrapping with space padding. `convert()` produces a code entity containing the full command with backticks.
**Rationale**: Single backtick wrapping would collide with the backticks in the command.

### Scenario: Missing tool_input keys (fallback)

**Given**: A Grep tool activity where `tool_input` has no `pattern` key
**When**: The Telegram formatter encounters the missing key
**Then**: The fallback placeholder `...` is still code-wrapped: `` Searching for `...` ``.
**Rationale**: Consistent visual treatment — all included tools show code-formatted arguments.

### Scenario: Aggregated summary (>2 uses)

**Given**: A tool→text transition with 5 Read activities
**When**: `summarize_tool_activity()` generates the summary
**Then**: The aggregated form is used: `"reading 5 files"`. No code wrapping is applied.
**Rationale**: Aggregated phrases contain counts, not dynamic arguments — no special characters to protect.

### Scenario: Agent tool (excluded)

**Given**: An Agent tool activity with description "research codebase patterns"
**When**: `handle_tool()` renders the live line
**Then**: The description is NOT code-wrapped: `*🔧 Agent: research codebase patterns*`.
**Rationale**: Agent descriptions are human-written prose, not file paths or patterns. Code formatting would look odd.

### Scenario: REPL rendering (unchanged)

**Given**: The REPL channel renders tool activity
**When**: Displaying a Grep with pattern `git.*push`
**Then**: Output is unchanged — `Searching for 'git.*push'` with no backtick wrapping. `summarize_tool_activity()` is called without `summary_map`, so it uses `TOOL_SUMMARY` as before.
**Rationale**: R4 — REPL behavior is preserved by the default parameter.

### Scenario: Mixed summary with code-wrapped and aggregated phrases

**Given**: A tool→text transition with 1 Grep (`config`) and 3 Read activities
**When**: The summary is rendered in Telegram
**Then**: Output is `` *🔧 Searching for `config` and reading 3 files* ``. The Grep phrase uses the Telegram formatter (code-wrapped, no quotes). The Read group uses the shared aggregated form (just a count).
**Rationale**: The `summary_map` parameter only affects the per-item formatter path (count ≤2). The aggregation path (count >2) always uses `_TOOL_AGGREGATE`.

## Notes

- Verified `convert()` behavior experimentally: backtick-wrapped content produces correct `code` entities; double-backtick wrapping with space padding works for content containing backticks; nested code inside italics produces the expected entity combination
- `code_wrap()` uses double backticks as the escalation for content containing backticks. CommonMark spec (section 6.1) allows arbitrarily long backtick strings, but double backticks cover all practical tool argument cases — tool commands with triple backticks are not a realistic scenario
- The `_TOOL_AGGREGATE` map is intentionally not parameterized — aggregated phrases are counts, not dynamic content
- Existing tests for `summarize_tool_activity()` in display.py should pass unchanged since the new `summary_map` parameter defaults to `None` (current behavior)
