## Purpose

This document explains the design rationale for DLT-048: how the plugin system is modeled and integrated, how plugin sources are materialized and reconciled, how the plugin loader hands off skill paths to the existing skills subsystem, and how the namespacing model preserves isolation between plugin sources.

After implementation, the "Detected Impacts" section will guide reconciliation into feature design docs (`docs/feature-designs/agent/`, `docs/feature-designs/configuration/`, and a new `docs/feature-designs/plugins/`).

## Shape

| Part | Mechanism | Flag |
|------|-----------|:----:|
| **S1** | `[plugins.<alias>]` config schema in `config.py`: Pydantic models for git-source (`git`, `subdir`, `ref` fields) and local-path-source (`path` field) variants. Validates `ref`-required for git, mutual-exclusion of source types, absolute-path requirement for local paths, and alias regex (`[a-z0-9][a-z0-9-]*`). | |
| **S2** | Plugin manifest parser: reads either Tachikoma-native `tachikoma-plugin.toml` or CC's `.claude-plugin/plugin.json` and produces a unified internal `PluginManifest` model (metadata + skill directory paths). Native takes precedence when both are present. CC non-skill contributions (commands, mcpServers, agents, hooks) are silently ignored with one INFO-level log entry per skipped contribution type per plugin. | |
| **S3** | Plugin source materializer: for git sources, performs `git clone --depth 1` of the repo at the configured `ref` into a temp location, copies the configured `subdir` into a sibling directory (`.tachikoma/plugins/<alias>.new/`), and atomic-renames over the existing `.tachikoma/plugins/<alias>/`; for local-path sources, copies the configured path's contents through the same atomic-rename mechanism. | |
| **S4** | Plugin reconciliation step: walks `[plugins]` config; for each entry, always re-materializes the plugin via S3; removes orphan directories not declared in config; on materialization failure, retains a stale copy if one exists with a valid manifest matching the alias (`stale-fallback` status), otherwise records `failed`. | |
| **S5** | Plugin discovery: scans `.tachikoma/plugins/` after reconciliation, parses each plugin's manifest via S2, validates structure, builds a list of loaded plugins with their contributions and statuses. Per-plugin failure isolation. | |
| **S6** | Plugins bootstrap hook: ordered before the skills hook in the registered-hooks list. Reconciles + discovers plugins (S4 + S5), then writes the resulting plugin skill paths to `ctx.extras` (e.g., `ctx.extras["plugin_skill_paths"]`) for the skills hook to consume when constructing the `SkillRegistry`. Also appends `.tachikoma/plugins/` to workspace `.gitignore` idempotently. | |
| **S7** | `SkillRegistry` source extension with namespacing: plugin skill directories are added as registry sources where each plugin's skills are registered under namespaced keys of the form `<alias>:<skill-name>`. Default namespace (built-in + workspace) retains existing last-wins precedence; plugin namespaces are isolated and cannot collide with the default namespace or with each other. | |
| **S8** | Plugin manager / state: in-memory model of currently loaded plugins exposing query (for `list_plugins`), install (validate-then-write source spec to config + targeted reconciliation + publish `SkillsChanged` event), and remove (config write-back + directory cleanup + publish `SkillsChanged` event) operations. Serializes concurrent operations against the install directory and config file. | |
| **S9** | Plugin MCP tools server: factory function building three tools — `install_plugin` (accepts source spec + optional `alias`; errors on collision), `list_plugins` (returns alias, source, ref, status, diagnostic, contributed-skill-names), `remove_plugin` (accepts alias). Closes over the plugin manager (S8). | |
| **S10** | `.gitignore` registration for `.tachikoma/plugins/` — implemented inside S6's hook, idempotent append. | |
| **S11** | Failure isolation infrastructure: per-plugin try/except boundaries in materialization, discovery, manifest parsing, and registry registration. Structured logging tagged by plugin alias for diagnostics. | |
| **S12** | Skill-name resolution updates in `SkillRegistry`: lookup-by-namespaced-name; classifier candidate-list emission of namespaced names alongside bare names for default-namespace skills; dependency resolver namespace handling for plugin skills. | ⚠️ |

### Flagged Unknowns

#### S12 — Dependency resolution semantics for plugin skills with bare-name `depends_on`

When a plugin skill's `SKILL.md` declares `depends_on: [some-skill]` with a bare (non-namespaced) name, how should the resolver look it up? The plugin author does not know the user-assigned alias, so they cannot reliably write `<their-alias>:<sibling>`. Three candidate rules:

- **(i) Own-namespace-first, default-namespace fallback.** Bare `some-skill` first looks up `<plugin-alias>:some-skill`; if not present, falls back to default-namespace `some-skill`. Most ergonomic for plugin authors who want to depend on sibling plugin skills without knowing the alias, with default-namespace deps still possible.
- **(ii) Default-namespace-only.** Bare `some-skill` always resolves in the default namespace (built-in + workspace). Plugin-internal sibling deps require an explicit prefix the author cannot reliably write — effectively forbidding intra-plugin deps via bare names. Simplest rule but least flexible.
- **(iii) Explicit-prefix-required.** Bare names are invalid inside plugin skill `depends_on`; authors must write a namespaced name. Plugin-internal sibling deps need a sentinel like `:sibling` (empty-namespace prefix means "this plugin"). Most explicit but verbose and requires authoring discipline.

Resolution requires investigating: (a) how plugin skills typically structure their internal dependencies (e.g., a skill bundle that splits responsibilities across multiple SKILL.md files), (b) whether existing CC plugins author skills with intra-plugin deps and what convention they assume, and (c) how the change interacts with skills.md R32 cycle handling and last-wins precedence.

The chosen rule must be captured in the skills feature spec (R32 update) and reflected in the `SkillRegistry` resolver implementation.
