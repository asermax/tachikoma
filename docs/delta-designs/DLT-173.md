# Design: DLT-173 - Plugin Lifecycle Hooks and Event Bus Access

**Delta Spec**: [../delta-specs/DLT-173.md](../delta-specs/DLT-173.md)
**Status**: Draft

## Purpose

This document explains the design rationale for this delta: the modeling choices, data flow, system behavior, and architectural approach.

After implementation, the "Detected Impacts" section will guide reconciliation into feature design docs.

## Problem Context

The plugin system currently supports skills only — plugins declare skill directories registered into the `SkillRegistry` at startup. There is no mechanism for plugins to run initialization code (e.g., establishing external connections, validating prerequisites) or to react to system events (e.g., coordinator idle, notifications, other plugin lifecycle changes).

**Constraints:**
- **Fail-safe.** Broken plugins must never block other plugins or application startup (consistent with the existing per-plugin error isolation pattern).
- **CC compatibility.** CC plugins declaring `hooks` or `events` contributions install successfully but those contributions are silently ignored.
- **Subscribe only.** Plugins cannot dispatch custom events — they receive events, not produce them.
- **No new system events.** This delta exposes existing events to plugins; it does not create new event types.
- **Handler isolation.** Each plugin's init hooks and event handlers run independently — failures are caught, logged, and do not affect other plugins.

**Interactions:**
- **Manifest parsing** — gains `[hooks]` and `[events]` sections with module-name entry points.
- **Loader** — extends `discover()` with handler validation (file exists, imports, callable present, correct signature, known event types).
- **Bootstrap / `__main__.py`** — init hooks run after `bootstrap.run()` completes, before `channel.run()` starts.
- **PluginManager** — `install()` runs init hooks and subscribes events before `PluginInstalled` dispatch; `remove()` unsubscribes during `PluginRemoving` phase.
- **Event bus (ADR-009)** — plugin handlers subscribe via `bus.on()`; bubus has no `off()` so unsubscription uses an active-flag wrapper.

## Design Overview

The design extends the existing plugin loading pipeline with three capabilities layered onto the current discovery → manager → lifecycle flow:

1. **Handler resolution and validation** — during `discover()`, declared hook/event entry points are validated end-to-end (file exists, module imports, expected callable with correct signature, event type is known). Validated callables are stored on the `LoadedPlugin` record.

2. **Init hook execution** — after bootstrap completes and before the channel starts, loaded plugins' init hooks run sequentially in alias alphabetical order with 30-second timeout and per-plugin error isolation. Successful init enables event subscriptions; failed init means the plugin runs without event handlers.

3. **Event subscription management** — after a successful init hook (or immediately if no init hook), handlers are subscribed on the event bus via `bus.on(EventType, wrapped_handler)`. The wrapper provides error isolation, injects `PluginContext`, and checks an active flag. On plugin removal, the flag is deactivated (bubus has no `off()` API).

New modules: `plugins/context.py`, `plugins/registry.py`, `plugins/lifecycle.py`. Modified modules: `plugins/manifest.py`, `plugins/loader.py`, `plugins/manager.py`, `__main__.py`.

```
┌──────────────────────────────────────────────────────────────────┐
│ plugins/ package (extensions)                                    │
│  manifest.py    +hooks dict, +events dict on TachikomaManifest   │
│  loader.py      +handler validation in discover()                │
│  context.py     PluginContext frozen dataclass (NEW)             │
│  registry.py    auto-discovered event type registry (NEW)        │
│  lifecycle.py   init executor + subscribe/unsubscribe (NEW)      │
│  manager.py     install → init+subscribe, remove → unsubscribe   │
├──────────────────────────────────────────────────────────────────┤
│ __main__.py                                                      │
│  After bootstrap.run(): run_plugin_init_hooks(manager, bus)      │
├──────────────────────────────────────────────────────────────────┤
│ bubus EventBus                                                   │
│  bus.on(EventType, wrapped_handler)  — subscribe                │
│  wrapper._deactivate()               — unsubscribe (flag-based) │
└──────────────────────────────────────────────────────────────────┘
```

## Shape

| Part | Mechanism | Flag |
|------|-----------|:----:|
| **S1** | Extend `TachikomaManifest` and `PluginManifest` with `hooks` and `events` fields; resolve module names to file paths during parsing | |
| **S2** | Handler validator in loader: verify each declared hook/event entry — file exists, module imports, expected function present with correct signature; validate event type names against auto-discovered registry | |
| **S3** | Event type registry: auto-discovery via recursive `BaseEvent.__subclasses__()` walk across explicitly-imported event modules, deriving snake_case names from class names (e.g., `CoordinatorIdle` → `coordinator_idle`) | |
| **S4** | Frozen `PluginContext` dataclass: carries validated config dict, event bus reference, plugin alias, and install path | |
| **S5** | Init hook executor: runs in `__main__.py` after `bootstrap.run()` completes, before `channel.run()`; iterates loaded plugins alphabetically, calls each init function with PluginContext, wraps in try/except with 30-second `asyncio.timeout()` | |
| **S6** | Event subscription registrar: after init hooks complete (or immediately for plugins without init hooks), subscribes handlers on event bus via `bus.on(EventType, wrapped_handler)` where the wrapper provides error isolation and passes PluginContext | |
| **S7** | Hook lifecycle manager: orchestrates init + subscribe at startup (in `__main__.py` post-bootstrap), runtime install (run init + subscribe before `PluginInstalled` dispatch), and runtime remove (unsubscribe via active-flag deactivation during `PluginRemoving` phase) | |

| Layer/Component | Responsibility | Key Decisions |

| `src/tachikoma/__main__.py` (modified) | Calls `run_plugin_init_hooks()` after `bootstrap.run()` completes, before channel construction | Post-bootstrap timing ensures all subsystems are initialized; runs only for plugins loaded at startup (runtime installs handled by manager) |

### Cross-Layer Contracts

**Startup lifecycle contract (`__main__.py` → lifecycle):**

```
__main__.py (after bootstrap.run())
    ├── manager = bootstrap.extras["plugin_manager"]
    ├── bus = bootstrap.extras["event_bus"]
    └── await run_plugin_init_hooks(manager.loaded_plugins(), bus)
            ├── Sort loaded plugins by alias (alphabetical)
            ├── For each plugin (status="loaded"):
            │   ├── If init_hook:
            │   │   ├── Create PluginContext(config, bus, alias, install_path)
            │   │   ├── await asyncio.timeout(30): init_hook(ctx)
            │   │   ├── On success → subscribe_plugin_events(plugin, bus)
            │   │   └── On failure → log ERROR, skip subscriptions
            │   └── If no init_hook but has event_handlers:
            │       └── subscribe_plugin_events(plugin, bus)
            └── Return
```

**Runtime install contract (`PluginManager._install_locked`):**

```
install(source, alias)
    ├── ... existing materialize + validate ...
    ├── plugin = LoadedPlugin(..., init_hook=..., event_handlers=...)
    ├── _loaded[alias] = plugin
    ├── NEW: if plugin.init_hook:
    │   ├── Create PluginContext
    │   ├── await _invoke_with_timeout(plugin.init_hook, ctx, timeout=30)
    │   ├── On success → subscribe_plugin_events(plugin, bus)
    │   └── On failure → log WARNING (install succeeds, events not registered)
    ├── NEW: elif plugin.event_handlers:
    │   └── subscribe_plugin_events(plugin, bus)
    └── await bus.dispatch(PluginInstalled(alias, plugin))
```

**Runtime remove contract (`PluginManager._remove_locked`):**

```
remove(alias)
    ├── ... existing existence check ...
    ├── await bus.dispatch(PluginRemoving(alias, namespaced_skills))
    ├── NEW: unsubscribe_plugin_events(plugin)
    │   └── wrapper._active = False  (for each registered wrapper)
    ├── ... existing config removal + directory deletion ...
    └── await bus.dispatch(PluginRemoved(alias))
```

### Shared Logic

- **`PluginContext`**: Shared between init hooks and event handlers — both receive the same frozen context. Created once per plugin at lifecycle execution time.
- **`_invoke_handler(func, *args)`**: Shared helper that calls a handler and awaits the result if it's a coroutine. Used by both init hook executor and event wrapper.
- **`build_event_registry()`**: Used by loader during validation and by tools if exposing available events to the agent.
- **Module name validation**: Bare-name check shared between manifest parsing (values in `hooks`/`events`) and path resolution. Reuses existing path-traversal protection patterns.

### Handler resolution

```
HandlerSpec (internal, not persisted)
├── For hooks:
│   ├── manifest key: hook type name (e.g., "init")

│   ├── manifest key: event type name (e.g., "coordinator_idle")

│   └── expected parameter count: 2
```

    │   ├── parse_manifest(plugin_dir)
    │   │   └── TachikomaManifest validated (hooks/events module names checked)
    │   ├── validate skill dirs, config (existing)
    │   ├── NEW: _validate_handlers(manifest, plugin_dir)
    │   │   ├── For each (hook_type, module_name) in manifest.hooks:
    │   │   │   ├── Resolve plugin_dir / "hooks" / {module_name}.py

    │   │   │   ├── Check module has {hook_type} callable (e.g., "init")

## Key Decisions

### Auto-discovery event type registry

**Choice**: Build the event type registry by importing all known event modules, then walking `BaseEvent.__subclasses__()` recursively and deriving snake_case names from class names.
**Why**: Avoids maintaining a manual mapping of string names to classes. Adding a new event type to any imported module automatically makes it available to plugins. The module import list is the only thing that needs updating when event modules are added.
**Alternatives Considered**:
- Static dict with explicit name → class mapping: Simpler but every new event requires updating the dict. Chosen approach trades one explicit list (modules to import) for automatic mapping generation.
- Fully automatic discovery without module imports: Fragile — requires all event modules to be imported before the registry is accessed, which depends on import ordering.

**Sources**: Python 3.12 documentation on `__subclasses__()` (from doc-researcher); bubus source inspection showing event class names as handler keys.
**Consequences**:
- Pro: New event types are automatically available to plugins with no registry changes.
- Pro: snake_case convention matches TOML key style and is predictable for plugin authors.
- Con: Adding a new event module requires adding it to the registry's import list.
- Con: Event class names must follow CamelCase convention for correct snake_case derivation.

### Post-bootstrap init hook execution in `__main__.py`

**Choice**: Init hooks run after `bootstrap.run()` completes, before `channel.run()` starts, orchestrated by a `run_plugin_init_hooks()` call in `__main__.py`.
**Why**: Guarantees all subsystems (sessions, tasks, skills, database) are fully initialized before plugin init hooks run. Plugin init hooks may need to interact with these subsystems (e.g., checking session state, scheduling tasks). Running inside bootstrap would limit access to only earlier-initialized subsystems.
**Alternatives Considered**:
- End of `plugins_hook` (during bootstrap): Simplest, but plugins can't access subsystems that haven't been bootstrapped yet (sessions, tasks, etc.).
- Separate bootstrap hook registered last: Same timing as chosen approach but adds another hook to the bootstrap registry for what is fundamentally a post-bootstrap concern.

**Consequences**:
- Pro: Plugins have access to all initialized subsystems via the event bus.
- Pro: Clean separation — bootstrap handles subsystem initialization, post-bootstrap handles plugin lifecycle.
- Con: Init hooks are not visible in the bootstrap hook registry. Mitigated by the explicit call site in `__main__.py`.

### LoadedPlugin field extensions

**Choice**: Add `init_hook: Callable | None` and `event_handlers: dict` fields directly to `LoadedPlugin`.
**Why**: `LoadedPlugin` already carries manifest-level data and mutable runtime state (`contributed_skills`). Handler callables are resolved at discovery time alongside existing validation. A separate wrapper type would add complexity without clear benefit.
**Alternatives Considered**:
- Separate `ResolvedPlugin` dataclass wrapping `LoadedPlugin`: Cleaner separation but adds another type to thread through the system, and the lifecycle module would need to handle both types.

**Consequences**:
- Pro: Single type flows through the entire plugin pipeline (discovery → manager → lifecycle).
- Pro: Consistent with existing pattern of `contributed_skills` being populated after discovery.
- Con: `LoadedPlugin` gains two more fields. Mitigated: both are optional/default-empty.

### Active-flag wrapper for event unsubscription

**Choice**: Wrap each plugin event handler in a closure that checks an `_active` flag before dispatching. On plugin removal, set `_active = False` on all registered wrappers.
**Why**: bubus `EventBus` has no `off()` / `remove()` / `unsubscribe()` method. The handlers dict is a `defaultdict(list)` keyed by event class name, but directly manipulating it is fragile and couples to bubus internals. The active-flag wrapper is self-contained and doesn't depend on internal data structures.
**Alternatives Considered**:
- Direct `bus.handlers[event_key].remove(handler)`: Requires knowing bubus's internal key scheme (class `__name__` strings) and modifying internal state. Fragile across bubus versions.
- Maintain a separate mapping of subscribed handlers and re-register all non-removed handlers on removal: Complex, error-prone, and doesn't actually remove from the bus.

**Sources**: bubus `EventBus` source inspection — confirmed no `off()` method; `handlers` is `defaultdict(list)` keyed by event class `__name__`.
**Consequences**:
- Pro: No coupling to bubus internals.
- Pro: Simple implementation — each wrapper is self-contained.
- Con: Minor memory retention — deactivated wrappers remain in the bus's handler list. Acceptable because plugin removal is rare.
- Con: Dispatched events still invoke the wrapper (which immediately returns). Negligible overhead.

### Handler validation during discovery (not manifest parsing)

**Choice**: Handler entry points (file existence, import, callable check, signature validation) are validated during `discover()` in the loader, not during `parse_manifest()`.
**Why**: Manifest parsing is a pure TOML/JSON concern — it validates syntax and basic structure. Handler validation requires filesystem access (file exists), dynamic imports (importlib), and event registry lookups. These are loader concerns, not manifest concerns. Keeping manifest parsing pure also means CC plugin manifests parse successfully without needing the event registry.
**Alternatives Considered**:
- Validation during manifest parsing: Couples manifest parsing to filesystem and importlib. CC manifests with hooks/events would need the registry to detect and ignore them, adding unnecessary complexity.

**Consequences**:
- Pro: Clean separation — manifest parsing handles syntax, loader handles semantics.
- Pro: Event type validation uses the fully-built registry (all event modules imported).
- Pro: CC manifest handling is unchanged (hooks/events in CC JSON are detected by `_CC_CONTRIBUTION_TYPES`).

### Support for sync and async handlers

**Choice**: Both init hooks and event handlers may be sync or async. The lifecycle module calls the function and checks `asyncio.iscoroutine(result)`, awaiting if needed.
**Why**: Plugin authors may write simple sync handlers (e.g., `def init(ctx): ctx.event_bus.on(...)`) or async handlers (e.g., `async def init(ctx): await some_async_setup()`). Supporting both removes a friction point for plugin authors without adding complexity.
**Alternatives Considered**:
- Async-only: Forces plugin authors to write `async def` even for trivial handlers. Unnecessary friction.
- Sync-only: Prevents async operations in handlers (e.g., making HTTP calls during init).

**Sources**: Python `asyncio.iscoroutine()` documentation (from doc-researcher); `bubus` `on()` accepts both sync and async handlers (from source inspection).
**Consequences**:
- Pro: Plugin authors can choose the style that fits their needs.
- Con: `asyncio.timeout()` only enforces timeouts for async handlers. Sync blocking handlers bypass the timeout. Documented as a known limitation. Plugin authoring guidance should recommend async handlers when timeout protection is needed.

### Path resolution convention: `hooks/` and `events/` directories

**Choice**: Module names in `[hooks]` and `[events]` are resolved as `{hooks|events}/{module_name}.py` relative to the plugin install directory.
**Why**: Mirrors the convention used by skill directories — plugin authors declare a directory-relative path, not an absolute one. Using dedicated `hooks/` and `events/` directories keeps plugin organization clean and makes the distinction between hook modules and event modules visible at the filesystem level.
**Alternatives Considered**:
- Single `handlers/` directory for both hooks and events: Less organized — harder to tell which modules handle which concern.
- Flat layout (module names resolve to plugin root): Risks collision with other plugin files.

**Consequences**:
- Pro: Clear directory convention — `hooks/` for lifecycle hooks, `events/` for event handlers.
- Pro: Consistent with existing `skills/` directory convention.
- Con: Plugin authors must create these directories. Mitigated: discovery fails with a clear diagnostic if the expected file doesn't exist.

## System Behavior

### Invariants

1. **Init-before-subscribe**: Event subscriptions are only registered after a successful init hook. Plugins without init hooks have events registered immediately.
2. **Sequential init**: Init hooks run one at a time in alphabetical order by alias. No parallel execution.
3. **Per-plugin error isolation**: Init hook failures and event handler failures are logged and contained — they never affect other plugins or application startup.
4. **No dispatch capability**: `PluginContext` provides the event bus reference for subscribing to events, but plugins have no mechanism to dispatch custom events.
5. **Handler validation is complete**: A plugin with invalid handlers (missing file, import error, wrong signature, unknown event type) fails at discovery with a diagnostic — no partial handler registration.
6. **Unsubscription is deactivation**: Removed plugins' event wrappers become no-ops but remain in the bus's handler list.

### Scenario: Plugin with init hook and event subscriptions (happy path)

**Given**: A plugin with `[hooks] init = "init"` and `[events] coordinator_idle = "on_idle"`. Both handler files exist and are valid.
**When**: Startup completes.
**Then**: Init hook runs with PluginContext. On success, `on_idle` handler subscribed to `CoordinatorIdle`. Subsequent `CoordinatorIdle` events invoke the handler.
**Rationale**: Full lifecycle — init prepares plugin, events keep it reacting.

### Scenario: Init hook raises exception

**Given**: Plugin A's init hook raises `ValueError`. Plugin B has a working init hook.
**When**: Init hooks execute.
**Then**: Plugin A's error logged at ERROR level. Plugin A's event subscriptions NOT registered. Plugin B's hook runs normally. Application startup proceeds.
**Rationale**: Per-plugin isolation — one plugin's failure is contained.

### Scenario: Init hook exceeds 30-second timeout

**Given**: Plugin's init hook is async and takes 45 seconds.
**When**: `asyncio.timeout(30)` fires.
**Then**: `TimeoutError` caught, WARNING logged with plugin alias and timeout duration. Plugin's event subscriptions not registered.
**Rationale**: Timeout prevents a stuck plugin from blocking startup indefinitely.

### Scenario: Plugin with no init hook but with event subscriptions

**Given**: A plugin with `[events] notification = "on_notify"` but no `[hooks]` section.
**When**: Startup lifecycle runs.
**Then**: No init hook called. Event handler subscribed immediately.
**Rationale**: Init hooks are optional. Event subscriptions work independently.

### Scenario: Event handler raises exception during dispatch

**Given**: Plugin A's `handle` raises during `CoordinatorIdle` dispatch. Plugin B also subscribes to `CoordinatorIdle`.
**When**: Event is dispatched.
**Then**: Plugin A's error logged at ERROR level with plugin alias and event type. Plugin B's handler still invoked. Dispatch completes normally.
**Rationale**: Event handler errors are isolated per-plugin per-handler.

### Scenario: Plugin removed at runtime

**Given**: Plugin with active event subscriptions.
**When**: `remove_plugin` runs.
**Then**: `PluginRemoving` dispatched. Event wrappers deactivated (`_active = False`). Config removed, directory deleted. `PluginRemoved` dispatched.
**Rationale**: Clean removal — deactivation ensures no further handler invocations even if the bus still holds the wrapper reference.

### Scenario: Plugin installed at runtime with init hook

**Given**: `install_plugin` called for a plugin declaring `[hooks] init = "init"`.
**When**: Installation completes.
**Then**: Materialize + validate succeeds. Init hook runs. On success, event subscriptions registered. `PluginInstalled` dispatched (skills listener registers skills).
**Rationale**: Runtime install mirrors startup lifecycle — init first, then subscribe, then announce.

### Scenario: CC plugin with hooks contribution

**Given**: A CC plugin with `"hooks": {"init": "init.py"}` in `plugin.json`.
**When**: Manifest parsed.
**Then**: `"hooks"` detected as an ignored CC contribution type. INFO log emitted. Plugin loads normally with no hooks support.
**Rationale**: Consistent with existing CC contribution handling.

### Scenario: Unknown event type name in manifest

**Given**: `[events] unknown_event = "handler"` in a Tachikoma-native manifest.
**When**: Handler validation runs during discovery.
**Then**: Plugin fails with diagnostic: "Unknown event type 'unknown_event'. Valid types: coordinator_idle, notification, ..."
**Rationale**: Fail-fast — invalid event references are caught early with a helpful error.

### Scenario: Handler module with wrong signature

**Given**: `events/on_idle.py` with `def handle(event, ctx, extra):` (3 params instead of 2).
**When**: Handler validation runs during discovery.
**Then**: Plugin fails with diagnostic: "Event handler 'handle' in events/on_idle.py must accept exactly 2 parameters, got 3".
**Rationale**: Strict signature validation prevents runtime errors from mismatched handler signatures.

### Scenario: Plugin whose init hook previously failed receives events

**Given**: Plugin A's init hook failed at startup.
**When**: `CoordinatorIdle` event is dispatched.
**Then**: Plugin A's event handlers are NOT invoked (subscriptions were not registered).
**Rationale**: Init failure means the plugin didn't complete initialization — event subscriptions are gated on successful init.

## Notes

- The handler import mechanism uses `importlib.util.spec_from_file_location` + `module_from_spec` (per Python 3.12 stdlib docs, confirmed via doc-researcher). Module names are registered in `sys.modules` using a unique key (`tachikoma_plugin.{alias}.{hooks|events}.{module_name}`) to avoid collisions.
- Signature validation counts positional-or-keyword parameters only (excludes `*args`, `**kwargs`, keyword-only params), matching the spec's "accepts N arguments" language.
- The `asyncio.timeout()` approach (Python 3.11+) only enforces timeouts for async handlers. Sync blocking handlers are not timeout-protected. This is documented as a known limitation.
- bubus uses event class `__name__` as the handler key (confirmed via source inspection). The registry's snake_case derivation matches this convention.
