# Design: DLT-061 - Apply Agent Update

**Delta Spec**: [../delta-specs/DLT-061.md](../delta-specs/DLT-061.md)
**Status**: Draft

## Purpose

This document explains the design rationale for this delta: the modeling choices, data flow, system behavior, and architectural approach.

After implementation, the "Detected Impacts" section will guide reconciliation into feature design docs.

## Problem Context

Tachikoma can check for updates (DLT-045) but cannot apply them from within the running application. Operators must manually run `uv tool upgrade tachikoma-agent` in a separate terminal. This delta closes the loop: the agent invokes an `apply_update` MCP tool, the upgrade runs, and the process restarts itself in-place — preserving the same terminal, tmux session, and PID.

Constraints:
- The MCP tool runs inside the SDK's tool execution context, but `os.execv` must happen after full async cleanup (event loop, I/O flushes, database close).
- `uv tool upgrade` does not produce machine-readable output or distinct exit codes for "upgraded" vs "already up to date."
- Editable/development installs (`uv pip install -e .`) are incompatible with `uv tool upgrade` — must be detected and reported.
- `os.execv` replaces the process immediately; all async resources must be released before the call.

## Design Overview

Add an `apply_update` MCP tool to the existing update tools server. The tool detects editable installs, runs `uv tool upgrade`, and on success fires a `RestartRequested` event on the event bus. Channels subscribe to this event and exit their run loops. After the channel returns, the coordinator performs its normal clean shutdown, the main `finally` block runs all cleanup, and then — after everything is torn down — `os.execv` replaces the process in-place.

The agent is made aware of both update tools through a brief `# Updates` section added to the system preamble.

### Cross-Layer Contracts

**Event Contract**:
```
RestartRequested(BaseEvent[None])
  — No payload. Restart is unconditional once fired — the channel doesn't need
    to know why it's exiting, only whether to exit for restart vs normal shutdown.
  — Fired by: apply_update MCP tool via bus.emit()
  — Consumed by: REPL, TelegramChannel (in run())
  — Handler behavior: set self._restart_requested = True, then trigger run-loop exit
```

**Tool Result Contract**:
```
apply_update() → dict
  Success: { content: [{ type: "text", text: "Upgrade successful: {old_version} → {new_version}\nRestarting..." }] }
  Already up to date: { content: [{ type: "text", text: "Already running the latest version: {version}" }] }
  Editable install: { content: [{ type: "text", text: "Cannot update: tachikoma-agent is running from an editable/development install. Self-update only works for tool installs (uv tool install). To update, pull the latest source and reinstall." }] }
  Failure: { content: [{ type: "text", text: "Upgrade failed (exit code {code}):\n{stderr}" }] }
```

**Integration Points**:
- `apply_update` tool → `bus.dispatch(RestartRequested())` → channel event handlers
- Channel `_restart_requested` attribute → main loop after `channel.run()` returns
- Main loop → `os.execv` after full cleanup

### Shared Logic

- **Editable install detection** (`updates/apply.py`): shared between `apply_update` tool and potentially future CLI commands. Uses `importlib.metadata.distribution("tachikoma-agent").read_text("direct_url.json")` per PEP 610. Returns the parsed JSON dict; the caller checks `dir_info.editable`. Missing or malformed file → assume non-editable, proceed with upgrade.
- **Version capture** (`updates/apply.py`): old version captured via `importlib.metadata.version("tachikoma-agent")` before `subprocess.run`. After successful upgrade, same call returns the new version (since `uv tool upgrade` updates the metadata in-place). The handler compares both to detect change. More reliable than parsing `uv`'s stdout, which may change format between versions.

## Key Decisions

### Restart signaling via event bus + channel attribute

**Choice**: The MCP tool fires a `RestartRequested` event on the shared `EventBus`. Channels subscribe and set a `_restart_requested` attribute on themselves, then exit their run loops. The main loop checks the attribute after `channel.run()` returns.

**Why**: The MCP tool runs deep inside the SDK's tool execution context — it cannot call `os.execv` directly (async resources are still live) or cancel the channel's run loop. The event bus provides a clean decoupling: the tool only signals intent, channels decide how to exit, and the main loop decides whether to execv. The channel attribute survives cleanup (unlike the event, which is consumed and gone by the time the bus is stopped in the `finally` block).

**Alternatives Considered**:
- **Module-level flag only**: Simpler, but the flag alone cannot stop the channel's run loop (the REPL blocks on `prompt_async`). The event provides the trigger; the attribute provides the memory.
- **Exception propagation**: Raise a `RestartRequested` exception from the MCP tool. Rejected because it would abort the current message exchange mid-stream, violating the spec requirement that the current exchange finishes before restart.
- **Coordinator mediation**: Have the coordinator detect a flag and initiate channel shutdown. Rejected because the coordinator has no concept of process lifecycle and shouldn't gain one — it's a message orchestrator, not a process manager.

**Consequences**:
- Pro: Clean separation of concerns — tool signals, channel exits, main execvs
- Pro: Uses the existing event bus pattern (same as `BufferedDelivery`, `Notification`)
- Con: Both channels need restart awareness (small subscription handler in each)

### os.execv after the finally block

**Choice**: `os.execv(sys.argv[0], sys.argv)` is called after the `finally` block in `run()` completes, as the last thing before the function returns.

**Why**: The `finally` block stops the buffer, cancels scheduler tasks, shuts down the background runner, stops the event bus, and closes the database. All async resources must be released before `os.execv` replaces the process. Placing execv after the finally block guarantees clean shutdown identical to the normal quit flow.

**Sources**: Python docs `os.execv` — "These functions all execute a new program, replacing the current process; they do not return." On Unix, `execv` inherits file descriptors that haven't been closed, making prior cleanup essential. For `uv tool install`, `sys.argv[0]` is the console script path (e.g., `/home/user/.local/bin/tachikoma`) which `os.execv` can execute directly. For `python -m tachikoma`, `sys.argv[0]` is the `__main__.py` path, also directly executable.

**Alternatives Considered**:
- **execv inside the finally block**: Would skip subsequent cleanup steps (bus stop, DB close) if execv runs before them. Fragile ordering.
- **execv before the finally block**: Coordinator cleanup hasn't run yet. Active sessions wouldn't be closed.

**Consequences**:
- Pro: Full clean shutdown guaranteed — identical to pressing 'q' in REPL
- Pro: No resource leaks (all async resources released before process replacement)
- Con: Slightly longer restart time (full cleanup sequence), but this is necessary for correctness

### Editable install detection via direct_url.json (PEP 610)

**Choice**: Read `direct_url.json` from the distribution metadata via `importlib.metadata.distribution("tachikoma-agent").read_text("direct_url.json")`. If the JSON contains `"dir_info": {"editable": true}`, report that updates are not available for editable installs.

**Why**: `uv tool upgrade` only works for tool installs (`uv tool install`). Editable installs (`uv pip install -e .`) are development setups where the source code is linked directly. Running `uv tool upgrade` on an editable install either fails silently or does nothing useful. Detecting this upfront gives a clear, actionable error message.

**Sources**: PEP 610 (Packages distribution "irect_url.json" — standard metadata for install origin), Python docs `importlib.metadata` (reading distribution metadata).

**Alternatives Considered**:
- **Try running `uv tool upgrade` and report failure**: Fragile — the command might succeed (doing nothing) or fail with an unclear error. Better to detect the condition explicitly.
- **Check if `sys.argv[0]` points to a `.venv`**: Indirect and unreliable. `direct_url.json` is the standard mechanism per PEP 610.

**Consequences**:
- Pro: Standard, reliable detection mechanism
- Pro: Clear user-facing error with actionable guidance
- Con: Depends on PEP 610 metadata being present (always true for pip/uv installs, may not be for exotic setups)

### System prompt injection in SYSTEM_PREAMBLE_TEMPLATE

**Choice**: Add a `# Updates` section to the `SYSTEM_PREAMBLE_TEMPLATE` string in `context/loading.py`, placed between the existing `# Detached Processes` section and `# Context Documents`.

**Why**: All other tool capabilities (tasks, workflows, projects, git, detached processes) are documented in the preamble. Adding update tools there is consistent and ensures the agent always knows about them. The preamble is rendered once at startup via `render_system_preamble(timezone)` and included in every session's system prompt.

**Alternatives Considered**:
- **Separate context entry via context provider**: Would require a new `ContextProvider` implementation and registration in the pre-processing pipeline. Overkill for a static two-line description.
- **Injected by the updates hook during bootstrap**: Would couple the updates subsystem to the context assembly process. The preamble template is the canonical place for tool documentation.

**Consequences**:
- Pro: Consistent with existing pattern (tasks, git, workflows all documented in preamble)
- Pro: Always included — no conditional loading or provider registration needed
- Con: Preamble grows slightly (negligible — ~6 lines)

## System Behavior

### Scenario: Successful upgrade

**Given**: A newer version is available on PyPI, the install is a tool install (not editable)
**When**: The `apply_update` tool is invoked
**Then**:
1. Editable check passes
2. Current version recorded from `importlib.metadata`
3. `uv tool upgrade tachikoma-agent` runs via `subprocess.run` (timeout: 120s)
4. Exit code 0, stdout indicates upgrade (not "already up to date")
5. `bus.dispatch(RestartRequested())` fires
6. Tool returns success message with old version
7. Agent generates response ("Restarting...")
8. Response fully rendered to user
9. Channel detects `_restart_requested` flag:
   - REPL: flag checked at top of while loop, breaks before `prompt_async`
   - Telegram: event handler called `stop_polling()`, polling loop exits
10. `channel.run()` returns
11. `Coordinator.__aexit__` runs: cancel idle PP, await pending tasks, close session, await background tasks, run final PP
12. Main `finally` block: buffer stop, scheduler cancel, background runner shutdown, bus stop, DB close
13. Check `active_channel._restart_requested` → True
14. `os.execv(sys.argv[0], sys.argv)` replaces the process

**Rationale**: The restart only triggers after the SDK finishes the complete tool call AND the agent's full response is rendered. The tool fires the event and returns; the SDK then finishes generating the agent's response (which includes telling the user about the restart); the channel renders every event; only then does the channel loop check the restart flag. This guarantees the user always sees the restart notification before the process exits. The shutdown sequence is identical to the user pressing 'q'.

### Scenario: Already up to date

**Given**: The installed version matches the latest on PyPI
**When**: The `apply_update` tool is invoked
**Then**: Tool runs `uv tool upgrade` (exit code 0). Stdout contains "already up to date" or similar no-change indicator. Tool returns informational message with current version. No restart event fired. Process continues normally.

**Rationale**: Idempotent behavior — calling `apply_update` when already current is safe and informative.

### Scenario: Upgrade failure

**Given**: `uv tool upgrade` fails (network error, permission denied, uv not found)
**When**: The `apply_update` tool returns a non-zero exit code
**Then**: Tool reports the error with stderr content. No restart event fired. Process continues normally.

**Rationale**: Failures should not disrupt the running process. The agent can relay the error to the user for manual resolution.

### Scenario: Editable/development install

**Given**: Tachikoma is installed via `uv pip install -e .` or similar
**When**: The `apply_update` tool checks `direct_url.json`
**Then**: Tool detects `"editable": true` in `dir_info`, returns error explaining that updates require a tool install. No subprocess runs.

**Rationale**: Prevents confusing failures from running `uv tool upgrade` on an incompatible install type.

### Scenario: Concurrent operations during restart

**Given**: Background tasks are running when restart triggers
**When**: The shutdown sequence begins
**Then**: Background tasks are cancelled as part of the normal shutdown flow (background runner shutdown in `finally` block). This matches existing shutdown behavior for background tasks.

**Rationale**: No special handling needed — the existing cleanup sequence already handles in-flight work correctly.

### Scenario: Telegram reconnection after restart

**Given**: The process restarts during an active Telegram session
**When**: The new process starts and begins polling
**Then**: Telegram delivers queued messages (server-side buffering). The new process processes them normally.

**Rationale**: Telegram's long-polling mechanism queues messages server-side during the restart gap. No special reconnection logic needed.

## Notes

- `os.execv` preserves PID and terminal session, making it compatible with tmux and systemd without special handling.
- The `RestartRequested` event has no payload because restart is unconditional once fired — the channel either exits for restart or exits for normal shutdown, and the main loop distinguishes via the `_restart_requested` attribute.
- `uv tool upgrade` output parsing detects "upgraded" vs "already up to date." Detection strategy: check stdout for known no-change patterns (`"Nothing to upgrade"`, `"already up to date"`, `"Already up to date"` — exact strings determined during implementation). If none match and exit code is 0, assume upgrade succeeded (safe fallback = restart). This is fragile to uv output format changes but practical — the fallback is harmless.
- The 120s subprocess timeout accommodates slow networks and large package downloads while preventing indefinite hangs. Not configurable — this is a system-level operation that shouldn't need per-user tuning.
- Version logging at startup already exists (`_log.info("Startup complete: ...")`) — the new process's version is captured by `importlib.metadata` automatically, so the user can confirm the upgrade from the startup log line.
