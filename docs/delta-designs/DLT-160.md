# Design: DLT-160 — Loop iteration via workflow composition

**Delta Spec**: [../delta-specs/DLT-160.md](../delta-specs/DLT-160.md)
**Status**: Draft

## Purpose

This document explains the design rationale for DLT-160: how the `loop` frontmatter field and the items-on-start mechanism extend the existing composition machinery (DLT-161) to support agent-driven batch iteration without introducing a parallel implementation.

| Part | Mechanism | Flag |
|------|-----------|:----:|
| **S1** | Add `loop: str \| None` to `StepDefinition`; loader parses the `loop` frontmatter key with the same warn-and-fall-back-to-`None` pattern used for `composes`/`condition` | |
| **S2** | Extend `UpdateWorkflowStateArgs` with optional `items: list[str] \| None`; existing Pydantic validation flow handles shape errors | |
| **S3** | New `loop_state` JSON column on `workflow_states` carrying runtime progress (`{<step_id>: {items, index}}`); the immutable definition snapshot stays as-is, this column holds the mutable position | |
| **S4** | Extend `_try_spawn_child` to accept an optional `current_item: str \| None` and thread it through the spawned child's response context. Loop iteration spawns reuse this same helper — no parallel spawn path | |
| **S5** | Extend the existing cascade pop-up branch in `_run_cascade`. When a child auto-finalizes and the parent layer's just-completed step is a loop step: read `loop_state[step].index`, advance it; if items remain, call `_try_spawn_child` again with the next item (same path the cascade uses for composition); if exhausted, mark the loop step `completed` and let the existing cascade-up logic continue. Empty-list start hits the exhaustion branch on the first check | |
| **S6** | Extend `_evaluate_and_advance` so pending loop steps halt auto-advance. The function returns the loop step as the next pending step but the caller does not auto-start it; the response prompts the agent for an explicit `start` with `items` | |
| **S7** | Extend `_validate_deps` composition validation: add `loop` edges to the same graph `composition.detect_cycles` / `validate_references` already walk (no new cycle algorithm); add a single mutex check rejecting steps that declare both `loop` and `composes` | |
| **S8** | Items validation in `handle_update_workflow_state` — required for loop-step starts, rejected for non-loop-step starts; surfaces clear errors before the cascade runs | |
| **S9** | Extend `_build_step_response` / `_render_breadcrumb` (and `handle_get_workflow_state`) to read `loop_state` and render the current item alongside the active step. One small rendering hook reused everywhere | |
| **S10** | Documentation updates — system preamble's Workflows section + `workflow-authoring-guide/references/step-design.md` document the `loop` field, `items` mechanism, current-item exposure, auto-complete-on-exhaust, mutex with composes, and the auto-start halt | |

### Inherited Behaviors (no new shape part needed)

- **Abort cascade** — `end_workflow(top_level_id, "abort")` already walks descendants via `parent_workflow_id`. Iteration children are regular composition children with `parent_workflow_id` set, so existing `abort_cascade` handles them automatically.
- **Mid-cascade error atomicity** — existing `MutationBatch` rollback semantics cover loop iteration spawn failures.
- **Single-ID routing / child-ID rejection** — existing deepest-active routing already handles iteration children identically to composition children.
- **Scratchpad inheritance** — iteration children inherit the parent's scratchpad path via the existing `_try_spawn_child` flow.
- **Snapshot-at-spawn** — each iteration captures a fresh snapshot of the loop target via the same path composition uses.
