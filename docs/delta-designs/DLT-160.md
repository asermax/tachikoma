# Design: DLT-160 — Loop iteration via workflow composition

**Delta Spec**: [../delta-specs/DLT-160.md](../delta-specs/DLT-160.md)
**Status**: Approved

## Purpose

This document explains the design rationale for DLT-160: how the `loop` frontmatter field and the items-on-start mechanism extend the existing composition machinery (DLT-161) to support agent-driven batch iteration without introducing a parallel implementation.

## Problem Context

Skills already model multi-step processes as workflows, and DLT-161 added composition so a step can pause its parent, run a referenced child workflow to completion, and auto-resume. That covers fixed-shape sub-flows. It does not cover *batch* sub-flows — running the same body once per item — which workflow authors keep needing (process every inbox note, send every reminder, delete every stale branch).

Two existing fallbacks are unsatisfactory:

- **Unrolling steps by hand.** The author has to know the items at authoring time, which is rarely true; and the workflow becomes brittle and bloated.
- **Agent self-looping.** The agent re-enters the workflow N times under its own discipline, with no engine-level guarantee that it visited every item exactly once. State, breadcrumb, and error semantics all degrade because the engine cannot see the iteration as one logical run.

**Constraints:**

- Reuse existing composition primitives. No parallel spawn/cascade/cycle-detection/scratchpad path.
- Agent provides items inline at start; engine drives iteration. No counters, no continuation predicate, no max cap — that complexity belongs to the iteration body.
- Items are opaque strings the iteration body interprets; the engine never inspects them beyond storing and surfacing.
- Persistence must survive context loss: items list and current index live on the parent's state record, not in conversation memory.
- Cycle-safety: loop edges are first-class members of the composition graph; load-time cycle detection bounds runtime depth.
- Mid-cascade errors stay atomic. No partial state on validation failure.

**Interactions:**

- `StepDefinition` (`workflows/definition.py`) — gains a `loop` field alongside `composes` and `condition`.
- Workflow loader (`workflows/loader.py`) — parses the new frontmatter key with the established warn-and-fall-back-to-`None` pattern.
- `composition.py` — cycle and reference validation already walks the composition graph; gains a unified treatment of `loop` and `composes` edges, plus a single mutex check.
- Cascade engine (`workflows/tools.py`) — gains an auto-start halt branch and an iteration-spawn branch in the cascade pop.
- Repository (`workflows/repository.py`) — writes a new `loop_state` JSON column when `UpdateState.loop_state` is set.
- Database migrations (`database.py`) — adds the `loop_state` column via the existing `pragma_table_info` + `ALTER TABLE` pattern.
- System preamble (`context/loading.py`) and `workflow-authoring-guide` skill — documentation updates.

## Design Overview

A loop step is a **second edge type in the same composition graph**. Where `composes` runs the target workflow once, `loop` runs it once per item in an agent-supplied list. The engine reuses every existing composition primitive — spawn helper, MutationBatch atomicity, cycle detection, deepest-active routing, scratchpad inheritance, abort cascade, snapshot-at-spawn — and adds three new mechanisms on top:

1. **A `loop` frontmatter field** on `StepDefinition`, parsed identically to `composes` and `condition`.
2. **An `items: list[str] | None` parameter** on the existing `update_workflow_state` start action. Required for loop steps, rejected for non-loop steps. Validation errors are atomic — no `loop_state` row written, no iteration child spawned.
3. **A `loop_state` JSON column** on `workflow_states` carrying runtime progress (`{<step_id>: {items, index}}`). The immutable definition snapshot is not mutated; only this column changes as iterations advance.

Cascade engine changes are localised to two branches:

- **Auto-start halt** — when the cascade reaches a pending loop step via auto-advance, it does not spawn iterations. The response prompts the agent for an explicit `start` with `items`.
- **Iteration advancement on cascade pop** — when an iteration child auto-finalizes and the parent's just-completed step is a loop step, the engine reads `loop_state[step].index`, advances it, and either re-spawns the next iteration via `_try_spawn_child` (queueing one more `CreateChild`) or marks the loop step `completed` and lets the existing cascade-up logic continue. Empty items hits the exhaustion branch on the first check.

The current item is surfaced via a breadcrumb suffix on the deepest segment (R17 satisfies R5):

```
weekly-review/03-process > process-item/01-step (item: foo.md)
```

`handle_get_workflow_state` renders a "Loop step" block on the parent's loop step showing items list, current index, and current item; the iteration child renders identically to an ordinary composition child — no parallel rendering path.

```
┌───────────────────────────────────────────────────────────────────┐
│  StepDefinition                                                   │
│  ├── composes: str | None  ──┐                                    │
│  └── loop:     str | None  ──┴──→ both edges in the same graph    │
└───────────────────────────────────────────────────────────────────┘
                                       │
                ┌──────────────────────┴───────────────────────┐
                ▼                                              ▼
        _validate_deps                                Cascade engine
        ├── detect_cycles (loop ∪ composes edges)     ├── auto-start halt branch
        ├── validate_references (both edge types)     ├── iteration advance branch
        └── mutex check (loop XOR composes)           └── _try_spawn_child(current_item=…)
                                                              │
                                                              ▼
                                                  CreateChild + UpdateState(loop_state)
                                                  applied via apply_mutation_batch
                                                              │
                                                              ▼
                                              workflow_states.loop_state column
                                              {<step_id>: {items, index}}
```

### Inherited Behaviors (no new shape part needed)

- **Abort cascade** — `end_workflow(top_level_id, "abort")` walks descendants via `parent_workflow_id`. Iteration children are regular composition children, so the existing `abort_cascade` handles them automatically (R18).
- **Mid-cascade error atomicity** — existing `MutationBatch` rollback covers spawn failures and halt-prompt construction errors (R14).
- **Single-ID routing / child-ID rejection** — existing deepest-active routing already handles iteration children identically to composition children (R13).
- **Scratchpad inheritance** — iteration children inherit the parent's scratchpad path via the existing `_try_spawn_child` flow.
- **Snapshot-at-spawn** — each iteration captures a fresh snapshot of the loop target via the same path composition uses (R3).

### Cross-Layer Contracts

**`update_workflow_state` schema** (additive — no breaking change):

```
update_workflow_state(
    workflow_id: str,
    step: str,
    action: "start" | "complete" | "skip",
    items: list[str] | None = None,   # NEW — required for loop-step starts
)
  → { ...activation response... }
  | { error: str }
```

**Validation rules at `start`** (in this order; first failure short-circuits):

1. **Routing** — `chain = get_active_chain(workflow_id)`; reject child IDs; resolve deepest-active layer; reject step IDs that don't match the deepest layer's snapshot.
2. **Transition** — `validate_transition` against the deepest layer's `step_states` and snapshot. Validates the agent's *requested transition* (start from `pending` is allowed) — note that this gate signs off on the request, not on the eventual persisted state (e.g., empty items will later short-circuit to `completed` instead of `started`).
3. **Step-kind / items consistency** (structural) — items provided iff step is a loop step. This check is purely structural and runs *before* condition evaluation so non-loop-step + items errors surface even when the step's condition would otherwise fail:
   - Non-loop step + items provided → reject with "items not allowed for non-loop steps".
   - Loop step + items omitted → defer the "required" check to gate 5 (a loop step with a failing condition does not need items).
4. **Condition** — if the step has a `condition`, evaluate. Non-passing → step `skipped`, cascade advances; items field (whether provided or not) is no longer consulted.
5. **Items required (semantic)** — only reaches this gate when (a) the step is a loop step and (b) condition evaluation passed (or the step had no condition):
   - `items=None` rejects with "items required for loop steps".
   - `items=[]` is *valid* (auto-completes the loop step with zero iterations).
   - Type errors (non-list input, non-string items) — already surfaced by Pydantic's native `list_type` / `string_type` ValidationError before reaching the handler at all (atomic by construction: the handler never executes).

**Atomicity rule:** All five validation gates run before any `MutationBatch` is queued. If any gate rejects, no `loop_state` row is written and no iteration child record is created.

**Auto-start halt response** (when the cascade reaches a pending loop step via auto-advance):

```
> <breadcrumb>          # if a child layer is active

The next step **<title>** (`<step_id>`) is a loop step. Call
update_workflow_state(workflow_id="<wid>", step="<step_id>", action="start",
items=[...]) to begin iterating, or items=[] to skip with zero iterations.
```

The loop step's state stays `pending` — not partially activated. The parent's `current_step` is also unchanged. If the agent retries with valid items, the response is deterministic.

**Iteration spawn cascade** (cascade pop after iteration N's last step finalizes):

```
1. _evaluate_and_advance on iteration N's child returns None (no pending steps).
2. Cascade queues UpdateState(child, current_step=None) + SoftDelete(child).
3. Cascade pops to parent. The just-completed step is the loop step.
4. Cascade reads loop_state[loop_step].index = N; advances to N+1.
5. If N+1 < len(items):
     queue UpdateState(parent, loop_state={loop_step: {items, index: N+1}})
     spawn iteration N+1 via _try_spawn_child(loop_target, current_item=items[N+1])
     queue CreateChild(child_N+1, ...)
     descend cascade into child_N+1's first step.
6. If N+1 == len(items):
     queue UpdateState(parent, step_states[loop_step]=COMPLETED, loop_state={loop_step: {items, index: N+1}})
     fall through to existing cascade-up logic (auto-completes the loop step,
     advances the parent's next pending step, etc.).
```

**`get_workflow_state` rendering** (additive — no schema change):

When the parent has an active loop step (`loop_state` set, current iteration child active or about to spawn), the parent's view inlines a `### Loop step` block:

```
### Loop step: <loop_step_title> (`<loop_step_id>`)

- Items (3): `foo.md`, `bar.md`, `baz.md`
- Current iteration: 2 / 3
- Current item: `bar.md`
```

The active iteration child renders as the existing composition child block (no parallel `### Loop iteration` section). The breadcrumb at the top of the response carries the `(item: bar.md)` suffix on the deepest segment.

**Integration Points**

- The MCP tool registry contract (`update_workflow_state`'s tool description) is updated to document `items`. Existing callers ignore the new parameter — non-loop starts continue to work unchanged.
- `_validate_deps` is called once at registry load and once per hot-reload; loop edges flow through the same call path.
- `apply_mutation_batch`'s atomic-write guarantee covers `loop_state` updates without any new transaction or session.
- The system preamble's Workflows section is reassembled from static text (ADR-008); no runtime cost.

### Shared Logic

- **Composition edge resolution** — `resolve_composes(value, parent_skill)` is the single helper used for both `composes` and `loop` values. The function does not care which frontmatter key carried the value; the cycle/reference validators iterate steps and pull whichever of `step.composes` / `step.loop` is set.
- **Spawn pipeline** — `_try_spawn_child` is the single entry point for creating a child layer; iteration spawns differ only by passing a non-`None` `current_item`. Snapshot-at-spawn, scratchpad inheritance, and child-step-states initialisation are all reused.
- **Cycle graph membership** — vertices are `(skill_name, workflow_name)`; edges include both edge types. The existing three-color DFS, fixed-point reference iteration, and per-cycle rejection logic apply unchanged.
- **Atomic write semantics** — `MutationBatch` + `apply_mutation_batch` already guarantee single-transaction commit; adding `loop_state` to `UpdateState` rides on the same machinery without introducing a new mutation type.

## Modeling

```
StepDefinition (filesystem):
  id: str
  title: str
  instructions_path: Path
  references_path: Path | None
  scripts_path: Path | None
  required: bool
  required_skills: tuple[str, ...]
  condition: str | None
  composes: str | None
  loop: str | None              # NEW — same syntax as composes; mutex with composes
  properties: dict

WorkflowState (database — table: workflow_states):
  ... existing fields ...
  loop_state: dict | None       # NEW — nullable JSON column
                                #
                                # Shape: {<step_id>: {"items": list[str], "index": int}}
                                # Set on any record whose own snapshot defines a loop
                                # step that has been started. Multiple keys possible
                                # when a record has multiple loop steps that have run
                                # (history kept on completed loop steps; the index
                                # reaches len(items) when the loop is exhausted).
                                # Iteration children carry NULL UNLESS they themselves
                                # contain a started loop step — `loop_state` always
                                # lives on the record whose snapshot defines the loop
                                # step. For nested loops, the outer iteration child
                                # holds the inner loop's state on its own record;
                                # the top-level parent's loop_state only carries the
                                # outer loop's progress.

UpdateState (in-memory mutation):
  layer_id: str
  step_states: dict[str, str]
  current_step: str | None
  loop_state: dict | None       # NEW — when set, persisted into the row's loop_state
                                # column inside apply_mutation_batch. None means
                                # "do not touch this column".

CreateChild (in-memory mutation):
  ... unchanged — current_item is carried on the spawning layer's response context,
      not persisted on the child record (the parent's loop_state holds it) ...

CompositionGraph (in-memory, transient — built only during _validate_deps):
  vertices: set[(skill_name, workflow_name)]
  edges:    dict[vertex, list[(vertex, edge_type)]]   # edge_type ∈ {"composes", "loop"}
                                                      # cycle detection treats them
                                                      # uniformly; mutex enforced
                                                      # before edge collection
```

The state-machine view of a loop step — its position in the parent's `step_states` over time:

```
        agent calls start (items=[])              agent calls start (items=[a, b, c])
                 │                                            │
                 ▼                                            ▼
   ┌──────────────────────────────┐         ┌──────────────────────────────┐
   │ exhausts immediately;        │         │ STARTED + spawn iter 0       │
   │ no STARTED transition        │         │   ↓ child finalizes          │
   │   ↓                          │         │ STARTED + spawn iter 1       │
   │ COMPLETED                    │         │   ↓ child finalizes          │
   └──────────────────────────────┘         │ STARTED + spawn iter 2       │
                                            │   ↓ child finalizes          │
                                            │ COMPLETED                    │
                                            └──────────────────────────────┘

PENDING ──┐                                  ┌──→  STARTED ──→  COMPLETED
          │                                  │
          │    condition fails on start  ────┘
          ├──→ SKIPPED (no STARTED)
          │
          │    required: false + skip action
          └──→ SKIPPED (no STARTED)
```

The loop step transitions from `PENDING` directly to `STARTED` only when iteration 0 spawns. Empty-list starts go directly to `COMPLETED` without a `STARTED` intermediate (the cascade exhaustion branch fires immediately). Condition-skip and `required: false` skip both go straight to `SKIPPED`. Once `STARTED`, the step stays `STARTED` until the last iteration finalizes — at which point the cascade pop transitions it to `COMPLETED`.

## Data Flow

### Start a loop step (items provided, condition passes)

```
Agent: update_workflow_state(parent_id, "03-process", "start", items=["a", "b", "c"])
  -> chain = get_active_chain(parent_id) = [parent]
  -> deepest = parent; step "03-process" matches.
  -> validate_transition: PENDING → STARTED for "03-process"  ✓
  -> condition: none (or evaluates to passing)
  -> items: list[str], non-empty                                ✓
  -> Cascade loop:
       mark "03-process" STARTED in mutable_ss[parent].
       _try_spawn_child(target=loop_target, current_item="a"):
         allocates child_id; snapshots target; child_ss = {step: PENDING, ...}.
       queue CreateChild(child_id, parent_id, "03-process", ...).
       queue UpdateState(
         parent,
         step_states={..., "03-process": STARTED},
         current_step="03-process",
         loop_state={"03-process": {"items": ["a","b","c"], "index": 0}},
       ).
       descend into child; child's first pending step (no condition, no composes,
         no loop) is marked STARTED.
       cascade terminates (non-special step started in child).
  -> MutationBatch:
      [UpdateState(parent, ..., loop_state=...),
       CreateChild(child_id_0, parent_id, "03-process", target_skill, target_wf,
                   {step: STARTED, ...}, snapshot, parent.scratchpad_path)]
  -> apply_mutation_batch commits atomically.
  -> Response:
       breadcrumb: "weekly-review/03-process > process-item/01-step (item: a)"
       body: child's "01-step" instructions.
```

### Iteration N finalizes, iteration N+1 spawns (same tool call)

```
Agent: update_workflow_state(parent_id, "01-step", "complete")
  -> chain = [parent, child_N]; deepest = child_N; step matches.
  -> Cascade loop:
       mark child's last step COMPLETED.
       _evaluate_and_advance on child returns None (no pending steps).
       queue UpdateState(child_N, current_step=None) + SoftDelete(child_N); pop layer.
       parent's just-completed step is "03-process" (a loop step).
       read loop_state["03-process"].index = N; advance to N+1.
       items[N+1] exists (e.g., "b"):
         _try_spawn_child(target=loop_target, current_item="b"):
           allocates child_id_N+1; snapshots target; child_ss = {...PENDING}.
         queue CreateChild(child_id_N+1, ...).
         queue UpdateState(
           parent,
           step_states={..., "03-process": STARTED},   # unchanged — still STARTED
           current_step="03-process",
           loop_state={"03-process": {"items": [...], "index": N+1}},
         ).
         descend into child_N+1; first step STARTED; cascade terminates.
  -> MutationBatch:
      [UpdateState(child_N, ..., current_step=None),
       SoftDelete(child_N),
       UpdateState(parent, ..., loop_state={"03-process": {"items": [...], "index": N+1}}),
       CreateChild(child_id_N+1, ..., scratchpad_path=parent.scratchpad_path)]
  -> apply_mutation_batch commits everything atomically (single SQLite transaction).
  -> Response:
       breadcrumb: "weekly-review/03-process > process-item/01-step (item: b)"
       body: child_N+1's "01-step" instructions.
```

### Last iteration finalizes (loop exhausts; cascade pops further)

```
Agent: update_workflow_state(parent_id, "01-step", "complete")
  -> chain = [parent, child_last]; deepest = child_last; step matches.
  -> Cascade loop:
       mark child's last step COMPLETED.
       child has no more pending steps.
       queue UpdateState(child_last, current_step=None) + SoftDelete(child_last); pop.
       parent's just-completed step is "03-process".  index = len(items)-1.
       advance to len(items): exhausted.
       queue UpdateState(
         parent,
         step_states={..., "03-process": COMPLETED},
         current_step="03-process",     # held until the next auto-advance
                                        # updates it to the parent's next pending
                                        # step (consistent with the existing
                                        # cascade-up-after-child-completion path)
         loop_state={"03-process": {"items": [...], "index": len(items)}},
       ).
       _evaluate_and_advance on parent: finds next pending step.
         If next step is regular: STARTED, queue UpdateState, return.
         If next step is composes: spawn child via _try_spawn_child.
         If next step is loop: halt — return halt prompt response.
         If no next step: SoftDelete(parent), set finalized_top_level=True.
  -> Response:
       breadcrumb: parent's next step (no item suffix unless inside another loop).
       body: parent's next step instructions OR top-level finalization message.
```

### Empty items list (auto-complete with zero iterations)

```
Agent: update_workflow_state(parent_id, "03-process", "start", items=[])
  -> chain = [parent]; deepest = parent.
  -> validate_transition: start request from PENDING is allowed  ✓
       (validates the agent's request — the empty-items branch will later
        write COMPLETED directly instead of STARTED, so the loop step
        never enters the STARTED state in the persisted record)
  -> step-kind / items consistency: items provided + step is a loop step  ✓
  -> condition: passes (or none).
  -> items required: items=[] is valid for a loop step                    ✓
  -> Cascade loop:
       The "spawn or exhaust" decision is centralised: the loop-step start path
       advances index = 0 against len(items) = 0 → exhausted on first check.
       queue UpdateState(
         parent,
         step_states={..., "03-process": COMPLETED},   # straight to COMPLETED
         current_step="03-process",                     # held until the next
                                                        # auto-advance updates it
         loop_state={"03-process": {"items": [], "index": 0}},
       ).
       _evaluate_and_advance on parent: finds next pending step or finalizes.
  -> MutationBatch: 1-3 mutations (no CreateChild).
  -> Response: parent's next step OR top-level finalization.
       Includes a one-line "Loop step <id> completed with zero iterations." note.

If "03-process" was the parent's last step:
  -> _evaluate_and_advance returns None.
  -> queue SoftDelete(parent); set finalized_top_level=True.
  -> apply_mutation_batch commits everything atomically.
  -> after commit: scratchpad file deleted (idempotent unlink).
  -> Response: "Workflow <name> complete and finalized."
```

### Auto-start halt at a pending loop step

```
Agent: update_workflow_state(parent_id, "02-prepare", "complete")
  -> chain = [parent]; deepest = parent.
  -> validate_transition: STARTED → COMPLETED  ✓
  -> Cascade loop:
       mark "02-prepare" COMPLETED.
       _evaluate_and_advance on parent: next pending = "03-process" with loop.
       Halt: do NOT mark STARTED, do NOT spawn anything.
       queue UpdateState(parent, step_states={..., "02-prepare": COMPLETED},
                         current_step="02-prepare").  (loop_state untouched)
  -> apply_mutation_batch commits the partial state (02-prepare COMPLETED only).
  -> Response (no breadcrumb suffix — no child active):
       "Step `02-prepare` completed.
       The next step **Process items** (`03-process`) is a loop step.
       Call update_workflow_state(workflow_id=..., step='03-process',
       action='start', items=[...]) to begin iterating, or items=[] to skip
       with zero iterations."
```

### Recovery after context loss mid-iteration

Display convention: `loop_state.index` is 0-indexed internally (0 means "iteration for items[0] is active"). Human-facing renderings (breadcrumb, `### Loop step` block) display it as 1-indexed ("iteration 1 / N") to match natural counting.

```
1. Agent loses context after iteration 3's child has spawned (loop_state.index = 3).
   The active iteration child is for items[3] = "d".
2. Agent calls list_active_workflows():
     parent surfaces (top-level only); iteration child does not.
3. Agent calls get_workflow_state(parent_id):
     response includes:
       - parent's step_states (with "03-process" STARTED)
       - "### Loop step: Process items (`03-process`)" block:
           "- Items (5): a, b, c, d, e
            - Current iteration: 4 / 5     # (loop_state.index = 3, displayed as 1-indexed)
            - Current item: d"
       - "### Active Child: process-item" block (the iteration-3 child)
       - breadcrumb: "weekly-review/03-process > process-item/01-step (item: d)"
4. Agent resumes by calling update_workflow_state on the iteration's current step.
```

### Abort cascade with active loop

```
Agent: end_workflow(parent_id, "abort")
  -> handle_end_workflow:
       reads parent state; rejects child IDs.
       calls abort_cascade(parent_id) — atomic.
         BFS-walks descendants via parent_workflow_id; collects all IDs
         (parent + the single in-flight iteration child).
         issues one UPDATE WHERE id IN (...) setting deleted_at.
       after commit: deletes the shared scratchpad once.
  -> Response: "Workflow aborted. (2 records cleaned up)"

Note: loop_state on the parent record stays intact on the soft-deleted row
(audit trail; no separate clear-on-abort step).
```

### Load-time validation (cycle/reference)

```
1. SkillRegistry._validate_deps() runs:
   1a. Mutex pre-pass: walk every workflow, every step. If any step
       declares BOTH `loop` and `composes`, log a malformed-step warning
       and remove the parent workflow entirely from _workflows. This pass
       runs before edge collection so the rejected workflow's other steps
       cannot contribute partial edges to the cycle graph.
   1b. Edge collection: for each surviving workflow, for each step that
       declares composes OR loop (now guaranteed to be at most one of the
       two), resolve via resolve_composes and add (vertex, target,
       edge_type) to the graph.
   1c. detect_cycles runs three-color DFS over the unified edge set;
       loop and composes edges are indistinguishable for cycle purposes.
       Cycle members are removed from _workflows.
   1d. validate_references iterates to fixed-point; rejected workflows
       cascade; missing/zero-step targets reject parents.
   1e. _workflows post-condition: only valid composable workflows remain;
       no surviving step declares both composes and loop.
2. Hot reload: registry.refresh() rebuilds the graph from scratch;
   loop-introduced cycles surface the same way composes-introduced ones do.
```

## Key Decisions

### Loop iteration as a second edge type in the existing composition graph

**Choice**: `loop` and `composes` are sibling frontmatter fields on the same step model; cycle detection, reference validation, spawn, snapshot-at-spawn, scratchpad inheritance, deepest-active routing, abort cascade, and atomic mutation are all reused. Iteration advancement is a new branch in the existing cascade loop, not a parallel cascade.

**Why**: The existing composition machinery already encodes "spawn a child, run it, auto-resume parent". An iteration is the same mechanism applied N times with a different `current_item`. Building a parallel pipeline would duplicate cycle detection, snapshot logic, atomicity, routing, and rendering — all of which already work correctly. The risk surface of one well-tested pipeline is dramatically smaller than two.

**Sources**: `docs/feature-designs/workflows/workflow-state-machine.md` (composition machinery sections); existing `composition.py` (`detect_cycles` at line 54, `validate_references` at line 112, `MutationBatch` at line 237); existing `tools.py` (`_run_cascade` at line 424, `_try_spawn_child` at line 368).

**Options Researched**:

- *Parallel pipeline* — separate `loop_state.py` module mirroring `composition.py`, separate cascade engine. Rejected: doubles cycle/reference logic; introduces "is this a loop or a composition?" branching everywhere downstream.
- *Items as a runtime-only concept (no engine support)* — agent unrolls iteration via repeated `start` calls. Rejected by spec (R0, R7) and by the user-driven motivation: agents drift on long lists without engine-level guarantees.
- *External iteration driver* (e.g., a cron job or a separate MCP tool that launches one composition per item). Rejected: cron is the wrong granularity, and "one composition per item" loses the breadcrumb/state-as-one-run guarantee that DLT-161 invested in.

**Why This Over Alternatives**: The composition machinery's invariants — top-level uniqueness, snapshot-at-spawn, scratchpad inheritance, single-ID routing — are exactly what loop iterations need. The only loop-specific logic is "advance index and re-spawn". Reusing the graph for cycle detection means a `loop: A` from `A` is rejected by the same DFS that already rejects `composes: A` from `A`.

**Consequences**:

- Pro: One spawn path, one cycle detector, one cascade engine. Bug fixes on either feature benefit both.
- Pro: Iteration children inherit composition's documented invariants (top-level filter, child-ID rejection, abort cascade) for free.
- Pro: Cross-edge cycles (`A` loops `B`, `B` composes `A`) fall out of the unified graph naturally — no special-case algorithm.
- Con: The cascade engine's pop branch grows a new conditional. Mitigated by keeping the loop-specific logic to ~15 lines: read `loop_state`, advance index, decide spawn vs. exhaust.

### `loop_state` as a JSON column on the parent record (not a separate table)

**Choice**: Items list and current iteration index live on the parent's `workflow_states` row in a new nullable `loop_state` JSON column shaped `{<step_id>: {items: list[str], index: int}}`. Iteration child records are *not* augmented — they remain identical to composition children.

**Why**: Loop progress is intrinsic to the parent's loop step, not to the iteration child. The child is ephemeral (one per item, soft-deleted on finalize); the parent's state record is the durable home. Storing on the parent means recovery via `get_workflow_state(parent_id)` returns everything in one query — no JOIN, no N-row aggregation. A separate `loop_iterations` table would force every reader to JOIN and every writer to coordinate two tables in the same transaction.

**Sources**: ADR-007 (persistence layer — JSON columns are the established pattern for `step_states` and `definition_snapshot`); existing `workflow_states` table schema (`workflows/model.py`); existing `pragma_table_info` migration pattern in `database.py:273–301` — concrete precedent: the `parent_workflow_id` and `parent_step_id` migrations from DLT-161 use the exact pattern this delta will follow for `loop_state`.

**Options Researched**:

- *Separate `loop_iterations` table* with FK to parent + step_id. Rejected: introduces a new table and migration, requires JOIN on every parent read, no real benefit for our scale (a parent has at most one or two active loop steps at a time).
- *Mutate the `definition_snapshot`* to embed the items list. Rejected: the snapshot is meant to be immutable — mutating it confuses snapshot-vs-runtime semantics and complicates audit trails.
- *Per-iteration child columns* (e.g., add `loop_index` to child rows). Rejected: spreads the items list across N child rows; recovery requires aggregating, and the current item is not knowable from the child alone (the items list lives elsewhere).

**Why This Over Alternatives**: Project precedent — `step_states` is a JSON column on the same table; `definition_snapshot` likewise. Adding `loop_state` follows the same shape. SQLite's TEXT-as-JSON storage is fast enough for our scale (single-digit-MB JSON per row max), and the column is read together with the rest of the parent state on every tool call.

**Consequences**:

- Pro: One read returns everything needed for the parent's view; no JOIN.
- Pro: Schema migration is a single nullable column add via the existing pattern.
- Pro: `loop_state` survives soft-delete intact (audit trail).
- Con: A loop step that ran with a 1000-item list embeds the list in the parent's row even after finalization. Acceptable: realistic batch sizes are dozens, not thousands, and the row is soft-deleted (read-only) once the workflow ends.

### Items on the existing `start` action (not a dedicated MCP tool)

**Choice**: The agent passes `items: list[str]` as an additional parameter to `update_workflow_state` when starting a loop step. No new tool is added.

**Why**: Adding a tool (e.g., `start_loop_iteration`) would force the agent to learn a parallel state-machine surface — when to call which tool, what the difference is. Reusing `start` keeps the state machine's vocabulary unified: there is exactly one way to begin a step, and the optional `items` parameter is the only difference loop steps require. Pydantic's union typing makes the parameter optional and forward-compatible with non-loop starts (which simply ignore it).

**Sources**: Pydantic v2.11.4 docs (verified via `katachi:doc-researcher` 2026-04-27): `list[str] | None` produces `list_type` and `string_type` ValidationError messages by default — exactly the shape the spec's R4 acceptance criteria require, with no custom validator. Existing `UpdateWorkflowStateArgs` model in `src/tachikoma/workflows/tools.py:59–63` (the model that already validates `workflow_id`, `step`, `action` — `items` slots in as a fourth field).

**Options Researched**:

- *New tool `start_loop_iteration(workflow_id, step, items)`*. Rejected: extra tool surface; the agent would have to know to use it instead of `update_workflow_state`; invites confusion when the agent calls the wrong tool.
- *Items as a separate setup call* (`set_loop_items`) followed by `start`. Rejected: introduces a multi-call protocol where atomicity is harder; if the agent calls `start` between the two, what state is the loop in? The spec demands atomicity (R4 last AC).
- *Items inferred from a producer step's scratchpad annotation*. Rejected: requires the engine to read the scratchpad, contradicting "scratchpad is agent-managed" (DLT-161 design decision).

**Why This Over Alternatives**: Single tool surface; atomic validation; Pydantic v2's default validation covers every spec'd error case (verified). Extra parameter is forward-compatible: non-loop starts that omit `items` work unchanged, and non-loop starts that *include* `items` are rejected with a clear "items not allowed for non-loop steps" message.

**Consequences**:

- Pro: Zero new tool surface; the agent's mental model stays "one tool drives the state machine".
- Pro: All four spec'd validation modes (missing items / non-list / non-string item / items-on-non-loop) covered with one optional Pydantic field plus one handler check.
- Pro: Atomic by construction — Pydantic rejects malformed input before the handler is called.
- Con: The tool description grows by a few lines. Acceptable.

### Auto-start halts at pending loop steps (cascade does not infer items)

**Choice**: When the cascade auto-advance reaches a pending loop step, it returns the loop step as the next pending step but does *not* mark it `STARTED` and does *not* spawn any iteration. The response prompts the agent for an explicit `start` with `items`.

**Why**: The engine cannot fabricate items. Auto-starting with an empty list would silently skip the loop step — invisible to the agent and contrary to the workflow author's intent. Auto-starting with synthesized items (e.g., from the scratchpad) would tie the engine to a specific producer pattern. The right default is to halt and require explicit input, with a self-explanatory error message that names the tool call to fix it.

**Sources**: Spec R12 (auto-start halts at loop steps); DLT-161 design rationale on auto-start (existing behavior for composes/condition steps); existing cascade auto-advance branch in `src/tachikoma/workflows/tools.py:651–706` — the new halt branch is added at the top of this loop's "next step is special?" decision.

**Options Researched**:

- *Auto-start with `items=[]`* (silently skip the loop). Rejected: invisible behavior change; contradicts the workflow author's likely intent.
- *Read items from the previous step's scratchpad annotations*. Rejected: implicit coupling between steps; brittle to scratchpad format changes; demands the engine parse agent-managed content.
- *Halt and emit a soft warning, but accept items via a follow-up update_workflow_state without re-`start`ing*. Rejected: introduces a new "step is half-started" state that the rest of the engine doesn't model.

**Why This Over Alternatives**: Halt + prompt is the only option that keeps the loop step in `PENDING` until the agent explicitly provides items. The agent can recover from the prompt with one tool call; nothing is partially activated; recovery after context loss is identical to first-time activation.

**`current_step` semantics on halt** (deliberate deviation from normal auto-advance): in the existing cascade, `current_step` is set to the next step whenever auto-advance starts a step. The halt branch instead leaves `current_step` at the just-finalized step (e.g., `current_step="02-prepare"` after the previous step completes and the cascade halts at the next pending loop step `03-process`). This is intentional — `current_step` semantically tracks "the step the engine most recently activated"; on halt no step is activated, so leaving it at the previous step is the correct invariant. The loop step is reachable through `_evaluate_and_advance` on the next tool call, so halt-recovery routing does not require `current_step` to point at it.

**Consequences**:

- Pro: No silent skips; the agent always sees a halt prompt naming the next tool call.
- Pro: The loop step's state stays `PENDING` — no half-activated state.
- Pro: Idempotent retries: if the agent's first attempt at providing items fails validation, the next attempt sees the same prompt.
- Con: The agent must know to provide items; mitigated by the explicit prompt and the system preamble's documentation.

### Validation order: routing → transition → step-kind/items consistency → condition → items-required

**Choice**: When `update_workflow_state` is called with `action="start"`, validation runs in this fixed five-gate order. Items validation is split into two distinct gates: a **structural** gate (gate 3) that runs *before* condition evaluation, and a **semantic required** gate (gate 5) that runs *after*.

**Why**: Two pressures pull in opposite directions:

1. *R8 says condition gates the step entirely* — demanding items before a failing condition forces the agent to assemble a list that's about to be discarded.
2. *R2 says non-loop step + items provided must reject* — silently swallowing this error when the step also has a failing condition would mask an agent bug.

Splitting the items check resolves the tension. The structural gate (items-vs-step-kind) is a static, parameter-vs-step-kind check that requires no dynamic state and surfaces all usage errors deterministically. The semantic gate (items-required-for-loop) only runs when the step is a loop step that survived its condition — at which point items absence is a real error. Items presence on non-loop steps surfaces *before* condition runs, so non-loop + failing-condition + items still produces the items-rejection error.

**Sources**: Spec R2 (items rejected on non-loop step), R8 (condition gates loop step); existing `_run_cascade` validation order in `tools.py:443–471`; existing `validate_transition` and condition-evaluation pattern in `tools.py:493–525`.

**Options Researched**:

- *Single items-validation gate after condition (4-gate order).* Rejected: silently swallows non-loop-step + items errors when condition fails — masking an agent bug.
- *Single items-validation gate before condition (4-gate order).* Rejected by R8: forces the agent to assemble items even when condition is about to skip the step.
- *Move items validation to Pydantic alone (no handler check).* Rejected: Pydantic validates *shape*, not *required-vs-not-allowed semantics*. The "items required for loop steps" / "items not allowed for non-loop steps" rules require knowing which step the agent is starting — only the handler has that.

**Why This Over Alternatives**: The five-gate order is the only configuration that satisfies both R2 and R8 without compromise. Structural-vs-semantic splitting is also conceptually cleaner: shape errors surface deterministically before any dynamic evaluation runs.

**Consequences**:

- Pro: R2 errors (items on non-loop step) surface even when the step's condition would otherwise fail.
- Pro: R8 still honoured — failing condition on a loop step skips items-required check; agent doesn't need to pre-assemble items.
- Pro: Atomic at every gate — first failure short-circuits, no `MutationBatch` is built.
- Pro: Pydantic catches the type errors (non-list, non-string) before the handler runs at all — three layers of defence (Pydantic shape → structural step-kind → semantic required).
- Con: Slightly more conditional logic in the handler. Acceptable — each gate is a 1–3-line check.

### Current item exposed via breadcrumb suffix (R17 satisfies R5)

**Choice**: The current item is appended to the deepest segment of the breadcrumb header as `(item: <value>)`. R17 (nice-to-have) is implemented as the primary surfacing mechanism, satisfying R5 (must-have).

**Why**: One rendering hook serves both requirements. The breadcrumb is already rendered on every iteration tool response and is a natural location for context that's tied to the deepest active layer. A separate `Current item: ...` prefix would duplicate the signal and add a second place to keep in sync. `get_workflow_state(parent_id)` adds a `### Loop step` block on the parent's view for explicit recovery, but the breadcrumb suffix is the moment-to-moment indicator.

**Sources**: Spec R5, R17; user confirmation during design interview.

**Options Researched**:

- *Separate `Current item: <value>` prefix line above the breadcrumb.* Rejected: duplicates the signal.
- *Both breadcrumb suffix + prefix line.* Rejected: verbose.
- *Item exposed only in `get_workflow_state` view (not in every tool response).* Rejected by R5: every iteration call must surface the current item.

**Why This Over Alternatives**: Compact, breadcrumb-co-located, hard to miss. Single rendering site; identical for activation responses and `get_workflow_state` nested views.

**Consequences**:

- Pro: One rendering hook, two requirements satisfied.
- Pro: The agent's iteration mental model — "I'm in iteration N looking at item X" — maps directly to the breadcrumb.
- Pro: Consistent across all tool responses inside an iteration.
- Con: Long item values (e.g., long filenames) make the breadcrumb wider. Acceptable: items are typically short identifiers; agents truncate on display when needed.

### `UpdateState` extended with optional `loop_state` (vs. new mutation type)

**Choice**: The existing `UpdateState` mutation dataclass gains an optional `loop_state: dict | None` field. `apply_mutation_batch` writes the column when set. No new mutation type is introduced.

**Why**: `UpdateState` already targets a single workflow row; adding another field-on-that-row keeps the mutation count constant and the transaction shape unchanged. A new mutation type would force the cascade engine to queue two mutations per iteration advancement — coordination that adds nothing because they always commit together.

**Sources**: Existing `composition.py` mutation types (`UpdateState`, `CreateChild`, `SoftDelete` at lines 206–243); existing `apply_mutation_batch` in `repository.py:341–390` (the `UpdateState` branch at lines 350–360 is where the new `loop_state` write slots in); user confirmation during design interview.

**Options Researched**:

- *New `UpdateLoopState(layer_id, loop_state)` mutation type queued alongside `UpdateState`.* Rejected: doubles mutation count per iteration advancement; the two are always queued together.
- *Embed `loop_state` directly in `step_states`.* Rejected: muddles two concepts (per-step status vs. per-loop-step runtime payload); requires every reader to know the difference.
- *Use the existing `repository.update(**fields)` method directly from the cascade.* Rejected: bypasses `MutationBatch` atomicity; iteration advancement must commit atomically with `CreateChild` and `SoftDelete`.

**Why This Over Alternatives**: Loop progress is conceptually "additional fields on the parent row that change atomically with step transitions". Putting it on `UpdateState` matches that conceptual model exactly. The optional field defaults to `None`, so loop-unaware callers stay unchanged.

**Consequences**:

- Pro: Same mutation type covers both step transitions and loop-progress updates.
- Pro: One transaction, one atomic write, one rollback boundary.
- Pro: Existing tests for `apply_mutation_batch` need only one new branch (write `loop_state` when set).
- Con: `UpdateState` becomes slightly less "pure" (mixes step transitions and loop progress). Acceptable: both target the same row, both must commit atomically, conceptually they are one update.

## System Behavior

### Scenario: First-time start with non-empty items

**Given**: Parent `weekly-review` is at step `02-prepare` STARTED. Step `03-process` declares `loop: process-item` and is `PENDING`.
**When**: Agent calls `update_workflow_state(parent_id, "02-prepare", "complete")`.
**Then**: Cascade marks `02-prepare` COMPLETED, advances, finds `03-process` is a loop step, halts auto-start, and returns: "Step `02-prepare` completed. The next step **Process items** (`03-process`) is a loop step. Call update_workflow_state(...) with items=[...] to begin iterating, or items=[] to skip with zero iterations." `03-process` stays `PENDING`.
**Rationale**: Auto-start cannot fabricate items; halting is the correct default.

### Scenario: Iteration N+1 spawns in the same tool call as iteration N's finalize

**Given**: Parent has `loop_state["03-process"] = {items: [a,b,c], index: 1}`; iteration child for item `b` is at its last step.
**When**: Agent calls `update_workflow_state(parent_id, <last_iter_step>, "complete")`.
**Then**: Cascade pop SoftDeletes child_1, advances `loop_state["03-process"].index` to 2, spawns child_2 with `current_item="c"`, and returns child_2's first step instructions with breadcrumb `weekly-review/03-process > process-item/01-step (item: c)`.
**Rationale**: Spawn-in-same-tool-call (R7) keeps the agent's progression linear — one `complete` per iteration, no manual re-`start`.

### Scenario: Empty items auto-completes the loop step

**Given**: Loop step `03-process` is `PENDING`. Agent calls `start` with `items=[]`.
**When**: The handler validates and the cascade runs.
**Then**: `03-process` transitions PENDING → COMPLETED in one atomic batch (no STARTED intermediate), `loop_state["03-process"] = {items: [], index: 0}` is persisted (audit trail), no iteration child is created, and the cascade auto-advances to the parent's next pending step (or finalizes the top-level if `03-process` was last).
**Rationale**: Empty items is a valid expression of "no items to process" — the engine treats it as zero-iteration completion, not an error.

### Scenario: Loop step's condition fails — items not consulted

**Given**: Loop step `03-process` declares `condition: "scratchpad has unprocessed items"` and the condition evaluates non-passing.
**When**: Agent calls `start` with or without `items`.
**Then**: The condition gate runs before items validation. The step is marked SKIPPED, no `loop_state` row is written, no iteration child is created, the cascade advances to the next pending step. If items were provided, they are silently discarded — the agent's response indicates the step was condition-skipped.
**Rationale**: Condition gates the entire loop step (R8). Demanding valid items first would force the agent to assemble a list it does not need.

### Scenario: Items-on-non-loop-step is rejected atomically

**Given**: Step `01-plan` is a regular (non-loop) step.
**When**: Agent calls `update_workflow_state(parent_id, "01-plan", "start", items=["a"])`.
**Then**: Validation rejects with "Items not allowed for non-loop steps". No state change. Step stays `PENDING`.
**Rationale**: R2 (items rejected when starting a non-loop step). Atomic — no partial mutation.

### Scenario: Non-string items rejected by Pydantic before the handler runs

**Given**: Loop step `03-process` is `PENDING`.
**When**: Agent calls `update_workflow_state(parent_id, "03-process", "start", items=[1, 2, 3])`.
**Then**: Pydantic raises a `ValidationError` with three `string_type` entries (one per non-string item). The handler is never called. No state change.
**Rationale**: Pydantic's default `list[str]` validation covers the shape error; handler-level checks are not needed.

### Scenario: Loop + composes mutex rejected at registry load

**Given**: A workflow `bad-step` declares both `loop: a` and `composes: b`.
**When**: The registry validates dependencies.
**Then**: `_validate_deps` rejects the parent workflow with a malformed-step warning identifying `loop` and `composes` as conflicting fields. The workflow is removed from `_workflows`.
**Rationale**: R9. Mutex check runs once during edge collection, before cycle/reference validation.

### Scenario: Cycle introduced via cross-edge chain

**Given**: Workflow `A` has `loop: B`; `B` has `composes: C`; `C` has `loop: A`.
**When**: The registry validates dependencies.
**Then**: `detect_cycles` finds the cycle `{A, B, C}` over the unified edge set (loop and composes treated identically). All three workflows are removed; one cycle warning is logged listing the members.
**Rationale**: R10. Loop edges and composes edges share the same cycle graph.

### Scenario: Self-reference rejected at load

**Given**: Workflow `A` has a step with `loop: A`.
**When**: The registry validates dependencies.
**Then**: `detect_cycles` flags the self-loop on the first DFS step; `A` is rejected with a self-reference cycle warning.
**Rationale**: R10 (self-reference is a special case of cycle detection).

### Scenario: Recovery after context loss mid-iteration

**Given**: An active loop on `03-process` with items=[a,b,c,d,e]. `loop_state["03-process"].index = 3` (the iteration for `items[3] = "d"` is active). The agent loses context.
**When**: The agent calls `list_active_workflows` then `get_workflow_state(parent_id)`.
**Then**: `list_active_workflows` returns only the parent (R11.2). `get_workflow_state` returns the parent's state with a `### Loop step` block showing `Items (5): a, b, c, d, e`, `Current iteration: 4 / 5` (1-indexed display of the underlying 0-indexed `index = 3`), `Current item: d`, plus the active iteration child block, plus the breadcrumb `weekly-review/03-process > process-item/01-step (item: d)`. The agent has everything needed to resume.
**Rationale**: R11, R11.2. State lives on the parent's `loop_state` column; nothing is in conversation memory.

### Scenario: Mid-cascade error rolls back atomically

**Given**: A cascade is advancing iteration N → N+1. The condition evaluator on the iteration N+1 child's first step raises an unexpected exception.
**When**: The exception propagates out of the cascade loop.
**Then**: `apply_mutation_batch` is never called. No state is written. Iteration N's child remains active (not soft-deleted), `loop_state` index remains at N, parent's loop step stays `STARTED`. The agent retries; the cascade reproduces the same path deterministically (the items list and index are unchanged).
**Rationale**: R14. `MutationBatch` is staged in memory; nothing commits until the cascade terminates cleanly.

### Scenario: Halt-prompt construction error

**Given**: Cascade reaches a pending loop step and is about to construct the halt-prompt response. An exception is raised during prompt construction.
**When**: The exception propagates.
**Then**: The in-flight `MutationBatch` (which had only the previous step's COMPLETED mutation queued) is rolled back. Step N's completion is not persisted. The agent retries; the same prompt is reproduced.
**Rationale**: R14 (atomic with halt-prompt construction). Even partial cascade work is staged in memory and never half-committed.

### Scenario: Abort cascade with active iteration

**Given**: Top-level `weekly-review` is active with iteration child for item `b` mid-flight (`loop_state["03-process"].index = 1`).
**When**: Agent calls `end_workflow(parent_id, "abort")`.
**Then**: `abort_cascade` BFS-walks descendants via `parent_workflow_id`, soft-deletes parent + iteration child in one transaction, deletes the shared scratchpad once. The parent's `loop_state` column remains intact on the soft-deleted row (audit trail).
**Rationale**: R18. Iteration children are regular composition children; `abort_cascade` handles them by structure, not by special-casing.

### Scenario: Iteration body has nested composition

**Given**: Loop target `process-item` has a step that `composes: validate-item`. Loop runs with items=[a,b,c].
**When**: Iteration 0 reaches the composes step.
**Then**: `validate-item` spawns as a grandchild of the parent (parent → iteration child → grandchild). The cascade descends 3 levels; the breadcrumb shows `weekly-review/03-process > process-item/02-validate > validate-item/01-check (item: a)`. When `validate-item` finalizes, the cascade pops to the iteration child, advances the iteration child, and so on. When iteration 0's child finalizes, iteration 1 spawns with `current_item="b"`. The grandchild for iteration 1's nested composes is fresh.
**Rationale**: R3. Iterations are composition children; nesting works recursively.

### Scenario: Iteration body has its own loop step (nested loops)

**Given**: Loop target `process-batch` has a step `02-each` declaring `loop: process-item`. Outer loop on top-level parent `weekly` runs with `items=[A, B]`; the inner loop on the outer iteration child runs with its own items per outer iteration.
**When**: Outer iteration 0 (item `A`) reaches step `02-each`, agent provides `items=[x, y]`, then proceeds through inner iterations.
**Then**: Auto-start halts at the inner loop step (R12 applies recursively); the agent calls `update_workflow_state` with `items` for the inner loop. Inner iterations run as grandchildren of the top-level parent. The inner loop's `loop_state` lives on the **outer iteration child's record** — that record's snapshot defines `02-each`, and `loop_state` always lives on the record whose snapshot owns the loop step. The top-level parent's `loop_state` only carries the outer loop's progress.

Persistence trace at the moment when outer iteration 0's inner loop is processing item `y` (inner iteration 1):

```
weekly (top-level)            : loop_state = {"03-process": {items: [A, B], index: 0}}
outer-iter-0 (process-batch)  : loop_state = {"02-each":    {items: [x, y], index: 1}}
inner-iter-1 (process-item)   : loop_state = NULL   (no loop step in its snapshot)
```

When the inner loop exhausts, the outer iteration child auto-finalizes naturally (per the existing exhaustion path); on its finalize, the outer loop's cascade pop advances `weekly.loop_state["03-process"].index` to 1 and spawns outer iteration 1 with its own opportunity to inner-loop.
**Rationale**: R3 + R12. Auto-start halt fires identically at every layer; `loop_state` is per-record, so each layer carries its own runtime state — no cross-record coordination required.

### Scenario: Routing rejects iteration-child ID

**Given**: Iteration child has ID `child-xyz`. Agent calls `update_workflow_state(child-xyz, "01-step", "complete")`.
**When**: The handler runs.
**Then**: Routing detects `chain[0].parent_workflow_id is not None`; rejects with the standard child-ID error directing the agent to operate on the top-level workflow.
**Rationale**: R13. Iteration children are composition children; existing child-ID rejection applies unchanged.

## Notes

- Loop progress is durable; iteration children are ephemeral. The parent's `loop_state` column is the recovery anchor — if every iteration child were soft-deleted (e.g., abort cascade) the items list and index would still be readable on the soft-deleted parent row for audit.
- The `loop_state` column key is the loop step's ID **on the record whose snapshot defines that step**. A record with two loop steps can carry two keys simultaneously (one active, one historical) without conflict. Nested loops live on different records — outer on top-level, inner on the outer iteration child.
- The cycle graph treats loop and composes edges identically. Mutex is enforced as a pre-pass that removes the offending parent workflow from `_workflows` *before* cycle/reference DFS runs, so detection never sees partial edges from an about-to-be-rejected workflow.
- Pydantic v2's default `list[str] | None` validation produces error messages of the form `Input should be a valid list [type=list_type, ...]` and `Input should be a valid string [type=string_type, ...]`. Per-index error reporting (e.g., `items.2`) makes it easy for the agent to locate the offending item in a long list.
- **Empty-string items** are accepted — `items=["", "foo"]` is a valid list of two strings. The breadcrumb suffix would render as `(item: )` for the empty entry. This is by design: items are opaque references and the iteration body decides what they mean. Workflow authors who want to reject empty items can do so with a `condition` on the iteration body's first step.
- **Audit-trail retention for `loop_state`**: soft-deleted parent rows retain their `loop_state` payload intact. Stale-cleanup (24h threshold) eventually soft-deletes idle workflows but does not touch already-soft-deleted rows. If retention of large `loop_state` payloads becomes a concern at scale, a future delta can add hard-deletion on a longer threshold — out of scope here.
- This delta builds on DLT-159 (conditions) and DLT-161 (composition); both are implemented. The implementation should focus on the minimal extensions required to lift loop semantics on top of the existing composition machinery, avoiding any parallel spawn / cascade / validation paths.
