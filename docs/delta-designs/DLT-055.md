# Design: DLT-055 - Plugin Update Mechanism

**Delta Spec**: [../delta-specs/DLT-055.md](../delta-specs/DLT-055.md)
**Status**: Approved

## Purpose

This document explains the design rationale for this delta: the modeling choices, data flow, system behavior, and architectural approach.

After implementation, the "Detected Impacts" section will guide reconciliation into feature design docs.

## Problem Context

The plugin system currently re-materializes every declared plugin on every startup, with no concept of plugin versions or available updates. Users cannot tell whether their installed plugins are current, and have no mechanism to apply updates beyond manually removing and re-installing.

**Constraints:**
- **No new long-lived dependencies.** Reuse `run_git()` subprocess calls, stdlib `hashlib`, and existing patterns.
- **Fail-safe updates.** A failed update must leave the existing plugin intact and functional — no half-replaced directories.
- **Source-specific semantics.** Git plugins auto-check daily; URL plugins check only on request; local plugins are always current (symlinks).
- **Atomic on-disk state.** Inherit the existing pip-style atomic-swap from `materializer.py`.
- **Database for state.** Plugin version and update status persist in a dedicated database table (per design decision), surviving restarts.
- **Central scheduler for periodic work.** Daily update checks use the existing scheduler (DES-010), not ad-hoc loops.

**Interactions:**
- **PluginManager** — gains update operations, per-plugin update locks, and `PluginStateRepository` dependency.
- **Materializer** — gains symlink path for local sources and `MaterializationResult` return type carrying version hashes.
- **Reconciler** — changes from always-re-materialize to first-time-only install.
- **MCP tools** — two new tools (`update_plugin`, `update_all_plugins`) alongside existing install/list/remove.
- **Scheduler** — one new `CronTrigger` job for daily update checks.
- **LoadedPlugin** — in-memory model unchanged; update status comes from `PluginState` lookup.

## Design Overview

The update mechanism adds a persistent version-tracking layer and two update flows (detection and application) to the existing plugin system. A new `PluginState` database model stores per-plugin version hashes and update status. Detection uses `git ls-remote` (lightweight remote ref resolution without downloading objects) for git sources and SHA-256 content hashing for URL sources. Application reuses the existing materializer's atomic-swap pattern, followed by a full unregister/re-register cycle for skills and events. A daily cron job on the central scheduler checks git-source plugins and notifies the user when updates are available.

```
┌──────────────────────────────────────────────────────────────┐
│ PluginState (database)                                       │
│  alias (PK), installed_version, update_status,               │
│  available_version, last_checked_at                          │
├──────────────────────────────────────────────────────────────┤
│ Update Detection (daily cron)                                │
│  Git: git ls-remote → compare SHA with installed_version     │
│  URL: skipped (check on explicit request only)               │
│  Local: n/a (symlink = always current)                       │
├──────────────────────────────────────────────────────────────┤
│ Update Application (MCP tools)                               │
│  update_plugin(alias)                                        │
│    lock → re-materialize → atomic swap → update version      │
│    → re-register (unregister old → discover new → register)  │
│  update_all_plugins()                                        │
│    iterate update-available → apply each sequentially        │
├──────────────────────────────────────────────────────────────┤
│ Startup Reconciliation (changed)                             │
│  Skip installed plugins → only materialize first-time        │
│  Migrate local copies → symlinks                             │
│  Persist initial PluginState for new installs                │
├──────────────────────────────────────────────────────────────┤
│ list_plugins (extended)                                      │
│  Join LoadedPlugin + PluginState → include update info       │
└──────────────────────────────────────────────────────────────┘
```

## Shape

| Part | Mechanism | Flag |
|------|-----------|:----:|
| **S1** | Plugin state database model — `PluginState` SQLAlchemy model (alias PK, installed_version, update_status, available_version, last_checked_at). `PluginStateRepository` for CRUD. New Alembic migration. | |
| **S2** | Git update detector — `git ls-remote` to resolve remote ref SHA without downloading objects. Annotated tags dereferenced via `^{}` suffix. Compare with stored `installed_version`. Network errors: retain previous status, log warning. | |
| **S3** | URL content hasher — `hashlib.file_digest()` (Python 3.11+) for SHA-256 of downloaded archive. Compare to stored hash. | |
| **S4** | Local source symlink materializer — `os.symlink()` replacing `shutil.copytree()` for local sources. Migration: detect existing copies on reconciliation, replace with symlink pointing to configured path. | |
| **S5** | Startup reconciliation refactor — skip plugins with existing install directories. Only materialize on first install. Keep orphan cleanup. Persist initial `PluginState` for new installs. | |
| **S6** | update_plugin MCP tool — per-plugin lock (non-blocking, error if held), re-materialize, atomic swap, update PluginState, re-register skills/events. Handle each source type. | |
| **S7** | update_all_plugins MCP tool — query plugins with `update-available`, apply sequentially via S6 logic, return structured summary. | |
| **S8** | Daily update check task — `CronTrigger` job on central scheduler (DES-010). Runs S2 for all git-source plugins, updates PluginState, sends notification if updates found. Task created during plugins bootstrap hook. | |
| **S9** | Plugin re-registration on update — on success: unregister skills, unsubscribe events, re-discover, re-register. On failure: new version stays on disk, old skills/events remain active, diagnostic attached. | |
| **S10** | Update status in list_plugins — extend output with `update_status`, `installed_version`, `available_version` from PluginState lookup. | |

### Cross-Layer Contracts

**Reconciliation → State persistence contract:**

```
reconcile(workspace, settings.plugins, state_repo)
    ├── For each [plugins.<alias>]:
    │   ├── If install_dir/<alias> exists with valid manifest:
    │   │   ├── Local source + not symlink → migrate to symlink
    │   │   └── Skip materialization
    │   ├── Else (first install):
    │   │   ├── result = materialize_<kind>(source, staging_dir)
    │   │   ├── _atomic_replace_dir(result.staging_dir, install_dir / alias)
    │   │   └── state_repo.upsert(alias, installed_version=result.version, update_status="unknown")
    │   └── Orphan cleanup (unchanged)
    └── Return reconciliation report
```

**Update application contract (update_plugin):**

```
apply_update(alias, manager, state_repo, bus)
    ├── Validate: alias exists, not local-source, not already updating
    ├── Acquire per-plugin lock (non-blocking → error if held)
    ├── result = materialize_<kind>(source, staging_dir)
    ├── manifest = parse_manifest(result.staging_dir)
    ├── validate_handlers(manifest, result.staging_dir, alias)
    ├── _atomic_replace_dir(result.staging_dir, install_dir / alias)
    ├── Update PluginState:
    │   ├── installed_version = result.version
    │   ├── update_status = "up-to-date"
    │   └── available_version = null
    ├── Re-register plugin:
    │   ├── Unregister old skills via remove_namespaced_source
    │   ├── Unsubscribe old events via wrapper._deactivate()
    │   ├── Re-discover: parse manifest, validate handlers
    │   ├── Re-register skills via add_namespaced_source
    │   └── Re-subscribe events
    ├── If re-registration fails:
    │   ├── Keep new materialized version on disk
    │   ├── Retain old skills and event subscriptions
    │   └── Attach diagnostic to PluginState
    ├── Release per-plugin lock
    └── Return success / error result
```

**Update application contract (update_all_plugins):**

```
apply_all_updates(manager, state_repo, bus)
    ├── Collect all plugins with update_status = "update-available"
    ├── Skip local-source plugins (report as skipped)
    ├── results = []
    ├── For each plugin (sequential):
    │   ├── try: apply_update(alias, ...)
    │   │   └── results.append({alias, status: "updated"})
    │   └── except:
    │       ├── results.append({alias, status: "failed", error: str(e)})
    │       └── Continue to next
    └── Return summary: {total, updated, skipped, failed, per_plugin: results}
```

**Daily check contract:**

```
plugin_update_check_tick(state_repo, loaded_plugins, bus)
    ├── git_plugins = [p for p in loaded_plugins if isinstance(p.source, GitPluginSource) and p.status == "loaded"]
    ├── updates_found = []
    ├── For each git_plugin:
    │   ├── remote_sha = git ls-remote <url> refs/heads/<ref> (or refs/tags/<ref>^{})
    │   ├── If remote_sha == state.installed_version:
    │   │   └── state_repo.upsert(alias, update_status="up-to-date", last_checked_at=now)
    │   ├── If remote_sha != state.installed_version:
    │   │   ├── state_repo.upsert(alias, update_status="update-available", available_version=remote_sha, last_checked_at=now)
    │   │   └── updates_found.append(alias)
    │   └── If error: retain previous status, log warning, update last_checked_at
    ├── If updates_found:
    │   └── dispatch notification listing aliases + available versions
    └── Log summary
```

**Integration Points:**
- **Materializer → Updater**: `MaterializationResult` carries version hash; updater reads it for state persistence
- **Updater → PluginStateRepository**: All state mutations go through the repository
- **Updater → PluginManager**: Manager owns the per-plugin lock map and orchestrates re-registration
- **Daily check → Event bus**: Notification dispatched via existing notification event pattern
- **list_plugins → PluginStateRepository**: Lookup state for each plugin to enrich output

### Shared Logic

- **`MaterializationResult` dataclass**: Shared between reconciler (first-time install captures version) and updater (update captures version). Replaces the previous bare `Path` return from materialize functions.
- **`run_git()` import**: Reused from `git/sync.py` for `git ls-remote` in the update detector — same subprocess wrapper, same error handling.
- **`_atomic_replace_dir()` helper**: Existing helper from `materializer.py`, reused unchanged for update swaps.
- **`PluginStateRepository`**: Shared between reconciler (initial state creation), daily check (status updates), updater (version updates), tools (status queries), and list_plugins (enrichment).

## Modeling

### PluginState (domain model)

```
PluginState (frozen dataclass)
├── alias: str
├── installed_version: str | None     (git: 40-char SHA, url: SHA-256 hex, local: null)
├── update_status: Literal["unknown", "up-to-date", "update-available", "stale-fallback"]
├── available_version: str | None     (remote SHA when update available)
├── last_checked_at: datetime | None
└── created_at: datetime
```

### PluginStateModel (ORM model)

```
PluginStateModel (SQLAlchemy)
├── __tablename__ = "plugin_state"
├── alias: String (PK)
├── installed_version: String (nullable)
├── update_status: String (default "unknown")
├── available_version: String (nullable)
├── last_checked_at: DateTime (nullable)
└── created_at: DateTime (server_default=now())
```

### MaterializationResult (new)

```
MaterializationResult (dataclass)
├── staging_dir: Path
└── version: str | None
    (git: full 40-char commit SHA from `git rev-parse HEAD` in clone)
    (url: SHA-256 hex digest of downloaded archive via hashlib.file_digest)
    (local: None — symlinks have no version state)
```

### UpdateStatus values

```
"unknown"           — plugin installed but never checked
"up-to-date"        — last check found no newer version
"update-available"  — last check found a newer version
"stale-fallback"    — source unreachable, using cached copy (inherited from LoadedPlugin.status)
```

### UpdateResult (for bulk update summary)

```
UpdateResult (frozen dataclass)
├── alias: str
├── status: Literal["updated", "failed", "skipped"]
├── error: str | None
└── message: str | None

UpdateSummary (frozen dataclass)
├── total: int
├── updated: int
├── skipped: int
├── failed: int
└── results: list[UpdateResult]
```

### LoadedPlugin (unchanged)

The existing `LoadedPlugin` dataclass is not modified. Update status is looked up from `PluginState` at query time (e.g., `list_plugins`). This keeps the in-memory plugin model focused on registration state and avoids coupling it to the persistence layer.

### Per-plugin lock map

```
PluginManager._update_locks: dict[str, asyncio.Lock]
    Lazily created per alias on first update attempt.
    Non-blocking acquisition: if lock is held, return "update already in progress" error.
    Cleared when plugin is removed.
```

### Startup reconciliation (changed)

```
plugins_hook(ctx)
    ├── mkdir .tachikoma/plugins/
    ├── append .tachikoma/plugins/ to .gitignore (idempotent)
    ├── state_repo = PluginStateRepository(db_session)
    ├── reconcile(workspace, settings.plugins, state_repo)
    │   └── For each [plugins.<alias>]:
    │       ├── If install_dir/<alias> exists with valid manifest:
    │       │   ├── If local source AND not symlink:
    │       │   │   └── Migrate: backup copy, create symlink, verify, remove backup
    │       │   └── Skip materialization
    │       ├── Else (first install):
    │       │   ├── result = materialize_<kind>(source, staging_dir)
    │       │   ├── _atomic_replace_dir(result.staging_dir, install_dir / alias)
    │       │   └── state_repo.upsert(alias, installed_version=result.version)
    │       └── Orphan cleanup (unchanged)
    ├── discover(install_dir)  (unchanged)
    ├── PluginManager(..., state_repo)
    ├── ctx.extras populated
    └── Register daily check task (if not exists)
```

### Daily update check (new)

```
scheduler tick (CronTrigger, once daily)
    └── plugin_update_check_tick(state_repo, manager, bus)
        ├── git_plugins = loaded plugins with GitPluginSource
        ├── For each git_plugin:
        │   ├── remote_sha = run_git(["ls-remote", url, ref_spec])
        │   │   └── ref_spec = "refs/heads/<ref>" or "refs/tags/<ref>^{}"
        │   ├── Compare remote_sha with state.installed_version
        │   └── Update PluginState accordingly
        └── If any update-available:
            └── dispatch_notification(bus, "Plugin updates available: ...")
```

### Single plugin update (new)

```
update_plugin(alias) MCP tool
    └── manager.update(alias)
        ├── Lookup plugin + state
        ├── Validate (exists, not local, not locked)
        ├── Acquire per-plugin lock (non-blocking)
        ├── result = materialize_<kind>(source, staging_dir)
        │   └── Returns MaterializationResult with version hash
        ├── parse_manifest + validate_handlers
        ├── _atomic_replace_dir(result.staging_dir, install_dir)
        ├── state_repo.upsert(alias, installed_version=result.version, update_status="up-to-date")
        ├── Re-register:
        │   ├── skills_listener: remove_namespaced_source(alias)
        │   ├── lifecycle: unsubscribe old wrappers
        │   ├── loader: re-discover plugin at install_dir
        │   ├── skills_listener: add_namespaced_source(alias, skill_paths)
        │   └── lifecycle: subscribe new event handlers
        └── Release lock
```

### Bulk plugin update (new)

```
update_all_plugins() MCP tool
    └── manager.update_all()
        ├── Query plugins with update_status = "update-available"
        ├── For each (sequential):
        │   ├── If local: record as skipped
        │   ├── Else: apply_update(alias) → record result
        │   └── Continue on failure
        └── Return UpdateSummary
```

### list_plugins with update info (extended)

```
list_plugins() MCP tool
    └── manager.list()
        └── For each LoadedPlugin:
            ├── Existing: alias, source, status, skills, config
            └── NEW: lookup PluginState → append update_status, installed_version, available_version
```

## Key Decisions

### Dedicated database table for plugin state

**Choice**: New `plugin_state` SQLAlchemy table with a `PluginStateRepository`, following the project's established persistence pattern (ADR-007).
**Why**: Plugin version and update status must survive process restarts. A dedicated table provides structured, queryable storage with type-safe access through the repository pattern already used throughout the project. It avoids mixing plugin concerns with general app state and keeps data management centralized.
**Alternatives Considered**:
- **JSON sidecar file** (`.tachikoma/plugins/<alias>/.plugin-state.json`): Simpler but co-locates transient state with the plugin's own files, risks getting out of sync, and adds filesystem operations to what is fundamentally a data-access concern.
- **Key-value app_state table** (ADR-013): Would work but mixes plugin-specific version tracking with general-purpose state, making queries harder and schema evolution awkward.

**Sources**: Project's own ADR-007 (persistence layer), existing patterns in `tasks/` and `sessions/` subsystems.
**Consequences**: Pro: Structured, queryable, follows established patterns. Pro: Clean separation of concerns. Con: Requires an Alembic migration. Con: Plugin subsystem gains a database dependency.

### `git ls-remote` for update detection

**Choice**: Use `git ls-remote` to resolve the remote ref SHA without downloading any git objects, then compare with the stored `installed_version`.
**Why**: `git ls-remote` performs a single HTTP request (~1-5 KB transfer) returning only the ref-to-SHA mapping. This is significantly lighter than `git fetch` (which negotiates and downloads objects even in a shallow clone). For a daily check running against potentially many plugins, minimizing per-check overhead matters.
**Alternatives Considered**:
- **`git fetch` in existing clone**: Would work but downloads objects unnecessarily for detection-only. Adds disk I/O in the clone directory for a check that should be read-only at the state level.
- **HTTP HEAD request against GitHub API**: GitHub-specific; would need different logic per git host.

**Sources**: Git documentation (git-ls-remote docs, git v2.46.0); research confirming ~50-200ms for ls-remote vs ~200-500ms for shallow fetch.
**Options Researched**: `git ls-remote`, `git fetch --dry-run`, `git fetch` in existing clone, GitHub REST API.
**Why This Over Alternatives**: No objects downloaded, no local git state mutation, works identically for all git hosting providers, fastest option.
**Consequences**: Pro: Minimal network overhead. Pro: No local state mutation during detection. Con: Needs `^{}` suffix for annotated tags to dereference to commit SHAs. Con: Requires the git URL (not just the local clone path) — already available from the source model.

### Re-clone for update application

**Choice**: Reuse the existing `materialize_git()` function (fresh shallow clone) for applying git updates, rather than `git fetch` + `git checkout` in the existing clone.
**Why**: The spec explicitly says "re-materialized from the remote" (R4 AC). Re-cloning reuses the battle-tested materializer and its atomic-swap logic. An in-place fetch+checkout would require new error paths for dirty working trees, ref divergence, and shallow-boundary issues. The cost difference (downloading ~1-50 KB for a shallow clone) is negligible for a user-initiated operation.
**Alternatives Considered**:
- **In-place `git fetch --depth=1` + `git checkout origin/<ref>`**: More efficient on paper but introduces git state management complexity. The existing clone might have local changes from the plugin's init hook, requiring stash/reset logic.

**Consequences**: Pro: Reuses proven materializer code. Pro: Clean state — no residual git history. Pro: Atomic swap already handles failure safety. Con: Downloads objects twice (once for ls-remote detection, once for clone — but the clone is user-initiated and expected).

### Per-plugin asyncio.Lock for update concurrency

**Choice**: A lazily-populated `dict[str, asyncio.Lock]` on `PluginManager`. `update_plugin` acquires the lock non-blocking (returns "update already in progress" error if held). `update_all_plugins` acquires each lock sequentially.
**Why**: The spec requires that concurrent update attempts for the same alias return an error (R4 AC). Per-plugin locks allow different plugins to be updated concurrently (e.g., `update_all_plugins` could overlap with a user's `update_plugin` for a different alias). Using the existing global `_lock` would serialize everything unnecessarily.
**Alternatives Considered**:
- **Global PluginManager lock for updates**: Simpler but prevents concurrent updates for different plugins and doesn't provide the non-blocking "already in progress" error (second call would block instead).
- **`set[str]` tracking in-progress aliases**: Would work but requires careful cleanup on all error paths; `asyncio.Lock` handles this naturally via context managers.

**Consequences**: Pro: Precise concurrency control matching spec requirements. Pro: Non-blocking error for concurrent same-alias updates. Con: Lock map needs cleanup when plugins are removed. Con: Slightly more complex than a single global lock.

### Symlink creation for local sources

**Choice**: Replace `shutil.copytree()` with `os.symlink()` for local-source plugins during materialization. Migration: existing copies are replaced with symlinks on the next reconciliation.
**Why**: The spec requires that local plugins "always reflect live source" (R3). A symlink achieves this trivially — no copy, no update needed, changes are immediately visible. The existing copy approach creates unnecessary duplication and a stale-copy problem.
**Migration path**: During reconciliation, if a local-source plugin's install directory is not a symlink, remove the directory and create a symlink. If the configured source path no longer exists, retain the copy and mark as `stale-fallback`.
**Alternatives Considered**:
- **Keep copy + filesystem watcher**: Over-engineered for the use case; requires inotify/watchdog dependency.
- **Keep copy + periodic sync**: Defeats the spec's "always reflect live source" requirement.

**Consequences**: Pro: Zero-copy, always current. Pro: No update detection needed for local sources. Con: Symlinks break if the source path is moved or deleted. Con: Source path must be absolute (already validated by source model).

### `hashlib.file_digest()` for URL content hashing

**Choice**: Use Python 3.11+'s `hashlib.file_digest()` for computing SHA-256 of downloaded archives during URL-source materialization.
**Why**: Available in the project's Python version (3.11+), purpose-built for file hashing with streaming internally, and avoids manual chunked reads. One-liner that handles memory-efficient hashing regardless of file size.
**Alternatives Considered**:
- **Manual chunked `hashlib.sha256()` loop**: Works but `file_digest` is the idiomatic approach since 3.11.
- **Hash the extracted directory**: Would require recursive hashing of all files, sensitive to file ordering, permissions, and metadata. Hashing the archive is deterministic.

**Consequences**: Pro: Simple, memory-efficient, stdlib. Con: Archive hash changes if the archive is re-packed (same content, different compression). Mitigated: URL sources are typically stable archives from a specific URL.

### LoadedPlugin unchanged; state looked up at query time

**Choice**: `LoadedPlugin` does not gain update-status fields. Update status comes from `PluginState` lookup when needed (e.g., in `list_plugins`).
**Why**: `LoadedPlugin` is a frozen dataclass representing the in-memory registration state of a plugin. Update status is persistence-layer data that changes asynchronously (daily checks). Coupling them would force updates to `LoadedPlugin` instances whenever the check runs, complicating the model. Keeping them separate means `LoadedPlugin` stays focused on registration and the database stays the source of truth for version/update state.
**Alternatives Considered**:
- **Add update fields to LoadedPlugin**: Would require re-creating the frozen dataclass on every status change, coupling the persistence layer to the in-memory model.

**Consequences**: Pro: Clean separation of concerns. Pro: LoadedPlugin stays unchanged (no migration of existing code). Con: `list_plugins` needs a join between in-memory plugins and database state (a simple dict lookup by alias).

## System Behavior

### Invariants

1. **First-time-only materialization**: Startup reconciliation only materializes plugins that don't have an existing install directory. Already-installed plugins are left untouched.
2. **Version hashes captured at materialization**: Every materialization (first install or update) captures the version hash (git SHA, URL hash, or null for local) and persists it to `PluginState`.
3. **Detection does not mutate on-disk state**: `git ls-remote` only reads remote refs. It does not fetch, modify the local clone, or change any files.
4. **Update application is atomic**: The pip-style atomic swap from the existing materializer applies. A failed update never leaves a half-replaced directory.
5. **Re-registration is all-or-nothing**: On a successful materialization, old skills/events are fully removed before new ones are registered. On re-registration failure, old skills/events remain active.
6. **Local plugins have no version state**: Symlinks are always current. `installed_version` is null, `update_status` is not queried.
7. **Daily check is stateless**: Each run checks all git-source plugins independently. A partially completed check does not affect the next run.
8. **PluginState survives restarts**: The database table is the source of truth for version and update status across process restarts.

### Scenario: Fresh install of a git plugin

**Given**: `[plugins.code-review]` declares a git source with `ref = "v1.0.0"`. No existing install directory.
**When**: Startup reconciliation runs.
**Then**: `materialize_git()` performs shallow clone, captures commit SHA as version. `_atomic_replace_dir()` installs. `PluginState` created with `installed_version = <sha>`, `update_status = "unknown"`.
**Rationale**: First install captures version for future comparison.

### Scenario: Startup with existing git plugin (no re-materialize)

**Given**: `[plugins.code-review]` declares a git source. `.tachikoma/plugins/code-review/` exists with valid manifest.
**When**: Startup reconciliation runs.
**Then**: Reconciler detects existing directory, skips materialization. `PluginState` retains previous values (no change).
**Rationale**: No unnecessary re-cloning on every restart.

### Scenario: Daily check finds update

**Given**: Git plugin `code-review` tracking branch `main`. Stored `installed_version = abc123`. Remote `refs/heads/main` now resolves to `def456`.
**When**: Daily update check runs.
**Then**: `git ls-remote` returns `def456`. Compared with stored `abc123` — differs. `PluginState` updated: `update_status = "update-available"`, `available_version = "def456"`. Notification dispatched listing `code-review`.
**Rationale**: User is informed that an update exists and can choose to apply it.

### Scenario: Daily check finds no update

## Notes

- The update detector uses `run_git()` from `git/sync.py` for `git ls-remote`, reusing the existing subprocess wrapper and its error handling.
- Annotated tag dereferencing (`refs/tags/<tag>^{}`) is critical for correct SHA comparison — without it, annotated tags return the tag object SHA, not the commit SHA.
- The daily check uses `CronTrigger` from the central scheduler (DES-010), not the task subsystem. It's a scheduler job (a zero-arg async tick function registered with the central `scheduler()` loop), not a `TaskDefinition` (which involves instance generation, status tracking, and database records). This distinction matters: the daily check is a system-internal housekeeping operation that doesn't need task-instance bookkeeping. The job is registered in `__main__.py` alongside other scheduler jobs, not created as a task definition.
- `hashlib.file_digest()` is a Python 3.11 addition that handles streaming internally — no manual chunked reads needed.
- The per-plugin lock map is lazily populated and cleaned up on plugin removal. This avoids pre-allocating locks for plugins that never get updated.
