# Design: DLT-075 - Re-evaluate skill context per message

**Delta Spec**: [../delta-specs/DLT-075.md](../delta-specs/DLT-075.md)
**Status**: Draft

## Purpose

This document explains the design rationale for this delta: the modeling choices, data flow, system behavior, and architectural approach.

After implementation, the "Detected Impacts" section will guide reconciliation into feature design docs.

## Problem Context

The skills context provider currently runs only on the first message of a new session. Its output is persisted as context entries and reused for all subsequent messages. When a conversation shifts topic mid-session, newly relevant skills are never loaded because classification was based on the first message alone.

**Constraints:**
- The Claude Agent SDK creates a fresh `ClaudeSDKClient` per message exchange — agents and system prompt are set per invocation, not locked to the session
- Context entries are persisted to the database and loaded on each message — they are the source of truth for what the agent sees
- Only the skills provider needs per-message evaluation; memory and projects remain session-gated
- The pre-processing pipeline runs providers in parallel with error isolation (existing pattern)
- Classification uses an Opus low-effort forked agent via `query()` (DES-007), adding ~1-2s latency per invocation

**Interactions:**
- The per-message pipeline runs BEFORE the SDK client is created (same timing as session-gated pre-processing)
- Context entries are loaded from DB before the pipeline runs, so providers can inspect what's already loaded
- Newly detected skills are appended as context entries, then the system prompt is re-assembled from all entries (including new)
- Agents derived from loaded skill names + registry lookup, passed to `ClaudeAgentOptions.agents`

## Design Overview

Introduce a `MessagePreProcessingPipeline` (mirroring the existing `MessagePostProcessingPipeline`) that runs per-message context providers on every message. The skills context provider moves from the session-gated `PreProcessingPipeline` into this new per-message pipeline. Providers in the per-message pipeline receive the session's existing context entries, enabling them to determine what's already loaded and filter accordingly.

Context entries become the single source of truth: skill names are extracted from existing entries, and agents are derived from those names via registry lookup. No independent state is maintained on the coordinator.

```
┌─────────────────────────────────────────────────────────────┐
│  Coordinator (send_message)                                 │
│                                                             │
│  1. Load context entries from DB                            │
│  2. Derive loaded skill names from entries (owner="skills")  │
│  3. Derive agents from skill names + registry               │
│                                                             │
│  if is_new_session:                                         │
│    4a. Run session-gated pipeline (memory, projects)        │
│    4b. Run per-message pipeline (skills, with empty entries) │
│  else:                                                       │
│    4. Run per-message pipeline only (skills, with entries)   │
│                                                             │
│  5. Save new context entries from pipeline results           │
│  6. Re-derive agents from all entries (including new)        │
│  7. Build system prompt from all entries                    │
│  8. Create SDK client with derived agents + system prompt    │
└─────────────────────────────────────────────────────────────┘
```

## Shape

| Part | Mechanism | Flag |
|------|-----------|:----:|
| **S1** | Per-message pre-processing pipeline — new `MessagePreProcessingPipeline` runs on every message; skills provider registers here instead of session-gated pipeline | |
| **S2** | Already-loaded skills detection — extract skill names from existing context entries (owner="skills") via regex on `<skill name="...">` attribute; entries are the source of truth | |
| **S3** | Registry filtering — provider filters registry skills by exclusion set before classification; skip entirely when no unloaded skills remain (R8) | |
| **S4** | Unified provide() — single `provide(message, existing_entries)` method handles both initial (empty entries) and subsequent (populated entries) evaluations | |
| **S5** | Context entry appending — newly detected skills persisted as additional context entries; existing entries never modified or replaced | |
| **S6** | Agent derivation — agents derived from loaded skill names + registry lookup; no independent `_agents` state on coordinator | |
| **S7** | Per-message error resilience — pipeline's parallel error isolation handles provider failures without blocking the message | |

## Components

### Implementation Structure

| Layer/Component | Responsibility | Key Decisions |
|-----------------|----------------|---------------|
| `per_message_pre_processing.py` (new) | `MessageContextProvider` ABC + `MessagePreProcessingPipeline` class | New file mirroring `message_post_processing.py` structure; pipeline runs providers in parallel with error isolation |
| `skills/context_provider.py` | `SkillsContextProvider` moves from `ContextProvider` to `MessageContextProvider` | Receives `existing_entries` in `provide()`; extracts loaded skill names, filters registry, classifies unloaded only |
| `coordinator.py` | Orchestrates both pipelines; derives agents from entries + registry | New `skill_registry` constructor param; agent derivation from entries instead of independent `_agents` state |
| `__main__.py` | Registers skills provider in per-message pipeline instead of session-gated pipeline | Skills provider moves from `pre_pipeline.register()` to `msg_pre_pipeline.register()` |
| `pre_processing.py` | Unchanged — session-gated pipeline continues for memory and projects | Skills provider removed from session-gated registration |

### Cross-Layer Contracts

**MessageContextProvider ABC**:
```python
class MessageContextProvider(ContextProvider):
    async def provide(self, message: str, *, existing_entries: list[SessionContextEntry]) -> ContextResult | None:
```

Extends `ContextProvider` so that the provider can be used in both pipeline types. The `existing_entries` parameter gives providers access to the session's current context state.

**Per-message pipeline contract**:
```python
pipeline = MessagePreProcessingPipeline()
pipeline.register(SkillsContextProvider(agent_defaults, registry))
results = await pipeline.run(message, existing_entries=entries)
# → list[ContextResult]
```

**Integration Points**:
- `MessagePreProcessingPipeline.run()` — receives message + existing entries, returns `list[ContextResult]`
- Coordinator loads entries → runs per-message pipeline → saves new entries → re-derives agents → builds system prompt
- SkillsContextProvider extracts loaded skill names from entries, filters registry, classifies only unloaded skills
- Coordinator derives agents from all loaded skill names + registry (not from results)

### Shared Logic

- **Skill name extraction** (`_extract_skill_names(entries)`): Shared regex utility that parses `<skill name="...">` from entries with `owner="skills"`. Used by both the coordinator (to check if evaluation is needed) and the skills provider (to filter the registry).
- **Agent derivation** (`_derive_agents(skill_names, registry)`): Looks up agents for given skill names from the registry. Used by the coordinator after loading entries.
- **DES-007 pattern**: SkillsContextProvider continues to use Opus low-effort classification via `query()`, consistent with the existing pattern.

## Modeling

### Data Types

```
MessageContextProvider(ContextProvider)       [new ABC]
├── provide(message, *, existing_entries) → ContextResult | None

MessagePreProcessingPipeline                [new pipeline]
├── __init__()
├── register(provider: MessageContextProvider)
└── run(message, *, existing_entries) → list[ContextResult]

SkillsContextProvider(MessageContextProvider) [modified]
├── _agent_defaults: AgentDefaults
├── _registry: SkillRegistry
└── provide(message, *, existing_entries) → ContextResult | None
    ├── Extract loaded skill names from entries
    ├── Filter registry to unloaded skills only
    ├── Skip if no unloaded skills (R8)
    ├── Classify via query() (DES-007)
    └── Return ContextResult for newly detected skills

Coordinator                                  [modified]
├── _skill_registry: SkillRegistry | None     [new]
├── _msg_pre_pipeline: MessagePreProcessingPipeline | None  [new]
├── _agents: dict[str, AgentDefinition] | None   [derived, not stored]
└── send_message()
    ├── Load entries → derive skill names → derive agents
    ├── Session-gated pipeline (memory, projects only)
    ├── Per-message pipeline (skills)
    ├── Save new entries → re-derive agents
    └── Build system prompt → create client
```

### Session Context Entry Flow

```
Session starts → no entries
  ↓
First message → per-message pipeline runs with empty entries
  → SkillsContextProvider classifies full registry
  → Result saved as new entries: [("skills", "<skill name='A'>..."), ("skills", "<skill name='B'>...")]
  ↓
Second message → entries loaded: [A, B]
  → SkillsContextProvider filters out A, B from registry
  → Classifies remaining skills → detects C
  → Result saved as new entry: ("skills", "<skill name='C'>...")
  ↓
Third message → entries loaded: [A, B, C]
  → SkillsContextProvider filters out A, B, C
  → No unloaded skills remain → returns None (R8: skip)
  → No new entries saved

Topic shift → new session → all entries cleared → cycle restarts
```

## Data Flow

### Per-message evaluation flow

```
1. Coordinator.send_message()
2. Load context entries from DB (includes foundational + previous skills)
3. Extract skill names from entries with owner="skills" via regex
4. Derive agents from skill names + registry lookup
5. if is_new_session:
      a. Run session-gated pipeline (memory, projects) → save results as entries
   b. [Run per-message pipeline with empty entries] — skills classifies full registry
   else:
      a. [Run per-message pipeline with loaded entries] — skills classifies unloaded only
6. Run per-message pipeline: MessagePreProcessingPipeline.run(message, existing_entries=entries)
   → SkillsContextProvider.provide(message, existing_entries=entries)
      ├── Extract loaded skill names from existing_entries
      ├── Filter registry to unloaded skills
      ├── If no unloaded skills → return None (R8 skip)
      ├── Classify via query() with Opus low effort (DES-007)
      └── Return ContextResult for newly detected skills
7. If results:
   a. Save new context entries (append, don't replace)
   b. Append new entries to in-memory entries list
   c. Re-derive agents from all entries (including new)
8. Build system prompt from all entries
9. Build SDK options with derived agents + system prompt
10. Create client, stream response
```

### Unified flow (first message = subsequent message)

The same `provide()` method handles both cases:
- First message: `existing_entries=[]` → no loaded skills → classify full registry → save results as entries
- Subsequent: `existing_entries=[A, B]` → loaded skills = {A, B} → classify registry minus {A, B} → append new entries

No separate code paths. The pipeline and provider are identical in both cases.

## Key Decisions

### SDK supports per-message agent changes

**Choice**: Rely on the SDK's existing behavior where agents are passed via `initialize` (not locked to session state) and system prompt via `--append-system-prompt` CLI flag.
**Why**: SDK research confirmed that `ClaudeSDKClient` is created fresh per message exchange. Agents go through the `initialize` control request (SDK source: `_internal/query.py` lines 151-156), not session state. System prompt is a CLI flag (`_internal/transport/subprocess_cli.py` lines 171-182). Both can change between resumed invocations without SDK modification.
**Sources**: Claude Agent SDK v0.1.56 source analysis — `_internal/query.py`, `_internal/transport/subprocess_cli.py`. Confirmed that `--resume` only loads conversation history, not agent or system prompt state.
**Options Researched**:
- Assume agents are session-locked: Would require SDK modification or per-session agent management — contradicted by source analysis
- Verify from source: Confirmed that `initialize` always sends current agents regardless of resume state

**Consequences**:
- Pro: No SDK modifications needed
- Pro: Agent accumulation works by simply updating the coordinator's agent derivation before each client creation
- Con: None — the SDK already supports this

### Per-message pipeline over direct coordinator call

**Choice**: Create `MessagePreProcessingPipeline` mirroring the existing `MessagePostProcessingPipeline`, rather than having the coordinator call the skills provider directly.
**Why**: The project already has a paired pipeline pattern — `MessagePostProcessingPipeline` runs per-message post-response. Creating the pre-response counterpart keeps the architecture symmetric. It also makes DLT-076 (memory re-evaluation) a simple registration away rather than requiring coordinator changes.
**Sources**: Codebase analysis — `message_post_processing.py` establishes the per-message pipeline pattern.
**Options Researched**:
- Direct coordinator call to skills provider: Simpler for this delta but creates a one-off pattern that DLT-076 would need to replicate
- New pipeline class: Slightly more code now, but follows established patterns and is extensible

**Consequences**:
- Pro: Architectural consistency with `MessagePostProcessingPipeline`
- Pro: DLT-076 (memory re-evaluation) becomes a registration, not a coordinator change
- Pro: Pipeline handles parallel execution and error isolation automatically
- Con: New file + new ABC (minimal overhead)

### SkillsContextProvider returns content only (no agents)

**Choice**: `SkillsContextProvider.provide()` returns `ContextResult` with `content` populated but `agents=None`. The coordinator derives agents from entries + registry independently.
**Why**: Since entries are the source of truth, the agents field on `ContextResult` is redundant — the coordinator already re-derives agents from all entries after saving new ones. Having the provider also populate agents creates a dual source of truth that could diverge.
**Sources**: Design analysis — user feedback on entries as source of truth.

**Consequences**:
- Pro: Single source of truth for agents (entries + registry)
- Pro: Provider becomes simpler — only responsible for skill content
- Pro: No risk of agents in ContextResult diverging from agents derived from entries
- Con: ContextResult.agents field unused for skills (acceptable — field is optional)

### Registry lookup failure for deleted skills

**Choice**: When deriving agents, skill names in entries that don't exist in the registry (skill was deleted from filesystem) are silently skipped with a debug log.
**Why**: Skills can be deleted at runtime via the filesystem watcher. The entry persists (it's historical context), but the registry no longer has the skill. Including the deleted skill's agents would fail anyway, and logging at debug level avoids noisy warnings for a benign condition.
**Sources**: Codebase analysis — registry's `get_agents_for_skill()` returns empty dict for missing skills; existing pattern of graceful degradation.

**Consequences**:
- Pro: Handles runtime skill deletion gracefully
- Pro: Entry content still includes the skill description (readable by the agent as context even if agents are gone)
- Con: Agent loses access to deleted skill's agents (correct behavior — skill no longer exists)

### Entries as single source of truth (no independent agent state)

**Choice**: Derive both loaded skill names and agents from context entries. Remove `self._agents` as independent coordinator state.
**Why**: The user identified that context entries are already the source of truth — they persist across messages, survive session resume, and are already loaded for system prompt assembly. Maintaining separate state creates a synchronization risk.
**Sources**: User feedback during design interview.
**Options Researched**:
- In-memory `_loaded_skill_names` set + `_agents` dict: Two new coordinator fields to manage and keep in sync
- Entries as source of truth: Zero new coordinator fields, single source, naturally consistent

**Consequences**:
- Pro: Zero new coordinator state fields
- Pro: Naturally consistent — entries and agents always agree
- Pro: Session resume works automatically (entries are persisted)
- Con: Agent derivation requires registry access on every message (negligible — dict lookup)
- Con: Removes `self._agents` as a constructor parameter (breaking change for any external consumers, but coordinator is internal)

### Skill name extraction from XML content

**Choice**: Parse skill names from context entry content using regex on `<skill name="([^"]+)"`.
**Why**: The content format is produced by our own code (`SkillsContextProvider`), so producer and consumer are always in sync. A schema migration (adding a metadata field) would be more robust but adds complexity for a derived value that's already reliably present.
**Sources**: Codebase analysis — `SkillsContextProvider` generates `<skill name="..." directory="...">` blocks.
**Options Researched**:
- Regex parsing from content: Zero schema changes, simple extraction, self-consistent
- New metadata field on context entries: More robust to format changes, but requires DB migration for a derived value
- Separate tracking table: Most normalized, but over-engineered for this use case

**Consequences**:
- Pro: No schema migration needed
- Pro: Simple, deterministic extraction
- Con: Tied to content format (mitigated: same codebase controls both)

### ContextProvider ABC unchanged

**Choice**: `MessageContextProvider` extends `ContextProvider` with an additional keyword argument rather than creating a standalone ABC.
**Why**: This lets the same provider class be used in both pipelines if needed. The base `provide(message)` signature works for the session-gated pipeline (no entries to pass). The extended `provide(message, existing_entries=...)` works for the per-message pipeline.
**Sources**: Design analysis — `ContextProvider` is the established interface.
**Options Researched**:
- Completely separate ABC: Clean separation but prevents code reuse
- Extending existing ABC: Backward compatible, allows dual registration if needed

**Consequences**:
- Pro: Backward compatible — existing providers unchanged
- Pro: Skills provider can be registered in either pipeline
- Con: Slightly looser typing (optional keyword arg instead of required)

### Skills provider moves entirely to per-message pipeline

**Choice**: `SkillsContextProvider` is removed from the session-gated `PreProcessingPipeline` and registered only in the `MessagePreProcessingPipeline`.
**Why**: Running skills in both pipelines would cause double classification on the first message (session-gated + per-message both running). Moving it entirely avoids this. On the first message, the per-message pipeline runs with empty entries → same result as the current session-gated behavior.
**Sources**: Codebase analysis — double invocation would waste an LLM call.

**Consequences**:
- Pro: No double classification on first message
- Pro: Skills evaluation always goes through the same code path (S4: unified process)
- Con: Session-gated pipeline no longer includes skills (memory and projects only)

## System Behavior

### Invariants

1. **Context entries are the source of truth**: Loaded skills and agents are always derived from persisted context entries, never from independent coordinator state.
2. **Skills accumulate, never remove**: Within a session, skills are appended as new context entries. Existing entries are never modified or deleted.
3. **Unified classification process**: The same `provide()` method handles both initial (empty entries) and subsequent (populated entries) evaluations.

### Scenario: First message — no skills loaded yet

**Given**: A new session with no context entries
**When**: The user sends their first message
**Then**: Per-message pipeline runs with `existing_entries=[]`. Skills provider classifies against the full registry. Results are saved as new entries. Agents are derived from entries.
**Rationale**: Same behavior as current session-gated pipeline, but through the per-message path.

### Scenario: Subsequent message — new skill relevant

**Given**: An active session with skills A and B in context entries
**When**: The user sends a message relevant to skill C
**Then**: Per-message pipeline runs with existing entries. Provider extracts {A, B}, classifies against registry minus {A, B}, detects C. New entry for C is appended. Agents re-derived to include C's agents.
**Rationale**: Incremental classification — only unloaded skills are considered.

### Scenario: All skills loaded — skip evaluation

**Given**: An active session where all registry skills are already in context entries
**When**: The user sends a new message
**Then**: Provider finds no unloaded skills and returns None immediately (no LLM call). No new entries saved. Existing agents unchanged.
**Rationale**: R8 — skip when no unloaded skills remain. Zero latency overhead.

### Scenario: Topic shift — fresh start

**Given**: An active session with accumulated skills
**When**: Boundary detection detects a topic shift
**Then**: Session closes, post-processing fires. New session created with no entries. Per-message pipeline runs with empty entries → full classification.
**Rationale**: Session boundary naturally clears all accumulated state.

### Scenario: Session resume — preserved context

**Given**: A closed session with skills A and B in context entries
**When**: Boundary detection matches and resumes that session
**Then**: Session reopens. Context entries for A and B are loaded. Provider sees {A, B} as loaded, classifies only remaining skills. Agents derived from {A, B} + registry.
**Rationale**: Entries are persisted, so resumed sessions naturally have their skills context. No special resume handling needed.

### Scenario: Classification failure on subsequent message

**Given**: An active session with existing skills context
**When**: The skills provider fails (SDK error, timeout)
**Then**: Pipeline's error isolation catches the failure, logs it, and continues. No new entries saved. Existing entries and agents remain intact. Message proceeds normally.
**Rationale**: R7 — graceful error handling. Pipeline's existing error isolation handles this automatically.

### Scenario: Registry changes mid-session (hot reload)

**Given**: An active session with skills A and B loaded
**When**: A new skill C is added to the registry via filesystem watcher
**Then**: Provider calls `registry.refresh()` (existing behavior). Registry now includes C. On the next message, provider sees {A, B} loaded, classifies against {C} (and any others). If C is relevant, it's detected and appended.
**Rationale**: Hot reload integrates naturally — new skills appear in the unloaded set on the next evaluation.
