## Purpose

This document explains the design rationale for this delta: the modeling choices, data flow, system behavior, and architectural approach.

After implementation, the "Detected Impacts" section will guide reconciliation into feature design docs.

## Problem Context

The memory context provider searches stored memories on every user message via a Glob → Grep → Read pattern. For facts and preferences directories, Glob discovers all `.md` files, then the agent uses Grep and Read to evaluate relevance. This means every search incurs the cost of directory listing and content inspection even when most files are irrelevant to the current message.

A `MEMORY.md` index file in each directory maps filenames to one-line descriptions. The search agent reads the index first and goes directly to relevant files — eliminating Glob-based discovery for facts and preferences. All write paths (extraction processors, maintenance agents) update the index when they modify files.

**Constraints:**
- The index is maintained by LLM agents (extraction, maintenance), not by Python code — consistent with DES-004 where agents perform all file I/O
- Episodic memories are excluded — they are date-organized and searched differently
- A missing or stale index must not break the system — graceful fallback to the current Glob pattern
- The index must remain human-readable markdown

**Interactions:**
- Memory context provider (`context_provider.py`): reads index on search path
- Facts/preferences extraction processors (`facts.py`, `preferences.py`): update index on write
- Maintenance ticks (`maintenance.py`): light consistency checks (Mon–Sat) and heavy rebuild (Sunday)
- Bootstrap hook (`hooks.py`): creates initial index on first run

## Design Overview

The design adds a `MEMORY.md` file to `memories/facts/` and `memories/preferences/` containing a markdown list of entries, each mapping a filename to a one-line agent-generated description. The index is maintained by four mechanisms:

1. **Write-path updates** — extraction prompts include a shared section instructing agents to update `MEMORY.md` when creating, modifying, or deleting memory files
2. **Read-path optimization** — the search prompt reads `MEMORY.md` first for facts/preferences, selecting files by description alone
3. **Light maintenance** — Mon–Sat ticks verify index consistency (missing entries, stale references) without regenerating descriptions
4. **Heavy rebuild** — Sunday ticks (and bootstrap) rebuild the index from scratch using batched description-worker sub-agents, with the orchestrator making structural decisions based on descriptions

The heavy rebuild uses a two-phase agent architecture to keep the orchestrator's context clean: lightweight description workers read file contents in batches and return one-line descriptions, then the orchestrator analyzes descriptions for merges/renames and writes the final `MEMORY.md`.

**Integration Points:**

### Shared Logic

- **`INDEX_UPDATE_SECTION`** (`prompts.py`): Format instructions for `MEMORY.md` entries, used by both facts and preferences extraction prompts. Specifies the entry format (`[Name](./filename.md): Description`), update rules (add on create, modify on content change, remove on delete), and the constraint that the agent must always keep `MEMORY.md` in sync with actual file operations. Example content:
  ```
  ## Memory Index
  When you create, modify, or delete a memory file, you MUST also update MEMORY.md
  in the same directory to keep the index in sync.

  Entry format: [Human-readable Name](./filename.md): One-line description of contents

  Rules:
  - When you CREATE a new file: add a new entry with an appropriate description
  - When you MODIFY a file and its topic/focus changes: update the description
  - When you DELETE a file: remove the corresponding entry
  - Always preserve the "# Memory Index" header
  - Keep descriptions concise (one line, under 80 characters)
  ```
- **`INDEX_LIGHT_MAINTENANCE_SECTION`** (`prompts.py`): Consistency verification instructions for weekday maintenance — add placeholder entries for new files (`Description pending update`), remove entries for deleted files, leave existing descriptions unchanged even if stale (Sunday rebuild handles regeneration). This section is appended to the existing maintenance prompt (FACTS_MAINTENANCE_PROMPT or PREFERENCES_MAINTENANCE_PROMPT) on Mon–Sat, preserving all existing maintenance behavior plus adding index consistency checks.
- **`run_index_rebuild(cwd, memory_type)`** (`index.py`): Shared heavy rebuild logic callable from both the bootstrap hook and Sunday maintenance. Uses `query_and_consume` with the description-worker orchestration prompt.
- **`DESCRIPTION_WORKER_PROMPT`** (`index.py`): System prompt for the lightweight sub-agents that read batches of files and return descriptions. Custom agent (not Explore) — focused task explanation, haiku model, Read tool only.
- **`HEAVY_INDEX_REBUILD_PROMPT`** (`index.py`): The main orchestrator prompt that instructs the agent to list files, spawn description workers in batches, collect descriptions, analyze for merges/renames, and write the final `MEMORY.md`.

## Modeling

The index has no persistent entities or database tables — it is a plain markdown file maintained by agents.

```
MEMORY.md (per directory: facts/, preferences/)
├── Header: "# Memory Index"
├── Entry: "[Name](./filename.md): One-line agent-generated description"
├── Entry: "[Name](./other-file.md): Another description"
└── ...

Entry Format:
  [HumanName](./slug.md): <one-line description>

Lifecycle States:
  Missing → Created by bootstrap or first write
  Empty → Header only (directory has no files)
  Populated → Entries with descriptions
  Stale → Entries reference deleted files or missing new files
  Degraded → Agent falls back to Glob, index rebuilt on next maintenance

memory/index.py (new module)
├── DESCRIPTION_WORKER_PROMPT: str
├── HEAVY_INDEX_REBUILD_PROMPT: str
└── run_index_rebuild(cwd: Path, memory_type: str) -> None

prompts.py (extended)
├── ... existing sections ...
├── INDEX_UPDATE_SECTION: str
└── INDEX_LIGHT_MAINTENANCE_SECTION: str
```

## Data Flow

### Search with index (happy path — facts/preferences)

```
1. MemoryContextProvider.provide() called
2. Provider builds search prompt (with updated Search Strategy section)
3. query() with DES-007 agent
4. Agent reads MEMORY.md in target directory
5. Agent evaluates each description against user message
6. Agent selects relevant files based on descriptions alone
7. Agent reads only selected files
8. Agent returns XML <memory> elements as before
9. Provider filters duplicates, creates ContextResults
```

### Search with index fallback

```
1. Agent attempts to Read MEMORY.md
2. File not found (or empty/malformed)
3. Agent falls back to Glob → Grep → Read (existing pattern)
4. Search proceeds as before
```

### Extraction with index update

```
1. FactsProcessor / PreferencesProcessor runs (DES-004)
2. Forked agent reads existing files, analyzes conversation
3. Agent creates/modifies/deletes memory files
4. After each file operation, agent updates MEMORY.md:
   - New file → adds entry with description
   - Modified file → updates description if content meaningfully changed
   - Deleted file → removes entry
5. MEMORY.md stays in sync with directory contents
```

### Light maintenance (Mon–Sat)

```
1. facts_maintenance_tick / preferences_maintenance_tick fires
2. datetime.now().weekday() != 6 → light path
3. Append INDEX_LIGHT_MAINTENANCE_SECTION to maintenance prompt
4. Agent performs normal maintenance (staleness, redundancy, consolidation)
5. Additionally verifies index consistency:
   a. Glob all .md files in directory
   b. Cross-reference with MEMORY.md entries
   c. Add placeholder entries for files missing from index
   d. Remove entries for files that no longer exist
6. git_commit_memory_changes()
```

### Heavy rebuild (Sunday)

```
1. facts_maintenance_tick / preferences_maintenance_tick fires
2. datetime.now().weekday() == 6 → heavy path
3. Append HEAVY_INDEX_REBUILD_PROMPT to maintenance prompt
4. Orchestrator agent (haiku):
   a. Glob all .md files in directory
   b. Group files into batches (~5-8 files; final batch may be smaller)
   c. For each batch, spawn description worker via Agent tool:
      - Custom system prompt (DESCRIPTION_WORKER_PROMPT)
      - Haiku model, Read tool
      - Returns structured XML: <file path="./name.md">description</file>
   d. Collect all descriptions from workers
   e. Analyze descriptions for structural improvements:
      - Merge files with same/similar descriptions
      - Rename files violating naming patterns (<project>.md, <system>.md)
      - Rework/consolidate fragmented files
   f. Perform identified merges/renames/reworks
   g. Write MEMORY.md from scratch with final file list
5. git_commit_memory_changes()
```

### Bootstrap index creation

```
1. memory_hook runs during startup (DES-003)
2. Create directories (existing behavior)
3. For each of facts/, preferences/:
   a. Check if MEMORY.md exists
   b. If exists → skip (idempotent)
   c. If missing:
      - Check if directory has any .md files
      - If empty → create MEMORY.md with header only
      - If has files → run_index_rebuild(cwd, memory_type)
4. run_index_rebuild reuses the same heavy rebuild mechanism:
   - query_and_consume with HEAVY_INDEX_REBUILD_PROMPT
   - Description workers for content analysis
   - Orchestrator writes MEMORY.md from scratch
```

## Key Decisions

### Prompt-driven index updates on write paths

**Choice**: A shared `INDEX_UPDATE_SECTION` prompt constant appended to facts and preferences extraction prompts instructs the forked agent to update `MEMORY.md` when it creates, modifies, or deletes memory files.
**Why**: Consistent with the existing DES-004 pattern where agents perform all file I/O. Adding index update logic in Python code would require intercepting agent file operations — contradicting the design where processors are thin orchestration wrappers and agents are autonomous writers. A prompt section keeps the index maintenance in the same layer as the file operations it tracks.

**Alternatives Considered:**
- **Post-extraction code-level update**: After the agent finishes, Python code reads the directory diff and updates MEMORY.md. Rejected because it requires diffing filesystem state before/after agent execution — fragile and contradicts the agent-driven file I/O pattern.
- **Separate post-processor for index updates**: A dedicated PostProcessor that updates indexes after extraction. Rejected because it adds pipeline complexity and ordering constraints (must run after all extraction processors) for something the extraction agent can handle inline.

**Sources**: Internal codebase analysis of DES-004 pattern and extraction prompt composition in `facts.py`, `preferences.py`.

**Consequences:**
- Pro: Zero code changes to processor classes — purely prompt-driven
- Pro: Index updates are co-located with the file operations that trigger them
- Pro: Consistent with existing shared section pattern (`STORE_PURPOSE_SECTION`, `CONTEXT_DEDUP_SECTION`)
- Con: Index update quality depends on agent compliance (mitigated by maintenance verification)
- Con: Agent must remember to update index after every file operation (mitigated by explicit prompt instructions)

### Two-phase heavy rebuild with description workers

**Choice**: The heavy rebuild uses a two-phase agent architecture. Lightweight description workers (custom haiku sub-agents, Read tool) read batches of files and return one-line descriptions. The orchestrator agent receives all descriptions and makes structural decisions — merging files with similar descriptions, renaming files violating naming patterns, and writing the final `MEMORY.md` — without ever reading file contents directly.
**Why**: A single agent reading all files would consume significant context on file contents, leaving less room for structural analysis. By delegating content reading to sub-agents, the orchestrator's context stays focused on descriptions and decisions. Batching files per sub-agent (rather than one sub-agent per file) balances parallelism with API overhead — typical workspaces have 10-30 files, so 2-5 sub-agent calls is efficient. Haiku model is chosen for description workers because generating a one-line summary is simple summarization work that doesn't benefit from higher-tier reasoning, and haiku provides adequate quality at lower cost. Batches of 5-8 files balance context window usage with parallelism; smaller batches increase API overhead while larger batches risk exceeding haiku's practical context. The final batch may contain fewer files.

**Alternatives Considered:**
- **Single agent reads all files**: Simpler (one agent call), but contaminates the orchestrator's context with file contents, reducing the quality of merge/rename decisions. Rejected per user preference for context isolation.
- **One sub-agent per file**: Maximum parallelism but high API overhead and orchestration complexity. For 20 files, this means 20 sub-agent calls. Batching is more efficient with negligible latency impact.

**Sources**: Internal codebase analysis of Agent tool usage in `facts.py`, `preferences.py` (workspace claim validation sub-agents); DES-004 sub-agent spawning patterns.

**Consequences:**
- Pro: Orchestrator context stays clean — only descriptions, not full file contents
- Pro: Orchestrator can make informed structural decisions (merges, renames) based on descriptions
- Pro: Batching balances efficiency with context isolation
- Con: More complex than a single-pass agent (multiple agent calls, result collection)
- Con: Description quality depends on sub-agent accuracy (mitigated by periodic heavy rebuilds)

### Day-of-week dispatch in tick functions

**Choice**: Maintenance tick functions check `datetime.now().weekday()` to conditionally append light (Mon–Sat) or heavy (Sunday) index maintenance sections to their prompt.
**Why**: The current scheduler uses a single `CronTrigger` (`0 3 * * *`) shared by all maintenance jobs. Adding day-of-week logic inside the tick function avoids any scheduler or configuration changes. The check is a one-liner that naturally extends the existing prompt composition pattern.

**Alternatives Considered:**
- **Two separate cron schedules**: Configure weekday (`0 3 * * 1-6`) and Sunday (`0 3 * * 0`) schedules. Rejected because it requires splitting each maintenance job into two scheduler entries, doubling the job count in `__main__.py` and adding config complexity.
- **Separate index-only tick**: Register a new scheduler job specifically for index maintenance. Rejected because it adds another job to the scheduler and would need its own git commit logic, duplicating the existing tick infrastructure.

**Sources**: Internal codebase analysis of `scheduler.py` (CronTrigger, Job registration), `__main__.py` (job wiring), `maintenance.py` (tick function structure).

**Consequences:**
- Pro: Zero changes to scheduler, config, or `__main__.py`
- Pro: Light/heavy logic is local to the tick function — easy to understand and test
- Pro: Consistent with existing prompt composition pattern (append sections conditionally)
- Con: Tied to system timezone (same as existing maintenance — acceptable)

### Index read-path change in search prompt

**Choice**: Modify `MEMORY_SEARCH_PROMPT` to instruct the agent to read `MEMORY.md` first for facts and preferences directories, selecting files based on descriptions. Keep Glob-based discovery for episodic. Include explicit fallback instructions: if `MEMORY.md` is missing or empty, fall back to Glob.
**Why**: Reading a single index file (MEMORY.md) and evaluating text descriptions is faster and cheaper than Glob + Grep + Read across multiple files. The search agent goes directly to relevant files instead of discovering and scanning them. Episodic memories are excluded because they are date-organized and searched by date range — an index doesn't add value there.

**Alternatives Considered:**
- **Code-level index parsing**: Python code reads and parses MEMORY.md, then injects the description list into the prompt. Rejected because it contradicts the agent-driven pattern — the search agent already knows how to read files and make relevance decisions.
- **Two-step agent**: One agent reads the index and selects files, another reads selected files. Rejected because the existing single-agent pattern (DES-007) already handles multi-step tool use efficiently.

**Sources**: Internal codebase analysis of `MEMORY_SEARCH_PROMPT` in `context_provider.py`.

**Consequences:**
- Pro: Search prompt change is minimal — replace discovery instructions
- Pro: Agent retains full autonomy in relevance decisions
- Pro: Fallback preserves current behavior when index is unavailable
- Con: Search agent must correctly handle missing/empty index (mitigated by explicit fallback instructions)

### Shared index module for rebuild logic

**Choice**: Create `src/tachikoma/memory/index.py` as a new module containing the heavy rebuild prompt constants (`DESCRIPTION_WORKER_PROMPT`, `HEAVY_INDEX_REBUILD_PROMPT`) and the `run_index_rebuild(cwd, memory_type)` helper function. Both bootstrap hook and Sunday maintenance call this shared function.
**Why**: The heavy rebuild logic is identical whether triggered by bootstrap or by Sunday maintenance. A shared module avoids duplicating the prompt constants and rebuild orchestration. Placing it in `memory/index.py` follows the subsystem pattern where each concern has its own module.

**Alternatives Considered:**
- **Inline in maintenance.py**: Put rebuild logic directly in the maintenance module. Rejected because bootstrap hook would need to import from maintenance, creating a circular dependency risk and mixing concerns.
- **Inline in hooks.py**: Put rebuild logic in the hooks module. Rejected because hooks should be lightweight (DES-003) — the heavy rebuild involves agent orchestration that belongs in a dedicated module.

**Sources**: DES-003 (subsystem-owned hooks should be thin); internal codebase analysis of module organization.

**Consequences:**
- Pro: Single source of truth for rebuild logic
- Pro: Clean separation — index logic in its own module
- Pro: Bootstrap and maintenance share the same implementation
- Con: One new module to maintain (minor)

### Structured XML output for description workers

**Choice**: Description workers return results as structured XML elements: `<file path="./filename.md">One-line description</file>`. The orchestrator agent parses these elements to collect descriptions.
**Why**: The existing memory search agent already uses XML output format (`<memory>` elements) for structured communication between agents. Using the same pattern for description workers ensures consistency and makes the orchestrator's parsing task unambiguous. Free-text format (`path: description`) risks parsing ambiguity (colons in descriptions, inconsistent formatting). Haiku generates well-formed XML reliably for simple schemas.

**Alternatives Considered:**
- **Free-text with defined format** (`path: description`): Simpler but fragile — colons in descriptions break parsing, inconsistent whitespace causes ambiguity. Rejected because structured output eliminates these failure modes.
- **JSON output**: Equally structured but heavier for a one-line-per-file response. XML matches the existing agent-to-agent communication pattern in the codebase.

**Sources**: Internal codebase analysis of `MEMORY_SEARCH_PROMPT` XML output format in `context_provider.py`.

**Consequences:**
- Pro: Consistent with existing XML-based agent communication pattern
- Pro: Unambiguous parsing by orchestrator
- Con: Requires workers to produce well-formed XML (mitigated by simple schema)

## System Behavior

### Scenario: First message of session, index present

**Given**: A session with facts and preferences directories containing `MEMORY.md` files
**When**: The memory context provider searches for facts or preferences
**Then**: Agent reads `MEMORY.md`, evaluates descriptions against the user message, selects relevant files, reads only those. Returns results or `NO_RELEVANT_MEMORIES` as before.

### Scenario: Index missing, graceful fallback

**Given**: A facts directory with `.md` files but no `MEMORY.md` (e.g., freshly cloned workspace)
**When**: The memory context provider searches for facts
**Then**: Agent attempts to read `MEMORY.md`, finds it missing, falls back to Glob → Grep → Read. Search proceeds normally. Index is created on next maintenance run or bootstrap.

### Scenario: Index references deleted file

**Given**: `MEMORY.md` has an entry for `old-project.md` which was deleted
**When**: The search agent selects `old-project.md` as relevant and tries to read it
**Then**: Agent finds the file missing, skips it, continues with other results. The stale entry is cleaned up on the next maintenance run (light or heavy).

### Scenario: Index malformed or corrupt

**Given**: `MEMORY.md` exists but contains malformed entries (broken markdown links, missing descriptions, invalid syntax)
**When**: The search agent reads `MEMORY.md`
**Then**: Agent attempts to parse the index. If entries are unreadable or don't match the expected format, the agent falls back to Glob → Grep → Read for that directory. The malformed index is overwritten on the next Sunday heavy rebuild. Light maintenance may partially fix the index (removing entries for deleted files, adding placeholders for new files) but does not attempt to repair broken formatting.

### Scenario: Extraction creates new memory file

**Given**: A conversation about a new project, the facts extraction processor runs
**When**: The forked agent creates `memories/facts/new-project.md`
**Then**: Agent adds an entry to `MEMORY.md`: `[New Project](./new-project.md): Facts about the user's new-project setup and configuration`. Index is immediately in sync.

### Scenario: Extraction modifies existing memory file

**Given**: A conversation adds new information about an existing topic tracked in `work-info.md`
**When**: The forked agent updates `memories/facts/work-info.md` with new details
**Then**: Agent updates the description in `MEMORY.md` if the topic, focus, or scope meaningfully changed. If the description still accurately describes the file's content, no update is needed.

### Scenario: Maintenance consolidates files (light)

**Given**: Tuesday maintenance run, facts directory has 5 files but MEMORY.md only has 4 entries
**When**: The facts maintenance tick fires
**Then**: Agent performs normal maintenance. Additionally detects the missing entry, adds a placeholder: `[New Topic](./new-topic.md): Description pending update`. No descriptions are regenerated.

### Scenario: Light maintenance with stale descriptions

**Given**: Wednesday maintenance run, a file was significantly modified since its description was generated
**When**: The facts maintenance tick fires
**Then**: Agent performs normal maintenance. The index consistency check verifies that every file has an entry and every entry has a corresponding file. The stale description is left unchanged — light maintenance never regenerates descriptions per R6. The stale description is corrected on the next Sunday heavy rebuild.

### Scenario: Heavy rebuild merges similar files (Sunday)

**Given**: Sunday maintenance run, facts directory has `api-work.md`, `api-errors.md`, and `api-design.md` with similar descriptions
**When**: The heavy rebuild runs
**Then**: Description workers read each file and return descriptions. Orchestrator detects overlapping descriptions, merges files into `api.md`, writes the final `MEMORY.md` with a single entry: `[API](./api.md): Facts about the user's API work, error handling, and design decisions`. Old files are deleted, new file is created.

### Scenario: Heavy rebuild renames poorly-named file (Sunday)

**Given**: A file named `2024-03-bugfix.md` that contains general debugging preferences
**When**: The heavy rebuild runs
**Then**: Description worker reads the file and returns "Debugging workflow and preferences." Orchestrator detects the file violates naming patterns (date-based name for general content), renames to `debugging.md`, and updates the index accordingly.

### Scenario: Bootstrap on fresh workspace

**Given**: Fresh workspace, no memories exist yet
**When**: `memory_hook` runs during startup
**Then**: Directories are created. `MEMORY.md` files are created with header only (no entries). No rebuild is triggered because directories are empty.

### Scenario: Bootstrap on existing workspace without index

**Given**: Workspace with existing fact/preference files but no `MEMORY.md`
**When**: `memory_hook` runs during startup
**Then**: Directories already exist (idempotent). Hook detects missing `MEMORY.md` and existing files. Triggers `run_index_rebuild()` for each directory that needs it. Index is built before the first message is processed.

### Scenario: Bootstrap with existing but stale index

**Given**: Workspace where `MEMORY.md` exists but has fewer entries than actual files (e.g., index was partially built, or files were added manually)
**When**: `memory_hook` runs during startup
**Then**: Hook checks that `MEMORY.md` exists → skips rebuild (idempotent). The stale index is usable — missing entries are added by the next light maintenance run (Mon–Sat) as placeholder entries, and descriptions are regenerated on the next Sunday heavy rebuild. The system degrades gracefully: files missing from the index are invisible to the search agent until maintenance catches up, but they remain discoverable via Glob fallback if the agent cannot find relevant results in the index.
