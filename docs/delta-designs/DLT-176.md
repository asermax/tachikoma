# Design: DLT-176 - Limit detached process memory using cgroups v2

**Delta Spec**: [../delta-specs/DLT-176.md](../delta-specs/DLT-176.md)
**Status**: Draft

## Purpose

This document explains the design rationale for adding cgroup v2 memory limits to the detached processes subsystem: the cgroup lifecycle management, integration with the existing spawn/reconcile/watcher flow, OOM detection, graceful fallback, and configuration.

## Problem Context

A single runaway detached process can consume all available RAM on a VPS, triggering kernel OOM kills that affect unrelated processes including Tachikoma itself. Linux cgroups v2 provide a filesystem-based memory hard-limit mechanism that the kernel enforces directly — no userspace polling needed.

**Constraints:**
- cgroups v2 is a pure filesystem API (mkdir, write to files) — no third-party library needed
- systemd delegates cgroup subtrees to user sessions; we cannot assume root access to `/sys/fs/cgroup/` directly
- The "no internal process constraint" in cgroups v2: a cgroup with child cgroups cannot have processes AND controllers enabled simultaneously — we must manage the hierarchy carefully
- The cgroup must be created before the process starts and the PID moved into it immediately after spawn
- All cgroup operations must be optional — if cgroups v2 is unavailable, spawn proceeds without limits
- Existing subsystem pattern (DES-003 bootstrap hooks, DES-006 tool server factory) must be followed
- Per ADR-007, new columns are added to the existing `ProcessRecordRow` table

**Interactions:**
- `spawn.py` gains a cgroup-creation step between fork and persist
- `reconcile.py` gains an OOM-detection step and a cgroup-cleanup step
- `hooks.py` gains cgroup availability probing at bootstrap and stale cgroup cleanup during crash recovery
- `tools.py` gains `memory_limit_mb` parameter on `start_process` and `memory_usage` on `get_process`
- `config.py` gains a `[detached_processes]` section for default memory limit
- `model.py` gains `memory_limit` and `cgroup_path` fields on `ProcessRecord`

## Design Overview

A new `cgroup_manager.py` module within `src/tachikoma/detached_processes/` owns all cgroup v2 lifecycle operations: probing availability, discovering the parent cgroup path, creating per-process cgroups, moving PIDs, reading memory stats, detecting OOM events, and cleaning up. All other modules interact with cgroups exclusively through this module's public API.

The cgroup lifecycle is:
1. **Bootstrap**: probe cgroup v2 availability, discover parent cgroup path, store result
2. **Spawn**: create per-process cgroup, set `memory.max`, move PID into it
3. **Running**: `get_process` reads `memory.current` for usage visibility
4. **Exit**: `reconcile_exit` checks `memory.events` for OOM, calls `cleanup`
5. **Cleanup**: remove the per-process cgroup directory

Every operation is guarded — failures produce warnings and proceed without limits, never blocking process spawn or reconciliation.

## Components

### Implementation Structure

| Layer/Component | Responsibility | Key Decisions |
|-----------------|----------------|---------------|
| `src/tachikoma/detached_processes/cgroup_manager.py` | All cgroup v2 filesystem operations — probe, discover, create, assign, read stats, detect OOM, cleanup | Pure stdlib (os, pathlib); stateless functions; returns `Optional` results to signal unavailability |
| `src/tachikoma/detached_processes/model.py` | Extend `ProcessRecord` with `memory_limit`, `cgroup_path`; extend `ProcessRecordRow` with matching columns | Nullable columns — None means no cgroup was created (fallback path) |
| `src/tachikoma/detached_processes/spawn.py` | Integrate cgroup creation into spawn flow after fork, before persist | Cgroup failure does not prevent spawn — falls back to no-limit mode |
| `src/tachikoma/detached_processes/reconcile.py` | Add OOM detection to `reconcile_exit`; call cgroup cleanup | OOM check is best-effort; missing cgroup path means no check (no error) |
| `src/tachikoma/detached_processes/tools.py` | Add `memory_limit_mb` param to `StartProcessArgs`; add memory usage to `get_process` response | Validation: `memory_limit_mb` must be ≥ 1 and ≤ system RAM |
| `src/tachikoma/detached_processes/hooks.py` | Probe cgroup at bootstrap; store availability in `ctx.extras`; clean stale cgroups in crash recovery | One-time availability probe; cached for session lifetime |
| `src/tachikoma/config.py` | Add `DetachedProcessesConfig` with `default_memory_limit_mb`; wire into `Settings` | Default None (opt-in); Pydantic validates ≥ 1 when set; system RAM check happens at tool level in tools.py |

**cgroup_manager public API:**

```python
def probe_cgroup_support() -> bool
    # Check /sys/fs/cgroup/ mounted, memory controller available

def discover_parent_cgroup_path() -> str | None
    # Auto-detect: read /proc/self/cgroup → find v2 path
    # → check if memory controller can be enabled
    # → return absolute cgroup path, or None

def create_process_cgroup(parent_path: str, record_id: str, memory_limit_bytes: int) -> str | None
    # mkdir {parent}/tachikoma-{record_id}
    # write memory.max = memory_limit_bytes
    # return cgroup path, or None on failure

def assign_pid(cgroup_path: str, pid: int) -> bool
    # write pid to cgroup.procs
    # return True on success, False on failure

def read_memory_current(cgroup_path: str) -> int | None
    # read memory.current; return bytes, or None

def check_oom_kill(cgroup_path: str) -> bool | None
    # read memory.events → parse oom_kill count
    # return True if > 0, False if 0, None if unreadable

def cleanup_cgroup(cgroup_path: str) -> None
    # rmdir cgroup directory; log on failure, never raise
```

**Integration Points:**
- spawn.py → cgroup_manager: create + assign during spawn
- reconcile.py → cgroup_manager: OOM check + cleanup during exit reconciliation
- hooks.py → cgroup_manager: probe at bootstrap, cleanup stale cgroups during crash recovery
- tools.py → cgroup_manager: read memory usage for get_process

**Error handling:**
- All cgroup_manager functions return `None` or `False` on failure — never raise
- Callers log warnings and proceed without cgroup functionality
- Cleanup failures are logged but never block reconciliation

## Modeling

### ProcessRecord Extension

```
ProcessRecord (frozen dataclass)
├── ... (existing fields unchanged)
├── memory_limit: int | None      (bytes; None = no cgroup / fallback mode)
└── cgroup_path: str | None       (absolute path to per-process cgroup dir)
```

The existing `ProcessRecordRow` ORM model gains two nullable columns:

```
ProcessRecordRow (SQLAlchemy ORM)
├── ... (existing columns unchanged)
├── memory_limit = Column(Integer, nullable=True)    # bytes, None = no limit
└── cgroup_path = Column(String, nullable=True)       # absolute path, None = no cgroup
```

Alembic migration: `ALTER TABLE process_records ADD COLUMN memory_limit INTEGER; ALTER TABLE process_records ADD COLUMN cgroup_path VARCHAR;` — both nullable, no data backfill needed.

### Cgroup Directory Layout

```
<discovered parent cgroup>/
├── ... (existing hierarchy)
└── tachikoma-{record_id}/
    ├── cgroup.procs      (PID written here)
    ├── memory.max        (hard limit in bytes)
    ├── memory.current    (read for usage)
    └── memory.events     (read for OOM detection)
```

Each spawned process gets its own cgroup named `tachikoma-{record_id}`. The record ID (UUID) ensures uniqueness.

### Cgroup availability state

```
Bootstrap probe result (stored in ctx.extras):
├── cgroup_available: bool              (cgroups v2 mounted + memory controller)
└── cgroup_parent_path: str | None      (where to create child cgroups)
```

This is computed once at bootstrap and passed through to spawn calls. If unavailable, all cgroup operations are skipped entirely (no per-spawn probing).

## Data Flow

### Cgroup Availability Probe (Bootstrap)

```
1. detached_processes_hook runs
2. probe_cgroup_support() → check /sys/fs/cgroup/ mounted, memory controller accessible
3. If available: discover_parent_cgroup_path() → read /proc/self/cgroup
   → parse v2 path (e.g., "/user.slice/user-1000.slice/session-1.scope")
   → verify memory controller can be enabled in subtree
   → return absolute path
4. Store result: ctx.extras["cgroup_available"] = bool; ctx.extras["cgroup_parent_path"] = str|None
5. During crash recovery: for dead records with cgroup_path, call cleanup_cgroup()
```

### Spawn with Cgroup (Extended Flow)

```
1. Agent calls start_process({name, command, cwd?, env?, memory_limit_mb?})
2. Resolve effective limit:
   - per_process_limit = memory_limit_mb arg OR config default OR None (no limit)
   - Convert to bytes; validate: >= 1MB, <= system RAM
3. Existing spawn flow (validation, id assignment, wrapper build)
4. asyncio.create_subprocess_exec(...) → proc
5. [NEW] If cgroup_available AND effective_limit is not None:
   a. create_process_cgroup(parent_path, record_id, limit_bytes) → cgroup_path
   b. If cgroup_path: assign_pid(cgroup_path, proc.pid)
   c. If either fails: log warning; cgroup_path = None (fallback)
6. process_create_time = psutil.Process(proc.pid).create_time()
7. Persist ProcessRecord(memory_limit=limit_bytes, cgroup_path=cgroup_path, ...)
8. Return {id, pid, log_path}
```

### Exit Reconciliation with OOM Detection

```
1. reconcile_exit(record) called by watcher, lazy reconciliation, or stop_process
2. Existing: conditional UPDATE, read exit sidecar
3. [NEW] If record.cgroup_path is not None:
   a. oom_detected = check_oom_kill(record.cgroup_path)
   b. cleanup_cgroup(record.cgroup_path)
   c. Clear cgroup_path on record (it's been cleaned up)
4. Dispatch notification:
   - If exit_code == 137 AND oom_detected:
     "Process '{name}' was killed (OOM - may have exceeded memory limit of {limit}MB)"
   - If exit_code == 137 AND not oom_detected:
     "Process '{name}' was killed by signal (SIGKILL)"
   - Otherwise: existing notification text unchanged
5. Priority: Urgent for non-zero exit code (including OOM), Normal for exit code 0
```

### Memory Usage Query (get_process)

```
1. Agent calls get_process({id})
2. Existing: lazy reconciliation, build response
3. [NEW] If record.cgroup_path is not None AND record.status == "running":
   a. memory_usage_bytes = read_memory_current(record.cgroup_path)
   b. Include in response: {"memory_usage_bytes": ..., "memory_limit_bytes": ...}
   c. If read fails: omit memory_usage_bytes, include memory_limit_bytes only
4. If no cgroup_path: omit both fields
```

### Bootstrap Crash Recovery (Extended)

```
1. detached_processes_hook runs
2. [NEW] Probe cgroup availability → store in ctx.extras
3. Existing: for record in list_running():
      if not is_alive(record):
        reconcile_exit(record, dispatch_notification=False)
4. [NEW] In reconcile_exit during crash recovery:
        If record.cgroup_path exists, call cleanup_cgroup (cgroup may be stale)
```

## Key Decisions

### No new dependencies — stdlib-only cgroup operations

**Choice**: Use Python stdlib (`os`, `pathlib.Path`) for all cgroup v2 filesystem operations. No third-party cgroup library.
**Why**: cgroups v2 is purely filesystem-based — `mkdir`, `echo value > file`, `cat file`. A library adds a dependency for operations that are trivially expressed as 1-3 line stdlib calls. Per Linux kernel cgroup v2 documentation, the interface is stable and simple.

**Sources**: [Linux kernel cgroup v2 documentation](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)

**Alternatives Considered:**
- `cgroups` PyPI package: adds a dependency for trivial file I/O; not widely maintained
- `python-prctl` / other process-control libraries: do not cover cgroup management
- `systemd-run` as a subprocess wrapper: would work but couples to systemd, adds a subprocess call per spawn, and is harder to control programmatically

**Consequences:**
- Pro: Zero new dependencies
- Pro: Full control over error handling and fallback behavior
- Con: Must handle filesystem permissions and edge cases manually (mitigated by graceful fallback)

### Auto-detect cgroup parent with fallback

**Choice**: Discover the parent cgroup path by reading `/proc/self/cgroup`, checking the v2 path, verifying the memory controller is available. If detection fails (no cgroup v2, no memory controller, permission denied), proceed without limits.
**Why**: Systems vary widely — bare-metal Linux may have cgroups at `/sys/fs/cgroup/` directly, while systemd-managed systems delegate subtrees under `/sys/fs/cgroup/user.slice/...`. Hardcoding either path would fail on the other. Auto-detection handles both, and fallback ensures the feature never breaks spawn.

**Alternatives Considered:**
- Fixed path `/sys/fs/cgroup/tachikoma/`: requires root or system-level setup; fails on systemd-managed user sessions
- systemd-delegated subtree only: would not work on non-systemd systems
- Require root: unacceptable for a personal assistant tool

**Consequences:**
- Pro: Works on both systemd and non-systemd Linux
- Pro: No setup required from the user
- Pro: Graceful degradation on unsupported systems
- Con: Slightly more complex discovery logic (one function, ~20 lines)

### No default limit — cgroups only when explicitly configured or per-process

**Choice**: If `[detached_processes] default_memory_limit_mb` is not set in config AND `memory_limit_mb` is not passed to `start_process`, no cgroup is created. The config default of 1024 MB applies only when the `[detached_processes]` section exists.
**Why**: The user confirmed this approach — preserves current behavior by default. Users opt in by adding the config section or passing per-process limits. The spec's R1 states "Default memory limit of 1GB applies to all detached processes unless overridden per-process" — this is honored when the config section is present.

**Consequences:**
- Pro: Zero behavior change without explicit opt-in
- Pro: Simpler bootstrap — no cgroup probing if no limits configured
- Con: Users must add config to get protection (documented in preamble hint)

### Separate cleanup function called from reconcile

**Choice**: `cgroup_manager.cleanup_cgroup()` is a standalone function called explicitly by `reconcile_exit()` and by the bootstrap crash-recovery hook. Not implicitly tied to model lifecycle.
**Why**: Cleanup must happen in two distinct paths: (1) normal exit reconciliation via watcher/lazy/stop, and (2) bootstrap crash recovery for stale cgroups. A standalone function called explicitly from both paths is clearer than coupling cleanup to the model or repository. The function never raises — it logs and returns, so cleanup failure never blocks reconciliation.

**Alternatives Considered:**
- Reconcile owns cleanup implicitly: less explicit, harder to test in isolation
- Destructor/cleanup on ProcessRecord: async destructors are unreliable in Python
- Background cleanup task: adds complexity for a synchronous `rmdir` operation

**Consequences:**
- Pro: Explicit cleanup call sites — easy to trace and test
- Pro: Single cleanup function shared between reconcile and crash recovery
- Pro: Never blocks reconciliation (failure is logged, not raised)

### OOM detection via memory.events oom_kill counter

**Choice**: After detecting exit code 137 (128+SIGKILL), read `memory.events` from the process's cgroup and check if `oom_kill` count is > 0. If so, the notification includes OOM context.
**Why**: Exit code 137 alone is ambiguous — it means "killed by SIGKILL" but doesn't distinguish OOM from external `kill -9`. The `memory.events` file's `oom_kill` counter is the authoritative kernel signal that the cgroup's memory limit was exceeded. This is documented in the kernel cgroup v2 docs.

**Sources**: Linux kernel cgroup v2 documentation — memory.events interface

**Consequences:**
- Pro: Accurate OOM attribution — user knows the process hit its memory limit
- Pro: Clean distinction from manual SIGKILL
- Con: The counter is cumulative for the cgroup's lifetime — since we create one cgroup per process and clean up after exit, this is not a concern (each cgroup sees exactly one process's events)

## System Behavior

### Scenario: Normal spawn with default limit from config

**Given**: Config has `[detached_processes] memory_limit_mb = 2048`; cgroups v2 is available.
**When**: `start_process({name: "worker", command: "npm run build"})` is called.
**Then**: A cgroup `tachikoma-{id}` is created under the discovered parent path, `memory.max` set to 2147483648 (2GB), the process PID is written to `cgroup.procs`. The record stores `memory_limit=2147483648` and the cgroup path.

### Scenario: Spawn with per-process override

**Given**: Default config limit is 1024 MB; agent passes `memory_limit_mb=512`.
**When**: `start_process({name: "small-worker", command: "...", memory_limit_mb: 512})` is called.
**Then**: The cgroup's `memory.max` is set to 536870912 (512MB), overriding the default.

### Scenario: Spawn without any limit configured

**Given**: No `[detached_processes]` section in config; no `memory_limit_mb` passed.
**When**: `start_process` is called.
**Then**: No cgroup is created. The record stores `memory_limit=None`, `cgroup_path=None`. Process runs with no memory constraint — identical to current behavior.

### Scenario: cgroups v2 unavailable

**Given**: `/sys/fs/cgroup/` is not mounted or memory controller is not available.
**When**: `start_process` is called with a memory limit.
**Then**: Bootstrap probe set `cgroup_available=False`. Spawn skips cgroup creation entirely. A one-time warning was logged at bootstrap. The record stores `memory_limit=None`, `cgroup_path=None`. Process runs without limits.

### Scenario: Cgroup creation fails mid-spawn

**Given**: cgroups v2 is available but `mkdir` for the per-process cgroup fails (e.g., permission denied).
**When**: `start_process` is called with a memory limit.
**Then**: `create_process_cgroup` returns None. Spawn logs a warning with the error. Process proceeds without a cgroup. Record stores `memory_limit=None`, `cgroup_path=None`.

### Scenario: OOM kill detected

**Given**: A process with `memory_limit=536870912` (512MB) attempts to allocate beyond the limit.
**When**: The kernel OOM-kills the process.
**Then**: Process exits with code 137. The exit watcher detects the exit. `reconcile_exit` reads `memory.events` → `oom_kill 1` → oom_detected=True. Notification text: "Process 'worker' exited with code 137 (OOM — may have exceeded memory limit of 512MB)". Priority is Urgent. Cgroup is cleaned up.

### Scenario: External SIGKILL (not OOM)

**Given**: A process with a cgroup is killed by external `kill -9`.
**When**: The process exits with code 137.
**Then**: `reconcile_exit` reads `memory.events` → `oom_kill 0` → oom_detected=False. Notification text: "Process 'worker' was killed by signal (exit code 137)". No OOM context. Priority is Urgent.

### Scenario: Process exit with cgroup cleanup

**Given**: A process exits normally (exit code 0) with an active cgroup.
**When**: `reconcile_exit` runs.
**Then**: OOM check returns False (exit code 0, not SIGKILL). `cleanup_cgroup` removes the cgroup directory. Record's `cgroup_path` is set to None. Notification dispatches with Normal priority.

### Scenario: Cgroup cleanup failure

**Given**: A process exits; its cgroup has child processes that were spawned by the user command.
**When**: `cleanup_cgroup` calls `os.rmdir(cgroup_path)`.
**Then**: `rmdir` fails (directory not empty). The error is logged. Reconciliation completes normally — the record is updated, notification is dispatched. The stale cgroup remains until manually cleaned or the system reclaims it.

### Scenario: Crash recovery cleans up stale cgroups

**Given**: Tachikoma crashes; processes with cgroups exited while Tachikoma was offline.
**When**: Tachikoma restarts; bootstrap crash recovery runs.
**Then**: For each dead `running` record with a `cgroup_path`, `reconcile_exit` calls `cleanup_cgroup`. Stale cgroup directories are removed. Records are updated to `exited`.

### Scenario: Memory usage query

**Given**: A running process with an active cgroup.
**When**: `get_process` is called.
**Then**: `read_memory_current(cgroup_path)` returns current memory usage in bytes. Response includes `memory_usage_bytes` and `memory_limit_bytes`.

### Scenario: Memory usage query — process without cgroup

**Given**: A running process spawned without a cgroup (fallback mode).
**When**: `get_process` is called.
**Then**: `cgroup_path` is None. Memory usage fields are omitted from the response.

## Notes

- No new runtime dependencies — cgroup v2 operations use only Python stdlib
- Linux-only feature (macOS does not support cgroups); graceful fallback handles this automatically
- The `cgroup_manager` module is stateless — all state lives in the record (cgroup_path) and bootstrap extras (availability)
- Per-process cgroup naming uses `tachikoma-{record_id}` for uniqueness and debuggability
- The `memory.max` file accepts "max" as a value for "no limit" — we never use this (either a concrete limit or no cgroup at all)
