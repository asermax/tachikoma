# Design: DLT-176 - Workflow Tasks as Background Execution

**Delta Spec**: [../delta-specs/DLT-176.md](../delta-specs/DLT-176.md)
**Status**: Draft

## Purpose

This document explains the design rationale for refactoring workflow execution to run as background tasks. After implementation, the "Detected Impacts" section will guide reconciliation into feature design docs.

## Problem Context

Workflows currently run inside the main interactive session — the agent calls `update_workflow_state` for each step, reads instructions from files, does work, then calls complete. This blocks the main conversation for the duration of the workflow and couples step-driving to the main session's SDK lifecycle. Moving to background task execution decouples workflow progress from the main session, enabling autonomous execution with user input via the existing notification mechanism.

## Design Overview

Each workflow becomes a series of background task instances — one per step. The main session retains only `start_workflow` for initiation. Once started, step tasks run autonomously: each step gets a fresh SDK session with full context injected into the initial prompt. Steps communicate via hand-off messages (relayed to the next step's prompt) and the shared scratchpad (for long-term context). New workflow-specific MCP tools (`complete_step`, `skip_step`, `abort_workflow`, `request_input`) are available only inside workflow step task sessions. The cascade logic runs inside the tool handlers — when a step completes, the handler determines the next step and enqueues it as a new background task instance.

## Shape

| Part | Mechanism | Flag |
|------|-----------|:----:|
| **S1** | Workflow task launcher — `start_workflow` creates workflow state, scratchpad, enqueues first step as a pending TaskInstance with `workflow_id` set | |
| **S2** | Main session MCP tool trim — remove `update_workflow_state` and `end_workflow` from main session servers | |
| **S3** | Workflow step task tools — new MCP server factory producing `complete_step`, `skip_step`, `abort_workflow`, `request_input`; registered only when TaskInstance has `workflow_id` | |
| **S4** | Step prompt builder — constructs the initial prompt for each step task with full context injection (instructions, skills, scratchpad, metadata, hand-off) | |
| **S5** | Step cascade enqueuer — inside `complete_step`/`skip_step` tool handlers, runs cascade logic and enqueues next step as a new TaskInstance | |
| **S6** | Hand-off relay — captures hand-off message from `complete_step`, validates length (max 4000 chars), injects into next step's prompt | |
| **S7** | Workflow wait timeout — `workflow_wait_timeout` config field used by expired waiter sweep for tasks with `workflow_id` | |
| **S8** | Authoring guide update — update workflow-authoring-guide skill with hand-off and scratchpad patterns | |
| **S9** | Failure propagation — when a workflow step task fails, triggers cascade abort on the parent workflow state (soft-delete all descendants, dispatch failure notification) | |
| **S10** | Workflow task metadata — `workflow_id` field on TaskInstance schema, enabling workflow-specific timeout, tool registration, and cascade coordination | |
