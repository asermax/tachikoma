| Part | Mechanism | Flag |
|------|-----------|:----:|
| **S1** | **Envelope protocol.** Define a base type / protocol for incoming messages that declares the universal surface only. At minimum: a method that renders the envelope into the prompt text the agent sees. Whether routing-related behavior (boundary detection, force-new) also lives on the protocol (e.g. a `session_routing()` method) or is handled coordinator-side via subtype discrimination is a design-phase decision. The protocol deliberately does NOT carry text, `force_new`, `pinned_skills`, or any other subtype-specific field — promoting something to the base requires evidence that it's universal, not just incumbent. | ⚠️ |
| **S2** | **`TextMessage` subtype.** Concrete subtype carrying today's `IncomingMessage` fields: `text`, `pinned_skills`, `force_new`. Implements the protocol's render method by returning `text` verbatim. Existing call sites that construct `IncomingMessage(text=…)` switch to `TextMessage(text=…)`. | |
| **S3** | **`ReactionMessage` subtype.** Concrete subtype carrying the reaction change (e.g. `added: frozenset[str]`, `removed: frozenset[str]`). Implements the protocol's render method by producing the prose ("user added 👍 / removed 🤔 / replaced 👍 with 🤔; interpret in the context of the last exchange and respond accordingly"). No emoji→meaning mapping in code. | |
| **S4** | **Telegram reaction handler.** aiogram handler subscribing to `message_reaction` updates. Applies the existing chat-level authorization filter, computes the diff between old and new reaction lists, drops no-op updates and updates whose only changes are uninterpretable reaction kinds (paid/custom emoji), constructs a `ReactionMessage`, and enqueues it through the existing channel→coordinator path (`enqueue()`, the same `enqueue()` used by text messages — no new mid-exchange machinery). | |
| **S5** | **Allowed-updates configuration.** Adds `message_reaction` to aiogram polling's `allowed_updates` list (default polling does not deliver these updates). | |
| **S6** | **Reactions skip boundary detection.** The coordinator's per-turn dispatch is adapted so reaction turns continue the current session — never run boundary detection, never force a new session. Exact mechanism (protocol method vs. coordinator-side subtype check) is tied to S1's design decision. | |
| **S7** | **Optional disable flag.** A `[telegram]` config flag that, when `false`, suppresses S4 (handler registration) and S5 (allowed-updates). Defaults to enabled. | |

### Flagged Unknowns

#### S1 — Protocol surface design

The minimum is one render method, but several adjacent concerns deserve a deliberate decision rather than a default:

- **Routing behavior.** Today `force_new` lives on the message. After the refactor, is "how should the coordinator route this turn?" a protocol method (e.g., `session_routing() -> NORMAL | CONTINUE_CURRENT | FORCE_NEW`), or does the coordinator just `isinstance`-discriminate? A protocol method keeps the rule next to the message type that owns it; `isinstance` keeps the protocol tighter but scatters knowledge.
- **`pinned_skills` placement.** Used by pre-processing today and currently text-only. Does it stay text-only (and pre-processing handles non-text by emitting empty), or does it move to the protocol as a method that defaults to empty? Same trade-off shape as routing.
- **Message-buffer payload type.** The coordinator's `_message_buffer` and forwarder currently round-trip a text string. After the refactor, either (a) the buffer carries the envelope subtype faithfully and rendering happens downstream (closer to the SDK boundary), or (b) the channel renders the envelope to text before `enqueue()` so the buffer remains text-only. Picking (a) keeps the envelope alive longer through the pipeline and makes future per-subtype logic (logging, observability, per-subtype routing rules) possible without re-introducing polymorphism; picking (b) is smaller in scope but defeats much of the point of S1.
- **Where rendering is invoked.** Tied to the previous point — once a buffer choice is made, the single rendering invocation point falls out (channel-side or coordinator-side).

The design phase resolves these by picking each concern explicitly. The principle, per the spec's R2 and the interview guidance: anything that ends up on the base needs a reason to be there beyond "it's already in `IncomingMessage` today."
