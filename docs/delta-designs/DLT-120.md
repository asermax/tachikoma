## Shape

| Part | Mechanism | Flag |
|------|-----------|:----:|
| **S1** | Extend `TaskStatus` literal with `"waiting"`; add `sdk_session_id`, `user_response`, and `updated_at` fields to the `TaskInstance` model and ORM; repository writes refresh `updated_at` on every modification | |
| **S2** | Change the evaluator loop's `needs_input` branch in the background task executor: instead of injecting a "proceed with best judgment" message, save the SDK session ID on the instance, transition it to `"waiting"`, dispatch a respondable notification carrying the evaluator rationale, and return — releasing the semaphore slot via the `async with` scope | |
| **S3** | Build respondable notifications by composing a prompt that includes the task question, task definition name, task instance ID, and explicit `respond_to_task` usage instructions; dispatch at `Priority.URGENT`. Non-respondable notifications (success/failure) continue to use the existing builder without response instructions | |
| **S4** | Add a `respond_to_task` MCP tool to the task tools server: validates non-empty response, resolves the instance, enforces `status == "waiting"` and no pending `user_response`, then writes `user_response` (refreshing `updated_at`). Returns clear errors for each failure mode (not found, not waiting, empty, duplicate) | |
| **S5** | Update two prompts: the background task system prompt (explain evaluator-mediated communication and question-asking mechanics) and the main conversation preamble's Tasks/Tools subsection (document `respond_to_task` parameters and when to invoke it) | |
| **S6** | Update the runner's instance-selection query to union `status == "pending"` with `status == "waiting" AND user_response IS NOT NULL`; both flow through the same semaphore acquisition path so new and resumed tasks are processed identically | |
| **S7** | In the executor, when picking up a waiting-with-response instance: mark it `"running"` (refreshes `updated_at`), consume (read + clear) the `user_response`, construct `ClaudeSDKClient` with `resume=sdk_session_id`, inject the user response as the next turn, then continue the existing evaluator loop — supporting multiple pause/resume cycles | |
| **S8** | Add `wait_timeout` to the `[tasks]` config section (default 7200s); the runner's periodic check scans for `status == "waiting" AND updated_at < now - wait_timeout`, marks expired instances as `"failed"` with a timeout reason, and dispatches a failure notification | |
| **S9** | Update crash recovery to leave `"waiting"` instances untouched on startup (only `"running"` is swept to `"failed"`); include `"waiting"` in the duplicate-prevention status list used by the cron instance generator so a waiting cron task doesn't spawn a new instance on the next match | |
