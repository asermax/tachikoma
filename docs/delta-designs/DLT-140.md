# Design: DLT-140 - Allow send_file to accept paths outside the workspace

**Delta Spec**: [../delta-specs/DLT-140.md](../delta-specs/DLT-140.md)
**Status**: Draft

## Purpose

This document explains the design rationale for this delta: the modeling choices, data flow, system behavior, and architectural approach.

After implementation, the "Detected Impacts" section will guide reconciliation into feature design docs.

## Problem Context

The `send_file` MCP tool enforces a strict workspace boundary: any absolute path that is not under the workspace root is rejected. In practice the agent frequently generates files in the system temp directory (PDF exports, rendered charts, one-off artifacts) and currently has to copy them into the workspace before calling `send_file`. The manual copy step is busywork and occasionally fails on the first try when the agent forgets the constraint.

The boundary also makes us silently coupled to the workspace layout: operators can't declare additional trusted roots (e.g. a shared `~/exports/` directory) without edits to the code.

**Constraints:**
- The tool's existing safety properties must be preserved: no arbitrary path (`/etc/passwd`), no directories, no traversal that escapes the allowed set, no attempts to send missing files.
- Validation happens inside an MCP tool handler — it must remain synchronous-friendly and side-effect-free.
- Follows DES-006 (factory + extracted handler): the factory captures state at construction, the handler is plain and testable.
- Skill instructions (`telegram/skill/SKILL.md`) shape the agent's behavior: they must match the new rules so the agent picks valid paths on the first try.

**Interactions:**
- `TelegramChannel.get_mcp_servers()` calls `create_send_file_server(...)` at startup; the factory now also takes the resolved set of allowed roots.
- `TelegramSettings` gains a nested `send_file` section with an `extra_roots` list.
- The agent's `send_file` skill loads `SKILL.md` via the skills pipeline — the documented constraints are part of the agent-facing contract.

## Design Overview

The core move is to replace the single-workspace-boundary check in `validate_file_path` with a membership check against a **resolved, cached set of allowed roots**: the workspace, the system temporary directory, and any operator-configured extras. The set is computed once when `create_send_file_server(...)` runs (at channel startup) and captured in the tool closure.

Symlink handling falls out of using `Path.resolve()` on both the input path and the roots: the *canonical target* is what governs membership, so a symlink inside an allowed root that points outside is rejected, and a symlink outside that points inside is accepted. Directory rejection is added alongside the existing existence check.

Configuration grows a nested `[telegram.send_file]` section so we have room for future `send_file` knobs without reshuffling the flat `TelegramSettings` later. Today it carries one field, `extra_roots: list[Path]`, with `~` expansion and an absolute-path post-validator.

Rejection messages list the allowed roots (resolved absolute paths), giving the agent the information it needs to self-correct and pick a valid location on the next attempt. The `SKILL.md` constraints section is rewritten to describe the three-class membership (workspace / system temp / configured extras) so the agent doesn't need to fail-then-correct in the common case.

## Modeling

### Config additions

```
TelegramSettings (frozen)
├── bot_token: str
├── authorized_chat_id: int
├── push_notifications: bool = True
└── send_file: SendFileSettings = Field(default_factory=SendFileSettings)   (new)
    └── extra_roots: list[Path] = Field(default_factory=list)
        — entries are Path objects
        — `~` is expanded at load (before-validator)
        — must be absolute after expansion (after-validator)
        — need NOT exist at load time
```

TOML shape:

```toml
[telegram]
bot_token = "..."
authorized_chat_id = 12345

[telegram.send_file]
extra_roots = ["~/exports", "/srv/artifacts"]
```

Missing `[telegram.send_file]` falls back to `SendFileSettings()` (empty `extra_roots`). This preserves prior behavior for existing operators.

### Allowed-roots set (per tool server)

```
allowed_roots: tuple[Path, ...]   # resolved, deduplicated, captured in closure
  ├── workspace_path.resolve()
  ├── Path(tempfile.gettempdir()).resolve()
  └── *(p.resolve() for p in configured_extra_roots)
```

- Computed once, at `create_send_file_server(...)` call time (channel startup).
- Stored as a `tuple` (immutable, ordered) so it can be safely captured by the tool closure.
- Deduplicated via `dict.fromkeys(...)` to handle the CI-sandbox case where the workspace is itself under the system temp dir — the AC requires membership to behave as a union regardless.

## Data Flow

### Path validation pipeline

```
1. Input: file_path (str), workspace_path (Path), allowed_roots (tuple[Path, ...])
2. path = Path(file_path)
3. If not path.is_absolute():
     path = workspace_path / path
4. resolved = path.resolve()                # symlinks collapsed, .. normalized
5. If not resolved.exists():
     → raise ValueError("File not found: {resolved}")
6. If not resolved.is_file():
     → raise ValueError("Path is not a regular file: {resolved}")
7. If not any(resolved.is_relative_to(root) for root in allowed_roots):
     → raise ValueError(
         "File must be under one of the allowed roots: "
         "{root_1}, {root_2}, ... (got {resolved})"
       )
8. return resolved
```

Order matters: we resolve first, then check existence, then regular-file, then membership. `resolve()` collapses symlinks so the membership check operates on the canonical target — this is what makes symlink-to-outside get rejected and symlink-to-inside get accepted.

### Startup flow (new path-validation wiring)

```
1. settings loaded, Settings.telegram.send_file.extra_roots is a list[Path]
2. TelegramChannel constructed; self._settings = settings.telegram
3. Coordinator calls channel.get_mcp_servers()
4. Channel calls create_send_file_server(
     bot,
     chat_id=self._settings.authorized_chat_id,
     workspace_path=self._workspace_path,
     configured_extra_roots=self._settings.send_file.extra_roots,
   )
5. Factory computes resolved allowed_roots tuple once, captures in closure
6. MCP server registered; agent tool calls reuse the same resolved set
```

## Key Decisions

### Nested `[telegram.send_file]` config section over flat field

| Field | Content |
|-------|---------|
| Choice | Nest `extra_roots` under a new `SendFileSettings` submodel exposed as `TelegramSettings.send_file` |
| Why | Leaves room to grow — future `send_file` knobs (size limits, MIME filters, per-root captions) can land in the same sub-section without reshuffling `TelegramSettings`. Avoids rename churn later. |
| Sources | Pydantic v2 model-composition docs; pattern already used in `Settings.tasks`, `Settings.workspace`. |
| Options Researched | (a) flat field `extra_file_roots` on `TelegramSettings`, (b) nested `[telegram.send_file]` submodel, (c) top-level `[send_file]` section |
| Why This Over Alternatives | (a) is cheaper today but invites a rename once we add a second knob; (c) decouples from Telegram which doesn't reflect reality — `send_file` is a Telegram-channel tool. (b) fits the existing `Settings.<subsystem>.<setting>` pattern. |
| Consequences | Slightly more nesting in TOML. Default `SendFileSettings()` keeps missing-section behavior clean. |

### Resolve allowed roots once at factory-call time

| Field | Content |
|-------|---------|
| Choice | Compute `allowed_roots` once inside `create_send_file_server(...)` and capture in the tool closure |
| Why | Matches the DES-006 "closure captures per-invocation state" pattern. Avoids per-request filesystem calls for `.resolve()`. |
| Sources | DES-006 (`docs/design/DES-006-sdk-mcp-tool-server-factory.md`); current `validate_file_path` already calls `workspace_path.resolve()` once per request — caching moves that cost to startup. |
| Options Researched | (a) resolve on each request, (b) resolve once at factory call |
| Why This Over Alternatives | (a) would correctly handle "root replaced by symlink at runtime" edge cases but costs a syscall per call; no AC depends on runtime re-resolution. (b) is simpler and sufficient — extra roots that don't exist at load time still resolve lexically and will match paths once the directory appears. |
| Consequences | If an operator replaces an extra root with a symlink at runtime — or creates it as a symlink after startup when it didn't exist at load time — the tool continues to use the resolution computed at factory-call time until restart. Acceptable: these are rare operator actions and a restart is a known recovery. |

### Use `Path.resolve()` + `is_relative_to()` for membership (symlink semantics)

| Field | Content |
|-------|---------|
| Choice | `resolve()` both the input path and each allowed root, then `is_relative_to()` |
| Why | `Path.resolve()` collapses symlinks so the canonical target governs membership. This satisfies both symlink ACs: a symlink inside an allowed root that points outside resolves to an outside target (rejected); a symlink outside that points inside resolves to an inside target (accepted). |
| Sources | Python stdlib `pathlib` docs — `Path.resolve(strict=False)` resolves symlinks of existing components; `Path.is_relative_to()` (3.9+) performs the prefix check. |
| Options Researched | (a) `os.path.realpath` + `os.path.commonpath`, (b) `pathlib.Path.resolve()` + `is_relative_to()`, (c) string-prefix matching against the raw input |
| Why This Over Alternatives | (a) works but forces `str` boundaries and loses type safety. (c) is unsafe — it trivially accepts `/tmp-other` if `/tmp` is allowed, and it ignores symlinks. (b) is idiomatic for this codebase and already used in the current implementation. |
| Consequences | Requires all components along the input path (up to the last existing one) to exist for `resolve()` to give a fully canonical result. Since we require the file itself to exist, this is automatically satisfied. |

### Extra roots may not exist at load time; rejected at request time

| Field | Content |
|-------|---------|
| Choice | Validate only absoluteness of `extra_roots` at config load; do not check existence. A path under a non-existent configured root is rejected naturally at request time by the existence check (step 5 of the pipeline). |
| Why | Explicit spec AC: "Given a configured extra root does not exist on disk at load time, when the config is loaded, then loading succeeds (the directory may be created later)". Operators may configure a directory they plan to create (or that their deployment creates). |
| Sources | DLT-140 spec, Acceptance Criteria § "Configurable extra roots". |
| Options Researched | (a) check existence at load and fail, (b) check existence at load and warn, (c) no existence check |
| Why This Over Alternatives | (a) would violate the AC and block deployment-managed directories. (b) adds noise for a valid configuration. (c) matches the AC and falls back to the request-time existence check, which produces a clear error when the root still doesn't exist when a file is actually used. |
| Consequences | A misspelled extra root is silent at load — it only surfaces when a path under it is tried. Acceptable trade-off for deployment flexibility. |

### Add explicit directory rejection

| Field | Content |
|-------|---------|
| Choice | Use `resolved.is_file()` rather than just `resolved.exists()` |
| Why | Acceptance criterion R5 requires rejecting directories. Today, `send_file` would accept a directory path (`exists() == True`) and hand it to the Telegram API, which returns an opaque error. Pre-check gives a clear, self-correcting error. |
| Sources | Python stdlib `pathlib` docs — `Path.is_file()` returns `False` for directories, symlinks-to-directories (after `resolve()`, symlinks are collapsed, so only the target's file-ness matters), and missing paths. |
| Options Researched | (a) `is_file()`, (b) `not is_dir()`, (c) leave it to the API |
| Why This Over Alternatives | (a) is strict: regular files only. (b) would accept block/char devices and FIFOs. (c) gives the agent a useless error. |
| Consequences | FIFOs, sockets, block devices are also rejected. Acceptable — the tool is for sending normal files. |

### Rejection error names all resolved allowed roots

| Field | Content |
|-------|---------|
| Choice | Error text enumerates the resolved allowed roots: `"File must be under one of the allowed roots: /home/me/ws, /tmp, /srv/artifacts (got /etc/passwd)"` |
| Why | R4 requires the agent can self-correct. Listing the actual roots (not a generic message) lets the agent pick a valid location on the next try without asking the user. |
| Sources | DLT-140 spec, R4. |
| Options Researched | (a) generic "outside allowed roots" message, (b) enumerate roots in error, (c) include an example valid path |
| Why This Over Alternatives | (a) leaves the agent guessing and likely to retry incorrectly. (c) is over-specified and quickly stale. (b) gives exactly the information needed to self-correct. |
| Consequences | Error messages are longer. They're visible to the agent (not the end user), so verbosity is a feature — it narrows the action space. The workspace path appearing in the message is not a leak concern: it is already widely exposed to the agent via prompt composition (see DES-008, which uses it as a prompt placeholder). |

## System Behavior

### Scenario: Successful send from the system temp directory

**Given**: The agent has written `/tmp/report.pdf` and calls `send_file({"file_path": "/tmp/report.pdf"})`
**When**: `handle_send_file` runs validation
**Then**: `resolve()` returns `/tmp/report.pdf` (or the platform equivalent, e.g. `/private/tmp/report.pdf` on macOS). `exists()` passes, `is_file()` passes, the resolved path `is_relative_to(tempfile.gettempdir().resolve())` passes. The document is uploaded.

### Scenario: Successful send using a workspace-relative path

**Given**: The agent calls `send_file({"file_path": "exports/report.pdf"})` and the file exists under the workspace
**When**: Validation runs
**Then**: Because the path is not absolute, it is joined with `workspace_path` before `resolve()`. The resolved path is under `workspace_path.resolve()`, which is in `allowed_roots`. The file is sent.

### Scenario: Successful send from a configured extra root

**Given**: Config contains `[telegram.send_file] extra_roots = ["~/exports"]`; the file `~/exports/chart.png` exists
**When**: The agent calls `send_file({"file_path": "/home/user/exports/chart.png"})`
**Then**: `~` was expanded at load, giving `/home/user/exports`. The resolved path is under that root. The photo is sent.

### Scenario: Configured extra root does not exist at load

**Given**: `extra_roots = ["/srv/artifacts"]` but `/srv/artifacts` does not exist on disk
**When**: The application starts
**Then**: Config load succeeds. If the agent immediately tries `send_file({"file_path": "/srv/artifacts/x.png"})`, validation fails at the existence check with "File not found". Once `/srv/artifacts/x.png` is actually created, the same call succeeds.

### Scenario: Relative extra root rejected at load

**Given**: Config contains `extra_roots = ["exports"]` (no `~`, not absolute)
**When**: Settings load runs
**Then**: `SendFileSettings.extra_roots` post-validator raises `ValueError("extra_roots entries must be absolute paths: 'exports'")`. `_format_validation_error` turns it into a clear startup error; the process exits with code 1.

### Scenario: Path outside all allowed roots

**Given**: The agent calls `send_file({"file_path": "/etc/passwd"})`
**When**: Validation runs
**Then**: `resolve()` → `/etc/passwd`, exists, is a file, but `is_relative_to(root)` is false for every root in `allowed_roots`. The tool returns `is_error: True` with a message listing the allowed roots (`/home/me/ws`, `/tmp`, etc.) and the rejected path, giving the agent enough information to retry with a valid location.

### Scenario: Path is a directory

**Given**: The agent calls `send_file({"file_path": "/tmp/some-folder"})`
**When**: Validation runs
**Then**: `resolve()` and `exists()` pass but `is_file()` is false. The tool returns `is_error: True` with "Path is not a regular file: /tmp/some-folder".

### Scenario: Symlink inside a root that points outside all roots

**Given**: `/tmp/escape` is a symlink to `/etc/passwd`
**When**: The agent calls `send_file({"file_path": "/tmp/escape"})`
**Then**: `resolve()` follows the symlink to `/etc/passwd`, which is not under any allowed root. The tool rejects with the standard out-of-roots error, naming the target path after resolution.

### Scenario: Symlink outside all roots that points inside a root

**Given**: `/home/user/shortcut` is a symlink to `/tmp/report.pdf`
**When**: The agent calls `send_file({"file_path": "/home/user/shortcut"})`
**Then**: `resolve()` follows the symlink to `/tmp/report.pdf`, which is under the system temp root. The file is sent.

### Scenario: System temp directory reached via platform symlink

**Given**: On macOS, `/tmp` is a symlink to `/private/tmp`. The agent calls `send_file({"file_path": "/tmp/report.pdf"})`
**When**: Validation runs
**Then**: Both the input and `tempfile.gettempdir()` resolve to `/private/tmp/...`, so the membership check passes. The file is sent. The reverse also works: if the agent passes `/private/tmp/report.pdf`, validation still matches because both sides are resolved.

### Scenario: Workspace sits under the system temp directory

**Given**: A CI sandbox where `workspace_path` is `/tmp/ci-run-42/ws`. The agent calls `send_file({"file_path": "src/main.py"})`
**When**: Validation runs
**Then**: The path is joined with the workspace, resolved, and matches `workspace_path.resolve()`. Dedup ensures the temp-dir entry doesn't shadow the workspace entry — the union behavior is preserved. The file is sent.

### Scenario: Missing `[telegram.send_file]` section

**Given**: Config has `[telegram]` with `bot_token` and `authorized_chat_id` but no `[telegram.send_file]` sub-section
**When**: Settings load
**Then**: `TelegramSettings.send_file` defaults to `SendFileSettings()` with `extra_roots = []`. Behavior matches existing operators — only workspace and system temp are allowed. Note: `SendFileSettings` validation (including the non-absolute rejection) runs only when `[telegram]` itself is configured — when `channel = "repl"` and `[telegram]` is absent, `Settings.telegram` is `None` and `SendFileSettings` is never instantiated.

## Notes

- Python's `tempfile.gettempdir()` honors `TMPDIR`/`TEMP`/`TMP` env vars and falls back to platform defaults; on macOS this is typically under `/var/folders/...`. `resolve()` on its result normalizes symlinks like `/tmp → /private/tmp`.
- `Path.is_relative_to(other)` was added in Python 3.9 and is already used by `validate_file_path`; no stdlib version bump required.
- The tool description passed to `@tool(...)` inside `create_send_file_server` is part of the agent-facing contract (the SDK exposes it in the tool listing) and must match `SKILL.md`.
