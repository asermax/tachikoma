# Design: DLT-161 — Workflow composition via inline sub-workflow references

**Delta Spec**: [../delta-specs/DLT-161.md](../delta-specs/DLT-161.md)
**Status**: Draft

## Purpose

This document explains the design rationale for DLT-161: how composition references are parsed and validated at registry-load time, how nested workflow state is persisted and routed at runtime, how the engine maintains the illusion of a single continuous workflow for the agent across nested layers, and how the auto-resume / abort cascades stay atomic.

After implementation, the "Detected Impacts" section will guide reconciliation into the workflow-state-machine feature documentation.

## Problem Context

Skill authors have started building real workflows that share sub-sequences. The motivating case is a "process inbox note" routine that both a weekly review and a daily review want to invoke at the same point in their flows. Today the only way to share it is to copy-paste the steps into both parents, which immediately drifts as the sub-sequence evolves.

The challenge is that a workflow is currently a single flat ordered list of steps with a single state record. Nesting introduces three new responsibilities the engine doesn't have today:

1. **Definition-time graph awareness** — the registry must detect cycles and missing references at load time, before the agent ever sees an invalid workflow.
2. **Runtime layer tracking** — at any moment during a nested run, the engine must know which workflow is the deepest active layer and route the agent's tool calls there. The agent must not have to juggle multiple workflow IDs.
3. **Multi-record atomicity** — when a child auto-finalizes, three things must happen as one: the child record is soft-deleted, the parent's composition step is auto-completed, the parent's next pending step is auto-started. Likewise abort must tear down a transitive descendant set as a single transaction.

**Constraints inherited from the existing workflow subsystem:**

- The persistence pattern (ADR-007) — SQLAlchemy 2.0 async + aiosqlite, ORM models internal to the persistence layer, frozen dataclasses across the boundary.
- Migrations are pragma-based (`pragma_table_info` + `ALTER TABLE`) — there is no Alembic.
- MCP tool servers (DES-006) — handlers extracted from `@tool` decorators so they're testable without the SDK.
- The condition evaluator (DLT-159) forks the SDK session via `fork_and_capture` (DES-004) and may take seconds per evaluation. Holding a DB transaction across that call would block any concurrent writer for the LLM round-trip.
- The agent uses a scratchpad file convention — a markdown file the agent reads/edits. There is no MCP tool for the scratchpad.

**Interactions:**

- Skill registry (`skills.registry.SkillRegistry`) — composition target lookup, cycle/reference validation extends `_validate_deps()`.
- Workflow loader (`workflows.loader`) — adds parsing of the `composes` frontmatter field.
- Workflow MCP tools (`workflows.tools`) — the bulk of new behavior lives in `handle_update_workflow_state`, `handle_get_workflow_state`, `handle_end_workflow`, `handle_list_active_workflows`.
- Repository (`workflows.repository.WorkflowStateRepository`) — new columns, new methods (`get_active_chain`, `get_active_child`, `abort_cascade`, `finalize_child_and_resume_parent`); modified methods (`get_active`, `list_active`, `list_stale`).
- Database (`database.py`) — schema migration for the two new columns and the new index.
- Stale cleanup processor (`workflows.cleanup.StaleWorkflowCleanupProcessor`) — uses subtree-aware staleness logic.
- Built-in `workflow-authoring-guide` skill — documents the new `composes` field plus the previously-undocumented `condition` field.
- System preamble (`context/loading.py`) — teaches the agent the single-ID driving rule, breadcrumb format, and behavioral changes to `list_active_workflows` and `get_workflow_state`.

## Design Overview

The design splits cleanly into three layers — load-time, runtime, and presentation:

```
┌──────────────────────────────────────────────────────────────────┐
│ Load Time (skills.registry._validate_deps)                       │
│   • parse `composes` field                                       │
│   • build composition graph                                      │
│   • DFS cycle detection → reject cycles                          │
│   • validate reference targets exist + have ≥1 step              │
│   • cascading rejection: parent fails if its target fails        │
└──────────────────────────────────────────────────────────────────┘
                            ↓
┌──────────────────────────────────────────────────────────────────┐
│ Runtime — handle_update_workflow_state                           │
│   1. read full chain via get_active_chain(parent_id)             │
│   2. validate step ID matches deepest layer                      │
│   3. enter cascade loop (in memory):                             │
│        evaluate conditions → accumulate MutationBatch            │
│        descend into composition spawn / pop on auto-finalize     │
│   4. one `async with db.begin():` applies the batch atomically   │
│   5. construct response with breadcrumb + next-step instructions │
└──────────────────────────────────────────────────────────────────┘
                            ↓
┌──────────────────────────────────────────────────────────────────┐
│ Persistence — WorkflowStateRepository                            │
│   • workflow_states adds parent_workflow_id, parent_step_id      │
│   • composite index on (parent_workflow_id, deleted_at)          │
│   • get_active filtered to top-level                             │
│   • get_active_chain / get_active_child for deepest-active walk  │
│   • abort_cascade / finalize_child_and_resume_parent for         │
│     atomic multi-record writes                                   │
└──────────────────────────────────────────────────────────────────┘
```

The agent never sees nesting as a structural concept. From its perspective:

- One ID per logical workflow (always the parent's).
- Each tool response carries a breadcrumb saying "you are at `<parent>/<step> > <child>/<step>` right now."
- The deepest-active routing rule means a step ID that doesn't match the active layer fails fast with a helpful error listing the valid step IDs for the current layer.

The single biggest design decision is the cascade atomicity model: **stage all state changes in memory while running condition evaluations, then commit them in a single atomic block.** This mirrors the existing DLT-159 `_evaluate_and_advance` pattern — conditions evaluate outside any transaction, mutations land in one final write — and avoids holding a SQLite transaction across slow LLM calls.

## Shape

| Part | Mechanism | Flag |
|------|-----------|:----:|
| **S1** | Add `composes: str \| None` to `StepDefinition`. `loader._load_step` parses it from frontmatter (validates string type); accepts `<workflow>` (same-skill) or `<skill>/<workflow>` (cross-skill) syntax. The composition step's `instructions.md` body is ignored at runtime — only its frontmatter (`title`, `required`, `condition`, `required_skills`) is honoured. | |
| **S2** | `_resolve_composes(composes_str, parent_skill_name) -> (skill_name, workflow_name)` — splits on first `/` if present, otherwise pairs with parent's skill. Called at registry validation time and at spawn time. | |
| **S3** | Cycle detection in `SkillRegistry._validate_deps()`: build adjacency map from each `(skill, workflow)` to its composed targets, run coloring DFS; any workflow in a cycle is removed from `_workflows` and one warning per cycle is logged. | |
| **S4** | Static reference validation in `SkillRegistry._validate_deps()`: each composition step's resolved target must exist and have ≥1 step. Cascading rejection: if the target is itself rejected (cycle or missing), the parent is also rejected. One warning per rejected workflow. | |
| **S5** | Two new `Mapped[str \| None]` columns on `WorkflowStateRecord` and the `WorkflowState` dataclass: `parent_workflow_id`, `parent_step_id`. Composite `Index("ix_workflow_states_parent", "parent_workflow_id", "deleted_at")` serves both top-level filter and active-child lookup from one index. Migration in `database.py` follows the existing `pragma_table_info` + `ALTER TABLE ADD COLUMN` pattern (both nullable, no DEFAULT). | |
| **S6** | Restrict `repository.get_active(skill, workflow)` to top-level rows (`parent_workflow_id IS NULL`). Add `get_active_child(parent_id) -> WorkflowState \| None`. Both existing callers of `get_active` want top-level uniqueness only (R10). | |
| **S7** | Composition spawn folded into the cascade-aware activation loop (see S9). When the loop reaches a step whose snapshot has `composes` set, it captures the current registered child definition as a snapshot, allocates a `child_id`, queues a "create child record" mutation in the in-memory batch, and makes the child the current layer for the next iteration. No call-stack recursion — pure iteration. | |
| **S7.1** | At spawn time, `registry.get_workflow(composes_skill, composes_workflow)` returns the *current* registered definition (per R4.1: snapshot at spawn time, not parent-start time). The definition is serialized via the existing `_step_to_snapshot` and stored on the child's `definition_snapshot`. | |
| **S8** | New `repository.get_active_chain(root_id) -> list[WorkflowState]` — Python-driven walk: read root, then iteratively `SELECT WHERE parent_workflow_id = current.id AND deleted_at IS NULL` until no child is found. Returns root-first list. Depth bounded by R5/R17. Routing in `handle_update_workflow_state` validates that the `step` arg matches the deepest layer's snapshot AND passes the deepest layer's transition rules — there is no fall-through to other layers' snapshots, so a step ID that exists in some non-deepest layer (parent's composition step, or a sibling/grandchild step in a non-active branch) returns the same routing error as a typo. Error names the deepest layer's workflow and lists valid step IDs. | |
| **S9** | Cascade-aware activation: an in-memory loop walks the active chain, applies the action to the deepest layer, then alternates between (a) advancing within the current layer via `_evaluate_and_advance`, (b) descending into a freshly-spawned child layer (S7), (c) auto-finalizing the deepest layer + auto-completing the parent's composition step + popping up. Conditions evaluate **outside** any DB transaction; mutations accumulate in an in-memory `MutationBatch` (state updates, child creates, soft-deletes). Once the loop terminates, one `async with db.begin():` block applies all queued mutations atomically. On any raise, the batch is dropped — no partial state ever committed. | |
| **S10** | Composition-step-level `condition` and `required: false` are evaluated by the existing `_evaluate_and_advance` helper *before* the spawn branch fires. By construction, S7's spawn only runs after a composition step transitions to `STEP_STARTED`. The condition evaluator template (`conditions.py::_PROMPT_TEMPLATE`) is unchanged — it sees only the parent's step_states, never the unborn child's. | |
| **S11** | At child-create time, the child's `scratchpad_path` is copied from its parent's path. Cleanup deletes the file once on top-level finalization or top-level abort. Children never own scratchpad lifecycle. | |
| **S12** | `_render_breadcrumb(chain, current_step_id) -> str` renders `<workflow_name>/<step_id>` per layer joined by ` > `. Prepended to activation responses (in `_build_step_response`) and `get_workflow_state` output. For non-deepest layers, the breadcrumb reads the layer's persisted `current_step` field (which holds the parent's composition step ID — the parent's `current_step` is committed during the spawn batch and is stable while the child runs); for the deepest layer the breadcrumb uses the freshly-activated step ID from the cascade outcome rather than the persisted record (the persisted record reflects the just-committed state). | |
| **S13** | `handle_get_workflow_state(parent_id)` calls `get_active_chain(parent_id)` and inlines the active child path under a `### Active Child` section. Completed composition steps surface as `completed` with no nested data. Backwards-compat: a direct call with a child ID returns the child's standalone view with a note recommending access via the parent. | |
| **S14** | `repository.list_active()` adds `parent_workflow_id IS NULL` to its WHERE so only top-level rows surface. `handle_list_active_workflows` is unchanged. | |
| **S15** | `repository.abort_cascade(root_id) -> list[str]` — reads the full descendant set via iterated `get_active_chain`-style widening, then in one `async with db.begin():` block soft-deletes every record and returns their IDs. `handle_end_workflow` calls `abort_cascade` for any abort/complete on a top-level ID. Calls on a child ID return an error directing the agent to operate on the top-level. Shared scratchpad is deleted once after the atomic block commits. | |
| **S16** | Stale cleanup walks each top-level root, computes `max(updated_at)` across its descendant subtree (Python-driven via the chain walker), and only stales the entire subtree if every record's `updated_at` exceeds the threshold. `repository.list_stale(threshold)` is rewritten to return top-level roots whose subtree max is older than the threshold. **Early-exit optimization**: roots whose own `updated_at >= cutoff` skip the subtree walk entirely (they're not stale regardless of descendants), so only stale-looking roots pay the descendant walk cost. `StaleWorkflowCleanupProcessor` calls `abort_cascade` per stale root. Cleanup runs as a post-processor in `pre_finalize` (existing pattern) — frequency tied to session close rate, so N × depth indexed lookups are amortized acceptably. | |
| **S17** | Update `src/tachikoma/skills/builtin/workflow-authoring-guide/SKILL.md` and `references/step-design.md` to document the `composes` frontmatter field: same-skill / cross-skill syntax; the rule that the composition step's `instructions.md` body is ignored; interaction with `required: false` and `condition`; rejection rules (cycle / missing / zero-step target); a worked example. | |
| **S17.1** | Backfill `condition` field documentation (DLT-159 carryover) in the same two files: how the natural-language prompt is evaluated by a forked sub-agent, fail-closed behavior, the rule that condition-skip overrides `required: true`, and an example. | |
| **S18** | Update `src/tachikoma/context/loading.py` `# Workflows` section to teach the agent: single-ID driving, breadcrumb format, `list_active_workflows` is top-level-only, `get_workflow_state` inlines active child path, and condition-skip behavior (DLT-159 backfill). | |

### Cross-Layer Contracts

**Repository surface (changes only):**

```
get_active_chain(root_id: str) -> list[WorkflowState]
  # Root-first; empty list if root not found or already deleted.
  # Walks parent_workflow_id back-edges via repeated SELECTs (depth-bounded).

get_active_child(parent_id: str) -> WorkflowState | None
  # Single-step lookup: SELECT WHERE parent_workflow_id = parent_id
  # AND deleted_at IS NULL. Returns first match (uniqueness invariant
  # enforced at spawn — at most one active child per parent).

abort_cascade(root_id: str) -> list[str]
  # Atomic. Soft-deletes root + every transitive descendant in one
  # `async with db.begin():` block. Returns the IDs that were soft-deleted.

finalize_child_and_resume_parent(
    *, child_id, parent_id, parent_step_id,
    parent_step_states, parent_current_step,
    next_layer_writes,  # zero or more "create child record" + state updates
    finalize_top_level,  # bool — whether the cascade collapsed all the way up
) -> tuple[WorkflowState | None, WorkflowState | None]
  # Atomic. Applies the entire MutationBatch in one transaction.
  # Returns (top_level_state, deepest_active_state) for response shaping.

# Modified semantics (no signature change):
get_active(skill, workflow)        # adds parent_workflow_id IS NULL
list_active()                      # adds parent_workflow_id IS NULL
list_stale(threshold)              # subtree-aware — returns top-level roots
                                   #   whose subtree MAX(updated_at) < cutoff
```

**MCP tool schemas (no changes — behavior changes only):**

The tool signatures in the workflow-state-machine feature design remain unchanged. What changes:

- `update_workflow_state(workflow_id, step, action)` — `workflow_id` is always the top-level ID; `step` must match the deepest active layer's expected step. Errors include the deepest layer's workflow name + valid step IDs.
- `get_workflow_state(workflow_id)` — top-level ID returns nested view; child ID still works for backwards compat with a routing note.
- `end_workflow(workflow_id, action)` — top-level ID triggers the abort cascade; child ID returns an error.
- `list_active_workflows()` — only top-level workflows surface.

**Cycle detection algorithm (S3):**

DFS with three-color marking on the composition graph. Vertices = `(skill_name, workflow_name)` pairs. Edges from each composition step to its resolved target. A back-edge to a vertex on the current DFS stack is a cycle; mark every vertex in the cycle for rejection. After the DFS pass, remove rejected vertices from `_workflows` and log one warning per cycle (listing the cycle's vertices). Self-loops are detected on the first DFS step.

**Reference validation algorithm (S4):**

After cycle detection, for each surviving workflow walk its composition steps:
- Resolve target via `resolve_composes(composes_str, parent_skill)`.
- If target not in `_workflows` → reject parent with "missing target" warning.
- If target has zero steps → reject parent with "zero-step target" warning.

Reference validation is iterated to fixed-point: rejecting a parent may cause its parents to fail validation in a second pass (cascading rejection). Two-pass implementation is sufficient because the graph is acyclic after S3 — every rejection propagates one edge per pass, and acyclic propagation converges in `depth` iterations; the second pass terminates when no new rejections were added in the previous pass.

### Shared Logic

- **Cascade outcome dataclass**: `CascadeOutcome(deepest_layer_id, active_step_id, condition_skips, finalized_top_level)` returned from `_run_cascade`. Drives both the persistence call and the response construction.
- **MutationBatch**: ordered list of typed mutations (`UpdateState`, `CreateChild`, `SoftDelete`). Materialized in memory during the cascade walk; applied as a unit by `finalize_child_and_resume_parent` or `abort_cascade`.
- **Step-snapshot lookup**: existing `_get_step_from_snapshot(snapshot, step_id) -> dict` extends naturally — composition steps store `composes` in their snapshot dict alongside `id`, `title`, `required`, `path`, `required_skills`, `condition`.
- **Skill resolution at activation**: existing `_render_required_skills(step_info, registry)` continues to fire on every step activation, including composition steps that declare `required_skills` at the parent level. Composition-step skills are emitted alongside the child's first step's skills, deduped via the existing `seen` set across both layers' skill lists.

## Modeling

```
StepDefinition (filesystem, frozen):
  id: str
  title: str
  instructions_path: Path
  references_path: Path | None
  scripts_path: Path | None
  required: bool = True
  required_skills: tuple[str, ...] = ()
  condition: str | None = None
  composes: str | None = None         # NEW — raw frontmatter value
  properties: dict

WorkflowDefinition (filesystem, frozen):
  skill_name: str
  workflow_name: str
  steps: list[StepDefinition]
  path: Path

WorkflowState (database — table: workflow_states):
  id: str (UUID, PK)
  skill_name: str (Indexed)
  workflow_name: str (Indexed)
  parent_workflow_id: str | None       # NEW — set on children, NULL on top-level
  parent_step_id: str | None           # NEW — composition step ID in the parent
  current_step: str | None
  step_states: JSON
  definition_snapshot: JSON
  scratchpad_path: str                 # children inherit parent's path
  deleted_at: datetime | None
  created_at: datetime
  updated_at: datetime

  Indexes:
    ix_workflow_states_skill_name        (skill_name)
    ix_workflow_states_workflow_name     (workflow_name)
    ix_workflow_states_active_lookup     (skill_name, workflow_name)
    ix_workflow_states_parent            (parent_workflow_id, deleted_at)   # NEW

  Invariants (application-level):
    - At most one active row per (skill_name, workflow_name) where
      parent_workflow_id IS NULL — top-level uniqueness (R10).
    - At most one active child per parent — enforced by spawn logic
      (a parent's composition step is started once before another spawn).
      No DB-level partial unique index is added — consistent with the
      codebase's no-partial-index convention. If the invariant is ever
      violated (corruption), `get_active_child` returns the first match
      and logs a warning; the situation is treated as recoverable via
      abort+restart of the affected top-level workflow.
    - parent_workflow_id and parent_step_id are set together (both NULL
      or both non-NULL).
    - All records in a connected component share the same scratchpad_path.

CascadeOutcome (in-memory, ephemeral):
  deepest_layer_id: str
  active_step_id: str | None     # None if top-level finalized
  condition_skips: list[(workflow_name, step_id, reason)]
  finalized_top_level: bool

MutationBatch (in-memory, ephemeral):
  ordered: list[Mutation]
  Mutation = UpdateState(layer_id, step_states, current_step)
           | CreateChild(child_id, parent_id, parent_step_id,
                         skill_name, workflow_name, step_states,
                         definition_snapshot, scratchpad_path)
           | SoftDelete(layer_id)
```

The composition graph (load-time only):

```
CompositionGraph (in-memory, transient — built during _validate_deps):
  vertices: set[(skill_name, workflow_name)]
  edges: dict[vertex, list[vertex]]   # from parent → composed targets
```

## Data Flow

### Load-time validation

```
1. SkillRegistry._discover() loads all skills + workflows.
2. SkillRegistry._validate_deps() runs:
   2a. Build composition graph: for each workflow, for each step with
       a composes field, resolve the target and add an edge.
   2b. Run cycle detection (DFS three-color). Collect cycles.
   2c. Remove cycle members from _workflows. Log one warning per cycle.
   2d. Run reference validation (target exists + has ≥1 step). Iterate
       to fixed-point so cascading rejections converge.
   2e. Remove rejected references' parents from _workflows. Log warnings.
   2f. Existing skill depends_on / required_skills validation runs as before.
3. After _validate_deps, _workflows contains only valid composable workflows.
```

### Normal nested execution

```
Agent: start_workflow("review-skill", "weekly-review")
  → top-level state record created, scratchpad file created
  → step list returned with composition steps marked as such

Agent: update_workflow_state(parent_id, "01-plan", "start")
  → routing: chain = [parent], deepest = parent, step matches parent's "01-plan"
  → action applied: parent.step_states["01-plan"] = STARTED
  → cascade loop terminates (non-composition step started)
  → MutationBatch = [UpdateState(parent, ...)]
  → committed atomically
  → response includes breadcrumb "weekly-review/01-plan" + step instructions

Agent: update_workflow_state(parent_id, "01-plan", "complete")
  → routing: deepest = parent, step matches
  → cascade loop:
      mark "01-plan" completed (in memory)
      _evaluate_and_advance finds next pending: "02-handle-inbox" with composes
      composition step gets STARTED (in memory) — its condition (if any)
        is evaluated here, possibly condition-skipping it (R14: no spawn)
      spawn branch fires: build child snapshot, allocate child_id, queue
        CreateChild mutation, descend into child layer
      child's first step "01-check" — evaluate its condition (out-of-txn)
      condition passes: mark "01-check" STARTED in child's step_states
      cascade loop terminates (non-composition step started)
  → MutationBatch:
      [UpdateState(parent, step_states={...,"01-plan":COMPLETED,
                                         "02-handle-inbox":STARTED}),
       CreateChild(child_id, parent_id, "02-handle-inbox",
                   skill, "process-inbox-note", {"01-check":STARTED, ...},
                   snapshot, parent.scratchpad_path),
       UpdateState(child_id, current_step="01-check")]
  → finalize_child_and_resume_parent applies the batch atomically
  → response: breadcrumb "weekly-review/02-handle-inbox >
                          process-inbox-note/01-check"
              + child's "01-check" instructions

Agent: update_workflow_state(parent_id, "01-check", "complete")
  → routing: chain = [parent, child], deepest = child, step matches
  → cascade loop:
      mark child.step_states["01-check"] COMPLETED (in memory)
      _evaluate_and_advance: find next pending → "02-categorize"
      "02-categorize" started; non-composition; cascade terminates
  → MutationBatch = [UpdateState(child, ...)]
  → committed atomically
  → response: breadcrumb + "02-categorize" instructions

(repeat through child's last step)

Agent: update_workflow_state(parent_id, "02-categorize", "complete")
  (assume "02-categorize" is the last step in the child)
  → cascade loop:
      mark "02-categorize" COMPLETED (in memory)
      _evaluate_and_advance returns None (no pending steps in child)
      auto-finalize child: queue SoftDelete(child_id)
      pop layer: parent's "02-handle-inbox" auto-completes (in memory)
      _evaluate_and_advance on parent: find next pending → "03-summary"
      "03-summary" started; non-composition; cascade terminates
  → MutationBatch:
      [UpdateState(child, step_states={..."02-categorize":COMPLETED}),
       SoftDelete(child_id),
       UpdateState(parent, step_states={..."02-handle-inbox":COMPLETED,
                                          "03-summary":STARTED},
                   current_step="03-summary")]
  → committed atomically
  → response: breadcrumb "weekly-review/03-summary" + "03-summary" instructions
```

### Cascade up to top-level (parent's last step is composition)

```
Agent: update_workflow_state(parent_id, <child_last_step>, "complete")
  → cascade loop:
      mark child step COMPLETED
      child auto-finalizes (queue SoftDelete)
      parent's composition step auto-completes
      _evaluate_and_advance on parent: returns None — parent's last step
      parent auto-finalizes (queue SoftDelete + scratchpad cleanup flag)
      cascade terminates with finalized_top_level=True
  → MutationBatch applied atomically
  → after commit: scratchpad file deleted (idempotent unlink)
  → response: "Workflow weekly-review complete and finalized"
```

### Abort cascade

```
Agent: end_workflow(parent_id, "abort")
  → handle_end_workflow:
      validate parent_id is top-level (parent_workflow_id IS NULL)
      call abort_cascade(parent_id) — atomic
        repository walks descendants via get_active_chain-style widening
        (BFS with continued queries while any record has children)
        in one async with db.begin(): block, soft-delete all records
        return list of soft-deleted IDs
      after commit: delete scratchpad file
  → response: "Workflow weekly-review aborted. State cleaned up."
```

### Stale cleanup

```
StaleWorkflowCleanupProcessor.process:
  stale_roots = repository.list_stale(threshold)
    # Walks each top-level record, computes subtree MAX(updated_at)
    # via get_active_chain. Only returns roots whose entire subtree
    # is older than the cutoff.
  for root in stale_roots:
    abort_cascade(root.id)         # atomic
    delete scratchpad once
```

### Recovery flow

```
Agent loses context (compaction):
  → reads scratchpad file → finds parent_id
  → calls get_workflow_state(parent_id)
    chain = get_active_chain(parent_id)
    response includes:
      - parent step states (composition step shown as STARTED)
      - "### Active Child" section with child name, current step, step states
      - breadcrumb header
  → agent re-orients, calls update_workflow_state(parent_id, <next>, ...)

Agent loses everything (no parent_id):
  → list_active_workflows() — only top-level workflows surface
  → pick the relevant one → get_workflow_state(parent_id) → resume
```

## Key Decisions

### Stage in memory, single atomic commit (cascade atomicity)

| Field | Content |
|-------|---------|
| Choice | Conditions evaluate outside the DB transaction. Mutations accumulate in an in-memory `MutationBatch`. One `async with db.begin():` block applies everything atomically at the end of the cascade. |
| Why | Holds the SQLite write lock only during the actual write phase, not across slow LLM calls in the condition evaluator. Mirrors the existing DLT-159 `_evaluate_and_advance` pattern. R13's "entire cascade rolled back atomically" is satisfied trivially because nothing is written until the final commit. |
| Sources | SQLAlchemy 2.0 async docs (verified via doc-researcher, 2026): `async with session.begin():` is the canonical idiom, rolls back on raise; aiosqlite delivers DBAPI rollback faithfully. DLT-159 implementation in `tools.py::_evaluate_and_advance` already uses "evaluate then write." |
| Options Researched | (A) Stage-then-commit (chosen). (B) Hold the transaction across condition evaluations. (C) Compensating writes — write each mutation immediately, undo on failure. |
| Why This Over Alternatives | Over (B): Holds a SQLite write transaction during slow LLM calls; depth-3 cascades with conditions on every step could hold the lock 30+ seconds. Doesn't match existing DLT-159 pattern. Over (C): Compensating writes are notoriously hard — multiple soft-deletes need re-undeleting on failure; child records need hard-deletion. Atomic `begin()` is simpler. |
| Consequences | Pro: Lock-hold time matches existing single-row updates (~ms). R13 atomicity satisfied. Adding new mutation types is uniform. Con: Slightly more in-memory bookkeeping (~5-10 mutations per call max, negligible). |

### Python-driven chain walk (vs. recursive CTE)

| Field | Content |
|-------|---------|
| Choice | `get_active_chain(root_id)` reads root, then iteratively `SELECT WHERE parent_workflow_id = current.id AND deleted_at IS NULL` until no child is found. Stale cleanup uses iterative widening per top-level root. |
| Why | Depth is bounded by R5/R17 (real workflows nest 1-3 levels). 2-5 sequential indexed queries cost sub-millisecond each on aiosqlite. Codebase has zero existing recursive CTE usage — introducing one would require a new SQL idiom for marginal benefit invisible against SDK call latency. |
| Sources | SQLAlchemy 2.0 async + SQLite docs (verified via doc-researcher, 2026): both partial indexes and recursive CTEs are supported, neither used elsewhere. Existing repository pattern (`workflows/repository.py`): every method is a single `select()` with simple WHERE clauses. |
| Options Researched | (A) Python-driven multi-query walk (chosen). (B) Single recursive CTE per traversal. (C) Cache `active_child_id` field on parent record. |
| Why This Over Alternatives | Over (B): No prior CTE usage; one-off pattern with invisible perf gain against LLM latency. Over (C): Adds invariant maintained on every spawn / finalize / abort. Three new failure modes. Premature optimization for an O(depth × indexed-lookup) query. |
| Consequences | Pro: Matches existing repository style. Each layer's `WorkflowState` is fully read into the chain — useful for breadcrumb and nested view without further queries. Con: 2-5 round-trips per `update_workflow_state`. Acceptable on local indexed file DB. |

### Composite (non-partial) parent index

| Field | Content |
|-------|---------|
| Choice | `Index("ix_workflow_states_parent", "parent_workflow_id", "deleted_at")`. No partial-index predicate. |
| Why | SQLite uses leading-column prefixes — single index serves both `parent_workflow_id IS NULL AND deleted_at IS NULL` and `parent_workflow_id = X AND deleted_at IS NULL`. No other model uses partial indexes; consistency wins. |
| Sources | SQLAlchemy 2.0 docs (verified, 2026): `sqlite_where=` for partial indexes is supported. `workflows/model.py::ix_workflow_states_active_lookup` is a plain composite index, no partial predicate. |
| Options Researched | (A) Composite (parent_workflow_id, deleted_at) — chosen. (B) Plain `Index(parent_workflow_id)`. (C) Partial `Index(parent_workflow_id, sqlite_where=text("deleted_at IS NULL"))`. |
| Why This Over Alternatives | Over (B): single composite handles both query patterns; (B) needs an additional filter step. Over (C): No prior partial-index usage in codebase; (A) is sufficient without introducing new pattern. |
| Consequences | Pro: One index, two query patterns served. Consistent with existing index conventions. Con: Tiny space overhead from including soft-deleted rows (negligible). |

### Repository-owned cascade methods (vs. transactional context manager)

| Field | Content |
|-------|---------|
| Choice | New `WorkflowStateRepository.abort_cascade` and `finalize_child_and_resume_parent` methods own one session each, use `async with db.begin():` internally. No `AsyncSession` exposed to handlers. |
| Why | ADR-007 mandates "no SQLAlchemy types escape the persistence layer." A transactional context manager that yields an `AsyncSession` to handlers would leak that type. |
| Sources | ADR-007 (Persistence Layer): explicit constraint that ORM types are internal. Existing repository methods: every public method opens its own session and commits, returning frozen dataclasses. |
| Options Researched | (A) Repository-owned cascade methods (chosen). (B) `async with repo.transaction() as txn:` context manager. (C) Pass `AsyncSession` into existing methods. |
| Why This Over Alternatives | Over (B): Leaks transaction-shaped object across boundary; requires handlers to know SQLAlchemy idioms. Over (C): Most disruptive — changes every call site of every repository method. |
| Consequences | Pro: ADR-007 compliance preserved. Cascade complexity stays in repository layer where it can be unit-tested. Con: Two new repository methods with shaped argument bags (mitigated by typed `MutationBatch`). |

### Single-ID driving for the agent

| Field | Content |
|-------|---------|
| Choice | The agent always passes the top-level workflow ID. The engine internally walks to the deepest active layer. Step IDs that don't match the deepest layer return an error listing the deepest layer's valid step IDs. |
| Why | Asking the agent to track child IDs adds error-prone bookkeeping unnecessary given the structure. Deepest-active routing is unambiguous (one active child per parent at any time, by spawn-loop invariant). Errors that name the active layer's workflow + valid step IDs are self-correcting. |
| Sources | Spec R7, R7.1, R8: explicitly require single-ID driving and breadcrumb. DES-006: tool errors carry structured guidance text. |
| Options Researched | (A) Single-ID driving (chosen — required by spec). (B) Expose child IDs and require the agent to switch IDs on spawn/finalize. (C) Hybrid: agent can use either; backwards compat for tools. |
| Why This Over Alternatives | Over (B): More agent state to track, more failure modes (wrong ID on resume after compaction, stale child ID after auto-finalize). Over (C): Spec rules out hybrid for `update_workflow_state` and `end_workflow`; `get_workflow_state` retains a backwards-compat path so child IDs persisted before this delta still work as standalone views. |
| Consequences | Pro: Agent's mental model stays simple — one ID per logical workflow. Routing errors are educational. Con: A composition step's step ID can't be addressed directly while a child is active (intentional). |

### Shared scratchpad inheritance

| Field | Content |
|-------|---------|
| Choice | When a child is created, its `scratchpad_path` field is set to the parent's path. Cleanup deletes the file once when the top-level workflow ends. |
| Why | Parent and child are conceptually one continuous run. Notes the agent takes during the child's execution belong in the same scratchpad. Two parents running independent compositions of the same child workflow remain isolated because each has its own parent scratchpad. |
| Sources | Spec R9: shared scratchpad explicitly required. `workflows/tools.py::handle_start_workflow` line 393-396: parent scratchpad creation is unchanged. |
| Options Researched | (A) Shared (chosen). (B) Per-workflow scratchpads with explicit "include parent's notes" guidance. (C) Single global workflow-scratchpad collection with naming by ID. |
| Why This Over Alternatives | Over (B): Two files for one logical run. Forces agent to remember which file holds which notes. Cleanup harder. Over (C): Discoverability and isolation issues — two simultaneous parents would write into a shared global file. |
| Consequences | Pro: One file, one lifecycle, one cleanup point. Two parents composing the same child remain isolated (each writes to own parent's scratchpad — confirmed by spec AC for R9). Con: Naïve reader might expect the scratchpad to be named after the child workflow during the child's execution; documented in the authoring guide. |

### Create-then-soft-delete in same transaction (empty children)

| Field | Content |
|-------|---------|
| Choice | When a child's only step is condition-skipped (or all child steps are condition-skipped on first activation), the child record IS created with its definition snapshot, then immediately queued for soft-delete in the same MutationBatch. Both writes commit atomically. |
| Why | Condition evaluation is dynamic (forks an SDK sub-agent) — we can't fully predict which steps will skip without running them. Creating uniformly and letting the cascade loop drive the rest keeps spawn path single-codepath. The brief existence of a soft-deleted child record is invisible to readers because it's the same transaction. |
| Sources | Spec R4.1: child snapshot at spawn time, not parent-start. Compatible with create-then-soft-delete since snapshot is captured before soft-delete. DLT-159 condition evaluator can return "skip" — outcome unknown without running. |
| Options Researched | (A) Create-then-soft-delete (chosen). (B) Detect "child has no would-run steps" before creating the record. |
| Why This Over Alternatives | Over (B): Static detection is impossible because conditions evaluate dynamically. A heuristic ("any step without a condition") would handle some cases but not all, and would split the spawn path into two codepaths. |
| Consequences | Pro: Single spawn path. Cascade loop handles all outcomes uniformly. R4.1 preserved — snapshot captured at spawn, even when child is short-lived. Con: A child record briefly exists in the transaction. Invisible to other readers because the transaction commits atomically — under aiosqlite the begin/commit pair is a single SQLite transaction, and other readers (single-process async loop) cannot interleave inside it. |

## System Behavior

### Scenario: Two parents composing the same child concurrently

**Given**: `weekly-review` is active and has just spawned a child instance of `process-inbox-note`. Independently, `daily-review` is started and reaches its own composition step that also references `process-inbox-note`.

**When**: `daily-review`'s composition step activates and tries to spawn its own child.

**Then**: The spawn succeeds. R10's exemption: `get_active(skill, "process-inbox-note")` filters on `parent_workflow_id IS NULL`, so the existing composed instance (whose parent_workflow_id is `weekly-review`'s ID) is invisible to the duplicate check. Two child records exist concurrently — one parented by `weekly-review`, one by `daily-review`. Each writes to its own parent's scratchpad.

**Rationale**: Composition is logically scoped — the same child workflow can run multiple times in parallel as long as each run is contained inside a different parent context. Top-level uniqueness is unchanged.

### Scenario: Child auto-finalizes on a condition-skipped last step

**Given**: A child workflow's last step has `condition: "scratchpad has unprocessed items"`, and the condition evaluates false.

**When**: The agent reaches that point in the cascade.

**Then**: `_evaluate_and_advance` condition-skips the last step (in memory). The cascade loop sees no more pending steps in the child, queues SoftDelete(child) and pops up. The parent's composition step auto-completes. The cascade continues into the parent's next pending step. The response carries a `### Condition-Skipped Steps` block listing the skipped step (breadcrumb-prefixed) plus the activated next step.

### Scenario: Cycle introduced by hot skill reload

**Given**: A skill is hot-reloaded with new workflow definitions that introduce a cycle (`A → B → A`).

**When**: `SkillRegistry.refresh()` runs.

**Then**: `_validate_deps` rejects A and B; both are removed from `_workflows` and warnings are logged. If a workflow with a now-invalid composition reference was already running (its definition_snapshot still references the deleted target), `get_workflow_state(parent_id)` and any subsequent `update_workflow_state` will surface a corruption error on the parent's resume — the snapshot's `composes` target is no longer in `_workflows`. The error directs the agent to abort.

### Scenario: Definition changes between parent-start and composition-step-activate

**Given**: A skill author modifies `process-inbox-note` to add a new step, between when `weekly-review` started and when `weekly-review` reaches its composition step.

**When**: The composition step activates.

**Then**: The child is spawned with the *current* (modified) `process-inbox-note` definition snapshot. This is per R4.1 — snapshot at spawn time, not parent-start. The parent's snapshot (from when it started) is not consulted for the child.

**Rationale**: Snapshotting at spawn captures the latest registered definition naturally. Snapshotting at parent-start would force the parent to embed every transitively-referenced child definition, blowing up record size and creating a stale-by-the-time-it-runs problem.

### Scenario: Cascade error mid-flight (condition evaluator failure)

**Given**: A cascade is in flight. The condition evaluator on the parent's next step (after auto-resume from a finalized child) raises an unexpected exception.

**When**: The cascade loop is building the MutationBatch.

**Then**: The exception propagates out of the cascade loop before any commit. `finalize_child_and_resume_parent` is never called. No state is written. The handler catches the exception, returns an error response to the agent. The child remains active, the parent's composition step remains `STARTED`, the parent's `current_step` is unchanged. The agent can retry.

### Scenario: Routing error with a typo'd step ID

**Given**: A child of `weekly-review` is active at step `02-categorize`. The agent calls `update_workflow_state(parent_id, "02-categorise", "complete")` (typo).

**When**: The handler runs.

**Then**: Routing reads the chain, finds the deepest layer (the child), checks the step ID against the child's snapshot. No match. Returns: "Invalid step `02-categorise`. The deepest active layer is `process-inbox-note`. Valid steps: `01-check`, `02-categorize`, `03-tag`."

**Rationale**: Self-correcting error message names the active workflow and lists the valid step IDs. The agent doesn't need to know which workflow is active — the error tells it.

### Scenario: Routing rejects a step ID from a non-deepest layer

**Given**: `weekly-review` is at step `02-handle-inbox` (a composition step) with the child `process-inbox-note` active at step `02-categorize`. The agent attempts to operate on the parent's composition step directly: `update_workflow_state(parent_id, "02-handle-inbox", "complete")`.

**When**: The handler runs.

**Then**: Routing identifies the deepest active layer as the child. The step ID `02-handle-inbox` does not match any step in the child's snapshot. The same routing error fires: "Invalid step `02-handle-inbox`. The deepest active layer is `process-inbox-note`. Valid steps: `01-check`, `02-categorize`, `03-tag`."

**Rationale**: There is no fall-through to other layers' snapshots. A parent step ID, a step ID from an unborn child, or a stale reference to a soft-deleted child all return the same self-correcting error. This avoids the agent accidentally completing the parent's composition step while the child is still mid-flight.

### Scenario: Deep nesting (3 levels)

**Given**: A non-cyclic graph A → B → C composes to depth 3 at runtime. The agent has progressed to a step in C.

**When**: The agent advances through every level.

**Then**: `get_active_chain(parent_id)` returns `[A, B, C]`. Routing always targets C until C finalizes. When C's last step completes, the cascade loop pops to B, auto-completes B's composition step, advances B; if B's next step is also a composition (spawning a sibling D), the cascade descends into D in the same tool call. Breadcrumb reflects the active path. R5's load-time cycle detection bounds depth statically — runtime never encounters infinite recursion.

### Scenario: Stale subtree cleanup

**Given**: A parent's `updated_at` is 30 hours old (past the 24h threshold). Its active child's `updated_at` is 10 minutes old.

**When**: `StaleWorkflowCleanupProcessor.process` runs.

**Then**: `repository.list_stale(threshold)` walks each top-level root, computes subtree MAX(updated_at) — for this parent, that's 10 minutes ago (the child's value). Subtree is NOT stale. The parent is not abort-cascaded. The active child keeps the parent alive.

**Rationale**: R16 — staleness is a connected-component property, not a per-record property. An active child indicates work is ongoing.

## Notes

- Idempotency on `update_workflow_state` is unchanged by composition: re-calling `start` on an already-started step returns the existing-step response per the existing validate_transition rule.
- The `required_skills` injection at activation continues to work for composition steps. A composition step may declare `required_skills` (e.g., to load skills the child workflow assumes are present); these are emitted alongside the child's first step's `required_skills`, deduped via the existing cross-anchor `seen` set across both layers' skill lists.
- Composition does not change the definition snapshot for the parent — only the child's snapshot is captured at spawn. The parent's snapshot was captured at parent-start and includes the composition step's frontmatter (with `composes` resolved to its raw string form).
- The `end_workflow(child_id, ...)` reject path is a safety net — under normal use the agent never has a child ID. The error message points to the top-level ID accessible via `list_active_workflows` or by following the parent_workflow_id chain in `get_workflow_state` output.
