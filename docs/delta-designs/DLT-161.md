# Design: DLT-161 — Workflow composition via inline sub-workflow references

**Delta Spec**: [../delta-specs/DLT-161.md](../delta-specs/DLT-161.md)
**Status**: Draft

## Purpose

This document explains the design rationale for DLT-161: how composition references are parsed and validated, how nested workflow state is persisted and routed, and how the engine maintains the illusion of a single continuous workflow for the agent across nested layers.

After implementation, the "Detected Impacts" section will guide reconciliation into feature design docs.

## Shape

| Part | Mechanism | Flag |
|------|-----------|:----:|
| **S1** | Add `composes` field to `StepDefinition` + loader; frontmatter parsing accepts `<workflow>` or `<skill>/<workflow>` form. Body of composition step's `instructions.md` is ignored at runtime; only frontmatter is honoured. | |
| **S2** | Composition reference resolution — given a `composes` string and the parent's skill, resolve to a `(skill_name, workflow_name)` tuple via the skill registry. | |
| **S3** | Load-time cycle detection — graph-walk all registered workflows' composition refs; any workflow participating in a transitive cycle is rejected (not registered) with a warning. | |
| **S4** | Load-time static reference validation — composition target must exist and have ≥1 step; if the target is itself rejected at load time, the parent is also rejected (cascading). | |
| **S5** | Extend `WorkflowState` (and ORM record) with `parent_workflow_id: str \| None` and `parent_step_id: str \| None`; database migration adds the columns and any indexes needed for active-child lookups. | ⚠️ |
| **S6** | Repository scoping — duplicate-prevention (`get_active`) restricted to top-level records (`parent_workflow_id IS NULL`); add helper to find the active child of a parent. | |
| **S7** | Composition spawn in `update_workflow_state` — when an activated step has a `composes` reference, the tool creates the child workflow record (with parent linkage + shared scratchpad) and recursively activates the child's first step in the same call. | ⚠️ |
| **S7.1** | Child-spawn-time definition snapshot — at child-record creation, capture the current registered child workflow definition into the child's `definition_snapshot`. Mirrors top-level snapshot timing but at spawn rather than start. | |
| **S8** | Single-ID routing — `update_workflow_state(parent_id, step, action)` walks from the given record through the active-child chain to find the deepest active layer and applies the action there. Step IDs that don't match the deepest layer's expected step return an error. | ⚠️ |
| **S9** | Auto-resume cascade — when the deepest active layer auto-finalizes, the engine walks back up: parent's composition step is auto-completed, parent's next pending step auto-starts (which may itself be a composition step). Cascade is atomic — partial failure rolls back. | ⚠️ |
| **S10** | Composition-step gating — `condition` and `required: false` on the composition step are honoured **before** spawning the child. If skipped, no child record is created. | ⚠️ |
| **S11** | Shared scratchpad inheritance — child's `scratchpad_path` is set to the parent's at child-create time; cleanup deletes the file once on top-level finalization. | |
| **S12** | Breadcrumb generation — helper renders the active stack (`parent_workflow/step > child_workflow/step`, separator `>`) and prepends it to activation responses and `get_workflow_state` output. | |
| **S13** | `get_workflow_state` nested view — walks the parent → active-child chain and inlines child state. Completed composition steps surface no nested data (their child records are soft-deleted). | |
| **S14** | `list_active_workflows` filter — query restricted to `parent_workflow_id IS NULL` so only top-level workflows surface. | |
| **S15** | Abort cascade — `end_workflow(top_level_id, "abort")` soft-deletes the parent and all transitive descendants atomically and removes the shared scratchpad. | |
| **S16** | Stale cleanup updated — uses the freshest `updated_at` across the stack so an active child keeps the parent alive (and vice versa). | |

### Flagged Unknowns

#### S5 — Migration & indexes

Migration adds `parent_workflow_id` and `parent_step_id` columns to `workflow_states`. The "find active child of parent" lookup needs an index on `parent_workflow_id` (filtered on `deleted_at IS NULL`). Need to confirm whether SQLite's partial-index support is sufficient, or whether a covering index is needed for the hot path. Decision in design.

#### S7 — Composition spawn recursion

When activating a composition step, the child's first step is recursively activated; the child's first step itself may be condition-skipped (DLT-159) or itself be another composition step. Open: how the recursion terminates (the helper returns the deepest first non-condition-skipped, non-composition step that is `started`?), how condition-skips along the way are reported in the same tool response, and how errors mid-recursion roll back partial state (interacts with S9 atomicity).

#### S8 — Routing implementation

Two candidate mechanisms: (a) walk parent → child via `parent_workflow_id` back-edges queried at each call (no extra state, but multiple DB queries per tool call), or (b) cache an `active_child_id` field on the parent record (faster, but invariant must be maintained on every spawn / finalize / abort). Both work; the choice affects DB query count and invariant enforcement.

#### S9 — Cascade atomicity boundary

Auto-resume and abort cascades must be all-or-nothing per tool call. Need to settle the transaction boundary: a single SQLAlchemy session covering all writes in the cascade, vs explicit savepoints, vs compensating writes. Same boundary applies to both R13 (auto-resume) and R15 (abort).

#### S10 — Composition-step condition context

The composition step's `condition` evaluator currently sees the workflow's `step_states` (the parent's). Need to confirm that, when the step being evaluated is a composition step, no leakage of unborn-child context occurs in the prompt — and decide whether this needs to be made explicit in the prompt template / evaluator API, or remains an implicit consequence of "evaluate before spawn."
