# Design: DLT-086 - Manual session switching via Telegram reply

**Delta Spec**: [../delta-specs/DLT-086.md](../delta-specs/DLT-086.md)
**Status**: Draft

## Purpose

This document explains the design rationale for this delta: the modeling choices, data flow, system behavior, and architectural approach.

After implementation, the "Detected Impacts" section will guide reconciliation into feature design docs.

## Problem Context

Users have no way to explicitly choose which previous conversation to resume — they can only rely on automatic boundary detection, which may or may not route to the desired session. Telegram's native reply-to gesture provides a natural, precise mechanism: reply to any message from a past conversation, and the new message continues where that conversation left off.

The design sits at two layers: the Telegram channel (reply detection + session lookup) and the coordinator (session validation). The existing `target_session_id` routing field on envelopes (DES-014) and the coordinator's `_route_to_target_session` mechanism are reused — no new routing infrastructure needed.

## Design Overview

Telegram message handlers detect `reply_to_message` on incoming messages, look up the associated session via the existing `find_session_by_external_id` registry method, and set `target_session_id` on the message envelope. The coordinator's `_route_to_target_session` is enhanced to validate the target session before closing the current one — on validation failure, it returns `False` and the caller yields a `Status` AgentEvent (which channels render as a visible message) preserving the current session. Handlers do not perform pre-validation; the coordinator owns that responsibility. All existing patterns (reaction handler's busy-channel deferral, `enqueue_deferred()`) are mirrored exactly.

## Shape

| Part | Mechanism | Flag |
|------|-----------|:----:|
| **S1** | Reply-to extraction helper — `_extract_reply_target(message) -> str \| None` on the Telegram channel class; returns `str(message.reply_to_message.message_id)` when present, `None` otherwise | |
| **S2** | Session lookup in handlers — `_handle_message` and `_handle_media` call `_extract_reply_target` → `find_session_by_external_id("telegram", reply_to_id)` → compare to active session ID → conditionally set `target_session_id` on envelope. Lookup logic mirrors reaction handler (compare session IDs, set routing field). Handlers do NOT validate reopenability — that is S4's coordinator-level concern | |
| **S3** | Busy-channel deferral with target routing — When delivery lock is held and reply targets a different session, defer via `enqueue_deferred()` with `target_session_id` set on envelope (mirrors reaction handler pattern exactly) | |
| **S4** | Coordinator-level resume validation — `_route_to_target_session` calls new `can_reopen_session(target_id)` registry method before closing current session. `can_reopen_session` checks the same preconditions as `reopen_session` without side effects: session exists, `transcript_path` is not None, transcript file exists on local filesystem, session is within `max_session_age`, session is closed. On failure, returns `False` and caller yields `Status` AgentEvent with error message; current session is preserved, message falls through to normal processing | |
| **S5** | Reply-to overrides commands — When both reply-to and `/new` or `/queue` are present, reply-to routing wins (`target_session_id` is set, `force_new` and queue flags are ignored) | |

## Components

### Implementation Structure

| Layer/Component | Responsibility | Key Decisions |
|-----------------|----------------|---------------|
| Telegram channel (`_extract_reply_target`) | Extract `reply_to_message.message_id` from incoming messages | Extracted helper shared by text and media handlers |
| Telegram handlers (`_handle_message`, `_handle_media`) | Detect reply-to, look up session, set routing field on envelope | No pre-validation — coordinator handles that; mirrors reaction handler |
| Session registry | `can_reopen_session(target_id) -> bool` (new) | Validation-only: checks same preconditions as `reopen_session` without side effects |
| Coordinator (`_route_to_target_session`) | Validate target before closing current session; yield error on failure | Returns `bool` instead of `None`; on `False`, caller yields `Status` event |

### Cross-Layer Contracts

**Handler → Registry**: `find_session_by_external_id(channel, external_id) -> str | None` (existing, no changes)

**Handler → Coordinator**: `target_session_id` on `TextMessage` envelope (existing field via DES-014); `enqueue_deferred()` for busy-channel deferral (existing method)

**Coordinator → Registry**: `can_reopen_session(target_id) -> bool` (new), `reopen_session(session_id)` (existing)

**Coordinator → Channel**: `Status` AgentEvent with error message when resume validation fails (existing event type, new usage)

### Shared Logic

- Session external ID mapping already exists and is maintained for all incoming/outgoing messages
- `target_session_id` routing is fully implemented in the coordinator (DES-014)
- The reaction handler provides the exact pattern to mirror for session lookup and busy-channel deferral
- `can_reopen_session` reuses the same validation logic as `reopen_session` (exists, transcript_path not None, file exists locally, within max_session_age, is closed)

## Modeling

No new entities or relationships. The design reuses:

- **MessageEnvelope.target_session_id** (existing routing field, dual-declared per [DES-014](../design/DES-014-generic-routing-fields-on-typed-envelopes.md)) — set by Telegram handlers when reply-to maps to a different session. The property hook on `MessageEnvelope` and dataclass field on each subtype (`TextMessage`, `ButtonTapMessage`, `ReactionMessage`) already exist; no envelope changes needed.
- **channel_messages table** (existing) — queried via `find_session_by_external_id` to map replied-to message ID to session ID
- **Session registry** — gains `can_reopen_session` as a read-only validation method (no schema changes)

## Data Flow

### Reply-to routing (idle agent)

```
1. User sends Telegram message with reply_to_message set
2. Handler calls _extract_reply_target(message) → reply_to_id: str | None
3. If reply_to_id is not None:
   a. find_session_by_external_id("telegram", reply_to_id) → target_id: str | None
   b. If target_id is not None and target_id != active_session_id:
      → Construct TextMessage with target_session_id=target_id
   c. If target_id is None or target_id == active_session_id:
      → Construct TextMessage without target_session_id (normal routing)
4. Coordinator.send_message() receives envelope
5. Sees target_session_id is set → calls _route_to_target_session(target_id)
6. _route_to_target_session:
   a. can_reopen_session(target_id) → True:
      - Close current session (fire post-processing)
      - Reopen target session
      - Return True
   b. can_reopen_session(target_id) → False:
      - Return False (no state changes)
7. send_message():
   a. If False: yield Status("Could not resume that conversation — its context is no longer available")
      → Message proceeds through normal boundary detection and processing in current session
      → No session switch occurs; current session remains active
   b. If True: message processed in resumed session
```

### Reply-to routing (busy agent)

```
1. User sends Telegram message with reply_to_message set
2. Handler extracts reply_to_id, looks up target session
3. Delivery lock is held (agent is busy)
4. If target maps to a different session:
   → Construct TextMessage with target_session_id=target_id
   → Call enqueue_deferred(envelope)
5. When deferred queue drains:
   → Coordinator processes deferred message
   → _route_to_target_session validates and switches session
6. If target maps to same/unknown session:
   → Call enqueue(envelope) (normal steering, no session switch)
```

### Reply-to with command (precedence)

```
1. User sends reply that is also a /new or /queue command
2. _detect_command returns (name, args)
3. _extract_reply_target returns reply_to_id
4. Reply-to takes precedence: target_session_id is set, command flags ignored
5. Coordinator routes to target session (no new session created)
```

## Key Decisions

### Coordinator-level resume validation

**Choice**: The coordinator's `_route_to_target_session` validates the target session before closing the current session. On validation failure, it returns `False` and the caller yields a `Status` AgentEvent. Handlers never perform pre-validation — they just set `target_session_id`.

**Why**: Centralizes validation in the coordinator, making it available to all `target_session_id` producers (reply-to, reactions, future routing mechanisms). Handlers stay thin. Channels render the error event in their own way. The current session is never unnecessarily closed.

**Alternatives Considered**:
- **Handler-level pre-validation (seed design S4)**: The handler calls `can_reopen_session` before setting `target_session_id`. Fragile — every handler that sets `target_session_id` must remember to validate. Inconsistent if one handler validates and another doesn't.
- **Post-hoc fallback (current behavior)**: Coordinator closes current session, tries to reopen target, falls back to fresh session on failure. Wastes the current session and confuses the user with an unexpected new session.
- **Coordinator-level with channel-specific error messaging**: Coordinator calls back to the channel to send the error message. Adds a channel-messaging dependency the coordinator doesn't currently have.

**Consequences**:
- Pro: Consistent validation for all `target_session_id` producers (reactions also benefit)
- Pro: No unnecessary session churn — current session stays intact on validation failure
- Pro: Clear error messaging via existing `Status` AgentEvent mechanism
- Con: Changes `_route_to_target_session` signature from `→ None` to `→ bool` (internal API change)
- Con: Reaction handler behavior changes — stale session targets now yield an error instead of silently falling back to fresh session (improvement, but a behavior change)

### Extracted reply-to helper

**Choice**: Private method `_extract_reply_target(message) -> str | None` on the Telegram channel class, called by both `_handle_message` and `_handle_media`.

**Why**: The extraction logic is identical for text and media handlers. A single method avoids duplication and provides a single place to test the Telegram API interaction.

**Alternatives Considered**:
- **Inline in each handler**: Duplicates the `if message.reply_to_message: ...` pattern. Simple but violates DRY for no benefit.
- **Shared filter/middleware**: aiogram supports `F.reply_to_message` as a filter, but routing filtered messages to a separate handler would split the processing flow and complicate existing handler logic.

**Consequences**:
- Pro: Single point of test for reply extraction
- Pro: Easy to extend (e.g., future `reply_to_message_id` field on envelopes)
- Con: Slight indirection for a small amount of logic

### Status event for resume failure

**Choice**: Yield a `Status` AgentEvent with the error message when resume validation fails.

**Why**: `Status` is the coordinator's existing mechanism for communicating processing states to channels (used during pre-processing: "Analyzing message..."). It's a processing status, not a fatal error. Channels already render `Status` events.

**Alternatives Considered**:
- **Error event with `recoverable=True`**: Already used for SDK errors (rate limits, transient failures). Overloading it for session-resume failures conflates two different error domains.
- **TextChunk event**: Would appear as agent response text. Misleading — the agent didn't say it.
- **New AgentEvent type**: Adds a type for a single use case. Not justified given `Status` already fits.

**Consequences**:
- Pro: Reuses existing event type, no new types needed
- Pro: Channels already handle Status events
- Con: Status rendering may differ between channels (REPL vs Telegram) — channels should ensure this status message is rendered as a visible, persistent message

### Reply-to overrides commands

**Choice**: When both a reply-to gesture and a bot command (`/new`, `/queue`) are present, reply-to routing wins.

**Why**: The reply-to gesture is a more deliberate and specific intent signal — the user physically selected a specific message to reply to. A text prefix is a weaker signal.

**Alternatives Considered**:
- **Command precedence**: Would ignore the user's explicit gesture in favor of a text prefix. Feels less intentional.

**Consequences**:
- Pro: Respects the user's deliberate gesture
- Con: `/new reply to old message` won't force a new session (extremely unlikely edge case)

## System Behavior

### Scenario: Reply to past message, different session, agent idle

**Given**: The user replies to a message from a previous session, and the agent is idle
**When**: The handler processes the message
**Then**: `target_session_id` is set on the envelope. The coordinator validates the target session, closes the current session (triggering async post-processing), reopens the target session, and processes the message in the resumed session context.
**Rationale**: Primary use case — explicit, precise session resumption.

### Scenario: Reply to past message, different session, agent busy

**Given**: The user replies to a message from a previous session, and the delivery lock is held
**When**: The handler processes the message
**Then**: The message is deferred via `enqueue_deferred()` with `target_session_id` set. When the current turn completes and the deferred queue drains, the coordinator performs the session switch.
**Rationale**: Mirrors the reaction handler pattern exactly. Session switches happen between turns, never mid-response (DES-009).

### Scenario: Reply to message from current session

**Given**: The user replies to a message from the active session
**When**: The handler processes the message
**Then**: The lookup returns the active session's ID. No `target_session_id` is set. Message routes normally (no session switch).
**Rationale**: Replying to the current conversation is a normal message — no routing needed.

### Scenario: Reply to unknown message (not in channel_messages)

**Given**: The user replies to a message whose external ID is not recorded (pre-feature messages, messages from other platforms)
**When**: The handler processes the message
**Then**: `find_session_by_external_id` returns `None`. No `target_session_id` is set. Message routes through normal boundary detection.
**Rationale**: Graceful degradation — feature silently degrades to current behavior for unmapped messages.

### Scenario: Reply targets a stale session (transcript deleted, too old)

**Given**: The user replies to a message from a session that fails validation (transcript file missing or session exceeds max age)
**When**: The coordinator's `_route_to_target_session` calls `can_reopen_session`
**Then**: `can_reopen_session` returns `False`. `_route_to_target_session` returns `False` without closing the current session. The coordinator yields a `Status` event: "Could not resume that conversation — its context is no longer available." The message falls through to normal processing in the current session.
**Rationale**: The user gets a clear explanation instead of an unexpected new session. The current session stays intact.

### Scenario: Reply combined with /new command

**Given**: The user sends a reply that also contains the `/new` command
**When**: The handler processes the message
**Then**: Both `_detect_command` and `_extract_reply_target` return values. Reply-to takes precedence: `target_session_id` is set, `force_new` is not set. The message routes to the target session.
**Rationale**: Reply-to is a more deliberate intent signal than a text prefix.

### Scenario: Media message with reply-to

**Given**: The user sends a photo/voice/document that is a reply to a past message
**When**: The media handler processes the message
**Then**: `_extract_reply_target` extracts the replied-to message ID. The same session lookup and routing logic applies as for text messages.
**Rationale**: Reply-to works for all message types — the Telegram API sets `reply_to_message` regardless of message type.

### Scenario: Reaction targeting a stale session (side effect)

**Given**: The user adds a reaction to a message from a stale session (existing reaction handler)
**When**: The coordinator's `_route_to_target_session` validates the target
**Then**: `can_reopen_session` returns `False`. The coordinator yields a `Status` event with the error message. The reaction is not processed in a new session.
**Rationale**: Coordinator-level validation applies uniformly to all `target_session_id` producers. The reaction handler benefits from the same pre-validation. **Current behavior**: reactions to stale sessions cause the coordinator to silently fall back to creating a fresh session. **New behavior**: the user gets an error message and the current session stays intact. This is an improvement, but a behavior change that should be noted in testing.
