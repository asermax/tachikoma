# Design: DLT-086 - Manual session switching via Telegram reply

**Delta Spec**: [../delta-specs/DLT-086.md](../delta-specs/DLT-086.md)
**Status**: Draft

## Purpose

This document explains the design rationale for this delta: the modeling choices, data flow, system behavior, and architectural approach.

After implementation, the "Detected Impacts" section will guide reconciliation into feature design docs.

## Problem Context

Users have no way to explicitly choose which previous conversation to resume — they can only rely on automatic boundary detection, which may or may not route to the desired session. Telegram's native reply-to gesture provides a natural, precise mechanism for selecting a specific conversation context: reply to any message from that conversation, and the new message continues where that conversation left off.

## Design Overview

The design extends the existing Telegram message handlers to detect `reply_to_message` on incoming messages, look up the associated session via the already-existing `find_session_by_external_id` registry method, and set `target_session_id` on the message envelope. This reuses the coordinator's existing `_route_to_target_session` mechanism (already used by reaction-based session routing). A new `can_reopen_session` registry method provides pre-validation to avoid unnecessary session churn when the target session can't be resumed.

## Shape

| Part | Mechanism | Flag |
|------|-----------|:----:|
| **S1** | Reply-to extraction helper — Extract `reply_to_message.message_id` from incoming Telegram messages (text and media), return as optional string | |
| **S2** | Session lookup and routing decision — Call `find_session_by_external_id("telegram", reply_to_id)` in `_handle_message` and `_handle_media`; compare result to active session ID; skip when command detected (reply-to overrides /new and /queue) | |
| **S3** | Busy-channel deferral with target routing — When delivery lock is held and reply targets a different session, defer via `enqueue_deferred()` with `target_session_id` set (mirrors reaction handler pattern) | |
| **S4** | Pre-validation before session switch — Add `can_reopen_session(target_id)` to the registry (checks transcript exists on local filesystem, within max age). Telegram handler calls it before setting `target_session_id`. If validation fails, send error message to user and fall through to normal routing | |
| **S5** | Reply-to overrides commands — When both reply-to and `/new` or `/queue` are present, reply-to routing wins (target_session_id is set, force_new and queue flags are ignored) | |

## Components

### Implementation Structure

| Layer/Component | Responsibility | Key Decisions |
|-----------------|----------------|---------------|
| Telegram handlers (`_handle_message`, `_handle_media`) | Detect reply-to, look up session, decide routing | Extends existing handlers, mirrors reaction handler pattern |
| Session registry | `can_reopen_session` pre-validation | Reuses existing validation logic from `get_recent_closed` filters |
| Coordinator | `target_session_id` routing (existing) | No changes needed — existing `_route_to_target_session` handles the session switch |

### Cross-Layer Contracts

**Handler → Registry**: `find_session_by_external_id(channel, external_id) -> str | None` (existing), `can_reopen_session(target_id) -> bool` (new)

**Handler → Coordinator**: `target_session_id` on `TextMessage` envelope (existing field), `enqueue_deferred()` for busy-channel deferral (existing method)

### Shared Logic

- Session external ID mapping already exists and is maintained for all incoming/outgoing messages
- `target_session_id` routing is already fully implemented in the coordinator
- The reaction handler provides the exact pattern to mirror for busy-channel deferral

## Key Decisions

### Pre-validation over post-hoc fallback

**Choice**: Validate the target session can be reopened *before* closing the current session or setting `target_session_id`
**Why**: Avoids unnecessary session churn — if the target can't be resumed, the current session stays intact and the user gets a clear error message
**Alternatives Considered**:
- Post-hoc fallback (coordinator creates fresh session on reopen failure): Wastes the current session and confuses the user with an unexpected new session

**Consequences**:
- Pro: No unnecessary state changes, clear error messaging
- Con: Adds a new method to the registry (`can_reopen_session`)

### Reply-to overrides /new and /queue

**Choice**: When both a reply-to gesture and a bot command are present, reply-to routing wins
**Why**: The reply-to gesture is a more deliberate and specific intent signal than a command prefix — the user physically selected a specific message to reply to
**Alternatives Considered**:
- Command precedence: Would ignore the user's explicit gesture in favor of a text prefix, which feels less intentional

**Consequences**:
- Pro: Respects the user's deliberate gesture
- Con: `/new reply to old message` won't force a new session if someone does this intentionally (extremely unlikely edge case)

## Open Questions

- [ ] Should `can_reopen_session` be exposed only to the Telegram handler, or should it be available wherever `target_session_id` is set (e.g., the reaction handler could also benefit from pre-validation)?
