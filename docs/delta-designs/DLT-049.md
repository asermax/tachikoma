# Design: DLT-049 - Plugin Hook for Custom Context Providers

**Delta Spec**: [../delta-specs/DLT-049.md](../delta-specs/DLT-049.md)
**Status**: Draft

## Purpose

This document explains the design rationale for DLT-049: how the plugin system discovers, validates, instantiates, and registers context providers declared in plugin manifests, and how they participate in the pre-processing pipelines with full lifecycle management.

After implementation, the "Detected Impacts" section will guide reconciliation into feature design docs.

## Problem Context

Tachikoma's plugin system currently supports three contribution types: skills, hooks, and events. Context providers — the components that inject relevant information into every agent conversation — are hardcoded built-ins (projects, skills, memory). Plugin authors have no way to contribute custom context sources (calendar data, CRM information, external knowledge bases) without modifying core code.

The plugin system already has the full contribution lifecycle pattern: manifest declaration → discovery-time validation → runtime registration → lifecycle management (remove/update). This delta extends that pattern to context providers, routing them into the existing `PreProcessingPipeline` and `MessagePreProcessingPipeline` based on ABC inspection.

**Constraints:**
- **Reuse existing ABCs.** Plugin providers implement the same `ContextProvider` and `MessageContextProvider` interfaces as built-in providers. No new provider base class.
- **Pipeline-agnostic registration.** The discovery layer inspects which ABC(s) a class implements and routes to the correct pipeline(s). Plugin authors don't specify the pipeline explicitly.
- **Config injection.** Providers receive the plugin's validated config dict at construction, consistent with how hooks receive `PluginContext`.
- **Error isolation (DES-002).** One plugin's broken provider must not affect other providers or core providers.
- **Event-driven decoupling.** Provider registration/unregistration uses the existing plugin lifecycle events (`PluginInstalled`, `PluginRemoving`, `PluginRemoved`), keeping `PluginManager` decoupled from pipeline internals — the same pattern used for skills registration.

**Interactions:**
- **`PluginManifest`** — gains `context_providers: dict[str, str]` field (manifest entry name → module name).
- **`LoadedPlugin`** — gains typed provider instance lists for lifecycle tracking.
- **`PreProcessingPipeline` / `MessagePreProcessingPipeline`** — gain `unregister()` method for provider removal.
- **Event listeners** — new `register_plugin_provider_listeners()` subscribes to lifecycle events, handles pipeline register/unregister.
- **`__main__.py`** — wires provider listeners after pipeline creation, before coordinator construction.

## Design Overview

The design follows the established plugin contribution pattern exactly. The manifest gains a `[context_providers]` section declaring provider entry points. During discovery, each entry point is imported and its classes inspected for `ContextProvider` and/or `MessageContextProvider` conformance. Validated provider instances are instantiated with `config=<validated_config>` and stored on `LoadedPlugin`. Lifecycle events trigger pipeline registration (on `PluginInstalled`) and unregistration (on `PluginRemoving`).

```
┌──────────────────────────────────────────────────────────────┐
│ Manifest: tachikoma-plugin.toml                              │
│  [context_providers]                                         │
│  calendar = "calendar"    → context_providers/calendar.py   │
│  crm = "crm"              → context_providers/crm.py         │
├──────────────────────────────────────────────────────────────┤
│ Discovery (loader.py)                                        │
│  1. Validate bare module names (reuse _validate_bare_module) │
│  2. For each (name, module):                                 │
│     a. Resolve context_providers/<module>.py                 │
│     b. Import via importlib.util                             │
│     c. Find concrete classes implementing ABC(s)             │
│     d. Instantiate with config=validated_config              │
│     e. Track instances on LoadedPlugin                       │
├──────────────────────────────────────────────────────────────┤
│ Event Listeners (plugins/provider_listeners.py)              │
│  on PluginInstalled → register instances into pipelines      │
│  on PluginRemoving  → unregister instances from pipelines    │
├──────────────────────────────────────────────────────────────┤
│ Pipelines (pre_processing.py, per_message_pre_processing.py) │
│  + unregister(provider) method                               │
│  Provider failures isolated per DES-002                      │
└──────────────────────────────────────────────────────────────┘
```

## Components

### Implementation Structure

| Layer/Component | Responsibility | Key Decisions |
|-----------------|----------------|---------------|
| `src/tachikoma/plugins/manifest.py` | Parse `[context_providers]` from TOML; validate bare module names | Reuses `_validate_bare_module_names` validator; same dict pattern as `[hooks]` and `[events]` |
| `src/tachikoma/plugins/loader.py` | Provider discovery, ABC inspection, instantiation | New `_validate_providers()` function; reuses `importlib.util` pattern from handler validation |
| `src/tachikoma/plugins/provider_listeners.py` | Event-driven pipeline registration/unregistration | New module; follows `skills/listeners.py` pattern; receives pipelines and PluginManager reference |
| `src/tachikoma/pre_processing.py` | Add `unregister(provider)` to `PreProcessingPipeline` | Minimal addition — `self._providers.remove(provider)` with safe no-op on miss |
| `src/tachikoma/per_message_pre_processing.py` | Add `unregister(provider)` to `MessagePreProcessingPipeline` | Same as above |
| `src/tachikoma/plugins/manager.py` | No changes — lifecycle events handle everything | Event-driven decoupling means manager is unchanged |

### Cross-Layer Contracts

**Discovery contract (loader.py):**

```
_validate_providers(manifest, plugin_dir, alias, validated_config)
    → (list[ContextProvider], list[MessageContextProvider])

For each (name, module_name) in manifest.context_providers:
    1. Resolve plugin_dir / "context_providers" / "{module_name}.py"
    2. Check file exists (else: raise ValueError with diagnostic)
    3. Import via importlib.util.spec_from_file_location
       Module key: "tachikoma_plugin.{alias}.context_providers.{module_name}"
    4. Scan module for concrete provider classes:
       - getattr(module, name) for each name in dir(module)
       - Skip non-class, abstract classes (inspect.isabstract)
       - Check issubclass(cls, ContextProvider) and/or issubclass(cls, MessageContextProvider)
       - Must implement at least one ABC (else: raise ValueError)
    5. For each discovered class:
       - Validate __init__ accepts "config" as keyword arg (inspect.signature)
       - Instantiate: cls(config=validated_config)
         - Catch TypeError from ABC (unimplemented abstract methods) and re-raise
           as ValueError with diagnostic naming the class and missing methods
       - Route to appropriate list based on ABC membership
    6. If no concrete provider classes found: raise ValueError with diagnostic
    Return (session_providers, message_providers)
```

**Event listener contract (provider_listeners.py):**

```
register_plugin_provider_listeners(bus, pre_pipeline, msg_pre_pipeline, plugin_manager)

on_plugin_installed(event):
    plugin = plugin_manager lookup by event.alias
    for provider in plugin.context_providers:
        pre_pipeline.register(provider)
    for provider in plugin.message_context_providers:
        msg_pre_pipeline.register(provider)

on_plugin_removing(event):
    plugin = plugin_manager lookup by event.alias
    for provider in plugin.context_providers:
        pre_pipeline.unregister(provider)
    for provider in plugin.message_context_providers:
        msg_pre_pipeline.unregister(provider)
```

**Integration Points:**
- `manifest.py` → `loader.py`: `manifest.context_providers` dict consumed by discovery
- `loader.py` → `LoadedPlugin`: provider instances stored on loaded plugin record
- `provider_listeners.py` → pipelines: `register()`/`unregister()` calls on lifecycle events
- `__main__.py` → `provider_listeners.py`: wires listeners after pipeline creation

**Error handling strategy:**
- Discovery errors (missing file, import error, no valid class, wrong signature) → plugin fails with diagnostic, same as hook/event validation
- Runtime provider errors → isolated by pipeline's `asyncio.gather(return_exceptions=True)`, same as built-in providers (DES-002)

### Shared Logic

- **`_validate_bare_module_names`** (manifest.py): Reused for `context_providers` validation — same validator as hooks and events.
- **`importlib.util.spec_from_file_location`** pattern: Reused from handler validation in loader.py — same dynamic import mechanism with unique module keys to avoid `sys.modules` collisions.
- **`inspect.signature`** for constructor validation: New usage of already-imported `inspect` module — checks `config` parameter acceptance.
- **Provider instance identity**: Identity-based `unregister()` (object reference comparison in list removal) ensures the exact provider instance is removed, not a different provider of the same class.

## Data Flow

### Provider discovery during plugin loading

```
loader._discover_one(outcome, install_dir, plugin_sources)
    ├── ... existing manifest parsing, config validation ...
    ├── validated_config = result.values or {}
    ├── NEW: if manifest has context_providers:
    │   ├── session_providers, msg_providers = _validate_providers(
    │   │       manifest, plugin_dir, alias, validated_config)
    │   └── On failure: return LoadedPlugin(status="failed", diagnostic=...)
    └── return LoadedPlugin(..., context_providers=session_providers,
                               message_context_providers=msg_providers)
```

### Provider registration on plugin install

```
PluginInstalled event dispatched
    └── provider_listeners.on_plugin_installed(event)
            ├── for provider in event.plugin.context_providers:
            │   └── pre_pipeline.register(provider)
            └── for provider in event.plugin.message_context_providers:
                └── msg_pre_pipeline.register(provider)
```

### Provider unregistration on plugin remove

```
PluginRemoving event dispatched
    └── provider_listeners.on_plugin_removing(event)
            ├── plugin = plugin_manager lookup by event.alias
            ├── for provider in plugin.context_providers:
            │   └── pre_pipeline.unregister(provider)
            └── for provider in plugin.message_context_providers:
                └── msg_pre_pipeline.unregister(provider)
```

### Provider re-registration on plugin update

```
_reregister_plugin(old_plugin, new_plugin)
    ├── Dispatch PluginRemoving → provider listener unregisters old providers
    ├── Unsubscribe old event wrappers
    ├── Dispatch PluginRemoved
    ├── Store new_plugin in _loaded
    ├── init_plugin(new_plugin, bus)
    └── Dispatch PluginInstalled → provider listener registers new providers
        (existing flow handles this — no changes to _reregister_plugin)
```

### Provider execution at runtime

```
PreProcessingPipeline.run(message)
    ├── asyncio.gather(*[_run_one(p) for p in self._providers], return_exceptions=True)
    ├── Built-in providers (projects) + plugin providers execute concurrently
    ├── Plugin provider raises → caught by return_exceptions, logged per DES-002
    └── Successful results (from all sources) collected uniformly
```

## Key Decisions

### Event-driven registration follows skills listener pattern

**Choice**: Provider pipeline registration/unregistration is handled by event listeners (`PluginInstalled`, `PluginRemoving`), not by `PluginManager` directly.
**Why**: This is the same decoupling pattern used by the skills system — `PluginManager` has no pipeline dependencies, and all registration logic is owned by a listener module. The manager just dispatches lifecycle events; the listener translates them into pipeline mutations.
**Alternatives Considered**:
- Manager receives pipeline references and registers directly: couples manager to pipeline internals, violates the decoupled design established for skills
- Provider registration inside `lifecycle.py`: conflates provider registration with hook/event lifecycle, which have different concerns

**Consequences**:
- Pro: `PluginManager` unchanged — zero new dependencies
- Pro: Registration logic is testable in isolation
- Pro: Consistent with established pattern
- Con: One more listener module to maintain

### Provider instantiation during discovery, not during registration

**Choice**: Provider instances are created during `_validate_providers()` in the loader, not during the `PluginInstalled` event handler.
**Why**: The loader already has the validated config dict and the plugin directory. Instantiation during discovery allows validation to catch constructor signature errors early (spec R6: handler validation at discovery time). The event handler receives pre-created instances and simply registers them.
**Alternatives Considered**:
- Lazy instantiation during `PluginInstalled`: defers signature validation to runtime, making diagnostics harder to trace; requires passing config and class references through the event
- Instantiation in the listener: requires listener to have plugin dir + config knowledge, adding unnecessary dependencies

**Consequences**:
- Pro: Early validation with clear diagnostics
- Pro: Listener is a thin routing layer
- Pro: LoadedPlugin carries fully-constructed instances

### Identity-based pipeline unregistration

**Choice**: Pipelines use `list.remove(provider)` (identity-based) in `unregister()`, not name-based or class-based lookup.
**Why**: Provider instances are unique objects. A plugin may register multiple instances of the same class with different configs. Identity-based removal ensures the exact instance is removed. The `list.remove()` call is O(n) but provider lists are small (typically 1-5 entries per pipeline).
**Alternatives Considered**:
- Name-based removal: requires providers to have a unique name, adding complexity to the ABC
- Dict-based registration (keyed by instance): more complex for a rarely-called operation

**Consequences**:
- Pro: Simple and correct — uses Python's built-in identity comparison
- Pro: No new provider naming requirements
- Con: O(n) removal, but n is small and removal is infrequent

### `context_providers/` directory convention

**Choice**: Provider modules live in `context_providers/<module_name>.py` relative to the plugin install directory.
**Why**: Consistent with the `hooks/` and `events/` directory conventions. Dedicated directory keeps plugin organization clean and makes the distinction visible at the filesystem level.
**Alternatives Considered**:
- Flat layout alongside other plugin files: risks collision, less organized
- Single `handlers/` directory for hooks/events/providers: conflates different contribution types

**Consequences**:
- Pro: Clear directory convention consistent with existing patterns
- Pro: Plugin authors can see all contribution types at a glance
- Con: One more required directory for plugins with providers

### ABC inspection for pipeline routing

**Choice**: Provider classes are inspected for `issubclass(cls, ContextProvider)` and `issubclass(cls, MessageContextProvider)` to determine which pipeline(s) to register in. Plugin authors don't specify the target pipeline in the manifest.
**Why**: The ABC a class implements is the authoritative declaration of its behavior. Requiring a manifest-level routing field would create a second source of truth that could diverge from the actual implementation.
**Alternatives Considered**:
- Manifest-level `pipeline = "session" | "message" | "both"` field: creates coupling between manifest and implementation; diverges from actual ABC conformance
- Separate manifest sections `[session_context_providers]` and `[message_context_providers]`: forces plugin authors to understand the pipeline distinction; prevents a single class from implementing both

**Consequences**:
- Pro: Single source of truth — the ABC determines routing
- Pro: Plugin authors only need to implement the right interface
- Pro: A single class implementing both ABCs works automatically
- Con: Plugin authors must understand which ABC to implement (mitigated: well-documented interfaces)

### Constructor signature validation for `config` parameter

**Choice**: Before instantiation, the loader validates that the provider class's `__init__` accepts `config` as a keyword argument via `inspect.signature`. If the parameter is missing, the plugin fails with a diagnostic.
**Why**: Spec R3 requires plugin providers receive the validated config dict. Validating at discovery time catches signature mismatches early with clear diagnostics, rather than failing at runtime with a confusing `TypeError`.
**Alternatives Considered**:
- Try/except around instantiation: catches the error but produces a less helpful diagnostic
- No validation (just pass config and let it fail): too late, harder to debug

**Consequences**:
- Pro: Early validation with clear error message
- Pro: Consistent with handler signature validation for hooks/events
- Con: Uses `inspect.signature` which has edge cases with `*args/**kwargs` (acceptable: we check that `config` appears in parameters)

### Multi-class provider modules

**Choice**: A single provider module can contain multiple concrete provider classes. All non-abstract classes implementing a recognized ABC are discovered and registered.
**Why**: Spec R11 supports multiple context providers per plugin. Allowing multiple classes per module gives plugin authors flexibility — they can organize related providers in a single file or split them across modules using multiple manifest entries.
**Alternatives Considered**:
- One class per module only: restrictive, forces artificial file splitting for closely related providers
- Only first discovered class: arbitrary, surprising for plugin authors

**Consequences**:
- Pro: Flexible organization for plugin authors
- Pro: Consistent with Python's natural module structure
- Con: Slightly more complex discovery logic (iterate all classes, filter abstracts)

### Dual-ABC provider instance model

**Choice**: When a class implements both `ContextProvider` and `MessageContextProvider`, a **single instance** is created and registered in both pipelines. The same object reference appears in both `LoadedPlugin.context_providers` and `LoadedPlugin.message_context_providers`.
**Why**: The provider is a single stateful object. Creating two instances would duplicate any internal state and waste resources. Both `provide()` methods operate on the same instance identity, so one object naturally serves both pipeline roles.
**Consequences**:
- Pro: Single instance, no duplicated state
- Pro: `unregister()` from both pipelines removes the exact same object
- Con: Provider must be safe for concurrent calls from both pipeline contexts (already required by the ABC contract — `provide()` is async and stateless per call)

### Listener needs LoadedPlugin lookup during PluginRemoving

**Choice**: The provider listener receives a reference to the `PluginManager` to look up provider instances during `PluginRemoving` handling.
**Why**: The `PluginRemoving` event carries `alias` and `namespaced_skill_names`, but not the full `LoadedPlugin` with provider instances. The listener needs the instances to call `unregister()`. Capturing the manager reference lets the listener look up the plugin by alias.
**Alternatives Considered**:
- Add provider instances to the `PluginRemoving` event: grows the event data for a single consumer's needs
- Pass provider lists in the event: same issue, plus would need to add to event type

**Consequences**:
- Pro: Event types unchanged — no event schema modification
- Pro: Listener has single dependency path (manager → list_plugins → find by alias)
- Con: Listener depends on `PluginManager` reference (mitigated: same pattern as skills listener depending on `SkillRegistry`)

## System Behavior

### Scenario: Plugin with session-gated provider, happy path

**Given**: A `tachikoma-plugin.toml` with `[context_providers] calendar = "calendar"`. The module `context_providers/calendar.py` contains a class subclassing `ContextProvider` with a valid `__init__(self, *, config)` and implemented `provide()` and `status_message()`.
**When**: Plugin loads.
**Then**: Provider discovered, instantiated with `config={validated_config}`, stored on `LoadedPlugin.context_providers`. On `PluginInstalled`, registered into `PreProcessingPipeline`. Next `pipeline.run()` includes the provider.
**Rationale**: Full happy path validates the session-gated provider pipeline.

### Scenario: Plugin with per-message provider

**Given**: A provider class subclassing `MessageContextProvider`.
**When**: Plugin loads.
**Then**: Provider registered into `MessagePreProcessingPipeline`. Runs on every message, not just session start.
**Rationale**: Correct routing based on ABC inspection.

### Scenario: Provider implementing both ABCs

**Given**: A provider class that subclasses both `ContextProvider` and `MessageContextProvider`.
**When**: Plugin loads.
**Then**: Single instance created, registered in both `PreProcessingPipeline` and `MessagePreProcessingPipeline`. Both `context_providers` and `message_context_providers` lists on `LoadedPlugin` reference it.
**Rationale**: Dual-ABC support per spec R2.

### Scenario: Provider module with no valid class

**Given**: A module `context_providers/calendar.py` containing only utility functions, no class implementing either ABC.
**When**: Discovery runs.
**Then**: Plugin fails with diagnostic: "No concrete class implementing ContextProvider or MessageContextProvider found in module 'calendar'".
**Rationale**: Fail-fast catches configuration errors early.

### Scenario: Missing provider module file

**Given**: Manifest declares `calendar = "calendar"` but `context_providers/calendar.py` does not exist.
**When**: Discovery runs.
**Then**: Plugin fails with diagnostic naming the missing file path.
**Rationale**: Consistent with hook/event validation behavior.

### Scenario: Provider module with import error

**Given**: `context_providers/calendar.py` has a syntax error or missing dependency.
**When**: Discovery runs.
**Then**: Plugin fails with diagnostic including the import error message.
**Rationale**: Error message helps plugin author fix the issue.

### Scenario: Provider class missing config parameter

**Given**: A provider class whose `__init__` takes no `config` parameter.
**When**: Discovery runs.
**Then**: Plugin fails with diagnostic: "Provider class 'CalendarProvider' __init__ must accept 'config' as a keyword argument".
**Rationale**: Early detection of signature mismatch per spec R3.

### Scenario: Provider raises during provide()

**Given**: A registered plugin provider raises an exception during `provide()`.
**When**: The pipeline runs.
**Then**: Exception caught by `asyncio.gather(return_exceptions=True)`, logged per DES-002. Other providers (built-in and plugin) complete normally. Message proceeds with results from successful providers.
**Rationale**: Error isolation per spec R4 — consistent with built-in provider behavior.

### Scenario: Plugin removed with active providers

**Given**: A plugin with registered providers in both pipelines.
**When**: `remove_plugin` runs.
**Then**: `PluginRemoving` dispatched → listener unregisters providers from both pipelines. Event wrappers deactivated. Config removed. `PluginRemoved` dispatched.
**Rationale**: Clean removal per spec R9.

### Scenario: Plugin updated with new providers

**Given**: A plugin with registered providers.
**When**: `update_plugin` runs with a new version.
**Then**: `PluginRemoving` dispatched → old providers unregistered. New plugin discovered with new provider instances. `PluginInstalled` dispatched → new providers registered.
**Rationale**: Full lifecycle re-registration per spec R8.

### Scenario: Plugin update fails re-registration

**Given**: An updated plugin whose new provider fails validation (e.g., missing file).
**When**: Re-registration runs.
**Then**: Old providers remain active in pipelines. New materialized version stays on disk. Diagnostic stored in `PluginState`.
**Rationale**: All-or-nothing re-registration — existing providers stay active on failure.

### Scenario: CC plugin with context_providers contribution

**Given**: A CC plugin with `"context_providers": {"calendar": "calendar"}` in `plugin.json`.
**When**: Manifest parsed.
**Then**: `"context_providers"` detected as an ignored CC contribution type. INFO log emitted. Plugin loads normally with no provider support.
**Rationale**: Consistent with existing CC contribution handling per spec R10.

### Scenario: Invalid module name with path traversal

**Given**: `[context_providers] evil = "../escape"` in the manifest.
**When**: Manifest validation runs.
**Then**: Pydantic validation rejects the module name at parse time: "Module name for 'evil' must be a bare name (no path separators)".
**Rationale**: Path traversal protection, same as hooks/events.

### Scenario: Multiple providers per plugin

**Given**: A manifest with `[context_providers] calendar = "calendar"` and `crm = "crm"`.
**When**: Plugin loads.
**Then**: Both modules discovered, validated, and instantiated. Two provider instances tracked on `LoadedPlugin`. Both registered into appropriate pipelines on `PluginInstalled`.
**Rationale**: Multi-provider support per spec R11.

### Scenario: Plugin with no config schema

**Given**: A plugin with no `[config]` section in manifest and a provider expecting `config`.
**When**: Provider is instantiated.
**Then**: `config={}` (empty dict) passed to the provider constructor.
**Rationale**: Consistent with existing plugin config behavior — no schema means empty validated config.

## Notes

- The `importlib.util.spec_from_file_location` module key uses `tachikoma_plugin.{alias}.context_providers.{module_name}` to avoid `sys.modules` collisions — same pattern as hooks and events.
- Provider instances are created once during discovery and reused across the plugin's lifetime. No per-message instantiation.
- The `unregister()` method on pipelines is a safe no-op if the provider is not found in the list — this handles edge cases where the same provider might be unregistered twice (e.g., during failed re-registration rollback).
- `PreProcessingPipeline` has no lock (unlike `MessagePreProcessingPipeline`), but `unregister()` is safe because lifecycle events are dispatched sequentially by the manager's async lock, and the session-gated pipeline's `run()` is only invoked during the first message of a new session — there is no concurrent access window between lifecycle mutations and pipeline execution.
- Provider classes that are abstract (have unimplemented abstract methods) are skipped during discovery — only concrete classes are registered. This allows plugin authors to define base classes in the same module.
- The `__main__.py` wiring point for provider listeners is immediately after pipeline creation and before coordinator construction, ensuring providers are registered before any message processing begins.
- Adding `context_providers` and `message_context_providers` fields to `LoadedPlugin` is backward compatible — both use `field(default_factory=list)`, so existing code constructing `LoadedPlugin` without these fields continues to work.
