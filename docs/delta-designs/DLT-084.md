# Design: DLT-084 - Resume matching conversation on return after restart

**Delta Spec**: [../delta-specs/DLT-084.md](../delta-specs/DLT-084.md)
**Status**: Approved

## Purpose

This document explains the design rationale for this delta: how startup matching is integrated into the coordinator, how candidates-only boundary detection works, and how the existing resumption infrastructure is reused.

After implementation, the "Detected Impacts" section will guide reconciliation into feature design docs.

## Problem Context

When the system restarts, all in-memory state is lost — there is no active session. Currently, the coordinator's `send_message()` sees `active is None`, creates a fresh session, and proceeds without checking whether the incoming message relates to a recently discussed topic. This means the user always starts a new conversation after a restart, losing continuity even if they're returning to something discussed minutes ago.

**Constraints:**
- Must not add latency beyond the existing ~1-2 second boundary detection budget (R6)
- Must fail-open: any error during startup matching falls through to fresh session creation (R5)
- Must respect the existing `session_resume_window` config for candidate lookup (R2)
- The startup path has no previous session to close and no post-processing to fire — it's simpler than normal transitions

**Interactions:**
- Coordinator (`send_message()`): gains a new startup matching block before session creation
- Boundary detector (`detect_boundary()`): gains candidates-only mode via optional summary
- Boundary prompts (`prompts.py`): gains a separate prompt template pair for candidates-only matching
- Session registry (`get_recent_closed()`, `reopen_session()`): reused as-is
- Bridging context (`_persist_bridging_context()`): reused as-is for startup resume

## Design Overview

The change inserts a new code path into the coordinator's `send_message()` that runs **before** session creation when no active session exists. It queries recent closed sessions, runs boundary detection in candidates-only mode, and either reopens a matching session or creates a fresh one.

```
┌──────────────────────────────────────────────────────────────┐
│               Coordinator.send_message() — startup path       │
│                                                              │
│  ┌──────────────┐   ┌──────────────┐   ┌────────────────┐   │
│  │ No active    │──▶│ Query        │──▶│ detect_boundary │   │
│  │ session?     │   │ candidates   │   │ (summary=None)  │   │
│  └──────────────┘   └──────────────┘   └───────┬────────┘   │
│                                                 │            │
│                          ┌──────────────────────┴─────┐      │
│                          │                            │      │
│                     match found                  no match    │
│                          │                            │      │
│                          ▼                            ▼      │
│                   ┌─────────────┐          ┌──────────────┐  │
│                   │ Reopen      │          │ Create fresh │  │
│                   │ session +   │          │ session      │  │
│                   │ bridging    │          │ (normal)     │  │
│                   │ context     │          │              │  │
│                   └─────────────┘          └──────────────┘  │
│                                                              │
│  Then: proceed to normal message processing                  │
└──────────────────────────────────────────────────────────────┘
```

The boundary detector gains an optional `summary` parameter. When `None`, it uses a separate prompt template pair (`CANDIDATES_ONLY_SYSTEM_PROMPT` + `CANDIDATES_ONLY_USER_PROMPT`) that frames the task as pure candidate matching with no continuation bias.

## Components

### Implementation Structure

| Layer/Component | Responsibility | Key Decisions |
|-----------------|----------------|---------------|
| `src/tachikoma/boundary/detector.py` | `detect_boundary()` gains `summary: str | None` parameter — when `None`, selects candidates-only prompt templates | Signature change; callers with an active session pass `summary` as before |
| `src/tachikoma/boundary/prompts.py` | New `CANDIDATES_ONLY_SYSTEM_PROMPT` and `CANDIDATES_ONLY_USER_PROMPT` templates for startup matching | Separate templates (not conditional in existing) for independent tuning. Same model/effort config (Opus low effort, `allowed_tools=[]`, `max_turns=3` per DES-007). |
| `src/tachikoma/coordinator.py` | New startup matching block in `send_message()` between "no active session" check and session creation | Inserted before existing `create_session()` call |
| `src/tachikoma/sessions/registry.py` | No changes — `get_recent_closed()` and `reopen_session()` reused as-is | Existing filtering is comprehensive per R8 |

### Cross-Layer Contracts

**Integration Points:**
- Coordinator → `detect_boundary`: now passes `summary=None` for startup matching, `summary=session.summary` for normal detection. Return type unchanged (`BoundaryResult`).
- Coordinator → `SessionRegistry.get_recent_closed()`: called identically to normal boundary detection — same `window` parameter from `session_resume_window` config.
- Coordinator → `SessionRegistry.reopen_session()`: called directly on match (no prior `_close_and_fire_postprocessing()` since there's no active session to close).
- Coordinator → `_persist_bridging_context()`: called after successful startup reopen, same as normal resume path.

**Error contract:**
- Startup matching errors (candidate query, boundary detection, reopen): caught in coordinator, logged, fall through to fresh session creation (fail-open per R5).
- `reopen_session()` returning `None` (validation failure): treated as no-match, fresh session created.

### Shared Logic

- **`_persist_bridging_context()`**: Already exists on the coordinator. Reused without modification for startup resume.
- **`BoundaryResult`**: Unchanged. In candidates-only mode, `continues` is always `false`; match outcome conveyed via `resume_session_id`.
- **`SessionCandidate`**: Unchanged. Built from `get_recent_closed()` results the same way.

## Modeling

No new domain types. The change extends existing interfaces:

```
detect_boundary(
    message: str,
    summary: str | None,          # Changed: was str, now str | None
    agent_defaults: AgentDefaults,
    *,
    candidates: list[SessionCandidate] | None = None,
) → BoundaryResult
```

When `summary is None`:
- `CANDIDATES_ONLY_SYSTEM_PROMPT` is used (neutral bias, no continuation preference)
- `CANDIDATES_ONLY_USER_PROMPT` is used (no "current conversation summary" section)
- `candidates` is required (otherwise there's nothing to match against — caller skips detection)
- `continues_conversation` in the JSON response is ignored (always treated as `false`)
- Match outcome conveyed solely via `resume_session_id`

## Data Flow

### Startup matching flow (match found)

```
1. Channel calls coordinator.send_message(text)
2. Coordinator reads text from buffer, updates last_message_time
3. Awaits any pending per-message post-processing task
4. Coordinator checks registry.get_active_session() → None (no active session)
5. Startup matching path:
   a. Query candidates: recent = registry.get_recent_closed(before=now, window=session_resume_window)
   b. Build SessionCandidate list (id + summary pairs, filtering summary IS NOT NULL)
   c. Build ended_at lookup: ended_at_by_id = {s.id: s.ended_at for s in recent}
      (retains ended_at from already-fetched data — no extra DB query needed)
   d. If candidates is empty → skip detection, create fresh session (step 7)
   e. Emit Status("Thinking...")
   f. Call detect_boundary(text, summary=None, agent_defaults, candidates=candidates)
   g. Result: BoundaryResult(continues=False, resume_session_id="abc123")
6. Startup resume path (match found):
   a. Look up captured_ended_at = ended_at_by_id[resume_session_id]
      (from the already-fetched get_recent_closed() results — must happen before
      reopen_session() clears ended_at on the DB record)
   b. Call registry.reopen_session("abc123")
   c. If reopen succeeds:
      - Set _sdk_session_id to reopened session's sdk_session_id
      - Call registry.record_resumption(session_id, previous_ended_at=captured_ended_at)
      - Call _persist_bridging_context(reopened, closed_at=captured_ended_at)
      - active = reopened session, is_new_session = False
   d. If reopen fails (returns None):
      - Fall through to fresh session creation (step 7)
7. Fresh session creation (no match or reopen failure):
   a. registry.create_session()
   b. is_new_session = True
8. Normal processing continues (foundational context, pre-processing, SDK client, etc.)
```

### Startup matching flow (no match)

```
1-4. Same as above
5. Startup matching path:
   a-e. Same as above (candidates available, status emitted)
   f. Call detect_boundary(text, summary=None, agent_defaults, candidates=candidates)
   g. Result: BoundaryResult(continues=False, resume_session_id=None)
6. No match → skip to step 7
7. Fresh session creation:
   a. registry.create_session()
   b. is_new_session = True
8. Normal processing continues
```

### Startup matching flow (no candidates)

```
1-4. Same as above
5. Startup matching path:
   a. Query candidates: registry.get_recent_closed() → empty list
   b. No candidates → skip boundary detection entirely
6. Skip to step 7
7. Fresh session creation:
   a. registry.create_session()
   b. is_new_session = True
8. Normal processing continues (no Status("Thinking...") emitted — no delay)
```

### Startup matching flow (error)

```
1-4. Same as above
5. Startup matching path:
   a-e. Same as above
   f. detect_boundary() raises an exception
   g. Exception caught, logged (fail-open)
6. Fall through to step 7
7. Fresh session creation (normal)
8. Normal processing continues
```

### Bridging context for startup resume

```
1. _persist_bridging_context(reopened_session, closed_at) called after successful startup reopen
2. Queries registry.get_by_time_range(closed_at, now)
   - closed_at is the resumed session's ended_at (before it was cleared by reopen)
   - This captures all sessions between when the resumed session closed and now
3. Filters: excludes the resumed session itself, includes only sessions with summaries
4. Concatenates summaries chronologically (earliest first)
5. Persists as context entry (owner="bridging-context") on the resumed session
6. On next _build_options(), bridging context is loaded from DB and included in system prompt
```

## Key Decisions

### Separate prompt templates for candidates-only mode

**Choice**: Add `CANDIDATES_ONLY_SYSTEM_PROMPT` and `CANDIDATES_ONLY_USER_PROMPT` as separate templates rather than conditionally modifying the existing boundary detection prompts.
**Why**: The two modes have fundamentally different goals and biases. Normal detection is biased strongly toward continuation ("when in doubt, say continuation") — this makes sense when there's an active conversation. Candidates-only mode has no conversation to continue; the safe default is "no match" (create fresh session). Sharing prompts would require diluting the continuation bias or adding complex conditionals.
**Alternatives Considered**:
- Conditional within existing prompt: Less duplication, but mixes two different framing goals. The continuation bias in the system prompt doesn't apply to candidates-only mode. Makes both prompts harder to reason about and tune independently.

**Consequences**:
- Pro: Each prompt pair optimized for its use case
- Pro: Easier to tune startup matching quality without affecting normal boundary detection
- Pro: Clear code path — `if summary is None: use candidates-only prompts`
- Con: Two prompt template pairs to maintain (but they serve distinct purposes)

### Startup matching before session creation (not after)

**Choice**: Run startup matching *before* creating a new session, so that on match we reopen the existing session directly without creating and immediately discarding a fresh one.
**Why**: Creating a session is a database write. If we create first and then discover a match, we'd need to close the just-created session and reopen the matched one — wasteful and leaves an orphaned session record.
**Alternatives Considered**:
- Create session first, then check for matches: Simpler control flow (always has an active session), but wastes a DB write on match and creates orphaned session records.

**Consequences**:
- Pro: No wasted session records
- Pro: No orphaned sessions to clean up
- Con: Slightly more complex control flow — the "no active session" block now has branching before session creation

### Direct reopen without transition handling

**Choice**: On startup match, call `reopen_session()` directly rather than going through `_handle_transition()`.
**Why**: `_handle_transition()` assumes there's a previous session to close and fire post-processing for. At startup, there is no previous session — calling `_handle_transition()` would require special-casing it to skip the close/post-processing steps, which defeats the purpose of reuse. The startup resume path is simpler: just reopen + bridging context.
**Alternatives Considered**:
- Reuse `_handle_transition()` with `previous_session=None`: Would require modifying `_handle_transition()` to handle a null previous session, adding complexity to an already nuanced method.

**Consequences**:
- Pro: Startup path is explicit and simple — no null-guarding in transition logic
- Pro: `_handle_transition()` stays focused on its current responsibility (mid-conversation transitions)
- Con: Some code similarity between startup resume and the resume branch in `_handle_transition()` (reopen + bridging context), but the surrounding logic is different enough to justify the duplication

### `previous_ended_at` for resumption tracking at startup

**Choice**: Use the resumed session's `ended_at` (looked up from the already-fetched `get_recent_closed()` results) as the `previous_ended_at` for `record_resumption()` and `_persist_bridging_context()`.
**Why**: At startup there's no "previous session" being closed, but we still want to record when the resumed session was last closed. The session's own `ended_at` is the most meaningful timestamp — it marks the boundary between the old conversation and the gap. The coordinator retains an `ended_at_by_id` lookup dict from the `get_recent_closed()` call, so the value is available without an extra DB fetch and before `reopen_session()` clears it.
**Alternatives Considered**:
- Use `datetime.now(UTC)`: Inaccurate — the session was closed potentially hours ago.
- Skip resumption tracking: Loses audit trail for startup resumes.
- Fetch session record separately before reopen: Unnecessary extra DB query — the data is already available from `get_recent_closed()`.

**Consequences**:
- Pro: Accurate timestamp reflecting when the conversation actually ended
- Pro: No extra DB query — reuses already-fetched data
- Pro: Consistent with the `record_resumption()` interface
- Con: Requires coordinator to retain lookup dict from candidate query (trivial)

## System Behavior

### Scenario: First message after restart matches a recent session

**Given**: The system just restarted, no active session exists, and a closed session about "Python testing" exists within the resume window
**When**: The user sends "Let's continue with the Python tests"
**Then**: Coordinator queries candidates, runs candidates-only boundary detection, gets a match, reopens the Python testing session, assembles bridging context (summaries of any sessions between the matched session's close and now), and processes the message with full SDK continuity via `resume`.
**Rationale**: The user expects seamless continuation. The startup matching path bridges the restart gap transparently.

### Scenario: First message after restart doesn't match any session

**Given**: The system just restarted, closed sessions exist within the resume window
**When**: The user sends "What's the weather like?"
**Then**: Coordinator queries candidates, runs candidates-only detection, gets no match (`resume_session_id=None`), creates a fresh session normally with full pre-processing.
**Rationale**: When the new topic doesn't match any previous session, the system behaves exactly as before this delta.

### Scenario: First message after restart with no recent sessions

**Given**: The system just restarted, no closed sessions exist within the resume window (or all are filtered out)
**When**: The user sends any message
**Then**: Coordinator queries candidates, gets an empty list, skips boundary detection entirely, creates a fresh session. No `Status("Thinking...")` emitted — no delay.
**Rationale**: No candidates means no possible match. Skipping detection avoids unnecessary latency and user-facing status indicators.

### Scenario: Startup matching fails (detection error)

**Given**: The system just restarted, candidates are available
**When**: `detect_boundary()` raises an exception (SDK error, timeout)
**Then**: Exception is caught and logged. Coordinator falls through to fresh session creation (fail-open).
**Rationale**: Matching is best-effort. A failure should never prevent the user from starting a conversation.

### Scenario: Startup match found but reopen fails

**Given**: Candidates-only detection returns a match, but `reopen_session()` returns `None` (e.g., transcript deleted since candidate query, session too old)
**When**: The coordinator processes the failed reopen
**Then**: Falls through to fresh session creation. Logged as a warning.
**Rationale**: Candidate filtering in `get_recent_closed()` minimizes this, but race conditions are possible (transcript deleted between query and reopen). Fail-open is the correct behavior.

### Scenario: Startup resume with bridging context

**Given**: Session A (Python testing) closed at 2pm. Session B (dinner plans) ran from 3pm-4pm. System restarts. User returns at 5pm.
**When**: User sends "Back to the Python tests" and matches Session A
**Then**: Session A is reopened. Bridging context includes Session B's summary ("dinner plans discussion"). System prompt tells the agent what happened between Session A's close (2pm) and now.
**Rationale**: The user may reference things from intermediate sessions. Bridging context prevents the agent from being confused by implicit references.

### Scenario: Normal boundary detection unchanged

**Given**: An active session exists with a summary
**When**: A new message arrives
**Then**: Boundary detection runs with `summary=session.summary` (the existing `str` value), using the original `BOUNDARY_DETECTION_SYSTEM_PROMPT` and `BOUNDARY_DETECTION_USER_PROMPT`. Behavior is identical to before this delta.
**Rationale**: This delta only affects the "no active session" path. All existing behavior is preserved.

## Notes

- This delta is intentionally surgical: the boundary detector gains one optional parameter and one conditional prompt selection. The coordinator gains one new code block. No new modules, no new domain types.
- The candidates-only system prompt should use neutral language: "Does this message match any of these sessions?" rather than "Is this a topic shift?" — there's no current topic to shift from.
- The `continues_conversation` field in the JSON schema output is retained for consistency (both modes use the same schema), but its value is ignored in candidates-only mode. The caller (coordinator) uses `resume_session_id` as the sole match signal.
