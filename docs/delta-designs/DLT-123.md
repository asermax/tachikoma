## Purpose

This document explains the design rationale for adding a third memory store — **learnings** — to the `memory` extension: the modeling choices, the store-set restructuring that keeps extraction duplication-free, the draft→permanent lifecycle that enforces "recurring", and how every mechanism reuses the topic store's existing layout, indexing, and extraction conventions.

After implementation, the "Detected Impacts" section will guide reconciliation into [../feature-designs/memory.md](../feature-designs/memory.md).

## Problem Context

The memory extension holds two stores today: **episodic** (the narrative of what happened, date-stamped) and **topics** (stable *what/why* knowledge about a subject — reference facts plus the user's preferences, one topic per file). What is missing is the **experience** substrate: the recurring friction, hard constraints, repeated failures, and the agent's own self-observations about what worked and what didn't. Experience is different in *kind* from knowledge — a topic says what is true; a learning says what *bites*, repeatedly, or what approach turned out to be a dead end. Without it, every session rediscovers the same gotchas the hard way.

The delta adds a `memories/learnings/` store alongside the other two. The hard constraints come from the spec and the existing code:

- **Reuse, don't rebuild.** Learnings reuses the topic store's directory layout, `MEMORY.md` index, context-injection, and trunk-close extraction/maintenance machinery — it is a new store over an existing pattern, not a new subsystem.
- **No duplication with topics (R4/R6).** The same extraction agent must classify each signal once — topic content vs learning content — and write it to exactly one store. Two passes (one per store) would let the same signal be written twice with no shared decision, so learnings is **folded into the topics extraction fork**, never its own fork.
- **"Recurring" is a lifecycle property, not a capture-time gate (R5).** A first sighting is captured as a tentative **draft**; only cross-session recurrence graduates it to **permanent**. Nothing valuable is lost on first sighting, but only repetition earns permanence.
- **Basic maintenance only (R8/R9).** Dedup, draft promotion, pruning, fragmentation consolidation, and index consistency ship now; the richer phased consolidation (orientation / signal-gathering / merging) is explicitly deferred to DLT-173, mirroring how the codebase already defers rich consolidation behind a marker-guarded seam.
- **Greenfield.** The "earlier agent-reflections idea" was never implemented, so there is no migration — this extends the memory extension in place.
- **Codebase constraints inherited from the existing stores** (see [memory](../feature-designs/memory.md)): the extraction fork is hard-limited to `FILE_EDIT_TOOLS` and runs as a silent-background follow-up turn; there is no delete tool (deletion is empty-a-file plus a host `sweepEmptyMarkdown`); context is a static index injected once per session (no retrieval subsystem); and the trunk-close pipeline is a single marker-guarded `memory-trunk-close` post-processor.

**Interactions:**
- The trunk-close extraction and prune phases own learnings (same `memory-trunk-close` processor) — see [conversation-loop](../feature-designs/conversation-loop.md).
- Headless runs and model tiers come from the agent manager — see [agent-integration](../feature-designs/agent-integration.md).
- The shared commit mechanism (`commitChanges`) commits each phase's workspace edits — see [git-workspace](../feature-designs/git-workspace.md).

## Design Overview

Learnings is added as a third store over the topic store's machinery, with one decisive modeling move: **learnings sits in the maintenance-iterating set but is excluded from the extraction-iterating set**, so it is folded into the topics fork rather than getting its own. That single asymmetry is what enforces "one agent, one decision per signal" (R4): the topics fork classifies each extracted signal inline as topic content or learning content and writes to the right store, so the two stores can never duplicate each other.

```
bootstrap       ──> ensureMemoryLayout: create memories/learnings/ + seed learnings/MEMORY.md (idempotent)
session start   ──> memories context section: layout (now lists learnings) + ## Topics Index + ## Learnings Index (once)
trunk close     ──> memory-trunk-close (main phase):
                     extract: for each unextracted branch, fork (episodic fork | topics+learnings fork)
                              topics+learnings fork classifies each signal → topics/ or learnings/ (as draft),
                              reads existing learnings to promote a matching recurring draft → Confirmed; sweep both
                     prune:   episodic maintenance + topics maintenance + learnings maintenance (dedup/promote/prune/consolidate/index) ──> sweep ──> commit
                     consolidate: marker-guarded no-op for learnings too (interim, pending DLT-173)
                     core-context: unchanged
```

A learning file is one theme of recurring friction per `<slug>.md` (broad, future-mergeable slug), holding two visible sections — `## Drafts` (tentative) and `## Confirmed` (permanent). Promotion happens at two points: the extraction agent promotes immediately when it recognizes this session's friction against an existing draft (primary), and the maintenance pass promotes any draft that is clearly corroborated as a recurring pattern (safety net). Both stores are surfaced independently in context — a learning in the `## Learnings Index`, a topic in the `## Topics Index` — because they hold different *kinds* of information about the same subject; learnings is orthogonal to the `Skills > Topics > Context` authority hierarchy, neither deferring to nor absorbed into topics.

### Flagged Unknowns

All resolved during design (the S5 ⚠️ from the spec-phase seed is cleared):

#### S5 — Draft→permanent lifecycle (resolved)

The structure is **two sections per slug file** (`## Drafts` / `## Confirmed`), and the mechanism reuses the topic store's proven **read-before-write-and-match** pattern (`TOPICS_BASE_PROMPT` already instructs the agent to "Read existing files … to see what is already stored about each subject" before creating). Current LLM-agent-memory best practice confirms this as the recommended approach — the **write–manage–read loop** with **read-before-write / dedup-on-write** and topic-organized files over flat append-logs (see Key Decisions for sources). Four sub-questions, all settled:

- **Recurrence-detection reliability.** No separate grep/embedding step is needed; the agent reading existing learnings files during extraction and matching is the mechanism (consistent with the codebase's "static index injection, agent reads on demand" decision and the research-backed read-before-write pattern). The extraction prompt carries an explicit "read existing learnings files before deciding whether this friction is new or recurring" instruction so the match is deliberate, not incidental.
- **Promotion-trigger semantics → extraction-time + maintenance safety-net (D1).** Extraction promotes on recognized recurrence (the agent that sees the repeat acts immediately); the maintenance pass additionally reviews drafts and promotes any clearly corroborated recurring pattern, catching a missed extraction-time re-read.
- **Section ↔ index interaction → surface all files (D2).** The `MEMORY.md` index lists every slug file; the draft/confirmed state lives *inside* the file (visible at a glance via the section headers per R5) rather than in the index. The Sunday full rebuild describes a file by its overall theme regardless of the draft/confirmed mix.
- **Contradiction vs recurrence.** The agent distinguishes them by comparison: a later session showing the *same friction recurring* promotes; a later session showing the friction was *resolved* (e.g. the flaky test was fixed) corrects or removes the draft. This mirrors the existing topics "prune contradicted entries" behavior, and the maintenance contradiction-detection instructions cover it too.

No empirical spike was required: the mechanism is grounded in an already-proven codebase pattern and validated without live LLM calls (DES-003), so reliability is assessed by prompt design and arg-asserting tests, not a one-off run.

### Cross-Layer Contracts

- **Store sets as the seam.** `MEMORY_STORES`, `INDEXED_STORES`, and `EXTRACTION_STORES` in `layout.ts` are the single source of truth. Extraction iterates `EXTRACTION_STORES`; dir creation, maintenance, and cross-store manifests iterate `MEMORY_STORES`; index seeding and context injection iterate `INDEXED_STORES`. Learnings propagates to dir/index/injection/maintenance by membership, and is excluded from extraction by *non*-membership. The `ExtractionStore` type (`EXTRACTION_STORES[number]`) keys `STORE_INSTRUCTIONS` and types `storeInstruction`/`branchStoreInstruction`, so the no-learnings-fork invariant (R4) is enforced at **compile time** — not only by the `extractBranches` loop constant. (Adding `learnings` to `MemoryStore` would otherwise be a `Record<MemoryStore, string>` error in `STORE_INSTRUCTIONS`; keying it on `ExtractionStore` resolves that and expresses the invariant.) The remaining call-site edits are the topics-fork instruction/scope (Batch 2).
- **`INDEXED_STORES` dual responsibility.** Adding learnings to `INDEXED_STORES` makes `ensureMemoryLayout` seed `learnings/MEMORY.md` on bootstrap *and* `buildMemoryContext` surface the `## Learnings Index` every session — the same membership drives both, so the store is initialized and surfaced consistently (a manually-deleted index is re-seeded on the next bootstrap, matching topics).
- **Cross-store manifest.** `buildCrossStoreManifest` iterates `MEMORY_STORES`, so adding learnings automatically makes it visible (names-only) to topics/episodic/context maintenance agents, and topics visible to learnings maintenance — exactly right for contradiction detection and the "don't restate a topic" rule (R6/R11), with no extra wiring.
- **Headless-LLM seam.** Extraction (topics+learnings fork via `forkAndContinue(..., FILE_EDIT_TOOLS)`) and maintenance (learnings pass via `SideRunner.run`) reuse the shared file-tool allowlist and the `processor` tier, exactly as the other stores do — the topics fork stays hard-limited to file tools even though it writes two directories.
- **Commit seam.** The learnings maintenance pass commits through the same `commitChanges` helper (`chore(memory): learnings maintenance`), so each phase leaves a clean committed, git-recoverable state.
- **Index contract.** Every agent that creates/modifies/deletes a learnings file also maintains `learnings/MEMORY.md` per the shared `INDEX_UPDATE_SECTION` rules; `ensureMemoryLayout` seeds it idempotently; the day-of-week maintenance keeps it consistent.

### Shared Logic

- **Store-set constants**: the three arrays in `layout.ts` are the shared seam every module iterates — adding learnings is membership, not a rewrite.
- **Shared prompt sections** (`prompts.ts`): `STORE_PURPOSE_SECTION`, `CONTEXT_DEDUP_SECTION`, `WORKSPACE_VALIDATION_SECTION`, `INDEX_UPDATE_SECTION`, `INDEX_LIGHT_MAINTENANCE_SECTION`, the Sunday rebuild, and the scope/silent-background sections are reused by the learnings instruction/prompt, keeping authority, dedup, validation, and index rules identical across stores.
- **Read-before-write-and-match pattern**: topics extraction and learnings draft-promotion share the same "read existing files → decide new vs recurring → write" idiom; learnings adds the draft↔confirmed promotion on top of it.

## Modeling

Three memory *kinds*, distinct in what they hold, all git-versioned markdown under `memories/`:

```
episodic/   what happened   — date-stamped narrative of events/outcomes
topics/     what is true    — stable reference facts + user preferences, one subject per file
learnings/  what bites      — recurring friction, hard constraints, repeated failures, self-reflections
            (NEW)             one theme per <slug>.md; ## Drafts (tentative) | ## Confirmed (permanent)
```

**Authority is two axes, not one ladder.** Topics participates in the `Skills > Topics > Context` authority hierarchy (a more authoritative source wins a conflict). Learnings does **not** join that ladder — it is orthogonal, because a learning and a topic about the same subject are not competing claims about truth; they are different *kinds* of information (experience vs knowledge). So neither overrides the other, and both are surfaced (a learning in `## Learnings Index`, a topic in `## Topics Index`).

**The store-set model** (the key structural decision):

```
MEMORY_STORES    = [episodic, topics, learnings]   ← type source, dir creation, maintenance iteration, manifests
INDEXED_STORES   = [topics,        learnings]      ← MEMORY.md seeding + context injection
EXTRACTION_STORES= [episodic, topics]              ← extraction iteration (learnings folded INTO the topics fork)
```

The asymmetry — learnings is in the top two sets but absent from `EXTRACTION_STORES` — is what makes the shared agent possible and prevents duplication.

**A learnings file** is one theme of recurring friction (`<slug>.md`, broad future-mergeable slug — never incident/date-scoped), concise, with two sections:

```markdown
# <Title Case Theme>

## Drafts
- <tentative lesson observed once, with what bit and the context>

## Confirmed
- <the same friction, now corroborated across sessions — permanent>
```

`## Drafts` may hold entries; `## Confirmed` is empty until a draft is promoted. The two headers make the tentative state visible at a glance (R5). The slug's `MEMORY.md` entry describes the file's theme.

## Data Flow

```
bootstrap
  ensureMemoryLayout → mkdir memories/learnings/
                     → if learnings/MEMORY.md absent: seed (header-only if empty dir;
                        else placeholder entries, Title-Case from filenames; idempotent)

session start (main + background)
  buildMemoryContext → LAYOUT_SECTION (now describes learnings too)
                    → ## Topics Index   (from topics/MEMORY.md)
                    → ## Learnings Index (from learnings/MEMORY.md, all files incl. drafts)
                    → injected once as a hidden "memories" message

trunk close — extract (per unextracted branch; shared `extracted` marker)
  episodic fork            → memories/episodic/<trunk-day>.md
  topics+learnings fork    → read existing topics/ AND learnings/
                           → classify each signal inline:
                               stable what/why or preference  → topics/ (create-or-merge)
                               recurring friction/constraint/failure/reflection → learnings/
                                   · new friction        → append under ## Drafts
                                   · matches existing draft → promote (move draft → ## Confirmed)
                                   · friction resolved   → correct/remove (not promote)
                               dual-character signal    → one store, by primary aspect
                           → sweep topics/ + learnings/

trunk close — prune (maintenance set: episodic, topics, learnings)
  learnings maintenance (LEARNINGS_MAINTENANCE_PROMPT):
    dedup · promote corroborated drafts (safety-net) · prune stale/contradicted ·
    consolidate per-incident fragmentation into broad slugs · keep concise ·
    repair malformed ## Drafts/## Confirmed · light index consistency (weekday) | full rebuild (Sunday)
  → sweep learnings/ → commit ("chore(memory): learnings maintenance")

trunk close — consolidate: marker-guarded no-op for learnings (DLT-173 owns rich phased consolidation)
```

## Key Decisions

### Learnings is folded into the topics fork (store-set split), not its own extraction pass

**Choice**: Learnings joins `MEMORY_STORES` and `INDEXED_STORES` (so it gets a directory, a seeded index, context injection, and a maintenance pass) but is **excluded** from `EXTRACTION_STORES`; the topics extraction fork becomes a topics+learnings fork that classifies each signal inline and writes to both stores.
**Why**: R4/R6 mandate that topic and learning content is never duplicated and that one agent makes one decision per signal. A separate learnings extraction fork (the uniform "iterate `MEMORY_STORES`" path) would let the same signal be written to two stores with no shared decision. Folding learnings into the topics fork makes the classification a single inline act, and excluding it from extraction iteration prevents the third fork entirely.
**Alternatives Considered**:
- Add learnings to the extraction-iterating set (a third fork): rejected — directly violates R4; the two forks could independently write the same signal to both stores.
**Consequences**:
- Pro: duplication-free by construction; one classification decision; no third per-branch fork (cost stays at two forks per branch).
- Con: breaks the uniform per-store extraction loop (now iterates `EXTRACTION_STORES`, not `MEMORY_STORES`) and requires the topics fork to write two directories with a relaxed scope section.

### Draft→permanent enforces "recurring" via a lifecycle, not a capture-time gate

**Choice**: Every new friction is captured as a tentative draft; it graduates to permanent only when a later extraction recognizes the same friction recurring (or a maintenance pass corroborates it).
**Why**: Nothing valuable is lost on first sighting, but only repetition earns permanence — keeping the store focused on patterns that actually bite repeatedly rather than every one-off annoyance.
**Alternatives Considered**:
- Gate at capture time (only record friction already seen recurring): rejected — loses high-value one-off lessons before they can recur.
**Consequences**:
- Pro: no lost lessons; the store self-curates toward confirmed patterns.
- Con: the store carries drafts that may never recur; visibility into the draft state (section headers + index listing) is required so tentative content reads as tentative.

### Recurrence detection is agent read-and-match, not an embedding/retrieval subsystem

**Choice**: The extraction agent reads existing learnings files during extraction and decides whether the branch's friction is new (→ draft) or recurring (→ promote), reusing the topic store's read-before-write-and-match pattern. No similarity index, no retrieval call.
**Why**: This is the recommended pattern for LLM-agent memory: the **write–manage–read loop** with **read-before-write / dedup-on-write**, and topic-organized files over flat append-only logs. The topic store already proves this idiom in the same codebase, and the "static index injection, agent reads on demand" decision already trades a retrieval subsystem for the agent's own file tools. Adding embeddings would introduce a new index, a model dependency, and a sync problem for marginal gain over an agent that is already reading the (small) store.
**Sources**: write–manage–read loop and dedup-on-write as the "manage" phase ([A Practical Guide to Memory for Autonomous LLM Agents](https://towardsdatascience.com/a-practical-guide-to-memory-for-autonomous-llm-agents/)); read-before-write and topic-organized files over flat append ([Maintainable Topic Documents for Long-Term LLM Agent Memory, arXiv](https://arxiv.org/html/2606.10677v1)); the anti-pattern of blindly appending to a file ([Mem0](https://mem0.ai/blog/your-ai-agents-memory-is-just-a-file-thats-the-problem)); general agent-memory design principles ([Designing Memory Systems for LLM Agents](https://medium.com/@candemir13/designing-memory-systems-for-llm-agents-from-short-term-context-to-long-term-knowledge-b27a1d4d5516)). No external library is introduced — the pi SDK primitives (`forkAndContinue`, `SideRunner.run`, `provideContext`, `FILE_EDIT_TOOLS`) are internal and already proven; the codebase is the authoritative source for them, so no external library documentation search is outstanding.
**Alternatives Considered**:
- Embedding-based similarity match over the learnings store (a la DLT-009's retrieval engine): rejected for DLT-123 — a heavyweight index/model dependency for a small store; the agent read-and-match already does the job and stays consistent with the no-retrieval design. (Semantic search remains available to a later delta if the store grows.)
**Consequences**:
- Pro: no new subsystem; reuses a proven, research-backed idiom; consistent with the existing memory architecture.
- Con: match reliability depends on prompt quality and the agent consistently re-reading drafts — mitigated by the explicit "read existing learnings before deciding" instruction and the maintenance safety-net promotion.

### Promotion runs extraction-time (primary) + maintenance safety-net

**Choice**: The extraction agent promotes a draft to Confirmed immediately when it recognizes the branch's friction matches an existing draft; the learnings maintenance pass additionally reviews drafts and promotes any that are clearly corroborated as a recurring pattern (D1).
**Why**: Extraction-time promotion is the elegant primary (the agent that sees the repeat acts in the moment), but a missed re-read would strand a draft. The maintenance safety-net catches those, and matches the codebase's existing split of consolidation work between extraction and the prune phase (the write–manage–read loop's "manage" stage).
**Alternatives Considered**:
- Extraction-time only: simpler, but a single missed re-read delays promotion until the friction is seen yet again.
- Maintenance-time only: keeps extraction simple, but the maintenance agent has files and no session context, making recurrence inference weaker.
**Consequences**:
- Pro: robust promotion; two independent chances to graduate a real pattern.
- Con: a little more logic in the learnings maintenance prompt (the safety-net promotion rule).

### The index surfaces all slug files, including draft-only ones

**Choice**: `learnings/MEMORY.md` lists every slug file (drafts and confirmed alike); the draft/confirmed state is visible *inside* the file via the `## Drafts`/`## Confirmed` headers, not flagged in the index (D2).
**Why**: Consistent with the idempotent index rules (the index mirrors actual files) and maximizes proactive awareness of emerging friction. Learnings index entries are low-noise (title + one line, like topics), and the per-file description can note a tentative state. The tentative-vs-permanent distinction is already visible at a glance inside the file (R5), so the index does not need to duplicate it.
**Alternatives Considered**:
- Hide draft-only files from the index until promoted: cleaner injected context, but blinds the agent to emerging friction and forces the index to track per-file draft/confirmed state (extra bookkeeping that drifts from "index mirrors files").
**Consequences**:
- Pro: simple, consistent index model; proactive awareness; no extra state to maintain.
- Con: tentative content appears in every session's context — acceptable given the low per-entry cost and the explicit tentative marking inside files.

### Two-section draft representation (`## Drafts` / `## Confirmed`)

**Choice**: Each learnings slug file carries `## Drafts` (tentative) and `## Confirmed` (permanent) sections; drafts move to Confirmed on promotion.
**Why**: The tentative state is visible at a glance in plain markdown (R5), needs no parser, and the maintenance AC already references this structure (so it is the spec-settled representation).
**Alternatives Considered**:
- A YAML front-matter status marker (`status: draft|confirmed`): more machine-parseable, but adds a parser concern, is invisible to a human skimming the file, and diverges from the free-form prose convention of the other stores.
**Consequences**:
- Pro: human-readable, no parser, consistent with sibling stores; maintenance can detect/repair a malformed structure in place.
- Con: a single file can hold both states, so promotion is a within-file move (the agent relocates the entry between sections) rather than a file rename.

### Learnings is orthogonal to the authority hierarchy, not a new tier

**Choice**: `STORE_PURPOSE_SECTION` gains a learnings bullet stating it holds *experience*, is orthogonal to `Skills > Topics > Context`, never merges into topics, and does not defer to topics.
**Why**: R11 — a learning and a topic about the same subject are different *kinds* of information (experience vs knowledge), so neither overrides the other; placing learnings *in* the ladder would imply one defers to the other, which is wrong.
**Alternatives Considered**:
- Insert learnings into the ladder (e.g. `Skills > Topics > Learnings > Context`): rejected — it would make a learning defer to or override a topic about the same subject, collapsing two kinds of information into one conflict-resolution axis.
**Consequences**:
- Pro: both stores coexist and surface independently about the same subject.
- Con: the authority section must state the orthogonality explicitly so the agent does not try to reconcile a learning against a topic.

## System Behavior

### Scenario: First sighting of a friction → draft

**Given**: A session surfaces a recurring-flavored friction not yet in `learnings/`.
**When**: The topics+learnings extraction fork folds the branch.
**Then**: The friction is written under `## Drafts` in the matching slug file (created with a broad slug if none exists) — tentative, not confirmed.
**Rationale**: A single occurrence does not yet establish a recurring pattern.

### Scenario: Recurring friction → promotion (extraction-time)

**Given**: A `## Drafts` entry exists for friction X.
**When**: A later session's extraction fork reads existing learnings and recognizes the same friction X recurring.
**Then**: The entry is moved from `## Drafts` to `## Confirmed`.
**Rationale**: Repetition is the signal that this is a real, recurring learning.

### Scenario: Maintenance safety-net promotion

**Given**: A draft that an extraction fork failed to promote.
**When**: The learnings maintenance pass runs and finds a draft clearly corroborated as a recurring pattern.
**Then**: It promotes the draft to `## Confirmed`.
**Rationale**: Two independent chances to graduate a real pattern; matches the write–manage–read "manage" stage.

### Scenario: Friction resolved → not promoted

**Given**: A draft describes a friction a later session shows was resolved (e.g. the flaky test was fixed).
**When**: Extraction or maintenance runs.
**Then**: The contradiction is resolved — the draft is corrected or removed — it is **not** promoted.
**Rationale**: A resolved friction is the opposite of recurrence; promoting it would record a falsehood.

### Scenario: Dual-character signal lands in one store

**Given**: A branch signal with both stable-knowledge and friction character (a fact that causes friction).
**When**: The shared extraction agent classifies it.
**Then**: It lands in exactly one store, by its primary aspect in context (a fact-that-bites is recorded in `learnings/` as the lesson, not also restated as a topic).
**Rationale**: One agent, one decision per signal — the two stores never duplicate.

### Scenario: One-time event is not a learning

**Given**: A branch contains a one-time event (a single bug fix, an outage).
**When**: Extraction runs.
**Then**: It is **not** written to `learnings/` (it belongs in episodic); only friction/lessons/reflections with experience character become learnings.
**Rationale**: Learnings capture experience, not the narrative of what happened.

### Scenario: Branch with nothing to learn

**Given**: A branch with no recurring friction, hard constraints, or reflections worth capturing.
**When**: Extraction runs.
**Then**: No learnings files are created and no error is thrown; the topics side may still write topics.
**Rationale**: Extraction must be a safe no-op for branches with no learnings signal.

### Scenario: Fragmentation consolidation

**Given**: Per-incident learnings files fragmenting one friction theme (the anti-pattern R12 forbids).
**When**: The learnings maintenance pass runs.
**Then**: They are consolidated into a single broad slug file.
**Rationale**: The store must not fragment into per-incident files; one theme per broad slug.

### Scenario: Malformed section structure repaired

**Given**: A learnings file whose `## Drafts`/`## Confirmed` structure is malformed.
**When**: Maintenance runs.
**Then**: It repairs the structure in place, or — if unrecoverable — logs a warning and leaves the file for the next pass rather than crashing.
**Rationale**: Maintenance must be resilient to agent-written drift.

### Scenario: Index consistency and Sunday rebuild

**Given**: The learnings maintenance step runs Monday–Saturday, vs Sunday.
**When**: The prompt is assembled (the `if (store !== "episodic")` day-of-week gate).
**Then**: Weekdays carry the light index-consistency section (sync `MEMORY.md` to actual files, preserve descriptions); Sunday carries the full rebuild (fresh descriptions for every file, by theme regardless of draft/confirmed mix).
**Rationale**: Cheap consistency daily, periodic freshening weekly — same cadence as topics.

### Scenario: `enabled = false` registers nothing

**Given**: `[extensions.memory] enabled = false`.
**When**: The extension loads.
**Then**: No learnings directory is ensured, no index seeded, no learnings index injected, and no learnings extraction or maintenance registered (the top-level disable gate covers the whole extension).
**Rationale**: Learnings lives inside the memory extension; its disable behavior is the extension's disable behavior (R10).

### Scenario: Idempotent re-extraction after a crash

**Given**: A branch already carrying the shared `extracted` marker.
**When**: The extract phase re-runs (e.g. after a crash).
**Then**: The branch is skipped — learnings were folded as part of the same marker, so no duplicate drafts are written.
**Rationale**: Extraction is idempotent per branch; the shared marker covers all stores folded in the topics fork.
