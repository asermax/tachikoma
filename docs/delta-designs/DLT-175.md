# Design: DLT-175 - Daily session with collapsible topic branches

**Delta Spec**: [../delta-specs/DLT-175.md](../delta-specs/DLT-175.md)
**Status**: Draft

## Purpose

This document explains the design rationale for replacing Tachikoma's topic-based session model with a daily-trunk session whose topic shifts become collapsible branches, with all conversational state living on the pi session file (plus a small key-value store) instead of a `sessions` database table. It covers the modeling, data flow, the trunk-close memory pipeline, registry-free lifecycle and recovery, and the pi SDK primitives the design adopts.

## Problem Context

The current model opens or resumes a separate session per topic. Every topic shift closes a session, orphaning that topic's context — the agent loses awareness of what was just discussed unless a session is explicitly resumed within a window. Cross-topic recall is brittle, bridging context is bolted on at resume, and the `sessions` registry duplicates state pi already tracks on its session files.

This delta makes the **day** the unit of conversation: one persistent trunk session per day, topic shifts collapsed into branch summaries on the trunk, earlier-day context reachable on demand. The pi SDK already provides the tree primitives (`branchWithSummary`, append-only branches, custom entries, headless forks); the current architecture deliberately bypasses them.

**Constraints (verified against the pi SDK in `node_modules/@earendil-works/pi-coding-agent/docs/`):**
- The pi session **header is not extensible** — only `parentSession` is honored (`docs/session-format.md`). Trunk *discovery* cannot live in the header.
- `sessionsDir` is **shared** with fork/side-run/shadow-fork sessions, so directory scanning cannot reliably identify "our" trunk.
- On `SessionManager.open`, `leafId` is set to the **last entry in file order**, not the active branch tip — the leaf must be explicitly re-seated.
- `branchWithSummary` does **not** record a pointer to the abandoned branch's leaf — we must store `originalLeafId` ourselves in the entry `details`.
- pi has no structured-output API for one-shots; classification builds on `completeSimple` / a headless session (see [agent-integration](agent-integration.md)).

**Interactions:** rewrites [boundary-detection](boundary-detection.md); reshapes the [conversation-loop](conversation-loop.md) session lifecycle; folds [memory](../feature-specs/memory.md) maintenance into trunk close; adopts pi tree primitives in [agent-integration](agent-integration.md); moves [git-workspace](../feature-specs/git-workspace.md) + [projects](../feature-specs/projects.md) commit to per-exchange; reshapes [telegram](telegram.md) routing; routes [tasks](../feature-specs/tasks.md)/[notifications](../feature-specs/notifications.md) deliveries into the current branch.

## Design Overview

A single **daily trunk** pi `AgentSession` is the conversation for the day. Its identity is held by an `app_state` pointer `{ sessionFile, day, openedAt }` where `day` is the local calendar date in the configured scheduler timezone. The trunk is a linear, append-only chain of `branch_summary` entries; the live topic is the branch extending the latest summary (the *current base*).

On each **idle** user message, a **shadow-fork classifier** forks the live branch into a throwaway headless no-tools session in an OS temp dir and asks the conversation itself whether the message continues the topic. On a shift, the current branch **collapses** via `branchWithSummary(currentBase, summary, details)` — the abandoned branch survives in the tree, reachable through the `originalLeafId` stored in `details` — and the base advances to the new summary entry. A **related-branch matcher** (LLM over prior summaries, no vector DB) and an **`ask_branch` tool** (headless fork of a prior branch's `originalLeafId`) provide cross-branch context. All boomerang state lives in `appendCustomEntry` snapshots (out of LLM context); injected cross-branch context uses `appendCustomMessageEntry` (in context).

The trunk **closes** on a configured nightly cron (in the scheduler timezone) with a **lazy stale-day backstop** on the inbound path for missed closes. Closing runs a **unified phased memory pipeline keyed on the day's branches** — per-branch extraction → pruning → a final consolidation pass — replacing the separate per-store maintenance crons, followed by the once-daily steps (transcript archive, workflow cleanup). Per-branch and per-step **completion markers** (custom entries) make close idempotent; an `app_state` `unclosed` index lets startup recovery close and consolidate every stale-day trunk left by multi-day downtime. **Git/projects commit continuously** as exchange processors so mid-day work is never lost.

The `sessions` table and `src/sessions/registry.ts` are removed. `app_state` is kept (active pointer + unclosed index). `channel_messages` is slimmed to a `messageId → { treeEntryId, branchId }` map and joins the retention sweep.

## Components

### Implementation Structure

| Component | Responsibility | Key Decisions |
|-----------|----------------|---------------|
| `src/coordinator.ts` | Owns the single daily trunk `ActiveSession`; ensure/close/recover keyed on the `app_state` pointer; runs the trunk-close memory pipeline; queues deliveries until a trunk is live | Drops registry coupling; lifecycle expressed via the pointer + on-file markers, not table rows |
| `src/sessions/trunk.ts` (replaces `registry.ts`) | Trunk identity & state: read/write the `app_state` active pointer + `unclosed` index; open today's trunk or create a new one; re-seat the leaf; rebuild branch records from the file | `KeyValueState` over `app_state`; no `sessions` table |
| `src/extensions/boundary/` (rewrite) | Shadow-fork classifier, branch collapse, related-branch pull, `ask_branch` tool, boomerang state on the file | Inbound middleware + a tool ([DES-001](../design/DES-001-unified-extension-api.md)); ports the validated prototype |
| `src/agent/manager.ts` | Adds branch primitives over pi: `branchWithSummary`, `createBranchedSession` shadow forks, `getBranch(originalLeafId)` walks | Reverses the "bypass session tree" decision in [agent-integration](agent-integration.md) |
| `src/extensions/memory/` | Trunk-close phased pipeline (extract per branch → prune → consolidate); per-branch + per-step completion markers; whole-trunk archive | Folds the per-store maintenance crons into the close event |
| `src/extensions/git/`, `src/extensions/projects/` | Register **exchange processors** (commit per response) in addition to a close-time commit | Continuous safety |
| `src/extensions/telegram/` | Slimmed `channel_messages` (`messageId → {treeEntryId, branchId}`); reply/reaction/button resolve to a branch and force append-or-shift | No `resumeSessionId` force-route |
| `src/scheduler.ts` consumer | Nightly-close cron in the configured timezone | Mirrors memory-maintenance cron registration |

### Integration Points

- **Boundary → coordinator**: the middleware drives collapse/shift on the live trunk through `app.agent` branch helpers; it no longer calls `closeSession`/`resumeSession` for topic transitions (those are deleted).
- **Coordinator → memory**: trunk close invokes the phased pipeline via the post-processing contract, but extraction iterates per branch (enumerated from the file) rather than over one transcript.
- **Telegram → boundary**: a reply/reaction/button resolves its referenced message to `{treeEntryId, branchId}` and hands the boundary middleware a forced outcome (append vs. shift+inject), bypassing classification.

### Model Tiers

Tachikoma exposes four configurable tiers (`[agent]`: `main`/`searcher`/`processor`/`classifier`, `src/agent/models.ts`) with fallback `classifier → processor → main` and `searcher → main`. The new mechanisms map as:

| Mechanism | Tier | Rationale |
|-----------|------|-----------|
| Trunk conversation (live turn) | `main` | The agent turn (unchanged) |
| Shadow-fork classifier (S2) | `classifier` | Discrete `{decision, reason}`; heavier per-call than today's classifier since it forks the live branch with context |
| Branch summary on collapse (S3/S4) | `processor` | Mechanical summarization |
| Related-branch matcher (S5) | `classifier` | Structured `{branchId\|null}` over prior summaries |
| `ask_branch` lookup (S6) | `searcher` | Retrieval over a prior branch's conversation |
| Per-branch extraction (S8) | `processor` | Same role as today's memory extraction |
| Pruning (S8) | `processor` | Mechanical removal of contradicted/stale info |
| **Consolidation (S8)** | `main` | Heaviest daily reasoning; runs once at close, so top-tier quality is affordable |
| Per-exchange safety commit (S14) | none | Cheap deterministic commit (no agent), just preserves intermediate state |
| Trunk-close grouped commit (S14) | `processor` | Agent-driven grouped commit (`createCommitAgent`) for clean daily history |

**Cost note:** the model drops the per-exchange rolling summary but adds a heavier `classifier` shadow-fork on each idle user message (loads branch context) plus a `processor` summary + `classifier` matcher per shift — net per-message classification cost rises, so the `classifier` tier choice matters. Commits are now agent-driven (a full `processor`-tier agent loop per commit, via `createCommitAgent`), which is why the per-exchange commit uses the cheap deterministic path and the agent-driven grouped commit is reserved for trunk close. The trunk-close pipeline fans out many parallel `processor` extraction agents plus the grouped commit → burst API load, which is the interplay point with **DLT-138** (stagger parallel API-consuming pipeline ops).

## Modeling

**Entities**

- **Trunk** — one pi session file per day. Identity in `app_state["trunk"]["active"] = { sessionFile, day, openedAt }`; the set of not-yet-consolidated trunks in `app_state["trunk"]["unclosed"] = [sessionFile, ...]`.
- **Branch** — a topic's conversation. Born as the live tip extending the current base; on shift becomes a `branch_summary` entry. Persists append-only after collapse.
- **Branch record** — derived from a `branch_summary` entry's `details`: `{ branchId: "topic-N", originalLeafId, baseId, summaryEntryId, lastExchange }`. Enumerated via `getEntries()` filtered by `customType`.
- **Boomerang state snapshot** — `appendCustomEntry(customType, { version, currentTopicBaseId, lastDecision, relatedBranchId })`; latest on the branch path wins on reload.
- **Completion markers** — custom entries: per-branch `{ branchId, extracted: true }` and per-step `{ step, completed: true }` for idempotent close/recovery.
- **Telegram routing row** — slimmed `channel_messages(messageId, treeEntryId, branchId)`.

**Relationships**: a Trunk has many Branches (linear summary chain); each Branch has one summary entry and one original leaf; each Telegram row points at one tree entry within one branch.

## Data Flow

**Inbound user message (idle):**
```
message → boundary middleware
  ├─ system-origin / mid-exchange (steer) / no assistant turn yet → skip detection, append
  ├─ reply/reaction/button → resolve channel_messages → same branch? append : forced collapse+fork+inject
  └─ shadow-fork classify(live branch)
       ├─ continue → append to current branch
       └─ shift → summarize since base → branchWithSummary → advance base
                  → related-branch matcher → maybe appendCustomMessageEntry(pointer)
→ ensureSession (today's trunk, leaf re-seated) → streamPrompt → channel.respond
→ exchange processors: git commit, projects commit
```

**Trunk close (cron or lazy backstop):**
```
close trigger → dispose live session → for each branch (enumerate branch_summary):
   if no "extracted" marker → fork-and-continue extraction(getBranch(originalLeafId)) → write marker
→ prune phase (stale/contradicted) → consolidation agent (whole day)
→ once-daily steps (transcript archive, workflow cleanup) each guarded by marker
→ remove trunk from unclosed index; clear/repoint active pointer
```

**Startup recovery:**
```
boot (before channel.start) → read active pointer + unclosed index
→ for each trunk with day < today: run the close pipeline (idempotent via markers)
→ while recovering, the scheduler/notify producers' deliveries are enqueued, not drained
→ open today's trunk (or defer creation to first message) → mark recovery complete → drain queue
```

## Pattern Alignment

- **ADR-001 (agent SDK)** — this delta reverses the "registry = source of truth / bypass the session tree" portion of ADR-001. That reversal is recorded in **[ADR-014](../architecture/ADR-014-session-source-of-truth.md)** (Accepted), which supersedes that portion only; the pi SDK choice, version pinning, prompt ownership, and fork-based extraction in ADR-001 stand. `AgentSessionRuntime` remains unused — the coordinator still drives the single-active invariant via `AgentManager.open`.
- **ADR-004 (persistence)** — compliant: keeps the `app_state` KV store and the (slimmed) extension-owned `channel_messages` table; only the core `sessions` table is dropped.
- **ADR-006 (scheduler)** — compliant: nightly close uses `app.scheduler.cron` in the configured timezone, with the lazy stale-day backstop as the restart catch-up.
- **DES-001 (unified extension API)** — impacted: the `app.sessions` surface (`onOpen`/`close`/`openNew`/`resume`) and the "session registry" core-module mention change. Per-topic `close`/`resume` are removed; the inbound-middleware contract no longer "resumes a session" for topic shifts (it drives collapse/branch on the live trunk). `app.sessions` gains trunk-lifecycle operations (open-today/close-trunk/recover) and `onOpen` fires once per day. Listed in Detected Impacts.
- **DES-005 (base prompt)** — compliant: the shadow fork inherits the live system prompt via `ctx.getSystemPrompt()` and sets `noExtensions`; no inline base prompt is introduced.

## Key Decisions

### All conversational state on the session file + `app_state`; drop the `sessions` table

**Choice**: Boomerang/trunk/branch state and idempotency markers live as pi custom entries on the session file; trunk identity and the unclosed set live in the existing `app_state` KV store; the `sessions` table and `registry.ts` are removed.
**Why**: The pi session file is already the durable source of truth for the conversation tree; the registry duplicated it and created a DB↔file dual source. Custom entries (`appendCustomEntry`) persist durably, reload on open, and stay out of LLM context; `branch_summary.details` carries arbitrary JSON read back verbatim. The prototype validates the full loop end-to-end.
**Sources**: pi SDK `docs/session-format.md`, `docs/sessions.md`; `dist/core/session-manager.d.ts`/`.js` (`appendCustomEntry`, `appendCustomMessageEntry`, `branchWithSummary`, `getEntries`, `getBranch`, `getEntry`); validated prototype `prototype/index.ts`.
**Options Researched**: (a) session-file + `app_state` (chosen); (b) keep the `sessions` table reshaped per-trunk; (c) defer to a design-phase spike. (b) reintroduces the dual source of truth the model removes; the spike (c) was run and resolved in favor of (a).
**Why over alternatives**: discovery is the only friction (header not extensible, shared `sessionsDir`), solved by the `app_state` pointer rather than a whole table.
**Consequences**: Pro — single source of truth, native reload, no migration of live rows. Con — trunk discovery needs the `app_state` pointer; recovery enumerates branches by scanning the file's entries.

### Shadow-fork classifier over a transcript classifier

**Choice**: Detect topic shift by forking the live branch into a separate `SessionManager` → `createBranchedSession(leafId)` in an OS temp dir → headless `createAgentSessionFromServices({ noTools: "all" })` with `noExtensions`, prompt `{decision, reason}`, dispose + delete.
**Why**: Asking the conversation itself ("does this continue?") is more accurate than classifying a rolling summary, and a separate manager + temp dir guarantees the live leaf is never mutated (R6). `noExtensions` prevents the boomerang extension from recursively loading in the shadow.
**Sources**: pi SDK `docs/sessions.md`, `docs/extensions.md`; `createAgentSessionServices`/`createAgentSessionFromServices` signatures; prototype `classifyWithShadowFork`/`promptHeadlessFork`. (`ctx.fork(...)` is a live *replacement*, not a shadow fork — rejected.)
**Consequences**: Pro — accurate, non-invasive, no rolling summary needed. Con — a forked headless session per idle shift-check (cost/latency; gated by "≥1 assistant exchange" and idle-only).

### `branchWithSummary` collapse, storing `originalLeafId`

**Choice**: Collapse via `branchWithSummary(currentBase, summary, details, true)`; store `originalLeafId` (and branch metadata) in `details`; advance the current base to the returned summary id.
**Why**: pi moves the leaf to the base and appends the summary but does **not** record the abandoned leaf; storing `originalLeafId` keeps the full branch walkable (`getBranch(originalLeafId)`) for `ask_branch` and per-branch extraction. Branches are append-only, so nothing is lost.
**Sources**: `session-manager.js` (`branchWithSummary` sets `parentId`/`fromId` to the base; branching only moves `leafId`); prototype `collapseCurrentTopic`/`getBranchRecords`.
**Consequences**: Pro — collapsed branches remain queryable; deterministic branch ids by counting summary entries. Con — `originalLeafId` correctness is our responsibility.

### Related-branch context by LLM matcher, not a vector DB

**Choice**: After a collapse (or on an explicit reply/reaction/button reference), an LLM matcher compares the new message against prior branch summaries; on a match inject a pointer (`appendCustomMessageEntry`) — the summary is already on the trunk, plus the branch's last exchange. Detail beyond that is pulled lazily via `ask_branch`.
**Why**: The idea's explicit decision — good summaries eliminate vector-similarity retrieval; a single-user day has few branches, so an LLM pass over summaries is cheap and avoids an embedding index/store.
**Sources**: idea `index.md` ("No vector DB needed"); prototype `findRelatedBranch`/`injectRelatedBranchContext`.
**Consequences**: Pro — no embedding infra; provenance-aware injection. Con — match quality depends on summary quality.

### Trunk close is the unified phased memory pipeline

**Choice**: Closing the trunk runs the entire nightly memory pipeline keyed on the day's branches: phase 1 per-branch extraction (parallel agents), phase 2 pruning of stale/contradicted info, phase 3 a final consolidation agent — then once-daily archive + workflow cleanup. The separate per-store maintenance crons are removed.
**Why**: The day's branches are the natural unit of "what happened today"; extraction feeds the stores and consolidation should run over fresh data, so coupling them to the close event removes ordering races between independent crons and a separate close. Aligns with the phased consolidation/pruning direction (DLT-173).
**Sources**: existing memory maintenance crons (`src/extensions/memory/index.ts`); scheduler timezone handling (`src/scheduler.ts`, `src/config/load.ts`); reuses fork-and-continue extraction (`extraction.ts`).
**Consequences**: Pro — one coherent nightly pipeline, correct ordering, per-branch granularity. Con — close becomes heavier (multiple agents); must be idempotent and crash-resumable (markers) and reconciled with DLT-173/172/123.

### Registry-free lifecycle: `app_state` pointer + cron + lazy backstop + idempotent markers

**Choice**: Trunk identity in an `app_state` pointer; an `unclosed` array index for multi-day-downtime recovery; nightly close via `app.scheduler.cron` in the configured timezone, with a **lazy stale-day backstop** on the inbound path; per-branch/per-step completion markers (custom entries) for idempotency.
**Why**: The shared `sessionsDir` rules out directory-scan discovery; the process may be down at the cron hour, so the cron must be an optimization over a lazy check, not the sole correctness path; cron-close and lazy-close can race, so close/extraction must be idempotent. The `unclosed` array covers >24h downtime where multiple prior trunks are unprocessed.
**Sources**: spike findings on `SessionManager.list`/`findMostRecentSession` (shared dir), croner timezone (`scheduler.ts`), the existing `recoverUnprocessedSessions` contract (`coordinator.ts`), `KeyValueState` (`src/db/state.ts`).
**Consequences**: Pro — O(1) discovery, DST-safe day keys, crash/multi-day-safe recovery. Con — two small `app_state` keys to keep consistent with on-file markers.

### Slimmed `channel_messages` table for Telegram routing

**Choice**: Keep a slimmed `channel_messages(messageId, treeEntryId, branchId)` table (row-level writes, O(1) lookup), joined to the retention sweep — instead of an on-file map or a day-scoped `app_state` blob.
**Why** (user decision): replies/reactions/buttons look up on every such event and write on every message; row-level writes avoid rewriting a whole-day JSON blob, and a table avoids O(n) tree-walks. The cost is one retained table, mitigated by adding it to DLT-171's sweep.
**Consequences**: Pro — efficient at volume; clean point lookups. Con — one table survives the "drop the DB" goal; needs retention (DLT-171).

### Reply/reaction/button force the outcome by referenced branch

**Choice**: Resolve the referenced message to its branch via `channel_messages`; same branch → append; different branch → force a collapse + new branch and inject the referenced branch's context — bypassing the shadow-fork classifier. The old `resumeSessionId` force-route is deleted.
**Why**: The reference is an explicit, deterministic signal of intent; running it through the probabilistic classifier would be both wasteful and less reliable. A reference to an earlier topic is, by definition, a shift.
**Empty-branch guard**: the "don't collapse a branch with no assistant exchange yet" guard applies to the forced path too — if the current branch is empty (just created), a forced shift starts the new branch without emitting an empty `branch_summary` (the same precondition the classifier path uses).
**Consequences**: Pro — deterministic, cheap, matches user intent. Con — depends on the routing table resolving the message; an unrecorded target falls back to normal detection.

### Continuous git/projects commit

**Choice**: Register workspace-git and projects commit as **exchange processors** (after each assistant response), plus a final commit at trunk close.
**Why** (user decision): a daily-only commit risks losing a full day's work to a mid-day crash; committing per response bounds loss to one exchange.
**Consequences**: Pro — no mid-day data loss. Con — many commits per day (acceptable; the day's history is granular).

### Queue deliveries until a trunk is live

**Choice**: While startup recovery is closing/consolidating a stale-day trunk (and before today's trunk is open), inbound background deliveries (session tasks, notifications) are enqueued and not drained until consolidation finishes and the new trunk is live.
**Why** (user decision): consolidation is a heavy multi-agent pass; a task/notification delivered into a half-recovered or not-yet-open trunk would land in the wrong place or race the pipeline. The coordinator already has a delivery queue gated on `exchanging`; this extends the gate to "trunk live."
**Sources**: existing delivery queue (`src/channels/delivery-queue.ts`, `coordinator.ts`); recovery runs before `channel.start` (`app.ts`).
**Consequences**: Pro — deliveries always land in a live trunk in order. Con — a long consolidation delays delivery of queued notices (acceptable; they drain immediately once live).

**Ordering (resolves reviewer gap):** recovery runs before `channel.start` (as today, `app.ts`). The delivery queue's drain gate is extended from `exchanging` to `exchanging || !trunkLive`; producers (scheduler/notify) may enqueue during recovery but nothing drains until `trunkLive` is set. Today's trunk is created lazily on the first event of the day — so a background delivery that is itself the first event triggers trunk open (after any stale-day recovery completes), then drains. Write-ordering invariant for the `app_state` keys: a trunk is added to `unclosed` **before** it becomes `active`, and removed from `unclosed` **only after** all per-branch/per-step completion markers are present — so a crash can never lose a trunk from recovery.

### Trunk-close pipeline atomicity

**Choice**: Per-branch extraction is idempotent via per-branch `extracted` markers (re-run skips done branches). The aggregate **prune** and **consolidation** phases — which mutate the shared memory stores — are made crash-safe by operating on a staged result committed atomically with their completion marker (marker written in the same unit as the store mutation), so a crash before the marker leaves the stores unchanged and recovery re-runs the phase cleanly. The phase content (what prune/consolidate actually do) is owned by DLT-173; this delta owns the trigger, ordering, and the atomicity contract.
**Why**: per-branch markers alone protect re-running *after success*, not a partial store mutation that crashed mid-write; store-mutating phases need atomic commit-with-marker to guarantee R7/R16 "exactly once" under crash.
**Consequences**: Pro — crash-safe exactly-once close. Con — requires the consolidation phase (DLT-173) to support staged/atomic commit; flagged in Open Questions.

### Continuous commit (cheap per exchange, agent-grouped at close), push at close

**Choice**: After every assistant response (including background/system-origin turns, since the workspace may change regardless), commit with the **cheap deterministic path** — the non-agent fallback `commitAll` already provides — skipping empty commits. The **agent-driven grouped commit** (`app.git.createCommitAgent`, introduced by the agent-driven-commits work) runs **once at trunk close** to produce clean, grouped daily history. **Push** stays at trunk close.
**Why**: R14 requires a per-exchange commit so an intermediate file state is never overwritten before being captured — but a commit is now a full headless `processor`-tier agent loop (status → diff → log → read context → grouped add/commit), far too heavy to run on every exchange. Splitting the cadence keeps per-exchange safety cheap (a plain deterministic commit, no model call) while still getting the grouped-history benefit once per day at close. Pushing per exchange would add network/rate-limit churn for no durability gain.
**Alternatives considered**: agent-driven commit per exchange (best continuous messages, but a full agent loop every response — rejected on cost/latency, and a DLT-138 burst-load hazard); daily-only commit (loses intermediate states mid-day — fails R14).
**Consequences**: Pro — no mid-day loss, cheap per-exchange, clean daily history, bounded push. Con — mid-day history is plain WIP commits until the close pass; whether the close agent regroups the day's WIP commits or only commits remaining changes is a plan-phase detail. Cross-ref **DLT-138** (stagger parallel API ops) for the close-time agent commit alongside per-branch extraction.

### Telegram routing-row write timing

**Choice**: For an **inbound** user message, the `{ messageId → treeEntryId, branchId }` row is written after the message is appended (so the pi entry id exists), in the same exchange-processing path that records messages today. For an **outbound** assistant message, the row is written at send time mapping the Telegram message id to the just-produced assistant entry. `branchId` for the live (un-collapsed) branch is computed with the same deterministic formula used at collapse (`topic-(count of branch_summary entries + 1)`), so the id written mid-branch equals the id assigned when that branch later collapses.
**Why**: tree entry ids are only known post-append; reply targets are usually outbound assistant messages; id stability requires the live-branch id to match its eventual collapse id.
**Consequences**: Pro — replies/reactions/buttons resolve to a stable branch id. Con — a row written for a branch that never collapses (e.g. the day's final live branch) still resolves via the live-branch formula at lookup time.

### Refactor migration reuses the migration subsystem

**Choice**: Add a one-time step to `src/migration/` following the existing self-detecting + idempotent pattern: detect the old schema (the `sessions` table present), **copy** the database to a backup (the live DB keeps being used — unlike the legacy import which renames and starts fresh), then let drizzle apply the migration that drops `sessions` and reshapes `channel_messages`. No-op once on the new schema.
**Why** (user decision): reuse proven backup/detection machinery; a backup before a destructive schema change lets the user recover. A copy (not rename) is right here because we keep `app_state`/tasks/workflows and only change two tables.
**Sources**: migration subsystem (`src/migration/`, `adaptLegacyDatabase` backup pattern), [migration feature spec](../feature-specs/migration.md) R0/R3/R4/R5/R6.
**Consequences**: Pro — safe, recoverable, idempotent upgrade. Con — one more migration step to maintain; the backup is a full DB copy.

## System Behavior

### Scenario: Topic shift detected
**Given** an active branch with ≥1 assistant exchange **When** an idle message on a new topic arrives **Then** the shadow fork returns `shift`, the branch collapses via `branchWithSummary`, the base advances, the related-branch matcher may inject a pointer, and the message continues on the fresh branch.

### Scenario: Reply to an earlier topic
**Given** a Telegram reply targeting a message in branch `topic-2` while `topic-5` is live **When** handled **Then** `channel_messages` resolves it to `topic-2`, a shift is forced (collapse `topic-5`, new branch), and `topic-2`'s context is injected — no classifier call.

### Scenario: Nightly close
**Given** the configured close hour in the scheduler timezone **When** the cron fires and no exchange is in flight **Then** the trunk closes, per-branch extraction → pruning → consolidation runs (each branch/step guarded by a marker), archive + workflow cleanup run once, the trunk is removed from `unclosed`, and the pointer is cleared.

### Scenario: Missed close (process down at the cron hour)
**Given** the process was down at the close hour and restarts mid-next-day **When** the inbound path sees the active pointer's `day < today` **Then** the stale trunk is lazily closed + consolidated before today's trunk opens.

### Scenario: Multi-day downtime
**Given** two prior-day trunks in the `unclosed` index **When** startup recovery runs **Then** each is closed + consolidated idempotently (markers skip already-done branches/steps) before the channel starts.

### Scenario: Task/notification during recovery
**Given** recovery is consolidating a stale-day trunk **When** a session task or notification fires **Then** it is enqueued and only drained once consolidation finishes and the new trunk is live (R17).

### Scenario: Mid-exchange message
**Given** the trunk is mid-exchange **When** a message arrives **Then** it steers the live run and detection is not invoked; a `/queue` message waits and is classified as idle next turn.

### Scenario: Restart mid-day
**Given** a restart mid-day **When** the trunk is reopened from the pointer **Then** boomerang state is rebuilt from the latest custom-entry snapshot, branch ids recomputed deterministically, and the leaf is re-seated onto the current base so the live conversation continues on the trunk (not a stale collapsed tip).

### Scenario: First run after the refactor (migration)
**Given** an install on the old schema (the `sessions` table present) **When** it first starts after this refactor **Then** the migration step copies the database to a backup, drizzle drops `sessions` and reshapes `channel_messages`, and on the next start the step detects the new schema and no-ops.

### Batch 6 (trunk-close memory pipeline) — landed

The nightly memory maintenance is folded into the trunk-close event as a phased, idempotent pipeline
keyed on the day's branches; the five `memory-*-maintenance` crons are gone and a nightly-close cron
fires the close on idle.

**Close-pipeline module + API (`src/extensions/memory/close-pipeline.ts`)** — the PLUGGABLE SEAM
DLT-173 later replaces. Exports:
- `extractBranches(session, records, { agent, workspaceRoot }, log)` — phase 1. For each branch
  lacking an `extracted` marker, `createBranchFile(session, record.originalLeafId)` → `forkAndContinue(branchFile, branchStoreInstruction(store, …), "processor", FILE_EDIT_TOOLS)` for all three stores, sweep emptied files, `rm(branchFile, { force: true })`, then `markBranchExtracted`. Idempotent re-run skips marked branches; a null `createBranchedSession` result is logged + skipped.
- `prunePhase(session, deps)` / `consolidatePhase(session, deps)` / `coreContextStep(session, deps)` — phases 2/3 + the once-daily core-context step, each guarded by `isStepDone`/`markStepDone`; **body → marker** ordering so a crash before the marker re-runs the phase cleanly. Interim bodies: `prunePhase` reuses `maintenance.ts` (`maintenanceSystemPrompt` per store); `coreContextStep` runs `contextMaintenanceSystemPrompt`. **`consolidatePhase` is an interim marker-only no-op** (review fix): a real interim pass would just duplicate the per-store prune + the core-context update, so there is no honest interim work — DLT-173 supplies the distinct staged/atomic consolidation body behind the seam.
- `createTrunkClosePipeline({ extraction, phases })` — a single `main`-phase `PostProcessor`
  (`name: "memory-trunk-close"`) running extraction → prune → consolidate → core-context **strictly
  ordered** (a single processor, since the phased runner parallelizes within a phase). No-op when
  `ctx.trunk == null` (background runs have no day's branches).
- `CLOSE_STEPS = { prune: "memory-prune", consolidate: "memory-consolidate", coreContext: "core-context-update" }` — the per-step marker names; per-branch markers reuse `markBranchExtracted` (`topic-N`).

existing `createTranscriptArchiveProcessor` (phase `finalize`, whole-trunk archive — once-daily step

`episodicSchedule`/`factsSchedule`/`preferencesSchedule`/`contextSchedule`; `recentDays`/
`weeklyThresholdMonths`/`monthlyThresholdMonths` stay (the close pipeline's `settings`).

**`pruneTranscripts`** retention is **kept as its own deterministic cron**, renamed
`memory-transcripts-prune` (was `memory-transcripts-maintenance`), on `maintenance.transcriptsSchedule`

### Batch 7 (continuous git/projects commit) — landed

Git + projects commit is now **per-exchange (cheap, deterministic, no agent)**; the agent-grouped
commit + push stays at trunk close.

**Deterministic-commit helper** — `commitAllDeterministic({ cwd, message, log })` in
`src/git/commit.ts`. One `git add -A` + single commit, no agent, no model call; returns the subjects
made (read from git, oldest-first) or `[]` when clean. `commitAll`'s fallback path now delegates to

**Two new exchange-processor factories** (registered via `app.sessions.onExchange`):
- `createGitExchangeProcessor({ workspaceRoot, log })` — `src/extensions/git/exchange.ts`,

- `createProjectsExchangeProcessor({ workspaceRoot, git, log })` — appended to
  `src/extensions/projects/processor.ts`, `name: "projects-exchange-commit"`. Lists submodules,
  commits each dirty one deterministically via `git.commitAllDeterministic` (per-submodule
  `projectFallbackMessage`). No push (push stays at close).

rewrite):** `createGitProcessor` (finalize) and `createProjectsProcessor` (preFinalize) still run the

`--amend`/rebase). If per-exchange already committed everything, the close commit is a no-op and only
the push runs (expected). A code comment in `git/index.ts` notes the **DLT-138 interplay**: the
close-time agent commit and B6's parallel per-branch extraction both fire at trunk close → burst
side-runner load.

**Deviations:** none. The per-exchange `ExchangeContext` (`{ userText, assistantText }`, B5) is unused
