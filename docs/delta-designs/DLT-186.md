## Purpose

This document explains the design rationale for this delta: the modeling choices, data flow, system behavior, and architectural approach.

After implementation, the "Detected Impacts" section will guide reconciliation into feature design docs.

## Problem Context

Every direct dependency moves in one delta: three majors (the pi SDK 0.84.2 → 1.6.0, vitest 4 → 5, croner 10 → 11) and a set of minor and patch bumps. The version numbers are the easy part. Each major changes a contract Tachikoma relies on somewhere else:

- **Schema ownership.** One schema language serves tool parameters, `classify` output and config (ADR-003). pi-ai 0.84.2's `StringEnum` returned a TypeBox schema; 1.6.0's returns a pi-schema `Schema`, which does not type-check where a TypeBox `TSchema` is expected. Since pi 1.5.0, tool arguments are validated as JSON Schema by `@earendil-works/pi-schema`, where TypeBox features outside JSON Schema stop applying without any compile-time signal.
- **Event shape.** Since pi 1.2.0, `before_agent_start` is a union on `messageType`; `prompt` and `images` exist only on user-started runs.
- **Scheduling semantics.** croner 11 parses patterns more strictly, returns no next run for an expression that can never match, and handles DST transitions differently for fixed-time and interval jobs.
- **Lockfile policy.** pnpm 11 resolves only versions that are at least a day old, and enforces that on transitive packages and on frozen installs — but only when `minimumReleaseAge` is set explicitly. Left at its default it falls back to younger versions and records them as exclusions in `pnpm-workspace.yaml`.
- **Formatter policy.** biome 2.6 formats Markdown and YAML. Two files are read by tools that depend on their layout (`CHANGELOG.md`, `docs/planning/DELTAS.md`), and the default Markdown parser corrupts YAML frontmatter.

Constraints:

- "Latest" is gated: a version enters the lockfile only once it is a day old, and the workspace file carries no release-age exclusions.
- CI and the publish workflow run Node 24, so semantic-release 26 (Node ≥ 26.13) is held.
- `typebox` stays in lockstep with pi's pin (ADR-003).
- The test tree is not type-checked by the gate (`tsconfig.json` includes only `src`), so anything proved at type level has to live in `src`.
- Runtime acceptance over Telegram is manual, by the maintainer.

Interactions: pi's agent loop with Tachikoma's tools; pnpm with the CI workflows; biome with semantic-release, the planning script and the skill loader; croner with the task tick.

Out of scope (R16, R17): moving `SideRunner` off pi-ai's `/compat` entry, Node and system tool upgrades, adopting new pi capabilities, an automated boot smoke.

## Design Overview

The delta is a controlled move of every dependency, plus a few small, local mechanisms that keep Tachikoma's contracts intact on the other side:

1. Tachikoma owns its string-enum builder.
2. The one handler that needs the latest prompt narrows the event on `messageType`.
3. Schemas are guarded as JSON Schema, and pi's coercion of tool arguments is pinned.
4. The tooling policies — release-age gate, build decisions, formatter configuration — are written where the tools read them.

Everything else is verification and documentation. The domain model does not change: the same extensions, tools and session model run on the upgraded tree.

None. Every mechanism was run against the target versions during design; the results are in [Notes](#notes).

### Cross-Layer Contracts

**Tool schema contract**:

```
Tool parameters   a TypeBox schema that is also plain JSON Schema
Validated by      pi-schema, inside pi's agent loop, before `execute`
Coerced           numeric strings to numbers; a single value to a one-item array;
                  `null` in an optional property dropped
On failure        `execute` is not called; the model receives
                  Validation failed for tool "<name>":
                    - <path>: <message>
                  Received arguments: { … }
```

**Guard contract**: every tool parameter schema is reachable by the guard, either through the host's registries, an exported schema, or the builder that hands a headless agent its tools. The source sweep turns "a tool the guard cannot see" into a test failure.

**Workspace policy contract**: `pnpm-workspace.yaml` is the only place pnpm reads `minimumReleaseAge` and `allowBuilds`. The release-age gate never writes to it. The build review does: an install that meets a package pnpm treats as needing a build and that `allowBuilds` does not rule on writes a placeholder entry for it and, because `strictDepBuilds` is on by default, fails with `ERR_PNPM_IGNORED_BUILDS`. That is why every such package carries an explicit `true` or `false`.

**Integration Points**:

- pi's agent loop calls `validateToolArguments` (pi-ai) before a Tachikoma tool's `execute`.
- `SideRunner.classify` validates the model's answer with Tachikoma's own `parseWithSchema` (`typebox/value`), independent of pi-schema.
- `pnpm install` writes the lockfile; CI's `pnpm install --frozen-lockfile` re-verifies it against the workspace policies.
- `biome check` reads `biome.json`; excluded files are neither linted nor formatted.

**Error handling across layers**: a tool argument failure is reported to the model and the run continues; an invalid config value fails startup with `ConfigError` and per-path details; an invalid schedule is a `ScheduleError` at create or update and a logged per-definition error on the tick; a version younger than the gate fails resolution with `ERR_PNPM_NO_MATURE_MATCHING_VERSION`, and a lockfile that already contains one fails a frozen install with `ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION`. A package pnpm treats as needing a build and that `allowBuilds` does not rule on fails the install with `ERR_PNPM_IGNORED_BUILDS`, after pnpm has written a placeholder entry for it.

### Shared Logic

- **`StringEnum`**: one builder shared by the root config schema and four extensions (`notifications`, `tasks`, `workflows`, `detached-processes`). It lives in `src/util/` because `src/config` and the extensions both import it and neither may import the other (DES-002).
- **The schema guard**: one chokepoint for three schema families that are otherwise defined across the config and the extensions.

## Modeling

Schemas come in three families and meet two validators. The guard is what ties them together.

```
Schema family            Validated by                         Reached by the guard through
tool parameters          pi-schema, in pi's agent loop        the host registries (S4), pins (S10)
classify output          typebox/value, in parseWithSchema    exported schemas (S4)
config (root, extension) typebox/value, in parseWithSchema    ConfigSchema and each configSchema (S4)
```

Tool parameters are the only family that crosses into pi, so they are the only one for which "JSON Schema and nothing else" is a hard requirement. The same builder (`StringEnum`) serves all three, which is why it has to be a real TypeBox schema: `typebox/value` applies defaults and asserts against it, and pi-schema compiles it as JSON Schema.

Dependencies follow one policy from manifest to CI:

```
package.json specifier ──► newest version at least a day old ──► pnpm-lock.yaml
        │                                                             │
minimumReleaseAge: 1440 (explicit, strict)                          CI: frozen install
refuses anything younger, never writes exclusions                   re-verifies every entry
```

## Data Flow

**A tool call.**

```
model emits a tool call (loosely typed JSON)
  → pi agent loop: validateToolArguments (pi-schema)
      ├─ coerces: numeric strings, single value → array, optional null dropped
      ├─ valid    → tool.execute(coerced arguments)
      └─ invalid  → no execute; error tool result returns to the model
```

**The start of a run.**

```
before_agent_start (messageType "user" | "custom")
  → context providers read systemPrompt and systemPromptOptions; unaffected
  → skill suggestion: on "user" only — classify(latest prompt, recent conversation)
                      → hidden skill-content message, or nothing
```

**Config load.** TOML is parsed by smol-toml 1.9 (stricter parsing; the returned objects have a null prototype — smol-toml 1.9.0 release notes, 2026-09-22, observed on 1.9.1), then `parseWithSchema` runs TypeBox 1.3.27's Clone → Default → Convert → Assert pipeline. A value outside a `StringEnum` fails with `ConfigError`, listing each failing path.

**Dependency resolution.** See the diagram under Modeling. A range whose newest version is under a day old resolves to the previous one; an exact pin that is under a day old fails until the next day.

**A skill file.** `SKILL.md` is formatted by biome with its frontmatter parsed as YAML, then read by pi's loader (`parseFrontmatter`), which needs the `description` to load the skill at all.

## Key Decisions

### Tachikoma owns its `StringEnum` builder

**Choice**: `src/util/string-enum.ts` exports a `StringEnum` built with TypeBox's `Type.Unsafe` over `{ type: "string", enum, …description, …default }`, typed `TUnsafe<T[number]>`. An exported type-level assertion in the same module states that `Static` of the result is the literal union.

**Why**: It is the construction pi-ai 0.84.2 shipped, so provider payloads, config parsing and static types are unchanged, and it is a TypeBox schema in both senses needed here: pi-schema validates it as JSON Schema, and `typebox/value` defaults and asserts against it. The assertion is needed because only five of the eight enum fields in the spec feed a consumer that narrows them; with the builder's type weakened, `tsc` fails at those consumers and at the assertion, which covers the other three. Tests are not type-checked, so the assertion lives in `src`.

**Sources**: pi-ai 0.84.2 `dist/utils/typebox-helpers.js` (shipped source); pi-ai 1.6.0 `dist/utils/string-enum.d.ts`; pi CHANGELOG 1.5.0; pi 1.6.0 `docs/extensions.md` ("TypeBox schemas are JSON Schema and work unchanged"); typebox 1.3.27, executed. TypeBox's official repository, `src/type/types/unsafe.ts` and the docs pages `type/unsafe.html` and `type/enum.html`: `Unsafe` creates "user-defined schemas with user-defined inference rules", which is the freedom the self-check exists to bound.

**Alternatives Considered**:

- **pi-ai 1.6.0's `StringEnum`**: emits the same JSON but is typed as a pi-schema `Schema`, so it does not type-check inside `Type.Object` and gives no `Static` union. This is the root cause of the 21 errors the unmigrated tree reports.
- **`@earendil-works/pi-ai/compat`**: exports the same function, and the entry is documented as temporary.
- **`Type.Enum`**: emits `enum` without `type: "string"`, so the JSON differs from what providers receive today.
- **`Type.Union` of literals**: emits `anyOf`/`const`, the provider incompatibility ADR-003 rules out.
- **Taking `@earendil-works/pi-schema` as a direct dependency**: a new direct dependency that still gives no TypeBox `Static`.

**Consequences**:

- Pro: a Tachikoma-wide convention that does not depend on pi for its types; one place to change.
- Con: Tachikoma maintains the helper, and every document that named the old import has to be updated.

### `before_agent_start` handlers narrow on `messageType`

**Choice**: the skill suggestion handler returns before any work unless `event.messageType === "user"`. The other two handlers (`force-load-skills.ts`, `system-prompt-section.ts`) are unchanged; they read only `systemPrompt` and `systemPromptOptions`.

**Why**: pi 1.2.0 made the event a union. A `"custom"` run starts from `pi.sendMessage(..., { triggerTurn: true })` and has no prompt. Tachikoma starts every run itself, through `session.prompt` or `pi.sendUserMessage`, so all of its runs are `"user"` runs: the guard is a correctness guarantee, not a behavior change today.

**Sources**: pi-coding-agent 1.6.0 `dist/core/extensions/types.d.ts`; pi CHANGELOG 1.2.0.

**Alternatives Considered**:

- **Reading `prompt` through an optional access**: would classify against an empty message on a custom run and hides the union from the type checker.
- **Classifying against the custom message's content**: no requirement asks for it; the spec decides there is no suggestion on such a run.

**Consequences**:

- Pro: type-safe and explicit.
- Con: a future Tachikoma path that starts a custom-message run gets no proactive skill suggestion, by design.

### Schemas are asserted to be JSON Schema, and pi's coercion is pinned

**Choice**: one test module, `tests/schema-guard.test.ts`.

- _Registry sweep_: a stubbed `ExtensionHost` loads every first-party extension, with a placeholder Telegram config because that extension registers its tools only when a token and chat are set. Each registered factory is bound against a recording `pi`.
- _Assertions_: every captured `parameters`, the two `classify` schemas, the root and per-extension config schemas, the exported schemas of `ask_user` and `update_goal`, and the tools returned by `createCommitAgent`, `createGitResolver` and `buildProposalTools` (captured through a recording `side.run`, or built directly) survive a JSON round-trip and use only `type` values from JSON Schema.
- _Source sweep_: every tool-shaped object literal in `src` — first two properties `name`, then `label`, whether written for `registerTool`, `defineTool` or as a plain object — is either captured or listed, so a new tool the guard cannot see fails the test. Matching only `registerTool`/`defineTool` call sites was considered and not chosen: it does not see the eleven plain-object tools the headless agents carry.
- _Coercion pins_: `validateToolArguments` from `@earendil-works/pi-ai` is called with a loosely typed and a malformed call.

**Why**: pi-schema ignores TypeBox features outside JSON Schema. A `Type.BigInt()` parameter or a codec compiles, type-checks, and fails only when the model calls the tool. The JSON round-trip alone misses `{ type: "bigint" }`, hence the `type` allowlist. The registry sweep covers a new extension or tool without anyone remembering to add it.

**Sources**: pi-schema 1.6.0 README ("TypeBox 1.x schemas are JSON Schema, so they compile as they are"; coercion "ported from TypeBox 1.3.27's `Value.Convert`"); pi 1.6.0 `docs/extensions.md` ("Tool parameter schemas and TypeBox"); pi-ai 1.6.0 `dist/utils/validation.d.ts`; pi-agent-core 1.6.0 `dist/agent-loop.js`.

**Alternatives Considered**:

- **Compiling the schemas with `@earendil-works/pi-schema` in the test**: the most direct check, but the package is transitive and would become a direct dependency for a test's sake.
- **An end-to-end session test on pi's faux provider**: closest to production, but the scripted provider needs auth plumbing through pi's model runtime; abandoned in research.
- **No guard**: leaves R3 without a regression test.

**Consequences**:

- Pro: a silent runtime failure becomes a test failure.
- Con: the sweep stands on a stubbed `HostServices`, and a tool built outside a factory is checked only through an exporter the test names (an exported schema, or the builder that returns it); the tripwire is what flags a tool that has neither.
- Con: the guard reads the JSON and nothing else. A refinement (`Type.Refine`) or a codec (`Type.Codec`) is plain JSON Schema with its behavior in non-enumerable metadata, so the guard cannot see it, and pi ignores both. Such behavior needs a test of the tool's own.

### `typebox` stays at pi's pin, 1.3.27

**Choice**: exact `1.3.27`.

**Why**: lockstep (ADR-003). pi-coding-agent 1.6.0 pins exactly that version, and pi-schema's coercion is ported from 1.3.27's `Value.Convert`, so Tachikoma's own coercion and pi's tool-argument coercion come from the same release. The installed tree holds a single copy.

**Sources**: registry (`pnpm view @earendil-works/pi-coding-agent@1.6.0 dependencies` → `typebox: 1.3.27`; latest 1.4.7); typebox `changelog/1.4.0.md` ("an internal update to TypeBox's memory subsystem … Output schema generation, validation, and type inference remain unchanged").

**Alternatives Considered**:

- **1.4.7**: two TypeBox copies in the tree, and lockstep broken for no functional gain.

**Consequences**:

- Pro: one schema library instance; coercion parity with pi.
- Con: 1.4's memory improvements wait for pi.

### The release-age gate is explicit, one day, with no exclusions

**Choice**: `minimumReleaseAge: 1440` in `pnpm-workspace.yaml`; `minimumReleaseAgeExclude` removed; strict mode, which is pnpm's default once the setting is explicit. Recorded as ADR-016.

**Why**: one day is pnpm 11's built-in default, but only an explicit setting is enforced: pnpm fails resolution and never writes to the workspace file. Left implicit, it installs a younger version anyway and appends exclusion lines, which is where the five stale entries in the file come from. The gate covers transitive packages and frozen installs, so the lockfile cannot carry anything younger than a day. One day keeps "latest" within reach.

**Sources**: pnpm settings, `dependency-resolution.md` (`minimumReleaseAge`: "Default: 1440 (since v11)"; `minimumReleaseAgeStrict`: "true if `minimumReleaseAge` is explicitly configured, false otherwise") and `build.md`; pnpm 11.0 release notes; observed on pnpm 11.3.0 — `^2.6.8` locked biome 2.6.8 and left the file unchanged, and `^2.6.9` failed while 2.6.9 was under a day old.

**Alternatives Considered**:

- **The default, left implicit**: auto-writes exclusions; the policy is advisory.
- **One week**: pi 1.6.0's AWS SDK chain and grammy 1.48.0 would have kept this delta's lockfile unresolvable until 2026-11-29.
- **Per-version exclusions for reviewed packages**: around two dozen lines, mostly unreviewed transitive packages.

**Consequences**:

- Pro: the policy is visible in the file and enforced by the tool.
- Con: a release younger than a day cannot be taken until the next day, so "latest" means "latest that is a day old".

### `allowBuilds` rules on every package pnpm treats as needing a build, and on nothing else

**Choice**: `@google/genai: false`, `esbuild: true`, `protobufjs: false`, `better-sqlite3: false`.

**Why**: pnpm 11 requires a decision for every package that requires a build, and it treats a package as requiring a build when the package declares `preinstall`, `install` or `postinstall`, ships a root `binding.gyp`, or ships files under `.hooks/`. A package in that set with no entry is unreviewed: the install writes a placeholder for it into `pnpm-workspace.yaml` and fails with `ERR_PNPM_IGNORED_BUILDS`, because `strictDepBuilds` is on by default. So the list has to be exact in both directions.

In the upgraded tree the set has four packages. `esbuild` is allowed: its `postinstall` places the platform binary. The other three are denied. `@google/genai` declares a preinstall that only echoes a message, and `protobufjs` declares a postinstall Tachikoma does not need. better-sqlite3 13.2.0 declares no install script but ships a `binding.gyp`; for such a package pnpm runs `node-gyp rebuild` when the build is allowed. better-sqlite3 loads its shipped `prebuilds/<platform>-<arch>.node` before it looks at a `build/` directory, so that run is never needed here. Its entry is a denial rather than a removal.

**Sources**: pnpm 11.3.0, read in its own distribution: `pkgRequiresBuild` and `filesIncludeInstallScripts` in `dist/worker.js`; `buildModules` in `building/during-install`, `runLifecycleHook` and `checkBindingGyp` in `exec/lifecycle`, and `handleIgnoredBuilds` in `installing/commands`, all in `dist/pnpm.mjs`. pnpm `settings/build.md` (`allowBuilds`, `strictDepBuilds`). An inventory of the resolved tree. better-sqlite3 13.2.0 `package.json` and `lib/binding.js`. Three probe installs on pnpm 11.3.0, recorded under Notes.

**Alternatives Considered**:

- **Leaving `better-sqlite3` out**: a fresh install fails with `ERR_PNPM_IGNORED_BUILDS` and pnpm rewrites the workspace file with a placeholder, so the lockfile cannot be installed frozen.
- **Keeping `better-sqlite3: true`**: installs succeed, but pnpm then runs `node-gyp rebuild` on every fresh install for a package that loads its shipped binary. It is an approval the tree does not need.
- **`strictDepBuilds: false`**: the install would pass with a warning and still write the placeholder.

**Consequences**:

- Pro: least privilege. One build is allowed.
- Con: a package that pnpm treats as needing a build and that has no entry fails the install until it is ruled on, which is the point.
- Con: a denial is not reviewed again. A future version of a denied package that needs its build fails at load rather than at install, so such a failure after a bump is the signal to revisit that package's entry.

### biome 2.6 formats Markdown and YAML, parsing frontmatter; two files are excluded

**Choice**: `biome migrate`; `markdown.parser.frontmatter: true`; `files.includes` gains `!CHANGELOG.md` and `!docs/planning/DELTAS.md`; one formatting-only commit. Embed formatting and embed analysis stay at their defaults.

**Why**: the default parser treats frontmatter as Markdown and strips the block scalar's indentation, which leaves a skill unloadable. With frontmatter parsing on, the two built-in skills' frontmatter is byte-identical after formatting and the real-loader test passes. The two excluded files are the ones a tool reads by layout.

**Sources**: Biome v2.6 announcement, 2026-10-15 ("To enable frontmatter support, use the `markdown.parser.frontmatter` option"); release notes `@biomejs/biome@2.6.9`; the published 2.6.9 JSON schema, for `linter.rules` and the Markdown options; observed on 2.6.9.

**Alternatives Considered**:

- **Excluding `**/SKILL.md`**: leaves every future file with frontmatter exposed to the same corruption.
- **Disabling Markdown formatting**: forfeits the uniform formatting the spec adopts.
- **Turning embed formatting off**: the default reformats fenced `ts` snippets in two design documents and moves blank lines in the example blocks of the two built-in guides; the change is formatting only, and every page renders the same outside those blocks.

**Consequences**:

- Pro: 79 files are formatted once, and frontmatter files need no exclusion.
- Con: it relies on an off-by-default option, and biome normalizes quoting in frontmatter that is not already canonical.
- Con: embed formatting also reaches the fenced examples inside the built-in guides. Four tagged `yaml` lose the blank line between the example's frontmatter and body, and three tagged `markdown` in the workflow guide gain blank lines around headings and lists. Only whitespace moves, and a guide's own frontmatter is untouched.

### The `useMathMinMax` finding is resolved by comparing timestamps

**Why**: the recommended rule flags the ternary, and the column is a drizzle `timestamp`, typed `Date`.

**Alternatives Considered**:

- **biome's suggested rewrite**, `Math.max(max, layer.updatedAt)`: three type errors.
- **A `biome-ignore` comment**, or disabling the rule: hides the finding instead of resolving it.

### croner 11 is adopted with behavior pins and no production change

**Choice**: tests only.

**Why**: `parseSchedule` already turns any constructor throw into `ScheduleError`, and `generateDueInstances` wraps each definition in a `try`/`catch` with a logged error. croner 11's stricter parsing and its `null` for unreachable expressions need no code. What changes is behavior worth pinning.

**Sources**: croner CHANGELOG 11.0.0 (2026-10-25) and 11.0.1 (2026-11-14); executed on 11.0.1 — `3* * * * *`, `SUN6`, `JANFEB` and `*/FRI` throw `TypeError: CronPattern …`; `nextRun("0 0 30 2 *")` is `null`; a fixed-time job in the 2026-03-08 spring-forward gap in `America/New_York` fires at 03:00; an hourly job runs on both occurrences of the repeated hour on 2026-11-01.

**Alternatives Considered**:

- **Wrapping `Cron` to translate errors**: unneeded; both callers already handle a throw.
- **Staying on 10.x**: contrary to R6.

**Consequences**:

- Pro: no production risk.
- Con: for a user with a fixed-time job inside a DST gap, the job now fires at the first valid time after the gap instead of as much later as the gap is long.
- Con: for a user with an interval job inside a DST gap, the times that do not exist are now skipped instead of moved past the gap. `*/30 2 * * *` does not run at all on the day of the gap, where croner 10 gave 03:00 and 03:30, and `*/30 1-3 * * *` loses two of its six runs that day. Adopted as it is: a time that does not exist never matches, which is Vixie cron's rule (croner's README, and `crontab(5)` for Vixie cron), and `tests/tasks/schedule.test.ts` pins both.

## System Behavior

### Scenario: A tool call with loosely typed arguments

**Given**: a registered tool whose parameters include a number, an array and a `StringEnum` field.
**When**: the model sends `{ "limit": "10", "tags": "one", "severity": "warning" }`.
**Then**: `execute` receives `{ limit: 10, tags: ["one"], severity: "warning" }`.
**Rationale**: the coercion rules are ported from TypeBox 1.3.27's `Value.Convert`, so they match what config parsing does.

### Scenario: A malformed tool call

**Given**: the same tool.
**When**: the model sends a call with a missing required path and a number written as a word.
**Then**: `execute` is not called, and the model receives `Validation failed for tool "<name>": - path: missing …` followed by the arguments it sent.
**Rationale**: the model can correct the call on the next turn.

### Scenario: A schema outside JSON Schema

**Given**: a tool parameter built with a TypeBox feature that is not JSON Schema.
**When**: the schema guard runs.
**Then**: the test fails and names the tool.
**Rationale**: without the guard the failure appears only when the model calls the tool.

### Scenario: Skill suggestion on a user-started run

**Given**: a trunk session with invocable skills.
**When**: `before_agent_start` fires with `messageType: "user"`.
**Then**: the classifier receives the latest prompt and the recent conversation, as before.

### Scenario: Skill suggestion on a custom-started run

**Given**: a run started by an idle custom message.
**When**: the handler fires with `messageType: "custom"`.
**Then**: it returns without calling the classifier or showing a status line, and the run proceeds with no suggestion.
**Rationale**: there is no latest user prompt to classify against.

### Scenario: An unknown enum value in config

**Given**: a config with an unsupported thinking level.
**When**: the config loads.
**Then**: startup fails with `ConfigError`, listing the failing path.

### Scenario: A schedule croner 11 rejects

**Given**: an expression such as `SUN6 * * * *`.
**When**: a task is created or updated with it.
**Then**: the tool reports an invalid schedule and nothing is stored.

### Scenario: A stored schedule croner 11 rejects

**Given**: a task definition whose expression croner 11 no longer accepts.
**When**: the task tick runs.
**Then**: that definition is skipped with a logged error, and the remaining definitions are still evaluated.

### Scenario: A schedule that can never match

**Given**: an expression such as `0 0 30 2 *`.
**When**: its next run is computed.
**Then**: there is none; the definition generates nothing and no error is raised.

### Scenario: A fixed-time schedule inside a DST gap

**Given**: a timezone with DST, and a fixed-time job such as `30 2 * * *`.
**When**: its wall-clock time falls inside a spring-forward gap.
**Then**: it fires at the first valid time after the gap — 03:00 for a 02:30 job — not as much later as the gap is long.
**Rationale**: croner 11 aligns fixed-time jobs with Vixie cron here; croner 10 fired as much later as the gap was long.

### Scenario: An `every` job through a DST overlap

**Given**: a timezone with DST, and an `every` job.
**When**: the clock falls back and an hour repeats.
**Then**: the job keeps firing on its elapsed interval; the change neither shortens nor stretches it.
**Rationale**: croner 11 counts the `interval` option in elapsed time, and interval jobs run on both occurrences of a repeated wall-clock time.

### Scenario: A dependency version under a day old

**Given**: a range whose newest version was published under a day ago.
**When**: the lockfile is resolved.
**Then**: pnpm locks the previous version that is a day old, or fails if the range has none, and the workspace file is unchanged.

### Scenario: A fresh clone

**Given**: the upgraded lockfile.
**When**: `pnpm install --frozen-lockfile` runs.
**Then**: it succeeds with no ignored build scripts, unmet peer dependencies or engine warnings, and the policy check passes.

### Scenario: A release rewrites the changelog

**Given**: `CHANGELOG.md` excluded from biome.
**When**: semantic-release rewrites it with `*` bullets.
**Then**: `just lint` still passes.

### Scenario: After an exchange on the trunk

**Given**: a model that declares a prompt-cache lifetime.
**When**: an exchange ends and the trunk stays open.
**Then**: pi may keep the prompt cache warm for up to 30 minutes; forks and headless runs do not, because they are disposed when they finish.

### Scenario: A trunk reopened after a restart

**Given**: tools that were active before the restart.
**When**: the trunk is reopened.
**Then**: pi restores the session's active tools. Checked by the maintainer in R10.

Findings from implementing the schema guard (2026-11-25, on the upgraded tree: pi 1.6.0, pi-schema 1.6.0, pi-agent-core 1.6.0, typebox 1.3.27, vitest 5.1.1):

- The shipped docs are the official ones. `node_modules/@earendil-works/pi-coding-agent/docs/extensions.md` and the pi-schema README are byte-identical to `packages/coding-agent/docs/extensions.md` and `packages/schema/README.md` at tag `v1.6.0` of `earendil-works/pi`, and `packages/ai/src/utils/validation.ts` at that tag matches the shipped `dist/utils/validation.js`. docs.pi.dev carries the same section. A later batch can verify a pi fact from the installed package alone.
- Where the validator is called. `prepareToolCall` in pi-agent-core 1.6.0 `dist/agent-loop.js` calls `validateToolArguments(tool, preparedToolCall)` inside a `try`, after a tool's `prepareArguments` hook and before the run's `beforeToolCall` hook. A throw becomes an error tool result carrying the thrown message, so `execute` is never reached and the run continues, as the contract above states.
- `validateToolArguments`. It is synchronous and is re-exported from the pi-ai root, so `@earendil-works/pi-ai` is the import. It compiles each schema object once, with `{ formats, coerce: true, unresolvedRefs: "reject" }`, and caches the validator in a `WeakMap` keyed on the schema. It parses a `structuredClone` of the arguments, so a tool cannot change the transcript's copy. Its message is `Validation failed for tool "<name>":`, then one `  - <path>: <message>` line per error with the JSON Pointer as a dotted path, then `Received arguments:` and the arguments indented by two spaces. pi-schema writes an enum message without spaces: `expected one of ["info","warning","urgent"]`.
- What the round-trip sees, and cannot. TypeBox 1.3.27 keeps a schema's kind in non-enumerable properties, `~kind` on every schema and `~optional`, `~readonly`, `~unsafe`, `~refine` and `~codec` on some, and none of the twenty builders examined carries a symbol key. `JSON.stringify` and a strict deep-equal both ignore them, so every TypeBox schema survives the round-trip. That is also the limit. `Type.Refine(...)` and `Type.Codec(...)` serialize as the schema they wrap, with the refinement or the codec in metadata, where pi-schema never looks.
- What the allowlist rejects. Eight TypeBox 1.3.27 builders emit a `type` JSON Schema does not define, and all eight survive the round-trip: `Type.BigInt()` gives `bigint`, `Type.Constructor()` `constructor`, `Type.Function()` `function`, `Type.Generic()` `generic`, `Type.Rest()` `rest`, `Type.Symbol()` `symbol`, `Type.Undefined()` `undefined` and `Type.Void()` `void`. pi-schema gives `bigint` and `undefined` meaning for values built in code, and its own builder has `bytes`. A model's arguments are JSON, so pi's doc is exact: such a parameter "reject[s] every argument".
- A parameter named `type`. `create_task` and `run_task_now` each take a `type` parameter, so their schemas hold `properties: { type: { type: "string", enum: [...] } }`. The guard counts a `type` as a keyword only when its value is a string or an array of strings. Across the 42 registered tools, only `array`, `boolean`, `number`, `object` and `string` are declared.
- Config schemas meet a different validator first. The host parses each extension's section against its `configSchema` at load, through `typebox/value`, where a `BigInt` is an ordinary type. A required one fails startup with a `ConfigError` naming the missing property, before any schema guard runs. An optional one loads, and only the guard objects. JSON Schema is a hard requirement for tool parameters alone, as the Modeling table says. For config the guard holds a convention.
- One name, several schemas. `read_file` is built by the commit agent and by the proposal agent, and `git` by three builders, each with its own parameters. A guard that compared names would check one `git` and let two through. A `Type.BigInt()` in the proposal agent's `read_file` is reported against `buildProposalTools` while the commit agent's `read_file` still passes.
- The capture is the weak point, and the sweep covers it. The registries hold 30 main factories and 14 background ones, and `subagentFactories` is empty. `notify_user` is registered for background runs only. With the Telegram placeholder removed from the stub, or with only the main list bound, nothing else fails, and the sweep lists exactly the tools that went unreachable: the five Telegram tools, and `notify_user`.
- vitest 5 clears mock history before each test. What a test learns from a mock, such as which extensions loaded, is read where the mock is called, in `beforeAll`.

Findings from implementing the croner pins (2026-11-25, on the locked tree: croner 11.0.1, vitest 5.1.1; compared with croner 10.0.1, the version on `master`, which was taken from the registry and checked against the integrity hash in `master`'s lockfile):

- Which expressions croner 11 rejects and 10.0.1 accepted. Of 44 tried, 16 changed that way, in four classes. What 10.0.1 made of each example is its next run from `2026-06-01T12:00:00Z` in Buenos Aires.
  - A number with something after it. `3* * * * *` ran every minute at the third second, and `0 3* * * *` ran daily at 03:00.
  - A day or month name next to a digit. 10.0.1 replaced the name by its number, so `0 0 * * SUN6` ran every Saturday at midnight and `0 0 * JANFEB *` ran daily in December.
  - An `L` that is not a value of its own in day-of-month. 10.0.1 dropped it, so `0 0 5L * *` ran on the 5th of the month.
  - A second `#`, or an `L`, on a day of week that already carries one. `0 0 * * 5##2` ran every Friday.
- Expressions both versions reject. `SUN6 * * * *`, `JANFEB * * * *` and `*/FRI * * * *` have a name in the minute field, and `15W5 * * * *` a weekday modifier there. Neither version allows one there, and 10.0.1 rejects them with the message 11.0.1 has. The changelog's "these patterns throw now" describes 11.0.1 against 11.0.0. Of the seven rejected expressions the plan listed, `3* * * * *` is the only one that changed. That is why the tests also use `0 0 * * SUN6`: a definition stored before the upgrade can carry it.
- What a rejected stored definition looks like. croner reads a stored expression in one place, the tick. `parseSchedule` is called from the two tool handlers. The legacy import has a function of the same name that does not call croner, and nothing validates definitions at startup. A definition whose expression is now rejected stays enabled, `list_tasks` shows it as enabled, and it never fires. The tick logs "error processing definition" for it once a minute. Whether to surface that is a decision for the tasks feature.
- Where the facts about 11.0.1 are. The npm package carries no changelog. Its README and `dist/croner.d.ts` are complete for 11.0.1. The documentation site's pattern page agrees with them on DST handling, but does not yet mention `fixedTimeRule` or the two stricter parsing rules. The changelog at tag `11.0.1` on GitHub holds the two sections the decision above cites, dated 2026-11-14 and 2026-10-25.
- The two kinds of job. `CronPattern.isFixedTime` is true when seconds, minutes and hours each have no `*`, no `/`, and exactly one value. `30 2 * * *` and `0 9 * * *` are fixed-time jobs. `0 * * * *` is an interval job, because its hour is a wildcard, and so is every pattern with a step.
- What changed across a transition in `America/New_York`. Each cell gives the runs on 10.0.1 and then on 11.0.1.

  | Pattern and kind           | Spring forward, 2026-03-08                                                                                                      | Fall back, 2026-11-01                                        |
  | -------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
  | `30 2 * * *`, fixed-time   | 07:30Z, now 07:00Z                                                                                                              | not tried                                                    |
  | `0 9 * * *`, fixed-time    | the same on both                                                                                                                | the same on both                                             |
  | `30 1 * * *`, fixed-time   | not tried                                                                                                                       | the same on both: the first occurrence only                  |
  | `0 * * * *`, interval      | not tried                                                                                                                       | from 00:59, 05:00Z and 07:00Z, now 05:00Z, 06:00Z and 07:00Z |
  | `*/15 * * * *`, interval   | not tried                                                                                                                       | from 01:30, 05:45Z then 07:00Z, now every 15 minutes         |
  | `*/30 2 * * *`, interval   | 07:00Z and 07:30Z, now not that day                                                                                             | not tried                                                    |
  | `*/30 1-3 * * *`, interval | from midnight, 06:00Z, 06:30Z, 07:00Z and 07:30Z on both; 10.0.1 then lists 07:00Z again, 11.0.1 goes on to 05:00Z the next day | not tried                                                    |

  Outside a transition, `0 9 * * *`, `*/15 * * * *`, `0 0 * * 1` and `30 2 14 * *` give the same instants on both versions.
- The gap day of an interval job on the timer path. A job on `*/30 2 * * *`, registered at 06:59Z on 2026-03-08, fires on 11.0.1 at 06:00Z the following day and not before. On 10.0.1 under vitest's fake timers it fired once, at 07:00Z, where its `nextRuns()` gives 07:00Z and 07:30Z. Replaying to that next run takes about 0.7 seconds, because croner re-arms a timer every 30 seconds. The hour after the gap takes about 80 milliseconds, and that window is what `tests/scheduler.test.ts` pins.
- `0 0 30 2 *` already had no next run on 10.0.1. `nextRun()` returned `null` and `nextRuns()` an empty list there too. What 11.0.0 changed is that `previousRuns()` stops throwing for it. Tachikoma does not call that.
- How the `interval` option spaces an `every` job. The first fire is the next whole second after registration. Only the later fires are spaced, each `interval` seconds of elapsed time after the previous run. A job registered at 05:59:00Z with `interval: 1800` fires at 05:59:01, 06:29:01 and so on through the repeated hour. A 24-hour interval stays 86 400 seconds across spring-forward. By the changelog, 10.0.1 gave 23 or 25 hours.
- A `Cron` built without a callback arms no timer. Its constructor calls `schedule()` only when it is given a function, so `parseSchedule` and `nextCronRun` leave nothing running behind them.
- Tachikoma's own jobs under these rules. Three are fixed-time jobs in the configured timezone: `trunk-nightly-close`, `memory-transcripts-prune` and `self-update-check`, at `0 4 * * *`, `50 3 * * *` and `0 10 * * *` by default. None is inside the 02:00 to 03:00 gap that Europe and North America have. The other three are `every` jobs, among them `tasks-tick` every 60 seconds, and they now keep their elapsed interval across a transition.
- croner 10.0.1 under vitest's fake timers. Hours of fake time took seconds of real time, and an interval job did not get through the repeated hour inside a 5-second test. The same probes on 11.0.1 finish in about two seconds. That agrees with the timer fix in the 11.0.0 changelog and was not taken further. The 10.0.1 values above come from `nextRuns()`, which uses no timer.

Findings from implementing the biome batch (2026-11-25, on the locked tree: biome 2.6.9, vitest 5.1.1; the hazards were reproduced in copies of the tree outside the worktree, never in it):

- What `biome migrate --write` writes on 2.6.9. Two changes and nothing else: `$schema` becomes the URL of the locked version, and `linter.rules.recommended: true` becomes `linter.rules.preset: "recommended"`. In the published schema `recommended` is deprecated and will be removed in the next major version, and `preset` takes `recommended`, `all` or `none`, with `recommended` as its default. A second run reports no migration needed.
- What the default Markdown parser does to a skill, and what pi does with it. `check --write` inserts a blank line after the opening `---` and removes the block scalar's indentation, so the description's text follows `description: |` at column 1. pi's `extractFrontmatter` hands everything between the two `---` lines to the `yaml` parser, which throws `Implicit map keys need to be followed by map values at line 4, column 1`. `loadSkillFile` returns no skill for the file. Because the file is named `SKILL.md`, it also records that message among the loader's diagnostics. With `markdown.parser.frontmatter` on, the block is parsed as YAML, and both guides' frontmatter is byte-identical after formatting.
- What `formatEmbeds` reaches. A fence tagged `ts`, `json`, `jsonc`, `yaml` or `markdown` is formatted with that language's formatter. A fence that does not parse is left as written, and no diagnostic reports it. An embed takes the top-level `formatter.lineWidth`, and `markdown.formatter.lineWidth` does not reach it: a plain 102-character line in a `ts` fence is wrapped under 100 and not under 120. Here that added a trailing comma and a semicolon in two design documents, and moved blank lines in the guides' examples: three `markdown` examples in the workflow guide gained lines around headings and lists, and four `yaml` examples across both guides lost the line after their `---`. A block that must stay verbatim needs a tag biome does not format, such as `text`.
- How the formatting commit was reviewed. Every changed Markdown file was rendered before and after with the repository's `markdown-it`. Outside code the HTML is the same in all 79, and every inline code span is the same text. That holds for four spans whose padding biome removed: it takes one leading and one trailing space off a code span that has both, as CommonMark does when it renders one. Outside embeds the diff is table padding, blank lines around lists and tables, emphasis written with `_` instead of `*`, and one pair of quotes in `pnpm-workspace.yaml`.
- What stays out of the formatter without an exclusion. `pnpm-lock.yaml` is in biome's own ignore list: named on the command line, it is reported as a path that was provided but ignored. With `vcs.useIgnoreFile` on, biome reads the repository's ignore files and not the global exclude file. A path that only the global file ignores is processed, as a probe with three files showed, and an entry in the repository's `.gitignore` is what keeps a file out. A checkout can hold such a file, and `check --write` would reformat it.
- `pnpm-workspace.yaml` under both tools. The formatter writes the scoped key with double quotes. pnpm reads it the same: a frozen install exits 0, `pnpm ignored-builds` lists the three denied packages, and a no-op install leaves the file as it is. pnpm does write the file on the paths the decisions above record, the build review's placeholder and the exclusions of an implicit gate, and what it writes there is not the formatter's layout. The file on `master`, which pnpm had written, used single quotes, and the placeholder it writes for an unruled package is unquoted. A tree where that has happened needs `just fmt`, and its install has failed in any case.
- `useMathMinMax` on a `Date`. biome's unsafe fix lints clean and fails `tsc` with three errors: `TS2769` and `TS2345` on the rule's line, and `TS2365` on the comparison below it. Comparing milliseconds leaves one difference, on a timestamp that does not parse. `Math.max` then returns `NaN` and the comparison is false, so the subtree is kept, where the ternary ignored that row. The application writes valid dates only.
- A resolving install re-resolves more than the bumped package. With only `@biomejs/biome` changed in the manifest, `pnpm install` also moved `vite@8.0.16`'s `picomatch` from 4.0.5 to 4.0.7. The package was already in the lockfile as the resolution of `vitest@5.1.1`, and it was published on 2026-08-24, so nothing entered the lockfile and the release-age gate played no part. A resolving install's lockfile diff is read whole, and not as the bumped package's entries.
