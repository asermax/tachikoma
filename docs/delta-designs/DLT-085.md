# Design: DLT-085 - Tracked Schema Migration System

**Delta Spec**: [../delta-specs/DLT-085.md](../delta-specs/DLT-085.md)
**Status**: Draft

## Purpose

This document explains the design rationale for replacing the monolithic pragma-based migration system with a tracked migration registry. It covers the modeling choices, data flow, system behavior, and architectural approach.

After implementation, the "Detected Impacts" section will guide reconciliation into feature design docs.

## Problem Context

`database.py`'s `_run_migrations()` is 264 lines of pragma-based checks — each one queries `pragma_table_info` or `sqlite_master` to detect whether a column/table exists before conditionally running ALTER TABLE or CREATE TABLE. This pattern has accumulated ~20 checks across 6 tables (sessions, task_instances, task_definitions, detached_processes, workflow_states, plugin_state).

Problems with this approach:
- **Linear growth**: Every schema change adds another pragma check block (~8-12 lines)
- **Startup cost**: 20+ pragma queries execute on every launch, even when no changes are pending
- **No tracking**: There's no record of which migrations have been applied — the system re-checks everything every time
- **Maintenance burden**: The method is hard to read, hard to test, and interleaves model imports with migration logic

Constraints:
- Must work with SQLite (aiosqlite driver) — supports transactional DDL
- Must preserve the existing `create_all()` for ORM-defined tables
- Must be forward-only (no rollback support) — per R8, no Alembic dependency
- Must handle both fresh installs and existing installations with no `schema_migrations` table
- Must integrate with the existing bootstrap hook pattern (DES-003)
- Concurrency is not a concern — the application follows a single-process deployment model (per ADR-007)

## Design Overview

Replace the pragma checks with a tracked migration system built from three components:

1. **`schema_migrations` table** — records which revisions have been applied (revision, name, applied_at)
2. **Migration registry** — ordered list of `Migration` dataclasses in a dedicated module, each pointing to a SQL file
3. **Migration runner** — queries applied revisions, diffs against the registry, executes pending migrations in order

The existing `create_all()` call remains for ORM-defined tables. All current pragma checks are consolidated into a single initial migration (`001`) that is stamped as applied without executing — it serves as a historical baseline. Future migrations follow the same pattern: add a SQL file, add a `Migration` entry, and the runner picks it up on next startup.

## Shape

| Part | Mechanism | Flag |
|------|-----------|:----:|
| **S1** | `schema_migrations` table: `revision` (VARCHAR PK), `name` (VARCHAR), `applied_at` (DATETIME). Created with `CREATE TABLE IF NOT EXISTS` before any migration logic. | |
| **S2** | `Migration` dataclass: `(revision, name, sql_path)`. Registry is an ordered list in `src/tachikoma/database_migrations.py`. No `down_revision` — forward-only, ordering is positional. | |
| **S3** | Migration runner: query applied revisions, diff against registry, execute pending in order. Each migration reads its SQL file, executes statements, and stamps the revision within a single atomic transaction. Stamp initial without execution for both fresh and existing installs. | |
| **S4** | Initial migration (`001_initial.sql`): all current ALTER TABLE / CREATE TABLE SQL from the pragma checks. Never auto-executed — stamped as applied. Lives at `src/tachikoma/migrations/001_initial.sql`. | |
| **S5** | Existing DB detection: if `schema_migrations` is empty after creation, check whether core tables exist. If yes → existing install, stamp `001` as applied. If no → fresh install, `create_all()` runs first, then stamp `001` as applied. | |
| **S6** | Remove all pragma-based checks from `_run_migrations()`. Replace with: `create_all()` → create `schema_migrations` → detect fresh vs existing → stamp `001` → run pending migrations. | |

## Components

### Implementation Structure

| Layer/Component | Responsibility | Key Decisions |
|-----------------|----------------|---------------|
| `database_migrations.py` | Defines `Migration` dataclass and ordered registry list | Separate module from `database.py` to isolate migration definitions |
| `migrations/*.sql` | SQL files containing migration statements | One file per migration, loaded at runtime by the runner |
| `database.py` (modified `_run_migrations`) | Engine lifecycle + migration orchestration | Retains `create_all()`, delegates to migration runner |
| `schema_migrations` table | Persistence layer for applied revision tracking | Created before any migration logic via `CREATE TABLE IF NOT EXISTS` |

### Cross-Layer Contracts

**Integration Points**:
- `database.py` imports the registry from `database_migrations.py` and passes the engine to the migration runner
- The runner reads SQL files from `src/tachikoma/migrations/` using `importlib.resources.files()` for static file loading — ensures compatibility with packaged installations
- The runner uses the same `AsyncEngine` connection context as the existing `_run_migrations()`
- Error handling: migration failure raises `RuntimeError` with revision ID and name, propagating to the bootstrap hook which aborts startup

### Shared Logic

- `Migration` dataclass is the single source of truth for migration metadata — used by both the runner (to execute) and the registry (to define)
- SQL file loading is encapsulated in the runner — `database.py` never handles SQL file paths directly

## Modeling

### Migration Dataclass

```python
@dataclass(frozen=True)
class Migration:
    revision: str   # e.g., "001", "002"
    name: str       # e.g., "initial_schema", "add_session_notes"
    sql_path: str   # relative path under src/tachikoma/migrations/
```

Frozen because migrations are immutable definitions — the registry is a constant.

### schema_migrations Table

```sql
CREATE TABLE IF NOT EXISTS schema_migrations (
    revision VARCHAR NOT NULL PRIMARY KEY,
    name VARCHAR NOT NULL,
    applied_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
)
```

Minimal schema — only tracks what was applied and when. No down-revision, no checksum (trust the registry as source of truth).

## Data Flow

### Startup Migration Flow

```
database.initialize()
  └─ _run_migrations()
       ├─ import model modules (existing)
       ├─ conn.run_sync(Base.metadata.create_all)
       │    └─ creates all ORM tables + schema_migrations (if new)
       ├─ ensure schema_migrations exists (CREATE TABLE IF NOT EXISTS)
       ├─ query: SELECT revision FROM schema_migrations
       ├─ if no revisions applied:
       │    ├─ check if sessions table exists
       │    ├─ if yes → existing install: stamp "001" as applied
       │    └─ if no → fresh install: (create_all already ran) stamp "001" as applied
       ├─ diff: registry - applied = pending
       ├─ for each pending migration (in order):
       │    ├─ read SQL file
       │    ├─ begin transaction
       │    ├─ execute all statements
       │    ├─ INSERT INTO schema_migrations
       │    ├─ commit (auto via engine.begin())
       │    └─ log: "Applied migration {revision}: {name}"
       └─ if no pending: log "Schema is up to date"
```

### Adding a New Migration (Developer Flow)

1. Create `src/tachikoma/migrations/002_descriptive_name.sql` with ALTER/CREATE statements
2. Add `Migration("002", "descriptive_name", "migrations/002_descriptive_name.sql")` to the registry list in `database_migrations.py`
3. On next startup, the runner detects "002" as pending and executes it

## Key Decisions

### Separate SQL Files per Migration

**Choice**: Each migration's SQL lives in its own `.sql` file under `src/tachikoma/migrations/`
**Why**: Keeps the registry module clean (just metadata), makes SQL reviewable in isolation, and avoids embedding large multi-line strings in Python.
**Alternatives Considered**:
- Inline SQL strings in the registry: simpler for tiny migrations but clutters the module and makes the initial migration (which consolidates 264 lines of SQL) unwieldy
- A single SQL file with revision delimiters: harder to parse, easier to accidentally mix revisions

**Consequences**:
- Pro: Clean separation of metadata and SQL, easy to review in PRs
- Con: One more file to create per migration, need to resolve SQL file paths at runtime

### Forward-Only with No down_revision

**Choice**: No `down_revision` field, ordering is purely positional in the registry list
**Why**: The system is forward-only (no rollback support). Alembic-style chain linking adds complexity with no benefit when downgrades aren't supported. Sequential revision IDs (`"001"`, `"002"`) make ordering self-evident.
**Alternatives Considered**:
- Alembic-style `down_revision` chain: useful for detecting branching but unnecessary without downgrade support
- Timestamp-based ordering: less readable than sequential IDs for a system with infrequent migrations

**Consequences**:
- Pro: Simpler `Migration` dataclass, simpler runner logic, no chain validation needed
- Con: Cannot detect if registry entries are accidentally reordered (mitigated by sequential IDs being self-documenting)

### One Transaction per Migration

**Choice**: Each migration runs in its own `async with engine.begin() as conn:` block
**Why**: Per R7, a failing migration must not partially apply. SQLite supports transactional DDL, so a single transaction per migration guarantees atomicity. Separate transactions mean a successfully applied migration (e.g., `002`) is preserved even if `003` fails — on restart, only `003` is re-attempted.
**Alternatives Considered**:
- Single transaction for all pending: would roll back all on failure, requiring re-execution of successful ones on restart
- No explicit transactions (autocommit): would leave partial state on failure

**Consequences**:
- Pro: Clean failure semantics — only the failed migration is re-attempted
- Con: Slightly more transaction overhead (negligible for SQLite with <10 pending migrations)

### Stamp Initial Migration Without Execution

**Choice**: Migration `001` is stamped as applied without executing its SQL for both fresh and existing installs
**Why**: For fresh installs, `create_all()` already creates the current schema. For existing installs, the changes are already present. The SQL file exists as historical documentation of what the initial state represents, not as executable code.
**Alternatives Considered**:
- Execute the initial migration for fresh installs: redundant since `create_all()` already creates the tables, and would require maintaining two sources of truth (ORM models + SQL file)
- Skip the initial migration entirely and start the registry at `002`: loses the historical record of what was consolidated

**Consequences**:
- Pro: No risk of the initial SQL drifting out of sync with ORM models
- Con: The `001_initial.sql` file must be maintained as a reference document (acceptable since it's frozen)

### Existing Install Detection via Core Table Check

**Choice**: When `schema_migrations` is empty, check if the `sessions` table exists to distinguish fresh vs existing installs
**Why**: `sessions` is the oldest and most fundamental table — if it exists, the database was created before the migration system. This is a one-time check that only fires on the first launch after the migration system is introduced.
**Alternatives Considered**:
- Check `sqlite_master` for any table count: less precise, could match any SQLite database
- Check for `schema_migrations` existence (not emptiness): doesn't work since `CREATE TABLE IF NOT EXISTS` creates it for fresh installs too

**Consequences**:
- Pro: Simple, reliable one-time detection
- Con: Couples detection to the `sessions` table name (acceptable — it's a core table that won't be removed)

### SQL File Loading via importlib.resources

**Choice**: Use `importlib.resources.files()` to load SQL files from the `tachikoma/migrations/` package
**Why**: Works correctly when the package is installed (not just when running from source). `pathlib`-relative resolution would break in packaged installations where the source tree doesn't exist.
**Alternatives Considered**:
- `pathlib.Path(__file__).parent / "migrations"`: works in development but may fail when packaged as a wheel
- Embedding SQL as module-level string constants: defeats the purpose of separate files

**Consequences**:
- Pro: Reliable in both development and packaged installations
- Con: Requires `migrations/` to contain an `__init__.py` (or use the `importlib.resources` namespace package convention)

## System Behavior

### Scenario: Fresh Installation

**Given**: No `tachikoma.db` file exists
**When**: `initialize()` runs
**Then**: `create_all()` creates all ORM tables including `schema_migrations`, the runner detects an empty `schema_migrations` table, finds no `sessions` table (fresh install), stamps `001` as applied, and logs "Schema initialized (fresh install). Migration 001 stamped."
**Rationale**: `create_all()` is the source of truth for fresh schema — the migration system only needs to record the baseline.

### Scenario: Existing Up-to-Date Installation

**Given**: A `tachikoma.db` with all current schema changes applied but no `schema_migrations` table
**When**: `initialize()` runs
**Then**: `create_all()` is a no-op (tables exist), `schema_migrations` is created, the runner detects it's empty but `sessions` exists (existing install), stamps `001` as applied, and logs "Schema initialized (existing install). Migration 001 stamped."
**Rationale**: No schema changes needed — just bring the existing database into the tracking system.

### Scenario: Existing Installation with Pending Migration

**Given**: A `tachikoma.db` with `schema_migrations` showing `001` applied, and a new `002` migration in the registry
**When**: `initialize()` runs
**Then**: The runner queries applied revisions (`["001"]`), diffs against the registry, finds `002` pending, reads `002_*.sql`, executes it in a transaction, stamps `002`, and logs "Applied migration 002: descriptive_name"
**Rationale**: Only the new migration executes — fast startup with no pragma checks.

### Scenario: Migration Failure

**Given**: A pending migration `003` with SQL that contains an error (e.g., references a non-existent column)
**When**: The runner executes migration `003`
**Then**: The transaction rolls back, `003` is not stamped, a `RuntimeError` is raised identifying migration `003` by revision and name, and startup aborts
**Rationale**: Fail-fast per R7 — no partial application, clear error message, retry on next launch.

### Scenario: Second Launch After Stamping

**Given**: A database where `001` was just stamped
**When**: `initialize()` runs again
**Then**: The runner queries applied revisions, finds `001`, diffs against registry (only `001` registered), finds no pending migrations, and logs "Schema is up to date"
**Rationale**: No-op on restart — the pragma checks are eliminated, only a single `SELECT revision FROM schema_migrations` query runs.

## Notes

- SQLite's transactional DDL means CREATE TABLE, ALTER TABLE, DROP TABLE all participate in transactions — no special handling needed
- `CREATE TABLE IF NOT EXISTS schema_migrations` is idempotent in SQLite — safe to call on every startup
- The `sessions` table was introduced in the earliest version of the project and is guaranteed to exist in any non-fresh database
