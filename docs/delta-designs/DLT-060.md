# Design: DLT-060 - Check for agent updates and notify user

**Delta Spec**: [../delta-specs/DLT-060.md](../delta-specs/DLT-060.md)
**Status**: Draft

## Purpose

This document explains the design rationale for this delta: the modeling choices, data flow, system behavior, and architectural approach.

After implementation, the "Detected Impacts" section will guide reconciliation into feature design docs.

## Problem Context

Tachikoma runs as a long-lived process that users interact with via Telegram or REPL. When a new version is published to PyPI, users have no way to discover it without manually checking. This delta adds periodic background version checking and user notification.

Constraints:
- Must integrate with the existing central scheduler (DES-010) — not its own loop
- Must use the existing event bus notification system — not a bespoke delivery mechanism
- Must persist dedup state across restarts via the database (ADR-013)
- Must follow the config pattern for `[updates]` settings (Pydantic, TOML)
- HTTP client must work in the existing async stack — `urllib.request` from stdlib suffices for a single periodic JSON fetch

## Design Overview

A lightweight update checker subsystem composed of:

1. **Version checker** — fetches PyPI metadata, compares versions, decides whether to notify
2. **Scheduled job** — runs the checker at a configurable interval via the central scheduler
3. **Config section** — `[updates]` in TOML with `enabled` and `check_interval`
4. **Bootstrap hook** — registers the scheduled job when enabled
5. **MCP tool** — `check_updates` for on-demand checks by the agent

The subsystem is minimal: one module (`src/tachikoma/updates/`) with a tick function, a PyPI fetcher, an MCP tool, and a bootstrap hook. It closes over the `AppStateRepository`, `EventBus`, and settings — no new long-lived objects beyond what the scheduler already manages.

## Shape

| Part | Mechanism | Flag |
|------|-----------|:----:|
| **S1** | Scheduled job in the central scheduler with `IntervalTrigger(check_interval)`, calling the update checker tick | |
| **S2** | PyPI version fetcher: `GET https://pypi.org/pypi/tachikoma-agent/json` with `User-Agent` header. ETag/`If-None-Match` caching is a future enhancement (deferred from initial implementation). | |
| **S3** | Version comparison using `packaging.version.Version`: read installed version via `importlib.metadata.version()`, parse `info.version` from PyPI response, filter pre-releases via `is_prerelease`/`is_devrelease` | |
| **S4** | Dedup via `app_state` table (ADR-013): read/write `updates.last_notified_version` key | |
| **S5** | Notification dispatch: `dispatch_notification()` via event bus at Normal priority, message includes current and available version | |
| **S6** | `[updates]` config section in TOML: `enabled` (bool, default true) and `check_interval` (int seconds, default 86400). When the section is absent from TOML, Pydantic's `default_factory` applies these defaults — consistent with how all other settings sections work (e.g., `TaskSettings`, `AgentSettings`). | |
| **S7** | Bootstrap hook (`updates_hook`): create `AppStateRepository` from the shared `Database.session_factory` (retrieved from `ctx.extras["database"]`), store in `ctx.extras["app_state_repository"]`. Job registration happens in `__main__.py` after bootstrap completes. | |
| **S8** | MCP tool `check_updates`: on-demand version check returning structured result — reuses `check_for_update()`. Returns `UpdateCheckResult` fields as a dict (no side effects: no notification, no dedup update). Follows DES-006 with an empty Pydantic args model. | |

### Cross-Layer Contracts

**Update check result** (internal, used by both tick and MCP tool):
```python
@dataclass(frozen=True)
class UpdateCheckResult:
    current_version: str
    latest_version: str | None  # None when PyPI unreachable
    update_available: bool
    latest_is_prerelease: bool
```

**Integration Points**:
- Tick function → `AppStateRepository` (dedup), `EventBus` (notification), settings (interval, enabled)
- MCP tool → same `check_for_update()` function, returns structured dict instead of dispatching notification
- Config → `UpdatesSettings` consumed by hook (to decide whether to register) and tick (for interval)

## Modeling

```
UpdatesSettings (Pydantic, frozen)
├─ enabled: bool = True
└─ check_interval: int = 86400

UpdateCheckResult (frozen dataclass)
├─ current_version: str
├─ latest_version: str | None
├─ update_available: bool
└─ latest_is_prerelease: bool

app_state table (SQLAlchemy)
├─ key: str (PK)     ← "updates.last_notified_version"
├─ value: str        ← e.g. "1.45.0"
└─ updated_at: datetime
```

## Data Flow

### Scheduled check flow

```
Scheduler tick
  → check_for_update()
    → urllib.request: GET https://pypi.org/pypi/tachikoma-agent/json
      (with User-Agent header)
    → parse response: info.version
    → importlib.metadata.version("tachikoma-agent")
    → packaging.version.Version comparison
      → filter prerelease/dev versions
    → compare: latest > current AND latest NOT prerelease?
      → YES: read app_state "updates.last_notified_version"
        → if app_state.get() raises: log warning, skip notification
        → if latest != last_notified:
          → dispatch_notification(bus, "Update available", ...)
          → app_state.set("updates.last_notified_version", latest)
        → else: skip (already notified for this version)
      → NO: no action, debug log only
```

### MCP tool flow

```
Agent invokes check_updates tool
  → check_for_update()
    → same fetch + compare logic
  → return UpdateCheckResult as dict:
      {
        "current_version": "1.42.0",
        "latest_version": "1.43.0" | null,
        "update_available": true/false,
        "latest_is_prerelease": false
      }
```

### Startup flow

```
Bootstrap: updates_hook (runs after database_hook)
  → database = ctx.extras["database"]  (Database instance from database_hook)
  → AppStateRepository(database.session_factory)
  → ctx.extras["app_state_repository"] = repository

__main__.py wiring (after bootstrap completes):
  → app_state_repo = bootstrap.extras["app_state_repository"]
  → read settings.updates
  → if enabled:
    → Job("update_checker", IntervalTrigger(check_interval), run=lambda: update_checker_tick(app_state_repo, bus))
    → add to jobs list
  → create_update_tools_server(app_state_repo) → add to mcp_servers
```

## Key Decisions

### HTTP client: stdlib `urllib.request` over `httpx`

**Choice**: Use `urllib.request` from the Python stdlib for the PyPI JSON fetch.
**Why**: This is a single periodic HTTP GET to a well-known endpoint — not a high-throughput or connection-pooled use case. Adding `httpx` as a direct dependency for one request every 24 hours is unjustified. `urllib.request` handles HTTPS, custom headers, and ETag/If-None-Match natively. The async tick can call it via `asyncio.to_thread()` to avoid blocking the event loop.
**Sources**:
- Python stdlib `urllib.request` docs: https://docs.python.org/3/library/urllib.request.html — supports custom headers via `Request` objects
- `packaging` library docs: https://packaging.pypa.io/en/stable/version.html — `Version` class with PEP 440 comparison
- `importlib.metadata` docs: https://docs.python.org/3/library/importlib.metadata.html — `version()` for reading installed package version
- PyPI JSON API docs: https://docs.pypi.org/api/json/ — endpoint structure and ETag caching behavior
**Options Researched**: `httpx` (full-featured async HTTP client — overkill for single periodic request), `aiohttp` (same concern), `urllib.request` (stdlib, sufficient for the task).
**Why This Over Alternatives**: Zero new dependencies. The operation is trivial (one GET, parse JSON). Connection pooling, streaming, and retry sophistication are not needed — the scheduler's own error containment handles failures at the tick level.
**Consequences**:
- Pro: No new dependency
- Pro: Stdlib is always available, no version pinning concerns
- Con: Slightly more verbose than `httpx.get()`, but the fetch function is ~20 lines

### Version comparison: `packaging.version.Version`

**Choice**: Use `packaging.version.Version` for all version parsing and comparison.
**Why**: `packaging` is already a transitive dependency (via Pydantic). It implements PEP 440 correctly, handles pre-release/dev versions (`is_prerelease`, `is_devrelease`), and supports natural ordering (`Version("1.2.0") < Version("1.3.0")`).
**Sources**: `packaging` library documentation — `Version` class with comparison operators, `is_prerelease`, `is_devrelease` properties (https://packaging.pypa.io/en/stable/version.html).
**Consequences**:
- Pro: No new dependency (already available)
- Pro: Correct PEP 440 semantics including pre-release filtering
- Con: None significant

### Dedup persistence: `app_state` table (ADR-013)

**Choice**: Persist `last_notified_version` in the general-purpose `app_state` key-value table.
**Why**: See ADR-013. The update checker's dedup state is exactly the kind of small, infrequently-written internal state the table is designed for.
**Consequences**:
- Pro: No dedicated table needed — uses shared infrastructure
- Pro: Automatically included in DB dump/restore flow (ADR-012)
- Con: Value is untyped string — the checker must handle serialization (trivial for a version string)

### Notification delivery: existing event bus at Normal priority

**Choice**: Use `dispatch_notification()` at `Priority.NORMAL` to deliver update notifications.
**Why**: The notification system already handles priority-based delivery, buffering, and channel routing. Update notifications are informational, not urgent — Normal priority is correct (delivered when the user has been idle for ~2 minutes, force-delivered after 15 minutes max hold).
**Consequences**:
- Pro: Consistent with how background tasks and other subsystems notify users
- Pro: Leverages existing priority buffer for delivery timing
- Con: None — this is the intended use of the notification system

### Config: separate `[updates]` section

**Choice**: Add `UpdatesSettings` as a new section in `Settings` with `enabled` and `check_interval`.
**Why**: Follows the established pattern (every subsystem has its own settings section). `enabled` allows users to opt out entirely. `check_interval` gives control over frequency without requiring a code change.
**Consequences**:
- Pro: Discoverable in the auto-generated config file
- Pro: Consistent with `TaskSettings`, `TelegramSettings`, etc.
- Con: Adds two more config fields, but they have sensible defaults

## System Behavior

### Scenario: New version available

**Given**: Installed version is `1.42.0`, PyPI latest stable is `1.43.0`
**When**: The scheduled tick runs
**Then**: Fetch PyPI metadata → compare versions → update available → read `app_state` → `last_notified_version` is not `1.43.0` → dispatch notification → write `1.43.0` to `app_state`
**Rationale**: One notification per new version (R4), then silence until the next version appears.

### Scenario: Already notified for this version

**Given**: Installed version is `1.42.0`, PyPI latest stable is `1.43.0`, `last_notified_version` is already `1.43.0`
**When**: The scheduled tick runs
**Then**: Fetch → compare → update available → read `app_state` → already `1.43.0` → skip notification, debug log only
**Rationale**: Dedup prevents notification spam across restarts and multiple ticks (R4).

### Scenario: Already on latest version

**Given**: Installed version matches PyPI latest stable
**When**: The scheduled tick runs
**Then**: Fetch → compare → no update available → no notification, debug log only
**Rationale**: Silent when current (R3).

### Scenario: Installed version higher than PyPI (dev build)

**Given**: Installed version is `1.44.0.dev1`, PyPI latest stable is `1.43.0`
**When**: The scheduled tick runs
**Then**: Fetch → compare → `1.43.0 < 1.44.0.dev1` → no update available → no notification
**Rationale**: Dev builds are ahead of stable — no point in notifying (R3).

### Scenario: PyPI returns a pre-release as latest

**Given**: PyPI `info.version` is `1.44.0b2` (pre-release)
**When**: The scheduled tick runs
**Then**: Fetch → detect `is_prerelease=True` → treat as no stable update → no notification
**Rationale**: Only stable releases trigger notifications (spec: version filtering AC).

### Scenario: PyPI unreachable

**Given**: Network error or DNS failure
**When**: The scheduled tick runs
**Then**: Catch exception → log at warning level → no notification → next tick retries
**Rationale**: Transient failures are expected; no point in alarming the user (spec: error handling AC).

### Scenario: PyPI response malformed

**Given**: Response is not valid JSON or missing `info.version`
**When**: The scheduled tick runs
**Then**: Catch `KeyError`/`json.JSONDecodeError` → log at warning level → no notification
**Rationale**: Defensive parsing, graceful degradation (spec: error handling AC).

### Scenario: Database error during dedup read/write

**Given**: `AppStateRepository.get()` or `.set()` raises (e.g., database locked, connection error)
**When**: The scheduled tick runs
**Then**: Catch exception → log at warning level → skip notification → next tick retries
**Rationale**: Database errors are transient and should not disrupt the scheduler. The scheduler's own error containment provides an outer safety net, but the tick catches DB errors specifically to avoid logging at ERROR for expected conditions.

### Scenario: First run (no dedup state)

**Given**: No `updates.last_notified_version` key in `app_state`
**When**: A check finds a newer version
**Then**: `app_state.get()` returns `None` → proceed with notification → write version to `app_state`
**Rationale**: First run should notify (R4 AC: no dedup state = notify).

### Scenario: Manual on-demand check

**Given**: Agent invokes `check_updates` MCP tool
**When**: Any time, regardless of schedule
**Then**: Run the same fetch + compare → return structured result → do NOT dispatch notification or update dedup state
**Rationale**: The tool answers a question; the scheduled job drives a notification. Mixing the two would cause unexpected notifications from agent queries.

### Scenario: Updates disabled

**Given**: `[updates]` section has `enabled = false`, or the section is absent (defaults to enabled)
**When**: Bootstrap runs
**Then**: If disabled: skip job registration entirely — no scheduled checks run. If absent: defaults apply (enabled=true, interval=86400) via Pydantic's `default_factory`.
**Rationale**: Clean opt-out; no wasted resources (R2). Default-on means users get update checks without any configuration.

## Notes

- ADR-013 (Key-Value Application State Table) created alongside this design
- ETag/If-None-Match caching is deferred from initial implementation — the fetch is once per day by default, so bandwidth savings are negligible. Can be added later without architectural changes.
- The MCP tool returns raw data without side effects, making it safe for the agent to call at any time
- DLT-061 (Apply agent update) will consume the update detection but is a separate delta with its own design
- Dependency chain for `AppStateRepository`: `database_hook` → `ctx.extras["database"]` → `updates_hook` creates `AppStateRepository` → `ctx.extras["app_state_repository"]` → tick function and MCP tool close over it
