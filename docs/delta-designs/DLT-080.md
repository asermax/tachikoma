## Shape

| Part | Mechanism | Flag |
|------|-----------|:----:|
| **S1** | New `skill-evolution` extension: config (`enabled` default true, `postWorkPrompt` optional), bootstrap creating `memories/skill-evolution/` and seeding the index + impact log | |
| **S2** | Shared branch-walk helper extracted from memory's close pipeline: enumerate topic records → cut branchFile → forkAndContinue with file tools → per-branch marker → cleanup; parameterized by marker store and instruction; memory refactored onto it | ⚠️ |
| **S3** | Trunk-close `main`-phase processor (runs parallel to `memory-trunk-close` via phase concurrency), fail-soft error isolation; no-`origin` gate skips the run | |
| **S4** | Reconciliation step: `git fetch`, then reachability-first classification per R1 (tip reachable from remote head → accepted; branch present → pending; else rejected) | ⚠️ |
| **S5** | Per-branch analysis fork: collect skill-usage data points, read current workspace skills, write/update pattern pages + index (agent-enforced dedup, ~50-line caps, in-run maintenance) | |
| **S6** | Skill-impact log format: per proposal — skill, pattern link, branch name, tip SHA, date, one-line description, status | |
| **S7** | Proposal agent pass — a separate agent, seeded with the analysis output (pattern pages + impact log + current workspace skills), that writes the proposal branches itself: per proposal, temporary worktree → edit files → commit → push to origin → cleanup; its input excludes rejected and still-pending patterns | ⚠️ |
| **S8** | Host safety net around the proposal agent — scoped tool surface (file tools + a git tool allowing exactly worktree/branch/push-of-new-branch, refusing pushes to the default branch and history rewrites; never the bash path); verifies outcomes from git state and records impact-log entries; guarantees no stray worktrees/branches survive a failure | ⚠️ |
| **S9** | Post-run reporter: when at least one proposal was verified, create an ad-hoc background task instance (the `run_task_now` ad-hoc path) with prompt = postWorkPrompt ?? default notification prompt, run-context summary and explicit goal baked in | ⚠️ |
| **S10** | Per-branch "analyzed" markers in the extension's own KV state (`app.state`), keyed by trunk session + branchId — no contention with memory's session-file markers | |

### Flagged Unknowns

#### S2 — shared walk parameterization and concurrency
How to parameterize the walk cleanly: memory's markers live on the trunk session file while skill-evolution's stay in KV state — what exactly is the shared surface (walk orchestration only, or also sweep/marker idioms)? Also: walk-concurrency — two processors invoking the shared walk over the same trunk simultaneously (both cutting throwaway branch files from the same source) must not corrupt each other.

#### S4 — reconciliation edges
Unreachable or missing tip SHAs after remote deletion, fetch failures, and how the remote default branch is resolved when `origin/HEAD` is unset (the workspace repo may not have a symbolic remote HEAD).

#### S7 — proposal agent surface and runner
The exact tool surface (scoped git allowlist + file tools scoped to the worktree), which runner hosts it (headless `side.run` with custom tools vs a persona-carrying fork), and whether same-skill proposals serialize within a run (each worktree branches from the same base, so same-file proposals will conflict at merge — accepted per the spec, but the run order may matter).

#### S8 — mid-proposal failure handling
What happens when the agent dies between worktree creation and push: what is retried vs. abandoned, how stray worktrees and local branches are pruned (`finally`-style guarantees), and push-denied recovery (read-only remote, missing credentials).

#### S9 — reporter plumbing
Direct use of the tasks repository (`TaskRepository.createInstance` ad-hoc path) vs. a small shared app-level API; precisely what run context is baked into the prompt; an explicit `goal` to skip the background runner's goal-extraction call.

## Notes

Research context from the spec phase (verified against the codebase): the memory trunk-close pipeline (`src/extensions/memory/close-pipeline.ts`) owns the walk recipe to extract (S2); trunk close runs at `nightlyCloseHour` (default 4) with stale recovery; phase concurrency within `main` gives parallel-with-memory semantics; no branch/worktree helpers exist in `src/git/` today (S4/S7/S8 add them); the ad-hoc background instance path is `TaskRepository.createInstance` (S9); the git bash guardrail blocks `git push`, so the proposal agent must never use the bash path for git (S8).
