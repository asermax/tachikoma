# Design: DLT-177 - Replace agentic memory search with static index injection

**Delta Spec**: [../delta-specs/DLT-177.md](../delta-specs/DLT-177.md)
**Status**: Draft

## Purpose

This document explains the design rationale for replacing the agentic memory search with static index injection: the modeling choices, data flow, system behavior, and architectural approach.

After implementation, the "Detected Impacts" section will guide reconciliation into feature design docs.

## Problem Context

The memory context provider runs an Opus sub-agent on every incoming message to classify relevance and search facts/preferences/episodic memories. This is expensive (Opus round-trip per message), unreliable (may miss or misload relevant memories), and unnecessary for structured memory types like facts and preferences where a `MEMORY.md` index already provides a navigable entry point.

**Constraints:**
- Facts and preferences directories already contain `MEMORY.md` index files maintained by the memory subsystem (bootstrap hook + maintenance ticks)
- The `MEMORY.md` format (`[Name](./path.md): description`) is stable and human-readable
- Background tasks also consume memory context through `MemoryContextProvider` in `tasks/executor.py`
- The system preamble already has a `## Memories` section that can be expanded with episodic documentation
- Episodic memory search is deferred to a future MCP tool (DLT-105) — not in scope

**Interactions:**
- Memory bootstrap hook (`memory/hooks.py`): creates directory structure and ensures MEMORY.md exists
- Context bootstrap hook (`context/loading.py`): loads foundational context (SOUL/USER/AGENTS.md) at startup
- Coordinator: saves foundational context for new sessions, runs per-message pipeline
- Task executor (`tasks/executor.py`): runs its own preprocessing pipeline that currently includes `MemoryContextProvider`
- Post-processing display (`post_processing.py`): shows "Loaded Memories" from `memory_path` metadata
- System preamble (`SYSTEM_PREAMLE_TEMPLATE` in `loading.py`): contains memory system documentation

## Design Overview

Replace the per-message Opus sub-agent with static injection of facts and preferences `MEMORY.md` indexes into foundational context at startup. The `memory_hook` stashes formatted index content in `ctx.extras["memory_indexes"]`, and `context_hook` reads from there, appending it to the foundational context list alongside SOUL/USER/AGENTS.md. The coordinator saves these entries for each new session, making them available as navigable sections in the system prompt.

The agent sees the indexes as browseable lists with one-line descriptions and file paths, and reads individual files on demand via the Read tool when the index suggests relevance. No per-message search or classification is needed — the static context is always present.

The entire `MemoryContextProvider` class and supporting infrastructure are removed from both the main pipeline and the background task executor. The task executor gets a lightweight inline injection of memory indexes into its enriched prompt (reading the same MEMORY.md files directly, without a provider class).

The system preamble's existing `## Memories` section is expanded with episodic memory documentation (naming conventions, retention tiers, content expectations, when to consult) so the agent knows what episodic files exist without any search mechanism.

### Cross-Layer Contracts

**Integration Points:**
- `memory_hook` → `ctx.extras["memory_indexes"]` → `context_hook` → foundational context list → coordinator saves as `SessionContextEntry`
- `load_memory_indexes()` in `tasks/executor.py` → `ContextResult` entries → enriched prompt via `assemble_context()`
- `SYSTEM_PREAMLE_TEMPLATE` → `render_system_preamble()` → `build_system_prompt()` → agent sees episodic documentation

**Error handling:**
- `memory_hook`: missing/empty MEMORY.md → skip silently; malformed entries → skip with debug log, include well-formed ones
- `context_hook`: no `memory_indexes` in extras → skip (memory_hook ran first but found nothing)
- `tasks/executor.py`: `load_memory_indexes()` failure → caught in `_run_preprocessing()`'s existing try/except, falls back to original prompt
- `post_processing.py`: memory display code removed entirely — no `memory_path` metadata to display

### Shared Logic

- **`format_memory_index(memory_type, raw_content)`** — shared function that formats a MEMORY.md file's raw content into an injectable section with header, description, and entries. Used by both `memory_hook` (during bootstrap) and `load_memory_indexes()` (during task preprocessing). Defined in `memory/index.py` alongside existing index logic.
- **`load_memory_indexes(workspace_path)`** — reads and formats both facts and preferences MEMORY.md files, returns `list[tuple[str, str]]` of `(owner_tag, formatted_content)` pairs. Used by `memory_hook` and the task executor.

## Modeling

```
Bootstrap Flow (startup):
  memory_hook(ctx)
    ├── Reads memories/facts/MEMORY.md
    ├── Reads memories/preferences/MEMORY.md
    ├── Formats each via format_memory_index()
    └── ctx.extras["memory_indexes"] = [(tag, content), ...]

  context_hook(ctx)
    ├── Loads SOUL.md, USER.md, AGENTS.md (existing)
    ├── Reads ctx.extras.get("memory_indexes", [])
    ├── Appends memory indexes to foundational context
    └── ctx.extras["foundational_context"] = [(owner, content), ...]

Main Session Flow:
  Coordinator.send_message()
    ├── New session → save_context_entries(foundational_context)
    │     → saves "soul", "user", "agents", "memory_index" entries
    ├── build_system_prompt(entries, timezone)
    │     → wraps each entry in XML tags by owner
    └── Agent sees: <memory_index>Facts Index...</memory_index>

Background Task Flow:
  TaskExecutor._run_preprocessing()
    ├── load_memory_indexes(workspace_path) → [(tag, content)]
    ├── Creates ContextResult entries
    ├── Appends to other preprocessing results
    └── assemble_context(all_results, prompt) → enriched prompt
```

## Data Flow

### Static index injection flow (at startup)

```
1. Bootstrap runs hooks in order:
   a. memory_hook runs (creates dirs, ensures MEMORY.md exists)
      - Reads memories/facts/MEMORY.md → format_memory_index("facts", content)
      - Reads memories/preferences/MEMORY.md → format_memory_index("preferences", content)
      - Stashes formatted results in ctx.extras["memory_indexes"]
   b. context_hook runs (loads foundational context)
      - Loads SOUL.md, USER.md, AGENTS.md as before
      - Reads ctx.extras.get("memory_indexes", [])
      - Appends memory index entries to foundational context list
      - Stores combined list in ctx.extras["foundational_context"]

2. Coordinator receives foundational_context from bootstrap extras

3. On new session:
   - Coordinator saves all foundational context entries (including memory indexes)
     as SessionContextEntry instances with metadata=None

4. On each message:
   - build_system_prompt() wraps entries in XML tags
   - Agent sees <memory_index>...</memory_index> sections in system prompt
   - Agent reads individual files via Read tool when index entries suggest relevance
```

### Background task preprocessing flow (at runtime)

```
1. TaskExecutor._run_preprocessing(prompt, pinned_skills)
2. Load memory indexes: load_memory_indexes(workspace_path)
   → reads and formats both MEMORY.md files
   → returns list of (tag, content) tuples
3. Create ContextResult entries from memory indexes
4. Include in preprocessing results alongside other providers
5. assemble_context(all_results, prompt) → enriched prompt with memory indexes
```

### Episodic memory flow (preamble-based, no search)

```
1. System preamble includes expanded ## Memories section
2. Agent sees episodic naming conventions, retention tiers, content expectations
3. Agent reads episodic files manually via Read when needed
   (future: DLT-105 adds MCP tools for episodic search)
```

## Key Decisions

### Memory hook stashes indexes in extras bag

**Choice**: `memory_hook` reads and formats MEMORY.md files, stashing results in `ctx.extras["memory_indexes"]`. `context_hook` reads from there and appends to foundational context.
**Why**: Preserves subsystem ownership — memory-related logic stays in the memory module, context-related assembly stays in the context module. The extras bag is the bootstrap's built-in mechanism for cross-hook communication (already used by workspace, skills, plugins hooks).
**Alternatives Considered**:
- Extend `context_hook` directly to read MEMORY.md: mixes memory-subsystem logic into the context module, violating the subsystem ownership pattern established by DES-003
- Dedicated `MemoryIndexProvider` in session-gated pipeline: adds a provider class when we're trying to eliminate providers for memory; also runs per-session rather than once at startup

**Consequences**:
- Pro: Clean subsystem boundaries per DES-003
- Pro: `memory_hook` already ensures MEMORY.md exists, so reading it there is natural
- Pro: `context_hook` only needs one extra line: `entries.extend(ctx.extras.get("memory_indexes", []))`
- Con: Subtle ordering dependency — `memory_hook` must run before `context_hook` (already guaranteed by `__main__.py` registration order)

### Shared helper function for memory index formatting

**Choice**: Extract `format_memory_index()` and `load_memory_indexes()` into `memory/index.py` (alongside existing index rebuild logic) for use by both `memory_hook` and the task executor.
**Why**: Both the bootstrap flow and the task executor need to read and format the same MEMORY.md files with the same rendering logic. Sharing a function prevents format drift between the two consumers.
**Alternatives Considered**:
- Duplicate the formatting logic in both locations: format drift risk, two places to maintain
- Create a provider class: heavier than needed — a pure function is sufficient

**Consequences**:
- Pro: Single source of truth for index formatting
- Pro: Natural home in `memory/index.py` alongside `run_index_rebuild()`
- Pro: Pure function, easy to test independently

### Direct function call in task executor (no provider)

**Choice**: The task executor calls `load_memory_indexes()` directly in `_run_preprocessing()` and creates `ContextResult` entries inline, without registering a provider class.
**Why**: The user's preference was to remove the context provider pattern entirely for memory. The task executor already has its own preprocessing flow — adding a function call is simpler and more transparent than introducing a new provider class just for this.
**Alternatives Considered**:
- Register a new `MemoryIndexProvider` in the task executor's pipeline: adds a provider class we're trying to eliminate
- Accept that background tasks lose memory context: they currently get memory through `MemoryContextProvider`, so this would be a regression

**Consequences**:
- Pro: No new provider classes
- Pro: Direct, readable code — function call with clear output
- Con: Task executor has slightly more inline logic (acceptable — it's ~5 lines)

### Owner tag "memory_index" for all injected sections

**Choice**: All memory index entries use the owner tag `"memory_index"` — one entry per directory (facts and preferences), not combined into a single entry.
**Why**: Matches the existing foundational context pattern (one entry per file: soul, user, agents). Allows `build_system_prompt()` to wrap each in its own XML tag, giving the agent distinct `<memory_index>` sections to navigate. Using a single tag for both means the XML wrapping naturally separates them by content.

**Consequences**:
- Pro: Consistent with foundational context pattern
- Pro: Each section gets its own XML tag with distinct content
- Con: Both entries share the same owner tag (acceptable — they're the same kind of content)

### Remove memory_path metadata display from post-processing

**Choice**: Remove the "Loaded Memories" display code in `post_processing.py` (lines 233-245) that reads `memory_path` metadata from entries with owner "memories".
**Why**: Static index injection replaces per-message memory entries. There are no more entries with `owner="memories"` and `metadata={"memory_path": "..."}` — the memory indexes are foundational entries with owner `"memory_index"` and no metadata. The display code would never match anything.
**Alternatives Considered**:
- Update display code to show "memory_index" entries instead: the display shows foundational context file names (SOUL.md, USER.md, AGENTS.md) — memory indexes aren't file names, they're formatted sections. Adding display logic for them adds complexity with little value.

**Consequences**:
- Pro: Removes dead code
- Pro: Simplifies the context display logic
- Con: Users won't see "Loaded Memories" in context summaries (acceptable — the indexes are always present in foundational context, not dynamically loaded)

### Episodic memory deferred to DLT-105

**Choice**: No episodic memory injection or search in this delta. The preamble documents episodic file structure so the agent can read files manually. DLT-105 will add MCP tools for episodic search.
**Why**: Episodic files are numerous and date-organized — they don't have a MEMORY.md index. Static injection would require loading all episodic file names, which is unbounded. The spec explicitly scopes this out (R7).

**Consequences**:
- Pro: Keeps scope focused on the high-value change (eliminating Opus round-trip for facts/preferences)
- Pro: Episodic documentation in preamble gives the agent enough context to read files manually
- Con: Agent loses automatic episodic search until DLT-105 lands (acceptable — DLT-105 is explicitly the follow-up)

## System Behavior

### Scenario: Normal startup with memory indexes

**Given**: A workspace with `memories/facts/MEMORY.md` and `memories/preferences/MEMORY.md` containing valid entries
**When**: The system starts up
**Then**: `memory_hook` reads both files, formats them into navigable sections, and stashes in `ctx.extras["memory_indexes"]`. `context_hook` appends them to foundational context. The coordinator saves them for each new session. The agent sees both sections in its system prompt.
**Rationale**: Memory indexes become part of foundational context — loaded once, always available.

### Scenario: Missing MEMORY.md for one directory

**Given**: A workspace where `memories/facts/MEMORY.md` exists but `memories/preferences/MEMORY.md` does not
**When**: The system starts up
**Then**: `memory_hook` reads facts/MEMORY.md successfully and formats it. Attempts to read preferences/MEMORY.md, gets FileNotFoundError, skips silently. Only the facts index is injected. No error or warning.
**Rationale**: The bootstrap hook already ensures MEMORY.md files exist, but race conditions or manual deletions shouldn't break startup.

### Scenario: Empty MEMORY.md file

**Given**: A workspace where `memories/facts/MEMORY.md` exists but contains only `# Memory Index\n`
**When**: The system starts up
**Then**: `memory_hook` reads the file, finds no valid entries (only the header), skips injection for that directory. No error or warning.
**Rationale**: Empty directories legitimately have empty indexes. The agent doesn't need an empty section.

### Scenario: Malformed entries in MEMORY.md

**Given**: A MEMORY.md file with some well-formed entries and some malformed entries (e.g., missing description, invalid link format)
**When**: `memory_hook` reads and formats the file
**Then**: Well-formed entries are included in the injected section. Malformed entries are skipped with a debug-level log warning. The section contains only valid entries.
**Rationale**: A single bad entry shouldn't prevent the entire index from being useful. Debug logging captures the issue without polluting normal logs.

### Scenario: No memories directory at all

**Given**: A workspace where the `memories/` directory does not exist
**When**: The system starts up
**Then**: `memory_hook` creates the directory structure (existing behavior). No MEMORY.md files exist yet, so no indexes are injected. `context_hook` reads an empty list from extras. Startup proceeds normally.
**Rationale**: First-run scenario — no memories exist yet, no context to inject.

### Scenario: Background task gets memory context

**Given**: A background task is being prepared for execution
**When**: `_run_preprocessing()` runs
**Then**: The executor calls `load_memory_indexes(workspace_path)` directly, creates `ContextResult` entries, and includes them in the assembled context. The background task's prompt is enriched with memory index sections.
**Rationale**: Background tasks previously got memory context through `MemoryContextProvider`. Direct function call preserves this capability without a provider class.

### Scenario: Background task preprocessing with missing MEMORY.md

**Given**: A background task is being prepared, but one MEMORY.md file is missing
**When**: `_run_preprocessing()` calls `load_memory_indexes()`
**Then**: The function skips the missing file, returns results for available files. The task proceeds with partial memory context. If both files are missing, no memory entries are added — task proceeds with the original prompt.
**Rationale**: Background tasks shouldn't fail because memory indexes are unavailable. The existing try/except in `_run_preprocessing()` handles any unexpected errors.

### Scenario: Agent reads a fact file on demand

**Given**: The agent sees the facts index in its system prompt with an entry like `[Restaurants](memories/facts/restaurants.md): Favorite restaurants`
**When**: The user asks "what restaurants do I like?"
**Then**: The agent uses the Read tool to read `memories/facts/restaurants.md` and responds with the content.
**Rationale**: Static injection provides the index; the agent reads individual files when relevant. No search agent needed.

### Scenario: Post-processing context display

**Given**: A session with foundational context including memory indexes
**When**: The post-processing context summary is generated
**Then**: The "Loaded Memories" line is no longer displayed (the code has been removed). Foundational context (SOUL.md, USER.md, AGENTS.md) is still listed.
**Rationale**: Memory indexes are foundational context, not per-message dynamic entries. They're always present and don't need per-summary display.

## Notes

- The `memory_hook` runs before `context_hook` in the bootstrap order (per `__main__.py` registration), guaranteeing that `ctx.extras["memory_indexes"]` is populated before `context_hook` reads it
- The `load_memory_indexes()` function is a pure utility — it reads files and returns formatted strings, with no dependency on the SDK, pipeline abstractions, or database
- Memory indexes are static for the lifetime of a session (loaded at startup). Changes to MEMORY.md during a session (from post-processing extraction or maintenance ticks) won't be reflected until the next startup. This is acceptable because MEMORY.md changes infrequently and the agent can still read newly created files directly via Read
- The formatted index sections include usage instructions ("read it with the Read tool") so the agent knows how to navigate the indexes without relying on the preamble
