## Purpose

This document explains the design rationale for DLT-181: temporary side conversations realized as **checkpoints** on the daily trunk. It covers how checkpoints park the main line while a tangent runs inline, how the tangent is summarized back, how the system auto-detects and rollbacks these decisions, and how the new controls are surfaced.

After implementation, the "Detected Impacts" section will guide reconciliation into feature design docs.

## Problem Context

A topic shift *collapses* the current branch and moves on — wrong tool for a quick tangent or side question, which should **park** the main line and return to it intact. The daily-trunk model (ADR-014) already has the right primitive (`branchWithSummary`); a checkpoint points it the other way: summarize the *tangent*, resume the *main line*. The open hard parts are reliably auto-detecting tangents, reversing an append-only tree decision for rollback, and rendering a stream-resistant decision header.

## Design Overview

_Checkpoints_ are passive markers at the main-line tip. A tangent taken after a checkpoint continues inline; `/back` (or the `summarize-to-checkpoint` classifier result) folds the tangent into a `branch_summary` rooted at the checkpoint and re-seats the leaf there, so the main line resumes. Tangents are marked distinct from topic branches so the branch-query tools (`ask_branch`, DLT-182 `open_branch`) exclude them. The boundary classifier gains two results; `/rollback` flips the most-recent automatic checkpoint/topic decision; decisions are surfaced via a persistent header; and the command surface is completed (all commands registered, arg-taking commands prompt via a pending-input flow).

### Flagged Unknowns

#### S3 — tangent detection
How to reliably distinguish a *tangent worth parking* (related enough to continue inline, but not part of the main thread) from an ordinary follow-up — and how to detect that an active checkpoint's tangent has *ended* (the conversation returning to the main line), which requires the classifier to know a checkpoint is active. Risk of over-triggering (parking normal replies) or under-triggering (missing tangents). Needs prompt/heuristic design and likely a classification-quality spike.

#### S4 — append-only-tree undo (load-bearing)
Whether pi's `SessionManager` can truly **delete/undo** an appended `branch_summary` entry, or only re-seat the leaf past it (leaving a dangling off-path branch). This determines whether rollback is clean or leaves residue, and how state is reconstructed when turns intervened between the decision and `/rollback` (the spec pins the user-level semantics: reverse the interpretation, turns continue under the new one). **Must verify** against `docs/reference/pi-sdk-notes.md` and the SDK (is there a `removeEntry`/undo primitive?). Recommend a spike before committing the rollback design — if undo is impossible, rollback may need a different representation (e.g., reverse-decision marker interpreted by readers rather than physical deletion).

#### S5 — stream-resistant header rendering
How the Telegram streamer anchors a header on the response message that the streamed text does not overwrite. Today's status lines are ephemeral and overridden by the stream. Need a rendering mechanism (anchored prefix / message lead-in preserved across text deltas). Conceptually overlaps the unimplemented DLT-064 (collapse intensive work) and DLT-150 (phase markers) — may generalize to a shared rendering primitive.

#### S6 — pending-input state placement
Where the per-chat pending-command state lives (the spec pins it as transient/not persisted), how it intercepts ahead of the coordinator's `submit`/steering and the single-active-trunk, REPL parity, and the TTL/abandonment mechanism.

### Notes for Reconciliation

- The daily-trunk model (ADR-014) needs a current feature spec/design; `conversation-loop` and `boundary-detection` both predate it. DLT-181's behaviors fold in once that reconciliation happens.
- The persistent-status-header (S5) is a general channel-rendering capability — candidate for a cross-cutting DES pattern (overlaps DLT-064/DLT-150).
- The pending-input flow (S6) is channel-agnostic in mechanism; the trigger (menu tap) is Telegram-specific but the state/routing should live in the commands/coordinator layer.
- `/new` bare semantics change (prompts for first message instead of immediate collapse) — reflect in commands/boundary docs.

## Notes

- Sibling delta DLT-182 (multi-turn `ask_branch` → `open_branch`/`message_branch`/`close_branch`) is related but independent; both must agree that summarized tangents are not branch-query targets.
- The checkpoint model replaced an earlier "parked sub-session" idea during speccing — checkpoints are strictly simpler (linear, reuse `branchWithSummary`, no single-active juggling, no context re-injection).
