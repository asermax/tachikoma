## Purpose

This document explains the design rationale for DLT-181: temporary side conversations realized as **checkpoints** on the daily trunk. It covers how a checkpoint parks the main line while a tangent runs inline, how the tangent is summarized back, how the boundary classifier drives both automatically, how `/rollback` reverses a wrong automatic decision by rewinding and replaying, and how the new controls are surfaced and made discoverable.

The load-bearing finding — verified against the official pi SDK docs and the project's `pi-sdk-notes.md` — is that **the session tree is append-only**: there is no delete/undo primitive, but `branch(id)` re-seats the active tip backward. Rollback is built on that re-seat, not on deletion.

After implementation, the "Detected Impacts" section will guide reconciliation into feature design docs.

## Problem Context

A topic shift *collapses* the current branch and moves on — the wrong tool for a quick tangent or side question, which should **park** the main line and return to it intact. The daily-trunk model (ADR-014) already has the right primitive (`branchWithSummary`); a checkpoint points it the other way: summarize the *tangent*, resume the *main line*.

**Constraints (from the codebase and ADR-014):**
- The pi session tree is **append-only** — `SessionManager` exposes no `removeEntry`/`undo`; the only tip-mutation primitives are `branch(id)` (re-seat leaf backward) and `branchWithSummary(id, summary)` (append a summary + re-seat). Verified against the official `sdk.md` and `pi-sdk-notes.md`.
- Conversational state lives on the session file as custom entries (ADR-014); the `boomerang-state` entry is re-read each inbound and survives restart. Rollback-relevant state must live there too (not in process memory).
- Classification must never block a message (fail-open) and must account for whether a checkpoint is active.
- Channels are thin; the streaming renderer edits one message in place, and `editMessageText` replaces the *full* message text — so any persistent-within-a-turn content must be recomposed by the renderer on every edit.

**Interactions:**
- Boundary detection owns branching decisions; DLT-181 extends its classifier and middleware.
- `ask_branch` (and sibling DLT-182's `open_branch`) enumerate branch records — tangents and reversed summaries must be excluded.
- The trunk-close memory pipeline extracts every un-extracted branch record — tangents and reversed summaries must be excluded.

## Design Overview

A **checkpoint** is a passive marker at the main-line tip, stored in the `boomerang-state` entry. A tangent taken after a checkpoint continues inline; `/back` (or the `summarize-to-checkpoint` classifier result) folds the tangent into a `branch_summary` rooted at the checkpoint and re-seats the leaf there, so the main line resumes. Tangents carry a `kind: "tangent"` discriminator and a `tangent-N` id so the branch-query tools and the memory extractor skip them and `topic-N` ids stay clean.

The boundary classifier gains two results — `set-checkpoint` and `summarize-to-checkpoint` — gated on whether a checkpoint is active, applied in the inbound middleware, conservative-by-default with a per-result kill-switch, and fail-open.

`/rollback` reverses the most-recent *automatic* decision in exactly two cases, by **rewinding to the pre-decision tip, applying the opposite transition, and replaying the triggering message**. The decision state lives on the session tree (`boomerang-state`), so it survives restart. The wrong-framing exchange goes off-path (append-only; not deleted), and a summary orphaned by the reversal is marked `reversed` so extraction and branch tools skip it.

Finally the command surface is completed: every slash command is registered in Telegram's menu; argument-taking commands entered bare enter a channel-agnostic **pending-input** flow; and every branching decision is surfaced as a **turn-scoped persistent header** on the decision's response (survives that response's streaming, not carried to later turns).

### Cross-Layer Contracts

**Decision-descriptor payload** (boundary/commands → coordinator → channel):
```
type DecisionHeader = {
  label: string;        // short emoji-prefixed label, e.g. "📌 Checkpoint set"
  note: string;         // one-line explanation
  rollbackable: boolean;// true only for automatic decisions (S4 target)
}
```
The coordinator attaches the latest decision descriptor for the exchange to the channel's response cycle; the channel sets it as the `StreamRenderer.header` before streaming begins. The renderer composes `header + body + transient` on every edit so the streamed text never overwrites it, and the header is dropped after the exchange (turn-scoped).

**Pending-input contract** (channel → coordinator):
- A bare arg-taking command produces a descriptor `{command, prompt}`; the coordinator stores `{command, promptedAt}` keyed by chat and asks the channel to render `prompt` (non-LLM) via the status path.
- The next inbound from that chat is captured as the argument and the command executes; any other command, TTL expiry, or restart clears the state. The capture happens before steering and before single-active-trunk logic, so the argument is never steered into a live run.

**Rollback replay contract** (boundary → coordinator):
- The boundary extension performs the tree surgery (rewind + opposite transition + `reversed` marker) and returns the triggering message text; the coordinator re-submits it as a fresh turn (`submit`) so it is re-answered under the corrected framing.

**Integration points / error handling:**
- All branching ops append to the session file (append-only); failures are logged and the exchange degrades gracefully (e.g. a failed summarize surfaces a notice and leaves the checkpoint active).
- `branch(id)` re-seat, like today's collapse, runs against the live trunk session's manager — it is a sanctioned tip-move, not the destructive `createBranchedSession` (which still must run on a detached manager).

### Shared Logic

- **`kind` discriminator on branch records**: a single field distinguishing `topic` / `tangent` / `reversed`, consulted by `getBranchRecords` (so tangents+reversed are excluded and `topic-N` ids stay clean), `ask_branch`, DLT-182 `open_branch`, and the trunk-close extractor. One mechanism, four consumers.
- **Boomerang-state snapshot pattern**: `checkpointId` and `lastAutoDecision` ride the existing latest-snapshot-wins `boomerang-state` entry, re-read each inbound (the same pattern `currentTopicBaseId` uses today). No new persistence surface.
- **Decision surfacing**: one decision-descriptor payload feeds both the turn-scoped header (S5) and (for auto decisions) the `/rollback` eligibility (S4) — a manual decision surfaces the header with `rollbackable: false`.

## Modeling

The daily-trunk tree gains two new entry flavors on top of the existing `branch_summary` (topic) and `boomerang-state`:

```
Session tree (append-only; ◀ = active leaf)
 root ─ msg ─ msg ─ [checkpoint C, in boomerang-state] ─ t1 ─ t2 ─▶ branch_summary(tangent-N, rootedAt=C) ─◀ leaf
                       │                                  └─ tangent turns, folded into the summary on /back
                       └─ main line resumes exactly at C (R5)

Contrast — topic shift (today):
 root ─ msg ─ (branch_summary topic-N, rootedAt=prior base) ─▶ leaf   (old branch collapsed; new topic continues)

Rollback (Case B: auto-new → checkpoint), rewind via branch(C):
 root ─ C ─ (branch_summary topic-N, now marked reversed) ─ M ─ resp      ◀ was the live leaf
              └─ branch(C) re-seats leaf back to C; M/resp + the topic-N go off-path
 root ─ C[checkpoint] ─ M' ─ resp' ─◀ leaf   (M replayed as the first tangent turn)
```

**Entities:**
- **Checkpoint** — `{checkpointId, setAt}`, carried in `boomerang-state`. One active; override-on-set; cleared on topic shift.
- **Tangent** — a `branch_summary` with `kind: "tangent"`, `tangentId: "tangent-N"`, rooted at the checkpoint. Excluded from branch-query and extraction.
- **Reversed summary** — a `branch_summary` (topic) carrying a `reversed` marker appended at rollback; excluded from branch-query and extraction.
- **`BoomerangState` (extended)** — `{currentTopicBaseId, lastDecision, relatedBranchId, checkpointId, lastAutoDecision?}`.
- **`lastAutoDecision`** — `{kind: "set-checkpoint" | "new", triggeringMessageId, preDecisionLeafId}`, in `boomerang-state`; consumed and cleared by `/rollback`.
- **`PendingInput` (transient)** — `{command, promptedAt}`, in an in-memory `Map<chatKey, …>`; not persisted.

**Checkpoint lifecycle:**
```
        (none) ──set (manual /checkpoint or auto set-checkpoint)──▶ active
         ▲                                                              │
         │                                              topic shift ────┘ (cleared, notice)
         │                                                              │
         └──────────── summarize-to-checkpoint (consumed) ──────────────┘
```

## Data Flow

**Set checkpoint (manual `/checkpoint`):**
```
/checkpoint ──▶ boundary command ──▶ writeBoomerangState({checkpointId: currentLeafId}) ──▶ header "📌 Checkpoint set"
```

**Auto set-checkpoint / summarize-to-checkpoint (inbound middleware):**
```
message M ──▶ boundary middleware ──▶ classifier (schema +2, knows checkpointActive?) ──▶ decision
   set-checkpoint:        writeBoomerangState({checkpointId: leaf, lastAutoDecision:{kind:"set-checkpoint", M, leaf}}); next()
   summarize-to-checkpoint: branchWithSummary(checkpointId, tangentSummary, {kind:"tangent"}); checkpointId=null; next()
   (continue/shift):       unchanged
```

**`/rollback` (the load-bearing flow):**
```
/rollback ──▶ read lastAutoDecision from boomerang-state
            ├─ none / manual / continue / summarize-to-checkpoint / not immediate ──▶ no-op + notice
            └─ eligible (set-checkpoint|new, immediate):
                  1. branch(preDecisionLeafId)              ◀ rewind; wrong-framing M+resp go off-path
                  2. Case A (was set-checkpoint): collapse branch-up-to-tip as topic (branchWithSummary)
                     Case B (was new):                       set checkpoint at tip; mark auto-new's summary `reversed`
                  3. clear lastAutoDecision
                  4. coordinator replays triggering message M as a fresh turn ──▶ header "🔄 Rolled back…"
```

**Pending-input (bare `/new`):**
```
/new (bare) ──▶ top-of-submit intercept ──▶ set PendingInput{command:"new"} + render prompt
next inbound ──▶ captured as arg ──▶ execute /new <arg> (collapse branch if it has an assistant turn since base) ──▶ clear
any other command / TTL / restart ──▶ clear PendingInput
```

## Key Decisions

### KD1 — Checkpoint rides `boomerang-state`, not a new table or session

**Choice**: Store the active checkpoint (`checkpointId`) in the existing `boomerang-state` custom entry on the session file.
**Why**: ADR-014 makes the session file the source of truth and the `boomerang-state` entry is already re-read each inbound and survives restart; a checkpoint is exactly "a small piece of conversational state the file serves well." Reusing it avoids a new persistence surface and a new dual-write.
**Sources**: ADR-014 (session file as source of truth); `pi-sdk-notes.md` (`appendCustomEntry`/boomerang-state pattern, verified against `@earendil-works/pi-coding-agent@0.79.1`); `src/sessions/trunk.ts` `BoomerangState`/`writeBoomerangState`.
**Alternatives considered**: a dedicated DB table (rejected — DB↔file dual source of truth, the duplication ADR-014 removed); a pi `appendLabelChange(id,"checkpoint")` label (the official `sdk.md` lists `appendLabelChange`, but a label carries no queryable id/`setAt`, so it is too thin for "one active, override, cleared-on-shift").
**Consequences**: Pro — restart-safe, no migration, idempotent-replay-friendly. Con — the snapshot is latest-wins, so clearing is an append (a `checkpointId: null` snapshot), not a deletion (consistent with the append-only model).

### KD2 — Summarize-to-checkpoint reuses `branchWithSummary` with the checkpoint as `branchFromId`

**Choice**: `/back` and `summarize-to-checkpoint` call `branchWithSummary(checkpointId, tangentSummary, details)`.
**Why**: The official `sdk.md` shows `branchWithSummary(id, summary)` takes an arbitrary `branchFromId` and re-seats the leaf onto the new summary rooted there. Using the checkpoint as that id folds the tangent into a summary rooted at the main-line tip, so the leaf returns to the main line — exactly R5. One primitive serves topic-collapse and tangent-collapse.
**Sources**: official pi `sdk.md` (`sm.branchWithSummary(id, "Summary…")` — branch with context summary); `pi-sdk-notes.md` (signature `(branchFromId, summary, details?, fromHook?) => string`); `src/agent/session-tree.ts` `branchWithSummary` wrapper; `src/extensions/boundary/collapse.ts` (existing collapse flow reused).
**Alternatives considered**: a bespoke tangent-collapse that copies turns elsewhere (rejected — reinvents `branchWithSummary`); folding the tangent into the *prior topic* summary (rejected — would collapse the main line, violating R5).
**Consequences**: Pro — tangent and topic share one well-tested primitive; the `details.kind = "tangent"` discriminator is the only addition. Con — `branchWithSummary` does not record the abandoned leaf, so `details.originalLeafId` is stored (the existing pattern for topic branches). **Empty-tangent guard**: when `checkpointId === currentLeafId` (no turns after the checkpoint), `/back` is a no-op with a notice and does **not** call `branchWithSummary` — no vacuous summary is created.

### KD3 — Tangent `kind` discriminator + separate `tangent-N` ids

**Choice**: Add `kind` (`topic` | `tangent` | `reversed`) to `BranchSummaryDetails`; enumerate tangents on their own `tangent-N` counter so `topic-N` ids stay clean; one discriminator consulted by `getBranchRecords`, `ask_branch`, `open_branch`, and extraction.
**Why**: `getBranchRecords` (`src/sessions/trunk.ts`) assigns `topic-${index+1}` over every `branch_summary`; without a discriminator, tangents would interleave into the topic sequence and become branch-query targets. A `kind` field keeps the topic sequence clean and makes exclusion a single filter.
**Sources**: `src/sessions/trunk.ts` `getBranchRecords`/`nextBranchId`; `src/extensions/boundary/ask-branch.ts` (enumerates via `getBranchRecords`).
**Alternatives considered**: a single `topic-N` sequence with a kind field only (rejected — pollutes topic ids and breaks the "topic-N" contract `ask_branch` already advertises); a separate `tangent-N` *file/entry type* rather than a discriminator on `branch_summary` (rejected — pi only has the one `branch_summary` entry type).
**Consequences**: Pro — one filter, four consumers; `topic-N` ids stable. Con — every branch-record consumer must apply the filter (a shared helper centralizes it).

### KD4 — Rollback = `branch(id)` re-seat + opposite transition + replay (no deletion)

**Choice**: `/rollback` rewinds via `branch(preDecisionLeafId)` (the sanctioned "move leaf to earlier entry" primitive), applies the opposite transition (collapse-as-topic / set-checkpoint), marks any orphaned summary `reversed`, and replays the triggering message.
**Why**: The official `sdk.md` and `pi-sdk-notes.md` confirm the tree is **append-only** — there is no delete/undo primitive (the full mutation surface is `appendLabelChange`, `branch`, `branchWithSummary`, `createBranchedSession`). The user's "we're at the tip, so roll it back" intuition is satisfied by `branch(id)`, which moves the active tip backward and leaves the wrong-framing exchange as an inert off-path branch — exactly pi's branching model. This matches the spec's "reverse the decision and replay the message" and keeps everything append-only and restart-safe.
**Sources**: official pi `sdk.md` (`sm.branch(entryId)` — "Move leaf to earlier entry"; no remove/delete in the tree API); `pi-sdk-notes.md` (`reseatLeaf` wraps `branch(id)`; append-only confirmed); ADR-014 (append-only / idempotent replay).
**Alternatives considered**: physical file truncation to delete the wrong-framing exchange (rejected — desyncs the live `AgentSession`'s in-memory index/`state.messages`, breaks the append-only/idempotent-replay recovery model ADR-014 relies on, and is brittle across pi upgrades); a pure "reclassify the old summary's kind by marker" without rewind+replay (rejected by the user — they want the message re-answered under the corrected framing, which requires the rewind + replay).
**Consequences**: Pro — fully append-only; restart-safe; reuses sanctioned primitives; the user gets a correctly-framed fresh answer. Con — the wrong-framing M+response physically remain as an off-path dead branch (inert; not re-extracted, since off-path branches are not extraction targets).

### KD5 — Rollback decision state on the session tree (`lastAutoDecision`), not in memory

**Choice**: Record each auto `set-checkpoint`/`new` decision as `lastAutoDecision = {kind, triggeringMessageId, preDecisionLeafId}` inside the `boomerang-state` snapshot; `/rollback` reads the latest snapshot.
**Why**: The user requires `/rollback` to survive a restart between the bad decision and noticing it. The `boomerang-state` entry already lives on the file and is re-read each inbound (how `currentTopicBaseId` survives restart); riding `lastAutoDecision` on it is restart-safe with no new persistence surface. `preDecisionLeafId` is recoverable from existing data (the checkpoint id for `set-checkpoint`; the topic summary's `originalLeafId` for `new`), but storing it makes rollback robust and avoids fragile tree-walking.
**Sources**: ADR-014; `src/sessions/trunk.ts` `readBoomerangState`/`writeBoomerangState` (latest-snapshot-wins, re-read each inbound); `BranchSummaryDetails.originalLeafId`.
**Alternatives considered**: an in-memory `Map` (rejected — lost on restart, and the user explicitly asked for tree state); deriving everything by walking the tree at rollback time with no stored record (rejected — fragile, and immediacy/identity checks are clearer with a stored `triggeringMessageId`).
**Consequences**: Pro — restart-safe; consistent with the existing boomerang pattern. Con — an extra field on the snapshot (negligible). Note: S6 pending-input is *intentionally* in-memory and ephemeral per R9 — the two are distinct by design.

### KD6 — `reversed` marker for orphaned summaries

**Choice**: When rollback orphans a summary (Case B: the auto-`new`'s topic summary), append a dedicated `tachikoma-reversal` marker entry (via `appendState`, mirroring the `markBranchExtracted` completion-marker pattern) naming the reversed `summaryEntryId`. Because a `branch_summary` entry cannot be mutated (append-only), consumers compute an **effective kind** at read time: a record whose `summaryEntryId` is in the reversal-marker set reads as `reversed`; otherwise its `details.kind` (`topic`/`tangent`) stands. The shared `kind` filter then excludes both `tangent` and `reversed` for `getBranchRecords`/`ask_branch`/`open_branch`/extraction.
**Why**: `getBranchRecords` enumerates *every* `branch_summary` on the file, so an off-path orphaned summary would otherwise be extracted into memory and become a branch-query target. Since the entry cannot be mutated (append-only), a marker is the only way — exactly the user's requested fallback. A dedicated marker entry (read by scanning, like completion markers) accumulates across snapshots cleanly and reuses the existing pattern.
**Sources**: `src/sessions/trunk.ts` completion-marker pattern (`markBranchExtracted`/`hasMarker` via `appendState`); `src/extensions/memory/close-pipeline.ts` `extractBranches` (iterates `trunk.branchRecords`).
**Alternatives considered**: physically removing the orphaned summary (rejected — append-only, no primitive); leaving it extractable (rejected — would create spurious memory from a reversed decision).
**Consequences**: Pro — reversed decisions leave no memory/query residue. Con — another `kind` value to filter (centralized in the shared helper).

### KD7 — Tangents excluded from memory extraction

**Choice**: The trunk-close extractor skips `kind: "tangent"` (and `reversed`) branch records.
**Why**: A summarized tangent's content already lives in the summary injected into the main line; extracting it separately would duplicate it as episodic/topic memory. A tangent is a scratch buffer, not a topic.
**Sources**: `src/extensions/memory/close-pipeline.ts` `extractBranches`; user decision (Decision 2).
**Alternatives considered**: extract tangents like topics (rejected — their content is already in the injected summary).
**Consequences**: Pro — no duplicated memory; tangents stay "parked." Con — a fact surfaced only inside a tangent is not independently memorized (acceptable — the summary captures it).

### KD8 — Auto-detection conservative-on, with a per-result kill-switch

**Choice**: Ship `set-checkpoint`/`summarize-to-checkpoint` auto-detection **on by default**, with prompts biased against parking (only when clearly a tangent), fail-open, plus two per-result config flags `autoSetCheckpoint`/`autoSummarizeToCheckpoint` (default `true`) so each can be disabled independently without losing manual `/checkpoint`,`/back` or topic detection. Tune quality later via a classification-quality eval.
**Why**: R6 makes the two results must-have and they are already gated by `[extensions.boundary] enabled`; conservative-on gives the feature immediately while bounding the over-trigger risk. The per-result kill-switch lets an operator disable auto-checkpointing without losing manual control or topic detection.
**Sources**: `src/extensions/boundary/index.ts` (`enabled` config gate, fail-open path); user decision (Decision 3).
**Alternatives considered**: manual-only first (slightly in tension with R6 must-have, though the capability could ship disabled); on with no extra kill-switch (relies on the coarse global `enabled` flag only).
**Consequences**: Pro — capability ships; risk bounded by conservative prompts + kill-switch. Con — detection *quality* is empirical and needs a tuning pass (flagged in Open Questions); over/under-triggering is the known residual risk.

### KD9 — Turn-scoped header as an anchored prefix recomposed by the renderer

**Choice**: `StreamRenderer` carries a `header` field, composed as `header + body + transient` on every edit, set before streaming for the decision's exchange, and dropped after the exchange (not carried to later turns).
**Why**: Telegram's `editMessageText` replaces the *full* message text, so the only way a prefix survives streaming is for the renderer to recompose it on every edit — which the existing `compose()` already does for `body + transient`. "Persistent" in R8 means resistant to the streaming renderer, not sticky across turns (user-confirmed). This matches the existing lead-in reclamation pattern (one message, prefix preserved).
**Sources**: `src/extensions/telegram/streaming.ts` (`compose()` builds `text + transient`; `editMessageText` replaces full text); Telegram Bot API `editMessageText`; grammY 1.43 (`bot.api.editMessageText`); user decision (Decision 4 + turn-scoping refinement).
**Alternatives considered**: a separate header message before the response (rejected — a second message lingers and breaks the single-message stream); a Telegram-native "pin prefix" primitive (none exists).
**Consequences**: Pro — one message; survives streaming; cheap. Con — the renderer owns header composition (contained in `streaming.ts`). On a render failure the decision descriptor is still logged at `info` (`{label, note, rollbackable}`) and the response streams without the header (best-effort, per R8).

### KD10 — Pending-input interception at the top of `submit()`, in-memory and ephemeral

**Choice**: A per-chat transient `Map<chatKey, {command, promptedAt}>` in the coordinator, checked at the very top of `submit()` — before `/queue`/`/new` prefix-stripping and before steering — so a captured argument is never steered into a live run or mis-parsed as a command.
**Why**: `submit()` does prefix-stripping and steering before the middleware chain, so the intercept must precede both. Pending state is deliberately ephemeral (R9) — a stale pending state across restart would wrongly capture an unrelated message — so it stays in memory. The mechanism lives in the coordinator/commands layer so any channel (Telegram today; the future pi-interface REPL of DLT-178) gets parity for free; the channel only renders the non-LLM prompt.
**Sources**: `src/coordinator.ts` `submit()` (prefix-stripping + steering ordering); `src/extensions/api.ts` `InboundMiddleware`; R9 (transient/not persisted).
**Alternatives considered**: implement as the first inbound middleware (rejected — `submit()` strips prefixes and steers before middleware runs, so it would be too late); persist pending state to the DB (rejected — R9 mandates transience; persistence risks capturing an unrelated post-restart message).
**Consequences**: Pro — channel-agnostic; correct capture ordering. Con — a process restart drops a pending prompt (intended); the TTL must be short to avoid capturing a late, unrelated message.

### KD11 — Full command-menu registration via `setMyCommands`

**Choice**: Expand the existing `bot.api.setMyCommands` call (today `new`, `queue`) to all commands with usage hints in each description.
**Why**: Telegram's command menu is driven entirely by `setMyCommands`; today `stop`, `skill`, `tasks`, `reload`, and the new `checkpoint`/`back`/`rollback` are invisible in the menu. grammY 1.43 exposes it directly (`bot.api.setMyCommands`), already used in `channel.ts`.
**Sources**: grammY 1.43 / Telegram Bot API `setMyCommands` (`{command, description}` per command; command names lowercase ≤32 chars, descriptions 3–256 chars); `src/extensions/telegram/channel.ts` (existing `setMyCommands` call).
**Alternatives considered**: per-scope commands via `BotCommandScope` (rejected for now — single-user bot, a global menu suffices; can revisit if concurrent channels DLT-052 need per-chat menus).
**Consequences**: Pro — all controls discoverable. Con — the call must stay in sync with the command set (a single registration point keeps it so).

## System Behavior

### Scenario: Set and later summarize a tangent (manual)
**Given** an active conversation at a main-line tip `C`, **when** the user sends `/checkpoint` then exchanges a tangent then `/back`, **then** `C` is recorded as `checkpointId`; on `/back` the tangent turns are folded via `branchWithSummary(C, …, {kind:"tangent"})`, the leaf re-seats to the summary rooted at `C`, `checkpointId` clears, and the main line resumes at `C` — never collapsed. A header "↩️ Summarized to checkpoint" is shown on the `/back` response only.
**Rationale**: R3/R5 — only the tangent is folded away; the main line is parked.

### Scenario: One-turn and multi-turn tangents share one mechanism
**Given** a checkpoint with a single tangent exchange, **when** it is summarized, **then** the behavior is identical to the multi-turn case (R4) — both call the same `branchWithSummary(checkpointId, …)`.
**Rationale**: R4 — one mechanism, no special-casing.

### Scenario: Summarize with no checkpoint / no tangent
**Given** no active checkpoint, **when** `/back` is invoked, **then** no-op + notice "No checkpoint to summarize to". **Given** an active checkpoint with no turns after it (`checkpointId === currentLeafId`), **when** `/back` is invoked, **then** no-op + notice "No tangent to summarize" and the empty-tangent guard skips `branchWithSummary` entirely — no vacuous summary is created (R11, KD2).
**Rationale**: R11 — graceful edges; the collapse primitive always appends, so the guard must short-circuit before it.

### Scenario: Concurrent manual and automatic checkpoint coincide
**Given** the user sends `/checkpoint` and the classifier concurrently emits `set-checkpoint` for the same inbound (same main-line tip), **when** both apply, **then** the result is a single active checkpoint — setting is idempotent per-tip: both write `checkpointId = currentLeafId`, and a `/checkpoint` at a tip that already carries `checkpointId = leaf` is a no-op with a notice ("Checkpoint already at this tip") (R11).
**Rationale**: R11 — manual and auto coincide rather than conflict; setting the same tip twice has one effect.

### Scenario: Checkpoint survives restart and clears on topic shift
**Given** an active checkpoint, **when** the process restarts and resumes, **then** the checkpoint is restored from the session file. **Given** an active checkpoint, **when** a topic shift occurs (manual `/new` or auto `new`), **then** the checkpoint clears and a notice is surfaced (R1/R2).
**Rationale**: ADR-014 — state on the file; a checkpoint is meaningless after the main line it marked has been collapsed.

### Scenario: Classifier auto set-checkpoint and summarize-to-checkpoint
**Given** the classifier detects a tangent beginning, **when** it classifies, **then** it returns `set-checkpoint`, a checkpoint is set, and `lastAutoDecision` records it. **Given** an active checkpoint and the classifier detects the tangent ended, **then** it returns `summarize-to-checkpoint` and the tangent is summarized. The classifier never emits `summarize-to-checkpoint` without an active checkpoint nor `set-checkpoint` when one is active (R6).
**Rationale**: R6 — the two results are gated on checkpoint state.

### Scenario: Classifier failure / disabled
**Given** the classifier errors or returns unparseable output, **when** detection runs, **then** it fails open (the message continues normally; no spurious checkpoint/summarize). **Given** `[extensions.boundary] enabled = false` (or the per-result kill-switch off), **then** the two new results are not emitted, while manual `/checkpoint`,`/back` still work (R6/R11).
**Rationale**: Detection must never block the loop.

### Scenario: Rollback Case A — auto set-checkpoint → topic
**Given** the most-recent auto decision was `set-checkpoint` (M answered as a tangent) and `/rollback` is the next message, **when** the user sends `/rollback`, **then** the leaf is re-seated to the pre-decision tip (M+resp go off-path), the branch up to that tip is collapsed as a topic summary, `lastAutoDecision` clears, and M is replayed as the new topic's first turn (re-answered). Header "🔄 Rolled back to topic".
**Rationale**: R7 — the wrong checkpoint framing is replaced by the topic shift that should have happened.

### Scenario: Rollback Case B — auto new → checkpoint
**Given** the most-recent auto decision was `new` (M answered as a new topic) and `/rollback` is the next message, **when** the user sends `/rollback`, **then** the leaf is re-seated to the pre-decision tip, the auto-`new`'s topic summary is marked `reversed`, a checkpoint is set at the tip, `lastAutoDecision` clears, and M is replayed as the first tangent turn. Header "🔄 Rolled back to checkpoint".
**Rationale**: R7 — the wrong topic shift is replaced by a checkpoint; the orphaned summary leaves no memory/query residue (KD6).

### Scenario: Rollback no-op cases
**Given** the most-recent decision was manual, `continue`, `summarize-to-checkpoint`, or there is no recent auto decision — or one or more exchanges have occurred since it — **when** the user sends `/rollback`, **then** no-op + notice "Nothing to roll back" (R7). **Given** the process restarted between the decision and `/rollback` (no exchange since), **then** rollback still works — `lastAutoDecision` is on the tree.
**Rationale**: R7 — exactly two cases; restart-safe by construction.

### Scenario: Wrong-framing exchange is not re-extracted
**Given** `/rollback` has moved the leaf past the wrong-framing M+response, **when** the trunk later closes, **then** that off-path exchange is not extracted into memory and the `reversed` summary is skipped (KD6/KD7).
**Rationale**: Append-only rollback must not create spurious memory.

### Scenario: Tangent excluded from branch-query
**Given** a summarized tangent, **when** `ask_branch` (or DLT-182 `open_branch`) is directed at it, **then** it is excluded — tangents are not enumerated in `getBranchRecords`, so `topic-N` ids stay clean (R3/KD3).
**Rationale**: A tangent is parked, not a queryable prior topic.

### Scenario: Persistent header is turn-scoped
**Given** a branching decision, **when** its response is rendered, **then** a header (e.g. "📌 Checkpoint set") anchors the top and the streamed text does not overwrite it. **Given** the next turn has no new decision, **then** no header is carried forward (R8).
**Rationale**: R8 — surfacing is for awareness at the decision moment, not a persistent banner.

### Scenario: Pending-input flow
**Given** the user invokes `/new` bare, **then** a non-LLM prompt asks for the first message and a pending state is set. **Given** the next message arrives, **then** it is captured as the argument, `/new` executes (collapsing a branch with an assistant turn since its base), and the state clears. Any other command, TTL, or restart clears it (R9). Over REPL (DLT-178) the mechanism behaves the same.
**Rationale**: R9 — channel-agnostic, ephemeral argument capture.

### Scenario: Command menu completeness
**Given** the Telegram command menu, **when** the user opens "/", **then** every command is listed (`new, queue, stop, skill, tasks, reload, checkpoint, back, rollback`) with usage hints (R10).
**Rationale**: R10 — discoverability.
