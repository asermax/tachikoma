# Delta Spec: DLT-185 - Goal-driven completion for background tasks

<!-- Backend/agent-tool delta — no User Flow section. -->

## Story

As a user, I want background tasks to work toward a defined goal and decide for themselves when the goal is met — backing their claim with evidence — so that long autonomous runs complete reliably without an external judge second-guessing every turn, and so that a task that genuinely cannot be finished tells me why instead of looping until it times out.

## What It Does

Background tasks gain an explicit `goal` and self-declare their own outcome through a structured goal-status tool: the agent either declares the goal **completed** (restating the goal and citing concrete, checkable evidence that its success check is met) or **not completable** (with a reason that reaches the user). The loop nudges the agent each turn to evaluate completion, and the hard iteration cap remains as the sole safety net that fails a run which never declares.

## Acceptance Criteria

### Goal field on definitions and instances (R1, R2)

- [ ] Given the agent calls `create_task` with a `goal`, when the definition is stored, then the goal is persisted on the definition and every subsequently generated instance snapshots that goal at creation
- [ ] Given the agent calls `update_task` with a `goal`, when the definition is updated, then the stored goal changes and the next generated instance snapshots the new goal
- [ ] Given the agent calls `run_task_now` by reference, when the instance is created, then it snapshots the definition's current goal; given ad-hoc `run_task_now` with a `goal`, then the instance carries that goal directly (no parent definition)
- [ ] Given the agent calls `run_task_now` with an explicit `goal` override, when the instance runs, then it uses the instance's goal rather than any definition goal
- [ ] Given a definition or instance with no goal, then the field is null and the run proceeds to goal extraction (R3)
- [ ] Given existing task definitions created before this delta, when queried before their next run, then their goal field is null (populated lazily on first run per R14)

### Goal extraction and migration (R3, R14, R15)

- [ ] Given a background instance with no goal, when the run starts, then the executor derives a goal from the task prompt via structured extraction before the agent begins work
- [ ] Given extraction succeeds with a usable goal for an instance whose parent definition still has no goal, when extraction completes, then the derived goal is written back to the definition so the next run reuses it without re-extracting
- [ ] Given the parent definition's goal was set (by `update_task` or a prior write-back) between instance creation and write-back, when write-back is attempted, then it is skipped — the existing definition goal is never clobbered by an extraction
- [ ] Given an ad-hoc instance (no parent definition) with no goal, when extraction succeeds, then the goal is stored on the instance only
- [ ] Given a queued instance created before a definition's goal was written back, when that instance starts, then it uses the goal it snapshotted at creation (null) and therefore extracts its own goal at run start — instances never inherit a goal written back after their creation
- [ ] Given existing task definitions created before this delta, when they next run, then they acquire a goal lazily through extraction — no backfill pass, no manual migration
- [ ] Given extraction fails (classify throws or returns unparseable output), when the run starts, then the run proceeds using the task prompt as the goal basis, nothing is persisted, and a later run retries extraction
- [ ] Given extraction succeeds but returns an unusable goal (empty, trivial, or malformed), when write-back is considered, then it is treated as a failure: nothing is persisted, the run proceeds on the task-prompt basis, and a later run retries (the "unusable" threshold is resolved in design)
- [ ] Given extraction failed or was treated as unusable on a run, then every subsequent run retries extraction until it produces a usable, persisted goal — there is no give-up counter

### Goal surfaced to the agent (R4, R13)

- [ ] Given a background run has a goal (provided, overridden, or extracted), when the first turn is prompted, then the agent is told its goal and that it must declare the outcome via the goal-status tool when the goal's check is met
- [ ] Given the tasks usage section, background system prompt, and the create/update/run-now tool descriptions, then each documents what a goal is and the recommended structure: a measurable end state, a stated check that proves it, and constraints on what must not change

### Self-declaration via the goal-status tool (R5, R6, R7, R10)

- [ ] Given the agent is running a background task, then a single goal-status tool is available to it (alongside `ask_user`) as the sole way to declare a terminal outcome; no post-turn evaluator judges its turns
- [ ] Given the agent declares `completed`, when it calls the tool, then it must restate the goal and provide concrete, checkable evidence that the stated check is satisfied, plus a summary of what was accomplished; a declaration lacking these is not accepted as a valid completion
- [ ] Given a valid `completed` declaration, when the loop processes it after the turn, then the instance is marked `completed`, the summary is written to the instance `result`, the session is disposed, and the registered post-processors run once against the transcript (memory extraction + workspace persistence) — no success notice is emitted automatically
- [ ] Given the agent declares `not completable` with a reason, when the loop processes it, then the instance is marked `failed`, the reason is written to the instance `result`, and a `warning`-severity failure notice carrying the reason is emitted on the `notify` event
- [ ] Given a completed or not-completable declaration, then the instance `result` holds the agent's summary or reason respectively; the goal-status tool is the source of the terminal `result` on declaration, while the full audit (re-stated goal + evidence) lives in the session transcript

### Loop restructure and completion nudge (R8)

- [ ] Given a turn ends without the agent declaring a terminal outcome and without calling `ask_user`, when the loop prepares the next iteration, then it injects a user-message nudge reminding the agent to evaluate whether the goal is complete and call the goal-status tool if so
- [ ] Given the agent is making multi-turn progress but has not yet declared, then the nudge is re-injected each non-terminal turn without forcing a premature declaration — the agent may continue working
- [ ] Given the agent calls `ask_user`, then the nudge is not injected; the existing waiting/resume behavior takes over unchanged

### Iteration cap as safety net (R9)

- [ ] Given the agent never declares a terminal outcome and never pauses via `ask_user`, when the run reaches the iteration cap, then the instance is marked `failed` with a max-iterations reason and a `warning`-severity failure notice is emitted — the sole automatic failure path for an undeclaring run, and a single clean fail-point
- [ ] Given the run reaches the cap, then the failure is structured so a future delta can intercept this exact point to escalate to the user instead of failing

### Evaluator removal (R11)

- [ ] Given the background executor, then completion and continuation are driven entirely by the agent's goal-status tool calls and the completion nudge; there is no post-turn evaluator, evaluation schema, or fail-open path

### Preserved behavior (R12)

- [ ] Given a background run calls `ask_user`, then the instance suspends to `waiting`, the question is emitted as an `urgent` notice, and a later `respond_to_task` resumes the run reopening its persistent session — unchanged
- [ ] Given the concurrency cap, stuck-running sweep, wait-timeout expiration, crash-recovery, and one-shot retention, then they continue to operate unchanged
- [ ] Given `stop_task` cancels a running instance, then the live run is aborted and the instance marked `failed` with a cancellation reason — unchanged; the goal-status mechanism does not interfere with cancellation
- [ ] Given background failure notices (not-completable, cap, thrown error), then they flow through the notifications router's warning→Normal-tier mapping as today

## Notes

- The goal-status tool's exact name and parameter shape, the extraction prompt + `GoalSchema`, and the nudge wording are design-phase decisions (flagged in the shape). The spec fixes their *behavior*, not their text.
- The threshold for an "unusable" extracted goal (R15) is a design-time validation rule, not specified here.
