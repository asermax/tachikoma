# DLT-061: Apply Agent Update

## Story

As a Tachikoma operator, I want to apply an available agent update from within the running application so that I can stay current without manually running shell commands.

## What It Does

Adds an `apply_update` MCP tool that runs `uv tool upgrade tachikoma-agent` and, on success, triggers a clean shutdown followed by an in-place process restart using `os.execv`. The tool works standalone — no prior update check is required. The agent is made aware of the update tools through a brief description injected into the system prompt.

## Requirements

| ID | Requirement | Status |
|----|-------------|--------|
| R0 | Apply a user-confirmed agent upgrade using uv's upgrade mechanism | Core goal |
| R1 | Expose an `apply_update` MCP tool the agent can invoke (works with or without a prior update check) | Must-have |
| R2 | Report the upgrade outcome clearly (success, already up-to-date, or failure) | Must-have |
| R3 | In-place restart after successful upgrade (same terminal/tmux session via execv) | Must-have |
| R4 | Clean shutdown before restart (matching the graceful quit flow — buffer flush, session close, cleanup) | Must-have |
| R5 | Include update tool descriptions in the system prompt so the agent knows about update capabilities | Must-have |

## Acceptance Criteria

### Upgrade execution (R0, R1, R2)

- [ ] Given the user asks the agent to apply an update, when the `apply_update` tool is invoked, then it runs `uv tool upgrade tachikoma-agent` and returns the result
- [ ] Given the upgrade command succeeds and installs a new version, when the tool completes, then it reports the new version and triggers a restart
- [ ] Given the installed version is already the latest, when the upgrade command runs, then it reports "already up to date" and does not restart
- [ ] Given the user asks to update without a prior `check_updates` call, when the `apply_update` tool is invoked, then it runs the upgrade regardless (idempotent)
- [ ] Given the upgrade command fails (network error, permission denied, uv not found), when the tool completes, then it reports the error and does not restart
- [ ] Given the upgrade command fails, when the error is reported, then the running process continues normally without interruption

### In-place restart (R3)

- [ ] Given the upgrade succeeded, when the restart triggers, then the process replaces itself via `os.execv` (or equivalent) preserving the same terminal and tmux session
- [ ] Given the restart completes, when the new process starts, then it runs the upgraded version of tachikoma-agent
- [ ] Given the new process starts after restart, when it logs its version at startup, then the user can confirm the upgrade succeeded from the log output

### Clean shutdown (R4)

- [ ] Given the upgrade succeeded, when the restart sequence begins, then the application performs a full graceful shutdown — buffer flush, session close with post-processing, scheduler cancellation, and resource cleanup — matching the behavior of pressing 'q' in the REPL
- [ ] Given the user is in an active conversation via Telegram, when the restart triggers, then the current session is closed gracefully (post-processing runs) before the process restarts
- [ ] Given the restart happens during a Telegram session, when the new process starts, then it reconnects to Telegram automatically and messages sent during the restart gap are processed normally (Telegram queues them server-side)

### Concurrent operations (R3, R4)

- [ ] Given the user invokes `apply_update` while the agent is processing another message, when the tool runs, then the upgrade proceeds and the restart waits for the current message exchange to finish before shutting down
- [ ] Given background tasks are running when the restart triggers, when the shutdown sequence begins, then running background tasks are cancelled (matching existing shutdown behavior for background tasks)

### Agent awareness (R5)

- [ ] Given the updates subsystem is initialized, when the agent's system prompt is assembled, then it includes a brief description of the available update tools (`check_updates` for checking, `apply_update` for applying) so the agent can guide the user

## Notes

- The restart signaling mechanism (how the MCP tool communicates the restart request to the main loop) is a design concern — the spec requires that the restart happens after the tool returns its result, but the specific mechanism (event bus, flag, exception) is determined during design.
- `uv tool upgrade` is the upgrade command for production installs via `uv tool install`. For development/editable installs (`uv pip install -e .`), this command does not apply — the tool should detect this case and report it clearly.
- `os.execv` preserves the process PID and terminal session, making it compatible with tmux and other terminal multiplexers without special handling.
- Telegram bot reconnection after restart is transparent — the new process starts polling again and Telegram delivers queued messages.
