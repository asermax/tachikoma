# Delta Spec: DLT-088 - Scheduled Memory Store Maintenance

<!-- This spec describes WHAT the delta does, not HOW it's implemented. -->

## Story

As the system, I need to periodically review and clean up stored memories so that the memory store remains useful and doesn't degrade over time from accumulated staleness, redundancy, and excessive verbosity.

## What It Does

Three separate nightly background tasks — one per memory type — periodically scan the memory store and perform maintenance. Episodic memories get tiered consolidation: daily entries are cleaned for verbosity, then consolidated into weekly summaries, then monthly summaries, with entries older than a year deleted. Facts are evaluated for staleness, redundancy, and overlap — stale entries are removed, overlapping files are merged. Preferences are evaluated for redundancy and overlap across files — similar files are consolidated. All maintenance is agent-driven using the same session-forking pattern as extraction processors.

## Requirements

| ID | Requirement | Status |
|----|-------------|--------|
| R0 | Periodically review and clean up the memory store, consolidating, archiving, or removing entries that no longer provide value | Core goal |
| R1 | Three separate built-in nightly background tasks — one per memory type (episodic, facts, preferences) — each running on a configurable schedule | Must-have |
| R2 | Episodic maintenance uses tiered time windows: clean daily notes (last 15 days), consolidate into weekly summaries (15 days–3 months), consolidate into monthly summaries (3 months–1 year), delete entries older than 1 year | Must-have |
| R3 | Facts maintenance evaluates files for staleness, redundancy, and overlap — consolidating, editing within files, merging files, or removing obsolete files | Must-have |
| R4 | Preferences maintenance evaluates files for redundancy and overlap across files — consolidating, editing within files, merging files, or removing obsolete files | Must-have |
| R5 | All maintenance is agent-driven — LLM agents read and edit memory files using the same session-forking pattern as extraction processors | Must-have |
| R6 | Tiered time window thresholds (daily/weekly/monthly boundaries) are configurable with sensible defaults | Nice-to-have |
| R7 | Maintenance is idempotent — running it multiple times produces the same result | Must-have |
| R8 | Episodic entries are never deleted within the recent daily window — only cleaned for verbosity/noise | Must-have |
| R9 | Maintenance handles errors gracefully — agent failures, malformed files, empty stores, and concurrent access do not corrupt the memory store | Must-have |

## Acceptance Criteria

### Task Scheduling (R1)

- [ ] Given the system has completed bootstrap, when task definitions are listed, then three built-in memory maintenance task definitions are present — one for episodic, one for facts, one for preferences
- [ ] Given the three built-in task definitions, when any one is inspected, then it has a nightly cron schedule (configurable, default once per night)
- [ ] Given the three built-in task definitions, when any one is inspected, then it is identifiable as system-owned (created by bootstrap, not by the user)

### Episodic Maintenance (R2, R8)

- [ ] Given the episodic maintenance task runs, when it scans the episodic directory, then it applies tiered time windows based on file dates: recent daily (last 15 days), weekly consolidation (15 days–3 months), monthly consolidation (3 months–1 year), deletion (older than 1 year)
- [ ] Given episodic files within the last 15 days, when the maintenance agent processes them, then it reduces verbosity by removing repeated information and excessive implementation detail — the agent exercises judgment on what constitutes noise vs. substance
- [ ] Given episodic files within the last 15 days, when the maintenance agent processes them, then no files are deleted and no substantive content is removed (R8)
- [ ] Given episodic files between 15 days and 3 months old, when the maintenance agent processes them, then it consolidates groups of daily files into weekly summary files (one per ISO week), removing the originals
- [ ] Given episodic files between 3 months and 1 year old, when the maintenance agent processes them, then it consolidates groups of files into monthly summary files (one per month), removing the originals
- [ ] Given episodic files older than 1 year, when the maintenance agent processes them, then they are deleted
- [ ] Given a weekly or monthly consolidation, when the agent creates the summary file, then it preserves the high-level narrative and significant events while discarding implementation detail and routine activity — the agent exercises judgment on what is significant
- [ ] Given consolidated summary files, when they are named, then they use a clear naming convention that distinguishes them from daily files (e.g., `2026-W15.md` for weekly, `2026-04.md` for monthly)
- [ ] Given a consolidation would create a summary file that already exists from a previous run, when the agent processes the relevant files, then it merges new content into the existing summary rather than overwriting
- [ ] Given episodic files at consolidation boundaries that don't divide evenly into full weeks or months, when the agent processes them, then partial groups are consolidated into a single summary for that period

### Facts Maintenance (R3)

- [ ] Given the facts maintenance task runs, when it reads all fact files, then it evaluates each file for staleness, redundancy, and overlap
- [ ] Given staleness evaluation, when the agent judges an entry as outdated or no longer accurate (using context clues: past dates, completed projects, contradicted information), then it removes or updates the entry — staleness detection is agent judgment, not deterministic code
- [ ] Given redundancy evaluation (essentially the same information stated in different files), when the agent identifies duplicate entries, then it keeps the most complete version and removes duplicates
- [ ] Given overlap evaluation (related topics split across files), when the agent identifies overlapping files, then it merges them into a single consolidated file and removes the originals
- [ ] Given a fact file that is entirely obsolete, when the maintenance agent processes it, then it deletes the file

### Preferences Maintenance (R4)

- [ ] Given the preferences maintenance task runs, when it reads all preference files, then it evaluates each file for redundancy and overlap
- [ ] Given redundancy evaluation (same preference stated multiple times across or within files), when the agent identifies duplicates, then it deduplicates — keeping the most complete version
- [ ] Given overlap evaluation (related preferences split across files), when the agent identifies overlapping files, then it merges them into a single consolidated file and removes the originals
- [ ] Given a preference file that is entirely superseded or obsolete, when the maintenance agent processes it, then it deletes the file

### Agent-Driven Maintenance (R5)

- [ ] Given a memory maintenance task instance executes, when the agent runs, then it uses a fresh SDK session with access to the memory directories — the agent performs all file I/O autonomously
- [ ] Given a maintenance agent session, when the system prompt is constructed, then it includes clear instructions for the specific maintenance strategy (episodic tiered consolidation, facts cleanup, or preferences dedup) appropriate to the task type
- [ ] Given a maintenance agent session, when the agent runs, then it has read access to the memory directories but no access to conversation transcripts or other session data
- [ ] Given a maintenance agent completes its work, then all file changes (edits, merges, deletions) are performed by the agent directly — no post-processing code handles file operations

### Idempotency (R7)

- [ ] Given the episodic maintenance task runs twice in succession, when no new conversations have occurred between runs, then the second run produces no changes (daily files already clean, summaries already consolidated)
- [ ] Given the facts or preferences maintenance task runs twice in succession, when no new information has been added, then the second run produces no changes (already deduplicated and consolidated)
- [ ] Given a maintenance run fails partway through, when it is re-run, then it processes the remaining files safely without duplicating work on already-consolidated files

### Error Handling (R9)

- [ ] Given the memory store is empty (no files in the target directory), when a maintenance task runs, then it completes as a no-op
- [ ] Given a memory file is malformed or empty, when the maintenance agent encounters it, then it skips the file and continues processing others
- [ ] Given the maintenance agent fails or produces invalid output, when the task executor detects the failure, then the task instance is marked as failed and other maintenance tasks are unaffected
- [ ] Given maintenance runs while a user is actively writing memories (concurrent access), when a file is modified during processing, then the agent's view reflects whatever state it read — no locking is required; the worst case is a file is processed in its next-run state on the following night
- [ ] Given maintenance deletes or modifies files, when the workspace git commit runs after the task completes, then the changes are committed — git provides implicit rollback for any maintenance mistakes

### Configurability (R6)

- [ ] Given the configuration file, when the user inspects the memory maintenance section, then tiered time window thresholds are present with sensible defaults (`recent_days: 15`, `weekly_threshold_months: 3`, `monthly_threshold_months: 12`)
- [ ] Given custom threshold values in configuration, when the maintenance tasks run, then they use the configured values instead of defaults
