# Delta Spec: DLT-098 - Capture SDK stderr on error for debugging

## Story

As an operator, I need SDK stderr output included in error logs when SDK calls fail so that I can diagnose SDK subprocess failures without guessing what went wrong.

## What It Does

When the Claude Agent SDK CLI subprocess fails, the raised `ProcessError` contains only a static placeholder for stderr (`"Check stderr output for details"`), not the actual subprocess output. The SDK provides a `ClaudeAgentOptions.stderr` callback that receives each stderr line during execution, but Tachikoma doesn't set it — so stderr is never piped from the subprocess at all.

This delta installs a stderr accumulator callback on `ClaudeAgentOptions.stderr` at centralized chokepoints (a wrapped `query()` function and the `ClaudeSDKClient` option construction sites). When an SDK call fails, the accumulated stderr lines are included in the error log entry. On success, the accumulated buffer is discarded. The existing fail-open error handling behavior is preserved unchanged.

## Requirements

| ID | Requirement | Status |
|----|-------------|--------|
| R0 | SDK stderr output is captured during execution and included in error logs when SDK calls fail | Core goal |
| R1 | Stderr capture is centralized in common SDK chokepoints — not duplicated per call site | Must-have |
| R2 | Stderr is logged using DES-002 structured logging conventions (key=value format) | Must-have |
| R3 | Fail-open error handling is preserved — stderr capture never causes secondary failures or changes error propagation behavior | Must-have |
| R4 | Large stderr output is truncated to prevent log explosion | Must-have |
| R5 | Stderr in Error events surfaced to channels | Out |
| R6 | Stderr capture for CLIConnectionError | Out |

## Acceptance Criteria

### R0 — Core: Stderr captured and logged on error

- [ ] Given an SDK call where the subprocess produces stderr output and then fails, when the error is caught, then the log entry includes the captured stderr lines as a structured field
- [ ] Given an SDK call where the subprocess produces no stderr output before failing, when the error is caught, then the log entry is emitted without a stderr field (no empty noise)
- [ ] Given an SDK call that succeeds, then the accumulated stderr buffer is discarded without logging

### R1 — Centralized chokepoints

- [ ] Given any standalone `query()` consumer, when a `ProcessError` occurs, then stderr is logged at the wrapper level — no per-consumer error handling changes needed
- [ ] Given a `ClaudeSDKClient` consumer (coordinator, background task executor), when a `ProcessError` occurs, then stderr is logged at the existing error handler using shared accumulator logic
- [ ] Given a new standalone `query()` consumer is added in the future, when it uses the wrapped function, then it automatically gets stderr capture with no additional code

### R2 — DES-002 logging conventions

- [ ] Given stderr is logged, then it uses structured key=value format (e.g., `stderr={stderr}`) consistent with existing `err={err}` patterns
- [ ] Given stderr is logged at an existing error handler, then it is added to that handler's existing log call — no log level changes

### R3 — Fail-open preserved

- [ ] Given the stderr accumulator callback raises an unexpected error, then the error is silently swallowed and SDK execution continues unaffected
- [ ] Given a `ProcessError` occurs at any SDK call site, then the exception propagation behavior is identical to the current behavior (caught and yielded as recoverable Error in coordinator, caught and logged in background tasks, propagated in query consumers)

### R4 — Truncation

- [ ] Given stderr output exceeds a size threshold, when the error is logged, then the output is truncated with a marker indicating truncation occurred
- [ ] Given stderr output is within the threshold, then it is logged in full
