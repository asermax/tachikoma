# Delta Spec: DLT-060 - Check for agent updates and notify user

## Story

As a Tachikoma operator, I want to be notified when a newer version of tachikoma-agent is available on PyPI so that I can stay current with bug fixes and features without manually checking for releases.

## What It Does

A scheduled job periodically queries the PyPI JSON API for the latest version of `tachikoma-agent` and compares it against the currently installed version. When a newer version is found, a notification is dispatched to the user through the active channel via the existing priority buffer. The user sees a message indicating what version is available and can act on it at their convenience — the actual update application is handled by DLT-061.

## Requirements

| ID | Requirement | Status |
|----|-------------|--------|
| R0 | Periodically check PyPI for newer versions of tachikoma-agent | Core goal |
| R1 | Notify the user via direct notification when a newer version is available | Must-have |
| R2 | Configurable check frequency with a sensible default (once per day) | Must-have |
| R3 | Silent when already on the latest version — no notification, no log noise | Must-have |
| R4 | Only notify once per new version — no repeated notifications for the same available version | Must-have |
| R5 | Manual trigger: agent can check for updates on demand (e.g., user asks "any updates?") | Nice-to-have |

## Acceptance Criteria

### Periodic version check (R0, R2)

- [ ] Given the scheduler is running, when the configured interval elapses, then the system queries PyPI for the latest version of `tachikoma-agent`
- [ ] Given the `[updates]` config section is absent, when the application starts, then check frequency defaults to once per day (86400 seconds)
- [ ] Given the `[updates]` config section specifies a custom interval, when the scheduler runs, then checks occur at that interval

### Update notification (R1)

- [ ] Given a PyPI check finds a version newer than the currently installed one, when the check completes, then a notification is dispatched through the priority buffer at Normal priority
- [ ] Given the notification is delivered, when the user sees it, then it contains the available version and the current version
- [ ] Given the application is running without an active channel (e.g., no Telegram configured), when an update is found, then the notification is still dispatched (it will be delivered when a channel becomes available or on shutdown flush)

### Silent on latest (R3)

- [ ] Given a PyPI check finds the installed version matches or exceeds the latest, when the check completes, then no notification is dispatched
- [ ] Given multiple checks occur while already on the latest, when each completes, then no log output beyond debug-level is produced

### One notification per version (R4)

- [ ] Given a notification was already dispatched for version X, when a subsequent check still finds X as the latest, then no additional notification is dispatched
- [ ] Given a notification was dispatched for version X, when a newer version Y becomes available, then a new notification is dispatched for Y

### Error handling

- [ ] Given the PyPI API is unreachable, when a check is attempted, then the error is logged at warning level and no notification is dispatched — the next scheduled check retries
- [ ] Given the PyPI response is malformed or missing version data, when the response is parsed, then the error is logged at warning level and no notification is dispatched

### Manual trigger (R5)

- [ ] Given the agent is asked to check for updates, when the MCP tool is invoked, then a version check runs immediately (bypassing the schedule) and the result is surfaced to the agent
