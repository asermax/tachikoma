# Delta Spec: DLT-064 - Collapse intensive work sections in Telegram

<!-- This spec describes WHAT the delta does, not HOW it's implemented. -->

## Story

As a Telegram user, when the assistant performs intensive work — rapid sequences of tool calls interspersed with short text responses, such as reading, editing, and searching files during code implementation — I want the intermediate tool activity and bridging text to collapse into a compact, expandable section so that the final substantive answer is the prominent content I see by default, rather than a wall of tool-summary lines and tiny prose paragraphs that bury it.

## What It Does

The Telegram `StreamRenderer` detects "intensive work" within a single streamed message by counting **tool→text segments** — each contiguous block of one or more tool calls followed by text counts as one boundary, not each individual tool call. When the number of boundaries in one message exceeds a configurable threshold, the turn is treated as intensive work: every intermediate segment (all tool summaries and bridging text except the final streaming tail) folds into a single collapsed section rendered as a Telegram **expandable blockquote** (collapsed by default, tap-to-expand). Only the final substantive text stays expanded.

The threshold acts as a trigger that distinguishes a normal turn (a few tool uses) from intensive work, not as a quota of segments to keep visible: turns at or below the threshold render exactly as today. Collapse is purely positional — everything chronologically before the live streaming tail is "intermediate" — so no length or content heuristic decides what is bridging versus substantive. In-progress tools always stay visible (expanded) while running; a segment collapses only once its tools have completed, at the next text or tool boundary. Detection resets at each Telegram message boundary, so when a long turn splits into multiple messages each is evaluated independently.

## Acceptance Criteria

<!-- Grouped by requirement area. Each R maps to one or more AC groups. -->

### Detection and threshold (R1, R6, R9)

- [ ] Given an exchange with several tool calls grouped into segments, when the renderer counts intensive work, then it counts one **segment** (a block of one or more tool calls followed by text) as a single boundary — not one per tool call (e.g. five `read` calls before one text block count as one boundary, not five)
- [ ] Given a turn whose boundary count is at or below the threshold (default 4), when it renders, then no collapse occurs and the message shape is identical to today (tool summaries bake inline as `_🔧 <summary>_` markers with blank-line separation)
- [ ] Given a turn whose boundary count exceeds the threshold, when the crossing boundary forms, then the turn is treated as intensive work and intermediate segments fold into a collapsed expandable block
- [ ] Given `intensiveWorkThreshold` is set to a custom value, when the renderer evaluates collapse, then that value is the trigger (boundary count must exceed it)
- [ ] Given the default threshold of 4, when exactly 4 boundaries have formed, then no collapse occurs (collapse triggers only once the 5th boundary forms — the count must *exceed* the threshold, not meet it)
- [ ] Given a turn with exactly one tool→text segment (boundary count = 1), when it renders under the default threshold, then it renders exactly as today — one baked `_🔧 <summary>_` marker, no collapse
- [ ] Given a tool block is followed by even a single character of text, when that text resumes, then it completes a boundary — there is no minimum text length required to form one (collapse is positional, not length-based)
- [ ] Given a turn whose final tool block has no following text (trailing tools), when the turn finalizes, then that trailing block does not add to the boundary count (a boundary requires tool→text); its summary bakes at finalize into the collapsed block as part of the all-intensive case
- [ ] Given a long turn whose stream splits into multiple Telegram messages at the 4096-char limit, when each message is streamed, then the boundary count is evaluated independently per message (detection resets at each split), a message already committed/sent is never retroactively collapsed, and a single committed chunk that itself exceeded the threshold carries its own collapsed block for its intermediate segments

### Collapse behavior (R2, R4, R5, R10)

- [ ] Given an intensive turn (boundary count above threshold) ending in a final answer, when it finalizes, then all intermediate segments (tool summaries and bridging text) are wrapped in a single collapsed expandable block and only the final substantive text is expanded by default
- [ ] Given the collapsed section, when rendered, then it is a Telegram expandable blockquote (collapsed by default, tap-to-expand) — not a spoiler tag and not inline-expanded text
- [ ] Given an intensive turn, when the collapsed block is displayed, then it contains the per-segment **baked `_🔧 <summary>_` markers** — not the live `_🔧 <activity>_` transient labels — so the block is non-empty and expandable to reveal the work
- [ ] Given an all-intensive turn that ends on a tool with no final text, when it finalizes, then the entire message is the collapsed block carrying the per-segment tool summaries (no expanded content outside it) — a meaningful collapsed block rather than an empty one
- [ ] Given a turn that crosses the threshold on its final boundary (no text after the crossing segment), when it finalizes, then the whole message is the collapsed block, since there is no final substantive text to leave expanded
- [ ] Given an intensive turn, when the finalized message is laid out, then the collapsed intermediate block renders above the final answer (chronological order, matching how the work streamed), with the final answer as the last expanded content

### Live streaming and in-progress tools (R3, R4)

- [ ] Given a tool is currently running (its live `_🔧 <activity>_` line showing), when collapse is active for the turn, then that running tool remains expanded and visible — it is never folded mid-execution
- [ ] Given the boundary count is about to exceed the threshold as text resumes after a tool block, when the boundary forms (the tools have completed), then the just-completed segment becomes eligible to fold — collapse is applied only at boundaries, never while a tool runs
- [ ] Given an intensive turn is streaming, when each new boundary forms, then the previously-live tail (the text/tool that was streaming) folds into the collapsed block while the new live tail stays expanded — so the user watches intermediate work collapse in as the answer grows
- [ ] Given the boundary count crosses the threshold mid-stream (e.g. on the 5th boundary), when the renderer recomposes the live message, then the earlier segments that had rendered inline are folded into the collapsed block retroactively (the live message is rebuilt from the buffer), leaving only the current live tail expanded

### Configuration and no-regression (R6, R7, R8)

- [ ] Given `collapseIntensiveWork` is explicitly `false`, when any turn renders, then no collapse ever occurs and every turn renders exactly as today regardless of boundary count
- [ ] Given `collapseIntensiveWork` is `true` (default) and `intensiveWorkThreshold` is unset, when the renderer evaluates collapse, then the default threshold of `4` is used
- [ ] Given a normal (non-intensive) turn at or below the threshold, when it renders under the default configuration, then its streamed message is indistinguishable from today's behavior (no new artifacts, no layout change)

### Composition with existing rendering (R11)

- [ ] Given an exchange that carries a turn-scoped decision header, when it renders intensively, then the decision header stays anchored above the collapsed block (and above the final answer), recomposed on every edit and never overwritten by the collapsed content
- [ ] Given push notifications are on and a turn qualifies for the completion push, when it finalizes with a collapsed block, then the copy-delete push behavior is unchanged (the finalized message — collapsed block included — is copied)
- [ ] Given a recoverable or non-recoverable `error` event arrives mid-stream, when handled, then the error notice renders as today and is not affected by collapse state
- [ ] Given a `status` event (transient line) arrives during an intensive turn, when handled, then it renders as today's transient line below the streamed content and is unaffected by collapse
- [ ] Given a turn that triggers a notifying tool (`send_telegram_file`, `pin_message`, `send_message_with_buttons`) during intensive work, when it renders, then the collapse behavior composes with those tool outputs without conflict
- [ ] Given a streaming send/edit failure trips the renderer into the broken-render fallback path, when `finalize()` resends the full text via the plain chunked path, then collapse is not applied — the message is delivered as plain text (intermediate segments inline) so that a collapse-entity failure can never lose or block delivery

### Affected Features

- **[../feature-specs/telegram.md](../feature-specs/telegram.md)** - Modifies: the Response Rendering behavior (currently R4 / "Response Rendering" group, which bakes every tool summary inline). Adds a new requirement describing intensive-work collapse, new acceptance criteria in the Response Rendering group, two new config keys (`collapseIntensiveWork`, `intensiveWorkThreshold`), and a note that the entity converter must emit Telegram `expandable_blockquote` entities (today it emits only `blockquote` for `>` markdown).
- **[../feature-designs/telegram.md](../feature-designs/telegram.md)** - Modifies: the `streaming.ts` component description and the "Progressive paragraph-gated rendering with baked tool markers" key decision, which gain intensive-work detection (boundary counting), the threshold trigger, the retroactive fold in `compose()`, and expandable-blockquote emission. A new key decision records the collapse mechanism choice (expandable blockquote over spoiler) and the "threshold as trigger, not quota" model.

### Notes for Reconciliation

- The Telegram feature spec gains a new requirement for intensive-work collapse and accompanying acceptance criteria; the existing inline tool-summary behavior is preserved as the below-threshold / disabled case (not removed).
- The Telegram config schema gains two keys under `[extensions.telegram]`: `collapseIntensiveWork` (boolean, default true) and `intensiveWorkThreshold` (number, default 4).
- The collapse mechanism adds `expandable_blockquote` to the set of entities the renderer can emit; the markdown→entity converter (`entities.ts`) currently has no path that produces it, so this is a new emission path driven by the renderer's collapse state rather than by agent markdown.
- No new feature doc is needed — this extends the existing Telegram channel capability.
