# Delta Spec: DLT-050 - Plugin hook for custom post-processors

## Story

As a plugin developer, I want to contribute session-level post-processors that run in plugin-declared phases so that my plugin can perform custom extraction, side effects, or integrations after a conversation session closes (e.g., syncing action items to a task tracker, sending summaries to a webhook).

## What It Does

Plugin post-processors implement the existing `PostProcessor` interface (or extend `PromptDrivenProcessor`), are loaded and validated during plugin discovery, and participate in the session-level post-processing pipeline at their declared phase with the same error isolation guarantees as built-in processors. The phase assignment mechanism is refactored from a registration-time parameter to a class attribute, and existing built-in processors are updated to match.

## Requirements

| ID | Requirement | Status |
|----|-------------|--------|
| R0 | Plugins can contribute PostProcessor implementations that run in plugin-declared phases (main, pre_finalize, finalize) during session-level post-processing | Core goal |
| R1 | Phase is declared as a class attribute on the processor; existing built-in processors refactored to use the same pattern | Must-have |
| R2 | Plugin post-processors follow the same error isolation as built-in processors (failure doesn't block other processors or phases) | Must-have |
| R3 | Plugin loader validates processor interface compliance at load time | Must-have |
| R4 | Plugin post-processors are registered/unregistered during plugin lifecycle via the existing event-driven pattern (PluginInstalled / PluginRemoving) | Must-have |
| R5 | Plugin post-processors can extend PromptDrivenProcessor to fork the SDK session, receiving `agent_defaults` at instantiation | Must-have |
| R6 | Ordering within a phase | Out |
| R7 | Plugin post-processors receive plugin configuration values at instantiation | Must-have |
| R8 | Manifest field naming should be extensible for DLT-171 (per-message post-processors) without rework | Nice-to-have |

## Acceptance Criteria

### Phase as class attribute (R1)

- [ ] Given the `PostProcessor` base class, it defines `phase: str = MAIN_PHASE` as a class attribute, so subclasses inherit the default
- [ ] Given a `PostProcessor` subclass without an explicit `phase` override, when it is registered with the pipeline, then it runs in the `main` phase
- [ ] Given a `PostProcessor` subclass with `phase = PRE_FINALIZE_PHASE`, when it is registered with the pipeline, then it runs in the `pre_finalize` phase
- [ ] Given a `PostProcessor` subclass with `phase = FINALIZE_PHASE`, when it is registered with the pipeline, then it runs in the `finalize` phase
- [ ] Given the existing built-in processors (EpisodicProcessor, FactsProcessor, PreferencesProcessor, CoreContextProcessor, ProjectsProcessor, StaleWorkflowCleanupProcessor, TranscriptArchiveProcessor, GitProcessor), when they are registered, then each runs in the same phase as before the refactor
- [ ] Given existing code that calls `register(SomeProcessor(...), phase=PRE_FINALIZE_PHASE)`, after the refactor, these calls continue to work without modification — the explicit `phase=` argument takes precedence over the class attribute

### Pipeline unregister support (R4)

- [ ] Given a `PostProcessingPipeline` with a registered processor, when `unregister(processor)` is called, then the processor is removed from its phase list
- [ ] Given a processor that is not registered, when `unregister(processor)` is called, then it is a safe no-op (consistent with the existing `PreProcessingPipeline.unregister()` pattern)

### Plugin manifest declaration (R0, R8)

- [ ] Given a plugin manifest with `[post_processors]` section containing `"my-processor" = "my_module"`, when the plugin is loaded, then the module is discovered and the processor is registered
- [ ] Given a plugin manifest without a `[post_processors]` section, when the plugin is loaded, then no post-processors are registered and loading succeeds normally
- [ ] Given a CC-format plugin manifest (`.claude-plugin/plugin.json`), when the `post_processors` key is present, then it is silently ignored (consistent with CC handling of non-skill contributions)

### Processor validation (R3, R5)

- [ ] Given a declared processor module containing a concrete class that implements `PostProcessor`, when the loader validates it, then the class is accepted and instantiated
- [ ] Given a declared processor module containing a concrete class that extends `PromptDrivenProcessor`, when the loader validates it, then the class is accepted and instantiated with both `config` and `agent_defaults`
- [ ] Given a declared processor module containing multiple concrete `PostProcessor` subclasses, when the loader validates it, then all are instantiated and registered (consistent with the context provider pattern)
- [ ] Given a declared processor module containing no concrete `PostProcessor` subclass, when the loader validates it, then the plugin fails with a diagnostic explaining the missing implementation
- [ ] Given a declared processor module file that does not exist, when the loader validates it, then the plugin fails with a diagnostic explaining the missing file
- [ ] Given a processor class whose `__init__` does not accept `config` as a keyword argument, when the loader validates it, then the plugin fails with a diagnostic explaining the required parameter
- [ ] Given a processor class with `phase = "invalid_phase"`, when the loader validates it, then the plugin fails with a diagnostic listing the valid phase values (main, pre_finalize, finalize)

### Dependency injection (R5, R7)

- [ ] Given a plugin with a `[config]` schema and user-provided values, when its post-processor is instantiated, then `config=validated_config` is passed to the constructor
- [ ] Given a plugin with no `[config]` schema, when its post-processor is instantiated, then `config={}` is passed to the constructor
- [ ] Given a processor class whose `__init__` accepts `agent_defaults`, when the loader instantiates it, then the system's `AgentDefaults` instance is passed as `agent_defaults=`
- [ ] Given a processor class whose `__init__` does not accept `agent_defaults`, when the loader instantiates it, then `agent_defaults` is not passed (no TypeError raised)

### Lifecycle registration (R4)

- [ ] Given a loaded plugin with validated post-processors, when the `PluginInstalled` event fires, then each processor is registered into the `PostProcessingPipeline` at the phase declared by its class attribute
- [ ] Given a plugin being removed, when the `PluginRemoving` event fires, then each of its post-processors is unregistered from the `PostProcessingPipeline`
- [ ] Given a plugin that fails validation, when discovery completes, then its post-processors are never registered with the pipeline

### Error isolation (R2)

- [ ] Given a plugin post-processor that raises an exception during execution, when the pipeline runs, then other processors in the same phase continue to completion
- [ ] Given a plugin post-processor that raises an exception during execution, when the pipeline runs, then subsequent phases still execute
