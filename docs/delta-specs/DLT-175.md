# Delta Spec: DLT-175 - Daily session with collapsible topic branches

<!-- This spec describes WHAT the delta does, not HOW it's implemented. -->

## Story

As a user, I want my whole day with the assistant to live in one continuous conversation where topic switches are remembered rather than orphaned, so that I can move between topics, come back to earlier ones, and have the assistant still know what we discussed — without manually resuming sessions.

## What It Does

Replaces the topic-based session model (each topic shift closes the active session and opens or resumes another) with a single **daily trunk session** whose topic shifts become **collapsible branches**. When the topic shifts, the current branch collapses into a concise summary recorded on the trunk and a fresh branch starts; the trunk grows into a linear chain of branch summaries. Topic shifts are detected non-invasively by forking the live conversation into a throwaway headless session and asking it whether the new message continues the topic. Earlier-day context is reachable two ways: a lightweight pull of a related branch's context when a new topic resembles a prior one, and an on-demand tool that answers focused questions from any prior branch's full conversation. The trunk closes on a configurable nightly boundary, at which point each branch is processed independently for memory extraction. All trunk/branch state lives on the session file itself — the separate sessions database table and registry are removed.

## Acceptance Criteria

### Daily trunk lifecycle (R0, R3, R7, R13, R15)

- [ ] Given no trunk exists for the current day, when the first message of the day arrives, then a new daily trunk session is opened and becomes the active conversation
- [ ] Given an active daily trunk, when subsequent messages arrive across topics throughout the day, then they are all handled within that one trunk session (no new session is opened per topic)
- [ ] Given an active daily trunk, when the configured nightly-close hour is reached, then the trunk closes and the unified phased memory pipeline runs — per-branch extraction, then pruning, then consolidation — followed by the once-over-the-day close steps (transcript archive, workflow cleanup)
- [ ] Given the trunk-close memory pipeline, when it runs, then it is the only nightly memory-maintenance path (no separate per-store maintenance crons run independently of trunk close)
- [ ] Given a restart finds a stale-day trunk to recover, when its close + consolidation is running and a session task or notification arrives, then that delivery is queued and not delivered until consolidation finishes and the new day's trunk is live
- [ ] Given a background delivery is dequeued, when it is placed, then it lands in whichever branch is current at that moment; turns are serialized so a forced topic shift in progress completes before the delivery is placed (the delivery never lands in a half-collapsed branch)
- [ ] Given the trunk has closed for the day, when the next message (user or background delivery) arrives, then a fresh daily trunk is opened for the new day
- [ ] Given the conversational channel is the single primary channel, when a trunk is opened, then there is one trunk per day for that channel; per-channel trunks under concurrent channels are out of scope (deferred with concurrent secondary channels)
- [ ] Given the nightly-close hour and detection sensitivity are set in config, when the system runs, then those values govern close timing and shift detection; documented defaults apply when unset (a default close hour always exists so lifecycle behavior is deterministic without configuration)

### Topic-shift detection (R1, R6, R10)

- [ ] Given an active branch with at least one completed assistant exchange, when an idle user message arrives, then it is classified continue-topic or topic-shift by forking the live branch into a throwaway headless session and asking it, without altering the live session
- [ ] Given a short follow-up, a reaction, an answer to the assistant, a correction, or an ambiguous message, when classified, then the decision is continue
- [ ] Given the classifier errors or returns unparseable output, when detection runs, then the message is treated as continue and proceeds, and the error is logged
- [ ] Given a branch with no completed assistant exchange yet (too small — e.g. immediately after a prior shift), when a message arrives, then detection is skipped and the message proceeds (so two shifts in immediate succession cannot collapse an empty branch)
- [ ] Given a message arrives while the active branch is mid-exchange, when it is handled, then it steers the live run and topic detection is not invoked (detection runs only on idle input); a `/queue`-prefixed message waits in the inbox and is classified as a normal idle message on the next turn
- [ ] Given a system-origin (background) or extension-injected message, when it arrives, then topic detection is skipped

### Branch collapse and trunk growth (R2, R3, R8, R11)

- [ ] Given a topic-shift decision, when the branch collapses, then a concise summary (goal, decisions, completed work, changed files/commands, open questions, next steps) tagged with a branch id is recorded on the trunk and a fresh branch starts from it
- [ ] Given several topic shifts across the day, when the trunk is inspected, then it is a linear chain of branch summaries with the active branch extending the latest, and each collapsed branch remains present in the tree
- [ ] Given a branch summary on the trunk, when the agent reads its context, then the summary is labeled as a summary of a branch the conversation came back from (the agent can tell it apart from live conversation)
- [ ] Given summarization fails during a collapse, when the shift is processed, then the user's message still proceeds without losing conversation content and the failure is logged

### Cross-branch context (R4, R5)

- [ ] Given the related-branch matcher (however implemented) returns a prior same-day branch for a newly started branch, when the match is applied, then exactly one pointer (the branch's trunk summary plus its last exchange) is injected as context and no branch merge occurs
- [ ] Given the matcher returns no related branch, when the new branch starts, then no pointer is injected
- [ ] Given the agent needs detail beyond what the trunk summary holds, when it calls the branch-lookup tool with a branch id and a focused question, then the answer is produced from that branch's full original conversation (its last message reachable), not from the summary
- [ ] Given the branch-lookup tool is asked about an unknown branch id, then it reports that no such branch exists rather than failing the turn
- [ ] Given the branch-lookup tool is asked about the currently active branch, then the request is rejected (that branch is already live in context) without disturbing the live conversation

### State persistence without a registry (R9)

- [ ] Given trunk/branch activity during the day, when state changes (trunk anchor, current topic base, branch records, related links, channel message map, extraction markers), then it is persisted on the session file
- [ ] Given the process restarts or the session reloads mid-day, when state is rebuilt, then the active trunk, its current topic base, and its branch records are restored from the session file with no duplicate trunk markers and no separate sessions database table consulted
- [ ] Given a restart, when branch records are rebuilt from the session file, then branch ids are stable/deterministic so existing Telegram message maps and per-branch extraction markers still resolve to the same branches
- [ ] Given the first run ever with no session files present, when the first message arrives, then a trunk is created with no recovery-scan errors and no spurious extraction markers
- [ ] Given a restart occurs after some branches were already extracted at a prior interrupted close, when startup recovery runs, then only branches lacking an extraction marker are processed (extraction is idempotent per branch)
- [ ] Given a restart occurs after per-branch extraction but before the once-daily close steps finished, when recovery runs, then each once-daily step (core-context update, transcript archive, workflow cleanup) carries its own completion marker so the interrupted close completes exactly once and already-completed steps are skipped

### Telegram reply/reaction/button handling (R12)

- [ ] Given a reply, reaction, or button tap targets a message in the current branch, when it is handled, then the turn appends to the current branch (no shift, no classifier invoked)
- [ ] Given a reply, reaction, or button tap targets a message in a different (earlier) branch, when it is handled, then a topic shift is forced — the current branch collapses, a new branch starts, and the referenced branch's context is injected — without invoking the shadow-fork classifier
- [ ] Given an inbound Telegram message, when it is recorded, then its message id is mapped to the corresponding session-tree entry and the branch that owns it
- [ ] Given a reply/reaction/button references a message with no recorded tree entry/branch, when it is handled, then it proceeds as a normal message through topic detection with no injected branch context

### Continuous git safety (R14)

- [ ] Given an assistant response completes, when exchange processing runs, then workspace git and project git state are committed (not deferred to nightly close)
- [ ] Given the process crashes mid-day after several exchanges, when it restarts, then no committed-eligible work from completed exchanges has been lost

### Migration (R18)

- [ ] Given an existing install on the old schema, when it first runs after this refactor, then the migration creates a database backup before any schema change is applied
- [ ] Given the migration runs, then the `sessions` table is removed and `channel_messages` is reshaped to `(messageId, treeEntryId, branchId)`
- [ ] Given the migration has already run, when the process restarts, then it detects the new schema and is a no-op (self-detecting, idempotent)

### Removed behavior (R0, R1, R9)

- [ ] Given the new model, when an exchange completes, then no per-exchange rolling session summary is generated
- [ ] Given the new model, when the system runs, then there is no idle-close timer (the trunk persists until nightly close)
- [ ] Given the new model, when a message arrives, then there is no continue/new/resume topic classifier and no resume-candidate listing
- [ ] Given the new model, when a conversation starts, then there is no bridging-context-on-resume injection
- [ ] Given the new model, when an exchange ends in an encoding error, then there is no session quarantine flag/behavior
- [ ] Given the migration, when the system runs, then the REPL channel no longer exists, Telegram is the default and sole built-in channel, and channel selection/startup no longer offers `repl`

The metadata fast-paths for `forceNew`/`resumeSessionId` and the quarantine handling are removed.
- **docs/feature-specs/conversation-loop.md** + **docs/feature-designs/conversation-loop.md** — Modifies: session lifecycle moves from one row per conversation to one daily trunk per day with branch structure; `closeSession`/`resumeSession`/`closeIfIdle`/`recoverUnprocessedSessions` semantics change; bridging-context-on-resume (R6) and quarantine (R19) are removed; per-branch extraction at nightly close replaces per-close extraction; the close pipeline runs once daily while git/projects also commit per exchange.
- **docs/feature-specs/memory.md** + **docs/feature-designs/memory.md** — Modifies: memory extraction iterates per branch at trunk close instead of one transcript per session; transcript archive archives the whole trunk once; the separate per-store nightly maintenance crons are folded into the trunk-close event as a unified phased pipeline (per-branch extraction → pruning → consolidation) keyed on the day's branches.
- **docs/feature-designs/agent-integration.md** — Modifies: reverses the decision to bypass pi's session tree; the delta adopts `branchWithSummary`, `createBranchedSession`, headless forked sessions, and tree traversal.

- **docs/feature-specs/workflows.md** — Modifies: stale-workflow cleanup runs once at nightly trunk close rather than per topic close.

- **src/db/core-schema.ts** (`sessions` table) and **src/sessions/registry.ts** — Removed: the sessions table and registry are deleted; `SessionRecord` consumers migrate to session-file state. `app_state` and extension-owned tables (tasks, workflows, detached-processes) are unaffected.
