# Delta Spec: DLT-075 - Re-evaluate skill context per message

<!-- This spec describes WHAT the delta does, not HOW it's implemented. -->

## Story

As the assistant, I need skill detection to run on every message so that newly relevant skills are loaded as the conversation topic evolves, rather than being locked to whatever was relevant when the session started.

## What It Does

The skills context provider currently runs only on the first message of a new session and persists the result. This delta makes it run on every message, classifying only against skills not already in context. Newly detected skills are appended as additional context entries — existing skills are never removed. The same unified classification process is used for both initial and subsequent evaluations. Only the skills provider runs per-message; the full pre-processing pipeline remains session-gated.

## Acceptance Criteria

<!-- Grouped by requirement area. Each R should map to one or more AC groups. -->

### Per-message evaluation (R0, R3)

- [ ] Given an active session with skills A and B loaded, when a new message arrives that is relevant to skill C, then skill C is classified, loaded, and appended to context
- [ ] Given an active session with no skills loaded yet, when the first message arrives, then classification runs against the full skill registry (same as current behavior)
- [ ] Given the classification code path, when comparing initial evaluation vs subsequent evaluation, then the same `SkillsContextProvider.provide()` method is used (unified process)
- [ ] Given only the skills context provider is invoked per-message, when other context providers (memory, projects) have already run for the session, then they are not re-invoked — only skills re-evaluates

### Session boundaries (R2)

- [ ] Given a topic shift triggers a new session (via boundary detection), when the new session starts, then all accumulated skills are cleared and classification runs fresh against the full registry
- [ ] Given a session is resumed (re-routing to a previous session), when the next message arrives, then the resumed session's accumulated skills remain in context and only unloaded skills are classified

### Registry filtering (R1, R8)

- [ ] Given skills A and B are already in context, when classification runs for a new message, then the classifier only receives skills not in {A, B} from the registry
- [ ] Given all skills in the registry are already loaded in context, when a new message arrives, then classification is skipped entirely (no LLM call, no latency)
- [ ] Given the skill registry has no skills at all, when the provider runs, then it returns immediately with no context (unchanged from current behavior)

### Accumulation (R2, R5)

- [ ] Given skills A and B are already in context, when classification detects skill C as relevant, then a new context entry is appended for skill C — entries for A and B remain unchanged
- [ ] Given multiple new skills (C, D) are detected in one evaluation, when results are persisted, then separate context entries are appended for each

### Agent definitions (R4, R6)

- [ ] Given newly detected skills have agent definitions, when the results are processed, then those agents are appended to the session's available agents alongside previously loaded ones
- [ ] Given a new session starts after a topic shift, when the session state is cleared, then the agent list resets — only agents from the new classification are loaded

### Error handling (R7)

- [ ] Given classification fails on a subsequent message (SDK error, timeout, unparseable response), when the error is caught, then the message proceeds with existing skills context intact
- [ ] Given classification fails on a subsequent message, when the error is logged, then the log includes enough context to diagnose the failure
