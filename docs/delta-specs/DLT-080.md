# Delta Spec: DLT-080 - Self-healing skill system via nightly analysis

<!-- This spec describes WHAT the delta does, not HOW it's implemented. -->

## Story

As a user, I want my assistant's skills to improve themselves from evidence of how they performed each day, so that gaps and friction get fixed without me having to notice and request every change.

## What It Does

At each day's trunk close (the nightly boundary — default ~04:00, or the next-morning/stale-recovery close when the nightly one was skipped), a skill-evolution pass runs alongside memory post-processing. It first reconciles the previous run's proposals from the state of their remote branches (accepted / rejected / still pending), then analyzes the day's closed topic branches — the same walk memory post-processing does — collecting skill-usage data points into a wiki-style store under `memories/skill-evolution/`. A separate proposal agent turns accumulated evidence into one pushed branch per proposed skill modification (edit or new skill); nothing is ever applied to the live skills automatically. When proposals were created, a background task seeded with the run's context is dispatched to report (or, when configured, to act — e.g. open PRs).

## Requirements

| ID | Requirement | Status |
|----|-------------|--------|
| R0 | The day's completed conversations are analyzed for skill usage, and recurring problems become reviewable, branch-based skill-modification proposals — live skills are never edited silently | Core goal |
| R1 | Each run first reconciles prior proposals from remote state after a fetch — a failed fetch aborts the run softly before any analysis. Classification is reachability-first: recorded tip reachable from the remote head → accepted (whether or not the branch still exists); otherwise branch still present → pending; otherwise → rejected. The log is updated before new analysis, and rejected proposals are never re-proposed | Must-have |
| R2 | Analysis runs at trunk close, in parallel with memory post-processing, reusing the same topic-branch walk through extracted shared logic (no duplicated walk) | Must-have |
| R3 | Per-branch data points are collected: which skills were invoked, which failed or were misapplied, and what workarounds the agent resorted to | Must-have |
| R4 | Data points persist under `memories/skill-evolution/` wiki-style: one-line index entries (PROBLEM + ROOT CAUSE + FIX) and per-pattern pages updated with new evidence instead of duplicated | Must-have |
| R5 | A skill-impact log records every proposal with its outcome (proposed → accepted / rejected / still pending) | Must-have |
| R6 | Pattern dedup and size caps are agent-enforced: update-not-duplicate conventions with per-pattern pages kept under ~50 lines (the memory-store convention) | Must-have |
| R6b | An in-run maintenance pass consolidates near-duplicate patterns and sweeps emptied files | Nice-to-have |
| R7 | Proposals cover edits to existing workspace skills and creation of new skills | Must-have |
| R8 | Branch-per-edit: a separate proposal agent authors each proposal on its own branch via a temporary worktree (edit → commit → push to origin); the worktree and local branch are removed afterwards, and the live working tree is never touched. Each proposal is logged only after the host confirms from git state that the pushed branch exists (tip SHA read from git) — the proposal agent's report alone never creates or confirms a log entry | Must-have |
| R9 | Branches are named `skill-evolution/<skill>-<slug>`, unique among currently-open proposals (impact-log entries still in `proposed` status); collisions get a suffix | Must-have |
| R10 | When a run creates at least one verified proposal, it dispatches an ad-hoc background task seeded with the run's context; the prompt is the configured post-work prompt, or a default prompt that only generates a notification | Must-have |
| R11 | Fail-soft: a failed run never blocks trunk close — it logs, warns, and the day is skipped. Completed per-branch analyses persist via markers; unanalyzed branches of a failed day are abandoned (the trunk retires) and never re-analyzed | Must-have |
| R12 | Analysis is idempotent per branch: at most once per branch, and a re-run close skips already-analyzed branches | Must-have |
| R13 | The feature is enabled by default and toggleable via a setting | Must-have |
| R14 | Proposals target workspace skills only; built-in bundled skills are out of scope | Must-have |
| R15 | The feature requires a workspace `origin` remote — when none is configured, the run is skipped entirely (logged; no analysis, no run-time store writes; the bootstrap layout seeding is unaffected) | Must-have |

**Out of scope:** analyzing background-task transcripts; editing built-in skills; auto-merging proposals; proposing skill retirement/deletion; a per-run proposal cap; semantic search over the store; perfect accounting of squash merges (recorded as rejected — the change has landed, and rejected also blocks re-proposal).

**Notes:** multiple open proposals may touch the same skill (different patterns); since each branch is cut from the same base, such proposals can conflict at merge time — an accepted risk of branch-per-edit, not something the run prevents.

## Acceptance Criteria

### Reconciliation (R1, R15)
- [ ] Given a previous run logged proposals as `proposed`, when the next run starts, then it fetches from origin and classifies each before any analysis: recorded tip reachable from the remote head → accepted (whether or not the branch still exists); otherwise branch still present → pending; otherwise → rejected
- [ ] Given a proposal merged via a squash merge, when it is classified, then it records as rejected (documented limitation: the change has landed, and rejected also blocks re-proposal)
- [ ] Given a fetch failure during reconciliation, when the run starts, then the run aborts softly (warning logged, nothing classified or analyzed) rather than analyzing against stale branch state
- [ ] Given the first run on a workspace (empty impact log), when it starts, then reconciliation is a no-op, the bootstrap-seeded store is used, and analysis proceeds
- [ ] Given a workspace with no `origin` remote, when the trunk closes, then the skill-evolution run is skipped entirely — no analysis forks, no run-time store writes, no log changes — and the skip is logged

### Analysis walk (R2, R3, R12)
- [ ] Given a trunk closes with topic branches, when the processor runs, then each unanalyzed topic branch is analyzed with that branch's conversation live in the analyzing agent's context — using the same topic-branch enumeration memory post-processing uses (tangents and reversed branches excluded), via the shared walk logic
- [ ] Given memory post-processing is running, when the skill-evolution processor runs, then both complete correctly and neither's writes corrupt the other's (the two run concurrently by design)
- [ ] Given a branch already carrying an analysis marker (e.g. the close re-ran after a memory failure), when the walk runs, then that branch is skipped
- [ ] Given a background/headless close with no trunk, when the processor runs, then it is a no-op
- [ ] Given a branch with no skill-usage signal, when analyzed, then the fork may record nothing for it (a clean no-op, not an error)

### Data store (R4, R5, R6, R6b)
- [ ] Given data points identifying a recurring pattern (e.g. a CLI flag used in practice but missing from a skill's guidance), when the analysis fork persists them, then the pattern's page is updated with the new evidence — not duplicated — and the index carries a one-line entry in the PROBLEM + ROOT CAUSE + FIX form
- [ ] Given patterns accumulating across nights, when the maintenance pass executes, then near-duplicate patterns are merged, pages stay under ~50 lines, and emptied files are swept
- [ ] Given a proposal is created and verified, when it is recorded, then the skill-impact log entry captures the skill, pattern link, branch name, tip SHA, date, one-line description, and status `proposed`
- [ ] Given a malformed impact-log entry or a missing pattern page (user-edited store), when reconciliation or the proposal agent reads the store, then the entry is logged and skipped — never fatal

### Proposals and branches (R7, R8, R9, R14)
- [ ] Given accumulated evidence of a recurring skill problem with no open or rejected proposal for it, when the proposal agent runs, then it creates exactly one proposal: an edit to the existing skill, or a new `SKILL.md` for a recurring workflow that has no skill
- [ ] Given the proposal agent's input, then it carries the impact log and excludes patterns with rejected or still-open proposals from proposal candidates (the "never re-proposed" rule is enforced input-side)
- [ ] Given proposals are created, then each is authored on its own branch in a temporary worktree, committed, and pushed to origin; the worktree and the local branch are removed afterwards; the main working tree and current branch are untouched throughout
- [ ] Given proposals, when branches are named, then they follow `skill-evolution/<skill>-<slug>` and are unique among currently-open proposals (collision suffix when needed)
- [ ] Given the proposal agent runs, then it may only modify workspace skills under `{workspace}/skills/` — built-in skills are never touched
- [ ] Given the proposal agent completes, then each logged proposal is verified from git state (the remote branch exists; the tip SHA is read from git) before the log entry is written — the agent's report alone never creates a log entry
- [ ] Given a push is denied by the remote mid-proposal (read-only remote, missing credentials), then already-pushed proposals are still verified and logged, no stray worktrees or local branches survive cleanup, and the run fails softly
- [ ] Given the proposal agent fails mid-run for any other reason, then the same guarantees hold: pushed proposals verified and logged, no stray worktrees or local branches, soft failure

### Reporting (R10)
- [ ] Given a run that created at least one verified proposal, when it completes, then an ad-hoc background task is dispatched seeded with the run's context (proposals created, patterns touched, log path), with the configured post-work prompt — or the default notification-only prompt when none is configured
- [ ] Given a run that created no proposals, then no background task is dispatched
- [ ] Given the default prompt is used, then the background agent only generates a notification and takes no further action
- [ ] Given a partially-failed proposal phase that still verified at least one proposal, then the reporter still dispatches

### Failure, idempotency, and configuration (R11, R12, R13)
- [ ] Given any failure inside the skill-evolution run, when the trunk closes, then memory post-processing and trunk retirement proceed unaffected; the failure is logged and a warning notification is emitted
- [ ] Given a failure after some branches were analyzed, then those branches' markers and store writes persist, the unanalyzed branches are abandoned for good, and the day yields no proposals
- [ ] Given `[extensions.skill-evolution] enabled = false`, then nothing registers; given the default configuration, then the feature is active
