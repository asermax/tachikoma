# Delta Spec: DLT-176 - Limit detached process memory using cgroups

<!-- This spec describes WHAT the delta does, not HOW it's implemented. -->
<!-- Technical Delta: infrastructure/resource management -->

## Story

As a system operator, I need detached processes to be memory-constrained via Linux cgroups v2 so that a single runaway process cannot consume all available RAM and trigger OOM kills that affect the entire VPS.

## What It Does

Wraps every spawned detached process in a Linux cgroup v2 with a configurable memory hard limit. When a process exceeds its limit, the kernel OOM-kills it and the existing exit detection and notification infrastructure surfaces the event. Falls back gracefully (warns, spawns without limits) when cgroups v2 is unavailable. Does not apply to the main Tachikoma process or in-process background tasks — only externally spawned detached shell commands.

## Acceptance Criteria

<!-- Grouped by requirement area. Technical delta — measurable completion criteria. -->

### Cgroup-based memory limiting (R0, R1, R7)

- [ ] Given cgroups v2 is available, a `[detached_processes]` config section exists, and a process is spawned via `start_process` with no memory limit override, then the process is placed in a cgroup with `memory.max` set to the configured default
- [ ] Given cgroups v2 is available, then the cgroup is created before the subprocess starts and the subprocess PID is written to `cgroup.procs` immediately after spawn
- [ ] Given a spawned process attempts to allocate memory beyond its cgroup's `memory.max`, then the kernel OOM-kills the process
- [ ] Given cgroups v2 is available and the system uses cgroups v2 exclusively (no v1 hybrid), then the limiting mechanism works correctly
- [ ] Given multiple processes are spawned concurrently, then each process is placed in its own separate cgroup directory (one cgroup per process)

### Per-process overrides (R2)

- [ ] Given the agent calls `start_process` with an explicit `memory_limit_mb` argument, then the spawned process's cgroup uses that value as `memory.max` instead of the default
- [ ] Given the agent calls `start_process` with `memory_limit_mb=0` or a negative value, then the tool returns a validation error including the invalid value and stating the minimum is 1, and no process is spawned
- [ ] Given the agent calls `start_process` with a `memory_limit_mb` value exceeding system RAM, then the tool returns a validation error indicating the limit exceeds available system memory, and no process is spawned

### Configuration (R3)

- [ ] Given the TOML config file has a `[detached_processes]` section with `default_memory_limit_mb = 2048`, then all spawned processes default to a 2GB memory limit
- [ ] Given no `[detached_processes]` section exists in the config, then no default memory limit is applied (opt-in behavior)
- [ ] Given the config value is set to 0 or negative, then startup logs a clear error (Pydantic validation rejects the value)

### OOM detection and notification (R4)

- [ ] Given a process is OOM-killed by the cgroup, then the existing exit watcher detects the exit (shell wrapper captures exit code 137, i.e. 128+SIGKILL) and the notification includes context indicating the process may have exceeded its memory limit
- [ ] Given a process is OOM-killed, then the notification distinguishes OOM termination from a normal SIGKILL by checking the cgroup's `memory.events` for `oom_kill` count > 0
- [ ] Given a process exits with exit code 137 (killed by signal) but no OOM was detected in the cgroup (`oom_kill` count is 0), then the notification reports the exit without OOM context (it was killed for another reason)

### Graceful fallback (R5)

- [ ] Given cgroups v2 is not available on the system (no `/sys/fs/cgroup/` mount, or `memory` controller not accessible), then startup logs a one-time warning and processes are spawned without memory limits
- [ ] Given cgroups v2 is unavailable and a process is spawned, then the process runs normally with no memory constraint — the system does not refuse to spawn
- [ ] Given cgroups v2 becomes unavailable between spawns (e.g. cgroup directory removed), then the individual spawn logs a warning including the reason and proceeds without a memory limit
- [ ] Given cgroups v2 is available but creating a specific cgroup directory fails (e.g. permission denied), then the individual spawn logs a warning and proceeds without a memory limit for that process

### cgroup cleanup (R6)

- [ ] Given a process exits (whether OOM-killed, normally, or agent-stopped), then its cgroup directory is cleaned up (removed from the filesystem)
- [ ] Given cleanup fails (e.g. cgroup not empty due to child processes), then the error is logged and does not prevent the exit from being reconciled
- [ ] Given Tachikoma restarts after an unclean shutdown where cgroups were not cleaned up, then stale cgroup directories from previously-exited processes are cleaned during bootstrap recovery

### Nice-to-have: Memory usage visibility (R8)

- [ ] Given the agent calls `get_process` on a running process with an active cgroup, then the response includes current memory usage read from the cgroup's `memory.current`
- [ ] Given the agent calls `get_process` on a process without a cgroup (fallback mode), then the memory usage field is absent or reports "unavailable"
