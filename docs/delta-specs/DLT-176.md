# Delta Spec: DLT-176 - Inbound Telegram reaction interpretation

## Story

As a Telegram user, I want to react to the agent's messages with emoji and have the agent treat the reaction as a turn in the conversation so that I can respond with low friction — a quick 👍, 🤔, or 👎 instead of typing out an acknowledgment, follow-up, or pushback.

## What It Does

Subscribes the Telegram bot to `message_reaction` updates and surfaces user reactions as conversational input. Reactions are carried through the system as a new subtype of the coordinator's incoming-message envelope (text messages become a sibling subtype). Before the agent sees a reaction, the envelope is rendered into a plain prose description of what the user did (added, removed, or replaced an emoji); the agent interprets the emoji itself — there is no hard-coded mapping from emoji to meaning.

## Requirements

| ID | Requirement | Status |
|----|-------------|--------|
| R0 | When the user adds, removes, or replaces an emoji reaction on a message in the authorized Telegram chat, the agent receives it as a conversational turn and responds contextually | Core goal |
| R1 | Telegram polling is configured to receive `message_reaction` updates from aiogram | Must-have |
| R2 | The coordinator's incoming-message representation is refactored into a polymorphic envelope with at least two concrete subtypes: a text subtype (carrying today's fields — text, pinned skills, force-new flag) and a reaction subtype (carrying the reaction change) | Must-have |
| R3 | A reaction envelope is rendered, before it reaches the agent, into a prose description that names the emoji and the kind of change (added / removed / replaced from→to) without prescribing a meaning | Must-have |
| R4 | When a reaction update contains multiple emoji changes (e.g. two emoji added at once, or one added and one removed in the same update), the rendered prose describes all changes in a single turn | Must-have |
| R5 | Authorization rules that gate text messages also gate reactions — only reactions from the configured authorized user/chat produce turns | Must-have |
| R6 | A reaction turn skips session-boundary detection and always continues the current session (it is inherently a follow-up to the agent's prior output) | Must-have |
| R7 | Existing text and media handling paths continue to work unchanged through the new polymorphic envelope (all current call sites that construct or consume incoming messages keep producing the same observable behavior) | Must-have |
| R8 | When the user sends multiple reactions in quick succession (or a reaction while the agent is mid-response), each reaction flows through the existing steering / message-buffer infrastructure — no new concurrency machinery | Must-have |
| R9 | A reaction update that produces no rendered change (e.g. a no-op update from Telegram) does not enqueue a turn | Must-have |
| R10 | Operator can disable inbound reaction handling entirely via Telegram configuration | Nice-to-have |

## Acceptance Criteria

### R0, R1 — Reactions arrive and become turns

- [ ] Given the Telegram bot is running, when the authorized user adds an emoji reaction to any message in the chat, then the system receives the reaction update from aiogram
- [ ] Given a reaction is received, when it is processed, then a synthetic turn is enqueued to the coordinator and the agent produces a response in the current session
- [ ] Given the bot polling is configured, when it starts, then `message_reaction` is among the allowed update types so reactions are actually delivered (default aiogram polling does not subscribe to them)

### R2, R7 — Polymorphic envelope, backward-compatible

- [ ] Given the existing text and media message paths, when they enqueue an incoming message after the refactor, then they construct the text subtype of the envelope and the coordinator behaves identically to before the refactor
- [ ] Given any existing consumer of incoming messages (boundary detection, pre-processing pipeline, deferred queue, /new and /queue commands, buffered delivery), when it processes an envelope of the text subtype, then its behavior is unchanged
- [ ] Given the reaction subtype, when it is constructed, then it carries enough information for downstream rendering (the set of added emoji, the set of removed emoji) without referencing a specific message ID
- [ ] Given the polymorphic envelope, when checked at type-check time, then `IncomingMessage` is a sealed/closed sum of its known subtypes — adding a new subtype later requires updating consumers, no silent fall-through

### R3, R4 — Reaction-to-prose rendering (no semantic mapping)

- [ ] Given a reaction envelope describing a single emoji added (e.g. 👍), when rendered, then the agent receives a prose message like "The user reacted with 👍 to your last message. Interpret it in the context of the last exchange and respond accordingly."
- [ ] Given a reaction envelope describing a single emoji removed (e.g. 👍 → none), when rendered, then the agent receives a prose message describing that the user removed their 👍 reaction
- [ ] Given a reaction envelope describing a replacement (👍 → 🤔), when rendered, then the agent receives prose describing the change from 👍 to 🤔
- [ ] Given a reaction envelope describing multiple changes (e.g. 👍 and ❤ both added; or 👍 removed and 🤔 added), when rendered, then all changes are described in a single prose message and a single turn is produced
- [ ] Given any reaction envelope, when rendered, then the prose does NOT attribute a fixed meaning to any emoji (no "thumbs up means approval"). The agent is left to interpret

### R5 — Authorization

- [ ] Given a reaction update from a chat other than the configured authorized chat, when received, then it is silently ignored (no turn enqueued, no error visible to the user)
- [ ] Given a reaction update from the authorized chat but the reacting user differs from the configured authorized user (rare in a 1:1 bot chat but possible in groups), when received, then it is silently ignored

### R6 — No boundary detection for reactions

- [ ] Given a reaction turn, when the coordinator processes it, then session-boundary detection does NOT run — the turn continues whatever session is current
- [ ] Given there is no current session (e.g. the previous session has closed), when a reaction arrives, then a new session is opened and the reaction prose is the opening turn (the absence of a session does not crash, drop, or queue indefinitely)

### R8 — Concurrency / steering / multiple reactions

- [ ] Given the agent is mid-response, when a reaction arrives, then it is enqueued through the existing mid-exchange path (same as a text steering message) without any new locking or buffering primitives introduced by this delta
- [ ] Given multiple reaction updates arrive in quick succession, when each is processed, then each produces its own turn in arrival order — no debounce, no merging across updates (merging only happens WITHIN a single update per R4)

### R9 — No-op reactions

- [ ] Given an aiogram `message_reaction` update where the new reaction list is identical to the old reaction list (no actual change), when received, then no turn is enqueued
- [ ] Given a reaction update whose changes consist only of non-emoji reaction kinds the system does not handle (e.g. paid/custom reactions that the bot does not interpret), when received, then no turn is enqueued

### R10 — Disable switch (nice-to-have)

- [ ] Given a Telegram config flag that disables inbound reactions, when the bot starts, then `message_reaction` is not in the allowed updates list and no reaction handler is registered
- [ ] Given the disable flag defaults to "enabled", when no flag is set in config, then reactions are received and processed (current behavior is preserved when this feature ships)

## Requires

Dependencies:
- None (this delta does the envelope refactor itself rather than waiting on DLT-125)

Assumes existing:
- Coordinator `enqueue()` and steering / mid-exchange infrastructure (channels/telegram, agent/core-architecture)
- Telegram channel scaffolding: aiogram dispatcher/router, authorization filter, bot lifecycle (channels/telegram)
- Configuration system with TOML loading (configuration)
