# Delta Spec: DLT-176 - Inbound Telegram reaction interpretation

## Story

As a Telegram user, I want to react to the agent's messages with emoji and have the agent treat the reaction as a turn in the conversation so that I can respond with low friction — a quick 👍, 🤔, or 👎 instead of typing out an acknowledgment, follow-up, or pushback.

## What It Does

Subscribes the Telegram bot to `message_reaction` updates and surfaces user reactions as conversational input. Reactions are carried through the system as a new subtype of the coordinator's incoming-message envelope (text messages become a sibling subtype, and the envelope itself defines a protocol for rendering its content into prompt text for the agent). The agent interprets the emoji directly — there is no hard-coded mapping from emoji to meaning. The reaction does not reference the message it was applied to; the prompt is generic ("user reacted with X, interpret in context of the last exchange").

## Requirements

| ID | Requirement | Status |
|----|-------------|--------|
| R0 | When the user adds, removes, or replaces an emoji reaction on a message in the authorized Telegram chat, the agent receives it as a conversational turn and responds contextually | Core goal |
| R1 | Telegram polling is configured to receive `message_reaction` updates from aiogram | Must-have |
| R2 | The coordinator's incoming-message representation becomes a polymorphic envelope. The envelope defines a protocol that all subtypes implement — at minimum, a way to produce the prompt text the agent receives. Initial concrete subtypes: a text subtype (carrying today's fields) and a reaction subtype (carrying the reaction change). Subtype-specific fields stay on their subtype, not on the base | Must-have |
| R3 | Rendering an envelope to prompt text is a responsibility of the envelope itself (via its protocol). Rendering happens at exactly one well-defined point in the pipeline, before the agent receives the prompt. The coordinator can inspect the envelope's subtype for routing (R6) prior to rendering | Must-have |
| R4 | The reaction subtype's rendered prose names the emoji and the kind of change (added / removed / replaced from→to), describes all changes from a single update in one prose message, and does NOT prescribe a meaning for any emoji or reference the specific message that was reacted to | Must-have |
| R5 | Authorization rules that gate text messages also gate reactions — only reactions in the configured authorized chat are processed. The reactor's user identity is not checked separately (matches the current channel behavior, which authorizes by chat, not by user) | Must-have |
| R6 | A reaction turn skips session-boundary detection and continues the current session (it is inherently a follow-up to the agent's prior output) | Must-have |
| R7 | Existing text and media handling paths continue to behave identically after the envelope refactor — same observable behavior at the coordinator's public surface (`send_message`, deferred queue, message buffer, `/new`, `/queue`, buffered delivery, REPL, tasks executor) | Must-have |
| R8 | A reaction received while the agent is busy flows through the same mid-exchange path as a steering text message (uses `enqueue`, not `enqueue_deferred`); a reaction received while idle is processed as a regular turn. No new mid-exchange concurrency machinery is introduced | Must-have |
| R9 | Reaction updates that produce no rendered change (no-op updates, or updates whose only change is in reaction kinds the system does not interpret) do not enqueue a turn | Must-have |
| R10 | A reaction is processed regardless of which message it was applied to (the agent's, the user's own, or any other message in the chat) — this delta does not introduce outbound message-ID tracking. This is an accepted limitation, addressable by a future delta if needed | Must-have |
| R11 | Operator can disable inbound reaction handling via Telegram configuration; default is enabled | Nice-to-have |

## Acceptance Criteria

### R0, R1 — Reactions arrive and become turns

- [ ] Given the Telegram bot is running, when the authorized user adds an emoji reaction to any message in the authorized chat, then the system receives a `message_reaction` update from aiogram
- [ ] Given a reaction is received, when it is processed, then a synthetic turn is enqueued to the coordinator and the agent produces a response in the current session
- [ ] Given the bot is starting up, when polling begins, then `message_reaction` is included in the allowed update types (default aiogram polling does not subscribe to them, so reactions would otherwise never arrive)

### R2 — Polymorphic envelope, protocol surface, subtype-locality

- [ ] Given the incoming-message representation after the refactor, when an existing consumer (boundary detection, pre-processing pipeline, deferred queue, `/new` and `/queue` commands, buffered delivery, REPL, tasks executor, memory/skills context providers, per-message post-processing) handles a text envelope, then its observable behavior is identical to before the refactor
- [ ] Given a reaction envelope, when constructed by the Telegram channel, then it carries the diff between old and new reaction lists (added emoji, removed emoji) and no reference to the specific message that was reacted to
- [ ] Given the envelope base/protocol, when reviewed, then it does NOT include `text`, `pinned_skills`, `force_new`, or any other field that exists only on the text subtype today — fields living on the base must have a reason to be there beyond "the previous dataclass had them"
- [ ] Given the message buffer (`_message_buffer`) and forwarder (`_forwarder` / `_drain_back`) round-trip, when a reaction envelope passes through, then either (a) the buffer carries the envelope subtype faithfully and rendering happens downstream (the recommended option), or (b) the channel renders the envelope to text before `enqueue()` so the buffer remains text-only. The design phase picks one explicitly and both options leave R6 (routing) and R7 (text-path unchanged) testable

### R3 — Rendering is the envelope's responsibility, single point of invocation

- [ ] Given the envelope protocol, when implemented, then each subtype provides its own rendering of its content to prompt text (no free-standing renderer keyed on subtype)
- [ ] Given the pipeline, when an envelope flows from `enqueue` toward the agent, then rendering is invoked at exactly one well-defined point; the location is documented as part of design and the choice is consistent for all subtypes
- [ ] Given a reaction envelope, when the coordinator decides on session routing (R6), then it does so by inspecting the envelope's subtype/protocol BEFORE rendering — the routing decision does not depend on the rendered string

### R4 — Reaction-to-prose content (no semantic mapping, no message reference)

- [ ] Given a reaction envelope describing a single emoji added (e.g. `added={👍}, removed={}`), when rendered, then the agent receives prose along the lines of "The user reacted with 👍. Interpret it in the context of the last exchange and respond accordingly." (exact wording is illustrative; the canonical wording is fixed during design)
- [ ] Given a reaction envelope describing a single emoji removed (`added={}, removed={👍}`), when rendered, then the agent receives prose describing that the user removed their 👍 reaction
- [ ] Given a reaction envelope describing a replacement (`added={🤔}, removed={👍}`), when rendered, then the agent receives prose describing the change from 👍 to 🤔
- [ ] Given a reaction envelope describing several simultaneous changes (e.g. `added={👍, ❤}, removed={🤔}`), when rendered, then all changes are described in a single prose message and a single turn is produced
- [ ] Given any reaction envelope, when rendered, then the prose does NOT attribute a fixed meaning to any emoji (no "thumbs up means approval"). The agent interprets
- [ ] Given any reaction envelope, when rendered, then the prose does NOT reference or include the specific message ID, message content, or any identifier of the message that was reacted to

### R5 — Authorization (chat-level only)

- [ ] Given a `message_reaction` update from a chat other than the configured authorized chat, when received, then it is silently ignored (no turn enqueued, no error visible to the user)
- [ ] Given a `message_reaction` update from the authorized chat where `MessageReactionUpdated.user` is None (anonymous / channel-style reaction), when received, then it is processed normally (chat-level authorization passes; the reactor identity is informational only)
- [ ] Given the authorization filter, when reviewed, then it relies on `chat_id` only — the same field used by existing text and media handlers — and does not introduce a new "authorized user" concept

### R6 — No boundary detection for reactions; cold-start handling

- [ ] Given a reaction turn, when the coordinator processes it, then session-boundary detection does NOT run — the turn continues whatever session is current and never forces a new session via topic shift
- [ ] Given there is no current open session (e.g. the previous session closed and no message has yet opened a new one), when a reaction arrives, then a session is opened the same way it would be for any other incoming message, and the rendered reaction prose is the opening turn. The agent is expected to handle the absurd-context case gracefully (e.g. asking what was reacted to); the rendered prose does NOT change based on session state

### R7 — Text and media paths unchanged

- [ ] Given the existing text-message construction sites (REPL, Telegram text handler, Telegram media handler, tasks executor), when each constructs an incoming message after the refactor, then it constructs the text subtype with today's field values and the resulting coordinator behavior is identical to before the refactor
- [ ] Given existing call sites that read `IncomingMessage.text` directly (per-message post-processing, memory and skills context providers), when each accesses content after the refactor, then it does so via the polymorphic protocol or via a typed branch that handles all subtypes, and observable behavior on text envelopes is unchanged
- [ ] Given the deferred queue (`enqueue_deferred`, `has_deferred`, `promote_next_deferred`) used by `/new` and `/queue`, when used after the refactor, then it operates on the polymorphic envelope and preserves existing command behavior

### R8 — Concurrency / mid-exchange / multiple reactions

- [ ] Given the agent is mid-response, when a reaction arrives, then it is enqueued via `enqueue()` (NOT `enqueue_deferred()`) — the same path text steering messages use — and reaches the agent as a mid-exchange steering input
- [ ] Given multiple reaction updates arrive in quick succession, when each is processed, then each is enqueued in arrival order and the agent observes them in arrival order; whether they collapse into one generation or surface as separate exchanges follows the existing mid-exchange / idle-state rules (no new behavior is introduced by this delta)

### R9 — No-op and unhandled-reaction-kind updates

- [ ] Given a `message_reaction` update where the new reaction list is identical to the old reaction list (no actual change), when received, then no turn is enqueued
- [ ] Given a `message_reaction` update whose changes consist only of reaction kinds the system does not interpret (e.g. paid reactions, custom emoji), when received, then no turn is enqueued
- [ ] Given a `message_reaction` update whose changes mix interpretable emoji and uninterpretable kinds (e.g. one standard emoji added and one custom emoji added in the same update), when processed, then the rendered prose describes only the interpretable changes and one turn is enqueued

### R10 — Any-message-target as an accepted limitation

- [ ] Given a reaction on a message that was not authored by the bot (e.g. the user reacting to their own earlier message), when received, then it is still processed as a reaction turn — the system does not check the reacted-to message's authorship (no outbound message-ID tracking in this delta)
- [ ] Given the rendered prose, when reviewed, then it never claims the reaction was specifically on the agent's message — it only states that the user reacted with X

### R11 — Disable switch (nice-to-have)

- [ ] Given the optional `[telegram]` config flag for inbound reactions, when set to `false` at startup, then no reaction turns are produced and the bot does not subscribe to or handle reaction updates
- [ ] Given the flag is unset (default), when the bot starts, then reactions are received and processed (current default behavior)
- [ ] Given the flag, when reviewed, then config changes apply at startup only (consistent with the rest of the Telegram configuration; live toggling is out of scope)

## Requires

Dependencies:
- None (this delta does the envelope refactor itself rather than waiting on DLT-125)

Assumes existing:
- Coordinator `enqueue()`, deferred queue, and mid-exchange steering infrastructure (channels/telegram, agent/core-architecture)
- Telegram channel scaffolding: aiogram dispatcher/router, authorization filter, bot lifecycle (channels/telegram)
- Configuration system with TOML loading (configuration)
