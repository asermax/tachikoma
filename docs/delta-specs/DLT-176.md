# Delta Spec: DLT-176 - Memory File Index for Efficient Discovery

## Story

As the memory search agent, I need a structured index of available memory files so that I can determine which files are relevant to the current message without performing Glob-based directory discovery on every search.

## What It Does

Adds a `MEMORY.md` index file in `memories/facts/` and `memories/preferences/` that maps each filename to a one-line agent-generated description. The index replaces the current Glob → Grep → Read discovery chain in the memory context provider with a single Read of the index, allowing the search agent to go directly to relevant files. All write paths (extraction processors, maintenance agents) update the relevant index. A two-tier maintenance schedule keeps indexes accurate: light consistency checks Monday–Saturday, full rebuild using haiku subagents on Sunday. Episodic memories are excluded since they are date-organized and searched differently.

## Requirements

| ID | Requirement | Status |
|----|-------------|--------|
| R0 | Add a `MEMORY.md` index in `memories/facts/` and `memories/preferences/` mapping each filename to a one-line agent-generated description, sufficient for the search agent to decide relevance without opening the file | Core goal |
| R1 | Index entries are formatted as markdown links with descriptions (e.g., `[Cookbook](./cookbook.md): Contains the user's recipes`) | Must-have |
| R2 | All agent-driven write paths (extraction, maintenance) that create/modify/delete memory files also update the relevant `MEMORY.md` | Must-have |
| R3 | The memory context provider reads the index first to determine which files to load, replacing Glob-based discovery for facts and preferences | Must-have |
| R4 | A missing or stale index does not break the system — the search agent falls back gracefully | Must-have |
| R5 | Episodic memories are excluded from the index mechanism | Must-have |
| R6 | Light index maintenance (Mon–Sat): verify all directory files have an index entry, remove entries for deleted files, no description regeneration | Must-have |
| R7 | Heavy index rebuild (Sunday): full reindex using haiku subagents per file to generate fresh descriptions, rebuild `MEMORY.md` from scratch, clear stale entries and duplicates | Must-have |
| R8 | Bootstrap uses the same heavy rebuild mechanism to create `MEMORY.md` on first run when the directory already has files | Must-have |
| R9 | Index files are human-readable markdown | Must-have |

## Acceptance Criteria

### Index Structure (R0, R1, R9)

- [ ] Given the memory system is initialized, when `MEMORY.md` exists in `memories/facts/` or `memories/preferences/`, then each entry is a markdown link with a one-line description in the format `[Name](./filename.md): Description`
- [ ] Given a `MEMORY.md` index, when a human opens it, then they can scan the descriptions and understand what each file contains without opening the individual files
- [ ] Given both `memories/facts/` and `memories/preferences/` directories, then each has its own `MEMORY.md` — there is no cross-directory index

### Write Path Index Updates (R2)

- [ ] Given the facts extraction processor creates a new memory file, when the agent finishes writing the file, then the `MEMORY.md` in `memories/facts/` includes a new entry for that file
- [ ] Given the facts extraction processor modifies an existing memory file, when the file content changes significantly, then the agent updates the description in `MEMORY.md` to reflect the new content
- [ ] Given the facts extraction processor deletes a memory file, when the file is removed, then the corresponding entry is removed from `MEMORY.md`
- [ ] Given the preferences extraction processor performs any create/modify/delete, then `memories/preferences/MEMORY.md` is updated identically to facts
- [ ] Given maintenance agents consolidate or merge files, when files are added/removed/renamed, then the relevant `MEMORY.md` reflects the changes

### Read Path — Context Provider (R3)

- [ ] Given a user message that triggers a Full or Shallow search, when the memory context provider searches facts or preferences, then it reads `MEMORY.md` first instead of using Glob to discover files
- [ ] Given the index lists N files with descriptions, when the search agent evaluates relevance, then it selects files based on descriptions alone and reads only the selected files
- [ ] Given the search agent determines no files are relevant from the index, then it returns `NO_RELEVANT_MEMORIES` without reading any individual files
- [ ] Given an episodic search is triggered (Full tier only), then the search agent uses the existing Glob-based discovery — the index is not involved for episodic memories

### Graceful Degradation (R4)

- [ ] Given `MEMORY.md` does not exist in a memory subdirectory, when the search agent needs to search that directory, then it falls back to Glob-based discovery without error
- [ ] Given `MEMORY.md` exists but is empty or malformed, when the search agent reads it, then it falls back to Glob-based discovery without error
- [ ] Given `MEMORY.md` references files that no longer exist, when the search agent tries to read a missing file, then it skips that file and continues with other results

### Episodic Exclusion (R5)

- [ ] Given the episodic memory directory, when the system runs, then no `MEMORY.md` is created or maintained in `memories/episodic/`
- [ ] Given the memory context provider searches episodic memories, when it performs a Full search, then it uses Glob-based discovery (unchanged from current behavior)

### Light Maintenance (R6)

- [ ] Given a light maintenance run (Mon–Sat), when it processes a memory directory, then it verifies every `.md` file in the directory has a corresponding entry in `MEMORY.md`
- [ ] Given a light maintenance run, when it finds files without index entries, then it adds placeholder entries for those files
- [ ] Given a light maintenance run, when it finds index entries pointing to files that no longer exist, then it removes those stale entries
- [ ] Given a light maintenance run, when it completes, then no existing descriptions are regenerated or modified

### Heavy Rebuild (R7)

- [ ] Given a heavy rebuild run (Sunday), when it processes a memory directory, then it reads every `.md` file and generates a fresh description for each using a haiku subagent
- [ ] Given a heavy rebuild run, when it completes, then `MEMORY.md` is rebuilt from scratch with all current files and accurate descriptions
- [ ] Given a heavy rebuild run, when it finds duplicate or stale entries, then they are cleared — the rebuilt index contains only files currently in the directory
- [ ] Given a heavy rebuild run, when a directory is empty, then the resulting `MEMORY.md` is empty (just a header, no entries)

### Bootstrap (R8)

- [ ] Given the system boots and `memories/facts/` has existing files but no `MEMORY.md`, when the bootstrap hook runs, then it triggers a heavy rebuild to create the index
- [ ] Given the system boots and `MEMORY.md` already exists, when the bootstrap hook runs, then it does not trigger a rebuild (idempotent)
- [ ] Given the system boots and the memory directory is empty, when the bootstrap hook runs, then it creates an empty `MEMORY.md` (header only, no entries)
