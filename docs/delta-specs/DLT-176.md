# Delta Spec: DLT-176 - Workflow Tasks as Background Execution

## Story

As a user, I want workflows to run autonomously as background tasks so that the main conversation stays free for interaction while multi-step processes execute independently.

## What It Does

Refactors workflow execution so every workflow runs as a subtype of background tasks. The main agent retains only the `start_workflow` tool — once started, the workflow runs autonomously. Each step fires as a separate background task instance with full step context injected into its initial prompt. Steps communicate through hand-off messages on completion and the shared scratchpad for long-term context. New workflow-specific tools (`complete_step`, `skip_step`, `abort_workflow`, `request_input`) are available only inside the workflow background task session, replacing the current `update_workflow_state` and `end_workflow` tools in the main session.

## Requirements

| ID | Requirement | Status |
|----|-------------|--------|
| R0 | Workflows always execute as background tasks — the main session only starts them via `start_workflow` | Core goal |
| R1 | Remove `update_workflow_state` and `end_workflow` from the main session MCP tools; replace with workflow-specific tools (`complete_step`, `skip_step`, `abort_workflow`, `request_input`) available only inside workflow background task sessions | Must-have |
| R2 | Each workflow step runs as a separate background task instance (fresh SDK session, own DB record) with full step context injected into the initial prompt | Must-have |
| R3 | Step context injection includes: step instructions, resolved required skills, scratchpad path, workflow metadata (ID, skill name, workflow name, step position), and hand-off from previous step | Must-have |
| R4 | Steps communicate through two mechanisms: (a) hand-off message passed as parameter on step completion, relayed to the next step's initial prompt; (b) scratchpad for long-term context referenced by hand-off | Must-have |
| R5 | Completing or skipping a step auto-enqueues the next step as a new background task instance, preserving cascade semantics (composition, loops, conditions) | Must-have |
| R6 | `request_input` tool pauses the workflow task and requests user input via the existing `send_notification(await_response=true)` mechanism; the task resumes in the same SDK session when the user responds | Must-have |
| R7 | Workflow background tasks use a separate `workflow_wait_timeout` config (default 7 days) for steps awaiting user input | Must-have |
| R8 | Existing workflow definition format, state persistence, composition/looping semantics, and recovery tools (`get_workflow_state`, `list_active_workflows`) remain unchanged | Must-have |
| R9 | The workflow-authoring-guide skill is updated to explain the hand-off and scratchpad communication patterns, with guidance for step instructions to use them properly | Must-have |

## Acceptance Criteria

### Workflow Start (R0)

- [ ] Given the main session agent calls `start_workflow`, when the call succeeds, then a workflow state record is created and the first step is enqueued as a pending background task instance — the main agent does not drive steps
- [ ] Given `start_workflow` succeeds, when the tool returns, then the result contains the workflow ID and confirms the workflow is running in the background
- [ ] Given a workflow already active for the same skill+workflow, when `start_workflow` is called again, then the tool returns an error indicating the workflow is already running (returns the existing ID) — unchanged from current behavior
- [ ] Given an invalid skill or workflow name, when `start_workflow` is called, then the tool returns an error — unchanged from current behavior

### Main Session Tool Changes (R1)

- [ ] Given the main session MCP tool servers, when inspected, then `update_workflow_state` and `end_workflow` are NOT present
- [ ] Given the main session MCP tool servers, when inspected, then `start_workflow`, `get_workflow_state`, and `list_active_workflows` ARE present
- [ ] Given a workflow background task session, when its MCP tools are inspected, then `complete_step`, `skip_step`, `abort_workflow`, and `request_input` ARE present
- [ ] Given a workflow background task session, when its MCP tools are inspected, then `update_workflow_state` and `end_workflow` are NOT present (replaced by the new tools)

### Step Execution as Background Task (R2, R3)

- [ ] Given a workflow step is enqueued, when the background task runner picks it up, then a fresh SDK session is created with the step's full context in the initial prompt
- [ ] Given the step's initial prompt, when the background task agent reads it, then it contains: step instructions (from instructions.md), resolved required skills content, scratchpad path, workflow metadata (workflow ID, skill name, workflow name, current step ID, step title, step position within the workflow)
- [ ] Given a step with required_skills, when the step task starts, then the required skills are resolved (transitive chain, deps-first) and injected into the prompt — the agent does not need to read skill files
- [ ] Given a step's initial prompt, when the background task agent reads it, then it contains guidance on available workflow tools (`complete_step`, `skip_step`, `abort_workflow`, `request_input`) and how to use them

### Hand-Off and Scratchpad Communication (R4)

- [ ] Given a step completes via `complete_step(handoff="summary of work done")`, when the next step is enqueued, then the hand-off message is included in the next step's initial prompt
- [ ] Given a step completes without providing a hand-off message, when the next step is enqueued, then the next step's initial prompt has no hand-off section
- [ ] Given a step's initial prompt, when the scratchpad exists and has content, then the prompt includes the scratchpad path and guidance to read it for accumulated context
- [ ] Given the hand-off message, when the next step's agent reads it, then the hand-off can reference scratchpad entries for detailed context

### Cascade and Step Enqueuing (R5)

- [ ] Given a step completes via `complete_step`, when a next pending step exists, then the next step is enqueued as a new pending background task instance automatically
- [ ] Given a step completes via `complete_step`, when no next pending step exists, then the workflow auto-finalizes (soft-delete, scratchpad removed) — unchanged from current behavior
- [ ] Given a step is skipped via `skip_step`, when the step is marked skippable, then the next step is enqueued as a new pending background task instance — cascade preserved
- [ ] Given a composition step activates, when the child workflow spawns, then the child's first step is enqueued as a new background task instance with the parent's workflow context
- [ ] Given a child's last step completes, when the cascade pops back to the parent, then the parent's next step is enqueued as a new background task instance — multi-level cascade preserved
- [ ] Given a loop step starts with items, when each iteration completes, then the next iteration is enqueued as a new background task instance — sequential iteration preserved
- [ ] Given a condition step is reached, when the cascade encounters it, then the step is enqueued with the condition prompt included in the initial prompt, and the step task evaluates it and calls `complete_step` or `skip_step`
- [ ] Given a step completes, when the cascade determines the next step, then the transition uses the same state machine validation as the current `update_workflow_state` (pending → started → completed/skipped)

### User Input Request (R6)

- [ ] Given a workflow step task calls `request_input(question="...")`, when the call succeeds, then a respondable urgent notification is dispatched via `send_notification(await_response=true)` and the task transitions to `waiting`
- [ ] Given a waiting workflow step task, when the user responds, then the task resumes in the same SDK session with the user's response injected
- [ ] Given a step task calls `request_input`, when the call succeeds, then the task's evaluator is NOT called — identical to the existing `await_response=true` behavior for background tasks
- [ ] Given a step task's `request_input` call, when the question is empty or whitespace-only, then the tool returns an error without dispatching a notification

### Workflow Wait Timeout (R7)

- [ ] Given a configuration field `workflow_wait_timeout` with default 7 days, when a workflow task enters `waiting` state, then the expired waiter sweep uses the workflow-specific timeout instead of the default background task timeout
- [ ] Given a non-workflow background task in `waiting` state, when the expired waiter sweep runs, then it uses the standard background task wait timeout — workflow timeout does not affect regular tasks
- [ ] Given a workflow task that has been waiting longer than `workflow_wait_timeout`, when the expired waiter sweep runs, then the task is marked failed and a non-respondable urgent notification is dispatched

### Unchanged Semantics (R8)

- [ ] Given a workflow definition in a skill's `workflows/` directory, when loaded, then the directory structure, step ordering, frontmatter fields, and validation are identical to the current implementation
- [ ] Given an active workflow, when `get_workflow_state` is called, then the response format is identical to the current implementation (step states, composition nesting, loop state)
- [ ] Given `list_active_workflows` is called, when active workflows exist, then the response lists only top-level workflows — unchanged from current behavior
- [ ] Given stale workflow cleanup runs, when a workflow's freshest `updated_at` exceeds the threshold, then the entire stack is soft-deleted atomically — unchanged from current behavior
- [ ] Given a workflow's state is persisted in the database, when the process restarts, then the state is recoverable via `get_workflow_state` — unchanged from current behavior

### Workflow Authoring Guide (R9)

- [ ] Given the workflow-authoring-guide skill, when read by the agent, then it explains the hand-off mechanism (pass context to next step via `complete_step(handoff=...)`)
- [ ] Given the workflow-authoring-guide skill, when read by the agent, then it explains the scratchpad mechanism (accumulate long-term context, reference it in hand-offs)
- [ ] Given the workflow-authoring-guide skill, when read by the agent, then it provides guidance on writing step instructions that properly use hand-offs and scratchpad
