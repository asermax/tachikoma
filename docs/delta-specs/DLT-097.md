# Delta Spec: DLT-097 - Keep local repositories in sync with remotes

<!-- This spec describes WHAT the delta does, not HOW it's implemented. -->
<!-- Technical Delta: git synchronization infrastructure -->

## Story

As the system, I need to keep local repositories synchronized with their remotes so that the agent works with up-to-date repository state and can push changes without conflicts.

## What It Does

Replaces bare git pushes with a fetch-detect-resolve-push sequence in both post-processors (workspace and project submodules), adds agent-driven conflict resolution when remote divergence is detected, and introduces workspace and project sync at startup with the same conflict resolution approach. On unresolvable conflicts, local commits are preserved for retry at the next sync opportunity. When remotes are unreachable, the system degrades gracefully — logging warnings and continuing with local state.

## Acceptance Criteria

### Workspace Startup Sync (R1)

- [ ] Given an origin remote is configured and .git exists, when the git bootstrap hook runs, then the workspace is fetched from origin and local is rebased onto the remote branch
- [ ] Given no origin remote is configured, when the git bootstrap hook runs, then sync is skipped silently (no-op)
- [ ] Given a newly initialized repository with no local commits and an origin remote, when sync runs, then the remote branch is fetched and local is fast-forwarded to match remote
- [ ] Given the fetch fails (network error), when sync runs, then the failure is logged and startup continues (non-blocking) — project submodule sync still runs independently
- [ ] Given uncommitted local changes exist in the workspace, when startup sync runs, then sync is skipped for the workspace, a warning is logged, and the workspace remains in its current state

### Project Submodule Startup Sync (R2)

- [ ] Given registered submodules exist, when the projects bootstrap hook runs, then all submodules are fetched and divergence checked before pulling
- [ ] Given a submodule has diverged from its remote, when startup sync detects divergence, then a Haiku agent is spawned to resolve conflicts and complete the pull
- [ ] Given the conflict resolution agent fails for a submodule, when resolution is unresolvable, then the submodule is left in its pre-sync state and the failure is logged (non-blocking for other submodules)
- [ ] Given no submodules are registered, when the hook runs, then it completes as a no-op
- [ ] Given uncommitted local changes exist in a submodule, when startup sync runs, then sync is skipped for that submodule, a warning is logged, and the submodule remains in its current state

### Push with Divergence Detection (R3, R4, R7, R8)

- [ ] Given sync/push runs, when the operation begins, then `git fetch` is always executed first to obtain latest remote state (R8)
- [ ] Given commits to push and remote is an ancestor of local (fast-forward), when push runs, then it pushes directly (same as current behavior)
- [ ] Given commits to push and remote has diverged (remote is not an ancestor of local), when push runs, then a Haiku agent is spawned to inspect local and remote changes, resolve conflicts, rebase locally, and push the result
- [ ] Given the conflict resolution succeeds, when the agent completes, then local commits are rebased on top of remote and pushed
- [ ] Given conflict resolution completes, when the repository state is verified, then no merge commits exist and `git log --oneline --graph` shows a linear sequence (R7)

### Conflict Resolution Failure Modes (R4, R5)

- [ ] Given the conflict resolution agent times out or encounters an API error, when the execution fails, then local commits are preserved intact, the push is aborted, and a warning is logged
- [ ] Given the conflict resolution agent explicitly signals it cannot resolve the conflicts, when the agent completes with failure, then local commits are preserved intact, the push is aborted, and a warning is logged with details about the conflicting files
- [ ] Given the conflict resolution agent produces an invalid result (conflict markers remain, or repo is in broken state), when the result is validated, then the rebase is aborted, local commits are restored, and a warning is logged
- [ ] Given a previous push was aborted due to unresolvable conflicts, when the next sync opportunity runs (startup or session close), then unpushed local commits are detected ahead of origin and resolution is retried

### Error Isolation (R6)

- [ ] Given multiple submodules need push, when one submodule's push/resolution fails, then other submodules continue processing independently
- [ ] Given the workspace push fails, when the failure occurs, then it does not affect project submodule pushes (and vice versa)
- [ ] Given a submodule's remote is unreachable, when push is attempted, then the failure is logged and the submodule's local state is preserved
