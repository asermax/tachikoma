# Delta Spec: DLT-112 - Buffer background task notifications until conversation is idle

## Story

As a user, I want background task notifications to wait for a natural pause in our conversation so that urgent results still reach me quickly while routine updates don't interrupt what I'm doing.

## What It Does

Notifications and session tasks are buffered until the conversation is idle instead of being delivered immediately. Three priority levels — Urgent, Normal, Low — determine how long items wait for a natural pause and how long they can be held before being force-delivered. A unified buffer component handles both notification and session task delivery, replacing the current pattern where notifications are injected as steering messages and session tasks use a separate idle-gated scheduler.

## Requirements

| ID | Requirement | Status |
|----|-------------|--------|
| R0 | Notifications from background tasks are never delivered as steering messages — they always arrive as separate conversation turns | Core goal |
| R1 | A unified priority buffer handles both notifications and session tasks, extensible for future item types | Must-have |
| R2 | Three priority levels (Urgent/Normal/Low) determine both queue ordering and timing parameters | Must-have |
| R3 | Only the front item's timing is active; subsequent items' timers start fresh when they reach the front of the queue | Must-have |
| R4 | When the front item's idle window is satisfied, it is delivered as a new message turn | Must-have |
| R5 | When the front item's max hold period expires, it is force-delivered regardless of conversation activity | Must-have |
| R6 | All automatic failure notifications from the executor default to Urgent priority | Must-have |
| R7 | Notifications carry a priority field, defaulting to Normal | Must-have |
| R8 | The `send_notification` MCP tool accepts an optional priority parameter (defaults to Normal) | Nice-to-have |
| R9 | Both Telegram and REPL channels support the buffered delivery pattern | Must-have |
| R10 | Session tasks are routed through the unified buffer at Normal priority (replacing direct idle-gated dispatch) | Must-have |
| R11 | The buffer's check frequency is sufficient to honor the shortest idle window (Urgent: 30s) | Must-have |

**Priority timing parameters:**

| Priority | Label | Idle Window | Max Hold |
|----------|-------|-------------|----------|
| 1 | Urgent | 30s | 2 min |
| 2 | Normal | 2 min | 15 min |
| 3 | Low | 5 min | Never force-delivered |

**Queue ordering:** Urgent items always at front (FIFO within tier), Normal notifications and session tasks interleave by arrival order in the middle tier, Low items always at back (FIFO within tier).

## Acceptance Criteria

### Core delivery guarantee (R0)

- [ ] Given a background task completes and dispatches a notification while the user is in an active conversation, when the notification is produced, then it is enqueued in the priority buffer instead of being injected into the coordinator's message buffer
- [ ] Given a buffered notification is delivered, when it reaches the channel, then it is processed as a new separate message turn through the coordinator (not appended to an ongoing exchange)

### Unified priority buffer (R1)

- [ ] Given the buffer component is running, when a `Notification` event is produced, then it is enqueued into the priority buffer
- [ ] Given the buffer component is running, when a session task becomes ready, then it is enqueued into the priority buffer at Normal priority
- [ ] Given the buffer contains items of different types (notifications and session tasks), when delivery conditions are met, then both types are delivered through the same mechanism
- [ ] Given the buffer is running with no items enqueued, then it idles without side effects until an item arrives
- [ ] Given the process starts up, then the buffer initializes empty (buffered items are not persisted across restarts; session task instances remain pending in the database and are re-detected by the scheduler)
- [ ] Given the process receives a graceful shutdown signal (SIGTERM/SIGINT), then pending buffered items are discarded (session task instances remain pending in the database for the next run)
- [ ] Given the buffer's internal loop encounters an error, then the error is logged and the loop continues on the next cycle without affecting the coordinator or channels

### Priority ordering and timing (R2, R3)

- [ ] Given multiple items are buffered at different priority levels, then Urgent items are always ahead of Normal items, and Normal items are always ahead of Low items
- [ ] Given multiple items are buffered at the same priority level, then they are ordered by arrival time (FIFO within tier)
- [ ] Given an Urgent notification is enqueued while Normal and Low items are already buffered, then the Urgent notification is placed ahead of all Normal and Low items (but behind any existing Urgent items)
- [ ] Given the front item is delivered, when the next item reaches the front, then its idle window countdown starts fresh from that moment (not from when it was enqueued)
- [ ] Given a Normal item is at the front of the queue and has accumulated T seconds of front-time, when an Urgent item is enqueued and preempts it, then when the Normal item returns to the front its idle window starts fresh but its max hold timer does NOT reset (total front-time accumulates across preemptions)

### Idle-gated delivery (R4)

- [ ] Given the front item has an idle window of N seconds, when `now - coordinator.last_message_time >= N`, then the item is delivered as a new message turn
- [ ] Given the front item's idle window is not yet satisfied, then the item remains buffered and is checked again on the next cycle
- [ ] Given `coordinator.last_message_time` is None (no messages exchanged yet), then the idle window is not considered satisfied — items remain buffered until the first message exchange establishes a timestamp

### Force-delivery on hold expiry (R5)

- [ ] Given the front item's accumulated front-time exceeds its max hold period, when the coordinator is not busy, then it is force-delivered as a new message turn
- [ ] Given the front item's accumulated front-time exceeds its max hold period but the coordinator is mid-response, then force-delivery waits until the current response completes (effectively extending the hold period by the response duration)
- [ ] Given the front item has priority Low (max hold = never), then it is never force-delivered — it waits indefinitely for the idle window to be satisfied

### Error notification priority (R6)

- [ ] Given a background task fails (stuck, error, max iterations, or any future failure mode), when the executor dispatches an automatic failure notification, then the notification is enqueued with Urgent priority
- [ ] Given the agent within a background task calls `send_notification` without specifying priority, then the notification is enqueued with Normal priority

### Notification priority field (R7)

- [ ] Given the `Notification` event class, then it has a `priority` field with a default value of Normal (2)
- [ ] Given `dispatch_notification()` is called, then it accepts an optional `priority` parameter that is set on the resulting `Notification` event

### send_notification priority parameter (R8)

- [ ] Given a background task agent calls `send_notification` with a `priority` argument, then the notification is enqueued with the specified priority level
- [ ] Given a background task agent calls `send_notification` without a `priority` argument, then the notification defaults to Normal priority
- [ ] Given the background task system prompt, then it documents the available priority levels (Urgent, Normal, Low), their intended use (Urgent for time-sensitive results, Normal for standard completion results, Low for informational updates), and the default (Normal)

### Channel support (R9)

- [ ] Given the Telegram channel is active, when the buffer delivers an item, then the channel routes it through the coordinator as a new message turn
- [ ] Given the REPL channel is active, when the buffer delivers an item, then the channel routes it through the coordinator as a new message turn
- [ ] Given the coordinator is mid-response when the buffer determines an item is ready for delivery, then the buffer waits for the coordinator to finish before dispatching (delivery only occurs when the coordinator is not busy)

### Session task unification (R10)

- [ ] Given a session task instance becomes ready (cron match, pending status), when the session task scheduler detects it, then the scheduler enqueues it into the unified buffer at Normal priority instead of dispatching a `SessionTaskReady` event directly
- [ ] Given a session task is at the front of the buffer and the Normal idle window (2 min) is satisfied, then the session task is delivered through the coordinator
- [ ] Given the session task scheduler, then it no longer performs its own idle gating — idle timing is handled entirely by the buffer
- [ ] Given a session task is delivered through the buffer and the coordinator completes processing it, then the session task instance is marked as completed (same lifecycle as current direct dispatch)

### Successive deliveries and check frequency (R4, R11)

- [ ] Given the front item is delivered and the delivery updates `coordinator.last_message_time`, when the next item moves to the front, then its idle window starts from the delivery timestamp (preventing rapid-fire delivery of queued items)
- [ ] Given the buffer's check frequency, then it is sufficient to honor the shortest idle window — checks occur more frequently than every 30 seconds

## Requires

Dependencies:
- None

Supersedes:
- **DLT-103** (Defer session tasks until user idle instead of silently skipping) — the unified buffer implements DLT-103's core mechanism: session tasks are enqueued and held until idle rather than silently skipped. DLT-103's staleness policy (discard deferrals older than N hours) is not addressed by this delta and can be pursued independently if needed.
