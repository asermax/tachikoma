# Delta Spec: DLT-160 — Loop iteration via workflow composition

## Story

As a skill developer, I want a step to iterate a referenced workflow once over each item in an agent-provided list so that I can express batch-processing flows (process every inbox note, send every reminder) without unrolling the steps by hand or relying on agent self-looping.

## What It Does

Adds a `loop` frontmatter field that points a step at another workflow. When the step activates, the agent supplies a list of string items inline via the existing `update_workflow_state` start action; the engine runs the referenced workflow once per item as a composition child, exposing the current item in each iteration's tool response. After the last item, the loop step auto-completes and the parent advances. Items are opaque references the iteration body interprets — no counters, no continuation predicate, no max cap. Cycles in the combined composition + loop graph are rejected at registry load.

## Acceptance Criteria

### Loop frontmatter parsing (R1)

- [ ] Given a step's frontmatter contains `loop: "<workflow>"`, when the workflow definition is loaded, then `loop` is preserved as a string on the step definition
- [ ] Given a step's frontmatter contains a `loop` value that is not a string, when the workflow definition is loaded, then a warning is logged and the step's `loop` is `None` (the step still loads)
- [ ] Given a step's frontmatter contains `loop: ""` (empty string), when registry validation runs, then the parent workflow is rejected with a malformed-loop warning
- [ ] Given `loop: "<workflow>"` (no slash), when resolved at validation time, then the target is `(parent_skill, "<workflow>")` — same-skill resolution
- [ ] Given `loop: "<skill>/<workflow>"`, when resolved at validation time, then the target is `(<skill>, <workflow>)` — cross-skill resolution
- [ ] Given a `loop` value contains multiple slashes (e.g., `a/b/c`), when registry validation runs, then the parent workflow is rejected with a malformed-loop warning
- [ ] Given a `loop` target does not exist in the registry, when validation runs, then the parent is rejected with a missing-target warning identifying the parent and the target
- [ ] Given a `loop` target has zero steps, when validation runs, then the parent is rejected with a zero-step-target warning

### Items parameter (R2, R4)

- [ ] Given a loop step is being started, when `update_workflow_state(workflow_id, <loop_step>, "start", items=["a", "b"])` is called, then the items list is persisted on the loop step's state and the first iteration's child is spawned with the first item as the current item
- [ ] Given a loop step is being started without items, when `update_workflow_state(..., "start")` is called, then the tool returns an error indicating items are required for loop steps
- [ ] Given a non-loop step is being started, when `update_workflow_state(..., "start", items=[...])` is called, then the tool returns an error indicating items are not allowed for non-loop steps
- [ ] Given items contains non-string values (numbers, dicts, nulls), when `update_workflow_state` is called, then the tool returns a validation error
- [ ] Given items is not a list (e.g., a single string, a dict), when `update_workflow_state` is called, then the tool returns a validation error
- [ ] Given items contains duplicate strings, when start is called, then duplicates are accepted as-is (the agent decides whether duplication is meaningful)

### Iteration spawning (R3, R7)

- [ ] Given a loop step is started with items=["a", "b", "c"], when iteration 0 spawns, then a child workflow record is created with parent_workflow_id pointing at the parent and parent_step_id pointing at the loop step, with the same scratchpad path as the parent
- [ ] Given iteration N's child finalizes (last step completed/skipped), when the cascade pops, then iteration N+1's child is spawned in the same tool call (single response returns iteration N+1's first step instructions)
- [ ] Given the last iteration's child finalizes, when the cascade pops, then the loop step is marked `completed`, the parent's next pending step auto-starts (or the top-level auto-finalizes if the loop step was the parent's last)
- [ ] Given an iteration body contains nested composition (`composes` step) or further loop steps, when the iteration runs, then those features behave identically to top-level composition (no special loop-context behavior)
- [ ] Given an iteration's child is spawned, when its definition snapshot is captured, then it reflects the current registered loop target (per-spawn snapshot, consistent with composition spawn semantics)
- [ ] Given iterations run, when the agent processes them, then they run sequentially in the order the agent supplied (item 0 → item 1 → item 2, no parallelism, no skipping ahead)

### Current-item exposure (R5, R17)

- [ ] Given an iteration's first step activates, when the tool response is returned, then the response surfaces the current item value alongside the active step (e.g., "Current item: <value>" or as a breadcrumb suffix)
- [ ] Given any tool call inside an iteration (start / complete / skip / get_workflow_state), when the response is returned, then the breadcrumb continues to identify the current item until the iteration's child finalizes
- [ ] Given a loop step is active, when `get_workflow_state(parent_id)` is called, then the response shows the items list, the current iteration index, the current item, and the active iteration's nested view
- [ ] Given the engine processes an iteration, when each iteration spawns, then the engine does not modify the scratchpad file with the current item (scratchpad remains agent-managed)

### Empty list and exhaustion (R6)

- [ ] Given a loop step is started with items=[], when the engine processes the start, then no child is spawned, the loop step is marked `completed`, and the parent's next pending step auto-starts (cascade behavior identical to a normal completion)
- [ ] Given a loop step with empty items completes, when the response is returned, then it indicates the loop step completed with zero iterations
- [ ] Given the loop step is the parent's last step and items=[], when start is called, then the top-level workflow auto-finalizes (cascade matches a normal last-step completion)

### Loop step frontmatter interactions (R8)

- [ ] Given a loop step has `condition: "<predicate>"`, when start is called and the condition fails, then the loop step is condition-skipped without spawning any iteration; no items are required (the action is rejected pre-condition); the cascade advances to the next pending step
- [ ] Given a loop step has `condition` and the condition passes, when start is called with items, then the first iteration spawns normally
- [ ] Given a loop step has `required: false`, when the agent calls `action="skip"` (no items), then the loop step is skipped, no iterations are spawned, and the cascade advances
- [ ] Given a loop step has `required_skills: [...]`, when start is called with items, then those skills are resolved via the registry and emitted in the activation response (alongside the first iteration's first step's required_skills, deduplicated across both layers)
- [ ] Given a loop step is activated, when the engine processes it, then the step's `instructions.md` body is not read at runtime — only frontmatter is honored (consistent with composition)

### Loop + composes mutex (R9)

- [ ] Given a step's frontmatter declares both `loop` and `composes`, when the registry validates the workflow, then the parent workflow is rejected with a warning identifying the conflicting fields, and the workflow is removed from the registry

### Cycle detection (R10)

- [ ] Given workflow `A` has a step with `loop: A`, when registry validation runs, then `A` is rejected with a self-reference cycle warning
- [ ] Given workflow `A` has a step with `loop: B` and workflow `B` has a step with `composes: A`, when registry validation runs, then both `A` and `B` are rejected with cycle warnings (loop edges treated identically to composes edges in the cycle graph)
- [ ] Given workflow `A` has a step with `loop: B` and workflow `B` has a step with `loop: A`, when registry validation runs, then both are rejected with cycle warnings
- [ ] Given a non-cyclic loop graph (`A` loops `B`, `B` does not reference `A`), when registry validation runs, then both workflows load successfully

### Persistence and recovery (R11)

- [ ] Given a loop step is started with items, when the workflow state is persisted, then the items list and the current iteration index are stored as part of the parent workflow state record
- [ ] Given context loss between iteration N completing and iteration N+1 starting, when the agent calls `get_workflow_state(top_level_id)`, then the response shows the items list, current iteration index, current item, and the active layer state
- [ ] Given the agent recovers via `list_active_workflows` after a process restart, when the loop step is mid-iteration, then the parent workflow surfaces (the in-flight iteration child does not surface, consistent with composition's top-level-only listing)
- [ ] Given a loop step's items are persisted, when an iteration's child fails or is aborted via `end_workflow`, then the items list and index remain on the parent record (recovery still possible after the cascade abort scope is resolved)

### Auto-start halts at loop steps (R12)

- [ ] Given the previous step completes and the next pending step is a loop step, when the cascade auto-advances, then auto-start halts at the loop step (the loop step is NOT auto-started); the response indicates "Next step is a loop step. Call `update_workflow_state(..., action='start', items=[...])` to begin iterating."
- [ ] Given the previous step is skipped (or condition-skipped) and the next pending step is a loop step, when the cascade evaluates the next step, then the same halt-and-prompt behavior applies
- [ ] Given the loop step's halt point is reached, when the response is returned, then the loop step's state is `pending` (not `started`) — the step is not partially activated until the agent provides items

### Single-ID routing (R13)

- [ ] Given an iteration's child is active, when the agent calls `update_workflow_state(top_level_id, <iteration_step>, <action>)`, then the action routes to the deepest active iteration child (existing deepest-active routing behavior)
- [ ] Given the agent passes a step ID that doesn't match the deepest iteration's snapshot, when the routing runs, then the standard error fires naming the deepest layer's workflow and listing valid step IDs
- [ ] Given the agent calls `update_workflow_state(<iteration_child_id>, ...)` directly with the child's ID, then the tool returns the existing child-ID rejection error directing the agent to the top-level workflow

### Mid-iteration error atomicity (R14)

- [ ] Given a cascade is in flight (e.g., spawning iteration N+1 after N's auto-finalize) and an error is raised mid-flight, when the error propagates, then no state is written, the iteration child remains in its prior state, and the agent can retry

### System preamble (R15)

- [ ] Given the system preamble is assembled, when the Workflows section is rendered, then it documents: the `loop` frontmatter field, the `items` parameter on `start`, current-item exposure in tool responses, auto-completion when items are exhausted, mutual exclusion with `composes`, items required for loop steps, and the auto-start halt behavior

### Workflow-authoring-guide (R16)

- [ ] Given the built-in `workflow-authoring-guide` skill is loaded, when the agent reads the step-design reference, then the `loop` field is documented alongside `composes` and `condition`, including a worked example showing a producer step that returns the items and a loop step that processes each item
