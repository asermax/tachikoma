# Delta Spec: DLT-117 - Attach specific skills to task definitions

## Story

As the system, I need task definitions to declare specific skills that are always loaded at execution time so that the agent has guaranteed access to domain knowledge regardless of how well LLM-based skill classification matches the task prompt.

## What It Does

Adds an optional `skills` field to task definitions. When a task executes — whether as a background task or a session task — the named skills are resolved from the skill registry (including transitive dependencies) and loaded unconditionally into context before the classification step runs. The task creation and update MCP tools expose this field so the agent can attach skills when defining tasks.

## Requirements

| ID | Requirement | Status |
|----|-------------|--------|
| R0 | Task definitions can declare an optional list of skill names to load unconditionally at execution time | Core goal |
| R1 | Named skills are resolved from the skill registry with transitive dependencies and loaded before LLM-based skill classification runs | Must-have |
| R2 | The `create_task` and `update_task` MCP tools accept a `skills` parameter | Must-have |
| R3 | The `get_task` and `list_tasks` MCP tools display attached skills | Must-have |
| R4 | Invalid or nonexistent skill names produce warnings but do not block task creation or execution | Must-have |
| R5 | Both session and background tasks support pinned skills | Must-have |
| R6 | Skill authoring documentation reflects the ability to pin skills to task definitions | Nice-to-have |

## Acceptance Criteria

### Task Definition Model (R0)

- [ ] Given a new task definition, when created with a `skills` list, then the skill names are persisted alongside the definition
- [ ] Given a new task definition, when created without a `skills` list, then the definition is valid with an empty skills list
- [ ] Given a task definition with skills, when retrieved from persistence, then the skill names are returned unchanged

### Skill Loading at Execution (R1)

- [ ] Given a background task definition with pinned skills, when the task executes, then the named skills (and their transitive dependencies) are loaded as context entries before the SkillsContextProvider classification runs
- [ ] Given a session task definition with pinned skills, when the task is delivered during idle time, then the named skills (and their transitive dependencies) are loaded as context entries before the normal pre-processing pipeline runs
- [ ] Given pinned skills loaded as context entries, when the SkillsContextProvider runs classification, then it skips re-classifying those skills (they appear in existing entries, detected via `skill_name` metadata)
- [ ] Given a task definition with no pinned skills, when the task executes, then execution proceeds identically to today (classification-only skill loading)
- [ ] Given multiple pinned skills with overlapping transitive dependencies, when skills are resolved, then each skill appears exactly once in dependency-first order (matching existing `resolve_chain()` behavior)
- [ ] Given pinned skills that include agent definitions, when the task executes, then those agents are derived from the skill entries and available to the task agent via the normal `derive_agents_from_entries()` flow

### MCP Tools — Create and Update (R2)

- [ ] Given the agent calls `create_task` with a `skills` parameter containing valid skill names, then the task definition is created with those skills attached
- [ ] Given the agent calls `create_task` without a `skills` parameter, then the task definition is created with an empty skills list (backward compatible)
- [ ] Given the agent calls `update_task` with a `skills` parameter, then the definition's skills list is replaced with the new value
- [ ] Given the agent calls `update_task` with `skills=[]` (explicit empty list), then the definition's skills list is cleared
- [ ] Given the agent calls `update_task` without a `skills` parameter, then the definition's skills list remains unchanged

### MCP Tools — Display (R3)

- [ ] Given the agent calls `get_task` on a definition with pinned skills, then the response includes a skills section listing the skill names
- [ ] Given the agent calls `get_task` on a definition with no pinned skills, then the response omits the skills section
- [ ] Given the agent calls `list_tasks`, then each task entry includes a compact indication of attached skills (skill names or count)

### Invalid Skill Handling (R4)

- [ ] Given the agent calls `create_task` with skill names that are not in the current registry, then the tool warns about unknown names in the response text (not as an error response) but still creates the definition
- [ ] Given the agent calls `update_task` with skill names that are not in the current registry, then the tool warns about unknown names in the response text but still updates the definition
- [ ] Given a task definition with pinned skills, when the task executes and some skills are not in the registry, then a warning is logged and execution proceeds with the skills that do resolve
- [ ] Given a task definition where none of the pinned skills resolve, when the task executes, then a warning is logged and the task proceeds with classification-only skill loading
- [ ] Given a pinned skill whose transitive dependencies include names not in the registry, when the task executes, then unknown dependencies are silently skipped (matching existing `resolve_chain()` behavior) and the skill loads with whatever dependencies resolve

### Session and Background Coverage (R5)

- [ ] Given a background task definition with pinned skills, when executed by the background task runner, then pinned skills are injected into the pre-processing results
- [ ] Given a session task definition with pinned skills, when the scheduler enqueues it for delivery, then the pinned skills are resolved and their content is injected as context entries via the BufferedItem metadata before the coordinator processes the message
- [ ] Given an ad-hoc background task (via `run_task_now` with `prompt` only), when no skills are specified, then execution proceeds with classification-only skill loading (ad-hoc tasks have no definition to pin skills to)
- [ ] Given a by-reference background task (via `run_task_now` with `task_id`), when the definition has pinned skills, then those skills are loaded during execution (the definition is snapshotted, including its skills list, just like the prompt)
