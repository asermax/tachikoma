# DLT-048: Plugin system with install, discovery, and loading

## Story

As a Tachikoma user, I want to install third-party plugins that contribute skills so that I can extend the agent with capabilities authored by the community without modifying core code.

## What It Does

Introduces a directory-based plugin system. Users declare plugin sources in a `[plugins]` config section — either a git repository (repo URL + folder path within the repo + pinned ref) or a local filesystem path. At startup, a bootstrap step reconciles `workspace/.tachikoma/plugins/` with the declared sources by always re-materializing each plugin from its source: it shallow-clones git repos and copies the configured subfolder, or copies from local paths, replacing the existing install directory contents. Orphan directories not in config are removed. The plugin loader then parses each plugin's manifest — preferring the Tachikoma-native `tachikoma-plugin.toml`, falling back to Claude Code's `.claude-plugin/plugin.json` when present — and registers each plugin's contributed skill directories with the existing `SkillRegistry` under namespaced names of the form `<alias>:<skill-name>`. Three MCP tools (`install_plugin`, `list_plugins`, `remove_plugin`) let the agent manage plugins on the user's behalf without restart. Failures (fetch errors, malformed manifests, broken skills) are isolated per plugin and never block startup; reconciliation falls back to a previously fetched copy if a source becomes unreachable.

This delta is intentionally scoped to **skills only**. Plugin contributions of MCP tool servers, slash commands, context providers, post-processors, secondary channels, and boundary hooks are out of scope and are tracked by DLT-049 / DLT-050 / DLT-051 / DLT-053. CC plugins that declare non-skill contributions install successfully but their non-skill contributions are silently ignored (logged at INFO level, one line per skipped contribution type per plugin) for forward compatibility. DLT-048 also subsumes DLT-056 (plugin removal) by including the `remove_plugin` MCP tool.

### Plugin lifecycle

`declare in [plugins] config` → `bootstrap reconciles install dir` → `loader parses manifest` → `registers namespaced skills with SkillRegistry` → `next message classification sees plugin skills`

## Requirements

| ID  | Requirement | Status |
|-----|-------------|--------|
| R0  | Provide a plugin system that lets users extend Tachikoma with skills contributed by third-party plugins, declared in config and reconciled at startup | Core goal |
| R1  | `[plugins]` TOML config section uses sub-table form `[plugins.<alias>]`; each entry declares one of three mutually-exclusive source variants: a **git source** (`git` URL or `gh:owner/repo` / `github:owner/repo` shorthand, `subdir` optional, `ref` required and constrained to branch/tag names — bare commit SHAs rejected at validation time), a **url source** (`url` field pointing to an HTTPS-served `.tar.gz` / `.tgz` / `.zip` archive, `subdir` optional), or a **local source** (`path` field, absolute filesystem path) | Must-have |
| R2  | At startup, a bootstrap step reconciles `workspace/.tachikoma/plugins/` with `[plugins]` config: always re-materialize each plugin from its source (overwriting the install directory atomically — write to a sibling directory, then atomic rename); materialization differs per source kind — git sources are shallow-cloned (`git clone --depth 1 --branch <ref>`) and the configured `subdir` is copied; url sources are downloaded over HTTPS, extracted (auto-stripping a single leading top-level directory if present, then drilling into `subdir` if specified); local sources are copied directly. Orphaned directories not declared in config are removed | Must-have |
| R3  | Plugins use a Tachikoma-native manifest file `tachikoma-plugin.toml` at the plugin folder root that declares plugin metadata (name, version, description) and contributed skill directory paths (relative to the plugin folder) | Must-have |

| R5  | Discovered plugin skill directories are added as sources to the existing `SkillRegistry`. Plugin-contributed skills are registered under namespaced names of the form `<alias>:<skill-name>`. Plugin namespaces are isolated: plugin skills cannot collide with built-in, workspace, or other plugin skills | Must-have |
| R6  | Plugin alias is the `[plugins.<alias>]` sub-table key. Convention: alias matches the manifest-declared name. The user can choose a different sub-table key to override the manifest name. The `install_plugin` MCP tool accepts an optional `alias` argument that becomes the sub-table key when provided. Aliases must match the regex `[a-z0-9][a-z0-9-]*` (lowercase, no `:` or other reserved characters) | Must-have |
| R7  | Validate each plugin's manifest and declared skill directories before loading; reject malformed plugins with a diagnostic that names the offending file/field/issue and surfaces both to logs (WARNING/ERROR level) and to the `list_plugins` MCP tool response (status field + diagnostic message) | Must-have |
| R8  | Resilient reconciliation: when a configured plugin's source cannot be re-materialized but the install directory still contains a valid manifest matching the alias, retain that copy, mark its status as `stale-fallback`, and log a warning. If the install directory is missing or its manifest does not match, mark `failed` instead | Must-have |
| R9  | Fail-safe loading: a plugin that fails to fetch, validate, or load is logged and skipped without affecting other plugins or core startup. Per-plugin failure isolation applies in materialization, discovery, manifest parsing, and registry registration | Must-have |
| R10 | MCP tool `install_plugin` validates the source spec, materializes the plugin into a temp location, parses its manifest, then writes the new `[plugins.<alias>]` entry to config (validate-then-write order) and triggers a registry refresh so the plugin is usable on the next message; supports an optional `alias` argument; errors on alias collision with an existing entry without mutating config | Must-have |
| R11 | MCP tool `list_plugins` returns all installed plugins with metadata (alias, source spec, ref, validation status from the enum `loaded` / `stale-fallback` / `failed`, diagnostic message if non-`loaded`, and the namespaced names of contributed skills) | Must-have |
| R12 | MCP tool `remove_plugin` removes a plugin's `[plugins.<alias>]` entry and cleans up its install directory; the registry refreshes so the plugin's namespaced skills are no longer available. Subsumes DLT-056 | Must-have |
| R13 | The plugins install directory (`workspace/.tachikoma/plugins/`) is added to workspace `.gitignore` since it is regenerable from config; the entry is appended idempotently by the plugins bootstrap hook on every startup | Must-have |
| R14 | **Out of scope**: plugins do not contribute MCP tool servers, slash commands, context providers, post-processors, secondary channels, or boundary hooks in this delta. Those contribution surfaces are deferred to DLT-049 / DLT-050 / DLT-051 / DLT-053 | Out |

## Acceptance Criteria

### Plugin source declaration (R1, R6)

- [ ] **AC-PSD-1**: Given a `[plugins.code-review]` sub-table with `git`, `subdir`, and `ref` fields, when settings load, then the entry is parsed as a git-source plugin with alias `code-review`
- [ ] **AC-PSD-2**: Given a `[plugins.dev-plugin]` sub-table with a `path` field pointing to an absolute filesystem path, when settings load, then the entry is parsed as a local-source plugin
- [ ] **AC-PSD-3**: Given a sub-table with more than one source-discriminator field populated (any combination of `git`, `url`, `path`), when settings load, then validation fails with an error naming the populated fields and stating they are mutually exclusive
- [ ] **AC-PSD-4**: Given a git-source sub-table without a `ref` field, when settings load, then validation fails with an error naming the missing `ref` field
- [ ] **AC-PSD-5**: Given a local-path source with a relative path, when settings load, then validation fails with an error stating that an absolute path is required
- [ ] **AC-PSD-6**: Given a sub-table key containing reserved characters (e.g., `:`, `/`) or uppercase letters, when settings load, then validation fails with an error stating the alias must match `[a-z0-9][a-z0-9-]*`
- [ ] **AC-PSD-7**: Given the user's sub-table key matches the manifest-declared name (e.g., key `code-review` and manifest `name = "code-review"`), when the plugin loads, then the active alias is `code-review`
- [ ] **AC-PSD-8**: Given the user's sub-table key differs from the manifest-declared name (e.g., key `my-cr` and manifest `name = "code-review"`), when the plugin loads, then the active alias is `my-cr` (sub-table key wins)
- [ ] **AC-PSD-9**: Given two `[plugins.<alias>]` sub-tables with the same alias, when settings load, then TOML parsing rejects the duplicate (TOML's native constraint — no additional Tachikoma logic required)
- [ ] **AC-PSD-10**: Given a git-source sub-table whose `git` field is `gh:owner/repo` or `github:owner/repo`, when settings load, then the value is expanded to `https://github.com/owner/repo.git` in the in-memory model while the original TOML form is preserved on disk; downstream materialization treats the entry as a normal git source
- [ ] **AC-PSD-11**: Given a git-source sub-table whose `ref` matches the SHA-shaped regex `^[0-9a-f]{7,40}$`, when settings load, then validation fails with an error stating that `ref` must be a branch or tag name, not a commit SHA
- [ ] **AC-PSD-12**: Given a url-source sub-table whose `url` field uses any scheme other than `https://`, when settings load, then validation fails with an error stating only HTTPS URLs are supported
- [ ] **AC-PSD-13**: Given a url-source sub-table whose `url` field has an extension other than `.tar.gz`, `.tgz`, or `.zip`, when settings load, then validation fails with an error naming the recognized extensions
- [ ] **AC-PSD-14**: Given a `[plugins.foo]` url-source sub-table with `url = "https://example.com/plugin.tar.gz"` and no `subdir`, when settings load, then the entry is parsed as a url-source plugin with alias `foo`

### Plugin reconciliation at startup (R2, R8, R9)

- [ ] **AC-REC-1**: Given a `[plugins.foo]` git-source entry, when reconciliation runs, then a shallow clone of the configured `git` URL at the configured `ref` is performed into a temp location, the configured `subdir` is copied into a sibling directory `.tachikoma/plugins/foo.new/`, the previous `.tachikoma/plugins/foo/` is replaced via atomic rename, and the temp clone is discarded
- [ ] **AC-REC-2**: Given a `[plugins.foo]` local-path entry, when reconciliation runs, then the configured path's contents are copied into a sibling directory `.tachikoma/plugins/foo.new/` and atomic-renamed over `.tachikoma/plugins/foo/`
- [ ] **AC-REC-3**: Given any reconciliation operation (git or local), when materialization fails mid-copy (disk full, permission denied, path issue), then the partially-written sibling directory is discarded, the existing `.tachikoma/plugins/foo/` (if any) is untouched, and the error is recorded against the plugin
- [ ] **AC-REC-4**: Given `.tachikoma/plugins/orphan/` exists but no `[plugins.orphan]` entry remains in config, when reconciliation runs, then the orphan folder is removed
- [ ] **AC-REC-5**: Given a configured plugin's source cannot be re-materialized (network failure, ref missing, local path inaccessible) and `.tachikoma/plugins/<alias>/` contains a valid manifest matching the alias, when reconciliation runs, then the existing copy is retained, the plugin's status is recorded as `stale-fallback`, and a WARNING-level log entry is emitted
- [ ] **AC-REC-6**: Given a configured plugin's source cannot be re-materialized and either no install directory exists or its contents do not contain a valid manifest matching the alias, when reconciliation runs, then the plugin is skipped with status `failed`, an ERROR-level log entry is emitted, and other plugins continue loading
- [ ] **AC-REC-7**: Given two plugins where one source is unreachable and one is reachable, when reconciliation runs in the same pass, then the reachable plugin is materialized and loaded successfully and the unreachable plugin is recorded as `stale-fallback` or `failed` per AC-REC-5/6 — failure of one does not block the other
- [ ] **AC-REC-8**: Given reconciliation already ran in this process and `install_plugin` is invoked while a previous install is still in flight, when the tool dispatches, then operations are serialized (no concurrent reconciliation against the same install directory) and the second call observes the first call's effects
- [ ] **AC-REC-9**: Given a fresh workspace where `.tachikoma/plugins/` does not exist, when the plugins bootstrap hook runs, then the directory is created
- [ ] **AC-REC-10**: Given reconciliation runs twice in the same process with no intervening config or source changes, when the second run completes, then both runs re-materialize each plugin successfully (re-materialization is always-on by design), the install directory state is equivalent to after the first run, no spurious WARNING/ERROR log entries are emitted, and no plugin status changes (e.g., a `loaded` plugin remains `loaded`)
- [ ] **AC-REC-11**: Given a `[plugins.foo]` url-source entry pointing at a `.tar.gz` archive, when reconciliation runs, then the archive is streamed over HTTPS to a temp file, extracted into a temp staging directory, the extracted content is copied into a sibling directory `.tachikoma/plugins/foo.new/`, and atomic-renamed over `.tachikoma/plugins/foo/`
- [ ] **AC-REC-12**: Given a url-source archive whose extracted root contains exactly one top-level directory and no other top-level entries, when reconciliation runs, then that single directory's contents are used as the install root (auto-stripped); given an extracted root with multiple top-level entries, then the extracted root itself is used as the install root
- [ ] **AC-REC-13**: Given a url-source entry with a `subdir` field, when reconciliation runs, then `subdir` is resolved relative to the install root produced by AC-REC-12 and only that subdirectory's contents are used as the final install
- [ ] **AC-REC-14**: Given a url-source download fails (HTTP non-2xx, network error, archive corruption) and the install directory contains a valid manifest matching the alias, when reconciliation runs, then the existing copy is retained with status `stale-fallback` (per AC-REC-5); given no valid existing copy, the plugin is recorded as `failed` (per AC-REC-6)

### Gitignore registration (R13)

- [ ] **AC-GI-1**: Given a workspace `.gitignore` without an entry for `.tachikoma/plugins/`, when the plugins bootstrap hook runs (before reconciliation in the same hook), then the entry is appended; running the hook again does not produce a duplicate entry

### Manifest parsing (R3, R4, R7)

- [ ] **AC-MP-1**: Given a plugin folder with `tachikoma-plugin.toml` declaring metadata (name, version, description) and one or more skill directory paths, when the loader parses it, then the plugin's metadata and skill paths populate the internal model
- [ ] **AC-MP-2**: Given a plugin folder with `.claude-plugin/plugin.json` and a CC-format `skills/` directory but no `tachikoma-plugin.toml`, when the loader parses it, then CC manifest values (name, version, description) are aliased into the internal model and the `skills/` directory is recognized as a skill source
- [ ] **AC-MP-3**: Given a CC plugin whose `plugin.json` declares non-skill contributions (`commands`, `mcpServers`, `agents`, `hooks`), when the loader parses it, then those declarations are silently ignored and one INFO-level log line is emitted per contribution type with the plugin alias
- [ ] **AC-MP-4**: Given a CC plugin without a `skills/` directory and no other recognized contributions, when the loader parses it, then the plugin is loaded with status `loaded` and zero contributed skills
- [ ] **AC-MP-5**: Given a plugin folder containing both `tachikoma-plugin.toml` and `.claude-plugin/plugin.json`, when the loader parses it, then the Tachikoma-native manifest takes precedence and the CC manifest is ignored
- [ ] **AC-MP-6**: Given a plugin folder missing both manifest formats, when the loader processes it, then validation fails with status `failed` and a diagnostic naming the missing files; the plugin is skipped
- [ ] **AC-MP-7**: Given a manifest is malformed (invalid TOML/JSON, missing required fields), when validation runs, then the plugin is rejected with status `failed` and a diagnostic naming the file and the specific issue
- [ ] **AC-MP-8**: Given a manifest declares a skill directory that does not exist on disk, when validation runs, then a WARNING is logged naming the missing directory, the missing directory is excluded from registration, and the plugin still loads with `loaded` status if at least one declared directory is valid; if all declared directories are missing, the plugin loads with status `loaded` and zero contributed skills (consistent with AC-MP-4)
- [ ] **AC-MP-9**: Given a Tachikoma-native manifest declares zero skill directories (empty list), when the loader parses it, then validation succeeds and the plugin is loaded with status `loaded` and zero contributed skills (no-op plugin is valid)

### Skill source registration (R5)

- [ ] **AC-SSR-1**: Given a plugin with alias `code-review` contributes a skill named `linter`, when the skills bootstrap hook completes, then the skill is registered in the `SkillRegistry` under the name `code-review:linter`
- [ ] **AC-SSR-2**: Given two plugins (`alpha` and `beta`) each contribute a skill named `deploy`, when the registry loads, then both are registered as separate skills `alpha:deploy` and `beta:deploy` with no collision
- [ ] **AC-SSR-3**: Given a workspace skill named `linter` exists and a plugin with alias `code-review` contributes a skill named `linter`, when the registry loads, then `linter` (default namespace) and `code-review:linter` coexist as distinct skills
- [ ] **AC-SSR-4**: Given the skills classifier returns the namespaced name `code-review:linter` as relevant, when the skills context provider parses the result, then the corresponding plugin skill content is loaded into context
- [ ] **AC-SSR-5**: Given `IncomingMessage.pinned_skills` contains `code-review:linter`, when the skills context provider runs, then the namespaced lookup resolves and the plugin skill is pinned alongside default-namespace pinned skills
- [ ] **AC-SSR-6**: Given the skills classifier prompt is built with built-in, workspace, and plugin skills present, when the candidate list is rendered, then plugin skills appear under their namespaced names (`<alias>:<name>`) while default-namespace skills appear under their bare names
- [ ] **AC-SSR-7**: Given the skill registry exposes context-entry metadata for detected skills, when a plugin skill is loaded into a session, then its metadata `skill_name` field carries the namespaced name (so accumulation, dedup, and removal logic remain unambiguous across plugins)

### MCP tools — install (R10)

- [ ] **AC-MCP-INST-1**: Given the agent invokes `install_plugin` with a git source (URL, subdir, ref) and no `alias` argument, when the manifest declares `name = "code-review"` and no `[plugins.code-review]` entry exists, then the source is materialized and parsed first; only after parsing succeeds is `[plugins.code-review]` written to config (preserving existing comments and formatting per config-system R6); reconciliation completes; the registry refreshes; and the tool returns success with the plugin's metadata
- [ ] **AC-MCP-INST-2**: Given the agent invokes `install_plugin` with a local-path source and no `alias` argument, when the manifest declares a name and no `[plugins.<name>]` entry exists, then the same validate-then-write flow runs and config is mutated accordingly
- [ ] **AC-MCP-INST-3**: Given the agent invokes `install_plugin` with no `alias` and the manifest's name collides with an existing `[plugins]` entry, when the tool runs, then it returns an error explaining the collision and prompting retry with an explicit `alias` argument; config is not mutated; the temp materialization is discarded
- [ ] **AC-MCP-INST-4**: Given the agent invokes `install_plugin` with an explicit `alias = "my-cr"` argument and no entry by that alias exists, when the tool runs, then `[plugins.my-cr]` is added regardless of the manifest's declared name
- [ ] **AC-MCP-INST-5**: Given the agent invokes `install_plugin` with an explicit `alias` that collides with an existing entry, when the tool runs, then it returns a clear collision error naming the existing alias; config is not mutated
- [ ] **AC-MCP-INST-6**: Given install fails (source unreachable, manifest invalid, validation error), when the tool returns, then it returns an error message naming the failure cause; config is not mutated; any temp materialization is cleaned up
- [ ] **AC-MCP-INST-7**: Given `install_plugin` returns success, when `list_plugins` is invoked, then the new plugin appears with status `loaded`
- [ ] **AC-MCP-INST-8**: Given `install_plugin` returns success, when the tool publishes a `SkillsChanged` event on the existing skills event bus, then the skill system marks the registry for refresh; on the next user message the classifier candidate list includes the new plugin's namespaced skill names without restart
- [ ] **AC-MCP-INST-9**: Given an `install_plugin` call is in flight, when a second `install_plugin` or `remove_plugin` is invoked concurrently for the same alias or any alias, then operations are serialized (no concurrent reconciliation, no torn config writes)

### MCP tools — list (R11)

- [ ] **AC-MCP-LIST-1**: Given plugins are installed, when the agent invokes `list_plugins`, then it returns one entry per plugin with: alias, source spec (git fields or local path), ref (for git sources), validation status (one of `loaded` / `stale-fallback` / `failed`), diagnostic message (present when status is not `loaded`), and the namespaced names of contributed skills
- [ ] **AC-MCP-LIST-2**: Given no plugins are installed, when the agent invokes `list_plugins`, then it returns an empty list
- [ ] **AC-MCP-LIST-3**: Given a plugin is in `stale-fallback` state because reconciliation could not refresh it, when listed, then its status is `stale-fallback` and the diagnostic message names the fetch failure so the user knows the install may not be at the configured ref

### MCP tools — remove (R12)

- [ ] **AC-MCP-REM-1**: Given a plugin is installed and at least one of its skills is currently loaded into an active session's context, when the agent invokes `remove_plugin` with its alias, then the `[plugins.<alias>]` entry is removed from config (preserving comments/formatting), `.tachikoma/plugins/<alias>/` is deleted, and a `SkillsChanged` event is published on the skills event bus; the active session's already-loaded plugin skill entries continue to function for the rest of the session (existing skills.md "deleted skill silently excluded" behavior applies to subsequent sessions)
- [ ] **AC-MCP-REM-2**: Given the agent invokes `remove_plugin` for an alias not present in `[plugins]`, when the tool runs, then it returns a clear "not found" error and no changes are made
- [ ] **AC-MCP-REM-3**: Given a plugin's directory cannot be deleted (e.g., permission error), when `remove_plugin` runs, then the config entry is still removed, the directory removal failure is reported in the tool's response with the OS error, and the orphan directory is cleaned up by reconciliation on next startup
- [ ] **AC-MCP-REM-4**: Given `remove_plugin` is invoked twice for the same alias, when the second call runs, then it returns a "not found" error with no partial side effects (no double-removal of config or directory)
