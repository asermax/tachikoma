# Delta Spec: DLT-152 - Boundary-aware message queueing

## Story

As a user, I want to explicitly route messages to a new conversation or defer them for later processing so that I can manage multiple topics without the current session being disrupted or without needing automatic boundary detection to guess my intent.

## What It Does

Adds two bot commands (`/new` and `/queue`) that let the user explicitly control message routing. `/new` forces a fresh session (skipping boundary detection), while `/queue` defers the message for boundary-detected processing after the current turn. The commands are registered as Telegram bot commands (native `bot_command` entities and `setMyCommands` registration) for structured detection and autocomplete discoverability. The queueing infrastructure in the coordinator is generic. Normal messages without a command continue to be steered into the active session as today. REPL integration is out of scope for this delta (REPL does not support steering).

## Requirements

| ID | Requirement | Status |
|----|-------------|--------|
| R0 | `/new [message]` forces a fresh session without boundary detection | Core goal |
| R1 | `/queue [message]` defers the message for boundary-detected routing after the current turn | Core goal |
| R2 | Command detection uses Telegram native bot commands; queueing infrastructure is generic | Must-have |
| R3 | Command messages during active processing are queued, not steered | Must-have |
| R4 | Queued messages are processed sequentially after the current turn completes | Must-have |
| R5 | No messages are dropped — queue drains completely (ephemeral in-memory queue, lost on restart) | Must-have |
| R6 | FIFO ordering in the queue | Must-have |
| R7 | `/new` works when both busy and idle — always closes current session (if any) and creates a new one | Must-have |
| R8 | `/queue` when idle bypasses the queue and processes immediately through boundary detection | Must-have |
| R9 | No user feedback on queueing — silent operation | Must-have |
| R10 | `/new` triggers session close on the active session (if any) when the queued message is processed (not when enqueued), with async post-processing | Must-have |
| R11 | Command text is stripped from message before processing — the agent never sees the command prefix | Must-have |
| R12 | Bare `/new` or `/queue` (or whitespace-only arguments) is treated as a normal message (not intercepted) | Must-have |
| R13 | First command wins on nested commands — `/new /queue message` is treated as `/new` with message "/queue message" | Must-have |

## Acceptance Criteria

### `/new` command (R0, R7, R10, R11, R12, R13)

- [ ] Given the user sends `/new let's talk about X`, when the command is detected, then the command is stripped, the active session (if any) is closed, and a new session is created with the message "let's talk about X"
- [ ] Given the user sends `/new` alone (no message body), when the command is detected, then it is treated as a normal message (passed through to the agent as-is)
- [ ] Given the user sends `/new   ` (whitespace-only arguments), when the command is detected, then it is treated as a normal message
- [ ] Given the user sends `/new /queue something`, when the command is detected, then it is treated as `/new` with message "/queue something"
- [ ] Given the agent is busy and the user sends `/new let's talk about X`, when the command is detected, then the message is queued and not steered into the active session
- [ ] Given the agent is idle and the user sends `/new fresh start`, when the command is detected, then the current open session is closed, a new session is created, and the message is processed
- [ ] Given the agent is idle with no active session and the user sends `/new fresh start`, when the command is detected, then a new session is created and the message is processed (nothing to close)
- [ ] Given `/new` triggers a session close, when the closed session has a valid SDK session ID, then async post-processing fires (same as boundary detection topic shift)
- [ ] Given a `/new` message, when the agent processes it, then the agent sees only the message text without the `/new` prefix

### `/queue` command (R1, R8, R11, R12, R13)

- [ ] Given the user sends `/queue remind me about Y`, when the command is detected and the agent is busy, then the message is queued for deferred processing
- [ ] Given the user sends `/queue` alone (no message body), when the command is detected, then it is treated as a normal message
- [ ] Given the user sends `/queue   ` (whitespace-only arguments), when the command is detected, then it is treated as a normal message
- [ ] Given the agent is idle and the user sends `/queue something`, when the command is detected, then it bypasses the queue entirely and processes immediately through the normal boundary detection pipeline
- [ ] Given a `/queue` message is deferred and the current turn completes, when the queued message is processed, then boundary detection runs and may result in: (a) continue the current session, (b) topic shift to a new session, or (c) resume a previous session
- [ ] Given a `/queue` message is processed from the queue and boundary detection classifies it as a continuation, when there is an active session, then the message is processed within that session
- [ ] Given a `/queue` message is processed from the queue and boundary detection classifies it as a topic shift, when it matches a previous session, then that session is resumed
- [ ] Given a `/queue` message is processed from the queue and boundary detection classifies it as a topic shift, when it does not match any previous session, then a new session is created
- [ ] Given a `/queue` message is processed from the queue and boundary detection fails (error), when the failure occurs, then the message proceeds as a continuation in the current session (fail-open, same as normal boundary detection)
- [ ] Given a `/queue` message, when the agent processes it, then the agent sees only the message text without the `/queue` prefix

### Queue processing (R3, R4, R5, R6)

- [ ] Given multiple command messages arrive during active processing, when the turn completes, then they are processed in FIFO order
- [ ] Given a `/new` and a `/queue` message are both in the queue, when the turn completes, then `/new` is processed first if it arrived first (FIFO regardless of type)
- [ ] Given the queue is being drained and a new command message arrives, when it is enqueued, then it joins the end of the queue and is processed after existing items
- [ ] Given a queued message is being processed (draining), when another normal message arrives, then the normal message follows standard steering/queueing rules
- [ ] Given the queue is being drained and processing a queued message triggers async post-processing, when the post-processing fails, then the error is logged and queue draining continues to the next item
- [ ] Given the queue contains messages and the process restarts, when the process starts again, then the queue is empty (ephemeral, in-memory only)

### Channel integration (R2, R9)

- [ ] Given Telegram is the active channel, when a bot command `/new` or `/queue` is detected via the `bot_command` entity, then the command arguments become the message text and the message is routed accordingly
- [ ] Given the Telegram bot starts, when `setMyCommands` is called, then `/new` is registered with description "Start a new conversation" and `/queue` is registered with description "Defer message for later processing"
- [ ] Given a queued message is waiting, when it is enqueued, then no acknowledgment or feedback is sent to the user
- [ ] Given a future channel is added, when it integrates with the coordinator, then the same queueing infrastructure is available (channel only needs to detect its own command syntax)

### Graceful shutdown

- [ ] Given messages are in the queue when shutdown begins, when the shutdown sequence runs, then the queue is drained before the process exits (queued messages are not lost on graceful shutdown)
