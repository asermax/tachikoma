# Delta Spec: DLT-120 - Pause background tasks to request user input

## Story

As a user, I want background tasks to be able to pause and ask me a question so that multi-step background work can incorporate my decisions without requiring persistent agent sessions.

## What It Does

Adds a "waiting" state to the background task lifecycle where the evaluator detects the agent asked for input, suspends execution, and sends a respondable notification to the user. The user responds through the main conversation via a `respond_to_task` MCP tool, which saves the response on the task instance. The task runner picks up waiting instances with responses the same way it picks up new pending instances — acquiring a semaphore slot, resuming the SDK session, and injecting the user's response as the next turn.

## Acceptance Criteria

### Waiting State Entry (R1, R6)

- [ ] Given a background task agent produces a response that the evaluator classifies as `needs_input`, when the evaluator returns its assessment, then the executor saves the SDK session ID on the instance, marks the instance as "waiting" (which also updates `updated_at`), dispatches a respondable notification containing the evaluator's rationale (the question the agent asked), releases the semaphore slot, and returns
- [ ] Given a background task instance transitions to "waiting", then the `sdk_session_id` field is persisted and `updated_at` is set to the current time
- [ ] Given the background task system prompt, then it explains: (1) the agent's messages are intercepted by an evaluator, not delivered directly to the user, (2) if the agent needs user input, it should ask its question clearly — the question will be routed to the user via a notification, (3) the user's response will arrive as the next conversation turn

### Respondable Notifications (R2, R2.1, R2.2)

- [ ] Given a background task enters waiting state, when the notification is dispatched, then the notification prompt text includes the task's question (from the evaluator's rationale field), the task definition name, and the task instance ID with explicit instructions for the main agent to use `respond_to_task`
- [ ] Given a background task enters waiting state, when the notification is dispatched, then it is dispatched with urgent priority
- [ ] Given a background task completes successfully, when a notification is dispatched (agent-driven via `send_notification`), then the notification prompt text does not include response instructions or `respond_to_task` usage guidance
- [ ] Given a background task fails, when the automatic failure notification is dispatched, then the notification prompt text does not include response instructions
- [ ] Given the main agent receives a respondable notification and attempts to respond, when it calls `respond_to_task`, then the tool enforces that the target instance is in "waiting" status — rejecting calls against any other status (this is the enforcement half of respondability)

### Response Tool (R3, R3.1, R3.2, R3.3, R3.4, R3.5)

- [ ] Given the main conversation agent, then a `respond_to_task` MCP tool is available in the task tools server
- [ ] Given the agent calls `respond_to_task` with a valid task instance ID and a non-empty response message, when the instance is in "waiting" status and has no pending response, then the response is saved to the `user_response` field on the instance, `updated_at` is refreshed, and the tool returns success
- [ ] Given the agent calls `respond_to_task` with a task instance ID that is not in "waiting" status, then the tool returns a clear error (e.g., "Task is not waiting for input")
- [ ] Given the agent calls `respond_to_task` with a nonexistent task instance ID, then the tool returns a clear "not found" error
- [ ] Given the agent calls `respond_to_task` with an empty or whitespace-only response, then the tool returns a clear error
- [ ] Given the agent calls `respond_to_task` for a waiting instance that already has a non-null `user_response` (response pending runner pickup), then the tool returns an error indicating a response is already pending
- [ ] Given the system prompt preamble's Tasks section, then the Tools subsection includes `respond_to_task` with parameter types, required indicators, and behavioral notes: when a notification indicates a background task is waiting for input, use this tool to send the user's response back to the task

### Resume Execution (R4, R4.1, R4.2)

- [ ] Given a waiting task instance with a non-null `user_response`, when the runner's next check loop runs, then the instance is picked up for execution — the runner queries `status == "waiting" AND user_response IS NOT NULL` alongside `status == "pending"`, both going through the same semaphore acquisition path
- [ ] Given a waiting-with-response instance is picked up by the runner, when the executor runs, then the instance is marked as "running" (refreshing `updated_at`), the `user_response` field is consumed (read and cleared), and a new `ClaudeSDKClient` is created with the saved `sdk_session_id` for session resume
- [ ] Given a resumed SDK session, then the user's response is injected as the next turn (query) and the evaluator loop continues normally from that point
- [ ] Given a resumed task completes or fails, then the standard completion/failure flow applies (status update, post-processing, notifications)
- [ ] Given a resumed task's evaluator detects `needs_input` again, then the task can re-enter "waiting" state (multiple pause/resume cycles supported)

### Wait Timeout (R5, R5.1)

- [ ] Given a `wait_timeout` setting in `[tasks]` configuration (default 7200 seconds / 2 hours), when a task instance has been in "waiting" status and `updated_at` is older than `wait_timeout`, then the instance is marked as "failed" with a timeout reason
- [ ] Given a task fails due to wait timeout, then a failure notification is dispatched to the user indicating the task timed out waiting for input
- [ ] Given the user calls `respond_to_task` after the task has already timed out, then the tool returns an error (task is no longer in "waiting" status)
- [ ] Given any persistence modification to a task instance (status change, response save, result save, timestamps), then `updated_at` is refreshed to the current time

### Semaphore Release (R7)

- [ ] Given a background task transitions to "waiting" state, then the semaphore slot is released immediately — waiting tasks do not count against the concurrency limit
- [ ] Given 3 tasks are running (at default limit) and one transitions to "waiting", then a new pending task can acquire the freed slot
- [ ] Given multiple tasks are in "waiting" state simultaneously and all receive responses, then they are queued for execution and processed as slots become available

### Crash Recovery and Duplicate Prevention (R8, R8.1)

- [ ] Given the system restarts while task instances are in "waiting" status, then those instances remain in "waiting" status (not marked as failed by crash recovery) — their SDK sessions persist across restarts within the session resume window
- [ ] Given the system restarts with waiting instances whose `updated_at` is older than `wait_timeout`, then the timeout check on the first runner loop iteration fails them with notifications
- [ ] Given a cron task definition has an instance in "waiting" status, when the next cron match fires, then no duplicate instance is created — "waiting" is included in the duplicate prevention status list
