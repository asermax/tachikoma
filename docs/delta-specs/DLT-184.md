# Delta Spec: DLT-184 - Web and extension tool access for delegated subagents

<!-- This spec describes WHAT the delta does, not HOW it's implemented. -->

## Story

As the assistant, I want to delegate tool-dependent work — most concretely web research — to an isolated subagent that can use the same extension tools the main session has (web search, scrape, fetch, or any extension-provided capability), so that context-heavy, tool-using work runs in parallel outside my own context instead of being forced back onto the main conversation.

As an extension author, I want to expose my extension's tools to delegated subagents, so the assistant can hand focused, tool-dependent tasks to a subagent that can actually use them.

## What It Does

Today a delegated subagent (`delegate_to_agent`) runs in a bare, isolated session that binds no extension factories and admits only pi's built-in file/shell tools. DLT-184 lets the calling agent grant a delegated subagent a configurable subset of extension tools — from Tachikoma factories that opt in, or from pi-native extensions loaded from the `.pi` folder — so tool-using work (web research most concretely) runs inside the isolated subagent instead of the main session. The grant is additive on top of the resolved built-in tool set, read-only stays the default, and the isolated/ephemeral run is preserved. It does not introduce any credential or secrets handling (deferred until a secrets store exists).

## Requirements

| ID | Requirement | Status |
|----|-------------|--------|
| R0 | A delegated subagent can be granted a configurable subset of extension tools so tool-dependent work (web research most concretely) runs in the isolated subagent, not the main session | Core goal |
| R1 | The calling agent requests extension tools by name at delegation time, *added on top of* the resolved built-in tool set (per-delegation override > agent-declared tools > read-only default for built-ins; granted extension tools augment that set) | Must-have |
| R2 | The isolated, ephemeral run is preserved — in-memory, `isolatePrompt`, disposed after the run; granted extension tools execute inside that same isolation boundary, never in the main session | Must-have |
| R3 | Read-only built-ins remain the default; extension tools are opt-in per delegation and are never granted by default | Must-have |
| R4 | The grant is **source-agnostic**: a requested tool name resolves to its provider whether that is a Tachikoma factory opted into the new `subagent` scope *or* a pi-native extension loaded from `.pi` / packages / settings. An unknown or unresolvable name yields a self-correcting error that lists what is grantable (evolving today's built-in-only error) | Must-have |
| R5 | Tachikoma factories opt their tools into subagent grantability through a new `subagent` session scope on `app.agent.use`. The opt-in granularity (per-factory vs per-tool) is a design decision | Must-have |
| R6 | A factory or extension bound into a subagent run receives its binding session context (`{ scope }`) so it can adapt — e.g. suppress user-facing surfaces in a subagent run, mirroring how factories adapt to `background` runs today | Must-have |
| R7 | Credential handling is out of scope — DLT-184 introduces no secrets mechanism. A subagent receives a granted tool exactly as the main session does, and credential security is deferred until a secrets store exists (DLT-156 / DLT-151) | Out |
| R8 | An operator allowlist/denylist constraining which tools subagents may receive | Out |
| R9 | Extension-tool access for *background tasks* (not delegations) | Out |
| R10 | An ADR documents the source-agnostic binding mechanism (the session-scope / factory-binding change for subagent runs) | Must-have |

## Acceptance Criteria

### Grant mechanism and composition (R0, R1, R3)

- [ ] Given an extension that has exposed a tool (e.g. `web_search`) for subagent use, when the calling agent delegates with that tool requested, then the subagent run has the granted extension tool *in addition to* its resolved built-in set (read-only default unless built-ins were overridden or declared), and can call it
- [ ] Given a delegation that requests an extension tool alongside a built-in override (e.g. extension `web_search` plus built-ins `read`, `bash`), when the run executes, then the subagent has exactly the requested built-ins plus the granted extension tool
- [ ] Given a delegation that does not request any extension tool, when the run executes, then the subagent has only built-ins (the agent's declared tools or the read-only default) and no extension tools — read-only stays the default
- [ ] Given a delegation that requests only built-in tools (today's `R6b` behavior), when the run executes, then it behaves exactly as before — built-in override, validation, and the rebuilt `general-purpose` prompt are unchanged

### Isolation preserved (R2)

- [ ] Given a delegation that grants an extension tool, when the run executes, then the session is still in-memory, prompt-isolated (`isolatePrompt: true`), and disposed after the run; the extension tool runs inside that boundary, not in the main session
- [ ] Given a granted extension tool that produces output, when the run finishes, then only the subagent's final text returns as the tool result (tail-truncated), with no leak of the main session's context into the run beyond the `task` prompt
- [ ] Given a delegated run that grants an extension tool, when the run ends (success or failure), then the session and any resources the binding opened are disposed

### Source-agnostic resolution and errors (R4)

- [ ] Given a tool provided by a Tachikoma factory opted into the `subagent` scope, when the calling agent requests it by name, then it is granted
- [ ] Given a tool provided by a pi-native extension loaded from `.pi` (or packages/settings), when the calling agent requests it by name, then it is granted on the same terms as a Tachikoma-factory tool
- [ ] Given a tool name that is neither a built-in nor an exposed extension tool, when the calling agent requests it, then the delegation throws a self-correcting error describing what is grantable and no run is attempted
- [ ] Given a tool provided by a Tachikoma factory that has *not* opted into the `subagent` scope, when the calling agent requests it, then it is treated as unresolvable and the delegation throws (it is not silently granted)

### Opt-in and binding context (R5, R6)

- [ ] Given a factory registered with `{ sessionScopes: ["main", "subagent"] }`, when a delegated run opens, then that factory binds into the subagent session with `{ scope: "subagent" }` and its tools are among the grantable set
- [ ] Given a factory registered without the `subagent` scope, when a delegated run opens, then that factory does not bind and its tools are not grantable
- [ ] Given a factory that adapts to its binding scope (e.g. suppresses a user-facing surface in `background`), when it binds into a `subagent` run, then it receives `{ scope: "subagent" }` and can apply the same adaptation

### Documentation (R10)

- [ ] Given the binding mechanism is implemented, when the delta lands, then an ADR records the source-agnostic binding approach (the new session scope, how Tachikoma factories and pi-native extensions are both covered, and the option chosen over the alternatives the delta description enumerates)

### Explicit non-goals (R7, R8, R9)

- [ ] Given a credential-bearing extension tool is granted to a subagent, when the subagent uses it, then the delta introduces no new secrets plumbing — the tool behaves as it does in the main session; any secret protection is deferred to DLT-156 / DLT-151 and is explicitly out of scope here
- [ ] Given the operator does not configure any allowlist/denylist, when a delegation requests an exposed tool, then it is granted solely on the basis of the extension's opt-in — there is no operator gate to satisfy (such a gate is out of scope)
- [ ] Given a background task run (not a delegation), when it executes, then its factory binding is unchanged from today (background-scoped factories); DLT-184 does not alter background-task tool binding

## Requires

Dependencies:
- None (builds on the existing `delegate_to_agent` subagent runner, the per-delegation built-in `tools` override landed as `R6b`, and the session-scope / factory-binding model already in place)

- **[docs/feature-designs/skills.md](../feature-designs/skills.md)** - Modifies: the `R6b` design note (which today states "only pi's built-in tools are grantable … exposing them is tracked separately as DLT-184") is updated to reflect that extension/web tools are now grantable, with a pointer to the new ADR

### Notes for Reconciliation
- New ADR under `docs/architecture/` documenting the source-agnostic binding mechanism and the `subagent` session scope (the session-scope model is currently two-valued `main`/`background` with no ADR of its own; this delta extends it and is the right place to record the decision)
- The skills spec's delegation Acceptance Criteria gain cases for granting an exposed extension tool, the source-agnostic resolution, the `subagent` scope opt-in, and the unknown-tool error evolving from "built-ins only" to "exposed tools"
