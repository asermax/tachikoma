# Delta Spec: DLT-118 — Declare dependencies between skills

## Story

As a skill author, I want to declare that my skill requires other skills, so that concepts and tools my skill assumes (e.g., the workflow authoring guide) are always loaded into context alongside it — without me or the classifier having to rediscover them on every message.

## What It Does

Adds a `depends_on` list field to SKILL.md frontmatter. When the skills context provider selects a skill (via classification), the registry's resolver returns the full transitive dependency chain (the anchor skill included, deps-first order) — unfiltered. The provider then dedups against skills already present in the session's context entries and emits one context entry per remaining skill. Cycles are safely broken at resolution time via a visited-set; unknown dependency names are logged as warnings once per dependent skill at registry load and silently skipped during resolution. Memoized chains in the registry are invalidated on refresh, and the provider performs refresh + resolution as an atomic per-message snapshot.

## Requirements

| ID | Requirement | Status |
|----|-------------|--------|
| R0 | A skill can declare other skills it requires so the foundations it assumes are always loaded alongside it | Core goal |
| R1 | `depends_on` list field (of skill names) is supported in SKILL.md YAML frontmatter and optional (missing or empty list → no declared dependencies) | Must-have |
| R2 | Registry parses and stores `depends_on` on the `Skill` record when loading | Must-have |
| R3 | Registry exposes a dependency-resolution entry point returning the transitive chain for a given skill, deps-first, with the anchor skill included as the last element, and each skill included at most once | Must-have |
| R4 | Resolution tolerates cycles — a visited-set breaks back-edges during chain expansion so the resolver always terminates; self-references behave the same as any other cycle | Must-have |
| R5 | Unknown dependency names (typo, deleted skill) are logged as a single warning per dependent skill at registry load/refresh; during resolution the unknown names are silently skipped while the remaining real deps are still resolved | Must-have |
| R6 | The classification-driven skills context provider expands every detected skill through the registry's resolver (full chain returned) and emits one context entry per resolved skill | Must-have |
| R7 | The provider dedups the resolved chain against skills already present in the session's context entries (by `skill_name` metadata); the registry resolver itself returns unfiltered chains, which keeps memoization keyed only by skill name | Must-have |
| R8 | Each loaded dep is emitted as a context entry identical in shape to a classification-loaded skill (same `<skill>` XML block, same `skill_name` metadata) so agent derivation and future refresh cycles treat it uniformly | Must-have |
| R9 | Classification remains unchanged — dependency resolution runs strictly after classification and does not influence the candidate list | Must-have |
| R10 | `resolve_chain` results are memoized on the registry and invalidated on refresh, so repeated resolutions within the same registry state avoid re-traversal | Must-have |
| R11 | The provider's `refresh() → resolve_chain()` sequence within a single message produces a consistent snapshot — either fully pre-refresh or fully post-refresh | Must-have |
| R12 | When a workspace skill replaces a built-in skill (per parent feature R17), the workspace version's `depends_on` is the one used by the resolver; dependency edges may cross sources (built-in → workspace and the reverse) | Must-have |

## Acceptance Criteria

### Frontmatter & registry parsing (R1, R2)
- [ ] Given a SKILL.md with `depends_on: [skill-a, skill-b]` in the frontmatter, when the registry loads the skill, then its `Skill` record carries both names in the declared order.
- [ ] Given a SKILL.md with no `depends_on` field, when the registry loads the skill, then the skill record's dependency list is empty.
- [ ] Given a SKILL.md with `depends_on: []` (explicit empty list), when the registry loads the skill, then behavior is identical to the missing-field case (empty dependency list, no warnings).
- [ ] Given a SKILL.md with an invalid `depends_on` value (not a list, or contains non-strings), when the registry loads it, then a warning is logged and the skill is loaded with an empty dependency list.
- [ ] Given skill names compared during parsing/resolution, then comparisons are case-sensitive (matching the folder-name convention used elsewhere in the registry).

### Dependency resolution (R3, R4, R10)
- [ ] Given skill A depends on skill B and skill B depends on skill C, when the resolver is asked for A's chain, then it returns [C, B, A] (deps-first; anchor skill last) with no duplicates.
- [ ] Given skill A depends on skill B and skill B depends on skill A (cycle), when the resolver is asked for A's chain, then it returns both skills exactly once and terminates without error.
- [ ] Given skill A declares `depends_on: [a]` (self-reference), when the resolver is asked for A's chain, then it returns `[A]` exactly once and terminates without error.
- [ ] Given skill A depends on B and C, and both B and C depend on D (diamond), when the resolver is asked for A's chain, then D appears exactly once before both B and C, and A appears last.
- [ ] Given a skill with no dependencies, when the resolver is called, then it returns a single-element chain containing only that skill.
- [ ] Given the resolver has computed A's chain, when it is called again for A without a registry refresh, then the previously computed chain is returned without re-traversal.
- [ ] Given the registry is refreshed (e.g., a SKILL.md changed), when the resolver is next called, then cached chains are invalidated and recomputed from the fresh registry state.

### Unknown dependency handling (R5)
- [ ] Given skill A declares `depends_on: [missing-x, missing-y]`, when the registry loads, then a single warning is logged for A naming both missing deps; skill A still loads successfully.
- [ ] Given the same registry state with A depending only on unknown names, when the resolver is asked for A's chain, then it returns `[A]` and silently omits the unknown names (no extra warning per resolution).
- [ ] Given skill A declares `depends_on: [missing-x, real-b]`, when the resolver is called, then the chain is `[real-b, A]` and `missing-x` is silently omitted from the returned chain.

### Integration with classification (R6, R7, R8, R9, R11)
- [ ] Given a classification run detects skill A (which depends on B), when the provider assembles its results, then both A and B are emitted as individual context entries, each with its own `<skill>` XML block and `skill_name` metadata.
- [ ] Given skill B is already present in the session context and classification detects skill A (which depends on B), when the provider assembles results, then only A is emitted (B is skipped as already-loaded).
- [ ] Given classification detects skill A with transitive chain `[C, B, A]` but B is already loaded, when the provider emits results, then A and C are emitted (B is skipped).
- [ ] Given the classification input list, when the provider builds candidate skills, then the list still contains every unloaded skill (dep relationships do not filter candidates).
- [ ] Given the skill classifier returns no relevant skills, when the provider runs, then no dep resolution occurs and the provider returns no context entries.
- [ ] Given the provider begins processing a message, when it calls `refresh()` followed by `resolve_chain()` for each detected skill, then all chain resolutions in that message observe the same registry snapshot (either fully pre-refresh or fully post-refresh).

### Workspace override (R12)
- [ ] Given a built-in skill and a workspace skill with the same name but different `depends_on` lists, when the resolver is called for that skill, then the workspace version's dependencies are used (consistent with parent feature R17 last-wins precedence).
- [ ] Given a built-in skill declares a dep on a workspace-only skill (or vice versa), when the resolver is called, then the cross-source dependency is resolved normally.

### Error isolation (cross-cutting, aligns with parent feature R14)
- [ ] Given the resolver encounters an unexpected exception for one skill, when the provider processes results, then other detected skills' chains are still emitted (one bad chain does not block the message).

## Out of Scope

- Integration with task attachment (DLT-117) and workflow step binding (DLT-119) — those deltas will call the registry's resolver when they land.
- Concurrent resolution across overlapping message handlers in the same session (the coordinator already serializes per-session message handling; intra-message atomicity is covered by R11).
