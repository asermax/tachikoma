# Delta Spec: DLT-118 — Declare dependencies between skills

## Story

As a skill author, I want to declare that my skill requires other skills, so that concepts and tools my skill assumes (e.g., the workflow authoring guide) are always loaded into context alongside it — without me or the classifier having to rediscover them on every message.

## What It Does

Adds a `depends_on` list field to SKILL.md frontmatter. When the skills context provider selects a skill (via classification), the registry resolves its transitive dependency chain and the provider loads each skill in the chain as its own context entry, deduping against skills already present in the session. Cycles are safely broken at resolution time via a visited-set; unknown dependency names are logged as warnings at registry load and skipped.

## Requirements

| ID | Requirement | Status |
|----|-------------|--------|
| R0 | A skill can declare other skills it requires so the foundations it assumes are always loaded alongside it | Core goal |
| R1 | `depends_on` list field (of skill names) is supported in SKILL.md YAML frontmatter and optional (defaults to empty) | Must-have |
| R2 | Registry parses and stores `depends_on` on the `Skill` record when loading | Must-have |
| R3 | Registry exposes a dependency-resolution entry point returning the transitive chain for a given skill, deps-first, with each skill included at most once | Must-have |
| R4 | Resolution tolerates cycles — a visited-set breaks back-edges during chain expansion so the resolver always terminates | Must-have |
| R5 | Unknown dependency names (typo, deleted skill) are logged as warnings at registry load/refresh; the dependent skill still loads and the unknown name is silently skipped during resolution | Must-have |
| R6 | The classification-driven skills context provider expands every detected skill through the registry's resolver and emits one context entry per resolved dep | Must-have |
| R7 | Dependencies already present in the session's context (by `skill_name` metadata) are not re-loaded | Must-have |
| R8 | Each loaded dep is emitted as a context entry identical in shape to a classification-loaded skill (same `<skill>` XML block, same `skill_name` metadata) so agent derivation and future refresh cycles treat it uniformly | Must-have |
| R9 | Classification's candidate list is not filtered by dep relationships — the classifier continues to see all unloaded skills, and dep resolution runs after classification | Must-have |
| R10 | Integration with task attachment (DLT-117) and workflow step binding (DLT-119) is explicitly out of scope — those deltas will call the registry's resolver when they land | Out |

## Acceptance Criteria

### Frontmatter & registry parsing (R1, R2)
- [ ] Given a SKILL.md with `depends_on: [skill-a, skill-b]` in the frontmatter, when the registry loads the skill, then its `Skill` record carries both names in the declared order.
- [ ] Given a SKILL.md with no `depends_on` field, when the registry loads the skill, then the skill record's dependency list is empty.
- [ ] Given a SKILL.md with an invalid `depends_on` value (not a list, or contains non-strings), when the registry loads it, then a warning is logged and the skill is either loaded with an empty dependency list or skipped (consistent with existing malformed-metadata handling).

### Dependency resolution (R3, R4)
- [ ] Given skill A depends on skill B and skill B depends on skill C, when the resolver is asked for A's chain, then it returns [C, B, A] (or any deps-first order where each dep appears before its dependent) with no duplicates.
- [ ] Given skill A depends on skill B and skill B depends on skill A (cycle), when the resolver is asked for A's chain, then it returns both skills exactly once and terminates without error.
- [ ] Given a skill with no dependencies, when the resolver is called, then it returns a single-element chain containing only that skill.

### Unknown dependency handling (R5)
- [ ] Given skill A declares `depends_on: [missing-skill]`, when the registry loads, then a warning is logged naming A and the missing dep; skill A still loads successfully.
- [ ] Given the same registry state, when the resolver is asked for A's chain, then it returns only A and silently omits the unknown name (no extra warning per resolution).

### Integration with classification (R6, R7, R8, R9)
- [ ] Given a classification run detects skill A (which depends on B), when the provider assembles its results, then both A and B are emitted as individual context entries, each with its own `<skill>` XML block and `skill_name` metadata.
- [ ] Given skill B is already present in the session context and classification detects skill A (which depends on B), when the provider assembles results, then only A is emitted (B is skipped as already-loaded).
- [ ] Given classification detects skill A with transitive chain [C, B, A] but B is already loaded, when the provider emits results, then A and C are emitted (B is skipped).
- [ ] Given the classification input list, when the provider builds candidate skills, then the list still contains every unloaded skill (dep relationships do not filter candidates).
- [ ] Given the skill classifier returns no relevant skills, when the provider runs, then no dep resolution occurs and the provider returns no context entries.

### Error isolation (cross-cutting)
- [ ] Given the resolver encounters an unexpected exception for one skill, when the provider processes results, then other detected skills' chains are still emitted (one bad chain does not block the message).
