# Delta Spec: DLT-161 — Workflow composition via inline sub-workflow references

## Story

As a skill author, I want a workflow step to inline-reference another workflow so that reusable sub-sequences (e.g. "process inbox note") can be shared across multiple parents (weekly review, daily review) instead of being duplicated.

## What It Does

Adds a frontmatter field that lets a step declare a sub-workflow to compose. When the engine activates such a step, it pauses the parent, runs the referenced workflow to completion (honouring `required` and `condition` semantics on every step inside the child), then auto-resumes the parent at the next step. From the agent's perspective the run is one continuous workflow: a single workflow ID drives everything, the active step is wherever the deepest active layer says it is, and tool responses include a breadcrumb (`parent_workflow/step > child_workflow/step`) identifying which workflow each step belongs to. "Auto-finalize" refers to terminal cleanup (soft-delete of state record + scratchpad teardown for the top-level); "auto-complete" / "auto-start" refer to step-state transitions.

## Requirements

| ID | Requirement | Status |
|----|-------------|--------|
| R0 | A step can declare a sub-workflow reference; activating that step runs the referenced workflow to completion before the parent advances | Core goal |
| R1 | The reference is a frontmatter field naming the target workflow; cross-skill references are supported | Must-have |
| R2 | Step-level semantics inside the child (`required`, `condition`, `required_skills`) behave exactly as if the child ran standalone | Must-have |
| R3 | The composition step itself supports `required: false` (whole sub-workflow can be skipped) and `condition:` (whole sub-workflow can be conditionally skipped) | Must-have |
| R4 | Nested execution state is persisted across both layers so progress survives context compaction and process restart | Must-have |
| R4.1 | The child workflow's definition is snapshotted at child-spawn time (not at parent-start time) and stored on the child record, identical to how a standalone workflow snapshots at start | Must-have |
| R5 | Cycle detection at workflow load time: a workflow that transitively composes itself is rejected with a warning and not registered | Must-have |
| R6 | Static validation at load time: a composition reference whose target does not exist (or whose target is itself rejected at load time) causes the parent workflow to be rejected with a warning | Must-have |
| R7 | The agent drives the entire nested run with a single workflow ID (the parent's); tool responses route automatically to the deepest active layer | Must-have |
| R7.1 | Routing is deepest-active-only: a step ID that does not match the deepest active layer's expected step returns an error listing the deepest layer's valid step IDs | Must-have |
| R8 | Tool responses include a breadcrumb (`<parent_workflow>/<step> > <child_workflow>/<step>`, separator `>`) so the agent always knows where it is in the stack | Must-have |
| R9 | The parent's and child's scratchpads are shared — the child writes into the parent's scratchpad file rather than getting its own | Must-have |
| R10 | A workflow being composed inside a parent does NOT count against the "one active per (skill, workflow_name)" uniqueness check applied to top-level starts | Must-have |
| R11 | `list_active_workflows` shows top-level workflows only; nested children are not surfaced as separate entries | Must-have |
| R12 | `get_workflow_state` on a top-level workflow includes the active nested execution stack inline (active child workflow, its current step, its step states); previously-completed composition steps do not surface child data | Must-have |
| R13 | When a child auto-finalizes (last step completes/skips), the parent's composition step is auto-completed and the parent's next pending step auto-starts atomically in the same tool response | Must-have |
| R14 | When the composition step is condition-skipped or skipped, the child is never spawned — no state record is created for it | Must-have |
| R15 | Aborting (`end_workflow` with `action="abort"`) the top-level workflow tears down all transitive descendants atomically — no orphaned child records remain active and the shared scratchpad is removed | Must-have |
| R16 | Stale cleanup considers the freshest `updated_at` across the active stack; an active child keeps its parent alive (and vice versa) | Must-have |
| R17 | Nesting depth has no hard cap; deep graphs (3+ levels) behave correctly. Cycle detection at load time guarantees finite depth from any reachable workflow | Must-have |

| R19 | Out — multiple sibling sub-workflows in a single composition step (each composition step references exactly one child) | Out |

## Acceptance Criteria

### R0, R1: Inline reference and composition trigger

- [ ] Given a step has `composes: <workflow_name>` in its frontmatter and the target lives in the same skill, when the workflow loader runs, then the step is parsed with the composition reference set to the target
- [ ] Given a step has `composes: <skill_name>/<workflow_name>`, when the workflow loader runs, then the step is parsed with the composition reference resolving across skills
- [ ] Given a parent workflow whose step `02-handle-inbox` declares `composes: process-inbox-note`, when the agent advances the parent and `02-handle-inbox` is activated, then the engine spawns the referenced child workflow and the agent's tool response describes the child's first activated step (not `02-handle-inbox`'s body)
- [ ] Given the parent's step has `composes:` set, when the loader parses it, then the step's `instructions.md` body is not used at runtime — only its frontmatter (title, `required`, `condition`, `required_skills`) is honoured

### R2: Child step semantics match standalone

- [ ] Given a child workflow whose step `01-check` has `condition: "inbox has notes"`, when the child runs as part of a parent and the condition fails, then `01-check` is condition-skipped exactly as it would be in a standalone run
- [ ] Given a child workflow whose step `02-categorize` has `required: false`, when the child runs as part of a parent, then the agent can skip `02-categorize` and the engine accepts the skip
- [ ] Given a child workflow whose step `03-tag` has `required_skills: [tagging-rules]`, when `03-tag` is activated inside a composed run, then the resolved skill chain is included in the tool response identical to a standalone run

### R3: Composition-step-level gating

- [ ] Given the parent's composition step has `condition: "should process inbox"` and the condition fails, when the parent reaches that step, then the step is condition-skipped, no child workflow record is created, no scratchpad is touched, and the parent advances to its next step
- [ ] Given the parent's composition step has `required: false`, when the agent calls `update_workflow_state(parent_id, comp_step, "skip")`, then the step is skipped, no child workflow record is created, and the parent advances
- [ ] Given the parent's composition step is `required: true` (default), when the agent calls `update_workflow_state(parent_id, comp_step, "skip")`, then the tool returns the standard "step is required" error and no child workflow record is created (no spawn side effect)

### R4, R4.1: Nested state persistence

- [ ] Given a parent at composition step has spawned a child, when the records are inspected, then a separate child workflow state record exists with `parent_workflow_id` set to the parent's ID and `parent_step_id` set to the parent's composition step ID
- [ ] Given a parent has an active child, when the process restarts, then both records remain in the database and the agent can recover via `get_workflow_state(parent_id)`
- [ ] Given a child auto-finalizes, when the record is inspected, then the child is soft-deleted, the parent's composition step is marked completed, the parent's next pending step is auto-started, and the parent's `current_step` reflects that next step
- [ ] Given a composition step is activated, when the child record is created, then the child's `definition_snapshot` is captured at that moment from the current registered child workflow definition (not from a snapshot taken at parent-start time)
- [ ] Given the referenced child workflow definition is changed between when the parent started and when the composition step activates, when the composition step activates, then the child runs against the latest definition (snapshot reflects current registered state at spawn)

### R5: Cycle detection at load time

- [ ] Given workflow A composes workflow B which composes workflow A, when the registry loads workflows, then both A and B are rejected, neither is registered, and a warning is logged identifying the cycle
- [ ] Given workflow A composes itself directly, when the registry loads workflows, then A is rejected, not registered, and a warning is logged
- [ ] Given a non-cyclic composition graph (A → B → C, no back-edge), when the registry loads workflows, then all three workflows register normally
- [ ] Given a skill is reloaded and the new workflow set introduces a cycle that includes a workflow with an active state record, when the active workflow resumes via `get_workflow_state(parent_id)`, then the engine surfaces a corruption error indicating the workflow is no longer registered and the agent is instructed to abort

### R6: Static validation of composition target

- [ ] Given a parent workflow whose step references `composes: nonexistent`, when the registry loads workflows, then the parent is rejected with a warning identifying the missing target; the workflow is not available for `start_workflow`
- [ ] Given a parent whose step references `composes: other-skill/missing`, when the registry loads, then the parent is rejected with a warning identifying the missing skill or workflow; the workflow is not available
- [ ] Given a parent whose composition reference targets a workflow that has zero steps, when the registry loads, then the parent is rejected with a warning (a zero-step workflow can't be a meaningful child)
- [ ] Given a parent's composition reference targets a workflow that is itself rejected at load time (cycle or missing target), when the registry loads, then the parent is also rejected (cascading rejection); the warning identifies both the parent and the underlying cause

### R7, R7.1, R8: Single-ID driving + breadcrumb + routing

- [ ] Given the parent has spawned a child and the agent calls `update_workflow_state(parent_id, <child_step_id>, <action>)`, when the tool resolves the call, then it routes the action to the active child layer and applies it
- [ ] Given the agent calls `update_workflow_state(parent_id, <step_id>, <action>)` with a step ID that does not match the deepest active layer's expected step (e.g. a parent step ID while the child is active, or a typo, or a stale reference to a soft-deleted child's step), when the tool resolves the call, then it returns an error listing the deepest active layer's workflow name and valid step IDs
- [ ] Given the parent's composition step is `started` and a child is active, when the agent calls `update_workflow_state(parent_id, <parent_comp_step_id>, "complete")` (attempting to complete the parent's composition step directly), then the tool returns an error directing the agent to operate on the active child's step
- [ ] Given any activation response while a child is running, when the response is constructed, then it includes a breadcrumb header showing the parent → child path using `>` as the separator (e.g. `weekly-review/02-handle-inbox > process-inbox-note/02-categorize`)
- [ ] Given the agent loses the breadcrumb context, when it calls `get_workflow_state(parent_id)`, then the response includes the active child path so the agent can re-orient

### R9: Shared scratchpad

- [ ] Given a parent is started and writes a scratchpad file at `.tachikoma/scratchpads/workflow-<parent_id>.md`, when a child is spawned, then the child uses the parent's scratchpad path — no new file is created
- [ ] Given the agent writes notes during the child's execution, when the parent resumes after the child auto-finalizes, then those notes remain in the parent's scratchpad
- [ ] Given the top-level workflow auto-finalizes (or is aborted), when cleanup runs, then exactly one scratchpad file is deleted (the parent's)
- [ ] Given two top-level parents `weekly-review` and `daily-review` are both active and each is currently composing a separate instance of `process-inbox-note`, when each child writes to its scratchpad, then each writes to its own parent's scratchpad — the two parent scratchpads remain isolated and no cross-write occurs

### R10: Composed instances exempt from uniqueness

- [ ] Given workflow `process-inbox-note` is currently composed inside an active `weekly-review`, when a `daily-review` is started and reaches its own composition step that also references `process-inbox-note`, then the second composed instance is created successfully (no duplicate-prevention error)
- [ ] Given workflow `process-inbox-note` is currently composed inside an active parent, when the agent calls `start_workflow("inbox-skill", "process-inbox-note")` to start it standalone, then the call succeeds because the duplicate check applies only across other top-level instances
- [ ] Given a top-level instance of `weekly-review` is already active, when the agent attempts to start another top-level `weekly-review` via `start_workflow`, then duplicate prevention rejects the call (proving R10's exemption applies only to composed instances, not to top-level uniqueness)

### R11, R12: Recovery view

- [ ] Given an active parent with an active child, when `list_active_workflows` is called, then the parent appears as the only entry and the child is not listed
- [ ] Given an active parent with an active child, when `get_workflow_state(parent_id)` is called, then the response includes: parent step states with the composition step shown as `started`, the child workflow name, the child's current step, and the child's step states
- [ ] Given the parent has previously completed a composition step whose child has been finalized (soft-deleted), when `get_workflow_state(parent_id)` is called, then the completed composition step appears as `completed` with no nested child data inlined
- [ ] Given the agent has never had context of the child, when it calls `get_workflow_state(parent_id)` after a context loss, then the active child is visible inline in the response and recovery is possible without ever needing the child's separate ID
- [ ] Given the agent persisted a child workflow ID before the agent was migrated to single-ID driving, when it calls `get_workflow_state(<child_id>)` directly, then the tool returns the child's state as a standalone view (the record still exists and is queryable by ID), but the response includes a note that the recommended access path is via the parent

### R13: Auto-resume on child finalize (atomic)

- [ ] Given a child is at its last step and the agent completes it via `update_workflow_state(parent_id, <last_child_step>, "complete")`, when the tool processes the call, then the child is auto-finalized (soft-deleted), the parent's composition step is auto-completed, the parent's next pending step is auto-started, and the response is the parent's next step's instructions (not a "child finalized" message followed by a separate `start` call)
- [ ] Given a child auto-finalizes and the parent's composition step was the parent's last step, when the tool processes the call, then the parent itself auto-finalizes (cascading up through any further parents) and the response confirms top-level completion
- [ ] Given a child auto-finalizes and the parent's next step is itself a composition step, when the tool processes the call, then the next child is spawned in the same tool call and the response is its first step's instructions
- [ ] Given the auto-resume cascade encounters an error mid-way (e.g. a `condition` evaluator fails on the next step), when the tool processes the call, then the entire cascade is rolled back atomically — no partial state is committed; the child is not marked finalized, the parent's composition step is not marked completed, and the agent receives an error response

### R14: Skipped composition step doesn't spawn

- [ ] Given the composition step is condition-skipped, when the next pending step is determined, then no child workflow record is created in the database and no scratchpad changes occur
- [ ] Given the composition step is explicitly skipped (allowed because `required: false`), when the parent advances, then no child workflow record is created in the database

### R15: Abort cascades (atomic)

- [ ] Given an active parent with an active child, when the agent calls `end_workflow(parent_id, "abort")`, then both records are soft-deleted, the shared scratchpad is removed, and `list_active_workflows` no longer includes the parent
- [ ] Given an active parent with multiple levels of nested children (parent → child → grandchild), when the parent is aborted, then every record in the stack is soft-deleted in a single atomic operation
- [ ] Given the abort cascade encounters an error while soft-deleting one of the descendants, when the operation is rolled back, then no records in the stack are soft-deleted (parent remains active, descendants remain active, scratchpad remains in place)

### R16: Stale cleanup interaction

- [ ] Given a parent and child are both active and the parent's `updated_at` is older than the stale threshold but the child has been updated within the threshold, when stale cleanup runs, then neither is removed because the cleanup considers the freshest `updated_at` across the active stack
- [ ] Given a parent and child are both active and every record's `updated_at` exceeds the stale threshold, when stale cleanup runs, then both are soft-deleted and the shared scratchpad is removed (no orphan child)

### R17: Deep nesting

- [ ] Given a non-cyclic composition graph that produces a 3+ level run at execution time (parent → child → grandchild), when the agent advances through every level, then activations route to the deepest layer correctly, breadcrumbs reflect the full path, and auto-resume cascades correctly walk back up to the top level
- [ ] Given a non-cyclic composition graph with arbitrary depth, when the agent runs it end-to-end, then no hard depth limit is enforced (R5's load-time cycle detection guarantees the runtime depth is bounded by the static graph)

### Edge cases

- [ ] Given a composition step's referenced workflow is renamed or removed between sessions (skill registry no longer contains the target), when an active workflow recorded with a now-missing reference resumes, then the engine surfaces a corruption error on the parent's resume and the agent is instructed to abort
- [ ] Given a composition step has `required_skills` declared on it (in addition to `composes:`), when the composition step activates, then the declared skills are injected as part of the tool response that announces the child's first step (composition-step skills don't conflict with skills declared inside the child)
- [ ] Given the agent calls `update_workflow_state(parent_id, <child_step>, "start")` against a child step that is already in the `started` state (idempotent retry, e.g. after a transient client-side error), when the tool resolves the call, then the standard step-state validation applies: the call returns the existing step's instructions or the standard "already started" error per current behavior — composition does not change idempotency semantics
- [ ] Given a child workflow's last step has `condition` and is condition-skipped (rather than completed), when the tool processes the call, then the auto-resume cascade still triggers and the parent's composition step is auto-completed exactly as if the last step had been completed
- [ ] Given a workflow definition is modified to add a new composition reference while a workflow with the old definition is currently running, when the active workflow continues, then it uses its existing definition snapshot — the new composition reference is irrelevant to the running instance
