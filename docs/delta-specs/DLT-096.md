# Delta Spec: DLT-096 - Include Last Exchange in Session Resumption Candidates

## Story

As the boundary detection system, I need the last assistant response from both the current session and candidate sessions so that I can make more accurate session routing decisions about whether a new message continues an active conversation or matches a previous session.

## What It Does

Adds a `last_exchange` field to the session model that stores the assistant's final text response from the most recent exchange. A new per-message processor updates this field after each agent response. The boundary detection prompt then includes this data alongside summaries for both the current session and candidate sessions, giving the routing decision concrete signal about the conversational state rather than relying solely on rolling summaries.

The `agent_response` string passed to the per-message pipeline is already the pre-aggregated final response text (assembled by the coordinator from the SDK event stream) — the processor stores it directly without additional extraction logic.

## Requirements

| ID | Requirement | Status |
|----|-------------|--------|
| R0 | Include the last assistant response from each candidate session (and the current session) in the boundary detection decision | Core goal |
| R1 | Add a `last_exchange` field to the session model, updated after each agent response by the per-message pipeline | Must-have |
| R2 | Gracefully handle sessions where `last_exchange` is null (first message, pipeline failure, corrupt data) — boundary detection proceeds with summary-only | Must-have |
| R3 | Include the current session's `last_exchange` in the boundary detection prompt alongside its summary | Must-have |
| R4 | Include each candidate session's `last_exchange` alongside its summary in the candidates section of the boundary detection prompt | Must-have |
| R5 | The boundary detection decision needs only the assistant's final synthesized response text, not intermediate tool results or streaming text chunks | Must-have |

## Acceptance Criteria

### Session Model Extension (R1, R5)

- [ ] Given a session with no agent responses yet, when the session is created, then `last_exchange` is null
- [ ] Given an active session, when the per-message processor receives the pre-aggregated `agent_response` string, then `last_exchange` is updated with that string
- [ ] Given the `agent_response` is empty or whitespace-only, when the per-message processor runs, then `last_exchange` is not updated (previous value retained or null)
- [ ] Given the per-message processor fails to persist `last_exchange`, when the error occurs, then it is logged and the conversation continues (consistent with existing per-message pipeline error isolation)
- [ ] Given the `last_exchange` field is added, then an Alembic migration adds the nullable column with no default to existing rows
- [ ] Given `last_exchange` updates run in the per-message pipeline, when the pipeline executes, then the update does not block or delay response delivery to the user (already guaranteed by the existing async per-message pipeline pattern)

### Boundary Detection — Current Session (R0, R3)

- [ ] Given an active session with both `summary` and `last_exchange`, when boundary detection runs, then the prompt includes both the summary and the last assistant response
- [ ] Given an active session with `summary` but null `last_exchange`, when boundary detection runs, then the prompt includes only the summary (no "Last assistant response" section)
- [ ] Given boundary detection receives the current session's last exchange, when the classifier evaluates the message, then it uses both the summary and last exchange as context for the continuation decision

### Boundary Detection — Candidate Sessions (R0, R4)

- [ ] Given candidate sessions with both `summary` and `last_exchange`, when the candidates section is rendered, then each candidate shows both its summary and its last assistant response
- [ ] Given a candidate session with `summary` but null `last_exchange`, when the candidates section is rendered, then that candidate shows only its summary
- [ ] Given multiple candidate sessions, when the boundary detector evaluates them, then each candidate's last exchange is available as additional matching signal alongside the summary

### Graceful Degradation (R2)

- [ ] Given a session where the per-message processor never ran (first exchange), when boundary detection runs, then `last_exchange` is null and boundary detection proceeds with summary-only
- [ ] Given a session where the per-message processor failed on the last exchange, when boundary detection runs, then `last_exchange` retains its previous value (or null) and boundary detection proceeds normally
- [ ] Given all sessions have null `last_exchange` (e.g., immediately after migration), when boundary detection runs, then it behaves identically to the current system (summary-only for all)

### Session Lifecycle (R1)

- [ ] Given a session is closed and later reopened, when it becomes active again, then `last_exchange` retains its previous value from before the session was closed
- [ ] Given a reopened session with new exchanges, when the per-message processor runs, then `last_exchange` is updated normally (overwriting the pre-close value)
