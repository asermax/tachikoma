# Delta Spec: DLT-049 - Plugin Hook for Custom Context Providers

## Story

As a plugin author, I want to declare context providers in my plugin manifest so that my plugin can inject custom context (calendar events, CRM data, external knowledge) into every agent conversation without modifying core code.

## What It Does

Extends the plugin system to discover, validate, and register context providers declared in plugin manifests. Plugin providers implement the existing `ContextProvider` and/or `MessageContextProvider` ABCs. During plugin loading, each declared provider module is imported, its class is inspected to determine which ABC it implements, and it is registered into the appropriate pipeline(s). Providers receive the plugin's validated config dict at construction time and participate in pre-processing with the same error isolation as built-in providers.

## Requirements

| ID | Requirement | Status |
|----|-------------|--------|
| R0 | Plugins can declare context providers that participate in pre-processing alongside built-in providers | Core goal |
| R1 | Plugin context providers implement the existing `ContextProvider` and/or `MessageContextProvider` ABCs | Must-have |
| R2 | Plugin providers are registered into the appropriate pipeline(s) based on ABC inspection — `ContextProvider` subclasses go to session-gated pipeline, `MessageContextProvider` subclasses go to per-message pipeline, classes implementing both go to both | Must-have |
| R3 | Plugin providers receive the plugin's validated config dict as a keyword argument at construction | Must-have |
| R4 | Plugin provider failures are isolated — one plugin's broken provider doesn't break other providers or core providers; failures are logged per the existing error isolation pattern (DES-002) | Must-have |
| R5 | Manifest declares context providers in a `[context_providers]` section with module-name entry points resolving to files in a `context_providers/` directory relative to the plugin install directory | Must-have |
| R6 | Handler validation at discovery time — missing files, import errors, classes not implementing a recognized ABC cause the plugin to fail with a diagnostic | Must-have |
| R7 | Plugin providers return full `ContextResult` objects (text, MCP servers, agents, metadata) identically to built-in providers | Must-have |
| R8 | Plugin context providers are re-registered on plugin update: old providers unregistered from pipelines, new providers discovered, validated, and registered | Must-have |
| R9 | Plugin context providers are removed from pipelines on plugin uninstall | Must-have |
| R10 | CC plugins declaring context_providers-like contributions in their manifest have those entries silently ignored with an INFO log, consistent with other CC contribution handling | Must-have |
| R11 | Multiple context providers per plugin are supported — the `[context_providers]` section can declare multiple entry points | Must-have |

## Acceptance Criteria

### Manifest Declaration (R5, R10, R11)

- [ ] Given a `tachikoma-plugin.toml` with a `[context_providers]` section containing `calendar = "calendar"` and `crm = "crm"` entries, when the manifest is parsed, the internal model contains two context provider entries resolving to `context_providers/calendar.py` and `context_providers/crm.py`
- [ ] Given a `[context_providers]` section with a single entry, when the manifest is parsed, one provider entry is captured
- [ ] Given a manifest without `[context_providers]`, when parsed, the plugin loads normally with no context provider contributions
- [ ] Given a CC plugin with a `"context_providers"` contribution in `plugin.json`, when parsed, the contribution is silently ignored with an INFO log

### Provider Class Discovery and Validation (R1, R2, R6)

- [ ] Given a provider module `context_providers/calendar.py` containing a class that subclasses `ContextProvider`, when discovery runs, the class is identified as a session-gated provider
- [ ] Given a provider module containing a class that subclasses `MessageContextProvider`, when discovery runs, the class is identified as a per-message provider
- [ ] Given a provider module containing a class that subclasses both `ContextProvider` and `MessageContextProvider`, when discovery runs, the class is identified for registration in both pipelines
- [ ] Given a provider module where no class implements either ABC, when discovery runs, the plugin fails with a diagnostic stating that no class implements a recognized provider interface
- [ ] Given a provider module where `context_providers/calendar.py` does not exist on disk, when discovery runs, the plugin fails with a diagnostic naming the missing file
- [ ] Given a provider module that exists but cannot be imported (syntax error, missing dependency), when discovery runs, the plugin fails with a diagnostic including the import error message
- [ ] Given a module name in `[context_providers]` containing `..` segments, path separators, or other traversal patterns, when discovery runs, the plugin fails with a diagnostic about invalid module name — only bare module names are accepted
- [ ] Given a provider class that does not implement the required abstract methods (`provide()`, `status_message()`), when instantiation is attempted, the plugin fails with a diagnostic about missing abstract methods
- [ ] Given a provider module containing multiple classes implementing the ABCs, when discovery runs, all concrete provider classes are discovered and registered (abstract base classes or non-ABC classes are skipped)

### Provider Instantiation (R3)

- [ ] Given a validated provider class whose `__init__` accepts `config` as a keyword argument, when the loader instantiates it, the plugin's validated config dict is passed
- [ ] Given a plugin with no config schema, when the provider is instantiated, an empty dict is passed as `config`
- [ ] Given a provider class whose `__init__` does not accept `config` as a keyword argument, when the loader attempts instantiation, the plugin fails with a diagnostic stating the expected signature

### Pipeline Registration (R2, R4, R7)

- [ ] Given a plugin with a `ContextProvider` subclass, when loading completes, the provider is registered in the session-gated `PreProcessingPipeline` and participates in the next pre-processing run
- [ ] Given a plugin with a `MessageContextProvider` subclass, when loading completes, the provider is registered in the per-message `MessagePreProcessingPipeline` and participates in the next message's pre-processing
- [ ] Given a plugin with a provider implementing both ABCs, when loading completes, the provider is registered in both pipelines
- [ ] Given a plugin provider returns a `ContextResult` with `mcp_servers`, when the pipeline collects results, the MCP servers are available to the coordinator for session configuration identically to built-in providers
- [ ] Given a plugin provider returns a `ContextResult` with `agents`, when the pipeline collects results, the agent definitions are available identically to built-in providers
- [ ] Given a plugin provider returns a `ContextResult` with `metadata`, when the coordinator persists the result, the metadata is stored with the context entry identically to built-in providers
- [ ] Given a plugin provider raises during `provide()`, when the pipeline runs, the failure is logged, other providers (built-in and plugin) complete normally, and the message proceeds with results from successful providers
- [ ] Given multiple plugins each contribute providers, when the pipeline runs, all providers execute concurrently with error isolation

### Provider Lifecycle (R8, R9)

- [ ] Given a plugin with registered context providers, when the plugin is updated via `update_plugin`, old providers are unregistered from their pipelines, new providers are discovered, validated, and registered
- [ ] Given a plugin with registered context providers, when `remove_plugin` runs, the providers are unregistered from their pipelines
- [ ] Given an updated plugin whose new provider fails validation, when re-registration runs, old providers remain active and a diagnostic is stored

### Status Messages

- [ ] Given a plugin provider that implements `status_message()` (inherited from ABC), when the pipeline runs with `on_status`, the provider's status messages are emitted identically to built-in providers
