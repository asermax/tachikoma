# Delta Spec: DLT-086 - Manual session switching via Telegram reply

## Story

As a user, I want to switch to a specific previous conversation by replying to any message from that conversation so that I can resume exactly the context I want without relying on automatic boundary detection.

## What It Does

When a user replies to a Telegram message that belonged to a previous session, the new message is routed to that session instead of following automatic boundary detection. The system looks up which session the replied-to message belonged to, closes the current session (if any), and reopens the target session with the new message as input. If the target session cannot be resumed, the user receives a message explaining the issue. All message types support reply-to routing — both text and the full set of media types (photos, voice, audio, documents, stickers, video, video notes, animations).

| ID | Requirement | Status |

| R2 | Detect `reply_to_message` in incoming media messages and extract the replied-to message ID | Must-have |

| R4 | Set `target_session_id` on the envelope when the reply maps to a different session | Must-have |

| R7 | Handle target session that cannot be reopened (validation failure, stale) — send error message to user | Must-have |
| R8 | When agent is busy and reply targets a different session, defer via deferred queue with `target_session_id` | Must-have |
| R9 | When agent is busy and reply targets the same/unknown session, steer normally (current behavior) | Must-have |

## Acceptance Criteria

### Reply detection and session lookup (R1, R2, R3)

- [ ] Given a user sends a text message that is a reply to another Telegram message, when the handler processes it, then `message.reply_to_message.message_id` is extracted and used for session lookup
- [ ] Given a user sends a media message (photo, voice, audio, document, sticker, video, video note, animation) that is a reply to another Telegram message, when the handler processes it, then `message.reply_to_message.message_id` is extracted and used for session lookup
- [ ] Given a reply targets a message whose external ID is recorded in `channel_messages`, when the lookup runs, then `find_session_by_external_id("telegram", str(reply_to_message_id))` returns the associated session ID
- [ ] Given a reply targets a message whose external ID is not in `channel_messages` (pre-feature messages, messages from other platforms), when the lookup runs, then `None` is returned

### Session routing (R4, R5, R6)

- [ ] Given a reply targets a message that maps to a session different from the current active session, when the message is processed, then `target_session_id` is set on the envelope and the coordinator closes the current session and reopens the target session
- [ ] Given a reply targets a message that maps to the current active session, when the message is processed, then no `target_session_id` is set and the message routes normally (no session switch)
- [ ] Given a reply targets a message whose external ID is not found (lookup returns `None`), when the message is processed, then no `target_session_id` is set and the message routes normally through boundary detection
- [ ] Given a reply targets a message and the current session reopens successfully, when the coordinator processes the message, then the message is delivered in the resumed session context

### Failed session resume (R7)

- [ ] Given a reply targets a session that fails pre-validation (transcript file missing on local filesystem), when `can_reopen_session` returns false, then an error message is sent to the user in the chat explaining the issue (e.g., "Could not resume that conversation — its context is no longer available") and the message falls through to normal routing without closing the current session
- [ ] Given a reply targets a session that is older than the configured max age, when `can_reopen_session` returns false, then an error message is sent to the user in the chat explaining the issue and the message falls through to normal routing
- [ ] Given pre-validation fails, when the message falls through to normal routing, then boundary detection runs normally and the message is delivered in whatever session the coordinator determines (current or new)

### Busy-channel behavior (R8, R9)

- [ ] Given the agent is busy (delivery lock held) and a reply targets a different session, when the message arrives, then it is deferred via `enqueue_deferred()` with `target_session_id` set on the envelope
- [ ] Given the agent is busy and a reply targets the same session as the active session, when the message arrives, then it is steered into the active session via `enqueue()` (no deferral, no session switch)
- [ ] Given the agent is busy and a reply targets an unknown session (lookup returns `None`), when the message arrives, then it is steered into the active session via `enqueue()` (no deferral)
- [ ] Given a deferred reply-to message is drained from the deferred queue, when the coordinator processes it, then the session switch (close current + reopen target) occurs as part of that processing cycle

### Interaction with existing features

- [ ] Given a reply-to message that is also a `/new` command, when the command is detected, then `/new` takes precedence (force_new=True, no target_session_id) — explicit user override wins over implicit session routing
- [ ] Given a reply-to message that is also a `/queue` command, when the command is detected, then `/queue` takes precedence — the reply-to routing is discarded
- [ ] Given a message that is not a reply, when processed, then behavior is unchanged from current implementation

### Flow Description

**Entry point**: User replies to any message in the Telegram chat that was part of a previous conversation.

**Happy path (idle, different session)**: The user replies to a message from a past session. The handler extracts `reply_to_message.message_id`, looks up the session via `find_session_by_external_id`, finds it maps to a different session, sets `target_session_id` on the envelope, and processes it. The coordinator closes the current session (triggering async post-processing) and reopens the target session. The message is delivered in the resumed session context.

**Busy path (different session)**: Same as above, but the delivery lock is held. The handler sets `target_session_id` on the envelope and defers it via `enqueue_deferred()`. When the current turn completes and the deferred queue drains, the coordinator processes the deferred message, performs the session switch, and delivers the message in the target session.

**Same-session path**: The user replies to a message from the current session. The lookup returns the active session's ID. No `target_session_id` is set and the message routes normally.

**Unknown-session path**: The user replies to a message whose ID is not recorded (e.g., sent before this feature was implemented). The lookup returns `None`. No `target_session_id` is set and the message routes through normal boundary detection.

**Failed-resume path**: The target session fails pre-validation (transcript missing, too old). An error message is sent to the user explaining the issue, and the message falls through to normal routing without closing the current session or creating a new one.

**Decision points**: Reply-to detection (has reply_to_message → extract ID for lookup, no reply → normal processing). Session lookup result (different session → set target_session_id, same session → normal, not found → normal). Pre-validation result (valid → proceed with session switch, invalid → error message + normal routing). Agent state (busy → defer with target_session_id, idle → process with target_session_id). Command precedence (/new or /queue → override reply-to routing).

**Exit points**: Message delivered in resumed session, message delivered in current session (same-session or unknown), error message sent with fall-through to normal routing, message steered into active session (busy + same/unknown).
