# Delta Spec: DLT-140 - Allow send_file to accept paths outside the workspace

## Story

As a user, I want the agent to be able to send me files it generates in system temp directories (PDFs, rendered charts, exports) without having to copy them into the workspace first, so that file delivery works on the first try without a manual detour.

## What It Does

Relaxes the path validation in the Telegram `send_file` MCP tool so absolute paths under the system temporary directory (and any additional roots the operator configures) are accepted alongside paths inside the workspace. Unqualified paths still resolve relative to the workspace, preserving the previous default. Paths outside all allowed roots are still rejected, with an error message that names the allowed roots so the agent can self-correct.

## Requirements

| ID | Requirement | Status |
|----|-------------|--------|
| R0 | `send_file` accepts files generated outside the workspace without requiring a manual copy first | Core goal |
| R1 | Unqualified (relative) paths continue to resolve against the workspace root | Must-have |
| R2 | Absolute paths under the system temporary directory are accepted | Must-have |
| R3 | Absolute paths inside the workspace continue to be accepted | Must-have |
| R4 | Absolute paths outside all allowed roots are rejected, and the error message names the allowed roots so the agent can self-correct | Must-have |
| R5 | Only existing regular files can be sent; missing paths and directories are rejected | Must-have |
| R6 | Operators can declare additional absolute roots that `send_file` will accept | Must-have |
| R7 | The agent is instructed (via its tool/skill documentation) about the accepted `file_path` locations so it chooses valid paths on the first try | Must-have |

## Acceptance Criteria

### Workspace-relative default (R1, R3)

- [ ] Given a relative `file_path` (e.g. `exports/report.pdf`), when the tool is called, then it resolves against the workspace root and the file is sent if it exists there
- [ ] Given an absolute `file_path` inside the workspace, when the tool is called, then it is accepted and sent
- [ ] Given a relative `file_path` with `..` components that resolves inside the workspace, when validated, then it is accepted

### Temp-directory absolute paths (R0, R2)

- [ ] Given an absolute `file_path` under the system temporary directory (e.g. `/tmp/report.pdf` on Linux), when the tool is called, then it is accepted and the file is sent without requiring a copy to the workspace
- [ ] Given a file written by the agent under `/tmp/tachikoma-media/…`, when later passed to `send_file` by absolute path, then it is accepted
- [ ] Given the system temp directory differs from `/tmp` (e.g. `TMPDIR=/var/folders/…` on macOS), when a file under that resolved path is passed, then it is accepted
- [ ] Given the system temp directory is reached via a platform symlink (e.g. `/tmp` → `/private/tmp` on macOS), when the user passes either the symlink or the real path, then both are accepted because the input path and the allowed roots are compared after symlink resolution

### Symlinks across allowed-root boundaries (R2, R4)

- [ ] Given an input path inside an allowed root that is a symlink pointing outside all allowed roots, when validated, then it is rejected (the resolved target governs the membership check)
- [ ] Given an input path outside all allowed roots that is a symlink pointing inside an allowed root, when validated, then it is accepted (the resolved target governs the membership check)

### Configurable extra roots (R6)

- [ ] Given a global config with one or more extra allowed roots declared under the Telegram section, when the tool is called with an absolute path under any of those roots, then it is accepted
- [ ] Given a configured extra root uses `~` for the home directory, when the config is loaded, then the root is expanded before being used for validation
- [ ] Given a configured extra root is not an absolute path (after `~` expansion), when the config is loaded, then loading fails with a clear validation error
- [ ] Given a configured extra root does not exist on disk at load time, when the config is loaded, then loading succeeds (the directory may be created later); a path under the configured root is accepted only after the directory and file actually exist
- [ ] Given the config has no extra roots declared, when the tool runs, then only the workspace and the system temp directory are treated as allowed (default behavior)
- [ ] Given the workspace path is itself under the system temp directory (e.g. CI sandboxes), when validation runs, then paths under the workspace are still accepted (allowed roots are treated as a union)

### Rejection of paths outside allowed roots (R4)

- [ ] Given an absolute `file_path` that resolves outside the workspace, the system temp directory, and any configured extra roots (e.g. `/etc/passwd`), when the tool is called, then it returns `is_error: True`
- [ ] Given a relative `file_path` with `..` components that resolves outside all allowed roots, when validated, then it is rejected
- [ ] Given a rejection occurs, when the error message is produced, then it names the allowed roots (workspace, system temp directory, configured extras) so the agent can pick a valid location

### Existence and file kind (R5)

- [ ] Given an allowed path that does not exist on disk, when the tool is called, then it returns `is_error: True` with a "File not found" message
- [ ] Given an allowed path that points to a directory, when the tool is called, then it is rejected

### Skill instructions (R7)

- [ ] Given the `send_file` skill documentation is loaded by the agent, when it describes the `file_path` parameter, then it states that absolute paths under the system temporary directory (and any configured extra roots) are accepted in addition to workspace-relative paths
- [ ] Given the skill's Constraints section is loaded, when the agent reads it, then the previous "must exist in the workspace" wording is replaced with the actual acceptance rules
