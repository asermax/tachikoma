# Delta Spec: DLT-035 - Receive images and audio from Telegram

## Story

As a user, I want to send images, voice messages, audio files, and other media through Telegram so that the agent can see and work with my non-text content.

## What It Does

Extends the Telegram channel to accept all common media types (photos, voice, audio, documents, stickers, video, video notes, animations) instead of silently ignoring them. Each media message is downloaded to a dedicated temp folder and forwarded to the agent as a text message describing the file with its metadata and path. The agent can then decide how to process the file using its existing tools. A bootstrap hook manages the temp folder lifecycle.

## Acceptance Criteria

### Media Proxy Pattern (R0)

- [ ] Given the bot is running, when an authorized user sends a media message of any supported type, then the file is downloaded to the temp folder and a text description including the file path is enqueued to the coordinator
- [ ] Given a media message is received, when it is processed, then the agent receives a text message it can act on using its existing tools (e.g., Read for images, Bash for audio)
- [ ] Given multiple media messages arrive while a response is streaming, when each arrives, then each is enqueued and processed in order (same buffering behavior as text messages)
- [ ] Given any media type, when the description is constructed, then it follows a consistent structure across all types: media type label, type-specific metadata, the saved file path on its own line, and optional caption — the file path is always present and unambiguous
- [ ] Given a saved file, when the file is named, then it has a unique name (e.g., UUID-based) to prevent overwrites from concurrent or repeated downloads
- [ ] Given a saved file, when the file is named, then it has an appropriate file extension matching its content type (e.g., `.jpg` for photos, `.ogg` for voice, original filename preserved for documents)
- [ ] Given a message type not in the supported set (e.g., contact, location, poll, venue), when received from the authorized user, then it is silently ignored

### Photo Messages (R1)

- [ ] Given a photo message from the authorized user, when received, then the largest available photo size is downloaded and saved to the temp folder
- [ ] Given a photo is saved, when the description is constructed, then it includes the image dimensions (width x height), file size, and the saved file path

### Voice Messages (R2)

- [ ] Given a voice message from the authorized user, when received, then the voice file is downloaded and saved to the temp folder
- [ ] Given a voice file is saved, when the description is constructed, then it includes the duration (in seconds), MIME type (e.g., audio/ogg), and the saved file path

### Audio Files (R3)

- [ ] Given an audio file message from the authorized user, when received, then the audio file is downloaded and saved to the temp folder
- [ ] Given an audio file is saved, when the description is constructed, then it includes the title, performer, duration, and the saved file path
- [ ] Given an audio file without title or performer metadata, when the description is constructed, then missing fields are omitted (not shown as "Unknown")

### Document Messages (R4)

- [ ] Given a document message from the authorized user, when received, then the document is downloaded and saved to the temp folder
- [ ] Given a document is saved, when the description is constructed, then it includes the original filename, MIME type, file size, and the saved file path

### Sticker Messages (R5)

- [ ] Given a sticker message from the authorized user, when received, then the sticker file is downloaded and saved to the temp folder
- [ ] Given a sticker is saved, when the description is constructed, then it includes the associated emoji (if any) and the saved file path
- [ ] Given an animated sticker (.TGS) or video sticker (.WEBM), when received, then it is downloaded and described with its format noted

### Video and Video Note Messages (R6)

- [ ] Given a video message from the authorized user, when received, then the video file is downloaded and saved to the temp folder
- [ ] Given a video is saved, when the description is constructed, then it includes the duration, dimensions (width x height), and the saved file path
- [ ] Given a video note (round video) from the authorized user, when received, then it is downloaded and described with duration and dimensions

### Animation Messages (R7)

- [ ] Given an animation/GIF message from the authorized user, when received, then the animation file is downloaded and saved to the temp folder
- [ ] Given an animation is saved, when the description is constructed, then it includes the duration, dimensions, and the saved file path

### Caption Forwarding (R8)

- [ ] Given any media message with a `caption` field, when the description is constructed, then the caption text appears as the user's message alongside the file description
- [ ] Given a media message without a caption, when the description is constructed, then only the file description is sent (no placeholder text for missing caption)

### Error Handling (R9)

- [ ] Given a media file that exceeds 20 MB (Telegram bot download limit), when the file size is known before download, then the bot sends an error message to the user in the chat explaining the size limit, and no file is saved
- [ ] Given a media file whose size is not available in the message metadata, when the download is attempted and fails due to the 20 MB limit enforced by the Telegram API, then the error is handled the same as a download failure
- [ ] Given a download fails due to a network or API error, when the error occurs, then the bot sends an error message to the user in the chat and the failure is logged
- [ ] Given a download failure or size limit error, when it occurs, then the conversation remains usable (no crash, no blocked state)

### Temp Folder Management (R10)

- [ ] Given the application starts, when the bootstrap hook runs, then the dedicated temp folder exists (created if missing)
- [ ] Given the bootstrap hook runs, when files older than 30 days exist in the temp folder, then they are deleted
- [ ] Given files newer than 30 days exist in the temp folder, when the bootstrap hook runs, then they are preserved
- [ ] Given the temp folder already exists and has no old files, when the bootstrap hook runs, then it completes with no side effects (idempotent)

## User Flow

### Breadboard: Telegram Media Message Flow

```
  User sends media
  -----------------
  - media in Telegram chat
            |
      +-----+-----+
      |           |
      v           v
  Authorized   Unauthorized
  ----------   ------------
  |            (silently drop)
  |
  +-----+---------+
  |               |
  v               v
  Supported Type   Unsupported Type
  --------------   ----------------
  |                (silently drop)
  |
  +-----+-------+
  |             |
  v             v
  Downloadable   Too Large (>20MB)
  ------------   ------------------
  |              - error message
  |                in chat
  v
  Download & Save
  ---------------
  - save to temp folder
    with unique name
        |
  +-----+-----+
  |           |
  v           v
  Success     Download Failed
  -------     ---------------
  |           - error message
  |             in chat
  v
  Describe & Enqueue
  ------------------
  - build text description
    with metadata + path
  - include caption if present
  - enqueue to coordinator
        |
        v
  Processing
  ----------
  - (same as text message
    flow from here)
```

### Flow Description

**Entry point**: User sends a media message (photo, voice, audio, document, sticker, video, video note, or animation) to the Telegram bot.

**Happy path**: The bot receives the media message, confirms the sender is authorized, verifies it is a supported media type, checks the file size is within the 20 MB limit, downloads the file to the dedicated temp folder with a unique name and appropriate extension, constructs a text description with relevant metadata and the saved file path (plus caption if present), and enqueues it to the coordinator. From there, processing follows the standard text message flow — the agent receives the description and can use its tools to interact with the file. Multiple media messages arriving during an active response are buffered via `enqueue()` and processed in order, the same as text messages.

**Decision points**: Authorization check (authorized -> process, unauthorized -> drop). Message type check (supported media -> process, unsupported type like contact/location/poll -> drop). File size check (within limit -> download, too large -> error message to user). Download result (success -> describe and enqueue, failure -> error message to user).

**Exit points**: Media processed successfully (enqueued as text, agent responds), file too large (error message sent, conversation continues), download failed (error message sent, conversation continues), unsupported message type (silently dropped), unauthorized sender (silently dropped).
