# Delta Spec: DLT-114 - Set TZ environment variable for agent subprocesses

## Story

As a developer, I need the agent's subprocess environment to include the configured timezone as `TZ` so that shell commands like `date` return times in my timezone without manual environment configuration.

## What It Does

Automatically injects the `TZ` environment variable (set to the user's configured IANA timezone from `settings.tasks.timezone`) into all agent subprocess environments. This ensures shell commands executed by the agent respect the user's timezone. Unlike hardcoded env vars (e.g. `CLAUDE_CODE_DISABLE_AUTO_MEMORY`) which reject collisions at startup, `TZ` is an auto-injected default that the user can override via `[agent.env]` config. The system prompt date command is simplified since `TZ` is now part of the environment.

## Requirements

| ID | Requirement | Status |
|----|-------------|--------|
| R0 | Agent subprocesses use the user's configured timezone for all date/time operations | Core goal |
| R1 | `TZ` is automatically set in the agent environment from `settings.tasks.timezone` | Must-have |
| R2 | User can override auto-injected `TZ` by explicitly setting `TZ` in `[agent.env]` config (auto-injected defaults are overridable, unlike hardcoded defaults which reject collisions) | Must-have |
| R3 | System prompt date command no longer includes `TZ=` prefix (environment handles it) | Must-have |

## Acceptance Criteria

### Automatic TZ injection (R0, R1)

- [ ] Given a user with `tasks.timezone = "America/Buenos_Aires"`, when the agent runs a shell command like `date`, then the output reflects the America/Buenos_Aires timezone
- [ ] Given a user with no explicit timezone configured (auto-detected from system), when the agent environment is constructed, then `TZ` is set to the auto-detected IANA timezone key
- [ ] Given the agent spawns sub-agents or post-processors that use `AgentDefaults.env`, when those sub-agents run shell commands, then `TZ` is also present in their environment
- [ ] Given the timezone is always validated at config load time (config-system.md R9), then `merge_env` can assume it receives a valid IANA timezone string

### User override (R2)

- [ ] Given a user sets `TZ = "UTC"` in their `[agent.env]` config section, when the agent environment is constructed, then `TZ` is `"UTC"` (user value wins over auto-injected value)
- [ ] Given a user sets `TZ` in `[agent.env]`, when the application starts, then no collision error is raised (unlike hardcoded env vars like `CLAUDE_CODE_DISABLE_AUTO_MEMORY`)

### System prompt cleanup (R3)

- [ ] Given the system prompt is rendered with a configured timezone, when the date command instruction is displayed, then it reads `date '+%A, %B %d, %Y at %H:%M:%S %Z (%z)'` without a `TZ=` prefix
- [ ] Given the system prompt still mentions the configured timezone name, when the agent reads it, then it knows its timezone context (the timezone name is still displayed, just not as a command prefix)
