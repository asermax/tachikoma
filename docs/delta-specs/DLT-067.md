# Delta Spec: DLT-067 — Telegram inline button support

## Story

As a Telegram user, I want to respond to the agent's structured prompts by tapping a button instead of typing, so that I can quickly answer multiple-choice questions, confirm/decline actions, and pick from a list without keyboard input on my phone.

## What It Does

Adds inline keyboard buttons to the Telegram channel: the agent presents a prompt with a configurable layout of buttons via a new MCP tool, the user taps a choice, and the tapped value flows back through the coordinator as a tap-tagged user message that the agent recognizes as a button response (not free text). Taps are acknowledged to Telegram immediately so the user never sees a stuck loading spinner, and the keyboard is removed after the tap by default to signal that the prompt has been answered.

## Requirements

| ID | Requirement | Status |
|----|-------------|--------|
| R0 | Agent presents interactive inline buttons in the active Telegram chat; user taps are routed back to the agent as conversational input | Core goal |
| R1 | MCP tool that sends a new message in the active Telegram chat carrying an inline keyboard built from the agent's button definitions; tool returns the sent message's ID on success | Must-have |
| R2 | Each button declares a `label` (visible text shown on the button) and a `value` (what is sent back to the agent when tapped); both fields are required per button | Must-have |
| R3 | Layout is fully agent-controlled — the tool accepts buttons as a list of rows (a list of lists), and each inner list becomes one row of the inline keyboard | Must-have |
| R4 | Tap acknowledgement is sent immediately on receipt of the `CallbackQuery`, independent of agent processing — the user's loading spinner clears within Telegram's deadline regardless of whether the agent is busy | Must-have |
| R5 | Tap value is routed through the coordinator as a tap-tagged incoming message that carries both the tapped label and value; the agent sees it as a button tap (not free text) and can use the value to interpret the user's choice | Must-have |
| R6 | Tap routing reuses the existing user-message flow: when an exchange is in flight the tap is enqueued for steering, when idle it starts a fresh processing cycle, and deferred-queue semantics apply where relevant | Must-have |
| R7 | After any tap, the inline keyboard is removed from the message by default (single-use semantics); the agent can opt to keep the keyboard via a `single_use=False` parameter on the tool | Must-have |
| R8 | Only the authorized user's taps are processed; taps from other users (in groups or any other origin) are answered to clear their spinner and otherwise silently dropped | Must-have |
| R9 | Stale taps (e.g., the user taps a button after a process restart or after the conversation has moved on) are routed to the agent like any other tap; the agent decides how to handle the choice from conversation context | Must-have |
| R10 | Telegram API failures during button presentation (rate limits, invalid params, network errors) surface a clear error result to the agent's tool call so it can self-correct or inform the user | Must-have |
| R11 | Input validation on the tool: per-button `value` fits Telegram's 64-byte `callback_data` limit, button rows are non-empty, and at least one row is provided; validation errors return a clear error result naming the offending field | Must-have |
| R12 | Keyboard-removal failures after a tap (e.g., message no longer exists, edit rate-limited) are logged but never block tap routing — the tap value still reaches the agent | Must-have |

## Acceptance Criteria

### R0, R1, R2, R3 — Presenting buttons

- [ ] Given the agent calls the button-presentation tool with a prompt and a single row of buttons (e.g. `[[{label: "Yes", value: "yes"}, {label: "No", value: "no"}]]`), when the tool executes, then a new Telegram message is sent in the authorized chat with the prompt text and a one-row inline keyboard containing those two buttons, and the tool returns the sent message ID
- [ ] Given the agent calls the tool with multiple rows of buttons, when the tool executes, then the inline keyboard renders each inner list as a separate row in the order provided
- [ ] Given the agent calls the tool, when the tool succeeds, then the response result includes the Telegram message ID so the agent can reference the prompt later
- [ ] Given the REPL channel is active (not Telegram), when the agent processes messages, then the button-presentation tool is not registered (consistent with `send_file` / `pin_message` REPL behavior)

### R4 — Immediate tap acknowledgement

- [ ] Given the user taps a button while the agent is idle, when the bot receives the `CallbackQuery`, then `callback_query.answer()` is called before any work is done that depends on agent state
- [ ] Given the user taps a button while the agent is mid-stream on another message, when the bot receives the `CallbackQuery`, then the tap is still acknowledged immediately — agent busyness never delays the acknowledgement
- [ ] Given `callback_query.answer()` raises a Telegram API error (e.g., the query is too old to answer), when the error occurs, then it is logged and tap processing continues without crashing

### R5 — Tap routing and tagging

- [ ] Given the user taps a button labeled "Yes" with value "approve", when the tap is routed to the coordinator, then the agent's next turn input is unambiguously marked as a button tap (not typed text) and carries both `label="Yes"` and `value="approve"`
- [ ] Given the agent is observing the conversation, when it receives a tap-tagged turn, then the rendered SDK input clearly signals "this is a button tap" so the agent does not mistake the value for a typed message
- [ ] Given the user taps the same button twice in quick succession (before keyboard removal completes), when both taps arrive, then each is routed independently (the system does not deduplicate taps server-side — single-use is enforced by removing the keyboard, see R7)

### R6 — Tap routing under coordinator state

- [ ] Given the agent is idle (no active exchange), when the user taps a button, then the tap is enqueued and processed as a fresh turn through the normal coordinator pipeline
- [ ] Given the agent is mid-exchange (delivery lock held), when the user taps a button, then the tap value is enqueued into the coordinator's message buffer so the SDK forwarder can steer it into the in-flight session, matching the behavior of typed text mid-stream
- [ ] Given the tap arrives while the deferred queue is draining, when the tap is routed, then it joins the message flow in the same order it would if typed
- [ ] Given a delivery cycle completes and a tap was buffered during it, when the next cycle starts, then the tap is processed in FIFO order with any other buffered messages

### R7 — Keyboard removal after tap

- [ ] Given a button is presented with default `single_use=True`, when any button on that message is tapped, then the message's inline keyboard is removed (replaced with no keyboard) so the user cannot tap again
- [ ] Given a button is presented with `single_use=False`, when any button on that message is tapped, then the keyboard remains attached and further taps from the same message are routed normally
- [ ] Given the agent calls the tool with no `single_use` argument, when the tool executes, then `single_use=True` is the default

### R8 — Authorization

- [ ] Given a tap arrives from the configured authorized user, when the bot processes it, then it follows the normal tap path
- [ ] Given a tap arrives from a different user (e.g., in a group chat where another member tapped), when the bot receives the `CallbackQuery`, then `callback_query.answer()` is still called (so their spinner clears) and the tap is otherwise silently dropped — no value reaches the agent, no keyboard is removed

### R9 — Stale taps

- [ ] Given the bot process restarts and the user taps a button on a message that pre-dates the restart, when the tap arrives, then it is acknowledged and routed to the agent as a normal tap; the agent receives the label and value and decides from context how to respond
- [ ] Given the agent has already moved past the topic that the button was attached to, when the user taps an old button, then the tap is acknowledged and routed normally; the agent's conversation context determines whether to act on it, ignore it, or ask for clarification

### R10 — Tool error surfacing

- [ ] Given the Telegram API returns a rate-limit error during button presentation, when the tool catches the `TelegramRetryAfter` (or general `TelegramAPIError`), then it returns `is_error: True` with the API error details so the agent can decide whether to retry
- [ ] Given the Telegram API rejects the request for any other reason (invalid markup, network failure), when the tool catches the error, then it returns `is_error: True` with the error details (no automatic retry)

### R11 — Input validation

- [ ] Given the agent provides a button whose `value` exceeds Telegram's 64-byte `callback_data` limit, when the tool validates inputs, then it returns `is_error: True` naming the offending button and the limit
- [ ] Given the agent provides an empty list of rows or an empty row, when the tool validates inputs, then it returns `is_error: True` explaining that at least one button is required
- [ ] Given the agent provides a button with an empty `label` or empty `value`, when the tool validates inputs, then it returns `is_error: True` explaining which field is empty

### R12 — Keyboard removal robustness

- [ ] Given the keyboard-removal edit fails (e.g., message was deleted, Telegram returned an error), when the failure occurs, then it is logged at warning level and the tap value is still routed to the agent
- [ ] Given a `single_use=True` tap triggers keyboard removal while the agent processes the value, when both operations run, then they are independent — neither blocks nor depends on the other completing first

### Flow Description

**Entry point**: The agent decides to ask the user a structured question and calls the button-presentation MCP tool. The user has not yet interacted — they will see a new message appear in their Telegram chat with the prompt and tappable buttons.

**Happy path (tap while idle)**: The bot sends a new message with the prompt text and an inline keyboard built from the agent-provided rows. The user taps one of the buttons. The bot's `CallbackQuery` handler acknowledges the tap immediately (no waiting on the agent), removes the keyboard from the message if `single_use=True`, wraps the chosen `label`/`value` in a tap-tagged incoming message, and enqueues it through the coordinator. From the coordinator's perspective, the tap is just another user message — it goes through boundary detection, pre-processing, and into the agent. The agent's SDK input clearly identifies it as a button tap so the agent doesn't confuse the value with a typed message. The agent responds via the usual streaming flow.

**Happy path (tap mid-exchange)**: The user taps a button while the agent is still responding to a previous message. The bot acknowledges the tap immediately and routes it through the same path; because the delivery lock is held, the coordinator's message buffer receives the tap and the SDK forwarder steers it into the in-flight session — matching how typed text behaves in the same state.

**Decision points**:
- Authorization: tap from authorized user → process; from any other origin → answer the query (clear spinner) and drop.
- `single_use` flag: True → remove keyboard on first tap; False → keep keyboard attached for further taps.
- Agent busy/idle: busy → buffer (steer into active session); idle → process normally.
- Stale-tap recognition: handled entirely by the agent based on conversation context — the system always routes the tap.

**Exit points**:
- Successful processing: agent responds to the tap (normal response stream); for `single_use=True`, the keyboard is gone and the prompt is visually "closed".
- Telegram errors during keyboard removal: logged, tap still processed.
- Unauthorized origin: silently dropped after answer.
- Tool-call failures during initial button presentation: error returned to the agent (no message sent in chat).
