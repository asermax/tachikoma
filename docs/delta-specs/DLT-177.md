# Delta Spec: DLT-177 - Replace agentic memory search with static index injection

## Story

As the system, I need memory context loading to be fast, cheap, and reliable so that the agent always has access to stored facts and preferences without paying an Opus round-trip on every message.

## What It Does

Replaces the agentic memory search (an Opus sub-agent running on every message to classify, search, and extract memories) with static injection of facts and preferences indexes into the foundational context at startup. The agent sees MEMORY.md indexes as navigable sections in its system prompt and fetches individual files on demand via Read. The entire MemoryContextProvider class and its supporting infrastructure are removed. Episodic memory search is removed entirely — deferred to a future MCP tool (DLT-105). The system preamble's existing `## Memories` section (under `# Memory System`) is expanded with general documentation about episodic memories (naming conventions, retention tiers, content expectations) so the agent knows what episodic files exist and can consult them manually when needed.

## Acceptance Criteria

### Static Index Injection (R0, R1, R2, R5)

- [ ] Given a workspace with facts and preferences directories containing MEMORY.md files, when the system starts up, then both index files are read and injected as sections in the foundational context with owner tag "memory_index"
- [ ] Given the injected index sections, when the agent receives a message, then it sees navigable lists of memory files with one-line descriptions and file paths
- [ ] Given a fact or preference listed in the index, when the agent determines it may be relevant, then it reads the file via the Read tool
- [ ] Given each injected index section, then it is prefaced with a description of the memory type and instructions for using the index (browse entries, Read relevant files on demand)
- [ ] Given a workspace where the facts or preferences directory has no MEMORY.md file, when the system starts up, then the injection is skipped for that directory without error or warning
- [ ] Given a workspace where MEMORY.md exists but is empty or contains only a header with no file entries, when the system starts up, then the injection is skipped for that directory without error
- [ ] Given a workspace with no memories directory at all, when the system starts up, then no memory index sections are injected and startup proceeds normally
- [ ] Given a MEMORY.md file containing entries that don't match the expected `[Name](./path.md): description` format (malformed entries), when the system reads it at startup, then well-formed entries are included and malformed entries are skipped with a debug log warning — the entire file is not rejected for individual bad entries

### Agentic Search Removal (R3, R6)

- [ ] Given the codebase after implementation, then the MemoryContextProvider class, MEMORY_SEARCH_PROMPT, ParsedMemoryEntry, parse_memory_entries(), extract_memory_paths(), and related constants (MEMORIES_OWNER, MEMORY_PATH_META_KEY, _NO_RELEVANT_MEMORIES) no longer exist in src/tachikoma/memory/context_provider.py
- [ ] Given the per-message pre-processing pipeline, when the system starts up, then no memory context provider is registered — only the skills context provider remains
- [ ] Given the codebase after implementation, when all modules are audited, then no active code imports MemoryContextProvider directly from context_provider.py or via the memory module's public API
- [ ] Given the memory module's public API (__init__.py), then MemoryContextProvider is no longer exported
- [ ] Given display code in post_processing.py that references memory_path metadata for context summary display, when the codebase is audited, then these references are removed or updated to handle the new foundational context model (no per-message memory_path metadata)
- [ ] Given the codebase after implementation, when searched for memory_path or MEMORY_PATH_META_KEY references, then no stale references to the removed per-message deduplication mechanism remain in active code

### System Preamble Expansion (R4, R7)

- [ ] Given the system preamble's existing `## Memories` subsection (under `# Memory System`), when it is rendered, then it includes general documentation about episodic memory naming conventions (daily YYYY-MM-DD.md, weekly YYYY-WNN.md, monthly YYYY-MM.md)
- [ ] Given the system preamble's Memories subsection, when it is rendered, then it describes retention tiers at a general level (daily files are recent detail, weekly are consolidated summaries, monthly are long-term arcs)
- [ ] Given the system preamble's Memories subsection, when it is rendered, then it explains content expectations (high-level summaries, not transcripts)
- [ ] Given the system preamble's Memories subsection, when it is rendered, then it provides guidance on when consulting episodic context is useful versus when facts/preferences suffice
- [ ] Given the system preamble's Memories subsection, then it does not include specific retention duration numbers (those are configuration-dependent)

### Latency Improvement (R8)

- [ ] Given a message received by the coordinator, when the per-message pre-processing pipeline runs, then no Opus sub-agent is invoked for memory search, and the pipeline completes with only the skills provider overhead
