# Delta Spec: DLT-177 - Replace agentic memory search with static index injection

## Story

As the system, I need memory context loading to be fast, cheap, and reliable so that the agent always has access to stored facts and preferences without paying an Opus round-trip on every message.

## What It Does

Replaces the agentic memory search (an Opus sub-agent running on every message to classify, search, and extract memories) with static injection of facts and preferences indexes into the foundational context at startup. The agent sees MEMORY.md indexes as navigable sections in its system prompt and fetches individual files on demand via Read. The entire MemoryContextProvider class and its supporting infrastructure are removed. Episodic memory search is removed entirely — deferred to a future MCP tool (DLT-105). The system preamble's memory section is expanded with general documentation about episodic memories (naming conventions, retention tiers, content expectations) so the agent knows what episodic files exist and can consult them manually when needed.

## Acceptance Criteria

### Static Index Injection (R0, R1, R2, R5)

- [ ] Given a workspace with facts and preferences directories containing MEMORY.md files, when the system starts up, then both index files are read and injected as sections in the foundational context
- [ ] Given the injected index sections, when the agent receives a message, then it sees navigable lists of memory files with one-line descriptions and file paths
- [ ] Given a fact or preference listed in the index, when the agent determines it may be relevant, then it reads the file via the Read tool
- [ ] Given each injected index section, then it is prefaced with a description of the memory type and instructions for using the index (browse entries, Read relevant files on demand)
- [ ] Given a workspace where the facts or preferences directory has no MEMORY.md file, when the system starts up, then the injection is skipped for that directory without error or warning
- [ ] Given a workspace where MEMORY.md exists but is empty or contains only a header with no file entries, when the system starts up, then the injection is skipped for that directory without error
- [ ] Given a workspace with no memories directory at all, when the system starts up, then no memory index sections are injected and startup proceeds normally

### Agentic Search Removal (R3, R6)

- [ ] Given the codebase after implementation, then the MemoryContextProvider class, MEMORY_SEARCH_PROMPT, ParsedMemoryEntry, parse_memory_entries(), extract_memory_paths(), and related constants no longer exist in src/tachikoma/memory/context_provider.py
- [ ] Given the per-message pre-processing pipeline, when the system starts up, then no memory context provider is registered — only the skills context provider remains
- [ ] Given any references to deduplication via memory_path metadata, when the codebase is audited, then no stale references to the removed deduplication mechanism remain in active code
- [ ] Given the memory module's public API (__init__.py), then MemoryContextProvider is no longer exported

### System Preamble Expansion (R4, R7)

- [ ] Given the system preamble's Memories section, when it is rendered, then it includes general documentation about episodic memory naming conventions (daily YYYY-MM-DD.md, weekly YYYY-WNN.md, monthly YYYY-MM.md)
- [ ] Given the system preamble's Memories section, when it is rendered, then it describes retention tiers at a general level (daily files are recent detail, weekly are consolidated summaries, monthly are long-term arcs)
- [ ] Given the system preamble's Memories section, when it is rendered, then it explains content expectations (high-level summaries, not transcripts)
- [ ] Given the system preamble's Memories section, when it is rendered, then it provides guidance on when consulting episodic context is useful versus when facts/preferences suffice
- [ ] Given the system preamble's Memories section, then it does not include specific retention duration numbers (those are configuration-dependent)

### Latency Improvement (R8)

- [ ] Given a message received by the coordinator, when the per-message pre-processing pipeline runs, then no Opus sub-agent is invoked for memory search, and the pipeline completes with only the skills provider overhead
