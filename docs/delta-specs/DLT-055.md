# Delta Spec: DLT-055 - Plugin Update Mechanism

## Story

As a Tachikoma user, I want installed plugins to be checked for updates automatically and updated on demand so that I receive bug fixes and improvements from plugin authors without manually reinstalling.

## What It Does

Adds an update detection and application mechanism to the plugin system. A daily system task checks git-source plugins for new versions at their remote ref; local-source plugins use symlinks so changes are always live; url-source plugins update only on explicit request. Users apply updates via MCP tools (single or bulk), and the system notifies when updates are available. Startup reconciliation no longer re-materializes existing plugins — it only handles first-time installs and orphan cleanup.

## Requirements

| ID | Requirement | Status |
|----|-------------|--------|
| R0 | Detect and apply plugin updates when newer versions are available from their sources, preserving existing plugin state on failure | Core goal |
| R1 | Git-source update detection: detect remote ref movement via fetch + commit hash comparison | Must-have |
| R2 | URL-source updates: only applied on explicit request, no automatic checking | Must-have |
| R3 | Local-source plugins use symlinks instead of copying; always reflect live source, no update state | Must-have |
| R4 | MCP tool to update a single plugin explicitly | Must-have |
| R5 | MCP tool to update all plugins at once | Must-have |
| R6 | Daily system task checks git-source plugins for available updates and reports findings | Must-have |
| R7 | Startup no longer re-materializes already-installed plugins; only handles first-time install and orphan cleanup | Must-have |
| R8 | Failed updates leave existing plugin intact via atomic swap | Must-have |
| R9 | Plugin status reflects update state: up-to-date, update-available, stale-fallback | Must-have |
| R10 | list_plugins shows whether updates are available for each plugin | Must-have |
| R11 | Version tracking: store resolved commit hash (git) or content hash (url) of installed version for comparison | Must-have |
| R12 | Updated plugins are unregistered then re-registered (remove + re-add lifecycle) | Must-have |
| R13 | Daily check task sends a notification when updates are available | Must-have |

## Acceptance Criteria

### Version Tracking (R11)

- [ ] Given a git-source plugin is installed, when installation completes, the resolved commit SHA is persisted alongside the plugin record
- [ ] Given a url-source plugin is installed, when installation completes, a content hash of the archive is persisted alongside the plugin record
- [ ] Given a local-source plugin is installed, when installation completes, no version hash is stored (local plugins have no version state)
- [ ] Given a plugin with a stored version hash, when list_plugins is invoked, the installed version is included in the output

### Git Update Detection (R1)

- [ ] Given a git-source plugin tracking a branch ref, when update detection runs, a fetch against the remote is performed and the remote HEAD commit SHA is compared to the stored local SHA
- [ ] Given the remote HEAD SHA differs from the stored local SHA, when the comparison completes, the plugin is marked as `update-available`
- [ ] Given the remote HEAD SHA matches the stored local SHA, when the comparison completes, the plugin is marked as `up-to-date`
- [ ] Given the remote is unreachable during update detection, when the fetch fails, the plugin retains its previous status (no state change) and the error is logged

### URL Update Application (R2)

- [ ] Given a url-source plugin, when the daily update check runs, the url-source plugin is skipped (no automatic checking)
- [ ] Given a url-source plugin and the user requests an update, when update_plugin is invoked, the archive is re-downloaded, the content hash is compared, and the plugin is updated if the hash differs
- [ ] Given a url-source plugin re-downloaded with the same content hash, when update_plugin completes, the plugin is reported as already up-to-date

### Local Source Symlinks (R3)

- [ ] Given a local-source plugin is installed, when materialization runs, a symlink is created at `.tachikoma/plugins/<alias>` pointing to the configured path
- [ ] Given a local-source plugin symlink exists, when the source directory contents change, the installed plugin reflects those changes immediately without any update step
- [ ] Given a local-source plugin, when list_plugins is invoked, no update-available status is shown (local plugins are always current)
- [ ] Given an existing local-source plugin that was previously copied, when reconciliation runs after this delta, the copy is replaced with a symlink

### MCP Tool: update_plugin (R4)

- [ ] Given a git-source plugin with `update-available` status, when `update_plugin` is invoked with its alias, the plugin is re-materialized from the remote, the version hash is updated, and status returns to `up-to-date`
- [ ] Given a url-source plugin, when `update_plugin` is invoked, the archive is re-downloaded and the plugin is updated if the content differs
- [ ] Given a local-source plugin, when `update_plugin` is invoked, the tool returns an informational message that local plugins are always current (symlink-based)
- [ ] Given a plugin already at the latest version, when `update_plugin` is invoked, the tool reports that no update is needed
- [ ] Given a non-existent alias, when `update_plugin` is invoked, the tool returns a "not found" error
- [ ] Given an update fails (network error, corrupt archive), when the update attempt completes, the existing plugin remains intact and the error is returned

### MCP Tool: update_all_plugins (R5)

- [ ] Given multiple plugins with `update-available` status, when `update_all_plugins` is invoked, all are updated sequentially and a summary is returned listing each plugin's result
- [ ] Given a mix of plugins (some updatable, some current, some local), when `update_all_plugins` is invoked, only plugins with available updates are processed; local and up-to-date plugins are reported as skipped
- [ ] Given one plugin update fails during a bulk update, when the operation continues, remaining plugins are still processed and the summary includes the failure

### Daily Update Check Task (R6)

- [ ] Given a session task definition exists for plugin update checking, when the task fires on its daily schedule, the check logic runs for all git-source plugins
- [ ] Given the daily check task definition does not exist in the database, when the plugins bootstrap hook runs, the task definition is created with a sensible default schedule
- [ ] Given the daily check task definition already exists, when the plugins bootstrap hook runs, the task is not re-created (idempotent)

### Startup Reconciliation Change (R7)

- [ ] Given a plugin configured in `[plugins]` with no existing install directory, when startup reconciliation runs, the plugin is materialized from source (first-time install)
- [ ] Given a plugin configured in `[plugins]` with an existing install directory, when startup reconciliation runs, the existing directory is left untouched (no re-materialization)
- [ ] Given a directory in `.tachikoma/plugins/` not matching any configured alias, when startup reconciliation runs, the orphan directory is removed
- [ ] Given a plugin installed via MCP tool at runtime, when the process restarts, the plugin is detected as already installed and not re-materialized

### Update Failure Safety (R8)

- [ ] Given a plugin update that fails mid-materialization, when the error is caught, the staging directory is cleaned up and the existing install directory remains unchanged
- [ ] Given a plugin update that succeeds at the filesystem level but fails during manifest parsing, when the error is caught, the atomic swap is not performed and the existing version remains active

### Update Status Tracking (R9, R10)

- [ ] Given a plugin with no stored version hash and no update check performed, when the plugin loads, its status is `unknown` (no update info available yet)
- [ ] Given an update check has run and no new version was found, when the plugin is listed, its status shows `up-to-date`
- [ ] Given an update check has run and a new version was found, when the plugin is listed, its status shows `update-available`
- [ ] Given a plugin in `stale-fallback` state from a previous failed materialization, when listed, it retains `stale-fallback` status
- [ ] Given `list_plugins` output, when a plugin has `update-available` status, the output includes the current installed version and (if known) the available version

### Plugin Re-registration on Update (R12)

- [ ] Given a plugin is updated via update_plugin, when the new version is materialized, the plugin's skills are unregistered from the SkillRegistry, the plugin is re-discovered (manifest re-parsed, hooks/events re-validated), and skills are re-registered under the same namespaced names
- [ ] Given a plugin with active event subscriptions is updated, when re-registration runs, old subscriptions are unsubscribed and new ones are registered based on the updated manifest
- [ ] Given a plugin whose updated manifest removes a previously contributed skill, when re-registration completes, the removed skill is no longer in the registry
- [ ] Given a plugin whose updated manifest adds a new skill, when re-registration completes, the new skill is available under its namespaced name

### Daily Check Notification (R13)

- [ ] Given the daily update check finds one or more plugins with available updates, when the check completes, a notification is delivered listing the plugins with available updates
- [ ] Given the daily update check finds no available updates, when the check completes, no notification is sent
- [ ] Given the daily check notification is delivered, when the user reads it, the message includes the plugin aliases and instructs that `update_plugin` or `update_all_plugins` can be used to apply updates
