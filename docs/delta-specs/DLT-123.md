# Delta Spec: DLT-123 - Learnings memory layer

<!-- This spec describes WHAT the delta does, not HOW it's implemented. -->
<!-- Technical delta (memory-model extension): no user-facing UI flow. -->

## Story

As the memory subsystem — the post-processing extraction and maintenance agents — I need a dedicated learnings layer that captures the *experience* of working in this workspace: the recurring friction, hard constraints, and repeated failures that bite across sessions, plus my own observations about what worked and what didn't. This lets future sessions start aware of what has already been learned the hard way, rather than rediscovering the same gotchas.

## What It Does

Adds a third memory store, `memories/learnings/`, alongside the existing `topics/` (stable what/why knowledge) and `episodic/` (the narrative of what happened). A learning is experience, not knowledge: an uncooperative test suite, a deployment step that keeps biting, a hard rule the user enforces, an approach that turned out to be a dead end. New lessons, frictions, and reflections observed in a session are captured as **drafts** — clearly marked tentative. When the *same* friction recurs across sessions, the learning **graduates to a permanent** entry. The recurring quality that defines a real learning is therefore enforced by the lifecycle, not at capture time: nothing valuable is lost on first sighting, but only repetition earns permanence.

Learnings are folded in by the existing trunk-close extractor, reusing the topic store's layout, `MEMORY.md` indexing, and file-tool-only extraction conventions — but they are extracted by the **same agent that extracts topics**, which classifies each signal inline as topic content (stable knowledge) or learning content (experience/friction) and writes to the right store. One agent, one decision per signal, so the two stores can never duplicate each other. Episodic continues as its own separate pass. The learnings index is injected into every session's context like the topics index, so the agent notices relevant friction proactively. Basic maintenance (dedup, promoting repeated drafts, pruning stale/contradicted lessons, index consistency) runs in the trunk-close pipeline; the richer phased consolidation is deferred to DLT-173.

| R4 | Learnings are folded by the **same extraction agent as topics**: a single extraction pass classifies each extracted signal as topic content (stable what/why knowledge) or learning content (experience/friction) and writes to the appropriate store, so topic and learning content is never duplicated across the two stores. Episodic remains its own separate extraction pass | Must-have |
| R5 | Newly-observed lessons, frictions, and reflections are captured as **drafts** — clearly marked tentative. A learning **graduates to a permanent** entry through repetition. Recurrence is detected by the extraction agent *reading existing learnings files during extraction* and recognizing that the new session describes the same friction/constraint/lesson (same subject, same kind of problem) as an existing draft; the agent makes that match decision inline, and a match promotes the draft. The "recurring" quality that distinguishes a real learning is enforced by this lifecycle, not at capture time. The exact matching judgement is refined in design, but promotion always follows an explicit read-and-match against existing drafts | Must-have |
| R6 | The shared extraction instruction defines the topic-vs-learning boundary inline: stable what/why knowledge and the user's preferences go to `topics/`; recurring friction, hard constraints, repeated failures, and self-reflections go to `learnings/` (as drafts). One-time events are explicitly excluded (those belong in episodic), and a learning must not simply restate a topic or a context file. When a signal has BOTH stable-knowledge and friction character, the agent classifies it by its PRIMARY aspect in context and writes it to exactly one store (the two never duplicate); a fact-that-causes-friction is recorded in `learnings/` as the lesson, not also restated as a topic | Must-have |
| R7 | Learnings extraction obeys the same constraints as the other stores: the fork is hard-limited to file tools (no messaging/notification/task tools), runs as a silent-background follow-up turn, writes only within `memories/learnings/` (and `memories/topics/` for the shared pass), expresses deletion by emptying files, and is swept for empty markdown after each run | Must-have |
| R8 | Basic learnings maintenance runs in the trunk-close prune pass as a per-store maintenance step: dedup, promote repeated drafts to permanent, prune stale or contradicted lessons, keep files concise, consolidate per-incident fragmentation into broad slug files, and keep the `MEMORY.md` index consistent (light consistency on weekdays, full rebuild on Sundays, same day-of-week dispatch as topics) | Must-have |
| R9 | Richer phased consolidation of learnings — orientation, signal-gathering, and merging passes — is deferred to DLT-173, which owns the layer-aware consolidation pipeline over both the topic store and the learnings layer. DLT-123 ships only the basic maintenance in R8 (mirroring how the codebase already defers rich consolidation behind its phased seam) | Must-have |
| R10 | `enabled = false` registers nothing for learnings: no layout directory, no index seeding, no context injection, no extraction, no maintenance (consistent with the existing memory extension's disable gate) | Must-have |
| R11 | Learnings sit orthogonal to the `Skills > Topics > Context` authority hierarchy: a learning is authoritative about what *bites* and what worked, is never absorbed into a topic file, and does not defer to topics. The two stores hold different *kinds* of information, so neither overrides the other, and both remain available about the same subject | Must-have |
| R12 | Learnings reuse the topic store's file conventions: one theme of recurring friction per `<slug>.md`, broad future-mergeable slugs (never incident/date-scoped names), and files kept concise — so the store does not fragment into per-incident files | Must-have |

## Acceptance Criteria

### Layout and Index Seeding (R1, R2)

- [ ] Given an empty workspace, when bootstrap runs, then `memories/` contains `learnings` alongside `episodic`, `topics`, and `transcripts`, and `learnings/MEMORY.md` contains only the `# Memory Index` header
- [ ] Given pre-existing learning files without an index (including files a user created manually before this delta), when bootstrap runs, then each gets a placeholder entry with a Title Case name derived from its filename
- [ ] Given an existing `learnings/MEMORY.md`, when bootstrap runs again, then its content is preserved (idempotent)

### Context Injection (R3)

- [ ] Given a learnings index with entries, when a message is handled, then the injected memory block contains a `## Learnings Index` section (layout note that these are experience notes, read on demand) with one bullet per entry, alongside the existing `## Topics Index`
- [ ] Given a header-only learnings index (or an empty learnings store with no `<slug>.md` files), when the provider runs, then it contributes no learnings index section while the layout section is still injected
- [ ] Given no `memories/` directory (or no learnings index), when the section is built, then the learnings portion yields empty content and contributes nothing
- [ ] Given malformed learnings index lines, when the index is formatted, then well-formed entries are kept and malformed ones dropped silently

### Shared Extraction and Topic-vs-Learning Classification (R4, R6, R7)

- [ ] Given a closed branch containing both a stable fact about a subject and a recurring friction, when extraction runs, then the fact is written to `memories/topics/` and the friction is written to `memories/learnings/` by the same extraction pass — not two separate passes
- [ ] Given a signal that has both reference-knowledge and friction character, when the shared extraction agent classifies it, then it lands in exactly one store, classified by its primary aspect in context (the two never duplicate)
- [ ] Given a one-time event in the branch (a single bug fix, an outage), when extraction runs, then it is NOT recorded as a learning (it belongs in episodic); only friction/lessons/reflections with experience character are written to `learnings/`
- [ ] Given a session/branch with no recurring friction, hard constraints, or reflections worth capturing, when extraction runs, then no learnings files are created and no error is thrown
- [ ] Given the shared extraction pass runs, when the agent acts, then it sends no user-facing message, uses only file tools, and writes only within `memories/topics/` and `memories/learnings/`
- [ ] Given a branch already carrying an `extracted` marker, when the phase re-runs (e.g. after a crash), then extraction is skipped (idempotent per branch) — learnings are folded as part of the same marker

### Draft → Permanent Lifecycle (R5)

- [ ] Given a friction or lesson observed for the first time in a session, when extraction folds it, then it is recorded in `learnings/` as a **draft**, clearly marked tentative (not as a confirmed/permanent learning)
- [ ] Given a draft already exists for a friction, when the same friction recurs in a later session and the extraction agent reads existing learnings files and recognizes the match, then that learning is promoted to a **permanent** entry
- [ ] Given a draft that never recurs, when maintenance runs, then it remains a draft (it is not deleted merely for being single-occurrence — only stale/contradicted learnings are pruned)
- [ ] Given a draft that a later session contradicts (e.g. the friction was resolved — the flaky test was fixed), when extraction/maintenance runs, then the contradiction is resolved (the draft is corrected or removed) rather than the contradicted draft being promoted
- [ ] Given the learnings store, when a user or reader opens a file, then drafts and permanent entries are distinguishable at a glance (the tentative state is visible, not implicit)

### Basic Maintenance (R8, R12)

- [ ] Given the trunk-close prune phase runs, then a learnings maintenance pass evaluates duplication, promotes repeated drafts to permanent, prunes stale or contradicted lessons, and keeps files concise
- [ ] Given per-incident learnings files that fragment one friction theme (the anti-pattern R12 forbids), when maintenance runs, then they are consolidated into a single broad slug file
- [ ] Given a learnings file whose `## Drafts`/`## Confirmed` structure is malformed, when maintenance runs, then it repairs the structure in place or, if unrecoverable, logs a warning and leaves the file for the next pass rather than crashing
- [ ] Given the learnings `MEMORY.md` lists a file that no longer exists, or a file exists with no index entry, when the light index-consistency step runs (Mon–Sat), then the index is synchronized to match the actual files; on Sunday the index is rebuilt from scratch with fresh descriptions
- [ ] Given a phase completes, then its workspace edits are committed to git via the shared commit mechanism, consistent with the other memory phases

### Scope Boundaries and Configuration (R9, R10)

- [ ] Given DLT-123 is implemented, then no orientation/signal-gathering/merging consolidation pass runs for learnings — maintenance performs ONLY dedup, draft promotion, pruning, fragmentation consolidation, and index consistency (the richer phased consolidation is the scope of DLT-173)
- [ ] Given `enabled = false`, when the extension loads, then no learnings directory is ensured, no index is seeded, no learnings index is injected, and no learnings extraction or maintenance is registered

### Authority (R11)

- [ ] Given a learning and a topic that touch the same subject, when maintenance runs, then the learning is not folded into the topic nor pruned in deference to it — the two coexist as different kinds of information, and the agent is told learnings are orthogonal to the `Skills > Topics > Context` chain
- [ ] Given both a learning and a topic exist about the same subject, when context is injected, then BOTH are surfaced (the learning in the `## Learnings Index`, the topic in the `## Topics Index`), each as a distinct kind of information

## Requires

Dependencies:
- None. This delta is greenfield (the "earlier agent-reflections idea" was never implemented — no migration is needed). It extends the existing `memory` extension in place.

## Detected Impacts

### Affected Features
- **[docs/feature-specs/memory.md]** - **Modifies**: Adds a third store (`learnings/`) to the memory model; extends the layout/index-seeding, context injection, extraction, and maintenance behaviors; changes the topics extraction to a shared topics+learnings classification pass; introduces the draft→permanent lifecycle; and adds NEW requirements specific to learnings — authority placement (orthogonal to the existing `Skills > Topics > Context` hierarchy, R11) and file conventions (one theme per file, broad slugs, concise, R12) — which have no direct analog in the current memory.md.

### Notes for Reconciliation
- **memory.md** gains requirements covering: layout (`learnings/`), index seeding (incl. handling pre-existing files), the `## Learnings Index` context section, the shared topics+learnings extraction/classification (with the one-store-wins rule for dual-character signals), the draft→permanent lifecycle (recurrence via read-and-match), basic learnings maintenance (and the explicit deferral of rich consolidation to DLT-173), the disable gate, the orthogonal authority placement, and the file conventions.
- The existing topics-extraction requirement (R11/R12 in memory.md) is modified: it now describes a shared pass that also classifies and writes learnings, not a topics-only fold.
- No new feature-spec doc is needed — learnings is part of the memory feature, not a separate feature.
- Downstream: **DLT-080** (skill self-healing) draws on the learnings store; **DLT-173** owns the richer phased consolidation over topics+learnings and should reference this delta's basic maintenance as its starting point.
