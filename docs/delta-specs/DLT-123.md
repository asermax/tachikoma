# Delta Spec: DLT-123 - Learnings memory layer

<!-- This spec describes WHAT the delta does, not HOW it's implemented. -->
<!-- Technical delta (memory-model extension): no user-facing UI flow. -->

## Story

As the system, I need a dedicated memory layer that captures the *experience* of working in this workspace — the recurring friction, hard constraints, and repeated failures that bite across sessions, plus my own observations about what worked and what didn't — so that future sessions start aware of what has already been learned the hard way, rather than rediscovering the same gotchas.

## What It Does

Adds a third memory store, `memories/learnings/`, alongside the existing `topics/` (stable what/why knowledge) and `episodic/` (the narrative of what happened). A learning is experience, not knowledge: an uncooperative test suite, a deployment step that keeps biting, a hard rule the user enforces, an approach that turned out to be a dead end. New lessons, frictions, and reflections observed in a session are captured as **drafts** — clearly marked tentative. When the *same* friction recurs across sessions, the learning **graduates to a permanent** entry. The recurring quality that defines a real learning is therefore enforced by the lifecycle, not at capture time: nothing valuable is lost on first sighting, but only repetition earns permanence.

Learnings are folded in by the existing trunk-close extractor, reusing the topic store's layout, `MEMORY.md` indexing, and file-tool-only extraction conventions — but they are extracted by the **same agent that extracts topics**, which classifies each signal inline as topic content (stable knowledge) or learning content (experience/friction) and writes to the right store. One agent, one decision per signal, so the two stores can never duplicate each other. Episodic continues as its own separate pass. The learnings index is injected into every session's context like the topics index, so the agent notices relevant friction proactively. Basic maintenance (dedup, promoting repeated drafts, pruning stale/contradicted lessons, index consistency) runs in the trunk-close pipeline; the richer phased consolidation is deferred to DLT-173.

## Acceptance Criteria

### Layout and Index Seeding (R1, R2)

- [ ] Given an empty workspace, when bootstrap runs, then `memories/` contains `learnings` alongside `episodic`, `topics`, and `transcripts`, and `learnings/MEMORY.md` contains only the `# Memory Index` header
- [ ] Given pre-existing learning files without an index, when bootstrap runs, then each gets a placeholder entry with a Title Case name derived from its filename
- [ ] Given an existing `learnings/MEMORY.md`, when bootstrap runs again, then its content is preserved (idempotent)

### Context Injection (R3)

- [ ] Given a learnings index with entries, when a message is handled, then the injected memory block contains a `## Learnings Index` section (layout note that these are experience notes, read on demand) with one bullet per entry, alongside the existing `## Topics Index`
- [ ] Given a header-only learnings index, when the provider runs, then it contributes no learnings index section while the layout section is still injected
- [ ] Given no `memories/` directory (or no learnings index), when the section is built, then the learnings portion yields empty content and contributes nothing
- [ ] Given malformed learnings index lines, when the index is formatted, then well-formed entries are kept and malformed ones dropped silently

### Shared Extraction and Topic-vs-Learning Classification (R4, R6, R7)

- [ ] Given a closed branch containing both a stable fact about a subject and a recurring friction, when extraction runs, then the fact is written to `memories/topics/` and the friction is written to `memories/learnings/` by the same extraction pass — not two separate passes
- [ ] Given a signal that qualifies as both reference knowledge and a lesson, when the shared extraction agent classifies it, then it lands in exactly one store (no duplication), with the agent deciding inline which kind it is
- [ ] Given a one-time event in the branch (a single bug fix, an outage), when extraction runs, then it is NOT recorded as a learning (it belongs in episodic); only friction/lessons/reflections with experience character are written to `learnings/`
- [ ] Given the shared extraction pass runs, when the agent acts, then it sends no user-facing message, uses only file tools, and writes only within `memories/topics/` and `memories/learnings/`
- [ ] Given a branch already carrying an `extracted` marker, when the phase re-runs (e.g. after a crash), then extraction is skipped (idempotent per branch) — learnings are folded as part of the same marker

### Draft → Permanent Lifecycle (R5)

- [ ] Given a friction or lesson observed for the first time in a session, when extraction folds it, then it is recorded in `learnings/` as a **draft**, clearly marked tentative (not as a confirmed/permanent learning)
- [ ] Given a draft already exists for a friction, when the same friction recurs in a later session, then that learning is promoted to a **permanent** entry
- [ ] Given a draft that never recurs, when maintenance runs, then it remains a draft (it is not deleted merely for being single-occurrence — only stale/contradicted learnings are pruned)
- [ ] Given the learnings store, when a user or reader opens a file, then drafts and permanent entries are distinguishable at a glance (the tentative state is visible, not implicit)

### Basic Maintenance (R8)

- [ ] Given the trunk-close prune phase runs, then a learnings maintenance pass evaluates duplication, promotes repeated drafts to permanent, prunes stale or contradicted lessons, and keeps files concise
- [ ] Given the learnings maintenance step runs Monday–Saturday, then its prompt includes the light index-consistency section; on Sunday it includes the full index rebuild instead
- [ ] Given a phase completes, then its workspace edits are committed to git via the shared commit mechanism, consistent with the other memory phases

### Scope Boundaries and Configuration (R9, R10)

- [ ] Given DLT-123 is implemented, then no orientation/signal-gathering/merging consolidation pass runs for learnings (that is the scope of DLT-173)
- [ ] Given `enabled = false`, when the extension loads, then no learnings directory is ensured, no index is seeded, no learnings index is injected, and no learnings extraction or maintenance is registered

### Authority (R11)

- [ ] Given a learning and a topic that touch the same subject, when maintenance runs, then the learning is not folded into the topic nor pruned in deference to it — the two coexist as different kinds of information, and the agent is told learnings are orthogonal to the `Skills > Topics > Context` chain

## Requires

Dependencies:
- None. This delta is greenfield (the "earlier agent-reflections idea" was never implemented — no migration is needed). It extends the existing `memory` extension in place.
