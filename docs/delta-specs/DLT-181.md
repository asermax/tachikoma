# Delta Spec: DLT-181 - Temporary Side Conversations

<!-- This spec describes WHAT the delta does, not HOW it's implemented. -->
<!-- Realized via the checkpoint mechanism (see "What It Does"). -->

## Story

As a user, I want to take a quick tangent or side question inside an active conversation and then return to exactly where the main thread was, so that a tangent doesn't derail the main work or force me to start a brand-new topic — like opening a scratch buffer while editing a file, then closing it and continuing.

## What It Does

Introduces **checkpoints** on the daily trunk: a passive marker at the current main-line tip that lets the conversation take an inline tangent (a quick question or a side topic) and later **summarize that tangent back into a collapsed branch rooted at the checkpoint**, returning the live leaf to the main line. The main line is **parked intact** — only the tangent is summarized away — which is the defining difference from a topic shift (which collapses the current branch and moves on).

Checkpoints and the summarize-to-checkpoint return are each available **manually** (commands) and **automatically** (the boundary classifier gains two new results). A `/rollback` command flips the most recent *automatic* checkpoint/topic decision when the system picked wrong.

The delta also completes the command surface so the new controls are discoverable and usable: every slash command is registered in Telegram's command menu with usage hints, argument-taking commands (`/new`, `/queue`, `/skill`) prompt for their argument via a pending-input flow when tapped bare, and every branching decision is surfaced as a **persistent header on the next response** so the user always knows what the system decided and can roll it back.

Mechanically, a summarize-to-checkpoint reuses the existing topic-collapse primitive (`branchWithSummary`) with the checkpoint entry as the branch point instead of the current base — folding the tangent into a summary rooted at the checkpoint, **marked as a tangent** (distinct from a topic branch), so the main line resumes. A summarized tangent is deliberately parked away: its full conversation is **not** queryable through the branch tools (`ask_branch`, DLT-182's `open_branch`), which serve prior topics — only the summary persists in the main line.

## Requirements

| ID | Requirement | Status |
|----|-------------|--------|
| R0 | A user can take a temporary tangent inside the active conversation and return to the main line with its context intact: set a checkpoint, converse inline, summarize the tangent back to the checkpoint. The main line is parked, never collapsed | Core goal |
| R1 | A checkpoint can be set at the current main-line tip, **manually** (`/checkpoint`) or **automatically** (boundary result `set-checkpoint`). Setting a checkpoint is free — one that is never summarized causes no harm | Must-have |
| R2 | Only **one checkpoint is active at a time**; setting a new checkpoint overrides the previous one | Must-have |
| R3 | The tangent taken after a checkpoint can be **summarized back to the checkpoint**, **manually** (`/back`) or **automatically** (boundary result `summarize-to-checkpoint`): the turns since the checkpoint become a collapsed branch rooted at the checkpoint, the live leaf returns there, and the main line resumes. A summarized tangent is parked away — it is **not** a target for the branch-query tools (`ask_branch`, DLT-182's `open_branch`); only its summary persists in the main line | Must-have |
| R4 | Both the **one-turn tangent** (checkpoint + a single exchange + summarize) and the **multi-turn side conversation** (checkpoint + several exchanges + summarize) are expressed through the same checkpoint mechanism | Must-have |
| R5 | **Defining property**: a checkpoint-based side conversation never collapses the main line. Only the tangent is summarized away; the main line resumes exactly at the checkpoint. This is what distinguishes it from a topic shift | Core goal |
| R6 | The boundary classifier gains two results: `set-checkpoint` (a tangent is beginning — related enough to the main thread to continue inline, but worth parking rather than treating as a new topic) and `summarize-to-checkpoint` (the tangent has ended, the conversation is back on the main line). Existing `continue`/`new` behavior is unchanged | Must-have |
| R7 | A single `/rollback` command reverses the most recent **automatic** branching decision in exactly two cases — by re-seating the active leaf to the tip that preceded the decision, applying the opposite transition, and **replaying the triggering message** as a fresh turn: (a) the decision was `set-checkpoint` → collapse the branch up to that tip as a topic and replay the message as the new topic's first turn; (b) the decision was `new` → set a checkpoint at that tip and replay the message as the tangent's first turn. It is a **no-op** in every other case (no recent auto decision; a manual decision; `continue`; `summarize-to-checkpoint`; or any exchange since the decision). The wrong-framing exchange goes off-path (append-only, not deleted); a summary orphaned by the reversal is marked so memory extraction and branch-query tools skip it | Must-have |
| R8 | Branching decisions (topic shift, set-checkpoint, summarize-to-checkpoint, rollback — automatic **or** manual) are surfaced to the user as a **persistent header on the next response message** that names the decision and gives a one-line note — a status the streaming renderer does not override — so the user sees what happened. Only automatic decisions are rollback targets; manual decisions are surfaced for awareness | Must-have |
| R9 | Argument-taking commands (`/new`, `/queue`, `/skill`) invoked **bare** enter a **pending-input** state: a hardcoded (non-LLM) prompt asks for the argument, and the user's next message is captured as that argument rather than handled normally. The flow is channel-agnostic (Telegram **and** REPL); pending state is transient (not persisted across restart), cleared by any other command, and expires after a short TTL if no argument arrives | Must-have |
| R10 | All slash commands are registered in Telegram's command menu (today only `new`/`queue`) — adding `stop`, `skill`, `tasks`, `reload`, `checkpoint`, `/back` (summarize-to-checkpoint), and `rollback` — each with a usage hint in its description | Must-have |
| R11 | Defined, graceful behavior for edge cases: summarize with no active checkpoint; rollback with no recent auto decision; checkpoint with no turns after it; pending-input abandoned or interrupted; classifier failure (fail open) | Must-have |

## Acceptance Criteria

### Checkpoints (R1, R2, R5)

- [ ] Given an active conversation at a main-line tip, when the user sends `/checkpoint`, then the current leaf entry is recorded as the active checkpoint (overriding any prior), and a confirmation is surfaced
- [ ] Given an active checkpoint already exists, when the user sets a new checkpoint, then the new one replaces it — exactly one checkpoint is active at any time
- [ ] Given an active checkpoint that is never summarized, when the conversation continues normally, then nothing breaks — the checkpoint is simply an unused marker (setting a checkpoint is free)
- [ ] Given an active checkpoint, when the trunk is reloaded or the process restarts and resumes, then the checkpoint is restored on resume (it lives on the session file per ADR-014, not in transient memory)
- [ ] Given an active checkpoint, when a topic shift occurs (manual `/new` or auto `new`), then the checkpoint is cleared — the tangent turns are absorbed into the topic collapse and the checkpoint no longer marks a returnable main-line point — and a notice is surfaced
- [ ] Given a checkpoint-based side conversation, when the tangent is summarized back, then the **main line** (everything up to the checkpoint) resumes intact and is never collapsed — only the tangent is folded away

### Summarize-to-checkpoint (R3, R4)

- [ ] Given an active checkpoint with one or more tangent turns after it, when the user triggers summarize-to-checkpoint, then the turns since the checkpoint are summarized into a collapsed branch rooted at the checkpoint, the live leaf is re-seated to that summary, and the main line resumes
- [ ] Given a one-turn tangent (a single exchange after the checkpoint), when it is summarized, then the behavior is identical to the multi-turn case — the single exchange is summarized away and the main line resumes (the modes share one mechanism)
- [ ] Given a tangent that has been summarized, when `ask_branch` or `open_branch` is directed at it, then it is excluded — summarized tangents are parked away, not queryable; only the summary persists in the main line
- [ ] Given a summarized tangent produces a `branch_summary` entry, when branch records are enumerated, then it is marked as a tangent and kept distinct from topic branches (so branch-query tools exclude it and `topic-N` ids stay clean)
- [ ] Given no active checkpoint, when summarize-to-checkpoint is invoked, then it is a no-op and a notice is surfaced ("No checkpoint to summarize to")

### Boundary Classifier Extension (R6)

- [ ] Given the classifier detects the start of a tangent (related enough to continue inline but not part of the main thread), when it classifies the message, then it returns `set-checkpoint` and a checkpoint is set at the current tip before the tangent proceeds
- [ ] Given an active checkpoint and the classifier detects the tangent has ended (the conversation returning to the main line), when it classifies the message, then it returns `summarize-to-checkpoint` and the tangent is summarized back to the checkpoint
- [ ] Given the classifier errors or returns unparseable output, when detection runs, then it fails open (the message continues normally) and no checkpoint is created or summarized spuriously
- [ ] Given `[extensions.boundary] enabled = false`, when a message arrives, then the two new results are not emitted (topic detection off) — manual `/checkpoint` and `/back` still work
- [ ] Given the classifier runs, when it decides, then it accounts for whether a checkpoint is currently active — `summarize-to-checkpoint` is only a valid choice when one exists (and conversely `set-checkpoint` is not emitted when one is already active)

### Rollback (R7)

- [ ] Given the most recent automatic decision was `set-checkpoint` and no exchange has occurred since, when the user sends `/rollback`, then the active leaf is re-seated to the tip that preceded the decision, the branch up to that tip is collapsed into a topic summary, and the triggering message is replayed as the first turn of the new topic (re-answered under the topic framing)
- [ ] Given the most recent automatic decision was `new` and no exchange has occurred since, when the user sends `/rollback`, then the active leaf is re-seated to the pre-decision tip, a checkpoint is set there, and the triggering message is replayed as the first tangent turn (re-answered under the checkpoint framing); the topic summary the auto-`new` created is marked `reversed` so it is neither extracted into memory nor queryable via the branch tools
- [ ] Given the wrong-framing exchange for the triggering message is now off-path after `/rollback`, when the session file is later processed, then that exchange is not re-extracted into memory (it is an off-path dead branch, not a deletion)
- [ ] Given the most recent decision was manual, was `continue`, was `summarize-to-checkpoint`, or there is no recent auto decision — or one or more exchanges have occurred since the most-recent auto decision — when the user sends `/rollback`, then it is a no-op and a notice is surfaced ("Nothing to roll back")
- [ ] Given several automatic decisions have occurred, when the user sends `/rollback`, then only the single most-recent qualifying one (`set-checkpoint` or `new`, with no exchange since) is the target

### Durable Decision Surfacing (R8)

- [ ] Given a branching decision occurs (topic, set-checkpoint, summarize-to-checkpoint, rollback — automatic or manual), when the next response is rendered, then a persistent header is attached that names the decision with a short label and a one-line note (e.g. "📌 Checkpoint set", "↩️ Summarized to checkpoint", "🆕 New topic", "🔄 Rolled back to checkpoint"), and the streamed text does **not** overwrite it
- [ ] Given the user sees a decision header they disagree with, when it was an automatic decision, then `/rollback` is available to flip it; for a manual decision the header is informational and `/rollback` no-ops
- [ ] Given the channel cannot render the persistent header, when the decision is processed, then the decision still takes effect and the rendering failure is logged (best-effort surfacing)

### Pending-Input Flow (R9)

- [ ] Given the user invokes `/new`, `/queue`, or `/skill` with no argument, when the bare command is received, then a hardcoded (non-LLM) prompt asks for the argument (e.g. "What's the first message for the new topic?", "What should I queue for the next turn?", "Which skill?") and a pending-input state is set for that command
- [ ] Given a pending-input state is active, when the user's next message arrives, then it is captured as the command's argument and the command executes with it — it is not handled as a normal conversation message or steered into a live run; the pending state then clears
- [ ] Given a pending-input state is active, when the user sends any other command, then the pending state is cleared and the new command is honored
- [ ] Given a pending-input state is active with no argument arriving within the TTL, when the TTL elapses (or the process restarts), then the pending state is cleared without capturing a later, unrelated message
- [ ] Given the pending-input flow over the REPL channel, when a bare arg-taking command is sent, then it behaves the same as over Telegram (the mechanism is channel-agnostic)
- [ ] Given `/new` completes via pending-input, when the argument message is captured, then the current branch is collapsed (if it has an assistant turn since its base) and the new topic begins with that message

### Command Surface Completeness (R10)

- [ ] Given the Telegram command menu, when the user opens "/", then every command is listed: `new`, `queue`, `stop`, `skill`, `tasks`, `reload`, `checkpoint`, `back`, and `rollback`
- [ ] Given a command that takes an argument, when its menu entry is shown, then the argument form is indicated in the description (e.g. "Start a new topic — `/new <first message>`")
- [ ] Given the existing `stop`, `skill`, `tasks`, and `reload` commands, when they are registered, then they appear in the menu (they are currently missing)

### Edge Cases (R11)

- [ ] Given summarize-to-checkpoint with no active checkpoint, when invoked, then no-op + notice
- [ ] Given `/rollback` with no recent auto decision, when invoked, then no-op + notice
- [ ] Given a checkpoint with no turns after it, when summarize-to-checkpoint is invoked, then it is a no-op with a notice ("No tangent to summarize") and no branch is created
- [ ] Given the user sends `/checkpoint` while the classifier concurrently emits `set-checkpoint`, when both apply, then the result is a single active checkpoint (setting is idempotent — the manual command and the auto result coincide)
- [ ] Given the classifier fails, when detection runs, then it fails open and the loop is never blocked

## Requires

Dependencies:
- None (DLT-181 builds on the daily-trunk model of ADR-014, which is already in the codebase). Sibling delta DLT-182 (multi-turn `ask_branch`) is related but independent.

### Notes for Reconciliation

- The daily-trunk model (ADR-014) needs a current feature spec — `conversation-loop.md` and `boundary-detection.md` both predate it. This delta's checkpoint/summarize/rollback behaviors extend the trunk model and should fold into that spec when it is written/reconciled.
- The persistent-status-header mechanism (R8) is a general channel-rendering capability that other features could use; it overlaps conceptually with the unimplemented DLT-064 (collapse intensive work) and DLT-150 (phase markers) and may warrant a cross-cutting DES pattern.
- The pending-input flow (R9) is channel-agnostic in principle (a bare command prompts, the next message is the argument); the trigger (menu tap) is Telegram-specific, but the mechanism should live in the commands/coordinator layer so REPL benefits too.
- `/new`'s bare semantics change: today bare `/new` immediately forces a topic shift; after this delta, bare `/new` prompts for the new topic's first message. This is an intentional behavior change to be reflected in the commands/boundary docs.
- **Memory extraction interaction (resolved in design)**: summarized tangents are `branch_summary` entries that the trunk-close pipeline would otherwise extract; they are **excluded** (a tangent's content already lives in the summary injected into the main line). A summary orphaned by a `/rollback` reversal (e.g. the topic summary an auto-`new` created before being flipped to a checkpoint) is marked `reversed` so the extractor — and the branch-query tools — skip it. Both reuse one kind/marker discriminator on the branch record.
