# Delta Spec: DLT-163 - Block message enqueue during exchange teardown

## Story

As a developer, I need the coordinator to guarantee that no user message is accepted by a session that cannot process it, so that messages arriving during exchange teardown are never silently lost or routed to a dead session.

## What It Does

When a `send_message()` generator completes (the event stream ends), messages that were enqueued during that exchange are left in `_message_buffer` with no consumer. The Telegram channel has a drain loop (`while has_pending_messages` → call `send_message()` again) intended to handle these leftover messages, but it doesn't work. This delta removes the broken drain loop and moves the responsibility into the coordinator: after the generator finishes one exchange, it checks the buffer for leftover messages and starts a new exchange in the same session internally. The channel sees one continuous event stream — no drain loop needed.

## Requirements

| ID | Requirement | Status |
|----|-------------|--------|
| R0 | No user message is accepted by a session that cannot process it | Core goal |
| R1 | After exchange teardown, leftover messages are automatically re-processed in the same session with their original message ID | Must-have |
| R2 | Remove the broken Telegram drain loop | Must-have |
| R3 | The re-queue mechanism is owned by the coordinator, not channels | Must-have |
| R4 | No behavioral change when messages arrive during active processing (outside teardown window) | Must-have |
| R5 | The re-queue does not add latency to the happy path | Nice-to-have |

## Acceptance Criteria

### Exchange teardown guard (R0, R1)

- [ ] Given a `send_message()` exchange completes and the generator has not yet returned, when leftover messages exist in `_message_buffer`, then the generator starts a new exchange in the same coordinator session (same `sdk_session_id`) and yields those events before returning
- [ ] Given multiple leftover messages exist after an exchange completes, when the generator re-processes them, then all messages are re-processed in FIFO order with their original message IDs preserved
- [ ] Given a leftover message is re-processed, when the response is streamed, then the channel can correlate it to the original message (message ID preserved)

### Coordinator ownership (R3)

- [ ] Given the coordinator completes an exchange and leftover messages exist in the buffer, when the generator checks for them, then re-processing starts automatically without any channel action
- [ ] Given the coordinator has leftover messages, when re-processing starts, then channels receive the same `AsyncIterator[AgentEvent]` interface as a normal turn — no new channel-side logic needed
- [ ] Given re-queue is processing leftover messages, when additional messages arrive during a re-queue exchange, then they are consumed by that exchange's forwarder (steering message) or picked up in the next re-queue cycle
- [ ] Given re-queue processing fails (exception or session closed), when the failure occurs, then messages are preserved in the buffer and an error is logged for recovery on next manual interaction

### Telegram drain loop removal (R2)

- [ ] Given the Telegram channel's `_process_through_coordinator` method, when processing messages, then there is no `while has_pending_messages` drain loop
- [ ] Given the drain loop is removed, when messages arrive during active processing, then they are handled by the coordinator's re-queue mechanism instead

### Happy path preservation (R4)

- [ ] Given an exchange is actively processing (not in teardown), when a message arrives via `enqueue()`, then the forwarder routes it to the SDK inbox as before (steering message behavior unchanged)
- [ ] Given no messages arrive during teardown, when the exchange completes, then no re-processing occurs and behavior is identical to the current flow
- [ ] Given the REPL channel's message processing flow, when coordinator exchange completes, then REPL behavior is unchanged
