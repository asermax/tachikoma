# DLT-085: Tracked Schema Migration System

## Technical Story

As a developer, I need a tracked migration system for database schema changes so that migrations execute exactly once, startup is efficient, and adding future schema changes follows a consistent pattern without accumulating pragma checks.

## What It Does

Replaces the monolithic pragma-based migration system with a tracked migration registry. A `schema_migrations` table records which migrations have been applied. On startup, the system queries applied migrations and only executes new ones in deterministic order. All current pragma-based checks are consolidated into a single initial migration that is stamped as applied (never auto-executed) for both fresh and existing installations. Future migrations contain SQL statements that execute against the database.

## Requirements

| ID | Requirement | Status |
|----|-------------|--------|
| R0 | Track applied migrations in a `schema_migrations` table; only execute new ones on startup | Core goal |
| R1 | Single initial migration consolidates all current pragma-based schema changes | Must-have |
| R2 | For existing up-to-date installations, stamp the initial migration as applied without re-executing | Must-have |
| R3 | For fresh installations, `create_all()` handles base schema, initial migration is stamped as applied | Must-have |
| R4 | Migrations run in deterministic order via revision chain (Alembic-style: sequential `"001"`, `"002"`, etc.) | Must-have |
| R5 | Future migrations follow the same pattern: revision ID, name, ordered SQL statements | Must-have |
| R6 | Migration application is logged with revision and name | Must-have |
| R7 | A failing migration halts startup with a clear error; no partial application (one transaction per migration, stamp on success) | Must-have |
| R8 | No Alembic dependency — raw SQL only | Must-have |

## Acceptance Criteria

### Fresh Installation (R3)
- [ ] Given a database file that does not exist, when `initialize()` runs, then `create_all()` creates all ORM-defined tables, `schema_migrations` is created, and the initial migration is recorded as applied without executing its SQL
- [ ] Given a fresh database, when initialization completes, then all tables defined by ORM models exist with current columns and the `schema_migrations` table contains one row for the initial migration

### Existing Installation (R2)
- [ ] Given a database with all current schema changes already applied but no `schema_migrations` table, when `initialize()` runs, then the `schema_migrations` table is created, the initial migration is stamped as applied, and no ALTER TABLE or CREATE TABLE statements execute
- [ ] Given an existing up-to-date database after migration, when the application restarts, then no schema modifications occur and startup is faster due to eliminated pragma checks

### Migration Tracking (R0, R4)
- [ ] Given a database with the initial migration applied, when a new migration is added to the registry, then only the new migration executes on the next startup
- [ ] Given multiple pending migrations, when they execute, then they run in the order defined by their revision chain (each migration references its `down_revision`)
- [ ] Given a migration registry with 2+ migrations, when querying `schema_migrations`, then applied revisions match the migration names in the registry

### Migration Execution (R5, R6, R7)
- [ ] Given a pending migration with multiple SQL statements, when it executes, then all statements run within a single transaction and the revision is stamped only after successful commit
- [ ] Given a pending migration that executes, when it completes, then a log entry is emitted with the revision ID and migration name
- [ ] Given a migration whose SQL fails, when execution is attempted, then the transaction rolls back, a clear error is raised identifying the failed migration, and no subsequent migrations execute
- [ ] Given a migration that fails, when the application restarts, then the failed migration is re-attempted (not marked as applied)

### Code Cleanup (R1)
- [ ] Given the new migration system is in place, when `_run_migrations()` is inspected, then no pragma-based checks remain — only `create_all()` and the migration runner
