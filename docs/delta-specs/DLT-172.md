# Delta Spec: DLT-172 - Unified topic-oriented memory store

<!-- This spec describes WHAT the delta does, not HOW it's implemented. -->

## Story

As the system, I need everything known about a subject — both the objective reference facts and the user's subjective preferences about it — to live together in one place, so that recalling a topic never depends on correctly guessing whether a piece of knowledge was classified as a "fact" or a "preference," and nothing about a subject ends up fragmented across two stores.

## What It Does

Replaces the separate `facts/` and `preferences/` memory stores with a single topic-oriented store at `memories/topics/`, where each `<topic>.md` file holds everything the assistant knows about a subject — stable reference facts and subjective preferences together, in free-form unified prose. The facts-vs-preferences classification/routing boundary that fragmented knowledge across two stores is eliminated. Extraction folds both factual and preferential signals from each closed conversation branch into the relevant topic file (creating or merging it), replacing the two separate facts and preferences extractions. A single `MEMORY.md` index with one entry per topic drives the static index injection (now a single Topics Index instead of separate Facts and Preferences indexes); the on-demand read pattern carries over. Topics maintenance consolidates and prunes the unified store, dropping the facts-vs-preferences misclassification logic. Episodic memory and transcript archives are unchanged. A one-time, self-detecting, idempotent migration folds any existing `facts/` and `preferences/` files into merged topic files without data loss.

**Terms used.** *Broad-topic naming* is the existing extraction convention carried over from the facts store — broad, future-mergeable topic filenames (e.g. `<domain>.md`, `<project>.md`), never names scoped to an incident, bug, or date. The *authority hierarchy* (`Skills > Topics > Context`) is the existing maintenance rule: when content conflicts, the higher source wins — skills override topics, which override the root context files (SOUL/USER/AGENTS).

## Acceptance Criteria

### Topic store layout and bootstrap (R0, R1, R2)
- [ ] Given an empty workspace, when the memory bootstrap runs, then `memories/` contains `topics/`, `episodic/`, and `transcripts/` (no `facts/` or `preferences/` is created), and `memories/topics/MEMORY.md` exists with only the `# Memory Index` header
- [ ] Given pre-existing topic files without an index, when bootstrap runs, then each gets a placeholder entry (`Description pending update`) with a Title Case name derived from its filename
- [ ] Given an existing `memories/topics/MEMORY.md`, when bootstrap runs again, then it is preserved (idempotent)
- [ ] Given any topic file, when it is written, then it holds both factual and preferential content about its subject in free-form unified prose, with no required internal Facts/Preferences structure, and carries exactly one index entry in `[Name](./file.md): description` format

### Static index injection (R4)
- [ ] Given a topics index with entries, when a message is handled, then the injected block (tag `memories`) contains the layout section (now describing the topics store) and a single `## Topics Index` section with one bullet per entry; there is no separate Facts or Preferences index section
- [ ] Given a header-only topics index, when the provider runs, then it contributes no index section while the layout section is still injected
- [ ] Given no `memories/` directory, when the section is built, then it yields empty content and contributes nothing
- [ ] Given malformed index lines, when the index is formatted, then well-formed entries are kept and malformed ones dropped silently

### Extraction (R0, R3, R6)
- [ ] Given a closed trunk with branches, when the trunk-close extraction phase runs, then each unextracted branch is forked (file-tool allowlist) and a single topics extraction folds both factual and preferential signals from that branch's turns into topic files (creating new broad-topic files or merging into existing ones) — there is no separate facts or preferences extraction pass
- [ ] Given no existing topic matches the conversation's new content, when the extraction runs, then it creates a new broad-topic file (broad, future-mergeable name) rather than appending to an unrelated topic
- [ ] Given the extraction runs, then no facts-vs-preferences classification self-check is performed; the agent decides which topic file a signal belongs to and merges rather than routing between stores
- [ ] Given information that duplicates content already in a root context file (SOUL/USER/AGENTS) or an existing topic, when the extraction runs, then it updates/merges rather than duplicating, and prunes entries contradicted by the conversation
- [ ] Given a branch already carrying an extraction marker, when the phase re-runs (e.g. after a crash), then it is skipped (extraction remains idempotent per branch)
- [ ] Given the agent emptied a topic file, when the run completes, then the sweep removes it while non-empty files survive

### Topics maintenance (R5, R6)
- [ ] Given the trunk-close prune phase runs, then a single topics maintenance pass evaluates staleness, redundancy, overlap, cluster fragmentation (3+ files sharing a topic merge into one broad file), and size limits across the unified topics store
- [ ] Given the maintenance runs, then no facts-vs-preferences misclassification detection is performed (there is no second store to misclassify into)
- [ ] Given a topic duplicates or contradicts content in a root context file, when maintenance runs, then it trims to a pointer or reconciles per the authority hierarchy (Skills > Topics > Context)
- [ ] Given the consolidate phase and core-context step, then they remain marker-guarded (consolidate is an interim no-op pending DLT-173's richer phases); episodic tiers and context-file cleanup are unchanged
- (deferred) Richer named-phase consolidation over the topic store is the scope of DLT-173, not this delta

### Migration of existing stores (R7)
- [ ] Given a workspace with `facts/` and/or `preferences/` files and no `topics/` store, when the migration runs (once, at startup), then an agent folds the existing files into merged `topics/` files — files about the same subject across both old stores merge into a single topic file; files about distinct subjects remain distinct — and the old stores are emptied and swept
- [ ] Given a non-empty old file, when the migration processes it, then its durable content is written into a topic file BEFORE the old file is emptied (fold-before-empty), so no content is lost
- [ ] Given the migration runs, then the pre-migration state is preserved via git (the stores are git-tracked markdown) and the result is committed; the migration is self-detecting and idempotent — its completion marker is written ONLY after the full pass, so re-running is a no-op
- [ ] Given the migration is interrupted mid-run (crash/kill) before its completion marker is written, when the system restarts and the migration check runs, then it re-runs cleanly — no duplication, no corrupted partial state, no data loss (the stores remain git-recoverable)
- [ ] Given the migration fails while processing one file (agent error, unreadable content), when the failure occurs, then it is logged and isolated — other files' content is still folded and no partial corruption is committed; the run is re-runnable and the failed file is retried on the next run
- [ ] Given an empty (0-byte or whitespace-only) old file, when the migration runs, then it is skipped without creating an empty topic file
- [ ] Given a workspace being migrated, when the first session begins, then its memory index injection reflects the migrated topics store (not the stale facts/preferences layout)
- [ ] Given the migration completes, when it finishes, then it logs an auditable summary (old facts/preferences file counts → topic files produced)
- [ ] Given a fresh install with no `facts/` or `preferences/`, when the migration check runs, then it is a no-op (bootstrap creates `topics/` directly)
- [ ] Given a workspace already migrated (`topics/` present), when the check runs, then it is a no-op

### Unchanged behavior (R8)
- [ ] Given episodic extraction and maintenance, when they run, then their behavior (one local-date file per day, time-tiered weekly/monthly consolidation) is unchanged by this delta
- [ ] Given transcript archival and age-based pruning, when they run, then their behavior is unchanged by this delta
