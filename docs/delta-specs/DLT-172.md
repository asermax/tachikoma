# Delta Spec: DLT-172 - Plugin Configuration Schema

<!-- This spec describes WHAT the delta does, not HOW it's implemented. -->

## Story

As a plugin author, I want to declare typed configuration settings in my plugin manifest so that users can configure my plugin through Tachikoma's config.toml without environment variables or separate config files. As a plugin user, I want all plugin settings in one place alongside built-in configuration.

## What It Does

Adds a `[config]` section to the plugin manifest where authors declare typed settings (string, integer, boolean, float) with defaults and descriptions. Users populate values in `[plugins.<alias>.config]` in config.toml. At load time, user values are validated against the schema, defaults are applied for missing optional fields, and the validated config dict is available to the plugin at runtime. Plugins with invalid configuration fail to load with a diagnostic message. All startup-time notifications (restart announcements, plugin load failures) are consolidated into a single message.

## Manifest Config Structure

The plugin manifest (`tachikoma-plugin.toml`) gains an optional `[config.<field_name>]` section per declared setting:

```toml
name = "weather-plugin"
version = "1.0.0"
description = "Weather lookup plugin"
skills = ["skills/weather"]

[config.api_key]
type = "string"
description = "API key for the weather service"
required = true

[config.timeout]
type = "integer"
description = "Request timeout in seconds"
default = 30

[config.debug]
type = "boolean"
description = "Enable debug logging"
default = false

[config.rate]
type = "float"
description = "Rate limit multiplier"
default = 1.5
```

Field names are case-sensitive (consistent with TOML). Each field section must contain `type` (one of `string`, `integer`, `boolean`, `float`) and `description`. Fields without `default` are optional at runtime only if `required` is absent or `false`; fields with `required = true` must not also declare a `default`.

## Acceptance Criteria

<!-- Grouped by requirement area. Each R should map to one or more AC groups. -->

### Manifest Schema Declaration (R0, R1)

- [ ] Given a manifest with `[config.api_key]` declaring `type = "string"`, `description = "API key"`, `required = true`, when parsed, the plugin's config schema contains one string field named `api_key` that is required
- [ ] Given a manifest with `[config.timeout]` declaring `type = "integer"`, `default = 30`, `description = "Request timeout in seconds"`, when parsed, the field is optional with default 30
- [ ] Given a manifest with `[config.debug]` declaring `type = "boolean"`, `default = false`, when parsed, the field is optional with default false
- [ ] Given a manifest with `[config.rate]` declaring `type = "float"`, `default = 1.5`, when parsed, the field is optional with default 1.5
- [ ] Given a manifest without a `[config]` section, when parsed, the plugin loads normally with an empty config schema
- [ ] Given a manifest `[config]` field with an unsupported `type` value (e.g., `"array"`, `"object"`), when loaded, then the plugin fails with a diagnostic naming the field, the invalid type, and the list of valid types (string, integer, boolean, float)
- [ ] Given a manifest `[config.timeout]` with `type = "integer"` and `default = "thirty"` (type mismatch), when the manifest is parsed, then the plugin fails with a diagnostic stating the default value doesn't match the declared type
- [ ] Given a manifest `[config.api_key]` with both `required = true` and `default = "fallback"`, when the manifest is parsed, then the plugin fails with a diagnostic stating that required fields cannot have defaults
- [ ] Given a manifest `[config.api_key]` with a `type` key but no `description` key, when the manifest is parsed, then the plugin fails with a diagnostic stating that `description` is required for all config fields

### Config Value Location (R2)

- [ ] Given `[plugins.weather.config]` with `api_key = "sk-..."` and `timeout = 60`, when config is loaded, the weather plugin receives `{"api_key": "sk-...", "timeout": 60}`
- [ ] Given `[plugins.weather]` with source fields (`git`, `ref`) and a `[plugins.weather.config]` sub-table, when config is parsed, source and config fields are cleanly separated
- [ ] Given `[plugins.weather.config]` with a key that matches a reserved source field name (e.g., `git`), when loaded, the key is treated as a config value (no collision since source fields and config live in separate sub-tables)
- [ ] Given a plugin alias with no `.config` sub-table, when config is loaded, the plugin receives only default values (or empty dict if no schema)

### Validation (R3)

- [ ] Given a required string field with no user value and no default, when the plugin loads, then the plugin fails with status `failed` and a diagnostic stating the field is required
- [ ] Given a field declared as `type = "integer"` with user value `"not a number"`, when the plugin loads, then it fails with a diagnostic stating the expected and actual types
- [ ] Given a field declared as `type = "boolean"` with user value `42`, when the plugin loads, then it fails with a diagnostic stating type mismatch
- [ ] Given a field declared as `type = "boolean"` with user value `"true"` (string), when validated, then validation fails with a diagnostic about type mismatch (no string-to-bool coercion)
- [ ] Given a field declared as `type = "integer"` with user value `30.0` (float), when validated, then the value is coerced to integer `30` (float-with-zero-fraction is integer-compatible)
- [ ] Given a field declared as `type = "integer"` with user value `30.5` (non-zero fraction), when validated, then validation fails with a diagnostic about type mismatch
- [ ] Given a field with a default value and no user override, when the plugin loads, then the default is used
- [ ] Given a field that is not required and has no default, when the user provides no value, then the runtime config dict does not contain a key for that field
- [ ] Given an optional string field with no default, when the user provides `api_key = ""` (empty string), then the runtime config contains `{"api_key": ""}` (empty string is a valid value, distinct from unset)
- [ ] Given a user provides a config key not declared in the schema, when the plugin loads, then the plugin status is `loaded`, a WARNING is logged with the unknown key name, and the unknown key is not included in the runtime config dict

### Runtime Access (R4)

- [ ] Given a loaded plugin with validated config, when plugin code accesses `loaded_plugin.config`, it returns a `dict[str, str | int | bool | float]` mapping field names to validated values
- [ ] Given a plugin with no `[config]` section, when accessed at runtime, `loaded_plugin.config` returns an empty dict
- [ ] Given a plugin with a config schema where all fields have defaults and the user provided no values, when accessed at runtime, `loaded_plugin.config` returns a dict populated with default values

### Config Surfacing (R5)

- [ ] Given a plugin with a config schema, when `list_plugins` is invoked, the entry for that plugin includes a `config` key containing a dict where each field maps to an object with keys: `type`, `description`, `default`, `required`, and `value` (current user value, or default if unset, or null if optional and unset)
- [ ] Given a plugin with no config schema, when `list_plugins` is invoked, the config section is absent from the output
- [ ] Given a plugin that failed config validation, when `list_plugins` is invoked, the output includes the config schema and the validation diagnostic

### Failed Plugin Notification (R6)

- [ ] Given two plugins fail to load during startup, when startup completes, a single notification is dispatched listing both failures
- [ ] Given all plugins load successfully, when startup completes, no plugin failure notification is dispatched
- [ ] Given one plugin fails and one succeeds, the notification includes only the failed plugin

### Startup Notification Consolidation (R7)

- [ ] Given a restart notification marker exists and one plugin failed config validation, when `bootstrap.run()` completes and before `channel.run()`, a single consolidated notification is dispatched containing both the back-online message and the plugin failure details
- [ ] Given a restart notification marker exists and all plugins loaded successfully, when startup completes, the standard back-online notification is delivered (no plugin section)
- [ ] Given no restart notification and plugin failures exist, when startup completes, only the plugin failure notification is delivered
- [ ] Given neither restart notification nor plugin failures exist, when startup completes, no startup notification is dispatched
- [ ] Given the restart notification marker is cleared during the consolidation, the DES-011 consume-once pattern is preserved

## Notes on Out-of-Scope Items

- **R12 (Config migration)**: When a plugin's config schema changes across versions, unknown user-provided keys are warned and ignored (existing behavior), and new fields without user values use their defaults. No automatic migration or cleanup of stale user config values.
- **Runtime config reload**: Modifying config.toml while Tachikoma is running does not reload plugin configs. Changes take effect on next startup.
- **Environment variable substitution**: Config values are literal TOML values. No `${VAR}` substitution or environment variable referencing.
- **Config value secrecy**: Config values appear in `list_plugins` output and may be logged. Sensitive field marking and redaction are deferred to DLT-156.
