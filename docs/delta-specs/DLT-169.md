# Delta Spec: DLT-169 - Track External Message IDs Per Session

## Story

As a user, I want my reactions on past messages to route me back to the correct conversation session so that follow-ups on older topics resume in the right context without manual intervention.

## What It Does

Adds a channel-agnostic mechanism to map platform-specific message IDs (e.g., Telegram `message_id`) to internal conversation sessions. Both incoming (user) and outgoing (agent) message IDs are recorded. When a reaction arrives on a message that belongs to a different session, the system closes the current session and reopens the target session, routing the reaction there.

## Requirements

| ID | Requirement | Status |
|----|-------------|--------|
| R0 | Map platform-specific message IDs to internal sessions for cross-referencing | Core goal |
| R1 | Store incoming (user) and outgoing (agent) message IDs per session in a `session_external_ids` database table with: `id` (auto-increment PK), `session_id` (FK to sessions, ON DELETE CASCADE), `channel` (string identifying the source channel — canonical values: "telegram", "repl"), `direction` ("incoming" or "outgoing"), `external_id` (string, the platform-specific ID); the `(channel, external_id)` pair is unique — recording a duplicate is a no-op (insert-or-ignore) | Must-have |
| R2 | Add an `external_id: str \| None = None` field to `TextMessage` and `ReactionMessage` envelopes so the coordinator and channels can pass the platform ID through the pipeline. `ButtonTapMessage` is explicitly excluded — button prompts are interactive responses to the current session's agent and are inherently session-scoped | Must-have |
| R3 | On the Telegram channel: capture `message.message_id` for incoming messages and set it on the envelope before enqueueing; capture outgoing message IDs (`_current_message_id` and `_split_message_ids`) from the `ResponseRenderer` after response finalization and persist them to the external IDs table | Must-have |
| R4 | When a reaction arrives and the reacted-to message's external ID maps to a session other than the current active session, close the current session (triggering async post-processing) and reopen the target session before routing the reaction | Must-have |
| R5 | Handle split messages: each outgoing split message ID is recorded as its own row in the table, so reactions on any split fragment resolve to the correct session | Must-have |
| R6 | Messages with no associated session lookup result (pre-feature messages, orphaned IDs, unknown channels) are handled gracefully — the reaction routes normally without session switching | Must-have |
| R7 | Periodic cleanup of stale external ID mappings | Out — deferred to a future delta for session cleanup |

## Acceptance Criteria

### External ID Storage (R1)

- [ ] Given a `session_external_ids` table, when created, then it has columns: `id` (integer PK, auto-increment), `session_id` (text FK to `sessions.id`, ON DELETE CASCADE), `channel` (text), `direction` (text, "incoming" or "outgoing"), `external_id` (text)
- [ ] Given a `session_external_ids` table, when created, then it has an index on `(channel, external_id)` for fast lookup by platform message ID
- [ ] Given a `session_external_ids` table, when created, then it has an index on `session_id` for session-scoped queries
- [ ] Given a session is deleted from the `sessions` table, when the delete commits, then all associated `session_external_ids` rows are automatically deleted (cascade)
- [ ] Given a session with multiple external ID records, when queried by session ID, then all records for that session are returned in insertion order
- [ ] Given a `session_external_ids` table, when created, then it has a unique index on `(channel, external_id)` so that recording a duplicate `(channel, external_id)` pair is a no-op (insert-or-ignore)
- [ ] Given a database without the `session_external_ids` table, when the migration SQL runs, then the table is created with all columns, indexes, and foreign key constraints

### Envelope External ID (R2)

- [ ] Given a `TextMessage` envelope, when constructed with `external_id="123"`, then the field is accessible as `envelope.external_id`
- [ ] Given a `ReactionMessage` envelope, when constructed with `external_id="456"`, then the field is accessible as `envelope.external_id`
- [ ] Given a `TextMessage` or `ReactionMessage` constructed without `external_id`, then the field defaults to `None` (callers must pass a non-empty string or omit the field entirely — empty strings are not a valid value)

### Telegram Incoming ID Capture (R3)

- [ ] Given the Telegram channel receives a text message from the authorized user, when constructing the `TextMessage` envelope, then the envelope's `external_id` is set to `str(message.message_id)`
- [ ] Given the Telegram channel receives a media message, when constructing the `TextMessage` envelope for the description, then the envelope's `external_id` is set to `str(message.message_id)`
- [ ] Given the Telegram channel has determined the active session (after session creation/resume), when the incoming message's `external_id` is available, then a record is persisted to `session_external_ids` with `direction="incoming"`

### Telegram Outgoing ID Capture (R3, R5)

- [ ] Given the ResponseRenderer finalizes a response with a single message, when finalization completes, then the `_current_message_id` is persisted to `session_external_ids` with `direction="outgoing"` and the current channel identifier
- [ ] Given the ResponseRenderer finalizes a response that was split into multiple messages, when finalization completes, then each split message ID is persisted as its own row in `session_external_ids` with `direction="outgoing"`
- [ ] Given the ResponseRenderer had no message to send (empty response), when finalization completes, then no outgoing external ID records are created
- [ ] Given outgoing ID recording fails, when the error occurs, then it is logged and the conversation continues (consistent with graceful degradation pattern)
- [ ] Given the ResponseRenderer finalizes a response, when outgoing IDs are recorded, then recording happens asynchronously after the Result event is yielded to avoid blocking response delivery

### Reaction-Based Session Routing (R4)

- [ ] Given a reaction arrives on a message whose external ID maps to a session that is not the current active session, when the session lookup succeeds and the target session is valid for resumption, then the current session is closed (with async post-processing) and the target session is reopened before the reaction is routed
- [ ] Given a reaction arrives on a message whose external ID maps to the current active session, when the session lookup succeeds, then no session switching occurs and the reaction routes normally
- [ ] Given a reaction arrives on a message whose external ID maps to a session that fails resumption validation (missing transcript, too old, already open), when the lookup returns no valid session, then the reaction routes to the current session without switching
- [ ] Given a reaction arrives and the reaction handler has access to the reacted-to Telegram message ID, when building the `ReactionMessage` envelope, then `external_id` is set to `str(event.message_id)` (the ID of the reacted-to message)
- [ ] Given a reaction arrives on a past-session message while an agent response is streaming in the current session, when the delivery lock is held, then the reaction is enqueued as a steering message into the current session (same as today's behavior); session switching does not occur mid-response
- [ ] Given two reactions arrive sequentially on messages from different past sessions, when the first is processed (session switches), then the second reaction's external ID lookup resolves to its target session relative to the now-current session — reactions are serialized by the delivery lock, so no race condition occurs

### Graceful Degradation (R6)

- [ ] Given a reaction arrives on a message whose external ID is not found in the mapping table, when the lookup returns no result, then the reaction routes to the current session without switching (no error surfaced to user)
- [ ] Given a reaction arrives from a channel that does not populate `external_id` (envelope has `external_id=None`), when the coordinator processes it, then no session lookup is attempted and the reaction routes normally
- [ ] Given the session registry is not available (None), when external ID recording or lookup is attempted, then the operations are skipped gracefully
