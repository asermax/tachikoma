# Delta Spec: DLT-173 - Plugin Lifecycle Hooks and Event Bus Access

## Story

As a plugin author, I want to declare init hooks and event subscriptions in my plugin manifest so that my plugin can run startup tasks and react to system events without modifying core code.

## What It Does

Extends the plugin manifest with `[hooks]` and `[events]` sections. Init hooks run once after all plugins are loaded but before the first conversation. Event subscriptions route typed system events (coordinator idle, notification dispatch, plugin lifecycle, etc.) to handler functions declared by the plugin. All handler execution is isolated per-plugin — failures are logged and never block other plugins or application startup.

## Requirements

| ID | Requirement | Status |
|----|-------------|--------|
| R0 | Plugins can declare an init hook that runs once after all plugins are loaded but before the first conversation | Core goal |
| R1 | Plugins can subscribe to existing system events and have matching events routed to declared handler functions | Core goal |
| R2 | Init hooks and event handlers are isolated per-plugin — failures are logged without blocking other plugins or application startup | Must-have |
| R3 | The manifest gains `[hooks]` and `[events]` sections with module-name entry points resolved against `hooks/` and `events/` directories | Must-have |
| R4 | Init hooks receive context (validated config dict, event bus reference, plugin alias and install path) | Must-have |
| R5 | Event handlers receive the typed event payload and the same plugin context as init hooks | Must-have |
| R6 | CC plugins cannot declare hooks or event subscriptions — the CC "hooks" contribution type continues to be silently ignored | Must-have |
| R7 | Handler entry points are validated at discovery time — missing files cause the plugin to fail with a diagnostic | Must-have |
| R8 | Init hooks have a configurable timeout — hooks exceeding it are cancelled and logged | Nice-to-have |
| R9 | Plugins cannot dispatch custom events onto the event bus | Out |
| R10 | New system events (e.g., session open/close) are not created as part of this delta | Out |

## Acceptance Criteria

### Manifest Extension (R3, R6, R7)

- [ ] Given a `tachikoma-plugin.toml` with `[hooks] init = "init"` and `[events] coordinator_idle = "on_idle"`, when the manifest is parsed, the internal model contains an init hook entry resolving to `hooks/init.py` and an event subscription mapping `coordinator_idle` to `events/on_idle.py`
- [ ] Given a `[hooks]` section with multiple entries (e.g., `init = "init"`), when parsed, all hook entry points are captured
- [ ] Given an `[events]` section with multiple entries, when parsed, all event subscriptions are captured as a mapping of event type name to handler module
- [ ] Given a manifest with `[hooks] init = "init"`, when the loader resolves the path, it looks for `hooks/init.py` relative to the plugin install directory
- [ ] Given a manifest with `[events] coordinator_idle = "on_idle"`, when the loader resolves the path, it looks for `events/on_idle.py` relative to the plugin install directory
- [ ] Given a CC plugin with a `"hooks"` contribution in `plugin.json`, when parsed, the hooks contribution is silently ignored with an INFO log (consistent with existing CC contribution handling)
- [ ] Given a manifest declaring an init hook where `hooks/init.py` does not exist on disk, when discovery runs, the plugin fails with a diagnostic naming the missing file
- [ ] Given a manifest declaring an event subscription where `events/on_idle.py` does not exist on disk, when discovery runs, the plugin fails with a diagnostic naming the missing file
- [ ] Given a manifest with `[hooks] init = "init"` and `hooks/init.py` exists, when discovery runs, the module is importable and contains an `init` function — if not, the plugin fails with a diagnostic
- [ ] Given a manifest with `[events] coordinator_idle = "on_idle"` and `events/on_idle.py` exists, when discovery runs, the module is importable and contains a `handle` function — if not, the plugin fails with a diagnostic
- [ ] Given an event type name in `[events]` that does not match a known system event, when discovery runs, the plugin fails with a diagnostic listing valid event type names

### Init Hook Execution (R0, R4, R8)

- [ ] Given a plugin with an init hook, when all plugins finish loading, the init hook runs before the first conversation is processed
- [ ] Given multiple plugins with init hooks, when hooks execute, they run sequentially in plugin alias alphabetical order
- [ ] Given an init hook that completes successfully, when it runs, the plugin is considered fully initialized and its event subscriptions become active
- [ ] Given an init hook that raises an exception, when it runs, the exception is logged at ERROR level with the plugin alias, the plugin's event subscriptions are not registered, but other plugins' hooks and startup proceed normally
- [ ] Given an init hook, when it runs, it receives a context object containing: the plugin's validated `config` dict, the event bus, the plugin alias, and the plugin install path
- [ ] Given a plugin with no `[hooks]` section, when loading completes, no init hook runs and the plugin's event subscriptions (if any) are registered immediately

### Event Subscription (R1, R5)

- [ ] Given a plugin with `[events] coordinator_idle = "on_idle"`, when the init hook completes (or immediately if no init hook), the handler is subscribed to `CoordinatorIdle` events on the event bus
- [ ] Given a `CoordinatorIdle` event is dispatched, when a plugin has subscribed to it, the plugin's handler function is called with the typed event payload and the plugin context
- [ ] Given a plugin subscribed to `Notification` events, when a notification is dispatched, the handler receives the full `Notification` event object
- [ ] Given an event handler that raises an exception, when the handler is invoked, the exception is logged at ERROR level with the plugin alias and event type, but the event dispatch continues to other subscribers
- [ ] Given a plugin subscribed to multiple event types, when events of different types are dispatched, each is routed to its corresponding handler function
- [ ] Given a plugin subscribed to `PluginInstalled` events, when another plugin is installed at runtime, the handler receives the `PluginInstalled` event

### Error Isolation (R2)

- [ ] Given plugin A's init hook raises and plugin B has an init hook, when hooks execute, plugin A's failure is logged, plugin B's hook runs normally, and application startup is not blocked
- [ ] Given plugin A's event handler raises during a `CoordinatorIdle` dispatch, when the event is dispatched, plugin A's error is logged, other subscribers to `CoordinatorIdle` still receive the event, and the event dispatch completes normally
- [ ] Given a plugin whose init hook failed, when subsequent events are dispatched, the plugin's event handlers are not invoked (subscriptions were not registered)

### Timeout (R8)

- [ ] Given an init hook that exceeds the configured timeout, when the timeout fires, the hook is cancelled, a WARNING is logged with the plugin alias and timeout duration, and the plugin's event subscriptions are not registered
- [ ] Given no timeout configuration, when init hooks run, a sensible default timeout applies
