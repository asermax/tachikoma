# Delta Spec: DLT-076 - Re-evaluate memory context per message

## Story

As a user, I want my assistant to surface relevant memories throughout the conversation — not just at the start — so that follow-up messages benefit from context that becomes relevant as the topic evolves.

## What It Does

Moves the memory context provider from the session-gated pre-processing pipeline (runs once on first message) to the per-message pipeline (runs on every message). The memory search agent forks the current SDK session so it has full conversation context and can decide whether the new message warrants searching for additional memories. Each memory is returned as an individual context entry (tag: "memories", differentiated by metadata) to prevent duplicate injection.

## Requirements

| ID | Requirement | Status |
|----|-------------|--------|
| R0 | Re-evaluate memory relevance on each message so the agent always has the most pertinent memories for the current point in the conversation | Core goal |
| R1 | Memory relevance evaluation must run on every message, not just the first message of a session | Must-have |
| R2 | Memory search agent forks the current SDK session so it has full conversation context to make informed decisions | Must-have |
| R3 | Prompt instructs the agent to decide whether the new message warrants searching for additional memories — skip search if not needed | Must-have |
| R4 | Return one ContextResult per memory file (all using "memories" tag), with metadata identifying the memory file path to prevent duplicate entries | Must-have |
| R5 | Never remove existing memory entries — only append new ones | Must-have |
| R6 | Maintain current error isolation — memory failures never block the conversation | Must-have |
| R7 | Code-level cost optimization (e.g., skipping agent spawn entirely for trivial follow-ups) | Out — R3 provides partial mitigation via agent-level decision; full optimization deferred until impact is measured |

## Acceptance Criteria

### Memory re-evaluation per message (R0, R1)

- [ ] Given a session is active, when a second message is sent that introduces a new topic, then the memory provider runs and surfaces memories relevant to the new topic
- [ ] Given a session is active, when a follow-up message continues the same topic, then the memory provider runs and can decide no new memories are needed
- [ ] Given it is the first message of a new session, when the memory provider runs, then it searches for memories relevant to that message (preserving current first-message behavior)

### Session fork for conversation context (R2)

- [ ] Given a session with an existing SDK session ID, when the memory provider runs on a subsequent message, then it forks the current SDK session so the search agent has full conversation context
- [ ] Given the first message of a new session (no SDK session ID exists yet because it is assigned after the first response completes), when the memory provider runs, then it operates as a standalone query without forking — same as current behavior

### Agent-driven search decision (R3)

- [ ] Given the memory search agent has conversation context (via fork), when it evaluates the new message, then it decides whether new memories are needed based on what topics have already been covered
- [ ] Given the agent decides no new memories are needed, when it returns its result, then the provider produces no new entries and the message proceeds with existing memory context intact

*Note: On the first message (no fork, no conversation context), the prompt should handle the no-context case gracefully — this is a design-phase concern for prompt construction.*

### Individual memory entries with metadata (R4, R5)

- [ ] Given the memory search agent finds N relevant memories, when it returns results, then the provider produces N individual ContextResult entries (one per memory file), all with tag "memories"
- [ ] Given a memory file is already present in the session's existing context entries (matched by metadata), when the provider processes results, then it skips that memory to avoid duplication
- [ ] Given new memory entries are produced, when they are persisted, then they are appended alongside existing entries — no existing entries are removed
- [ ] Given each memory entry, then its metadata contains the memory file path for identification

### Error isolation (R6)

- [ ] Given the memory search agent fails (e.g., SDK connection error, fork failure), when the provider catches the error, then it logs the failure and returns None — the conversation proceeds unaffected
- [ ] Given the SDK session referenced by the fork has expired or become invalid, when the fork fails, then the provider logs the failure and returns None — the conversation proceeds unaffected
- [ ] Given the memory search agent exhausts its turn limit, when the provider processes the response, then it returns None
