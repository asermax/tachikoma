# Delta Spec: DLT-111 - Prevent message loss during response finalization

## Story

As a user, I want every message I send to be guaranteed to reach the assistant so that I never experience a silently dropped message when I happen to send it at the wrong moment.

## What It Does

Eliminates timing windows in the coordinator and channel layers where messages can be silently dropped during response finalization. When a user sends a message at the exact moment a previous response is completing, two independent race conditions can cause the message to disappear: the coordinator's message source generator can consume it from the shared buffer during SDK teardown, and the channel's processing loop can miss it during the transition from "active" to "idle" state. This delta closes both windows so that every enqueued message is guaranteed to be processed.

## Requirements

| ID | Requirement | Status |
|----|-------------|--------|
| R0 | Every message consumed from the queue is guaranteed to be processed or returned to the queue — no silent drops | Core goal |
| R1 | Messages arriving during SDK teardown (client.disconnect) must not be lost to _message_source cancellation | Must-have |
| R2 | Messages arriving after the channel's drain loop exits but before the processing flag resets must be processed | Must-have |
| R3 | Message ordering is preserved — messages are processed in the order they were enqueued | Must-have |
| R4 | The fix applies uniformly to all channels (Telegram, REPL) and all message sources (user input, session tasks, notifications) | Must-have |
| R5 | No regression on mid-stream message delivery to the SDK — steering messages during an active response still work | Must-have |
| R6 | The fix does not introduce new await points that could widen other timing windows | Nice-to-have |

## Acceptance Criteria

### R0/R1 — Buffer isolation during SDK teardown

- [ ] Given the SDK is finalizing a response (between `receive_response()` completing and `client.disconnect()` finishing), when a new message is enqueued, then the message remains in the coordinator's main buffer and is available for the next `send_message()` call
- [ ] Given the `_message_source` generator is cancelled during SDK teardown, when it had a pending `await buffer.get()`, then no message is consumed from the main buffer by the cancellation
- [ ] Given the SDK session ends normally, when `send_message()` returns, then all messages enqueued during finalization are reflected in `has_pending_messages`

### R2 — Channel drain guarantee

- [ ] Given the Telegram channel's `while has_pending_messages` loop has exited, when a message is enqueued during post-loop cleanup (ChatActionSender teardown, on_complete callback), then the message is processed before the channel transitions to idle
- [ ] Given the REPL processes a session task or notification, when a message is enqueued during or after coordinator processing, then the message is not stranded in the buffer

### R3 — Ordering

- [ ] Given messages A, B, C are enqueued in that order, when they are processed across turn boundaries, then the coordinator processes them in A, B, C order
- [ ] Given message A is a mid-stream steering message consumed by the active SDK session, when message B arrives after the session ends, then B is processed as the next turn (not reordered ahead of any pending messages)

### R5 — Mid-stream message regression

- [ ] Given the SDK is actively processing a turn, when a follow-up message is enqueued, then it is delivered to the SDK as a steering message within the current turn (same behavior as today)
- [ ] Given multiple mid-stream messages arrive during a single turn, when the SDK consumes them, then they are delivered in enqueue order

### Error/edge cases

- [ ] Given a stream error (CLIConnectionError) during SDK processing, when the error is caught, then messages in the buffer are preserved (existing behavior maintained)
- [ ] Given `send_message()` is called with an empty buffer, when no message exists, then it returns immediately without side effects (existing behavior maintained)
- [ ] Given a per-message post-processing task is pending from the previous turn, when the next `send_message()` starts, then it awaits the pending task before processing the new message (existing behavior maintained)
