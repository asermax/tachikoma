# Delta Spec: DLT-111 - Prevent message loss during response finalization

## Story

As the coordinator and channel system, I need to eliminate race conditions in the message processing pipeline so that no user messages are silently dropped during response finalization.

## What It Does

Closes two independent timing windows where messages can be silently lost. The `_message_source` async generator and `send_message()` both read from the same `_message_buffer` queue — during SDK teardown (`client.disconnect()`), the message source's pending `buffer.get()` can consume a message that is then discarded when the generator is cancelled, removing it from the queue without processing it. Separately, each channel's processing loop has a gap between its drain loop exiting (buffer empty) and its processing flag clearing — messages enqueued during that window sit in the buffer with no active consumer. This delta isolates the mid-stream queue from the main buffer and adds drain guarantees to channel processing loops.

## Requirements

| ID | Requirement | Status |
|----|-------------|--------|
| R0 | Every message consumed from the queue is guaranteed to be processed or returned to the queue — no silent drops | Core goal |
| R1 | Messages arriving during SDK teardown (`client.disconnect`) must not be lost to `_message_source` cancellation. The implementation must not introduce new `await` points in the critical path between buffer consumption and message processing. | Must-have |
| R2 | Every channel's processing loop must guarantee that messages enqueued after the drain loop exits but before the processing flag resets are processed before transitioning to idle. Applies uniformly to all channels (Telegram, REPL) and all message sources (user input, session tasks, notifications). | Must-have |
| R3 | Message ordering is preserved — messages are processed in the order they were enqueued | Must-have |
| R4 | No regression on mid-stream message delivery to the SDK — steering messages during an active response still work | Must-have |

## Acceptance Criteria

### R0/R1 — Buffer isolation during SDK teardown

- [ ] Given the SDK is finalizing a response (between `receive_response()` completing and `client.disconnect()` finishing), when a new message is enqueued, then the message remains in the coordinator's main buffer and is available for the next `send_message()` call
- [ ] Given the `_message_source` generator is cancelled during SDK teardown, when it had a pending `await buffer.get()`, then no message is consumed from the main buffer by the cancellation
- [ ] Given the SDK session ends normally, when `send_message()` returns, then the coordinator's pending state correctly reflects that unprocessed messages exist
- [ ] (R0) Given a stream error (`CLIConnectionError`) during SDK processing, when the error is caught, then messages in the main buffer are preserved (existing behavior maintained)

### R2 — Channel drain guarantee

- [ ] Given any channel's processing loop has finished iterating the coordinator, when a message was enqueued during or after the final coordinator call, then the message is processed before the channel transitions to idle
- [ ] Given the check for remaining messages and the clearing of the processing flag, then no `await` point exists between the final empty check and the flag transition — the idle transition is atomic with respect to the event loop
- [ ] **Telegram**: Given the `while has_pending_messages` loop has exited, when a message is enqueued during post-loop cleanup (`ChatActionSender` teardown, `on_complete` callback), then a final drain processes it before `_is_processing` is cleared
- [ ] **Telegram**: Given a user message, session task prompt, or notification prompt is the source, then each follows the same drain guarantee path
- [ ] **REPL**: Given a session task or notification is processed through the coordinator, when a message is enqueued during or after coordinator processing, then the message is drained before the REPL returns to the input prompt
- [ ] **REPL**: Given a user message, session task prompt, or notification prompt is the source, then each follows the same drain guarantee path

### R3 — Ordering

- [ ] Given messages A, B, C are enqueued in that order, when they are processed across turn boundaries, then the coordinator processes them in A, B, C order
- [ ] Given message A is a mid-stream steering message consumed by the active SDK session, when message B arrives after the session ends, then B is processed as the next turn (not reordered ahead of any pending messages)
- [ ] Given messages arrive in rapid succession during the SDK teardown window, when they are all preserved in the main buffer, then they are processed in their original enqueue order

### R4 — Mid-stream message regression

- [ ] Given the SDK is actively processing a turn, when a follow-up message is enqueued, then it is delivered to the SDK as a steering message within the current turn (same behavior as today)
- [ ] Given multiple mid-stream messages arrive during a single turn, when the SDK consumes them, then they are delivered in enqueue order

### Existing behavior preservation

- [ ] (R0) Given `send_message()` is called with an empty buffer, when no message exists, then it returns immediately without side effects
- [ ] (R0) Given a per-message post-processing task is pending from the previous turn, when the next `send_message()` starts, then it awaits the pending task before processing the new message

### Scope boundaries

- [ ] Coordinator shutdown (`__aexit__`) with buffered messages is out of scope — the existing behavior (run post-processing, exit) is preserved; buffered messages during shutdown are not guaranteed
- [ ] Single-channel architecture is assumed — concurrent multi-channel message processing is not addressed (see DLT-052)
