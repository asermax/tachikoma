# pi SDK — verified API surface (1.6.0)

Verified against the installed `@earendil-works/pi-coding-agent` 1.6.0 package: the docs and `.d.ts` files it ships. This is the ground truth for how Tachikoma embeds pi. Re-verify on every pi upgrade. The SDK moves fast between minors, which is why Tachikoma pins the exact version ([ADR-001](../architecture/ADR-001-agent-sdk.md)). The daily-trunk primitives (`branch`/`branchWithSummary`/`AgentSession.refreshContext`/`appendCustomEntry`, the append-only re-seat model that rollback depends on) are listed with their signatures in [the seam table](#daily-trunk-session-tree-seam); each was checked against `dist/core/session-manager.d.ts` at 1.6.0.

## Embedding model

```ts
const modelRuntime = await ModelRuntime.create({ authPath?, modelsPath }); // the model/auth runtime; authPath defaults to <agentDir>/auth.json
const modelRegistry = new ModelRegistry(modelRuntime); // synchronous facade: find(provider, modelId), getApiKeyForProvider(provider), ...
const settingsManager = SettingsManager.create(cwd, agentDir);

const loader = new DefaultResourceLoader({
  cwd, agentDir,
  systemPromptOverride: () => "...",
  additionalExtensionPaths: ["/path/ext.ts"],
  extensionFactories: [(pi) => { /* inline extension */ }],
  additionalSkillPaths: ["/path/skills"],           // merged into discovered skills
  noSkills: true,                                   // drops defaults; added paths still load
  skillsOverride: (current) => ({ skills: [...], diagnostics: current.diagnostics }),
  agentsFilesOverride: (current) => ({ agentsFiles: [...] }),
  promptsOverride: (current) => ({ prompts: [...], diagnostics: current.diagnostics }),
  eventBus,                                          // createEventBus() — shared with host
  settingsManager,
});
await loader.reload();

const { session, extensionsResult, modelFallbackMessage } = await createAgentSession({
  cwd, agentDir,
  model,                              // a pi-ai Model; omitted → from settings, else the first available model
  thinkingLevel: "medium",            // off|minimal|low|medium|high|xhigh|max
  tools: ["read", "bash", "my_tool"], // built-ins: read,bash,edit,write,grep,find,ls,powershell (default: read,bash,edit,write)
  customTools: [defineTool({ ... })],
  excludeTools: [...],
  resourceLoader: loader,
  sessionManager: SessionManager.create(cwd) | .inMemory(cwd) | .continueRecent(cwd) | .open(path) | .forkFrom(srcPath, targetCwd, sessionDir),
  settingsManager: SettingsManager.create(cwd, agentDir) | .inMemory({...}),  // applyOverrides(), flush(), drainErrors()
  modelRuntime,
});
await session.bindExtensions({});     // fires resources_discover, which lets extensions contribute skills and paths
```

Key facts:

- **One long-lived `AgentSession` per conversation** — pi sessions live in-process, with no per-message client recreation or resume bookkeeping. The coordinator holds a session open and replaces it on boundary.
- **`AgentSessionRuntime`** (`createAgentSessionRuntime` + factory using `createAgentSessionServices`/`createAgentSessionFromServices`) owns session _replacement_: `newSession()`, `switchSession(path)`, `fork(entryId, { position: "before"|"at" })`, `importFromJsonl()`. After replacement: `runtime.session` changes, event subscriptions must be re-attached, extensions are rebound (`session_shutdown` → reload → `session_start`).
- `session.prompt(text, { images, streamingBehavior, source, preflightResult })` resolves when the full run finishes. `steer()` / `followUp()` queue during streaming.
- `session.agent.state` can be assigned: `messages`, `tools`, `model` and `thinkingLevel`. `systemPrompt` is read-only at 1.6.0; the prompt is replayed from the transcript's system messages, so it is changed by appending a system message or through `before_agent_start`. `session.agent.waitForIdle()`. `session.refreshContext()` re-syncs `messages` from the session manager's projection, the transcript's source of truth. Assigning `messages` by hand does not replace the persisted context: the request is still projected from the session manager.
- Compaction is built in: `session.compact(instructions?)`, auto-compaction via settings, extension hooks to customize.

### Session events (`session.subscribe`)

`agent_start/end`, `agent_settled` (carries `aborted`), `turn_start/end`, `message_start/update/end` (with `assistantMessageEvent.type === "text_delta" | "thinking_delta"`), `tool_execution_start/update/end` (`durationMs` on end), `queue_update`, `compaction_start/end`, `auto_retry_start/end`. This is what channels consume (maps to domain `AgentEvent`s).

### ExtensionAPI methods

`registerTool` (works at load time AND at runtime — immediate availability, no reload; `promptSnippet` + `promptGuidelines` feed the system prompt; `prepareArguments` for legacy-shape migration; `terminate: true` result skips the follow-up LLM call — structured-output pattern), `registerCommand` (slash commands w/ completions), `registerShortcut`, `registerFlag`/`getFlag`, `sendMessage(msg, { deliverAs: "steer"|"followUp"|"nextTurn", triggerTurn })`, `sendUserMessage(content, { deliverAs })`, `appendEntry(customType, data)` (session-persisted state, not in LLM context), `setSessionName`/`getSessionName`, `setLabel`, `getCommands`, `registerMessageRenderer`, `exec(cmd, args, { signal, timeout })`, `getActiveTools`/`getAllTools`/`setActiveTools`, `setModel`, `getThinkingLevel`/`setThinkingLevel`, `events` (shared bus), `registerProvider`/`unregisterProvider`.

### ExtensionContext (`ctx` in handlers)

`ui` (notify/confirm/select/input/editor/setStatus/setWidget — TUI/RPC-bound; guard with `ctx.hasUI`, `ctx.mode`: `"tui"|"rpc"|"json"|"print"`), `cwd`, `sessionManager` (read access: `getEntries/getBranch/getLeafId/getLabel...`), `modelRegistry`, `model`, `signal` (agent abort signal), `isIdle()`, `abort()`, `hasPendingMessages()`, `shutdown()`, `getContextUsage()`, `compact()`, `getSystemPrompt()`, `isProjectTrusted()`.

`ExtensionCommandContext` (commands only) adds: `waitForIdle()`, `newSession({ parentSession, setup(sm), withSession(ctx) })`, `fork(entryId, { position, withSession })`, `navigateTree(targetId, { summarize, customInstructions, label })`, `switchSession(path, { withSession })`, `reload()`, `getSystemPromptOptions()`.

**Footgun:** after session replacement, captured `pi`/`ctx`/`sessionManager` objects from the old session are stale and throw. Only use the fresh `ctx` passed to `withSession`; capture only plain data across the boundary.

### Tool arguments are validated as JSON Schema

Pi's agent loop calls `validateToolArguments` (`@earendil-works/pi-ai`) before a tool's `execute`, whatever built the schema: TypeBox schemas are JSON Schema and work unchanged. Loosely typed arguments are coerced first — numeric strings to numbers, `"true"` to `true`, a single value to a one-item array, `null` in an optional property dropped. A failure never reaches `execute`; the model receives `Validation failed for tool "<name>":` followed by one `  - <path>: <message>` line per error.

TypeBox features outside JSON Schema give no compile-time signal and do not apply to tool arguments:

- `Type.Refine()` refinements are not run. Check such constraints in `execute`.
- Codecs (`Type.Codec()`) do not decode: `execute` receives the JSON value.
- `Type.Void()` and `Type.Function()` reject every argument a model can send.
- A `Type.BigInt()` parameter is converted, not rejected (`"42"` to `42n`, `null` to `0n`), and `Type.Undefined()` takes `null` as `undefined`.

`tests/schema-guard.test.ts` fails on a registered schema that is not plain JSON Schema. It reads the JSON, so it cannot see a refinement or a codec: those need a test of the tool's own.

## Sessions on disk

JSONL trees at `~/.pi/agent/sessions/--<cwd-slug>--/<timestamp>_<uuid>.jsonl`; entries have `id`/`parentId`; entry types include `session` (header, may carry `parentSession`), `message`, `thinking_level_change`, `model_change`, `usage` (model-attributed usage outside the model context, such as a cache warm), `compaction`, `branch_summary`, `custom` (extension state via `appendEntry`), `custom_message`, `context_edit` (an append-only edit to an earlier entry's contribution to the model context), `label`, `session_info`.

Tachikoma reads entries by matching the types it knows — `message`, `branch_summary`, its own `custom` entries — and skips every other type, so an entry type it does not know, `context_edit` among them, passes through its filters untouched. Tachikoma writes no context edits.

`SessionManager` instance API: `getEntries/getTree/getLeafEntry/getEntry/getChildren/getLabel/appendLabelChange/appendMessage/branch(entryId)/branchWithSummary(id, summary)/createBranchedSession(leafId)/getSessionFile`. Static: `list(cwd)`, `listAll(sessionDir?)`, `findById(cwd, id)`, `forkFrom(srcPath, targetCwd, sessionDir?)` — reads the source read-only and writes a fresh history-seeded session file (`parentSession` points at the source).

**Post-processing patterns (two shapes):**

- **Conversation-aware (fork-continue):** for work that benefits from the live conversation — memory extraction, core-context — fork the just-ended session with `SessionManager.forkFrom` (wrapped by `AgentManager.forkAndContinue`) and send a follow-up user instruction. The same assistant continues with the full history live and persona intact; pass a `tools` allowlist to restrict it (the `tools` option is independent of the system prompt, so persona survives). The source transcript is never mutated.
- **Context-free (one-shot):** for work that needs no conversation context — boundary classification, rolling summaries, commit messages, nightly store maintenance — run `pi-ai` `completeSimple()` from `/compat` or a bare in-memory `createAgentSession` with a tool allowlist. `terminate: true` tool results give structured output.

## Cache warming between runs

pi keeps an eligible provider prompt cache warm by re-sending the request that wrote it, capped at one output token, before its entry expires. `cacheWarming` is `"off"`, `"streaming"` or `"idle"` and defaults to `"idle"`: caches warm during a run and, once it settles, for up to 30 minutes. `"streaming"` warms only during a run. It is a global setting only, read from `{workspace}/.tachikoma/pi/settings.json` (the agent directory's `settings.json`); the project-level `.pi/settings.json` cannot set it. Tachikoma sets no override, so pi's `idle` default applies.

- **When a refresh is sent.** Only when the model declares a prompt-cache lifetime and pi expects the refresh to save at least $0.05 (`CACHE_WARMING_MINIMUM_EXPECTED_SAVINGS`). Both phases are bounded from the request that started them: warming during a run ends after one hour, warming between runs after 30 minutes.
- **What a refresh leaves behind.** Each one is persisted as a `usage` entry of kind `cache_warm` and emitted as `entry_appended`. It counts toward pi's session totals and never enters the model context. Tachikoma's per-exchange usage is summed from the exchange's own assistant messages, so a refresh does not change it.
- **Which sessions warm.** Only the long-lived trunk sits idle after an exchange. Tachikoma disposes forks and headless runs when they finish, and `session.dispose()` cancels warming.
- **Per-session control.** An extension handling `cache_warming_decision` can return `{ action: "warm" }` or `{ action: "stop" }` to override each decision. Tachikoma registers no such handler.

## Skills

pi implements the **Agent Skills standard** (agentskills.io) — `SKILL.md` + YAML frontmatter (`name`, `description`, optional `license`, `compatibility`, `metadata`, `allowed-tools`, `disable-model-invocation`), the same format Tachikoma's workspace skills use. Discovery: `~/.pi/agent/skills/`, `~/.agents/skills/`, `.pi/skills/`, `.agents/skills/` (ancestors, post-trust), settings `skills` array, packages, `resources_discover` event (`skillPaths`). Progressive disclosure: descriptions in system prompt, agent `read`s SKILL.md on demand; `/skill:name` commands force-load. Missing description ⇒ skill not loaded; name collisions keep first found. Loader options (verified against 1.6.0 `dist/core/resource-loader.js`, guarded by the real-loader test in `tests/agent/force-load-skills.test.ts` — re-check on upgrade): `additionalSkillPaths` merges the given directories into discovered skills **even under `noSkills: true`** (a nonexistent added path is a diagnostic, not a throw), and `noSkills` plus non-empty added paths loads with `includeDefaults: false` — so an isolated run's catalog is exactly the added directories' skills. The skills-catalog _section_ renders in the system prompt only when a tool that can read a file, `read` or `bash`, is active (pi gates the catalog behind a reader because progressive disclosure loads bodies through it) — a run with neither (e.g. skill-evolution's proposal agent, whose allowlist holds only its own tools) still has the skills in `systemPromptOptions.skills` for extension code to read, and force-loads their content through a `before_agent_start` hidden message instead.

**Consequences for Tachikoma:** progressive disclosure handles base detection; a per-turn conversation-aware classifier (`before_agent_start` in the skills extension) augments it by recommending the skills most relevant to the latest message for the agent to load (it does not replace pi's discovery/loading); skill refresh is `ctx.reload()` rather than a filesystem watcher; skill `dependencies` and bundled agent definitions are not part of the standard — bundled agents can be supported via a subagent-style extension (see `examples/extensions/subagent/`, which discovers `agents/*.md` with frontmatter and spawns isolated `pi` processes).

## What pi does NOT provide (stays ours)

- **MCP, codemode and tool search**: Tachikoma loads none of them. pi ships MCP, `codemode` and `tool_search` as built-in extensions and its CLI loads them by default, but SDK sessions do not load its built-in MCP, codemode and tool-search extensions: they load only when the host adds `createMcpExtension()`, `createCodemodeExtension()` and `createToolSearchExtension()` to the `DefaultResourceLoader`'s `extensionFactories`, which Tachikoma does not. Agent tools are `pi.registerTool()` / `customTools` registrations.
- **Scheduling/cron, idle gating, buffered delivery** — host concern (croner + our buffer; inject via `pi.sendMessage`/`sendUserMessage` with `deliverAs` + `triggerTurn`).
- **Channels** (Telegram/REPL) — host consumes `session.subscribe()`; extension `ctx.ui` calls only function in pi's own TUI/RPC modes, so host-facing UX flows through our channel layer instead.
- **Cross-session orchestration** — boundary detection, session registry/recovery, topic resume: ours, on top of `SessionManager`/`AgentSessionRuntime`.
- **Database** — ours (drizzle + node:sqlite).

## Daily-trunk session-tree seam

The daily-trunk model (ADR-014) relies on these `SessionManager` primitives and one `AgentSession` method — re-verify each on a pi upgrade. They are wrapped in `src/agent/session-tree.ts` (tree ops) and `AgentManager.shadowFork` (classification fork):

| Primitive                                              | Signature                                                                                                                                      | Used for                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `branchWithSummary`                                    | `(branchFromId: string \| null, summary: string, details?: unknown, fromHook?: boolean, usage?: Usage) => string`                              | Collapse the current branch into a `branch_summary` entry at the base; returns the new summary id (advanced base). Does NOT record the abandoned leaf — we store `originalLeafId` in `details`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| `createBranchedSession`                                | `(leafId: string) => string \| undefined`                                                                                                      | Write a new session file with only the root→leaf path; returns the new file path. Backs the shadow-fork classifier and per-branch extraction. **DESTRUCTIVE IN PLACE:** it repoints the manager it runs on at the new branch file and rebuilds that manager's entry index from only the branch path — so it MUST run on a `SessionManager` loaded fresh from disk, NEVER on a live session's manager. Run on a live session it silently turns that session into the branch: other branches become unreachable (the next call throws `Entry <id> not found`) and later appends — including idempotency markers — land in the wrong file. Always go through `AgentManager.branchFile`/`shadowFork`, which load a detached manager. |
| `getBranch`                                            | `(fromId?: string) => SessionEntry[]`                                                                                                          | Walk an entry to root in path order — branch enumeration / extraction slicing.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `appendCustomEntry`                                    | `(customType: string, data?: unknown) => string`                                                                                               | Persist trunk/branch/boomerang state + idempotency markers out of LLM context.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `appendCustomMessageEntry`                             | `(customType: string, content: string \| (TextContent \| ImageContent)[], display: boolean, details?: unknown) => string`                      | Inject the related-branch pointer into LLM context with `display: false`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `getEntries` / `getEntry` / `getLeafId` / `branch(id)` | `getEntries(): SessionEntry[]`, `getEntry(id): SessionEntry \| undefined`, `getLeafId(): string \| null`, `branch(branchFromId: string): void` | Rebuild branch records on reload; re-seat the leaf onto the current base after `open` (pi sets the leaf to the LAST file entry, not the active tip).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `AgentSession.refreshContext`                          | `() => void`                                                                                                                                   | Re-sync the agent's in-memory transcript from the leaf path's projection (`buildSessionProjection()`), with the bookkeeping pi keeps beside it. The seam calls it after every leaf move, which bypasses pi's own re-sync.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `getHeader`                                            | `() => SessionHeader \| null`                                                                                                                  | The session's creation instant (`header.timestamp`), wrapped by `sessionCreatedAt`. Recovers a stale trunk's true calendar day on a late close (`localDay(header.timestamp)`) instead of defaulting to the recovery day.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |

**A leaf move is two steps.** pi builds every request from the session file: `buildSessionProjection()` re-projects the leaf path on each request, and the tools and prompt sections the model may see are replayed from the system messages on that path (pi 0.86.0). Whether anything new must be declared is decided against the agent's in-memory transcript (`session.agent.state.messages`). pi re-syncs that transcript after each change it commits through the session layer — queued messages, compaction, recovery omissions, its own `navigateTree()` — and a write made through `SessionManager` directly bypasses that layer. A leaf move is the case that matters: it puts the leaf on a different path while the transcript still describes the old one. So the seam's leaf-moving wrappers (`branchWithSummary`, `reseatLeaf`) end with `session.refreshContext()`, pi's own re-sync. The seam's raw appends (`appendCustomEntry`, `appendCustomMessageEntry`) do not call it: they extend the current path and cannot change its declarations. An in-context append stays out of the in-memory transcript until one of those re-syncs runs; the request itself is projected from the file, so it carries the entry regardless. Without the re-sync, a re-seat onto a path with no system message — the trunk's summary chain — sends requests with no tools while the in-memory transcript still reports them as declared. With it, pi persists one system message holding every prompt section and tool declaration as the first entry under the new base, at the next request. The re-sync covers `messages` only; the projection also derives `thinkingLevel` and `model` from the path, which Tachikoma does not read (the model is passed at open). On upgrade, re-check every place pi consults the in-memory transcript while building a request, and every write the seam makes through `SessionManager` directly.

`AgentManager.shadowFork(sourceFile, { systemPrompt, tier })` reuses the existing `open({ sessionFile, bare: true, tools: [] })` path rather than pi's lower-level `createAgentSessionServices`/`createAgentSessionFromServices` two-call construction — `bare` + empty `tools` already yields an extension-free, tool-free headless session, and `open` composes the loader/model/tier. The fork file is deleted on `dispose`. The source file is opened in a separate `SessionManager` and is never mutated (R6).

`AgentManager.branchFile(sourceFile, leafId)` is the non-fork sibling: it just cuts the root→leaf branch into a new file (for per-branch memory extraction and `ask_branch`) via the same detached-manager rule, returning the path (the caller opens/forks it separately). Both funnel `createBranchedSession` through `loadDetachedSession`, which is the single place that enforces "never branch a live session's manager."

## Misc verified utilities

`parseFrontmatter`/`stripFrontmatter`, `withFileMutationQueue(path, fn)` (parallel tool calls mutating the same file MUST use it), `truncateHead/truncateTail/DEFAULT_MAX_BYTES (50KB)/DEFAULT_MAX_LINES (2000)`, `StringEnum`, `isToolCallEventType`, `createCodingTools/createReadOnlyTools/create{Read,Bash,PowerShell,Edit,Write,Grep,Find,Ls}Tool` with pluggable `operations` (remote/sandbox exec) and bash `spawnHook`, run modes (`InteractiveMode`, `runPrintMode`, `runRpcMode`).

`StringEnum` for a string union — use it instead of `Type.Union` of literals (Google API compat) — is Tachikoma's own, in `src/util/string-enum.ts`. It produces the same `{ type: "string", enum: [...] }` as pi-ai's own builder. pi-ai 1.6.0 still exports a `StringEnum`, but as a pi-schema `Schema`: it does not type-check inside `Type.Object` and gives no TypeBox `Static` union. Do not import that one.

`validateToolArguments` and `validateToolCall` are exported from `@earendil-works/pi-ai`, not from the coding-agent root.

API keys: a runtime override (`ModelRuntime.setRuntimeApiKey(providerId, key)`) is a non-persistent overlay on the credential store; otherwise a stored credential in `auth.json` wins, then the first set provider variable such as `ANTHROPIC_API_KEY`. A provider declared in `models.json` takes its `apiKey` there (a literal, a `"$NAME"` interpolation or a `"!command"` output). OAuth (Claude Pro/Max) is supported through `/login`-style flows.
