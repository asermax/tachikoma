- Modify: `src/tachikoma/skills/registry.py` (`_validate_deps`, lines 199–248)

The pass runs **before** edge collection, so the workflow's other steps cannot contribute partial edges. Mirror the warning shape used by existing rejection logs in this file.

```python
# Before detect_cycles call:
# Mutex pre-pass: a step cannot declare both `composes` and `loop`.
mutex_violations: list[tuple[str, str]] = []
for vertex, wf_def in list(self._workflows.items()):
    for step in wf_def.steps:
        if step.composes and step.loop:
            _log.warning(
                "Workflow rejected: step declares both `composes` and `loop`: ...",
                # ... structured kwargs
            )
            mutex_violations.append(vertex)
            break
for v in mutex_violations:
    self._workflows.pop(v, None)
```

#### Step 4.3: Initialize `mutable_loop_state` from chain records

> **Order rationale**: This step lands BEFORE the gate logic (Step 4.4) because Steps 4.5–4.8 all read from `mutable_loop_state` and write back to it. Establishing the in-memory tracking first keeps the rest of the diff focused on behavior.

        dict(state.loop_state) if state.loop_state is not None else None

**Write discipline (binding contract for downstream steps):** every cascade branch that queues an `UpdateState` with a non-None `loop_state` value MUST also write the same value into `mutable_loop_state[layer_id]` immediately before queuing. ## Notes

- **`mutable_loop_state` is the bridge between Batch 3 and Batch 4.** Batch 3 introduces the column and the `UpdateState.loop_state` field; Batch 4 introduces the in-memory cascade tracking that writes to that field. **Step 4.3 establishes the in-memory tracking before any consumers (4.5, 4.6, 4.8) read or write it; every cascade branch that queues `UpdateState(loop_state=...)` MUST also update `mutable_loop_state[layer_id]` immediately before queuing — this paired-write discipline is the explicit contract of Step 4.3 and is restated in Steps 4.5, 4.6, 4.8.**
- **5-gate validation order** (Step 4.4) is the trickiest part of Batch 4. The design's Cross-Layer Contracts section (lines 158–171) is the authoritative reference; deviations risk breaking R2 and R8 simultaneously.
- **Snapshot-time loop detection** (Batch 1 Step 1.3 → Batch 4 Steps 4.7, 4.8): the cascade engine reads `step_info.get("loop")` from the snapshot, not the live registry. Iteration children's snapshots include the field via `_step_to_snapshot` extension in Batch 1, so nested loops work without a special-case path.
- **Atomicity discipline** (Batch 4): every validation gate must short-circuit with `_error_response` *before* any `MutationBatch.append`. Any "queue then validate" pattern would violate spec R14 and the AC "validation errors are atomic — no partial state".
- **Halt invariant** (Step 4.7): on auto-start halt, the loop step's `step_states` entry stays PENDING and the parent's `current_step` remains the just-finalized step — NOT the loop step. This is verified by `test_halt_does_not_advance_current_step`.
- **Breadcrumb suffix vs Loop-step block** (Batch 5): the breadcrumb is the moment-to-moment indicator on every tool response; the `### Loop step` block is the recovery surface in `get_workflow_state`. Both surface from the same `loop_state` data — no duplication of source.
- **Mutex pre-pass ordering** (Batch 2 Step 2.4): the mutex pre-pass must run *before* `detect_cycles`. If a workflow declares both `composes` and `loop` on the same step, `_composition_edges` would yield ambiguous edges; removing the workflow up-front guarantees the unified graph never sees those partial edges.
- **`composition.py` is touched by Batches 2 and 3.** Batch 2 adds `_composition_edges` and modifies `detect_cycles`/`validate_references`; Batch 3 adds `loop_state` to `UpdateState` (and possibly `halted_at_loop_step` to `CascadeOutcome` if Approach A is chosen for Step 4.7). Diffs are non-overlapping; no merge conflict expected.
