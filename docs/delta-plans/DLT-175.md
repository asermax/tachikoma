# Implementation Plan: DLT-175 — Daily session with collapsible topic branches

**Delta Spec**: [../delta-specs/DLT-175.md](../delta-specs/DLT-175.md)
**Delta Design**: [../delta-designs/DLT-175.md](../delta-designs/DLT-175.md)

> Big-picture: a coordinated refactor that makes the **day** the unit of conversation. Topic shifts
> become collapsible branches on a daily trunk; all conversational state moves from the `sessions`
> DB table to the pi session file + `app_state`. Batches are ordered bottom-up: additive foundations
> (B1–B3), the coordinator cutover that flips the model and deletes the registry (B4), then the
> schema migration + enhancements that build on the new model (B5–B8).
>
> **Verification baseline**: `just check` (lint + typecheck + test) must pass at the end of every
> batch. Additive batches (B1–B3) keep the old machinery wired, so the suite stays green; B4 is the
> cutover where old tests are rewritten alongside the code they cover.

  - guard: skip (return `continue`) when the current branch has **no completed assistant exchange** since the base (empty-branch guard), and for system-origin / mid-exchange inputs (those never reach here — coordinator gate, but assert defensively).

## Batch 4: Coordinator cutover — ✓ Done
Depends on: Batch 2, Batch 3

The big-bang. The coordinator stops owning a `SessionRecord`-backed session and owns the daily trunk
keyed on the `app_state` pointer. The registry and the superseded machinery are deleted; the
`sessions` **table definition stays** (physically dropped in B5). Tests for the removed/old paths are
rewritten here.

> **Typecheck-window invariant (resolves reviewer Critical #1).** The `sessions` table is retained
> through B4 *precisely so* the `SessionRecord` type still compiles for the consumers B4 does not
> touch: `ExchangeContext.session: SessionRecord`, `InboundContext.session: SessionRecord | null`,
> and the Telegram store (`sessionId`). B4 changes **only** `PostProcessorContext` and the trimmed
> `SessionsApi` members — and updates **every** consumer of those changed members within B4. It does
> **not** retire `SessionRecord` itself. `just check` is green at the end of B4. The full retirement
> of `SessionRecord`/`sessionId` (ExchangeContext, InboundContext, telegram store, `tests/tasks/session-delivery.test.ts`)
> happens atomically in B5 Step 19–20, in the same batch that drops the table.

### Context & Research
- `docs/delta-designs/DLT-175.md` — Shape S9/S12/S15; "Components / Implementation Structure" (coordinator + `trunk.ts`); "Data Flow" (inbound + startup recovery); "Key Decisions" (registry-free lifecycle; queue deliveries until a trunk is live; the **Ordering** paragraph — drain gate extended from `exchanging` to `exchanging || !trunkLive`).
- `docs/delta-specs/DLT-175.md` — AC groups "Daily trunk lifecycle", "State persistence without a registry", "Removed behavior"; R13/R17.

#### Step 18: Remove the superseded machinery (registry deletion deferred to B5)

- Create/modify: remove `src/extensions/boundary/summary.ts` + `idle.ts` + `detector.ts`; remove rolling-summary/idle-close registration; delete the coordinator's `resumeSession`/`injectBridgingContext`/`pendingContext`/bridging hook, `closeActiveSessionIfIdle`, the quarantine tap + `markErrored`, and the `forceNew`/`resumeSessionId` fast-paths (the new boundary middleware drives collapse on the live trunk instead).

Full deletion (registry.ts, table, orphaned `SessionsApi` methods, `SessionRecord`) is the atomic B5 Step 19–20 unit.
