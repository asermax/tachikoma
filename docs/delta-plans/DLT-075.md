## Batch 2: Per-message pre-processing pipeline — ⧗ Pending
Depends on: Batch 1

### Context & Research
- `src/tachikoma/message_post_processing.py` — structural template: same parallel execution + error isolation pattern
- `src/tachikoma/pre_processing.py` — `ContextProvider` ABC and `ContextResult` (now with metadata field)
- Design doc S1 (per-message pipeline), S4 (unified provide)

### Steps

#### Step 6: Create MessageContextProvider ABC and MessagePreProcessingPipeline

- Create: `src/tachikoma/per_message_pre_processing.py`
- What to do:
  - Define `MessageContextProvider(ContextProvider)` ABC with abstract method:
    ```python
    async def provide(self, message: str, *, existing_entries: list[SessionContextEntry]) -> list[ContextResult]:
    ```
  - Add `MessagePreProcessingPipeline` class mirroring `MessagePostProcessingPipeline`:
    - Constructor: empty `_providers` list + `asyncio.Lock`
    - `register(provider)`: appends to list
    - `run(message, *, existing_entries)`: runs all providers in parallel via `asyncio.gather(return_exceptions=True)`, collects successful non-None results (flattening lists), logs failures per DES-002 using `_log.exception()` with provider name
    - Named logger bound to `component="per_message_pre_processing"`
- Test: Unit tests for empty providers, single provider, parallel execution, error isolation, `existing_entries` pass-through

#### Step 7: Add skill name extraction and agent derivation helpers

- Modify: `src/tachikoma/per_message_pre_processing.py`
- What to do:
  - Add `extract_skill_names(entries: list[SessionContextEntry]) -> set[str]`: reads `entry.metadata["skill_name"]` for entries where `owner="skills"` and metadata is not None. Gracefully handles entries without metadata (skips them).
  - Add `derive_agents_from_entries(entries: list[SessionContextEntry], registry: SkillRegistry) -> dict[str, AgentDefinition]`: calls `extract_skill_names(entries)`, then for each name calls `registry.get_agents_for_skill(name)`, accumulating into a dict. Silently skips names not in registry with debug log (deleted skills).
  - Import `SkillRegistry` from `skills.registry` and `AgentDefinition` type.
- Test: Unit tests for extraction (empty entries, entries without metadata, entries with skill metadata, mixed). Unit tests for derivation (empty, with agents, with deleted skills).

#### Step 8: Modify SkillsContextProvider for per-message evaluation

- Modify: `src/tachikoma/skills/context_provider.py`
- What to do:
  - Change `SkillsContextProvider` to extend `MessageContextProvider` (from `per_message_pre_processing`) instead of `ContextProvider`
  - Update `provide()` signature to `provide(self, message: str, *, existing_entries: list[SessionContextEntry] | None = None) -> list[ContextResult]`
  - At the start of `provide()`, call `extract_skill_names(existing_entries or [])` to get loaded skill names
  - Filter `self._registry.skills` to exclude loaded names before building `skills_list`
  - If no unloaded skills remain after filtering, return `[]` immediately — no LLM call (R8)
  - Remove the combined XML assembly (the block that concatenates multiple skills into one string with `\n\n`.join)
  - Instead, for each detected skill, create a separate `ContextResult(tag="skills", content=skill_xml_block, metadata={"skill_name": skill_name})`
  - Return the list of individual ContextResults
  - Remove `agents` field from all returned ContextResults (agents=None, derived from entries)
- Test: Update existing tests to work with new signature (list return, existing_entries param). Add new tests for filtering, R8 skip, one-entry-per-skill, metadata on results.

## Notes

- `extract_skill_names` and `derive_agents_from_entries` live in `per_message_pre_processing.py` (not coordinator) for independent testability and cohesion with the pipeline module
- `ContextProvider` base class is unchanged — `MessageContextProvider` extends it with an optional keyword argument
- `context/assembly.py` requires no changes — `build_system_prompt()` already wraps entries by owner tag, so one-entry-per-skill produces multiple `<skills>` blocks naturally
- DLT-076 (memory re-evaluation) can plug into `MessagePreProcessingPipeline` by registering a memory provider — no coordinator changes needed
- No migration of existing entries needed — metadata is nullable and gracefully handled as None
- `ContextResult.metadata` flows through the pipeline to `save_context_entries` without coordinator interpretation
