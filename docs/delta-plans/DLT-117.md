## Batch 1: Data Layer — IncomingMessage envelope + TaskDefinition model + Schema migration — ⧗ Pending
Depends on: — (none)

### Context & Research
- `docs/delta-specs/DLT-117.md` R0, AC "Task Definition Model" — requirements for skills field on task definitions
- `docs/delta-designs/DLT-117.md` S1, S2, S3, Modeling section — IncomingMessage frozen dataclass, TaskDefinition extension, schema migration
- `src/tachikoma/tasks/model.py` — `TaskDefinition` (line 91), `TaskDefinitionRecord` (line 136), JSON column pattern from `ScheduleConfig` (lines 38-87, 147), existing frozen dataclass pattern
- `src/tachikoma/database.py` — pragma-based migration pattern (lines ~100-317)
- `src/tachikoma/coordinator.py` — `enqueue(text: str)` at line 1095, consumed as `text` in `send_message()` line 435

### Steps

#### Step 1: Create IncomingMessage frozen dataclass

- Create: `src/tachikoma/message.py`
- What to do: Define a frozen dataclass with `text: str` and `pinned_skills: tuple[str, ...] = ()`. This is the new boundary type at the coordinator enqueue boundary.
- Test: Instantiate with text only, with text+pinned_skills, verify defaults.

#### Step 2: Add skills field to TaskDefinition and TaskDefinitionRecord

- Modify: `src/tachikoma/tasks/model.py`
- What to do:
  - Add `skills: tuple[str, ...] = ()` to `TaskDefinition` dataclass (after `created_at`, before closing)
  - Add `skills: Mapped[str] = mapped_column(Text, default="[]")` to `TaskDefinitionRecord` (JSON array string)
  - Update `TaskDefinitionRecord.to_domain()` to deserialize: `skills=tuple(json.loads(self.skills))`
- Test: Create `TaskDefinition` with skills, verify round-trip through `TaskDefinitionRecord.to_domain()`. Create without skills, verify default `()`.

#### Step 3: Add schema migration for skills column

- Modify: `src/tachikoma/database.py`
- What to do: Add a pragma check for `skills` column on `task_definitions` table. If missing, execute `ALTER TABLE task_definitions ADD COLUMN skills TEXT NOT NULL DEFAULT '[]'`. Follow existing pattern (e.g., `since` column migration around line 246).
- Test: Run `just test tests/test_database.py` — verify migration applies cleanly.

#### Step 4: Update coordinator.enqueue() to accept IncomingMessage

- Modify: `src/tachikoma/coordinator.py`
- What to do:
  - Change `enqueue(self, text: str)` signature to `enqueue(self, msg: IncomingMessage)` (import from `tachikoma.message`)
  - Update `self._message_buffer.put_nowait(text)` to `self._message_buffer.put_nowait(msg)`
  - In `send_message()`, change `text = self._message_buffer.get_nowait()` to `msg = self._message_buffer.get_nowait()` and extract `text = msg.text`. Keep `pinned_skills = msg.pinned_skills` available for the pipeline (will be wired in Batch 4).
- Test: Run `just test tests/test_coordinator.py` — verify compilation and basic tests pass (they will need to construct `IncomingMessage` now).

#### Step 5: Update all enqueue callers to construct IncomingMessage

- Modify: `src/tachikoma/repl.py` — wrap `text` in `IncomingMessage(text=...)` at lines 164, 234
- Modify: `src/tachikoma/telegram/__init__.py` — wrap `text`/`description` in `IncomingMessage(text=...)` at lines 770, 774, 821, 825, 897
- Modify: `tests/test_coordinator.py` — update all `coordinator.enqueue("...")` calls to `coordinator.enqueue(IncomingMessage(text="..."))`
- Modify: `tests/test_repl.py` — update any enqueue calls to construct IncomingMessage
- Modify: `tests/telegram/test_channel.py` — update any enqueue calls to construct IncomingMessage
- What to do: All callers construct `IncomingMessage(text=...)` with empty `pinned_skills` (default). No behavior change for regular user messages.
- Test: `just test` — all existing tests pass with the new envelope.

  - Add module-level `_decode_skills(raw: str) -> list[str]` helper in `tools.py` following DES-006 `_decode_paths` pattern (JSON parse, validate array of strings, clear error messages). Module-level for direct testability.

#### Step 7: Wire skills into create_task handler

- Modify: `src/tachikoma/tasks/tools.py` — `create_task` handler (line 312)

  - After parsing `CreateTaskArgs`, decode `parsed.skills` via `_decode_skills` if non-None

  - Pass `skills=tuple(decoded_skills)` to `TaskDefinition` constructor

  - Update tool description string to document `skills` parameter with example: `'["skill-a", "skill-b"]'`
- Test: Create task with valid skills, with unknown skills (verify warning), without skills (backward compatible).

#### Step 8: Wire skills into update_task handler

- Modify: `src/tachikoma/tasks/tools.py` — `update_task` handler (line 425)
- What to do:
  - Decode `parsed.skills` if non-None
  - Validate against registry, collect warnings
  - Add `skills=tuple(decoded_skills)` to updates dict
  - Include warnings in response text
  - Handle `skills='[]'` as explicit clear
  - Handle omitted `skills` as no-change (existing behavior for optional fields)
  - Update tool description string to document `skills` parameter
- Test: Update with skills, clear skills with `[]`, omit skills (no change), update with unknown skills.

#### Step 9: Display skills in get_task and list_tasks

- Modify: `src/tachikoma/tasks/tools.py` — `get_task` handler (line 237) and `list_tasks` handler (line 178)
- What to do:
  - `get_task`: If `d.skills` is non-empty, add a `- Skills: skill-a, skill-b` line after the existing fields. If empty, omit the line.
  - `list_tasks`: If a definition has non-empty skills, append a skill count or names indicator to the entry line (e.g., `[2 skills: research, planning]`).
- Test: `get_task` with skills shows them, without skills omits section. `list_tasks` includes skill indicator.

#### Step 10: Pass SkillRegistry to create_task_tools_server

- Modify: `src/tachikoma/tasks/tools.py` — `create_task_tools_server` signature (line 147)
- Modify: `src/tachikoma/coordinator.py` — caller of `create_task_tools_server` (passes `skill_registry`)
- Modify: `src/tachikoma/tasks/executor.py` — caller of `create_task_tools_server` (passes `self._skill_registry`)
- What to do: Add `skill_registry: SkillRegistry | None = None` parameter to the factory. Pass it through to tool closures for validation. Update callers to pass the registry.
- Test: Verify existing tests still pass (registry is optional for backward compat).

#### Step 11: Update SYSTEM_PREAMBLE_TEMPLATE with skills parameter

- Modify: `src/tachikoma/context/loading.py` — Tasks section (around line 282)

- `src/tachikoma/skills/registry.py` — `SkillRegistry.resolve_chain()` (line 146), raises `KeyError` for unknown names

### Steps

#### Step 12: Add pinned_skills parameter to MessageContextProvider.provide()

- Modify: `src/tachikoma/per_message_pre_processing.py`
- What to do:
  - Add `pinned_skills: tuple[str, ...] = ()` parameter to `MessageContextProvider.provide()` abstract method
  - Add same parameter to `MessagePreProcessingPipeline.run()`
  - Thread `pinned_skills` from `run()` through to each provider's `provide()` call in `_run_one()`
- Test: Verify existing tests still pass (default empty tuple, no behavior change).

#### Step 13: Implement pinned skill resolution in SkillsContextProvider.provide()

- Modify: `src/tachikoma/skills/context_provider.py`
- What to do: Before the existing classification logic in `provide()`:
  - If `pinned_skills` is non-empty, resolve each via `self._registry.resolve_chain(name)`
  - Catch exceptions on unknown skills, log WARNING, skip
  - Dedup resolved skills across chains (first-seen wins, same as existing classification logic)
  - Emit `ContextResult` entries with `tag=SKILLS_OWNER`, `content=render_skill_block(skill)`, `metadata={SKILL_NAME_META_KEY: skill.name}` (shape-identical to classified entries per ADR-011)
  - Add pinned skill names to `loaded_names` so the existing classification logic naturally skips them
  - If no unloaded skills remain after pinning, return pinned results only (skip classification)
  - Otherwise combine: pinned results first, then classification results
- Test: Unit test with mock registry — pinned skill resolves, unknown skill logs warning, transitive deps expand, dedup works, classification skips pinned skills.

#### Step 14: Update SkillsContextProvider status_message for pinned skills

- Modify: `src/tachikoma/skills/context_provider.py`
- What to do: Update `status_message()` to reflect pinned skills in the status when they are loaded (e.g., "Loaded 2 pinned + 1 classified skills").
- Test: Verify status messages for pinned-only, classified-only, and mixed scenarios.

- Test: Verify channels construct `IncomingMessage` with pinned skills from session task items.

#### Step 18: Wire IncomingMessage.pinned_skills through coordinator pipeline

- Modify: `src/tachikoma/coordinator.py`

  - This threads the pinned skills through to `SkillsContextProvider.provide()` which handles resolution (Batch 3)
- Test: Verify coordinator passes pinned skills through to pipeline. Integration test with mock pipeline.
