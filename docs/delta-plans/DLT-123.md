> **Batch status markers**: ⧗ Pending → ⧗ Implementing → ✓ Done. Updated by the implementing agent as it progresses.

> **Structure note (2 batches, not 3):** The original scope sketch was foundation / extraction /
> maintenance. Research into `layout.ts` showed a hard constraint: `ensureMemoryLayout` creates
> directories from `MEMORY_STORES` and writes indexes from `INDEXED_STORES` via `writeFile` (which
> throws ENOENT on a missing parent), so `learnings` must join **both** sets at once. The moment it
> joins `MEMORY_STORES`, it activates (a) the maintenance iteration (`prunePhase`/`runStoreMaintenance`
> loop over `MEMORY_STORES`) and (b) a would-be third extraction fork (`extractBranches` still loops
> `MEMORY_STORES`, and `STORE_INSTRUCTIONS["learnings"]` is undefined → crash). So the learnings
> maintenance prompt and the `EXTRACTION_STORES` loop-switch must land *with* the store-set change.
> Maintenance is therefore folded into Batch 1; only the *extraction instruction* (the topics fork
> learning to classify/write learnings) is deferred to Batch 2. Every batch boundary is correct and green.

## Batch 1: Establish the learnings store (layout, injection, maintenance) + extraction neutralization — ✓ Done

Covers design shape parts **S1** (store-set split), **S2** (context injection), **S6** (learnings

  ```ts
  export const scopeSection = (stores: MemoryStore | readonly MemoryStore[]): string => {
    const list = Array.isArray(stores) ? [...stores] : [stores];
    const dirs = list.map((s) => `\`$WORKSPACE/memories/${s}/\``).join(" and ");
    return `## Scope\n\nYou can read files anywhere in the workspace (needed for validation and deduplication). Only create or modify files within ${dirs}. You have no delete tool: when a file must go away (merged into another, obsolete, or misnamed), overwrite it with empty content — empty files are cleaned up automatically after you finish.`;
  ```

#### Step 2: Add `LEARNINGS_EXTRACTION_SECTION` and generalize `SILENT_BACKGROUND_SECTION` in `extraction.ts`

- Modify: `src/extensions/memory/extraction.ts`
- What to do:
  - Generalize `SILENT_BACKGROUND_SECTION(store: MemoryStore)` to `SILENT_BACKGROUND_SECTION(stores: MemoryStore | readonly MemoryStore[])` the same way as `scopeSection`, so its "create or modify files under …" clause lists every store the fork writes.
  - Add a `LEARNINGS_EXTRACTION_SECTION` constant (folded into the topics instruction) defining, per spec R5/R6/R12 and design S4/S5:
    - **Boundary**: recurring friction, hard constraints, repeated failures, self-reflections about what worked / dead ends → `memories/learnings/`; one-time events (a single bug fix, an outage) stay episodic and are NOT learnings; never restate a topic or a context file.
