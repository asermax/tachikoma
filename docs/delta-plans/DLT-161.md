#### Step 1.4: Cycle detection in `composition.py`

- Modify: `src/tachikoma/workflows/composition.py`
- What to do:
  - Add `detect_cycles(workflows: dict[tuple[str, str], WorkflowDefinition]) -> list[list[tuple[str, str]]]` — pure function returning a list of strongly-connected components (each SCC is a list of vertices). A single self-loop is one SCC of size 1; a mutual cycle A↔B is one SCC of size 2. Callers flatten across SCCs to get the full rejection set.
  - Use three-color DFS (WHITE/GRAY/BLACK). When a GRAY vertex is encountered, mark every vertex on the current DFS stack from that vertex onward as one SCC. Self-loop (vertex points to itself) is detected on the first DFS recursion.
  - Build the adjacency map by iterating each workflow's steps, calling `resolve_composes` for any step with `composes`, skipping steps whose target raises `ValueError` (those are caught later in reference validation).
- Test: `tests/test_workflow_composition.py::TestDetectCycles` — graphs (a) acyclic A→B→C, (b) self-loop A→A, (c) two-cycle A→B→A, (d) cycle plus dangling acyclic branch (only cycle members returned).

```python
from tachikoma.workflows.composition import detect_cycles, validate_references

def _validate_deps(self) -> None:
    # New: composition graph validation runs BEFORE depends_on / required_skills checks
    sccs = detect_cycles(self._workflows)  # list[list[(skill, workflow)]]
    cycles_flat: set[tuple[str, str]] = set()
    for scc in sccs:
        cycles_flat.update(scc)
        _log.warning("Composition cycle detected, rejecting: cycle={members}", members=scc)
    bad_refs = validate_references(self._workflows, already_rejected=cycles_flat)
    rejected = cycles_flat | bad_refs
    for key in rejected:
        self._workflows.pop(key, None)

    # ... existing depends_on / required_skills validation continues unchanged ...
```

#### Step 2.5: Add `abort_cascade`

- Modify: `src/tachikoma/workflows/repository.py`
- What to do:
  - `abort_cascade(root_id: str) -> list[str]` — atomic. In a single `async with self._session_factory() as db:` + `async with db.begin():` block, walk descendants (re-using a private helper that issues SELECTs against the open session, no nested transactions), collect IDs, then issue UPDATEs setting `deleted_at = now` for every record. Returns the soft-deleted IDs in root-first order.
  - Internal walk uses the same session — must NOT call back into `get_active_chain` (which opens its own session). Inline the descendant walk.
  - Idempotent on already-deleted: if `root_id` is already soft-deleted (i.e., the initial SELECT for the root with `deleted_at IS NULL` returns nothing), returns `[]` and the transaction is a no-op. The frontier walk filters every layer on `deleted_at IS NULL`, so dangling soft-deleted records do not propagate to descendants.
  - **Orphaned-child semantics** (corruption case): if `root_id` is soft-deleted but a child record's `parent_workflow_id` still points to the deleted root and the child's `deleted_at IS NULL`, this represents corruption. `abort_cascade(root_id)` returns `[]` (root not found) and does NOT walk to the orphan child — the orphan persists. Surfacing this is out of scope for this delta; if it occurs in practice, stale cleanup will eventually remove the orphan via the subtree-aware staleness logic. Document this behavior in the docstring.
