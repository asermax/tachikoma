#### Step 4: Add migration runner function

- Modify: `src/tachikoma/database_migrations.py`
- What to do: Add an async `run_pending_migrations(engine: AsyncEngine) -> None` function. Implementation follows the design's data flow:
  ```python
  # In database_migrations.py, add:

  # Module-level logger per DES-002
  _log = logger.bind(component="database")

  async def run_pending_migrations(engine: AsyncEngine) -> None:
      # 1. Ensure schema_migrations table exists
      #    CREATE TABLE IF NOT EXISTS schema_migrations (revision VARCHAR PK, name VARCHAR, applied_at DATETIME)
      #    Use engine.begin() for this DDL operation

      # 2. Query applied revisions: SELECT revision FROM schema_migrations
      #    Use engine.connect() for read-only query

      # 3. If no revisions applied (first run):
      #    a. Check if 'sessions' table exists via:
      #       SELECT name FROM sqlite_master WHERE type='table' AND name='sessions'
      #    b. Stamp "001" as applied (INSERT INTO schema_migrations) without executing SQL
      #    c. Log: "Schema initialized ({fresh|existing} install). Migration 001 stamped."
      #       Use install_type variable: "existing" if sessions exists, "fresh" otherwise
      #    d. Re-query applied revisions

      # 4. Diff: [m for m in MIGRATIONS if m.revision not in applied_set]
      #    If no pending: log "Schema is up to date" and return

      # 5. For each pending migration (in MIGRATIONS list order):
      #    a. Load SQL file via:
      #       importlib.resources.files("tachikoma").joinpath(m.sql_path).read_text("utf-8")
      #    b. Split SQL on ";\n" pattern, strip each chunk, filter empty strings
      #    c. Execute in its own transaction:
      #       async with engine.begin() as conn:
      #           for statement in statements:
      #               await conn.execute(text(statement))
      #           await conn.execute(text(
      #               "INSERT INTO schema_migrations (revision, name, applied_at)"
      #               " VALUES (:rev, :name, datetime('now'))"
      #           ), {"rev": m.revision, "name": m.name})
      #    d. Log: "Applied migration {revision}: {name}"
      #    e. On failure: engine.begin() auto-rolls back the transaction
      #       Raise RuntimeError(f"Migration {m.revision} ({m.name}) failed: {e}") from e
  ```
  SQL splitting approach: split on `;\n` (semicolon + newline), strip each chunk, filter empty strings. This is sufficient for DDL statements (ALTER TABLE, CREATE TABLE) which never contain semicolons in string literals. For the rare case of data-migration SQL with string literals containing semicolons, migration authors should use parameterized queries via the Python runner rather than raw SQL files.
- Test: Module imports, function is callable, signature matches. Run a quick smoke test: create a temp database, call `run_pending_migrations(engine)`, verify `schema_migrations` table exists and "001" is stamped.

      import tachikoma.app_state  # noqa: F401, PLC0415

## Notes

- SQLite's transactional DDL means all DDL statements participate in transactions — no special handling needed for CREATE/ALTER/DROP
- `CREATE TABLE IF NOT EXISTS schema_migrations` is idempotent — safe to call every startup
- The `sessions` table is the oldest and most fundamental table, guaranteed to exist in any non-fresh database — used for fresh/existing detection
- `importlib.resources.files()` is used for SQL loading to support packaged installations where source tree doesn't exist
- SQL splitting approach: split on `;\n` (semicolon + newline), which is sufficient for DDL statements that never contain semicolons in string literals. For complex data-migration SQL with string literals, use parameterized queries in the Python runner.
- Test migrations in Batch 3 are created dynamically via `tmp_path` and `mocker.patch` on `MIGRATIONS` — no permanent test fixture files needed
- MIGRATIONS ordering is by position in the list — developers add new entries at the end. No sorting or chain validation needed for forward-only migrations.
