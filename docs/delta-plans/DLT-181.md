### Plan-phase decisions (resolved here, per design Open Questions)

- **Command-handler home**: `/checkpoint`, `/back`, `/rollback` live in the **boundary extension** (`src/extensions/boundary/`), for cohesion with the classifier + collapse machinery. Rollback reuses boundary's `collapseCurrentTopic`. They register as inbound command-detection middleware (same pattern the `commands` extension uses for `/new`).
- **Rollback `triggeringMessageId` realization**: the user-message entry does not exist at classification time (the classifier runs in inbound middleware, before the turn). `lastAutoDecision` stores `{ kind, preDecisionLeafId }` (the leaf *before* the triggering exchange). At rollback, the triggering message is **read from the tree** (the first user entry after `preDecisionLeafId`) and immediacy is verified by a tree walk (exactly one user→assistant exchange between `preDecisionLeafId` and the current leaf). This is more robust than the design's literal `triggeringMessageId` field and is restart-safe (state is on the tree).
- **Decision header on command acks vs streamed responses**: manual commands (`/checkpoint`, `/back`) ack immediately (no agent turn, no stream), so their header label is baked into the ack delivery text. The `StreamRenderer.header` anchored-prefix mechanism (KD9) serves decisions that **do** stream — automatic checkpoint decisions (Batch 3) and rollback replay (Batch 4) — where the header must survive `editMessageText` recomposition.
- **`getBranchRecords` is the single kind-filter chokepoint**: filtering `tangent`+`reversed` records there automatically serves `ask_branch`, related-branch matching, and memory extraction — keeping `topic-N` ids clean (KD3). A separate `getAllBranchRecords` (unfiltered) exists for the tangent counter and rollback target lookup.

## Batch 4: Rollback `/rollback` — ⧗ Pending
Depends on: Batch 1, Batch 2, Batch 3 (needs `lastAutoDecision` recorded on automatic decisions)

R7 — the load-bearing flow (KD4). Reverses the most-recent *automatic* `set-checkpoint`/`new` decision in exactly two cases by rewinding to the pre-decision tip, applying the opposite transition, and replaying the triggering message. Append-only — the wrong-framing exchange goes off-path, not deleted.

### Context & Research

- Design KD4 (rollback = `branch(id)` re-seat + opposite transition + replay, no deletion), KD5 (decision state on the tree), KD6 (`reversed` marker)
- `docs/reference/pi-sdk-notes.md` — **load-bearing**: `branch(entryId)` re-seats the active leaf backward (the sanctioned tip-move; no delete primitive exists). The wrong-framing exchange becomes an inert off-path branch. Re-verify on pi upgrade.
- `src/agent/session-tree.ts` — `reseatLeaf` (wraps `branch(id)`), `getBranch`/`getEntries` for the immediacy tree-walk and to read the triggering message text
- `src/sessions/trunk.ts` — `lastAutoDecision` (Batch 1), `markReversed`/`effectiveKind` (Batch 1), `setCheckpoint`/`clearCheckpoint`
- `src/extensions/boundary/{index,collapse}.ts` — `collapseLiveBranch`/`collapseCurrentTopic` reused for Case A's topic transition
- `src/coordinator.ts` — `handle()`/`submit()` internals to add `replay()` (a fresh turn bypassing pending-input, command parsing, and boundary classification)

### Steps

#### Step 1: Rollback eligibility + immediacy check

- Create: `src/extensions/boundary/rollback.ts`
- What to do: read `lastAutoDecision` from the trunk. No-op + notice ("Nothing to roll back") when:
  - `lastAutoDecision` is `null`, or `kind ∉ { "set-checkpoint", "new" }` (manual/`continue`/`summarize-to-checkpoint`), or
  - not immediate — count **user-message entries** (not infrastructure entries like `branch_summary`) between `preDecisionLeafId` and the current leaf; more than one (a later user turn happened) ⇒ no-op. Counting user messages avoids false negatives when a summarize/summary was appended since the decision without a new conversational turn.
  - The triggering message is read from the tree: the first user entry after `preDecisionLeafId` (its text is what gets replayed).
  - Re-validate the decision's preconditions and no-op if they no longer hold — e.g. a `set-checkpoint` target whose checkpoint has since been consumed/cleared by a summarize, or a `new` target whose topic summary has been further mutated. (The boundary between "still reversible" and "stale" is finalized here; default to no-op on ambiguity.)
- Test: unit — each no-op branch returns a notice; an eligible snapshot (single exchange past `preDecisionLeafId`) proceeds; restart resilience (state is on the tree, so a restart between decision and `/rollback` with no further exchange still rolls back).

#### Step 2: Rewind via `reseatLeaf`

- Modify: `src/extensions/boundary/rollback.ts`
- What to do: `reseatLeaf(session, preDecisionLeafId)` — moves the active tip back before the triggering exchange; the wrong-framing M + assistant response becomes an inert off-path branch (append-only; not deleted, not re-extracted).
- Test: integration — after reseat, the leaf is `preDecisionLeafId`; the off-path exchange is no longer on the active path and is not an extraction target.

#### Step 3: Opposite transition — Case A (`set-checkpoint` → topic)

- Modify: `src/extensions/boundary/rollback.ts`
- What to do: reuse `collapseLiveBranch`/`collapseCurrentTopic` to collapse the branch up to the tip as a **topic** summary. The replayed message becomes the new topic's first turn (re-answered under the topic framing).
- Test: integration — Case A produces a topic collapse; header "🔄 Rolled back to topic".

#### Step 4: Opposite transition — Case B (`new` → checkpoint) + `reversed` marker

- Modify: `src/extensions/boundary/rollback.ts`
- What to do: `setCheckpoint(session, preDecisionLeafId)`; `markReversed(session, <the auto-`new`'s summary entry id>)` so the orphaned topic summary is excluded from extraction and branch-query (effective kind `"reversed"`). The replayed message becomes the first tangent turn.
- Test: integration — Case B sets a checkpoint + marks the summary `reversed`; `effectiveKind` is `"reversed"`; `getBranchRecords`/extraction skip it; header "🔄 Rolled back to checkpoint".

#### Step 5: Clear decision state + `Coordinator.replay(text)`

- Modify: `src/extensions/boundary/rollback.ts`, `src/coordinator.ts`
- What to do:
  - Clear `lastAutoDecision` (write boomerang-state) once the reversal is staged.
  - Add `Coordinator.replay(text)`: construct a synthetic `InboundMessage` (mirror the queue-flush/system message shape in `coordinator.ts`) with `metadata: { origin: "system", boundary: "skip" }` and route it through the `handle()` turn path directly — **not** `submit()`, so it skips pending-input, command parsing, and prefix-stripping; `boundary: "skip"` keeps the classifier from re-classifying (the corrected framing is already applied; the message runs as a plain `continue` turn).
- Test: integration — `replay` re-answers the triggering message under the corrected framing; the response carries the rollback header (renderer-anchored); pending-input does not intercept it.

#### Step 6: `/rollback` command handler + end-to-end

- Modify: `src/extensions/boundary/index.ts`
- What to do: command-detect `/rollback` at the top of the boundary middleware → run the rollback orchestration (Steps 1–5); set the decision header on the replayed streamed response; the command itself sets `handled` only in no-op cases (where it acks the notice), otherwise the replayed turn produces the streamed response.
- Test: end-to-end — Case A and Case B roll back correctly; no-op cases surface "Nothing to roll back"; only the single most-recent qualifying auto decision is the target; wrong-framing exchange is not re-extracted at trunk close (KD6/KD7).

## Notes

- **Append-only is load-bearing and pi-upgrade-sensitive** (KD4, ADR-014): rollback relies on `branch(id)` re-seat and the absence of a delete primitive. Re-verify `pi-sdk-notes.md` on every pi upgrade.
- **`lastAutoDecision` shape refinement**: stored as `{ kind, preDecisionLeafId }`; the triggering message text is read from the tree at rollback (the user entry does not exist at classification time). Immediacy = exactly one triggering exchange between `preDecisionLeafId` and the current leaf.
- **Batch 1 realized**: `effectiveKind(session, summaryEntryId, kind?)` — takes the summary entry id + persisted `details.kind` (default `"topic"`), not a `BranchRecord`, because `BranchRecord` deliberately carries no kind field (the filter runs during enumeration from `details` + the reversal scan). `getBranchRecords` is the kind-filter chokepoint (excludes tangent + reversed, assigns clean `topic-N`); `getAllBranchRecords` returns all summaries (internal); `nextTangentId` counts tangents on their own sequence. `collapseTangent`/`checkpointHasTangent` live in `src/agent/session-tree.ts` (the latter imports `BRANCH_SUMMARY` from `trunk.ts` — a benign function-body-only ESM cycle). Checkpoint lifecycle (`setCheckpoint`/`clearCheckpoint`/`recordLastAutoDecision`/`clearLastAutoDecision`) is in `trunk.ts` via a private `patchBoomerangState`. `collapseCurrentTopic` now clears `checkpointId` and preserves `lastAutoDecision` on the shift snapshot. `TrunkInbound` gained `checkpointId`/`checkpointActive`/`lastAutoDecision`, populated in `buildTrunkInbound`.
- **Batch 2 corrected `checkpointHasTangent` (a Batch 1 latent bug)**: pi's `appendCustomEntry`/`_appendEntry` sets `this.leafId`, so `setCheckpoint`'s boomerang append advances the leaf *past* the checkpoint message. The Batch 1 `checkpointHasTangent = getLeafId !== checkpointId` would therefore report a phantom tangent after every `/checkpoint`. Batch 2 redefined it to walk the leaf path for a real message turn (mirroring `hasAssistantTurnSinceBase`): `branchEntriesSinceBase(session, checkpointId).some(e => e.type === "message")`. The `/checkpoint` idempotent-at-tip check is now `checkpointId != null && !checkpointHasTangent(session, checkpointId)` (not a raw leaf-id compare). Batches 3/4 must use `checkpointHasTangent` (not leaf-id compares) for any "is there a tangent" decision.
- **Batch 2 realized**: `DecisionHeader {label, note, rollbackable}` + `decisionHeaderFrom(metadata)` in `src/domain/message.ts`; `Exchange.header?` in `src/channels/types.ts`; coordinator forwards `decisionHeaderFrom(message.metadata) ?? undefined` to `respond` (turn-scoped). `StreamRenderer.setHeader` + `compose()`/`finalize()` prepend the header (best-effort dropped + logged when the body exceeds the edit limit, or on a render failure — `commitOverflow` is unchanged because `compose` drops the header before overflow ever triggers). Manual `/checkpoint`,`/back` live in `src/extensions/boundary/commands.ts` (`handleCheckpointCommand`/`handleBackCommand`), wired at the top of the boundary inbound middleware (before the classifier); both set `handled=true` + ack via `app.channels.deliver({text, immediate:true})` and never set `decisionHeader`. `summarizeCurrentTangent` (collapse.ts) generates the tangent summary via `side.complete` over `branchEntriesSinceBase(session, checkpointId)`, calls `collapseTangent`, and `clearCheckpoint`s — reused by Batch 3's auto `summarize-to-checkpoint`.
- **Sibling delta DLT-182** (`open_branch`/`message_branch`/`close_branch`) must agree tangents + reversed records are not branch-query targets — already guaranteed by the `getBranchRecords` chokepoint filter (KD3).
- **Detection quality is empirical** (Open Question): the conservative prompts + per-result kill-switch bound the risk; a classification-quality eval/tuning pass should follow implementation.
- The checkpoint model replaced an earlier "parked sub-session" idea during speccing; checkpoints reuse `branchWithSummary`/`branch` with no sub-session juggling.
