# Implementation Plan: DLT-172 — Unified topic-oriented memory store

**Delta Spec**: [../delta-specs/DLT-172.md](../delta-specs/DLT-172.md)
**Delta Design**: [../delta-designs/DLT-172.md](../delta-designs/DLT-172.md)
**Status**: Not Started

## Overview

Collapse the separate `facts/` and `preferences/` memory stores into a single topic-oriented store at `memories/topics/`, where each `<topic>.md` holds everything known about a subject. Eliminate the facts-vs-preferences classification/routing boundary in extraction and maintenance, unify the static index injection into a single Topics Index, and add a one-time, self-detecting, idempotent migration that folds legacy stores into topics with no data loss.

Episodic memory and transcript archives are unchanged (R8). Richer phased consolidation is deferred to DLT-173 (R5).

### Key implementation constraint — the store model is a type-interlocked wave

`MemoryStore` (in `layout.ts`) is a union, today `episodic | facts | preferences`. Narrowing it to `episodic | topics` **simultaneously breaks** `layout.ts`, `indexes.ts` (`STORE_DESCRIPTIONS: Partial<Record<MemoryStore>>` — excess-property check), `extraction.ts` (`STORE_INSTRUCTIONS: Record<MemoryStore>`), and `maintenance.ts` (`STORE_LABELS`, `basePrompt`'s `store === "facts"` comparisons). These modules plus `prompts.ts` (which extraction and maintenance import) **must change together** — there is no compile-green way to split the type narrowing. Batch 1 is therefore one cohesive unit, not arbitrarily grouped.

### No external libraries (design KD7)

This is an internal store-model restructuring. It reuses already-validated infrastructure (`SideRunner`, `app.git`, `node:fs`, the legacy migration state-detection idiom). **No `katachi:research-docs` dispatch is required** — there is no external library whose currency could affect the design.

## Batch 3: One-time memory-store migration — ⧗ Pending

Depends on: Batch 1 (needs the topics store + shared fold conventions + `storeDir`/`sweepEmptyMarkdown` + `SideRunner`/`app.git` reuse). Independent of Batch 2.

A one-time, self-detecting, idempotent agent-driven fold of legacy `facts/` + `preferences/` into `topics/`, with no data loss. Design part **S7**, decisions **KD4–KD6**.

### Context & Research

- **Spec R7** ([delta-spec](../delta-specs/DLT-172.md)) — all migration ACs: runs once at startup; same-subject files across both old stores merge, distinct stay distinct; **fold-before-empty** (no data loss); git is the backup; self-detecting + idempotent (runs while old stores hold any non-empty `.md`, no-op once empty); interruption re-runs cleanly; per-file failure isolation; empty files skipped; first session sees migrated topics; auditable summary; no-op on fresh installs and already-migrated workspaces.
- **Design S7 + KD4–KD6** ([delta-design](../delta-designs/DLT-172.md)) — bootstrap hook before `init-memory-layout`; state-based detection keyed on **old-content presence** (not `topics/` presence — that would false-"done" after a mid-fold crash); one agent run over all old files; two commits bracket the sweep (fold → commit → sweep → commit); soft failure (skip+retry) vs hard failure (abort without sweeping); no persisted marker — empty-old-stores is the done signal.
- **`src/app.ts:57–127`** — startup ordering: legacy migration (57) runs before the `AgentManager` exists (69), so the agent-driven fold cannot live there; `host.bootstrap()` (98) runs after the agent is ready and before `channel.start()` (127) → the only seam that satisfies R7's first-session AC.
- **`src/extensions/host.ts:127–153`** — bootstrap hooks run in **registration order** (a `for…of` over the regs array), so registering `migrate-memory-stores` before `init-memory-layout` in `setup()` guarantees the fold creates topic files before the layout hook seeds/preserves their index.
- **`src/extensions/api.ts`** — `app.agent.side` (SideRunner), `app.git.createCommitAgent("workspace")` + `app.git.commitAll(...)`, `app.workspace.root`, `app.log`.
- **`src/migration/drop-sessions-table.ts` + `src/migration/context.ts`** — the state-detection idiom to mirror (detect work by filesystem/DB state, not a persisted flag; self-detecting + idempotent; fast no-op when already done).
- **`src/extensions/memory/index.ts`** — the existing `commitChanges` closure (inside the `maintenance.enabled` block) and the `init-memory-layout` bootstrap registration — the wiring site and the commit pattern to reuse/lift.
- **Batch 1 outputs** — `storeDir(ws, "topics")`, `sweepEmptyMarkdown` (and its blank threshold), shared `INDEX_UPDATE_SECTION` + broad-topic-naming conventions. **`FILE_EDIT_TOOLS`** (`src/agent/file-tools.ts`) is the file-ops-only tool allowlist (`read`/`grep`/`find`/`ls`/`edit`/`write`) already used by the maintenance/extraction side-runs — the migration reuses it so the fold agent can read and write topic/old-store files but cannot message users or fire tasks.

### Out of scope

- Running the migration against a real LLM in CI (tests use a mocked `side.run`); reconciling feature docs (deferred to `/katachi:land-delta` / `/katachi:reconcile-delta`).

### Steps

#### Step 1: Create the migration module `migration.ts`

- Create: `src/extensions/memory/migration.ts`
- What to do — export `migrateMemoryStores(deps)` where `deps = { side: Runner; workspaceRoot; log; commitChanges }`:
  - **Detection (state-based, no marker):** a helper that scans `memories/facts/` and `memories/preferences/` for any non-empty `.md`, reusing the `sweepEmptyMarkdown` blank threshold (`size === 0 || (size <= 64 && content.trim() === "")`). Treat a missing dir (ENOENT) as empty. If no non-empty old file is found → log + return (no-op: fresh install or already migrated).
  - **Fold (one agent run):** build a system prompt (inline, feature-local per DES-005; reuse the shared `INDEX_UPDATE_SECTION` and broad-topic-naming wording from `prompts.ts`) instructing the agent to:
    1. read **all** old `facts/` + `preferences/` files, plus any existing `topics/` files;
    2. fold durable content into broad topic files — **same-subject files across the two old stores merge into one** topic file; distinct subjects stay distinct;
    3. use broad-topic naming and merge/dedup so a re-run after an interrupted pass never duplicates;
    4. skip empty/unreadable old files (soft failure: leave the file in place so it retries next run);
    5. update `topics/MEMORY.md` per `INDEX_UPDATE_SECTION` (write full descriptions, not placeholders).
    Run via `side.run({ tools: FILE_EDIT_TOOLS, system, prompt, tier: "processor" })`.
  - **Detection threshold stays in sync with sweeping** by construction: the non-empty check reuses `sweepEmptyMarkdown`'s exact blank threshold (`size === 0 || (size <= 64 && content.trim() === "")`), so "what counts as content" and "what gets swept" can never drift.
  - **Fold-before-empty + two commits:** `commitChanges("chore(memory): migrate facts+preferences into topics")` **before** any old store is touched; then `sweepEmptyMarkdown(factsDir)` + `sweepEmptyMarkdown(prefsDir)` (and `rmdir` the now-empty old dirs); then `commitChanges("chore(memory): sweep emptied legacy memory stores")`.
  - **Hard failure:** wrap the fold `side.run` in try/catch; on error, log and **abort without sweeping or sweeping-commit** so the old stores still hold content and the whole pass retries next startup. (Soft per-file failures are handled inside the agent prompt.)
  - **Auditable summary:** log old facts/preferences file counts → topic files produced.

#### Step 3: Migration tests `migration.test.ts`

- Create: `tests/memory/migration.test.ts`
- What to do — real temp workspaces + a mocked `side.run` + a spy `commitChanges`:
  - **No-op on fresh install** (no `facts/`/`preferences/`) — `side.run` not called, no commits.
  - **No-op when already migrated** (`topics/` present, old stores empty/absent).
  - **Detection keys on old content, not `topics/` presence (KD6)** — `topics/` present **with** files but old stores empty → still a no-op (`side.run` not called, no commits). This is the case that would false-"done" if detection keyed on `topics/` presence instead of old-store content; it guards the interrupted-fold re-run guarantee.
  - **Happy path** — `facts/` + `preferences/` files present → `side.run` called once with a fold prompt naming both old dirs and `topics/`; old files are swept (gone) afterward.
  - **Two commits in order (fold-before-empty)** — assert **exactly two** `commitChanges` calls, in order: first `"...migrate facts+preferences into topics"` (fold), then `"...sweep emptied legacy memory stores"`; the fold commit precedes any sweep/filesystem mutation, and no third commit fires.
  - **Idempotent re-run** — after a run, a second `migrateMemoryStores` call is a no-op (old stores now empty).
  - **Interruption re-run** — simulate a mid-fold crash (old content still present) → re-run calls `side.run` again (merge/dedup is the prompt's job).
  - **Hard failure** — `side.run` rejects → no sweep, **no sweep-commit**, old files untouched (still present); error handled (no throw out).
  - **Empty old file** — a 0-byte/whitespace-only old file does not trigger the migration and creates no topic file.
  - **Detection specificity** — a `.txt` or empty `.md` in the old dirs does not count as content.
