- What to do: implement the design's contract:

```ts
// src/sessions/branch-walk.ts — neutral walk skeleton shared by memory and skill-evolution (R2).
export interface BranchWalkDeps {
  agent: Pick<AgentManager, "forkAndContinue" | "branchFile">;
  body: (record: BranchRecord, branchFilePath: string) => Promise<void>; // caller's forks/sweeps
  isDone: (session: AgentSession, record: BranchRecord) => boolean;
  markDone: (session: AgentSession, record: BranchRecord) => void;
  log: Logger;
  /** Raw status surface for any caller-shaped line (the processor's `status` callback). */
  status?: (text: string) => void;
  /**
   * Caller-shaped per-branch progress lines. Memory's three templates ("Extracting branch
   * i/n…", "Extracted branch i/n", "Branch i/n failed — will retry" — asserted verbatim in
   * tests/memory/close-pipeline.test.ts) and skill-evolution's ("Analyzing skills — branch
   * i/n") are different shapes, so a single label string cannot reproduce them. `failed`
   * fires only when a branch errors; `start`/`done` bracket a completed body.
   */
  progress?: {
    start: (i: number, n: number) => string;
    done: (i: number, n: number) => string;
    failed: (i: number, n: number) => string;
  };
}
export function walkBranches(
  session: AgentSession,
  sessionFile: string,
  records: BranchRecord[],
  day: string,
  deps: BranchWalkDeps,
): Promise<{ failed: BranchRecord[] }>;
```

  The walk owns: skip-if-marked; the `branchFile(sessionFile, record.originalLeafId)` cut (`undefined` ⇒ warn + skip the branch, not a failure); per-branch error isolation into the returned `failed` list; `finally { rm(branchFilePath, { force: true }) }` after the body settles; `markDone` only after the body completes; 1-based progress via the caller's `progress` templates. The body and the marker key stay caller-supplied. (Plan-level deviation from the design's `statusLabel: string` contract — see Notes.)
- Test: `tests/sessions/branch-walk.test.ts` with a structural fake `agent` (`vi.fn()` `branchFile`/`forkAndContinue`) and in-memory marker pair — asserts skip-if-marked, cut-failure skip, settle-then-delete ordering (body promise observed before `rm`), marker-after-body, failure isolation across branches; plus the concurrency case — two `walkBranches` calls over the same session file with independent fake agents run concurrently → both complete, both marker sets land, neither deletes the other's branch file (the mechanism-level backing for the memory∥skill-evolution AC; safe by the detached-manager design, asserted here so it stays true).

### Steps

#### Step 1: Scoped proposal tools

- Create/modify: `src/extensions/skill-evolution/propose.ts` (new)
- What to do: `buildProposalTools({ workspaceRoot, tmpDir, defaultBranch, remoteBranchNames })` returning five `ToolDefinition`s (`remoteBranchNames` — an injected `() => Promise<Set<string>>` backed by `listRemoteBranchTips` — is what the push-time existence check consults):
  - `read_file` / `write_file` / `list_dir` — every path `resolve`d and refused unless it lands under `tmpDir` (the `resolve.ts` shape); this is what confines edits to the worktrees
  - `git` — allowlist exactly: `worktree` (`add` with a path under `tmpDir` and `-b` matching `^skill-evolution/[a-z0-9][a-z0-9-]*$`, or `remove`), `status`, `diff`, `log`, `show`, `add`, `commit` (with editor/gpg disabled); `push` accepts only `origin <name>` where the name matches the regex, is not the default branch, carries no force flag, and — checked at push time via the injected remote-view — does not already exist on the remote; every refusal returns instructive text (the agent retries with a suffix, executing the collision rule itself). The `git` tool takes an optional `path` parameter validated under `tmpDir` exactly like the file tools and runs with that directory as `cwd` (`runGitCapture(path ?? workspaceRoot, args)`) — that is how the agent targets a specific worktree, never `-C` string surgery
  - `report_proposals(proposals: [{ branch, skill, pattern, description }])` — terminal step; the execute handler writes into a closure variable the host reads after the run (the tasks `update_goal` idiom)
- Test: `tests/skill-evolution/propose.test.ts` — refusal matrix: path escapes, non-allowlisted subcommand, bad branch name, default-branch push, force push, existing remote branch (fake remote view), and the happy path for each allowed subcommand; `report_proposals` captures its argument into the closure.

- What to do: `verifyAndRecord({ workspaceRoot, tmpDir, reported, defaultBranch, now, log, store deps })` (`now` injects the impact-log row's `date`), entirely `try/finally`:

```ts
// process({ trunk, log, status }) — stage order per the design's Data Flow. The whole body
// sits in ONE fail-soft try/catch (catch → log.warn + emit(NOTIFY_EVENT,
// { text, severity: "warning", source: "skill-evolution" }); never rethrow):
// 1.  trunk == null → return (headless no-op)
// 2.  !hasRemote(workspaceRoot, "origin") → log "skipped: no origin" + return (R15; no writes)
// 3.  reconcile → soft-abort (fetch / default-branch failure) → log.warn + emit the same
//     warning notification + return — nothing classified, no analysis (the design's
//     fetch-failure scenario: "logged and notified")
// 4.  analyzeBranches (shared walk, summaryEntryId markers) — log failed branches, continue
// 5.  runMaintenance (side.run maintenance pass)
// 6.  eligible = filterEligible(listPatternPages(...), impactLog); empty → done (no LLM call)
// 7.  proposalError = null; try { reported = await runProposalAgent(...) }
//     catch (e) { proposalError = e }   // a proposal-stage death must NOT skip verification:
//                                        // pushed branches still get verified, logged,
//                                        // swept, and reported (R8/R10 partial-failure ACs)
// 8.  verified = await verifyAndRecord(...)  // ALWAYS runs after 7; own try/finally sweep
// 9.  verified.length >= 1 → reportRun (dispatch event; R10)
// 10. if (proposalError != null) throw proposalError   // boundary wrapper warns + notifies
// status lines: "Reconciling skill proposals…", "Analyzing skills — branch i/n",
//               "Verifying N proposals…"
```
